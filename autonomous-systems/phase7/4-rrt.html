Phase 7 · Lesson 4

Sampling planners: RRT & RRT*

Grids die in high dimensions: a robot arm with six joints would need a trillion cells. So stop building the grid. Throw random darts at the space, grow a tree toward them, and you'll find a path surprisingly fast. Then rewire the tree as you go, and the path keeps getting better.

🧰 You'll need (quick reminders)
  • Grid search: A* expands cells of a grid toward the goal (Lesson 7.2). Its cost grows with the number of cells.
  • Configuration space: the list of numbers that pins down the robot. A car in a lot: (x, y, heading) = 3 numbers; a drone: position + yaw = 4; a 6-joint arm: 6 joint angles. Each number is one dimension.
  • Random sampling: drawing points uniformly at random from a region. Refresher: sampling in the Math course.
🎯 Hook · a puzzle first

You want to plan for a robot arm with 6 joints, and you'd like each joint split into 100 steps, like a fine grid. How many cells is that? A million? A billion? And if your computer checks 10 million cells a second, how long does one search take? Guess, then check the first playground.

In 1998 Steven LaValle proposed a way out: the rapidly-exploring random tree (RRT), which never builds the grid at all (LaValle 1998). In 2011 Karaman and Frazzoli showed that plain RRT's path quality stops improving, and fixed it with RRT*, which provably converges to the shortest path (Karaman & Frazzoli). Today OMPL, a library of these planners, is the default planning library in MoveIt, the ROS framework for robot arms (OMPL).

The RRT idea, in four lines

  1. Sample a random point in the space (sometimes, with probability called the goal bias, just pick the goal).
  2. Nearest: find the tree node closest to that point.
  3. Steer: take one step of at most η (the step size) from that node toward the point.
  4. Check and add: if the little segment is collision-free, add the new node, with the old one as its parent. Stop when a node lands near the goal.

Why does such a dumb rule explore well? Because the nodes most likely to be “nearest” to a random point are those on the frontier, next to big empty regions: a big empty area catches more random darts. The tree is pulled outward into unexplored space, like roots growing toward water. That's the “rapidly exploring” part.

✏️ Worked example: one RRT step by hand

Tree so far: A = (2, 9) (the start) and B = (3.5, 9). Step size η = 1.5 m. A random sample lands at S = (6.5, 13).

  1. Nearest: distance A→S = √(4.5² + 4²) = 6.02; B→S = √(3² + 4²) = 5.00. B wins.
  2. Steer: direction B→S = (3, 4) ÷ 5 = (0.6, 0.8). One step: B + 1.5 × (0.6, 0.8) = (4.4, 10.2).
  3. Check: test points along B → (4.4, 10.2) against obstacles (the playgrounds check every 0.15 m). Free? Add node C = (4.4, 10.2) with parent B. Its cost-from-start is 1.5 + 1.5 = 3.0 m.
  4. RRT* extra: look at all nodes within a radius of C. If one offers a cheaper route to C (cost to it + distance to C), make it C's parent instead. Then, for each neighbour, if going through C is cheaper for it, re-parent the neighbour to C: that's rewiring.
💡 Big idea Sampling planners replace “check every cell” with “check random points and the segments between them”. The work grows with the number of samples you take, not with how many cells a grid would have, so the same 30-line algorithm plans for a 2D robot, a 4D drone or a 7-joint arm. RRT finds a path quickly (and, given enough samples, will find one if it exists: probabilistic completeness). RRT* keeps improving it toward the shortest (asymptotic optimality).
🧠 Analogy: exploring a dark cave with a ball of string

You can't map the whole cave first. So you pick a random direction, walk a few steps from the nearest point you've already reached, and tie a string there. Do it again and again, and the strings spread into every open chamber, fastest into the biggest ones. When one string reaches daylight, follow it back: that's your path. RRT* is a tidier explorer who, every time they tie a new string, checks whether nearby strings could be shortened by re-tying them through the new knot.

🧩 Predict: on the chart, RRT's line goes flat right after its first path, while RRT*'s keeps falling. Why does plain RRT never improve, even with 10× more samples?
Because a node's parent is fixed forever: the first wiggly branch that reached the goal stays wiggly. New samples only add new branches; nothing goes back and straightens the old ones. Karaman and Frazzoli proved that, under mild conditions, RRT's path cost converges to a non-optimal value with probability one. RRT* fixes it by choosing the best parent among nearby nodes and rewiring neighbours through each new node, at a constant-factor extra cost.
🤔 Why this? (and not something simpler)
  1. The problem before. Grid search is exact but its size is stepsdimensions. A 2D floor at 100 steps per axis is 10,000 cells; a 6-joint arm at the same resolution is 1012: about 28 hours for one sweep at 10 million cells a second, and a terabyte of memory.
  2. What people tried. Coarser grids (miss narrow gaps, Lesson 7.2). Potential fields: obstacles push, the goal pulls (fast, but gets stuck in local minima). Probabilistic roadmaps (PRM): sample many free points, connect neighbours into a graph once, then run A* on it for every query (great when the world doesn't change).
  3. Why this works. RRT only ever checks the points it samples and the short segments between them, so the cost doesn't depend on a grid's size. On this lesson's Forest map, RRT typically finds a path within about 100 samples (a few milliseconds), and RRT* drives it from ~35 m toward ~28.1 m, beating the 0.5 m grid A*'s 29.2 m, because it isn't stuck with 45° moves.
  4. What it costs, when it fails. Results are random: different seeds give different paths. RRT's paths are jagged and never improve; RRT* is slower per sample (neighbour search and rewiring). Narrow passages are the classic failure: the chance that a random sample lands inside a thin gap is tiny (Playground 3). And it plans a geometric path; a car's turning limits or a drone's dynamics need extra care (steering with real motion models, or smoothing afterwards).
  5. What came next. RRT-Connect grows two trees, from start and goal, and is OMPL's go-to for arms; Informed RRT* and BIT* focus samples where a shorter path could still be; kinodynamic RRTs steer with real motion models; smarter samplers (bridge tests, learned samplers) target narrow passages.

The narrow-passage problem

Imagine a 1 m door in a 32 × 18 m room. A uniform sample lands inside the doorway with probability roughly (door area) ÷ (room area), well under 1%, and it has to land there when the tree is next to it. Every robot planner fights this. One elegant fix is the bridge test: pick a point that's inside an obstacle, pick a second one nearby that's also inside an obstacle, and keep their midpoint if it's free. Midpoints between two walls are, by construction, in gaps.

🧰 Tools you'll actually use

OMPL (the Open Motion Planning Library) is the standard: RRT, RRT-Connect, RRT*, Informed RRT*, BIT*, PRM and many more, with C++ and Python bindings. It deliberately contains no collision checker or visualization; you plug in your own validity function. MoveIt uses it for arms; you can call it directly for anything else.

# pip install ompl   (Python bindings for OMPL)
from ompl import base as ob, geometric as og

trees = [(10.0, 9.0, 1.5), (18.0, 6.0, 1.2)]          # (x, y, radius) obstacles
def is_free(state):
    x, y = state[0], state[1]
    return all((x - cx) ** 2 + (y - cy) ** 2 > (r + 0.3) ** 2 for cx, cy, r in trees)

space = ob.RealVectorStateSpace(2)
bounds = ob.RealVectorBounds(2)
bounds.setLow(0, 0.0); bounds.setHigh(0, 32.0); bounds.setLow(1, 0.0); bounds.setHigh(1, 18.0)
space.setBounds(bounds)
ss = og.SimpleSetup(space)
ss.setStateValidityChecker(is_free)
start, goal = space.allocState(), space.allocState()
start[0], start[1], goal[0], goal[1] = 2.0, 9.0, 30.0, 9.0
ss.setStartAndGoalStates(start, goal)
ss.setPlanner(og.RRTstar(ss.getSpaceInformation()))   # or og.RRTConnect, og.InformedRRTstar, og.BITstar
if ss.solve(1.0):                                     # plan for up to 1 second
    ss.simplifySolution()
    print(ss.getSolutionPath())

RRT* is anytime: the longer you let solve run, the shorter the path. On a robot you pick a time budget per replanning cycle, exactly the trade-off on Playground 2's chart.

🚗 How Tesla / Waymo / drones do it

🛸 Drones & arms

Sampling planners shine where the space has many dimensions or full 3D: drone flights through forests and buildings, and robot arms (OMPL is MoveIt's default planning library). Skydio describes its Pathfinder as autonomously planning “the best flight path” while factoring terrain, buildings, geofences, flight policies and airspace rules; it doesn't publish which algorithm. PX4's own built-in feature, Collision Prevention, only slows and stops near obstacles; planning around them runs on a companion computer (PX4's older ROS avoidance planners are archived).

Sources: Skydio Autonomy, PX4 Collision Prevention, PX4-Avoidance (archived), OMPL

🚘 Tesla

Tesla's publicly described planner (AI Day 2021) is a tree search too, but not uniform random sampling: a neural network proposes promising maneuvers and a Monte Carlo tree search expands them (288 nodes on the parking-lot example). That's the same “grow a tree, keep the good branches” idea, with learned sampling instead of random darts.

Sources: Tesla AI Day 2021

🚕 Waymo

Waymo hasn't published using RRT-style planners on its cars. Road driving is structured: lanes give a natural coordinate system, so sampling is usually done along the road (lateral offsets and speeds, Lesson 7.5) rather than uniformly in space. Uniform random trees fit open, unstructured spaces better than lanes.

Sources: Waymo research (no RRT planner published)

Why they differ: a drone or an arm lives in open, high-dimensional space with no lanes, where random sampling is the natural way to explore. Cars live on roads, where structure (lanes, rules) gives better samples than randomness, so they sample along the road or learn where to look. RRT's randomness is also harder to certify for a car: two runs can give two different paths.

🎤 Interview angle

“When would you use RRT instead of A*?” A strong answer:

  • High-dimensional or continuous spaces (arms, drones in 3D, car poses with dynamics), where a grid is too big; A* when the space is small and 2D and you want determinism.
  • Explains the loop (sample, nearest, steer, collision-check) and probabilistic completeness vs RRT*'s asymptotic optimality (choose-parent + rewire).
  • Knows the knobs and failure modes: step size, goal bias, narrow passages, the cost of nearest-neighbour search (k-d trees), and that output needs smoothing or a kinodynamic steer function.
  • Names practical variants: RRT-Connect (bidirectional), Informed RRT*, BIT*, PRM for multi-query; and OMPL/MoveIt as the tools.
🏭 In the real world
The original RRT 📜 History · 1998 LaValle, tech report TR 98-11

How: grow a tree by extending the nearest node toward random samples.

Why this method: designed for problems with nonholonomic and dynamic constraints, where exact grids and roadmaps were impractical.

RRT* and PRM* 🧪 Research · 2011 Karaman & Frazzoli, IJRR

How: connect each new node to its best nearby parent and rewire neighbours, within a radius shrinking like √(log n / n) in 2D.

Why this method: proved that RRT's cost converges to a non-optimal value, and that the * versions converge to the optimum at a constant-factor extra cost.

OMPL in MoveIt 🧰 Open source ompl.kavrakilab.org

How: a library of sampling planners (RRT-Connect, RRT*, Informed RRT*, BIT*, PRM…) used as MoveIt's default; you supply the collision checker.

Why this method: robot arms have 6–7 joints; sampling makes them plannable in fractions of a second.

Skydio Pathfinder 🏢 Company · 2026 skydio.com/autonomy

How: plans and executes a flight path to a destination considering terrain, buildings, geofences, flight policies and airspace rules (algorithm not published).

Why this method: 3D routes for drone-as-first-responder missions must be planned automatically, quickly and within rules.

🤯 Fun fact · a robot arm with 150 joints

OMPL's own homepage shows a parallel manipulator with over 150 degrees of freedom (150 numbers to choose at once) for which feasible motions “can still be computed in seconds” (OMPL). A grid with just 10 steps per axis would need 10150 cells: about 1070 times the number of atoms in the observable universe (roughly 1080).

Check yourself

1. A drone planner uses (x, y, z, yaw) with 50 steps per axis. How many cells would a grid need?
504 = 50 × 50 × 50 × 50 = 6,250,000. Manageable in memory, but add speed (4 more numbers for velocities and yaw rate) and it's 508 ≈ 3.9 × 1013: that's where sampling takes over.
2. Your RRT finds paths quickly in open areas but often needs thousands of samples to get through a doorway. Raising the goal bias from 5% to 30% made it worse. Why?
Goal bias helps when the way is open toward the goal and hurts when the route detours. Narrow passages need more samples inside them: bridge tests, obstacle-boundary samplers, or bidirectional trees that approach from both sides.
3. You give RRT and RRT* the same 3,000 samples on the same map and seed. Which statement is true?
Both grow from the same samples, but RRT* reconnects nodes through cheaper routes as it goes, so its best path keeps shrinking. The price is the neighbour search and extra collision checks for every new node.
📝 TL;DR
  • Grids cost stepsdimensions: 1012 cells for a 6-joint arm at 100 steps. Sampling avoids building the grid.
  • RRT: sample, nearest, steer by η, collision-check, add. Fast first path; probabilistically complete; never improves.
  • RRT*: choose the best nearby parent and rewire; converges toward the optimum (beat the 0.5 m grid A* in Playground 2).
  • Goal bias helps in the open, hurts in detours; narrow passages need smarter samples (bridge test: ~1,100 → ~500 samples for a 1 m gap here).
  • OMPL/MoveIt for arms and drones; cars prefer road-aligned sampling (7.5) or learned tree search (Tesla's AI Day demo).
