ROS 2 & tf2: the transform tree

A real robot has dozens of frames, some bolted down, some moving, all changing over time. tf2 keeps every one of them in a tree, remembers the last ten seconds, and answers “where was the camera, in the map, when this image was taken?” in one call. Here's how it works and how it breaks.

🧰 You'll need (quick reminders)
  • map → odom → base_link: map doesn't drift but jumps, odom is smooth but drifts (Lesson 1.1, REP 105).
  • Chaining transforms: Tmap_camera = Tmap_odom · Todom_base · Tbase_camera, inner names cancel; inverse = [Rᵀ, −Rᵀt] (Lesson 1.5).
  • Quaternions store the rotation part in ROS messages, as (x, y, z, w) with w last (Lesson 1.4).
🎯 Hook · a puzzle first

Your robot drives at 2 m/s. Its camera spots a person. The image reaches your code 200 ms after it was taken. You ask: “where is the camera in the map frame right now?”, and use that to place the person. How far off is the person, and what does tf2 say when you ask for “right now”?

Timing matters even for the best-calibrated cars. The Waymo Open Dataset gives every lidar point its own vehicle pose, “the pose at the time the LiDAR point is captured”, and reports camera–lidar synchronization within −6 to +7 ms for 99.7% of images (Sun et al.). In ROS, the library that handles “which frame, at what time?” is tf2: the transform library, introduced (as tf) by Tully Foote in 2013 (TePRA 2013).

🧩 Predict: 2 m/s, image 200 ms old. If you use the robot's latest pose instead of its pose when the image was taken, how far off is the person?
About 2 m/s × 0.2 s = 40 cm (a bit less if the latest pose is itself slightly old). And if you literally ask tf2 for the transform at now, it usually refuses: “Lookup would require extrapolation into the future”, because no odometry message stamped “now” has arrived yet. The right question is “at the image's timestamp”. Playground 2 lets you try all three.

One tree, many frames

tf2 stores one transform per link between a parent frame and a child frame, and links them into a tree: every frame has exactly one parent (except the root), and any number of children. A typical mobile robot:

Link (parent → child)KindWho publishes it
map → odomdynamicLocalization (it corrects drift by moving odom inside map)
odom → base_linkdynamic, e.g. 20–50 HzWheel odometry or a state estimator
base_link → laser, imu_link, camera_linkstaticCalibration: static_transform_publisher or the robot description (URDF)
camera_link → camera_opticalstaticFixed rotation to the optical convention (z forward, x right, y down)

Why a tree and not a web? Because a frame with two parents could get two different answers for where it is. REP 105 makes the point directly: you might expect both map and odom to attach to base_link, but that's not allowed, because each frame can only have one parent; so map is the parent of odom, and odom the parent of base_link.

To answer a lookup, tf2 walks from the source frame up to the closest common ancestor and down to the target frame, multiplying (and inverting) the transforms it passes. You never write the chain by hand.

✏️ Worked example: where is the camera on the map?

Three links (2D for simplicity, as x, y, yaw):

  • map → odom = (0.5, −0.2, 0°): localization says odometry has drifted by that much.
  • odom → base_link = (4, 3, 90°): the robot, facing “up” the odom frame.
  • base_link → camera_link = (0.3, 0, 0°): the camera, 30 cm ahead of the robot's center.
  1. Camera in odom: the robot faces 90°, so “0.3 m ahead” is +0.3 in odom y: (4, 3 + 0.3) = (4, 3.3), facing 90°.
  2. Camera in map: add map → odom's shift (no turn): (4 + 0.5, 3.3 − 0.2) = (4.5, 3.1), facing 90°.

That's Tmap_odom · Todom_base · Tbase_camera, the product tf2 computes for lookup_transform("map", "camera_link", time). Note the argument order: target first, source second; the result turns source-frame data into target-frame data.

    💡 Big idea tf2 turns “which frame?” into data. Every node publishes the links it knows (static ones once, moving ones continuously, each with a timestamp); every node that needs geometry asks for any frame pair at any recent time. The tree guarantees one answer, the timestamps make it the answer for the right moment.

    Static vs dynamic, and the role of time

    Each link arrives as a geometry_msgs/TransformStamped: a header with a timestamp and the parent's name (frame_id), the child_frame_id, and a transform (translation x, y, z and a quaternion x, y, z, w). Its definition says it “expresses a transform from coordinate frame header.frame_id to the coordinate frame child_frame_id at the time of header.stamp”.

    • Static links (sensor mounts) go on the /tf_static topic, once. The ROS 2 docs: “static transforms are published once and assumed to not change, so no history is stored.”
    • Dynamic links (odometry, localization, joints) go on /tf, continuously. Each listener keeps a buffer: tf2 stores a time snapshot for every transform “for up to 10 seconds by default”.
    • A lookup at time t interpolates between the two stored samples around t. If base_link was at x = 2.0 at t = 1.00 s and x = 2.2 at t = 1.10 s, at t = 1.04 s tf2 answers x = 2.0 + 0.4 × 0.2 = 2.08.
    • Ask for a time after the newest sample and you get “Lookup would require extrapolation into the future”; older than the buffer and you get “…extrapolation into the past”. tf2 never guesses outside its data.
    • Ask with time 0 (rclpy.time.Time()) and you get the latest available transform, whatever its age. Convenient, and wrong for anything that moves fast.
    🧠 Analogy: a family tree with dated photos

    Every frame is a family member with exactly one parent. Static links are birth certificates: written once, never updated. Dynamic links are a shoebox of dated photos showing where each child stood relative to its parent. Asking tf2 a question is like asking “where was cousin Camera relative to grandma Map at 3:04 pm?”: tf2 walks up and down the family tree and, for each moving link, picks the photos taken just before and after 3:04 and splits the difference. No photos after 3:04 yet? It won't make one up.

    🤔 Why this? (and not something simpler)
    1. The problem before. A robot has dozens of frames: map, odom, the base, every sensor, every arm joint. Each program needs some of them, at the time its data was captured, and every program used to carry its own copy of the offsets and its own chaining code. Sensor data from 100 ms ago was routinely combined with the robot's pose “now”.
    2. What people tried. Hard-coded offsets in each node (copies drift apart when a sensor is remounted). One central “pose” topic (fine for the base, useless for arms, gimbals and multiple sensors). Always using the latest pose (simple, but at 2 m/s a 200 ms-old image is placed 40 cm wrong).
    3. Why tf2 works. A shared, timestamped tree: publishers own their links, listeners query any pair at any buffered time, and tf2 does the path finding, multiplication, inversion and time interpolation. map → odom (0.5, −0.2) · odom → base (4, 3, 90°) · base → camera (0.3, 0) gives the camera at (4.5, 3.1) with no hand-written chain. Looking up at the image stamp removes the 40 cm error.
    4. What it costs, when it fails. Every message must carry the right frame_id and timestamp; a sensor driver that stamps with arrival time instead of capture time silently reintroduces the lag. Buffers cost memory and lookups cost CPU at high rates. Common failures: a missing link (“frame does not exist”, or “not part of the same tree”), a link published by two nodes (the frame jumps between two parents), clocks that disagree between machines or with simulation time, and asking for “now” (extrapolation errors).
    5. What came next. Message filters that hold sensor data until the transform for its timestamp is available, the robot description (URDF) with robot_state_publisher to publish all static and joint links from one file, lookups between two different times through a fixed frame (“time travel”), and, beyond ROS, estimators that fuse each measurement at its own timestamp (PX4's delayed fusion horizon, Lesson 3.7).

    Doing it for real: the commands and the code

    The tf2_ros package ships a command-line static publisher. In current ROS 2 releases (Jazzy is the long-term-support release, supported until May 2029) it takes named arguments, angles in radians:

    ros2 run tf2_ros static_transform_publisher --x 0.3 --y 0 --z 1.2 \
    --yaw 0 --pitch 0 --roll 0 --frame-id base_link --child-frame-id camera_link

ros2 run tf2_ros static_transform_publisher --x 0 --y 0 --z 0 \
    --qx 0 --qy 0 --qz 0 --qw 1 --frame-id world --child-frame-id mystaticturtle   # quaternion form

    All arguments except --frame-id and --child-frame-id are optional and default to the identity. Angles are radians: 15° is 0.2618, not 15.

    🧰 Tools you'll actually use

    In Python (rclpy), a node owns a Buffer and a TransformListener that fills it from /tf and /tf_static. This is the pattern from the official ROS 2 tf2 tutorials, with the lookup done at the data's own timestamp:

    import rclpy
from rclpy.node import Node
from rclpy.duration import Duration
from tf2_ros import TransformException
from tf2_ros.buffer import Buffer
from tf2_ros.transform_listener import TransformListener
import tf2_geometry_msgs                    # registers PointStamped etc. with tf2

class PersonLocator(Node):
    def __init__(self):
        super().__init__("person_locator")
        self.tf_buffer = Buffer()                          # keeps ~10 s of transforms
        self.tf_listener = TransformListener(self.tf_buffer, self)

    def on_detection(self, point_stamped):                # a geometry_msgs/PointStamped from the camera
        try:
            t = self.tf_buffer.lookup_transform(
                "map",                                     # target frame
                point_stamped.header.frame_id,             # source frame, e.g. camera_optical
                point_stamped.header.stamp,                # at the time the image was taken
                timeout=Duration(seconds=0.1))
        except TransformException as ex:
            self.get_logger().info(f"Could not transform: {ex}")
            return
        p_map = tf2_geometry_msgs.do_transform_point(point_stamped, t)
    # Debugging on a live robot
ros2 run tf2_tools view_frames                 # PDF of the whole tree, with publish rates and buffer ages
ros2 run tf2_ros tf2_echo map camera_link      # translation, quaternion, RPY and the 4×4 matrix, live
ros2 topic echo /tf_static                     # see every static link

    Static links in a broadcaster node use StaticTransformBroadcaster from tf2_ros.static_transform_broadcaster; moving links use TransformBroadcaster. Both send TransformStamped messages.

    🚗 How Tesla / Waymo / drones do it

    🚕 Waymo

    Waymo doesn't use ROS on its cars as far as it has published, but its open dataset shows the same two ideas tf2 implements: a full set of frames with 4×4 transforms between them, and time-correct poses: each lidar range-image pixel carries the vehicle pose at the moment that point was captured, and lidar-to-camera projections compensate for the cameras' rolling shutter. Camera–lidar synchronization error is within −6 to +7 ms for 99.7% of images.

    Sources: Waymo Open Dataset paper

    🛸 Drones (PX4)

    PX4 solves the same timing problem inside its estimator: each sensor has a delay parameter (EKF2_*_DELAY), and EKF2 fuses measurements on a delayed time horizon so that, for example, a GPS fix is combined with the state from when the fix was actually taken, then a fast filter carries the result forward to now. ROS 2 users talking to PX4 still need tf2-style care with frames (NED vs ENU, Lesson 1.1).

    Sources: PX4 EKF2 docs, PX4 ROS 2 guide

    🚘 Tesla

    Tesla hasn't published its internal transform or timing infrastructure. Publicly, at AI Day 2021, it described networks that fuse camera features into one vehicle-centered vector space and across time. Combining frames from different moments while the car moves requires accounting for the car's own motion between them, the same “transform at time t” question tf2 answers, though Tesla hasn't said how its stack does it.

    Sources: Tesla AI Day 2021

    🤖 ROS robots

    ROS 2 robots run tf2 throughout. The Nav2 navigation stack's docs say the tree must contain “a full map → odom → base_link → [sensor frames]” (REP 105): localization or SLAM provides map → odom, odometry provides odom → base_link, and the sensor links are static, defined in the robot's URDF description. robot_state_publisher reads that file and publishes fixed joints once to /tf_static and moving joints to /tf.

    Sources: Nav2: state estimation, robot_state_publisher

    Why they differ: ROS needs a general, shared service because its robots are assembled from packages by different authors. A company with one vertically integrated stack (Waymo, Tesla) can build frames and timing into its own data formats and code. A flight controller has a fixed set of sensors, so it bakes the timing into the estimator instead of a general library.

    ⚖️ Trade-offs
    Choice✅ Gains❌ Costs
    Lookup at Time() (latest)Never fails once the frames exist; simplest codeWrong by speed × age for moving robots (40 cm at 2 m/s, 200 ms)
    Lookup at the data's stampCorrect geometry for that momentCan fail until newer transforms arrive: needs a timeout or a message filter
    Static links via /tf_staticPublished once, no history, cheapA missing publisher breaks the tree with no warning until someone looks up
    Longer bufferCan process older data (slow detectors, logs)Memory; doesn't help with future-time requests
    🎤 Interview angle

    “Your detections are placed 30 cm off on the map when the robot moves fast, and fine when it's still. Debug it.” A strong answer:

    • Suspects time: lookup at Time() (latest) instead of the image stamp, or a driver stamping with arrival time; error ≈ speed × latency.
    • Knows tf2's API: lookup_transform(target, source, time, timeout), its errors (does not exist, not part of the same tree, extrapolation into the future/past) and the 10 s default buffer.
    • Checks the tree with view_frames / tf2_echo: one parent per frame, static links present, map → odom → base_link per REP 105.
    • Mentions clocks: all machines synchronized, use_sim_time consistent in simulation and playback.
    🏭 In the real world
    tf, the transform library 🧪 Research · 2013 Foote, TePRA 2013

    How: a distributed, timestamped tree of coordinate frames that any node can publish to and query.

    Why this method: robots built from many independent programs need one shared, consistent answer to “where is X relative to Y, at time t?”.

    Navigation on ROS 2 🧰 Open source Nav2: state estimation

    How: localization publishes map → odom, odometry publishes odom → base_link, sensors hang off base_link; the planner and costmaps look everything up through tf2.

    Why this method: swap the lidar or the localization package and nothing else changes, as long as the frames are published.

    Time-correct sensor fusion 🧰 Open source PX4 EKF2

    How: each measurement is fused against the state at its own (delayed) time, then the result is propagated to now.

    Why this method: the same lesson as lookups at the image stamp: combine data with the pose from when it was measured.

    🤯 Fun fact · tf2 won't guess the future

    The exact error text you'll meet, straight from tf2's source: “Lookup would require extrapolation into the future. Requested time … but the latest data is at time …”. It's a feature: tf2 interpolates between messages it has, but refuses to extrapolate, because a guessed pose that's wrong is worse than an honest failure. The fix is almost always to ask at the data's timestamp and allow a short timeout, not to ask for “now”.

    Check yourself

    1. odom → base_link was published at t = 5.00 s with x = 3.0 m and at t = 5.05 s with x = 3.1 m. What does tf2 return for x at t = 5.02 s?
    5.02 s is 40% of the way from 5.00 to 5.05, so tf2 interpolates: 3.0 + 0.4 × 0.1 = 3.04 m. Errors only happen outside the stored samples.
    2. Your node calls lookup_transform("map", "laser", node.get_clock().now()) and keeps getting “Lookup would require extrapolation into the future”. What's the usual fix?
    The newest transform is always a few milliseconds older than “now”, so tf2 refuses to extrapolate. Ask at the data's timestamp, which is in the past, and give it a timeout so it can wait for the transform that brackets it. A bigger buffer only helps for requests that are too old.
    3. Two nodes both publish a transform with child_frame_id = base_link: one with parent odom, one with parent map. What happens?
    tf2 assumes one parent per frame. REP 105's design is exactly the fix: localization publishes map → odom (computed from map → base_link and odom → base_link), so base_link keeps a single parent, odom.
    📝 TL;DR
    • tf2 keeps a tree of frames (one parent each); lookups walk up to the common ancestor and down, multiplying transforms for you.
    • Static links (/tf_static) are published once; dynamic ones (/tf) are timestamped and buffered (10 s by default) and interpolated.
    • lookup_transform(target, source, time, timeout): ask at the data's stamp. Time() = latest (stale for movers); now() → extrapolation into the future.
    • Errors: frame does not exist, not part of the same tree, extrapolation into the future / past. Tools: static_transform_publisher (radians!), tf2_echo, view_frames.
    • Waymo stores per-point poses and tight sensor sync; PX4 fuses each measurement at its own time; ROS robots get both from tf2.
