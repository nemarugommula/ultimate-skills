Recap: Foundations

What machine learning is, the loop around the model, the kinds of learning, when (not) to use it, the scikit-learn verbs, and the splits that keep your scores honest. Here's the phase on one page, a game that mixes all six lessons, a project to design yourself, and your first lab.

🧾 Cheat sheet

🧩

0.1 What ML is

ML = pick a function family, let an algorithm fit its parameters to labelled examples, judge it on unseen inputs.

From 12 orders a line cut new-order error from 9.8 min (fixed rule) to 3.0. k = 1 memorizes: 100% train, 79% new. Parameters are learned; hyperparameters you choose.

🧰 LinearRegression, KNeighborsRegressor, mean_absolute_error

🔁

0.2 The workflow

Frame → data & labels → features → baseline → model → evaluate → deploy → monitor → retrain.

ML code is a small box (≤ ~5% of a mature system's code). With 10% churn, “nobody churns” scores 87%. Same feature code in training and serving; watch for drift (91% → 81% in a year).

🧰 DummyClassifier, Pipeline, joblib, MLflow, Evidently

🧭

0.3 Kinds of learning

The feedback decides: labels for all (supervised), none (unsupervised), a few (semi), made from data (self), rewards (RL).

Clusters aren't classes (k-means matched the moons 74%). 6 labels + unlabelled shape: 100% vs 86%. BERT: 3.3 B words, 15% masked, zero human labels.

🧰 KMeans, LabelSpreading, SelfTrainingClassifier

⚖️

0.4 When to use ML

Rule possible? → rules. Table? → boosted trees (+ linear check). Pixels/audio/text? → pre-trained deep learning.

Rules of ML #1: launch without ML if you must; #3: replace complex heuristics. Value = decisions × error-rate saved × cost per error − running cost.

🧰 cross_val_score, DecisionTreeClassifier(max_depth=1), HistGradientBoosting

🔌

0.5 The scikit-learn API

Constructor = settings; fit(X, y) learns (attributes end in _); predict / predict_proba / score / transform.

Fit only on training data: test gets transform and predict, never fit_transform. predict_proba columns follow classes_. Swapping models is one line.

🧰 fit, predict, transform, set_output, clone, get_params / set_params

🔒

0.6 Splits & leakage

Train = fit, validation = choose, test = once. Split first; every learned step inside a Pipeline.

Best of 100 coin flips on 100 rows ≈ 63%. Selecting columns before the split: pure noise scores 78%. Watch target leaks, duplicates, groups and time. 294 papers in 17 fields got it wrong.

🧰 train_test_split, GroupKFold, TimeSeriesSplit, Pipeline

🗣️ Teach it back

Answer out loud, like in an interview: “Our product manager says: we have a year of order data; can machine learning tell us which deliveries will be late, and is it worth building? Walk me from that question to a number you'd trust, and tell me what could make that number lie.”

A strong answer covers: framing (predict at order time, what action the prediction triggers, the cost of each kind of error); a rule and a “never late” baseline first; features known at order time only; gradient-boosted trees for a table of this size; a time-based split with validation for choices and one final test month; the dollar value per month vs build and running costs; and the leaks that would inflate it: actual pickup time as a feature, restaurant averages computed with future orders, random splits, tuning on the test month. Then deployment with the same feature code, and drift monitoring.

🏗️ Build it yourself: will this delivery be late?

✏️ The problem

A food-delivery app handles 40,000 orders a month; 9% arrive late. The team wants to warn customers at the moment they order (“this one may be late, here's a $1 credit”). Illustrative economics: warning a customer whose order really is late saves about $4 (fewer refunds and support tickets); warning one whose order is on time wastes the $1 credit. You have 12 months of orders (480,000 rows) with restaurant, address, distance, timestamps, weather, rider logs and the actual delivery time.

Using this phase's ideas, decide: rules or ML, which features, which model, how you'd split and measure, the value per month, and what could make your numbers lie. Then open the reveal.

Reveal: one good answer

Requirements

  • Predict at order time, before a rider is assigned: “will this order arrive later than the promised time?” A yes/no label from the actual delivery time (supervised classification).
  • Fast enough to show on the checkout screen (tens of milliseconds); retrained regularly as restaurants and seasons change.

Numbers

  • Late orders: 40,000 × 9% = 3,600 a month. Baseline “never late” is 91% accurate and saves $0.
  • Warn everyone: 3,600 × $4 − 36,400 × $1 = −$22,000 a month. Accuracy isn't the goal; value is.
  • A model that catches 60% of late orders with 40% of its warnings correct: 2,160 caught, 5,400 warnings, 3,240 false alarms → 2,160 × $4 − 3,240 × $1 = +$5,400 a month. Measure the real precision and recall on the test month before believing this.
  • First check a rule (“late if distance > 6 km or raining”) the same way. If it already earns most of the $5,400, ship it while you build the model (Rules of ML #1).

Data and features (known at order time only)

  • Distance, hour, weekday, current weather, promised time, number of open orders in the zone right now, riders available right now.
  • Restaurant's median prep time over the previous 7 days, computed only from orders before this one.
  • ❌ Not: actual pickup time, route taken, rider's actual speed, “refund issued”. All of these happen after the order, so they are target leaks.

Model, and why

  1. DummyClassifier and the rule, as baselines.
  2. Logistic regression in a Pipeline: an interpretable check.
  3. Gradient-boosted trees (HistGradientBoostingClassifier, later LightGBM): this is a table with hundreds of thousands of rows, mixed features and interactions (rain × distance), exactly where trees are the strong default (Lesson 0.4, Phase 4).

Validation plan

  • Split by time: train on months 1–9, validate (choose features, hyperparameters, the warning threshold) on months 10–11, test once on month 12 (40,000 orders, so a precision of 40% has a margin of about ±1.3 points over its 5,400 warnings).
  • All preprocessing inside a Pipeline fitted on training months; restaurant statistics computed with past data only.
  • Report: precision and recall at the chosen threshold, and the dollar value per month, next to the baselines.

Deployment and monitoring

  • Ship the whole pipeline; compute live features with the same code (a shared function or feature store) to avoid training-serving skew; log features, scores and outcomes.
  • Monitor the late rate, the warning rate and weekly precision; retrain monthly or on a drift alert (new cities, holidays, a new rider app).

Classic mistakes

  • A random split over the year: the model sees the busy Friday before and after each test Friday.
  • “Restaurant average prep time” computed over the whole year, future included.
  • Choosing the threshold on the test month, then reporting that month's value.
  • Optimizing accuracy, which “never late” already wins at 91%.

What this design doesn't cover yet: calibrated probabilities for “may be late” wording (Lesson 5.6), picking the threshold from the cost curve (5.3–5.4), and explaining a warning to the support team (8.1–8.2).

🏆 Boss quiz

1. A learned line says delivery minutes ≈ 6.0 + 4.3 × km. Three new orders: 2 km took 16 min, 4 km took 21 min, 6 km took 34 min. What's the MAE on them?
Predictions: 6.0 + 8.6 = 14.6, 6.0 + 17.2 = 23.2, 6.0 + 25.8 = 31.8. Errors: |16 − 14.6| = 1.4, |21 − 23.2| = 2.2, |34 − 31.8| = 2.2. MAE = (1.4 + 2.2 + 2.2) ÷ 3 = 5.8 ÷ 3 ≈ 1.9 minutes (Lesson 0.1). 5.8 is the total, not the average; 0.5 keeps the minus signs, so over- and under-predictions cancel.
2. 1 million support tickets, 2,000 labelled by topic. Which plan fits best?
Few labels and many unlabelled examples is the semi-supervised setting (Lesson 0.3). Clusters may not match the topics you need, and RL is for sequential decisions with rewards. Whatever you add must beat the labelled-only model on held-out labels.
3. 50,000 decisions a month. A model cuts the error rate from 6% to 4%; each error costs $3; the model costs $1,200 a month to run and $30,000 to build. Payback time?
Errors saved: 50,000 × 2% = 1,000 × $3 = $3,000 a month, minus $1,200 running = $1,800 net. $30,000 ÷ $1,800 ≈ 16.7 months (Lesson 0.4). Worth it only if the system will live well beyond that.
4. Which line is the bug? scaler = StandardScaler() / Xtr = scaler.fit_transform(X_train) / Xte = scaler.fit_transform(X_test) / model.fit(Xtr, y_train).score(Xte, y_test)
fit_transform on the test set re-learns the statistics from test data, so the model sees differently scaled numbers than it trained on (and in production, a batch of one becomes all zeros). fit returns the estimator, so chaining is fine (Lesson 0.5).
5. A churn model scores 0.96 on a random 20% of monthly customer rows. In production it scores 0.78. Which pair of problems most likely explains it?
A random split of repeated, time-ordered rows lets the model recognize customers and peek at the future, and post-outcome features inflate scores too (Lesson 0.6). Group and time splits plus a “known at prediction time?” review give an honest estimate; then monitor for drift (Lesson 0.2).
