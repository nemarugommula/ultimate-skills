Phase 5 · Lesson 7

Hyperparameter search: grid, random, Bayesian (Optuna)

Every model has knobs you set before training. Trying them all is impossible and trying them by hand is slow. The surprise: throwing darts at random beats a neat grid, and a search that learns from its darts does better still.

🧰 You'll need (quick reminders)
  • Hyperparameters (knobs) are set before training: tree depth, learning rate, C, k. Parameters (weights) are learned (Lesson 0.5).
  • Each setting is scored with cross-validation, and picking the best of many scores makes that score optimistic (Lesson 5.1).
  • Regularization strengths and learning rates usually matter on a log scale: 0.001, 0.01, 0.1 (Lesson 2.2).
🎯 Hook: random search beat the experts' grid

In 2012, James Bergstra and Yoshua Bengio re-ran a large earlier study that had tuned neural networks with grid search and expert hand-tuning. They replaced the grid with random settings drawn from the same ranges.

Random search found models “as good or better within a small fraction of the computation time”. Against deep belief networks tuned by a mix of experts and grids over 32 knobs, pure random search matched them on four of seven datasets and beat them on one. Their explanation: for most datasets only a few knobs really matter, and which ones differ from dataset to dataset.

Why would randomness beat careful, even coverage? You'll see it in one picture.

🔮 Predict first

You have budget for 25 trials and two knobs, but only one of them actually matters. A 5 × 5 grid tries how many different values of the knob that matters?

Only 5: each value of the important knob is repeated 5 times with different values of the useless one. 25 random trials try 25 different values of every knob. That's Bergstra and Bengio's argument in a sentence. See it in Playground 1.

💡 Big idea Hyperparameter search is an expensive black-box optimisation: each evaluation is a full cross-validated training run. Grid search wastes trials repeating values of knobs that don't matter. Random search covers each knob more densely for the same budget. Bayesian optimisation (such as TPE in Optuna) uses the results so far to choose the next trial. Successive halving and pruning stop bad trials early. And whatever you use, the test set is never part of the search.
🧠 Analogy: finding the best spot to fish

You can fish a lake from 25 spots. A grid of 5 rows × 5 columns means you only ever try 5 distances from the shore, and if the fish all live at one distance you didn't pick, you catch nothing. Picking 25 random spots tries 25 distances. Better still: after each catch, move closer to where you've been catching (Bayesian search). And if a spot gives nothing in five minutes, leave early (pruning).

🤔 Why this? Why random search, Bayesian optimisation and early stopping?
  1. The problem before. A gradient-boosted model has 5–10 knobs that matter. Each evaluation is a 5-fold CV run costing minutes. Hand-tuning is slow and biased toward the knobs you believe in; you need an automatic, reproducible search.
  2. What people tried. Grid search: every combination of a few values per knob. With 6 knobs × 5 values that's 5⁶ = 15,625 runs, and most of them only vary unimportant knobs. Coarse-to-fine grids help a bit but still waste trials.
  3. Why this works. Random search gives each knob as many distinct values as there are trials, so the few knobs that matter get covered densely (25 values instead of 5). Bayesian methods spend later trials near good earlier ones: in Playground 2, after 40 trials TPE reached the target in about 79% of runs vs 18% for random. Successive halving trains 27 settings briefly and only the best ones long, for 81 units of compute instead of 729.
  4. What it costs, when it fails. Random search is still blind to past results. Bayesian methods are sequential (harder to run 100 trials at once) and can over-focus. Early stopping can kill “late bloomers” (a small learning rate starts slow). And every search overfits its validation score a little, more with more trials (Playground 4).
  5. What came next. Hyperband (2016) runs successive halving at several aggressiveness levels; Optuna (2019) made define-by-run TPE search with pruning easy; Optuna 5.0 (September 2026) made multivariate TPE the default. AutoML systems search over whole pipelines. And for gradient boosting, good defaults plus early stopping often get you most of the way (Lesson 4.4).

✏️ Worked example: the odds of a random hit

Suppose the good region covers 5% of the search space (any shape, any number of knobs). Each random trial lands in it with probability 0.05, independently.

  • Chance that none of n trials hits: 0.95ⁿ. For n = 60: 0.95⁶⁰ ≈ 0.046.
  • So 60 random trials find a top-5% setting with probability about 95%, whatever the number of knobs.
  • A grid has no such guarantee: if the good region is a thin ridge between grid lines, any number of grid points can miss it (36 did, above).

This back-of-the-envelope rule (“60 random trials for a top-5% setting”) is a classic piece of folk wisdom that follows directly from 1 − 0.95ⁿ.

Smarter: Bayesian optimisation and TPE

Random search ignores what it has learned. Bayesian optimisation builds a cheap model of “score as a function of settings” from the trials so far, and uses it to pick the next trial where improvement looks likely. The classic version uses a Gaussian process (Snoek et al., 2012). TPE (the tree-structured Parzen estimator, Bergstra et al., 2011), the default in Optuna, flips it around:

  1. Split the trials so far into good (top ~20%) and bad (the rest).
  2. Fit a smooth density to each: l(x) = where good trials live, g(x) = where bad trials live.
  3. Draw candidates from l(x) and run the one with the highest l(x) ÷ g(x): likely good, unlikely bad.

Like Optuna's TPE, the version below starts with 10 random trials and scores 24 candidates per step.

Cheaper: successive halving and pruning

Most bad settings look bad early. Successive halving (Jamieson and Talwalkar) exploits that: start many settings with a small budget (few rows or few boosting rounds), keep the best third, give them three times the budget, repeat. Pruning in Optuna does the same inside one trial: report the score after each epoch, and stop the trial if it's worse than the median of earlier trials at that step.

Three rounds cost 27 + 27 + 27 = 81 budget units (plus one final full training), against 27 × 27 = 729 to train every setting fully: about 9× cheaper. With noise 0.05 it picks the true best about 57% of the time and a top-3 setting about 93%. Turn the noise up to see the risk: early scores that mislead kill good settings in round one.

Never tune on the test set

🔮 Predict first

You try 100 models that are all pure coin flips (true accuracy 50%) and keep the one with the best accuracy on a 200-row test set. What test accuracy does the “winner” report, on average?

About 59%, from models that know nothing. With 200 rows, a coin-flip model's test accuracy has a spread of about 3.5 points, and the best of 100 lands about 2.5 spreads above 50%. On fresh data the winner gets 50%. That's what “tuning on the test set” buys you: a beautiful, fake number.

Real models aren't coin flips, but the effect is the same: the more settings you compare on one dataset, the more the winner's score is inflated by luck. The protocol: search with cross-validation on the training set (or a validation set), pick the winner, then evaluate it once on a test set nobody looked at. For an unbiased estimate of the whole tune-then-train procedure, use nested CV (Lesson 5.1). Kaggle competitions build this in: the public leaderboard you can probe is separate from the private one that decides the winners.

🧰 Tools you'll actually use

scikit-learn (1.9): GridSearchCV, RandomizedSearchCV (pass scipy.stats distributions such as loguniform), and the experimental HalvingGridSearchCV / HalvingRandomSearchCV (since 0.24; enable them with an import).

from scipy.stats import loguniform
from sklearn.datasets import load_digits
from sklearn.experimental import enable_halving_search_cv  # noqa: switches the halving classes on
from sklearn.model_selection import GridSearchCV, HalvingRandomSearchCV, RandomizedSearchCV, train_test_split
from sklearn.svm import SVC

X, y = load_digits(return_X_y=True)
X_tr, X_te, y_tr, y_te = train_test_split(X, y, test_size=0.25, stratify=y, random_state=0)  # test: touch once, at the end

grid = GridSearchCV(SVC(), {"C": [0.1, 1, 10, 100], "gamma": [1e-4, 1e-3, 1e-2, 1e-1]}, cv=5).fit(X_tr, y_tr)  # 16 runs
space = {"C": loguniform(1e-2, 1e3), "gamma": loguniform(1e-5, 1e0)}
rand = RandomizedSearchCV(SVC(), space, n_iter=16, cv=5, random_state=0).fit(X_tr, y_tr)        # same budget
halv = HalvingRandomSearchCV(SVC(), space, n_candidates=64, factor=3, cv=5, random_state=0).fit(X_tr, y_tr)

for name, s in [("grid", grid), ("random", rand), ("halving", halv)]:
    print(name, round(s.best_score_, 4), s.best_params_)               # CV scores ≈ 0.98–0.99
print("test:", rand.score(X_te, y_te))                                   # the one honest look

Optuna (5.0 as of late 2026): you write an objective(trial) that asks for values with trial.suggest_float / suggest_int / suggest_categorical and returns a score; create_study(direction=…) and study.optimize(objective, n_trials=…) run TPE by default. Report intermediate scores to enable pruning:

import optuna
from sklearn.datasets import load_digits
from sklearn.linear_model import SGDClassifier
from sklearn.model_selection import train_test_split

X, y = load_digits(return_X_y=True)
X_tr, X_va, y_tr, y_va = train_test_split(X, y, stratify=y, random_state=0)

def objective(trial):
    clf = SGDClassifier(
        alpha=trial.suggest_float("alpha", 1e-6, 1e-1, log=True),     # search on a log scale
        loss=trial.suggest_categorical("loss", ["hinge", "log_loss", "modified_huber"]),
        random_state=0)
    for epoch in range(20):
        clf.partial_fit(X_tr, y_tr, classes=list(range(10)))
        acc = clf.score(X_va, y_va)
        trial.report(acc, step=epoch)                   # tell the pruner how it's going
        if trial.should_prune():                        # worse than the median trial at this epoch?
            raise optuna.TrialPruned()
    return acc

study = optuna.create_study(direction="maximize", pruner=optuna.pruners.MedianPruner(n_warmup_steps=3))
study.optimize(objective, n_trials=50)
print(study.best_value, study.best_params)

Optuna 5.0 turned on multivariate TPE (it models knobs jointly) and the “constant liar” strategy for parallel trials by default; optuna.importance.get_param_importances(study) tells you which knobs mattered. Use log=True for scale-like knobs in any tool. For boosted trees, LightGBM and XGBoost have callbacks for Optuna pruning in the optuna-integration package.

🚀 Startup vs big tech

Week one

Start from library defaults, then run 30–100 random or Optuna trials over 3–5 knobs that matter, with log-scale ranges, overnight on one machine. Spend more time on features and validation than on tuning: a leak-free split is worth more than the fifth decimal.

At scale

Hyperparameter search runs as a service: hundreds of parallel trials on a cluster, Hyperband-style early stopping, every trial logged (Lesson 9.2: experiment tracking). Teams retune when data drifts, and keep tuned defaults per model family so most new projects start close to good.

🎤 Interview angle

“How would you tune a gradient-boosting model's hyperparameters?” A strong answer:

  • Separates the search (CV on training data) from the final evaluation (a test set touched once), or uses nested CV.
  • Prefers random over grid (Bergstra & Bengio: few knobs matter) and Bayesian/TPE (Optuna) when trials are expensive, with log-scale ranges.
  • Uses early stopping / pruning or successive halving to save compute, aware of the late-bloomer risk.
  • Names the knobs that usually matter for boosting (learning rate with number of rounds, leaves/depth, min child samples, subsampling, regularisation) and starts from defaults.
  • Mentions the winner's curse: many trials inflate the best validation score.
🏭 In the real world
Random search for hyper-parameter optimization 🧪 Research · 2012 Bergstra & Bengio (JMLR)

How: replaced grid and manual search with random search in a large neural-network study, and analysed which knobs mattered with a Gaussian process.

Why this method: as good or better models in a small fraction of the compute; only a few knobs mattered per dataset, and different ones on different datasets.

TPE, the algorithm behind Optuna's default 🧪 Research · 2011 Bergstra et al.: Algorithms for Hyper-Parameter Optimization (NeurIPS)

How: models “good” and “bad” regions of the search space with Parzen (kernel) density estimates and samples where good/bad is highest.

Why this method: cheap per step, handles tree-structured (conditional) spaces, and beat random and manual search on deep belief networks.

Optuna 🧰 Open source Akiba et al.: Optuna, a Next-generation Hyperparameter Optimization Framework (KDD 2019)

How: a define-by-run API (the search space is written as ordinary code inside the objective), efficient sampling and pruning, and storage for distributed studies.

Why this method: conditional search spaces (“if model is SVM, ask for C”) become plain if statements; pruning cuts wasted training.

Hyperband 🧪 Research · 2016 Li et al.: Hyperband, a bandit-based approach to hyperparameter optimization

How: runs successive halving at several trade-offs between “many settings, small budget” and “few settings, big budget”.

Why this method: over an order-of-magnitude speedup over Bayesian competitors on deep-learning and kernel problems, without having to guess how aggressive to be.

🤯 Fun fact · the experts were the baseline

Bergstra and Bengio's strongest baseline wasn't a dumb grid: it was a combination of expert manual tuning and grid search on deep belief networks with a 32-dimensional configuration space. Pure random search matched it on four of the seven datasets. A Gaussian-process analysis then showed why: on each dataset only a handful of the 32 knobs mattered.

Check yourself

1. You have 4 knobs and want to try 5 values of each. How many runs does a full grid need, and how many distinct values of each knob would 100 random trials try?
Grid: 5⁴ = 625. Random: each trial draws a fresh value for every knob, so 100 trials try 100 values of each, at less than a sixth of the cost.
2. After 200 Optuna trials, your best 5-fold CV accuracy is 0.912. The model scores 0.894 on the untouched test set. What's the most likely explanation?
Picking the maximum of many noisy estimates inflates it: the winner's curse (Playground 4). A drop of a couple of points on fresh data is typical. Report the test score, or estimate the whole procedure with nested CV.
3. Successive halving starts 81 settings with 1 unit of budget each and keeps the best third every round (×3 budget). How much budget do the first four rounds use?
81 × 1, then 27 × 3, then 9 × 9, then 3 × 27: 81 each round, 324 total. Training all 81 settings with 81 units each would cost 6,561, about 20× more.
📝 TL;DR
  • Grid search wastes trials on knobs that don't matter; random search covers every knob densely for the same budget (Bergstra & Bengio, 2012).
  • Bayesian optimisation / TPE (Optuna) learns where good settings live; pruning and successive halving stop bad trials early.
  • Search on a log scale for scale-like knobs; 60 random trials find a top-5% setting with ~95% probability.
  • The best of many scores is optimistic: tune with CV on training data, test once at the end (or nested CV).
