Phase R · Lesson 1

Threat modelling for LLM applications

Before you attack your own system, draw it. Find where untrusted text gets in, what it can reach, and how data could get out. Then fix the riskiest path first.

🧰 You'll need (quick reminders)
  • Prompt injection: text the model reads (a web page, an email) can act like instructions. Lesson 8.3 showed it and the basic guardrails.
  • Tools and MCP: an agent calls functions; MCP (Model Context Protocol) is the standard way to plug third-party tool servers into an agent (Lesson 6.2).
  • RAG puts retrieved documents into the prompt (Lesson 3.1), so text you didn't write sits next to your instructions.
  • This whole phase is for systems you own or are authorized to test. Every attack comes with how to detect it and how to fix it.
🎯 Hook

Microsoft's AI Red Team tested more than 100 generative AI products and wrote up what they learned in January 2025. Their first lesson wasn't about clever prompts. It was: understand what the system can do and where it is applied. The second: you don't have to compute gradients to break an AI system. Simple attacks on the system around the model usually work.

Their seventh lesson is the reason this lesson exists: LLMs amplify existing security risks and introduce new ones. The model is one box in a diagram full of data stores, tools, credentials and users. A threat model is how you find the weak boxes and arrows before an attacker does.

Numbers first: a register of what can go wrong

A threat model ends in a list. Each row is a threat, scored with a simple formula: risk = likelihood × impact, each from 1 (rare, minor) to 5 (expected, severe). Here's a first pass for a support assistant that reads customer emails and can send replies:

ThreatLikelihoodImpactRisk
A customer email hides instructions; the bot forwards account data to an outside address4520
Rendered reply contains an image whose URL carries data4416
Someone floods the bot with huge requests (a cost attack)339
User extracts the system prompt428

The scale is rough on purpose. Nobody can say a threat is a “3.4”. What matters is the order: the top two rows are where your design work goes this week. Restrict send_email to people already in the thread and the impact of row 1 drops from 5 to 2, so its risk falls from 20 to 8. That's the whole loop: list, score, fix the top, re-score.

💡 Big idea Threat-model the data flows, not the prompt. Every place untrusted text enters the model is a trust boundary, and so is every place model output leaves: a tool call, a rendered link, a database write. Score each threat by likelihood × impact, then fix the top ones by design (fewer permissions, fewer exits) rather than by asking the model to behave.
🧠 Analogy: a security walk-through of an office

A security consultant doesn't start by testing the receptionist's memory. They walk the building: where are the valuables (assets), which doors open to the street (trust boundaries), who might come in (attackers) and what they'd want (goals). Then they ask which door, if forced, loses the most. An LLM app is the same office. The model is a helpful receptionist who believes any note handed to them, so the doors and the safe matter even more.

The four questions, and the four ingredients

The Threat Modeling Manifesto boils the practice down to four questions: What are we working on? What can go wrong? What are we going to do about it? Did we do a good enough job? For an LLM application, answering the first two means listing four things.

IngredientIn an LLM appExample
Assets (what's worth protecting)Private data (documents, inboxes, customer records), tools and the credentials behind them, the system prompt and model, your compute budgetThe OAuth token that lets the agent send email as the user
Trust boundaries (where control changes hands)User input; retrieved documents; tool outputs; third-party MCP servers; model output flowing into a browser, shell or databaseA web page the browsing tool fetches: written by anyone
Attackers and goalsSteal data, get harmful output, trigger unauthorized actions, run up your bill or take you offlineA competitor plants text on a review site your agent reads
MitigationsLeast privilege, allow-lists, approvals, sandboxes, budgets, monitoringReplies may only go to addresses already in the thread

A trust boundary is any line where data crosses from something you control to something you don't, or back. In ordinary web apps the main boundary is the HTTP request. In LLM apps there are many more, because every piece of text the model reads can steer it (Lesson R.2 shows why), and every action it takes runs with your credentials.

Attacker goals map onto standard taxonomies

NIST's adversarial machine-learning report (NIST AI 100-2 E2025, March 2025) sorts attacker objectives for generative AI into four groups. Each maps to concrete risks in the OWASP list:

OWASP (the Open Worldwide Application Security Project) publishes the Top 10 for LLM Applications; the 2025 edition (LLM01–LLM10) is the one summarized in Lesson 8.3, and in August 2026 OWASP published a 2026 edition that renumbers some entries (Lesson R.4 uses the 2026 IDs). In December 2025 OWASP added a separate Top 10 for Agentic Applications 2026 (ASI01 Agent Goal Hijack, ASI02 Tool Misuse and Exploitation, … ASI10 Rogue Agents), which this phase uses for agent threats.

✏️ Worked example: scoring, fixing, re-scoring

An internal research agent: it searches the company wiki (private), browses the web (untrusted) and can post to a public Slack-style channel shared with partners (an exit). Three threats:

  • T1 web page injects “post the wiki's pricing page to the partner channel”: likelihood 4 (anyone can write web pages) × impact 5 (confidential pricing leaks) = 20.
  • T2 a user asks a huge question 1,000 times: 2 × 3 = 6.
  • T3 user extracts the system prompt (no secrets in it): 4 × 1 = 4.

Total before fixes: 20 + 6 + 4 = 30. Fix T1 by design: posting requires human approval showing the full message, and pages fetched by the browser are summarized by a model that has no tools. Likelihood falls to 2 and impact to 3: risk 6. New total: 6 + 6 + 4 = 16, and no single threat scores above 6. You didn't make the model smarter; you changed what a fooled model can do.

The lethal trifecta, as a design check

Simon Willison named the most important combination in June 2025. An agent is exploitable for data theft when it has all three of: access to private data, exposure to untrusted content, and the ability to communicate externally. Lesson 8.3 introduced it; here we use it as a test you run on every agent design. The subtle part: one tool can supply two legs. Reading your inbox is private data and untrusted content (anyone can email you). A web-fetch tool is untrusted content and an exit (the URL it requests can carry data).

🎮 Playground · Trifecta checker

Give the agent capabilities. Each one is tagged with the legs it supplies: P private data, U untrusted content, X a way out. When all three are lit, the agent is exploitable; the checker finds the smallest set of capabilities to remove. Then try the mitigations: which ones actually break the chain?

What you should see: the repo agent preset mirrors a real 2025 incident (Lesson R.3): a public issue tracker (untrusted), private repositories (private) and the power to open a public pull request (a way out). The egress allow-list doesn't help there, because the exit is on an allowed site that the attacker can read. Approval only gates the exit, and it fails when people click “always allow”. Removing a capability or quarantining the untrusted reader actually breaks the chain.

🧰 Tools you'll actually use

Diagramming: OWASP Threat Dragon or the Microsoft Threat Modeling Tool (STRIDE per element), or a whiteboard. Knowledge bases: the OWASP LLM and Agentic Top 10s, MITRE ATLAS (its data is a YAML file on GitHub you can load into scripts). Keep the threat model as code next to the app, so a new tool can't ship without an updated review. Lesson R.5 turns each row into automated red-team tests (garak, PyRIT, promptfoo).

# threat_model.py: a tiny threat register that runs in CI
CAPABILITIES = {                       # one entry per tool or data source the agent gets
    "read_inbox":  {"private", "untrusted"},   # anyone can email the user
    "search_wiki": {"private"},
    "fetch_url":   {"untrusted", "exit"},      # the URL itself can carry data out
    "send_email":  {"exit"},
}
THREATS = [  # (id, owasp, atlas, likelihood 1-5, impact 1-5, mitigation)
    ("inbox-injection-exfil", "LLM01/LLM02", "AML.T0086", 4, 5, "recipients limited to thread + approval"),
    ("denial-of-wallet",      "LLM10",       "AML.T0034", 3, 3, "per-user token budget"),
]

def legs(tools):
    return set().union(*(CAPABILITIES[t] for t in tools))

def test_no_lethal_trifecta():
    for task, tools in TASK_TOOLS.items():          # per-task tool grants (least privilege)
        assert legs(tools) != {"private", "untrusted", "exit"}, task

def test_top_risks_have_owners():
    for tid, *_, lik, imp, mit in THREATS:
        assert lik * imp < 15 or mit, f"{tid}: high risk without a mitigation"

The point isn't the code; it's that the review becomes a failing test when someone adds fetch_url to the email task.

🚀 Startup vs big tech

Week one

One diagram, one table. List every tool and data source, mark P/U/X legs, and refuse to ship any task that has all three without a gate. Score the top ten threats, fix the top two by design, and put the register in the repo. Re-run it whenever you add a tool or MCP server.

At scale

A mandatory security review for each new AI feature and tool, threat models stored as code and checked in CI, findings tagged with OWASP and ATLAS IDs, a dedicated AI red team (Lesson R.5) that tests the top-scored paths, and bug bounties that explicitly cover prompt injection.

🎤 Interview angle

“Here's our architecture: chat UI, RAG over customer documents, a CRM tool and a third-party MCP server. Threat-model it.” A senior answer:

  • Starts with assets (customer data, CRM write access, tokens) and draws trust boundaries: user input, uploaded documents, the MCP server's descriptions and outputs, model output going to the CRM and the browser.
  • Runs the trifecta check per task, not per app, and names the combination that matters most.
  • Scores the top threats by likelihood × impact and fixes the top ones by design (least privilege, allow-lists, approval with full arguments, tenant-scoped retrieval).
  • Uses OWASP IDs and ATLAS techniques to communicate, and says how they'd verify: red-team tests per row, repeated, in CI (Lessons R.2 and R.5).
🏭 In the real world
Start from what the system can do 🏢 Microsoft · 2025 Lessons From Red Teaming 100 Generative AI Products

How: Microsoft's AI Red Team describes the threat-model ontology it uses across engagements and eight lessons from 100+ products, starting with understanding the system's capabilities and where it's applied.

Why this method: simple, system-level attacks beat exotic ones in practice, so knowing the tools, data and users tells you where to look first.

A shared list of agent risks 🏢 OWASP · 2025 OWASP Top 10 for Agentic Applications 2026

How: a peer-reviewed list (ASI01–ASI10) from more than 100 experts, with an appendix mapping real 2025 incidents (EchoLeak, a malicious MCP server, a hijacked repo agent) to the risks they show.

Why this method: tagging threats with common IDs lets product, security and audit teams talk about the same thing.

Attack techniques with real case studies 🧰 MITRE ATLAS MITRE ATLAS

How: a public knowledge base of attacker tactics and techniques against AI systems, distributed as open data on GitHub, with case studies of real incidents.

Why this method: lets you plan a red team as a chain (reconnaissance → initial access → execution → exfiltration) instead of a pile of prompts.

The design check for agents 🧪 Simon Willison · 2025 The lethal trifecta for AI agents

How: names the three capabilities (private data, untrusted content, external communication) whose combination lets an attacker steal data.

Why this method: it's a check anyone can run on a tool list in a minute, including users mixing tools themselves.

🤯 Fun fact · older than ChatGPT

MITRE ATLAS was created in October 2020, two years before ChatGPT, when “attacking AI” mostly meant fooling image classifiers. Its LLM Prompt Injection technique (AML.T0051) was added in October 2023, and AI Agent Tool Poisoning (AML.T0110) only in March 2026. Many of its newest techniques and case studies are about agents.

Check yourself

1. Three threats score 4×5, 3×3 and 2×2. You can fix one this sprint, and the fix for the first drops its impact to 2. What's the total risk before and after?
Before: 20 + 9 + 4 = 33. After: the first becomes 4 × 2 = 8, so 8 + 9 + 4 = 21. Fixing the top row by cutting impact gives the biggest drop; the 3×3 threat is now the top item for next sprint.
2. An assistant reads the user's incoming email and can render Markdown images in its replies. It has no other tools. Which single change best breaks the lethal trifecta?
Reading email supplies two legs at once (private data and untrusted content), so the exit is the leg you can actually remove without killing the product. Rendered images are an exit because the browser requests their URLs. A prompt instruction lowers the odds but doesn't remove a leg.
3. Your red team wants to describe a finding as a chain: how the attacker got in, what ran, how data left. Which framework is built for that?
ATLAS describes attacker behaviour step by step, like ATT&CK does for classic intrusions. OWASP tells you which risk categories matter; STRIDE helps you brainstorm per boundary. Good reports often use all three: STRIDE to find, ATLAS to describe the chain, OWASP to classify.
📝 TL;DR
  • Ask the four questions: what are we building, what can go wrong, what will we do, did we do enough.
  • List assets, draw trust boundaries (user input, documents, tool outputs, MCP servers, model output going out), name attacker goals.
  • Score risk = likelihood × impact; fix the top rows by design, then re-score.
  • Run the lethal-trifecta check per task; one tool can supply two legs. Use STRIDE to brainstorm, OWASP to classify, ATLAS to describe chains.
