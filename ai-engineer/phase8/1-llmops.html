Phase 8 · Lesson 1

LLMOps: tracing, gateways, fallbacks & cost tracking

Your LLM feature works on your laptop. In production a model provider is a dependency that goes down, slows down, changes behaviour without warning and bills you per token. LLMOps is how you see all of that and survive it.

🧰 You'll need (quick reminders)
  • Tokens are what you pay for: input tokens (the prompt) and output tokens (the answer), priced per million (Lesson 0.3).
  • A RAG request retrieves document chunks and puts them in the prompt (Lesson 3.6); an agent loops model call → tool call → model call (Lesson 6.1).
  • p95 latency = the time 95% of requests finish under. Averages hide the slow tail.
🎯 Hook

In August and early September 2025, some Claude users noticed answers getting worse. Nothing was “down”: requests succeeded, just with lower-quality output. Anthropic's postmortem traced it to three separate infrastructure bugs: a context-window routing error, an output-corruption misconfiguration on some TPU servers, and a compiler bug in approximate top-k sampling. At the worst hour, on August 31, 16% of Sonnet 4 requests were affected.

If you were building on that model, your error-rate dashboard stayed green the whole time. Only tracing real requests and scoring their quality would have shown you something was wrong. That gap is what this lesson closes.

Three things jump out. One user question became two model calls and seven steps. Input tokens dominate the bill (6,800 vs 220). And without a record of each step, you couldn't tell which one to fix when the bill or the latency doubles.

💡 Big idea Treat every model call like a call to a flaky, expensive, ever-changing third-party API. Trace each request step by step (time, tokens, cost, inputs and outputs), put a gateway between your code and the providers (timeouts, retries, fallbacks, budgets), and pin and version everything that changes behaviour: model, prompt, retrieval settings.
🧠 Analogy: the flight recorder and the air-traffic controller

A trace is a flight recorder for one request: every step, how long it took, what went in and what came out, so after a bad answer you can replay exactly what happened. A gateway is air-traffic control: every flight goes through it, it knows which runways (providers) are open, diverts traffic when one closes, and stops anyone from taking off without a flight plan (a budget).

Tracing: spans, traces and the GenAI conventions

A trace is the record of one request. It is made of spans: timed steps, nested in a tree (the request span contains the retrieval span, the model-call spans, the tool spans). This is standard distributed tracing from web services, with LLM-specific fields added: model name, input and output tokens, the prompt and the completion.

OpenTelemetry (OTel), the open standard for traces, metrics and logs, has GenAI semantic conventions: agreed attribute names so every tool records the same thing the same way. For example gen_ai.operation.name (chat, execute_tool, invoke_agent…), gen_ai.provider.name, gen_ai.request.model, gen_ai.response.model, gen_ai.usage.input_tokens and gen_ai.usage.output_tokens. As of late 2026 these conventions are still marked Development (not yet stable) and live in their own repository, so attribute names can still change: an older name, gen_ai.system, has already been replaced by gen_ai.provider.name.

Cost tracking: attribute every token

✏️ Worked example: who is spending the money?

Your monthly bill is $72,000. Tag every span with a feature and a hashed user_id, then group:

  • Chat assistant: 2.4 M requests × $0.024 = $57,600 (80%).
  • Nightly document summaries: 60,000 docs × $0.18 = $10,800 (15%). Not interactive, so a batch API at half price (Lesson 8.2) saves $5,400 a month.
  • “Other”: $3,600. Drill in: one integration test hitting production in a retry loop.

Then set budgets: a per-user daily cap (say $2) and a per-feature monthly cap with an alert at 80%. Without tags you only know the total, and the total never tells you what to fix.

Gateways: one front door for every model

An LLM gateway is a proxy or library that sits between your code and the model providers and gives every call one interface. What it handles for you:

FeatureWhat it doesTypical setting
TimeoutsGive up on a call that hangs. SDK defaults can be minutes long.A few seconds to TTFT for chat; longer for big batch jobs
Retries with backoffRetry rate-limit errors (HTTP 429) and server errors (5xx), waiting longer each time, with random jitter.1–2 retries; never retry forever
FallbacksWhen a model or provider fails, send the call to another (a different region, provider or model).Primary → same model elsewhere → a different model
Circuit breakerAfter many failures, stop trying the broken provider for a while and go straight to the fallback.Open at > 50% errors over a few seconds; retry after a cool-down
Rate limits and budgetsCap requests and spend per key, user or team, before the provider's limit or your CFO's does.Per user, per feature, per environment
Keys, logging, cachingKeep provider keys in one place; log every call; cache repeats (Lesson 8.2).Virtual keys per team

What you should see: with no timeout, hanging calls eat the user's whole patience. Retries alone push p95 latency up and send more traffic to the provider that is already struggling (a retry storm). A short timeout plus a fallback rescues almost every request for a little more money, and a circuit breaker stops hammering the broken provider at all.

✏️ Worked example: the worst case of “timeout + retries”

Timeout 10 s, 3 retries, backoff 0.5 s, 1 s, 2 s. If every attempt hangs: 4 × 10 + 0.5 + 1 + 2 = 43.5 s before the user sees an error. Your latency budget is the sum of every attempt, so keep timeouts short, retries few, and move to a fallback quickly. Same logic for an agent: 8 steps × a 10 s timeout = 80 s worst case.

Versioning and the incidents you will actually have

Pin a dated model snapshot (not a moving alias) in production, version prompts like code (Lesson 1.5), and record both on every trace. Then a change in behaviour always has a cause you can find, and a rollback is a config change.

🧰 Tools you'll actually use

Tracing and LLM observability: Langfuse (core is MIT-licensed open source, self-hostable), LangSmith (from the LangChain team, hosted), Arize Phoenix (source-available under the Elastic License 2.0), Helicone (Apache-2.0, integrates by changing the base URL to its gateway), plus your existing OpenTelemetry stack. Gateways: LiteLLM (open-source SDK and proxy), Portkey (MIT gateway), Cloudflare AI Gateway (managed; caching, rate limiting, fallbacks).

# 1) Trace every call: Langfuse decorator + drop-in OpenAI client
from langfuse import observe, get_client
from langfuse.openai import openai   # same API, every call becomes a span

@observe()                              # the function becomes the parent span
def answer(question: str) -> str:
    docs = retrieve(question)              # decorate retrieve() too for its own span
    resp = openai.chat.completions.create(
        model=MODEL,                       # a pinned, dated snapshot from your provider
        messages=[{"role": "user", "content": build_prompt(question, docs)}],
    )
    return resp.choices[0].message.content

answer("Where is my order #1042?")
get_client().flush()                       # send buffered spans before a script exits

# 2) Timeouts, retries and a fallback model in one place: LiteLLM Router
from litellm import Router

router = Router(
    model_list=[
        {"model_name": "chat-primary",  "litellm_params": {"model": "openai/" + OPENAI_MODEL}},
        {"model_name": "chat-fallback", "litellm_params": {"model": "anthropic/" + CLAUDE_MODEL}},
    ],
    fallbacks=[{"chat-primary": ["chat-fallback"]}],
    num_retries=1,
    timeout=20,                             # seconds per attempt
)
resp = router.completion(model="chat-primary",
                         messages=[{"role": "user", "content": "hi"}])

Langfuse reads LANGFUSE_PUBLIC_KEY, LANGFUSE_SECRET_KEY and LANGFUSE_BASE_URL from the environment. Fill the model constants from each provider's models page. If you emit raw OpenTelemetry instead, use the GenAI attribute names above and check the conventions repo for changes.

🚀 Startup vs big tech

Week one

Wrap the model client in a tracing decorator (Langfuse or similar), tag every call with feature and user, set an explicit timeout and one retry, pin the model version, and put a hard monthly spend limit in the provider console. A fallback model can wait until you have customers who notice outages.

At scale

A central gateway every team must use: virtual keys, per-team budgets, multi-provider and multi-region failover, PII redaction before logs, OTel traces flowing into the company's observability stack, online evals on sampled traffic, and on-call runbooks for “provider down” and “quality dropped”.

🎤 Interview angle

“Your LLM feature is live. How do you operate it?” A senior answer:

  • Traces with spans per step (retrieval, each model call, each tool), with tokens, cost, latency, model and prompt versions.
  • Dashboards on cost per request and per feature, p95 latency and TTFT, error and 429 rates, and a quality signal (online evals, user feedback), because quality can fail silently.
  • A gateway with short timeouts, bounded retries, fallbacks and a circuit breaker; budgets per user.
  • Pinned model snapshots and versioned prompts, so every change is deliberate and reversible.
  • Privacy: redaction, sampling, retention and access control on logged prompts.
🏭 In the real world
Quality bugs with no errors 🏢 Anthropic · 2025 A postmortem of three recent issues

How: three overlapping infrastructure bugs (request routing, a server misconfiguration, a compiler issue in sampling) degraded some responses for weeks; up to 16% of Sonnet 4 requests at the worst hour.

Why this method: the postmortem is a case study in why you monitor quality, not just availability, and keep enough trace data to tell “the model got worse” from “my prompt got worse”.

The same model name, different behaviour 🧪 Research · 2023 How is ChatGPT's behavior changing over time?

How: Stanford and Berkeley researchers ran the same tasks against the March and June 2023 versions of GPT-4 and GPT-3.5.

Why this method: behaviour shifted a lot between versions (GPT-4's accuracy at identifying prime numbers fell from 84% to 51%), so pin versions and re-run your evals before you move.

One vocabulary for LLM telemetry 🧰 Open source OpenTelemetry GenAI semantic conventions

How: standard span and attribute names for model calls, tool executions and agent invocations (gen_ai.usage.input_tokens, execute_tool, invoke_agent…).

Why this method: instrument once and send traces to any backend; LLM spans sit in the same trace as your HTTP and database spans.

Failover at the edge 🏢 Cloudflare AI Gateway: fallbacks

How: a managed gateway in front of many model providers, with configured fallback models or providers, plus caching and rate limiting.

Why this method: teams get failover, logging and limits without running their own proxy.

🤯 Fun fact · the convention that keeps moving

The OpenTelemetry GenAI conventions have changed enough that they now live in a repository of their own, and are still marked “Development”. Even the attribute for “which provider” was renamed (gen_ai.system → gen_ai.provider.name). In this field even the monitoring vocabulary needs a version pin.

Check yourself

1. Each request makes two model calls of 4,000 input and 200 output tokens each. At $3 / $15 per million tokens and 50,000 requests a day, what's the daily bill?
Per call: 4,000 × $3/M = $0.012, plus 200 × $15/M = $0.003, so $0.015. Two calls make $0.03 per request, and × 50,000 = $1,500 a day. Note that input is 80% of it.
2. Error rate and latency are normal, but over two weeks thumbs-down feedback doubles. You changed nothing. What's the best first move?
A quality drop with no errors points to a changed model (a moving alias, or a provider-side issue) or changed inputs. Traces that record the returned model name and online evals tell you which. Fallbacks fix outages, not quality.
3. A gateway is set to a 15 s timeout and 2 retries with 1 s and 2 s backoff, no fallback. During an outage where every call hangs, how long does the user wait for an error?
Three attempts × 15 s + 1 s + 2 s of backoff = 48 s. That's why you combine short timeouts with a fallback or a circuit breaker, instead of retrying a provider that is clearly down.
📝 TL;DR
  • Trace every request as spans (retrieval, each model call, each tool) with tokens, cost, latency, model and prompt versions; use the OpenTelemetry GenAI attribute names.
  • Tag spans by feature and user so cost is attributable; set budgets and alerts.
  • Put a gateway in front of providers: short timeouts, few retries with backoff, fallbacks, a circuit breaker, rate limits.
  • Quality can fail silently: pin model snapshots, version prompts, run online evals. Redact PII before it reaches your logs.
