Phase 4 · Recap

Recap: Advanced RAG strategies

Naive RAG retrieves once, from one index, and trusts the result. Every strategy in this phase fixes one specific way that breaks. The senior skill is matching the failure to the fix, and paying only for the fixes you need.

Cheat sheet

4.1

Query transformation

The user's message is a draft query.

Rewrite follow-ups (the chat default), multi-query + RRF (k = 60) for recall, HyDE for vocabulary gaps, step-back for over-specific, decompose compound questions. One small LLM call, ≈ 0.3–2 s each.

LangChain MultiQueryRetriever · LlamaIndex QueryFusionRetriever, HyDEQueryTransform

4.2

Advanced indexing

Search small, read big.

Small-to-big and sentence windows; index summaries, hypothetical questions or propositions; RAPTOR's collapsed tree for broad questions; ColBERT MaxSim per token (~10× storage before compression).

ParentDocumentRetriever · SentenceWindowNodeParser · AutoMergingRetriever · PyLate, RAGatouille

4.3

GraphRAG

Some answers are paths or summaries, not chunks.

LLM extracts entities and relations, Leiden finds communities, LLM summarises them. Local search follows edges; global search maps over summaries. Indexing ≈ hundreds of × embedding cost; LazyGraphRAG, FastGraphRAG and LightRAG are cheaper.

Microsoft GraphRAG · LightRAG · Neo4j + Cypher

4.4

Agentic & adaptive RAG

Retrieval becomes a decision.

Whether (router), where (sources), good enough? (grader: similarity isn't relevance), what next (rewrite, web, abstain). Self-RAG, CRAG, Adaptive-RAG. Cap loops; multi-agent research ≈ 15× chat tokens.

LangGraph · provider tool calling · small classifiers

4.5

Multimodal RAG

Evaluate by where the answer lives.

Convert (OCR, tables → Markdown, VLM captions) or embed visuals (ColPali page images). ColPali: 81.3 vs 67.0 nDCG@5, 0.39 vs 7.22 s/page, ≈ 257.5 KB/page; a page image ≈ 1,300 tokens.

Docling · Unstructured · ColPali/ColQwen (byaldi) · Voyage multimodal

4.6

Text-to-SQL

Retrieval can't add: let the database compute.

Retrieve tables, then schema + sample values + few-shot. Errors are easy (retry); wrong values that run are dangerous. Single SELECT, LIMIT, read-only user. Spider 91.2% vs Spider 2.0 21.3%.

sqlglot · read-only roles · semantic layers

4.7

RAG in production

The retrieval scope is a security boundary.

Pre-filter ACLs with groups from auth; key caches by permissions and index version; deletes reach every copy; freshness is a measured staleness window; generation dominates latency and cost.

Qdrant/Pinecone/Weaviate multi-tenancy · pgvector + RLS · semantic caches

4.8

RAG pipelines at scale

Indexing is a data pipeline: run it like one.

Orchestrated, idempotent ingestion jobs; queues and workers; batch embedding under provider rate limits; incremental re-indexing of what changed; backfills into a new index when the embedding model changes, with cutover after evals pass.

workflow orchestrators · message queues · provider batch APIs

🏗️ Build it yourself

The problem

A 50,000-employee company wants one assistant over Confluence and Google Drive (including slide decks), Jira tickets and a Snowflake sales warehouse. About 5 million documents. Employees should only see what they can already open. Expected load: 200,000 questions a day. Design the system: retrieval strategies, permissions, freshness, latency and cost.

Reveal a reference design

Requirements. Answers with citations; permission parity with the source systems; staleness under 15 minutes for Jira, under a day for documents; p95 latency under 6 s; deletes honoured everywhere; abstain rather than guess.

Pipeline.

  • Router (small classifier or LLM call, 4.4): chit-chat → no retrieval; aggregates (“bookings by region”) → text-to-SQL over Snowflake with table retrieval, sample values and a read-only role (4.6); “why” questions → SQL + documents; everything else → document RAG.
  • Query rewrite with conversation history; decomposition for compound questions (4.1).
  • Indexes: hybrid (BM25 + dense) over structure-aware chunks with sentence-window or parent returns (4.2); ColPali-style page images for slide decks, with their text layer kept for citations (4.5); Jira as ticket trees linked by issue links (as LinkedIn did) if multi-hop questions show up in evals (4.3).
  • Grader on borderline retrievals with one capped rewrite, then abstain (4.4). No open-web fallback for internal questions.
  • Permissions: ACLs synced from each source as chunk metadata; pre-filtered queries with the user's groups from SSO; caches keyed by permission set and index version (4.7).
  • Pipelines: event-driven sync for Jira, incremental sync by content hash for Confluence and Drive, batch embedding under rate limits, deletion propagation with an audit log, and backfills into a parallel index when the embedding model changes (4.8).

Eval plan. 300 labelled questions stratified by type (lookup, follow-up, compound, multi-hop, aggregate, visual, permission-sensitive) and by source; retrieval recall@k per stratum; groundedness and citation accuracy with an LLM judge spot-checked by humans; red-team permission tests (one test user per role); latency and cost per route. Phase 5 builds all of this.

Costs (illustrative). Indexing: 5M docs ≈ 50M chunks × 300 tokens = 15B tokens × $0.02/M = $300 once; 1% daily change ≈ $3 a day. Serving: 200,000 × ≈ $0.012 per answer = $2,400 a day; a 25% permission-keyed cache hit rate → ≈ $1,800. Generation is most of the bill, so context packing and routing matter more than vector database costs.

Pitfalls. Oversharing in the source systems becomes oversharing in answers (fix the source permissions); summaries or graph communities built across permission boundaries leak (derive per ACL or inherit the strictest); semantic-cache false hits; silent wrong SQL; slide decks with no text layer; mixing vectors from two embedding models; prompt injection inside documents and tickets (8.3).

Boss quiz

1. GraphRAG extraction over 30,000 chunks with 2 gleaning passes. Roughly how many extraction LLM calls?
Each chunk gets the first extraction plus 2 gleaning passes: 30,000 × (1 + 2) = 90,000 calls, before entity and community summaries. That multiplier is why gleaning is a cost knob.
2. Legal asks both “What's the notice period in the Acme contract?” and “What risk themes recur across all 4,000 vendor contracts?”. Which design serves both?
Lookups need precise leaves; themes across thousands of documents need summaries that no single chunk contains. Retrieving from both levels in one pool handles each question at the right altitude.
3. A relevance grader uses cosine ≥ 0.6. Users asking about today's outage get confident answers built from your generic status-page FAQ. What's the fix?
On-topic text is similar but not relevant. CRAG's evaluator and Self-RAG's IsRel token ask the right question; volatile facts belong to a live tool, not a stale index.
4. You upgrade to a better embedding model. A teammate proposes embedding only new documents with it and leaving old vectors as they are. What happens?
Different models produce different, incompatible vector spaces (often different dimensions too). Re-embed everything into a parallel index, evaluate, then switch: the backfill pipeline of Lesson 4.8, costed in 4.7.
5. Generated SQL for “revenue from Plus customers” runs cleanly and returns NULL. The data uses 'Plus'; the SQL says plan = 'plus'. What prevents this class of error?
No error was raised, so a retry loop never fires. Real values in context (BIRD's lesson) prevent the mismatch; treating suspicious results as signals catches what slips through.
🌉 What's next

Every strategy in this phase came with the same advice: measure it. Phase 5 is how. You'll build golden datasets (5.1), learn metrics and LLM-as-judge (5.2–5.3), and then evaluate RAG specifically, retrieval recall, context precision, faithfulness and answer relevance (5.4), so you can prove that the rewrite, the grader or the graph actually helped.
