Phase 4 · Lesson 8

RAG pipelines at scale: ingestion orchestration, batch embedding & backfills

A notebook that indexes 50 PDFs is a script. Keeping millions of changing documents indexed, fresh and correct, and rebuilding the whole index when you change models, is a data pipeline. Build it like one.

🧰 You'll need (quick reminders)
  • The indexing path: parse documents (Lesson 3.2), cut them into chunks (3.3), embed each chunk into a vector (2.1) and store it in a vector database (2.3).
  • Rate limits: providers cap requests per minute and tokens per minute, and answer HTTP 429 when you exceed them (Lesson 0.5).
  • Freshness and permissions: a stale or wrongly-permissioned index gives wrong answers (Lesson 4.7).
🎯 Hook

Notion's AI Q&A chunks every page into spans, embeds them and stores them with metadata such as authors and permissions. In the original pipeline, any edit to a page re-chunked, re-embedded and re-uploaded every span on it, even if a single character changed.

In 2025 they started storing two fingerprints per span: a hash of its text and a hash of its metadata. Text changed? Re-embed only that span. Only permissions changed? Skip embedding entirely and patch the metadata in place. That cut the data volume flowing through the pipeline by 70%, saving on both embedding API costs and vector-database writes (Notion engineering, February 2026). Same model, same index. The win was pipeline engineering.

The embedding bill is often the smallest number in the project: OpenAI's own guide estimates about 62,500 pages per dollar for its small model. What hurts is time (rate limits), failures (millions of files means thousands of broken ones), re-work (re-embedding what didn't change), and the day you change the embedding model and must redo all 12 million chunks without taking search down.

💡 Big idea Your vector index is a derived dataset: a function of (source documents, parser version, chunker config, embedding model). Build the pipeline so every stage is idempotent (running it twice = running it once) and keyed by stable IDs and content hashes. Then you can retry anything, re-run only what changed, and rebuild everything into a new index and switch over atomically when any of those versions changes.
🧠 Analogy: a warehouse that re-labels its stock

Goods arrive on conveyor belts (connectors), get unpacked (parse), split into boxes (chunks) and labelled (embed) before going on shelves (the index). A fingerprint on each box means you only re-label boxes whose contents changed. Damaged goods go to a returns shelf instead of jamming the belt (the dead-letter queue). And when you adopt a new labelling system, you don't re-label the shelves while customers shop: you fill a second warehouse next door, check it, then swap the address on the sign overnight (a blue-green cut-over).

Stages talk through queues (a durable list of work items that workers pull from: SQS, Kafka, Redis, or a database table), so a slow stage doesn't block a fast one and each can scale on its own. Figma's AI search pipeline splits steps into discrete jobs for exactly this reason: “more precise control over batching and retry behavior”. A message that keeps failing (a “poison message”) is moved after N attempts to a dead-letter queue (DLQ), a holding area you inspect and replay later, instead of retrying forever or blocking the line.

Idempotency: IDs and hashes

  • Document ID: stable and from the source, e.g. confluence:123456, never a random UUID generated at ingest time.
  • Chunk ID: derived, e.g. confluence:123456:7 (or a UUID computed from that string, since some databases such as Qdrant require integer or UUID point IDs). Re-running produces the same IDs, so an upsert (insert-or-replace) overwrites instead of duplicating.
  • Content hash: a fingerprint of the chunk text (SHA-256, or a fast hash like Notion's 64-bit xxHash). Same hash as last time → skip embedding. Keep a separate metadata hash so permission changes become cheap metadata patches.
  • Pipeline version: store parser, chunker and model versions on every chunk. When they change, the hash check alone isn't enough: everything is “changed”, which is a backfill (below).
  • Deletes: if a doc disappears or shrinks from 9 chunks to 6, delete chunks 6–8. Forgotten deletes are the classic source of “the bot quoted a policy we removed last year”.

Incremental vs full re-index

Incremental processes only what changed since the last run: cheap and fast, but it can drift (missed webhooks, missed deletes). Full re-processes everything: slow and expensive, but it resets drift. Most teams run incremental continuously and a full reconciliation (compare source listing to index, fix differences) weekly. You also don't need to index every keystroke: Figma found that indexing a file at most every four hours, instead of on every change, meant processing only 12% of the data.

Embedding throughput: the math under rate limits

Three things cap your speed, and the smallest one wins:

tokens/min = min( TPM limit, RPM limit × tokens per request, workers × (60 ÷ seconds per request) × tokens per request )
  • TPM / RPM: tokens per minute and requests per minute your account may send.
  • Batch many chunks per request. OpenAI's embeddings endpoint takes up to 2,048 inputs and 300,000 tokens per request. One chunk per request makes you RPM-bound: 12M chunks at 3,000 RPM is 4,000 minutes (67 hours). A hundred per request is 120,000 requests: at a 1M TPM limit that's only 20 requests a minute.
  • Concurrency (Little's law: work in flight = rate × time each item takes): 20 requests/minute × 2 s each ≈ 0.7 requests in flight, so a couple of workers suffice. More workers than your limits allow just collect 429s.
  • Backoff: on a 429, wait for the Retry-After header if present, otherwise back off exponentially with random jitter (so workers don't retry in lockstep), and cap total attempts. If you manage retries yourself, disable the SDK's built-in ones to avoid nested retry loops (both from OpenAI's rate-limit guide). The same guide warns that above ~1M TPM, ramping traffic faster than ~50% every 15 minutes can trigger slow-down errors: warm up a backfill, don't slam it.
  • Batch APIs trade latency for price and headroom. OpenAI's Batch API is 50% cheaper, uses a separate rate-limit pool, and completes within 24 hours (up to 50,000 embedding inputs per batch). Perfect for backfills; useless for “this edit should be searchable in a minute”. That's why Notion ran two paths: batch jobs for onboarding whole workspaces, and a streaming path (Kafka consumers) for live edits.
  • Self-hosting an open embedding model on GPUs removes rate limits and per-token fees but adds a cluster to run (Lesson 7.4). Figma serves its model on SageMaker; Notion began moving its embedding pipeline to Ray in 2025.
✏️ Worked example: how long is the backfill?

You're switching all 2M docs (6B tokens, 12M chunks) to a new embedding model.

  • Sync API at 1M TPM, 100 chunks per request: 6B ÷ 1M = 6,000 min = 100 h. At 5M TPM: 20 h. Cost $120 on the small model, $780 at $0.13/1M on the large one.
  • Batch API: 12M inputs ÷ 50,000 per batch = 240 batches, well under the 2,000-per-hour creation limit. The real cap is the queued tokens per model limit on your account: if it's 2B tokens, you submit 3 waves, each finishing within 24 h. Cost $60 (small) or $390 (large).
  • Storage: 74 GB of raw vectors per index, and you'll hold two indexes until the old one is deleted (3,072 dimensions on the large model doubles it again).

The dollars are small. The calendar is not: plan the backfill like a database migration, with a timeline.

Backfills: changing the model or the chunker without downtime

Vectors from two different embedding models live in different spaces: a query embedded with model B compared against chunks embedded with model A returns noise. So you can't upgrade “gradually in place”. The standard move is blue-green (two full copies, “blue” serving while “green” is built):

  1. Provision v2: a new collection/index, and pipeline code with the new model or chunker version.
  2. Backfill: run every document through the v2 pipeline (batch API, high concurrency off-peak).
  3. Keep v2 current: either dual-write (live edits go to both v1 and v2 during the backfill) or record a change log and replay it after. Skip this and v2 is missing everything edited during a multi-day backfill.
  4. Validate: counts per source, spot checks, and your retrieval eval (recall@k on a golden question set, Lesson 5.4) must be at least as good as v1. Optionally shadow real queries to both.
  5. Cut over: point the alias at v2 and switch the query embedder to the new model in the same release. Qdrant documents that alias changes are atomic, so concurrent queries aren't affected.
  6. Keep v1 for a rollback window (days), then delete it.

Notion did exactly this when moving to a new vector database: full re-index with a newer embedding model, migrated “generations one at a time, validating correctness before moving to the next.”

Multimodal documents at scale

OCR and vision captioning (Lessons 3.2 and 4.5) are the expensive, slow stages, so they get their own queue, their own (often GPU) worker pool and their own autoscaling. Route only what needs them: a page with a usable text layer skips OCR; a page with no text, or with charts and figures, goes to the vision stage. Measure per stage: Figma found its major compute cost came not from embedding but from identifying and rendering thumbnails of designs, and attacked that stage (a Ruby → C++ rewrite, cheaper CPU rendering, autoscaling).

🧰 Tools you'll actually use

An async embedding worker with bounded concurrency and your own backoff (OpenAI Python SDK; other providers are similar), then a Dagster asset sketch for scheduling it, then the Qdrant alias swap for cut-over.

import asyncio, hashlib, random, uuid
from openai import AsyncOpenAI, RateLimitError, APIConnectionError, InternalServerError

client = AsyncOpenAI(max_retries=0)          # we own retries: no nested retry loops
sem = asyncio.Semaphore(8)                    # at most 8 requests in flight

def chunk_id(doc_id: str, i: int) -> str:      # deterministic → idempotent upserts
    return str(uuid.uuid5(uuid.NAMESPACE_URL, f"{doc_id}:{i}"))

def text_hash(text: str) -> str:
    return hashlib.sha256(text.encode()).hexdigest()

async def embed_batch(batch: list[dict]) -> list[dict]:
    async with sem:
        for attempt in range(6):
            try:
                resp = await client.embeddings.create(
                    model="text-embedding-3-small", input=[c["text"] for c in batch])
                return [{**c, "vector": d.embedding} for c, d in zip(batch, resp.data)]
            except (RateLimitError, APIConnectionError, InternalServerError) as e:
                resp_ = getattr(e, "response", None)
                wait = resp_.headers.get("retry-after") if resp_ else None
                await asyncio.sleep(float(wait) if wait else min(60, 2 ** attempt) * random.uniform(0.5, 1.5))
        raise RuntimeError("retries exhausted")       # caller sends the batch to the DLQ

async def embed_changed(chunks: list[dict], seen: dict[str, str], size: int = 100):
    todo = [c for c in chunks if seen.get(c["id"]) != text_hash(c["text"])]  # hash check
    batches = [todo[i:i + size] for i in range(0, len(todo), size)]
    return await asyncio.gather(*(embed_batch(b) for b in batches), return_exceptions=True)
import dagster as dg

@dg.asset(retry_policy=dg.RetryPolicy(max_retries=3, delay=30, backoff=dg.Backoff.EXPONENTIAL))
def parsed_docs(context: dg.AssetExecutionContext) -> None:
    changed = list_changed_since(load_cursor())          # your connector: new, updated AND deleted
    context.log.info(f"{len(changed)} changed docs")
    write_parsed(parse_all(changed))

@dg.asset(deps=[parsed_docs])
def chunk_embeddings() -> dg.MaterializeResult:
    n = upsert_and_delete(asyncio.run(embed_changed(load_chunks(), load_hashes())))
    return dg.MaterializeResult(metadata={"chunks_upserted": n})

defs = dg.Definitions(
    assets=[parsed_docs, chunk_embeddings],
    schedules=[dg.ScheduleDefinition(name="index_hourly", target=dg.AssetSelection.all(),
                                     cron_schedule="0 * * * *")])
# Cut-over: both alias actions are applied atomically (Qdrant docs)
from qdrant_client import models
qdrant.update_collection_aliases(change_aliases_operations=[
    models.DeleteAliasOperation(delete_alias=models.DeleteAlias(alias_name="docs")),
    models.CreateAliasOperation(create_alias=models.CreateAlias(collection_name="docs_v2", alias_name="docs")),
])   # ship the query-embedder switch in the same release

For bulk backfills, write the same requests as JSONL lines (each with a custom_id = your chunk ID) and submit them with client.batches.create(input_file_id=…, endpoint="/v1/embeddings", completion_window="24h"). 🚀 Startup vs big tech

Startup

One worker process, a Postgres table of (chunk_id, text_hash, pipeline_version), pgvector, and a cron job or a light orchestrator. Deterministic IDs and delete handling from day one: they cost nothing now and are miserable to retrofit. Backfills run overnight through a batch API into a new table, then a rename.

Big tech

Two paths (bulk batch jobs on Spark or Ray for onboarding and backfills, streaming consumers on Kafka for live edits), per-tenant namespaces, self-hosted embedding on GPUs, freshness and DLQ SLOs with on-call, blue-green for every model or chunker change, and per-stage cost dashboards. Notion and Figma both describe this shape.

🎤 Interview angle

“Design the indexing pipeline for 50 million documents across five SaaS sources, updated continuously. Next quarter we'll change embedding models.” A senior answer:

  • Draws the stages with queues between them, sizes throughput with the rate-limit math, and separates OCR/vision as its own scaled stage.
  • Makes it idempotent: source doc IDs, deterministic chunk IDs, content hashes, upserts, tombstones for deletes, a DLQ with replay.
  • Runs two paths: streaming incremental for freshness (with a debounce) and bulk batch for onboarding and reconciliation.
  • Plans the model change as a blue-green backfill: new index, batch API, dual-write, eval-gated validation, atomic alias flip together with the query embedder, rollback window.
  • Names the metrics: index lag, DLQ depth, retry rate, chunks per doc, cost per doc.
🏭 In the real world
Hash-based change detection and a full re-index 🏢 Notion · 2026 Two years of vector search at Notion

How: offline Spark batch jobs plus online Kafka consumers; per-span text and metadata hashes (xxHash64, stored in DynamoDB); a full re-index with a newer embedding model during a database migration, cut over one generation at a time.

Why this method: 70% less data through the pipeline from the hashes; the migration cut search-engine spend by 60% and improved p50 query latency from 70–100 ms to 50–70 ms.

Discrete jobs, debounced indexing 🏢 Figma · 2024 The infrastructure behind AI search in Figma

How: separate queued jobs for identifying designs and thumbnailing, batch embedding on a SageMaker endpoint, then writing to OpenSearch; indexing debounced to at most every four hours.

Why this method: separate jobs gave precise control over batching and retries; the debounce meant processing only 12% of the data; most compute went to the pre-embedding stages, so that's where they optimized.

Half-price bulk embedding 🏢 OpenAI · docs Batch API guide

How: upload a JSONL file of requests, get results within a 24-hour window; embeddings batches hold up to 50,000 inputs.

Why this method: 50% discount and a separate rate-limit pool that doesn't eat the limits your live pipeline needs. The guide lists “embedding content repositories” as a target use case.

Atomic cut-over with aliases 🧰 Open source Qdrant collection aliases

How: queries use an alias; build a second collection in the background (e.g. with a new model), then delete and re-create the alias in one call.

Why this method: alias changes happen atomically, so no concurrent request is affected, and rolling back is one more alias change.

Check yourself

1. 1 million documents × 2,000 tokens each, embedded on a sync API with a 1M tokens-per-minute limit. Roughly how long?
2 billion tokens ÷ 1M per minute = 2,000 minutes ≈ 33 hours, if you batch well enough that TPM is the bottleneck. A batch API with its own limits, or a higher tier, shortens it; one chunk per request would make it far longer.
2. After switching to a new embedding model, the team started writing new-model vectors into the live index as documents changed. Within days, retrieval quality collapsed. Why, and what's the fix?
Each model has its own vector space: similarity between a model-A vector and a model-B vector is meaningless. Upgrades are blue-green: full backfill into a new index, dual-write or replay changes, eval-gated validation, then an atomic cut-over of index and query model.
3. Each nightly re-run of your indexing job makes the index grow by the size of the corpus, and search starts returning the same passage several times. Most likely cause?
Idempotency needs deterministic IDs: doc ID + chunk position (or a UUID derived from them). Then a re-run overwrites, a hash check skips unchanged chunks, and stale chunks (a doc that shrank or was deleted) are explicitly deleted.
📝 TL;DR
  • The index is a derived dataset: stages with queues, stable doc and chunk IDs, content hashes, upserts, deletes and a DLQ.
  • Re-embed only what changed (hashes, cursors, debouncing); reconcile with a periodic full check.
  • Throughput = the smallest of TPM, RPM × tokens per request, and worker capacity. Batch many chunks per request, bound concurrency, back off with jitter, use batch APIs for bulk.
  • Model or chunker change = blue-green backfill: new index, dual-write, eval-gated validation, atomic alias flip with the query embedder, rollback window.
