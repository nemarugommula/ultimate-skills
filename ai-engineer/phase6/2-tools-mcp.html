Tool design & the Model Context Protocol (MCP)

The model only knows a tool by its name, its description and its input schema. Write those badly and a brilliant model calls the wrong one. MCP is the standard way to plug tools into any AI app.

🧰 You'll need (quick reminders)
  • The agent loop: model asks for a tool call, your code runs it, the result goes back into the context (Lesson 6.1).
  • Function calling and JSON Schema: a tool is declared as a name, a description and a JSON Schema for its arguments (Lesson 1.3).
  • Tokens: tool definitions are sent with every call and cost tokens like any other prompt text (Lesson 0.3).
🎯 Hook

When Anthropic built its agent for SWE-bench (a benchmark of real GitHub issues to fix), the team wrote that they spent more time optimizing the tools than the overall prompt. One example: the model kept making mistakes with relative file paths after it had moved out of the root directory. The fix wasn't a smarter model or a longer prompt. They changed the tool to always require absolute file paths, and the model then used it flawlessly.

They gave the idea a name: the agent–computer interface (ACI). You design it with the same care as a human UI, because the model is its user.

Two lessons hide in that table. Every tool you add is paid for on every call (in a 10-step agent, ten times). And more tools means more chances to pick the wrong one, especially when names and descriptions overlap.

💡 Big idea A tool definition is a prompt. The model chooses tools by reading names and descriptions, fills arguments by reading the schema, and decides its next move by reading your tool's output and errors. Design all four for a reader who is smart, literal, and has never seen your codebase.
🧠 Analogy: labels on a breaker panel

A fuse box labelled “circuit 1, circuit 2, misc” makes even an expert electrician guess. “Kitchen sockets (not the oven)” doesn't. The electrician didn't get smarter; the labels did. Tool names and descriptions are those labels, and “not the oven” (when not to use it) is often the most useful part.

Anatomy of a good tool

Part❌ Vague✅ Clear
Nameprocesspayments_issue_refund: a namespace prefix (payments_) plus verb + object
Description“Processes the request.”What it does, when to use it, when not to, what it returns, side effects: “Sends money back for one order. Use only when the user explicitly asks for a refund. Not for questions about the refund policy.”
Input schema{"data": "string"}Typed fields, enums for fixed choices, formats and examples: order_id “like ORD-1042”, reason ∈ {damaged, late, other}
OutputA raw 4,000-token API dump with UUIDsOnly high-signal fields, human-readable names, paginated or truncated with a note on how to get more
Errors“Error 400”“order_id must look like ORD-1042 (got 1042)”: an error the model can act on
SafetyOne run_sql tool that can do anythingRead and write tools separated; writes idempotent (an idempotency key makes a retry safe) and gated by approval when risky (Lesson 6.6)

Few vs many tools. Prefer a few tools that match tasks (schedule_event that finds a free slot and books it) over many thin wrappers around every API endpoint (list_users, list_events, create_event), which make the model do the plumbing and burn tokens. When you really need hundreds, load them on demand (tool search) or split them across specialised agents (Lesson 6.5).

The Model Context Protocol (MCP)

Before MCP, every AI app wrote its own connector for every system: your IDE assistant, your chat app and your support bot each needed their own GitHub, Jira and database integration. MCP, the Model Context Protocol, is an open standard (introduced by Anthropic in November 2024, donated to the Linux Foundation's Agentic AI Foundation in December 2025) so that a tool server written once works in any app that speaks MCP.

✏️ Worked example: why a protocol pays off

Your company has 4 AI apps (IDE assistant, chat, support bot, an internal agent) and 6 systems (GitHub, Jira, Postgres, Slack, Drive, billing).

  • Without a standard: every app × every system = 4 × 6 = 24 integrations to build, secure and maintain.
  • With MCP: 6 servers (one per system) + 4 clients (one per app, usually built into the framework) = 10. A 7th system adds 1 server, not 4 integrations.
  • Token check: if all 6 servers expose 10 tools each at ≈950 tokens, that's ≈57,000 tokens of definitions per call. Connect only the servers a task needs, or use tool search.

It's the same N × M → N + M argument that made USB and the Language Server Protocol (used by code editors) win.

PieceWhat it isExample
HostThe AI application the user runs; it owns the model and the UIA desktop chat app, an IDE, your agent service

Transportsstdio: the host launches the server as a local subprocess and they exchange newline-delimited JSON. Streamable HTTP: each message is an HTTP POST to one endpoint; the reply is JSON or a stream (SSE, server-sent events)Local tools vs remote, shared servers (with OAuth 2.1 authorization)

Messages are JSON-RPC 2.0: a small standard where each request has an id, a method and params, and each response has the same id and either a result or an error. The field moves fast: the current spec version (2026-07-28) made MCP stateless, replacing the old initialize handshake with a server/discover call and per-request metadata, and deprecated the Roots, Sampling and Logging features. 🧰 Tools you'll actually use

The official MCP SDKs (Python, TypeScript and others), the MCP Inspector for testing servers, and the provider SDKs and frameworks that act as MCP clients (Claude Agent SDK, OpenAI Agents SDK, LangGraph via adapters). In v2 of the Python SDK (as of 2026) the high-level class is MCPServer (it was called FastMCP before); type hints and docstrings become the tool's schema and description.

from mcp.server import MCPServer
from mcp.server.mcpserver.exceptions import ToolError

mcp = MCPServer("orders")

@mcp.tool()
def orders_get_status(order_id: str) -> str:
    """Look up where an order is: shipped or not, tracking link, delivery date.
    Use when the user asks where their parcel is. order_id looks like ORD-1042."""
    if not order_id.startswith("ORD-"):
        # ToolError → a result with isError: true and this message, so the model can fix its call
        raise ToolError(f'order_id must look like "ORD-1042" (got "{order_id}")')
    o = db.get_order(order_id)
    return f"{o.id}: {o.status}, delivered {o.delivered_on}, tracking {o.tracking_url}"  # high-signal only

if __name__ == "__main__":
    mcp.run(transport="stdio")        # or "streamable-http" for a remote server

Test it with uv run mcp dev server.py (opens the Inspector). Lesson 6.9 goes further: remote deployment, authorization and securing a server. Raise ToolError for errors the model should see; any other exception is treated as a crash and the model learns only that the call failed. The spec also defines tool annotations (readOnlyHint, destructiveHint, idempotentHint, openWorldHint) so hosts can decide what needs confirmation; clients must treat them as untrusted unless the server is trusted.

🚀 Startup vs big tech

Week one

3–8 task-level tools as plain functions in your agent, with careful descriptions and actionable errors. Write 20 test prompts with the expected tool and check tool-selection accuracy on every description change. Wrap in an MCP server only when a second app needs the same tools.

At scale

An internal MCP registry of vetted servers, OAuth-scoped per user, tool-search or per-task tool subsets to keep definitions small, tool-selection evals in CI, audit logs of every call, and a review process for third-party servers like any other dependency.

🎤 Interview angle

“Our agent keeps calling the wrong tool. What do you do?” A senior answer:

  • Reads traces to see which tools get confused, then fixes names and descriptions first (namespaces, when-to-use and when-not-to-use, examples).
  • Reduces overlap: merges thin tools into task-level ones, removes tools a task doesn't need, or loads them on demand.
  • Makes errors actionable and outputs concise, and separates read from write tools.
  • Measures tool-selection accuracy on a labelled prompt set before and after (Lesson 5.5), and explains where MCP fits (standard plumbing, not a fix for bad descriptions).
🏭 In the real world
The agent–computer interface 🏢 Anthropic · 2024 Building effective agents (appendix on tools)

How: for the SWE-bench agent, tools were iterated like a UI: test how the model uses them, then change formats and parameters (absolute paths only) so mistakes become hard to make.

Why this method: the team found tool design mattered more than the overall prompt; “poka-yoke” (mistake-proofing) the arguments removed a whole class of errors.

Tools written and tested with agents 🏢 Anthropic · 2025 Writing effective tools for agents

How: namespacing related tools under common prefixes, returning only high-signal information, pagination/filtering/truncation with sensible defaults, and prompt-engineered error messages; evaluated with realistic tasks.

Why this method: agents have limited context and read everything literally; Claude Code caps tool responses at 25,000 tokens by default for the same reason.

Loading tools on demand 🏢 Anthropic · 2025 Introducing advanced tool use

How: instead of sending all tool definitions, the model gets a search tool and loads only the definitions it needs.

Why this method: 58 tools from 5 servers cost ≈55K tokens up front; on-demand loading cut that by 85% and raised tool-selection accuracy on their MCP eval (Opus 4: 49% → 74%).

A neutral home for the protocol 📜 History · 2024–2025 MCP donated to the Agentic AI Foundation

How: open-sourced by Anthropic on 25 Nov 2024; on 9 Dec 2025 donated to the Agentic AI Foundation, a fund under the Linux Foundation, alongside Block's goose and OpenAI's AGENTS.md.

Why this method: a standard only wins if competitors can trust it; vendor-neutral governance makes it safe for every provider and tool vendor to build on.

Strict schemas, few functions 🏢 OpenAI · 2025 Function calling guide

How: recommends always enabling strict mode so calls follow the schema, and (softly) fewer than 20 functions available at the start of a turn.

Why this method: schema-valid arguments remove a whole class of parse errors, and a short tool list keeps selection accurate.

Check yourself

1. Your agent has 40 tools at about 500 tokens each and runs 10 model calls per task. How many tokens go on tool definitions per task?
40 × 500 = 20,000 tokens per call, resent on each of 10 calls = 200,000 tokens, before any actual work. Caching helps the price, but trimming tools or loading them on demand helps price, latency and accuracy.
2. Users ask “what's your refund policy?” and your agent sometimes calls refund and actually refunds an order. What's the best fix?
The model picked the tool whose label matched the words. Clear names, when-not-to-use guidance and a proper tool for the other intent fix the selection; an approval gate (Lesson 6.6) limits the damage when it still goes wrong.
3. An MCP tool is called with a date in the past. How should the server report it?
The spec separates protocol errors (unknown tool, malformed request → JSON-RPC errors) from tool execution errors (bad input, API failure, business rules → isError: true in the result). The latter should go to the model so it can correct itself.
📝 TL;DR
  • The model sees only name, description, schema, output and errors: design them like a UI for a literal reader.
  • Say when to use a tool and when not to; namespace names; prefer few task-level tools; keep outputs short; make errors actionable.
  • Tool definitions cost tokens on every call (≈55K for 58 tools in one real example): load only what the task needs.
  • MCP: hosts contain clients that talk JSON-RPC to servers exposing tools, resources and prompts, over stdio or Streamable HTTP. Current spec: 2026-07-28.
