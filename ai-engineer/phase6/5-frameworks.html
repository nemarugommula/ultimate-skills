Phase 6 · Lesson 5

Multi-agent systems & frameworks (LangGraph, Agents SDKs, CrewAI)

Several agents can search in parallel and keep their contexts small, at a multiple of the cost. Every handoff between them is a place where information gets lost. And there's a framework for every taste.

🧰 You'll need (quick reminders)
  • The agent loop and its cost growth (Lesson 6.1); tools and MCP (6.2).
  • Orchestrator–workers: a planner model spawns workers and merges their results (Lesson 6.3).
  • Memory and context: each agent only knows what's in its own prompt (Lesson 6.4).
🎯 Hook

In June 2025, two well-known agent teams published on consecutive days. On 12 June, Cognition (makers of the Devin coding agent) posted “Don't Build Multi-Agents”: splitting work across agents that don't share full context leads to conflicting decisions. On 13 June, Anthropic described its multi-agent research system: a lead agent with parallel subagents beat a single agent by 90.2% on its internal research eval.

Both were right. Anthropic's own post says most coding tasks have fewer truly parallel parts than research, and that its multi-agent system uses about 15× the tokens of a chat. Whether multiple agents help depends on the shape of the task, and you can reason about it before writing any code.

On Anthropic's browsing benchmark (BrowseComp), token usage alone explained 80% of the variance in performance. Multi-agent systems mostly work by letting you spend more tokens in parallel, each subagent with its own clean context. That's worth it for broad, valuable, parallelisable work (research, due diligence), and wasteful for tightly coupled work (most code changes), where agents need to see each other's decisions.

💡 Big idea Use multiple agents when the work splits into independent parts that each need lots of context or different tools. Don't when the parts share decisions. And at every handoff, ask: what does the next agent need to know, and is it actually getting it? Context lost at a handoff is the #1 multi-agent bug.
🧠 Analogy: a relay race vs a research team

A relay works because the baton is simple: one object, passed in full. Hand over a sticky note that says “finish the race” and the next runner may head the wrong way. A research team works well in parallel: five people read five sets of sources, then an editor merges notes. But ask five people to each paint one fifth of a mural without seeing the others' sections, and the styles won't match. That mural is a coding task; Cognition's example was two subagents building the background and the bird of a Flappy Bird clone in clashing styles.

Cognition's two principles are a good checklist for any of these: share context (full agent traces, not just a one-line message), and remember that actions carry implicit decisions: two agents acting on different assumptions produce conflicting results.

✏️ Worked example: is multi-agent worth it here?

A due-diligence report on a company: read filings, news, patents, reviews, hiring data. Single agent: 40 sequential steps, ≈6 s each = 240 s; its context passes 150,000 tokens and it starts missing details. Multi-agent: a lead plans (10 s), 5 subagents each do 8 steps in parallel (≈48 s) with small contexts, then the lead synthesises (20 s) = ≈78 s.

  • Speed: 240 s → 78 s, about 3× faster.
  • Cost: if the single agent costs $0.80, at roughly 15 ÷ 4 ≈ 3.75× the tokens the multi-agent run costs about $3.
  • Decision: for a $10,000 investment decision, yes. For a free-tier chatbot answering “summarise this article”, no.

Rule of thumb: multi-agent pays when the task is valuable, broad and parallel. Measure on your eval set before committing.

Agent-to-agent: A2A

MCP connects an agent to tools and data. A2A (Agent2Agent), launched by Google in April 2025 and moved to the Linux Foundation in June 2025, connects agents to other agents, possibly built by other companies with other frameworks. An agent publishes an Agent Card (a JSON description of its skills and endpoint, at /.well-known/agent-card.json); clients send it tasks, stateful units of work with an ID that can run for a long time and stream updates, over HTTP with JSON-RPC 2.0 and server-sent events. The spec reached version 1.0 in 2026. Rule of thumb: inside one codebase, call your own agents as functions; across team or company boundaries, A2A gives a contract.

🧰 Tools you'll actually use

Handoffs and agents-as-tools in the OpenAI Agents SDK (Python). The same two patterns exist in LangGraph (subgraphs, Command to jump to another node), ADK and the Microsoft Agent Framework under different names.

from agents import Agent, Runner, function_tool

@function_tool
def search_flights(origin: str, dest: str, date: str, earliest_departure: str = "00:00") -> str:
    """Search flights. date is YYYY-MM-DD; earliest_departure is HH:MM local time."""
    ...

flights = Agent(name="Flights", tools=[search_flights],
                instructions="Book flights. Respect EVERY user constraint you are given.")
food = Agent(name="Food", instructions="Suggest restaurants that respect dietary needs.")

# 1) Supervisor: specialists as tools; the lead keeps control and merges results
planner = Agent(
    name="Trip planner",
    instructions="Plan the trip. When calling a specialist, pass ALL constraints: dates, budget, diet, times.",
    tools=[flights.as_tool(tool_name="book_flights", tool_description="Find and book flights"),
           food.as_tool(tool_name="find_food", tool_description="Find restaurants")],
)
result = Runner.run_sync(planner, "3 days in Lisbon from 12 June, vegetarian, €600 total, no flights before 10:00",
                         max_turns=10)
print(result.final_output)

# 2) Handoffs: control transfers to the specialist, which continues the conversation
triage = Agent(name="Triage", instructions="Route to the right specialist.", handoffs=[flights, food])

Tracing is on by default in this SDK: read the traces to see exactly what each agent received. In the Claude Agent SDK the equivalent knobs are ClaudeAgentOptions(allowed_tools=…, mcp_servers=…, max_turns=…).

🚀 Startup vs big tech

Week one

One agent, plain SDK or the lightest framework your team likes. Add a second agent only for a measured reason (parallel speed, a context that won't fit, tools that confuse each other), and pass full constraints explicitly. Read the traces.

At scale

A standard framework across teams, shared tracing and evals, a registry of internal agents with typed interfaces (A2A or plain APIs), per-agent budgets and permissions, and an architecture review asking “why isn't this one agent?”

🎤 Interview angle

“Would you use multiple agents for this?” A senior answer:

  • Asks whether the work is parallel and independent or coupled (shared decisions), and how valuable each task is.
  • Quotes the cost: roughly 4× tokens for an agent and 15× for multi-agent vs chat in Anthropic's measurements.
  • Designs the handoffs: what context passes, how constraints are preserved, how conflicts are resolved (one decider).
  • Picks a framework for concrete needs (state, human approval, language, provider) and explains MCP (tools) vs A2A (agents).
🏭 In the real world
Lead agent + parallel subagents 🏢 Anthropic · 2025 How we built our multi-agent research system

How: a Claude Opus 4 lead plans, spawns Claude Sonnet 4 subagents that search in parallel with their own context windows, and synthesises.

Why this method: 90.2% better than single-agent Opus 4 on their research eval, because breadth-first research parallelises; at about 15× chat tokens, so reserved for valuable tasks.

The case against 🏢 Cognition · 2025 Don't Build Multi-Agents (Walden Yan)

How: argues for single-threaded agents with full shared context, plus compression for long tasks, over parallel subagents.

Why this method: share full traces, not messages; actions carry implicit decisions, and parallel agents make conflicting ones (the mismatched Flappy Bird example).

Handoffs as a primitive 🧰 Open source OpenAI Agents SDK: handoffs

How: a handoff is exposed to the model as a tool; calling it transfers the conversation to another agent, optionally with input filters that control what history passes.

Why this method: it replaced the experimental Swarm with a maintained, traced primitive, making “what context travels” an explicit, configurable choice.

A protocol between agents 📜 History · 2025 Linux Foundation launches the A2A project

How: Google announced A2A on 9 April 2025; on 23 June 2025 it became a Linux Foundation project, with agent cards, tasks and JSON-RPC over HTTP.

Why this method: agents from different vendors need a neutral contract, the same reason MCP moved to a foundation for tools.

Consolidating frameworks 🏢 Microsoft · 2025–2026 Microsoft Agent Framework overview

How: merges AutoGen's agent abstractions with Semantic Kernel's enterprise features and adds graph-based workflows; the AutoGen repo is archived and points here.

Why this method: two overlapping frameworks confused users; one supported successor with explicit workflows is easier to run in production.

🤯 Fun fact · one day apart

“Don't Build Multi-Agents” (12 June 2025) and “How we built our multi-agent research system” (13 June 2025) were published a day apart, and they mostly agree once you read past the titles: multiple agents for parallel research, a single context for tightly coupled work like code.

Multi-agent systems are orchestrator–workers (6.3) with agents as workers, each a loop (6.1) with its own tools (6.2) and memory (6.4). Check yourself

1. A chat answer uses 2,000 tokens. Using Anthropic's rough multipliers, about how many tokens would a multi-agent system use for a comparable request?
Multi-agent ≈ 15× chat: 2,000 × 15 = 30,000. A single agent is ≈ 4× (8,000). The gap is why multi-agent is reserved for tasks valuable enough to pay for it.
2. You split a feature change across three parallel coding subagents (API, UI, tests). The pieces don't fit together: different field names and assumptions. What's the best fix?
The parts share implicit decisions (names, types, contracts). Parallel agents with partial context make conflicting choices. Keep coupled work in one context, or fix the shared decisions up front.
3. Your travel agent must call a partner company's hotel-booking agent, built on a different framework. Which protocol fits?
A2A is designed for agent-to-agent calls across vendors and frameworks: agent cards for discovery, long-running stateful tasks, streaming updates. MCP is for exposing tools and data to an agent.
📝 TL;DR
  • Multi-agent ≈ 15× chat tokens (single agent ≈ 4×). Worth it for valuable, broad, parallel work; not for coupled work.
  • Architectures: single agent, supervisor (agents as tools), handoffs, network, hierarchical.
  • Handoffs lose information: pass constraints explicitly, prefer full context for coupled work, one decider per decision.
  • Frameworks (2026): LangGraph, OpenAI Agents SDK, Claude Agent SDK, CrewAI, Microsoft Agent Framework, Google ADK, LlamaIndex, Pydantic AI. MCP = tools; A2A = agents.
