Phase 6 · Lesson 8

Build an agent from scratch: the raw loop, parsing, errors & testing

The happy path of an agent is twenty lines. The other forty decide what happens when the model sends bad arguments, a tool throws, the API says “slow down”, or the loop won't stop. Then you need tests that catch all of it without paying for a model on every run.

🧰 You'll need (quick reminders)
  • The agent loop: call the model → run the tools it asks for → append the results → repeat until a final answer or a stop condition (Lesson 6.1).
  • Function calling: tools are described with JSON Schema; the model answers with a structured call (Lesson 1.3). Tool errors should be actionable (Lesson 6.2).
  • Agent evals: success rate over many runs, judged by code or a model (Lessons 5.3, 5.5).
🎯 Hook

In April 2025, Thorsten Ball, an engineer working on the Amp coding agent, published “How to Build an Agent”. His claim: a code-editing agent that reads files, lists directories and edits code, the kind of thing that looks like magic in a demo, takes less than 400 lines of Go, most of it boilerplate, with three tools. His summary of what's inside: “an LLM, a loop, and enough tokens.”

He's right about the core, and it's the best way to demystify agents. But the gap between that weekend agent and one you can put in front of customers is everything this lesson covers: malformed calls, failing tools, rate limits, runaway loops, and tests that prove each of those is handled.

Numbers first: rare failures are common in loops

An agent makes many calls per task, so a failure that's rare per call becomes likely per run (the same compounding as Lesson 6.6, applied to plumbing).

Per-call failure (illustrative)Calls per runRuns that hit it at least onceWith the right handling
Model API returns 429 “rate limited” on 2% of calls20 model calls1 − 0.98²⁰ = 33%2 retries with backoff: 1 − (1 − 0.02³)²⁰ ≈ 0.016% of runs fail
Text-parsed tool call is malformed 3% of the time20 steps1 − 0.97²⁰ = 46%Native function calling with strict schemas: OpenAI measured 100% schema adherence vs under 40% before
A tool throws (timeout, bug, API down) 5% of the time10 tool calls1 − 0.95¹⁰ = 40%Return the error as an observation; the model retries or works around it

Retry math assumes independent failures; real 429s cluster, which is why backoff waits longer each time. The 100% vs <40% figure is OpenAI's own eval of complex JSON-schema following (gpt-4o-2024-08-06 with Structured Outputs vs gpt-4-0613), August 2024.

Without handling, a third of runs crash on rate limits and nearly half on parsing. With it, both nearly vanish. That's why the “boring” code is most of a production agent.

💡 Big idea Every failure in an agent must land in exactly one of three buckets: an observation (the model can fix it: bad arguments, a tool error), a retry (infrastructure can fix it: 429s, timeouts, 5xx), or a stop (a human must fix it: max turns, budget, a spend cap, a refusal). A failure that lands in none of them is a crash. Then test each bucket with a fake model, so the tests are fast, free and deterministic.
🧠 Analogy: training a pilot

You don't test a pilot only by flying passengers. You check each instrument on the ground (unit tests for tools). You put them in a simulator and script the weather: engine failure at 3,000 feet, every time (a mocked model that returns exactly the bad tool call you want). You fly real test flights on a quiet route (integration tests with the real model). And every real flight's black box is kept, so after any change you can replay the recording and see whether the new system would have done the same thing (recorded trajectories as regression tests).

Two ways to get a tool call out of a model

The old way: text parsing. Before native function calling, ReAct agents asked the model to write a fixed text format, stopped generation at “Observation:”, and parsed the text with a regular expression:

Thought: I need the order's status first. Action: get_order Action Input: {"order_id": "ORD-1042"} Observation: ← generation stopped here (a stop sequence); your code runs the tool and pastes the result match = re.search(r"Action: (\w+)\nAction Input: (.*)", text) # hope for the best

It works in demos and fails in four ways in production: the model writes “Action: Get order”, emits invalid JSON (a trailing comma, single quotes), adds prose after the JSON, or, if the stop sequence is missing, writes the Observation itself, hallucinating a tool result your code never produced.

The current way: native tool calling. In June 2023 OpenAI shipped function calling, with models fine-tuned to detect when to call a function and to answer with JSON that fits its signature; every major provider followed. The model now returns a typed block with a name, arguments as JSON and an id; you send back a result referencing that id. Strict modes constrain generation to your schema. Parallel calls in one turn come for free. As of 2026 the shapes are:

Anthropic Messages APIOpenAI Responses API
Declare a tool{"name", "description", "input_schema"} (+ "strict": true){"type": "function", "name", "description", "parameters", "strict": true}
Model asks for a calla tool_use content block {id, name, input}; stop_reason == "tool_use"an output item {"type": "function_call", call_id, name, arguments} (arguments is a JSON string)
You send the result{"type": "tool_result", "tool_use_id", "content", "is_error"} inside a user message; all results of a turn in one message{"type": "function_call_output", "call_id", "output"} appended to the input

The loop, in about 60 lines

Lesson 6.1 showed the 25-line happy path. Here's the version with the other buckets filled in: a tool registry, schema validation, errors as observations, a timeout per tool, output capping, retries, and a hard stop. Anthropic's Python SDK as of 2026; the OpenAI version differs only in the shapes above.

import json, logging, concurrent.futures as cf
import anthropic
from jsonschema import Draft202012Validator

client = anthropic.Anthropic(max_retries=4)   # retries 408/409/429/5xx + connection errors, with backoff
MODEL, MAX_TURNS, TOOL_TIMEOUT_S, MAX_RESULT_CHARS = "claude-opus-5-5", 12, 20, 8000
pool = cf.ThreadPoolExecutor(max_workers=8)
TOOLS = {}                                      # name -> (function, JSON Schema)
log = logging.getLogger("agent")
class AgentStopped(Exception): pass                # bucket: stop (carries the transcript)

def tool(schema):
    def register(fn):
        TOOLS[fn.__name__] = (fn, schema)
        return fn
    return register

@tool({"type": "object", "additionalProperties": False, "required": ["order_id"],
       "properties": {"order_id": {"type": "string", "pattern": "^ORD-[0-9]+$"}}})
def get_order(order_id):
    """Look up one order: status, delivery date, total. order_id looks like ORD-1042."""
    return orders_api.get(order_id)

def run_tool(block):
    if block.name not in TOOLS:                                   # bucket: observation
        return f"Unknown tool {block.name!r}. Available: {', '.join(TOOLS)}", True
    fn, schema = TOOLS[block.name]
    errors = [e.message for e in Draft202012Validator(schema).iter_errors(block.input)]
    if errors:
        return f"Invalid arguments for {block.name}: {'; '.join(errors)}", True
    future = pool.submit(fn, **block.input)
    try:
        out = json.dumps(future.result(timeout=TOOL_TIMEOUT_S), default=str)
        return out[:MAX_RESULT_CHARS], False                         # cap what enters the context
    except cf.TimeoutError:
        return f"{block.name} timed out after {TOOL_TIMEOUT_S}s. Try again or another way.", True
    except Exception as e:                                          # tool bug, API down, ...
        return f"{type(e).__name__}: {e}", True

def run_agent(question, system=""):
    tool_defs = [{"name": n, "description": fn.__doc__, "input_schema": s} for n, (fn, s) in TOOLS.items()]
    messages = [{"role": "user", "content": question}]
    for turn in range(MAX_TURNS):
        try:
            resp = client.messages.create(model=MODEL, max_tokens=16000, system=system,
                                          tools=tool_defs, messages=messages)
        except anthropic.RateLimitError as e:                        # retries exhausted: bucket stop
            raise AgentStopped("rate limited after retries", messages) from e
        messages.append({"role": "assistant", "content": resp.content})  # unchanged, incl. thinking blocks
        if resp.stop_reason == "end_turn":
            return "".join(b.text for b in resp.content if b.type == "text")
        if resp.stop_reason != "tool_use":                           # max_tokens, refusal, ...
            raise AgentStopped(f"stop_reason={resp.stop_reason}", messages)
        results = []
        for block in [b for b in resp.content if b.type == "tool_use"]:
            out, is_err = run_tool(block)
            log.info("turn %d tool %s %s error=%s", turn, block.name, block.input, is_err)
            results.append({"type": "tool_result", "tool_use_id": block.id,
                            "content": out, "is_error": is_err})
        messages.append({"role": "user", "content": results})        # ALL results, one message
    raise AgentStopped("max turns reached", messages)                # escalate with the transcript

Details that matter, each one a real bug in someone's first agent:

  • Append the assistant content unchanged, including any thinking blocks, and return every tool_result for a turn in one user message, each with the matching tool_use_id. A missing result makes the next request fail.
  • Validate arguments yourself even with strict modes (not every provider or model enforces them, and streamed inputs can arrive truncated). A validator message like “1042 is not of type 'string'” is an instruction the model can follow; a Python traceback isn't.
  • A thread timeout doesn't kill the thread. The tool keeps running in the background; for real cancellation run risky tools in a subprocess or container, or use async tools that respect cancellation.
  • Not every 429 is temporary. Anthropic's docs note that once an organisation hits its spend cap, requests return 429 with no retry-after header and every retry fails until access resumes. Retry what's transient, and stop and alert on what isn't.
  • Message history is state. Persist messages after every turn (a database row per run) so a crash or deploy can resume, and so you have the trajectory for debugging and tests.

Streaming changes the plumbing, not the loop. For a chat UI, stream text as it's generated with client.messages.stream(...), iterate stream.text_stream, then take stream.get_final_message() and continue the loop with it as before. Tool arguments stream as partial JSON fragments: only run a tool once its block is complete, and validate it first.

What you should see: the happy path takes 3 model calls and 6 messages, and every tool call is followed by a user message carrying its tool_result. Inject the malformed call: with validation on, the error names the problem and the model fixes it in one extra turn. Turn validation off and the tool itself crashes with AttributeError: 'int' object has no attribute 'startswith'; the model can't learn anything from that, retries the same call, and gives up on a question it could have answered. Turn off exception catching too and the whole run dies. A 429 without retries kills the run; with retries it costs 2 seconds. The never-stopping model only ends because max turns fires.

✏️ Worked example: what a timeout really costs

The orders API hangs on 1 call in 50. Your tool timeout is 20 s; a model call takes 1.4 s; a normal tool call 0.4 s. A typical run makes 3 model calls and 2 calls to the orders API.

  • Normal run: 3 × 1.4 + 2 × 0.4 = 5.0 s.
  • Run with one hang: the 20 s timeout, plus one extra model call (1.4 s) to read the error and retry, plus the retry (0.4 s): 5.0 + 20 + 1.4 + 0.4 = 26.8 s.
  • Average over all runs: 5.0 + 0.02 × 2 calls × 21.8 s ≈ 5.9 s, but your p95 latency is now dominated by timeouts.

A 20 s timeout on a call that normally takes 0.4 s is far too generous. Set per-tool timeouts from measured latency (say 3× the p99), and retry once inside the tool before involving the model, which costs a whole extra model call.

Testing an agent: four layers

LayerWhat runsCatchesSpeed and cost
Unit tests for toolsEach tool function alone, with fake upstream APIsWrong logic, bad output formats, oversized outputs, unclear error messagesMilliseconds, free; hundreds of tests
Mocked-LLM loop testsThe real loop with a fake client that returns scripted responses (a malformed call, two parallel calls, a model that never stops)Harness bugs: missing tool_results, crashes on exceptions, no stop condition, retry logicMilliseconds, free, deterministic
Recorded-trajectory replaysReal past runs saved as JSON; replay the recorded model responses through today's harness, and compare the requests and tool calls it makesRegressions from refactors: dropped system prompt, changed tool names, reordered messagesSeconds, free
Integration and end-to-end evalsThe real model with real (sandboxed) tools on a set of tasks, several trials each, scored by code or a judgePrompt and model changes, wrong tool choice, flaky behaviour, real API schema rejectionsMinutes, real tokens; run on important PRs or nightly

The fake client is the key trick. Your loop only needs an object with messages.create; give it one that returns whatever you script, and you can test the 1-in-100 failure on every commit. For end-to-end evals, remember agents are stochastic: a 75% per-trial success rate passes 3 trials in a row only (0.75)³ ≈ 42% of the time, which is why Anthropic recommends reporting pass^k (all k trials succeed) for customer-facing agents, not just pass@k (at least one succeeds).

🧰 Tools you'll actually use

The provider SDKs (anthropic, openai) with their built-in retries and typed errors; jsonschema or Pydantic for validation; pytest with a fake client; tracing (LangSmith, Langfuse, Arize Phoenix or OpenTelemetry) to capture trajectories; and an eval harness (Lesson 5.5). A mocked-LLM test of the loop above:

# test_agent.py: the model is a script, so the loop's logic is tested in milliseconds, for free
from types import SimpleNamespace as NS
import agent

class FakeMessages:
    def __init__(self, script):
        self.script, self.calls = list(script), []
    def create(self, **kw):
        self.calls.append({**kw, "messages": list(kw["messages"])})   # snapshot of what was sent
        return self.script.pop(0)

def call(name, args, id="t1"): return NS(type="tool_use", name=name, input=args, id=id)
def text(t): return NS(type="text", text=t)

def test_tool_exception_becomes_an_observation(monkeypatch):
    fake = FakeMessages([
        NS(stop_reason="tool_use", content=[call("get_order", {"order_id": "ORD-1042"})]),
        NS(stop_reason="end_turn", content=[text("Sorry, the order system is down.")]),
    ])
    monkeypatch.setattr(agent, "client", NS(messages=fake))
    schema = agent.TOOLS["get_order"][1]
    monkeypatch.setitem(agent.TOOLS, "get_order", (lambda **_: 1 / 0, schema))   # the tool crashes

    assert "down" in agent.run_agent("Where is ORD-1042?")
    result = fake.calls[1]["messages"][-1]["content"][0]          # what the model saw
    assert result["is_error"] and "ZeroDivisionError" in result["content"]

def test_runaway_model_hits_max_turns(monkeypatch):
    forever = [NS(stop_reason="tool_use", content=[call("get_order", {"order_id": "ORD-1"}, id=f"t{i}")])
               for i in range(50)]
    monkeypatch.setattr(agent, "client", NS(messages=FakeMessages(forever)))
    monkeypatch.setitem(agent.TOOLS, "get_order", (lambda **_: {"status": "shipped"}, agent.TOOLS["get_order"][1]))
    try:
        agent.run_agent("loop forever")
        assert False, "should have stopped"
    except agent.AgentStopped as e:
        assert "max turns" in str(e)

The same loop with OpenAI's Responses API: resp = client.responses.create(model=..., tools=tools, input=items); append resp.output to items; for each output item with type == "function_call", parse json.loads(item.arguments), run the tool and append {"type": "function_call_output", "call_id": item.call_id, "output": result}; stop when there are no function calls. Model IDs change often: check each provider's models page.

🚀 Startup vs big tech

Week one

Write the loop yourself once (this lesson), with validation, errors as observations, a max-turns cap and logging of every message. Save every trajectory as JSON from day one. Add five mocked-LLM tests for the failure buckets and a 20-task eval you run before each prompt or model change.

At scale

A shared agent runtime (or framework) owned by a platform team: persisted runs that resume after deploys, per-tool timeout and retry policies, concurrency and rate-limit budgets per tenant, idempotent writes, OpenTelemetry traces, thousands of recorded trajectories replayed in CI, and nightly multi-trial evals with pass^k dashboards gating model upgrades.

🎤 Interview angle

“Walk me through how you'd implement and test an agent loop without a framework.” A senior answer:

  • Sketches the loop and the message contract: append assistant content unchanged, one result per tool call matched by id, all results of a turn in one message.
  • Sorts every failure into observation / retry / stop: validation and tool errors back to the model; 429s, 5xx and timeouts retried with backoff (and idempotent writes); max turns, budgets, spend caps and refusals stop with the transcript.
  • Persists the history per run for resumption, debugging and replay.
  • Describes the test pyramid: unit tests for tools, a fake client for loop logic, recorded trajectories for regressions, multi-trial evals with pass^k for behaviour, and which run on every PR versus nightly.
🏭 In the real world
An agent in under 400 lines 🏢 Amp · 2025 How to Build an Agent (Thorsten Ball)

How: a Go program that loops over the Anthropic API with three tools (read_file, list_files, edit_file), appending each tool result to the conversation.

Why this method: to show there's no secret: the capability comes from the model; everything else in a product agent is practical engineering around the loop.

From text parsing to function calling 🏢 OpenAI · 2023 Function calling and other API updates

How: developers describe functions to the model, which was fine-tuned to decide when a function is needed and to reply with JSON matching its signature.

Why this method: a more reliable way to connect models to tools than parsing free text, which every provider then adopted in some form.

Schema-constrained outputs 🏢 OpenAI · 2024 Introducing Structured Outputs in the API

How: strict mode constrains decoding to the developer's JSON Schema, for both responses and function-call arguments.

Why this method: on OpenAI's complex-schema eval, 100% adherence versus under 40% for an earlier model that only followed instructions, removing a whole class of parse failures.

Reliability, not just capability 🏢 Anthropic · 2026 Demystifying evals for AI agents

How: evaluate agents over several trials per task and distinguish pass@k (at least one trial succeeds) from pass^k (all k succeed).

Why this method: a 75% per-trial agent passes 3 out of 3 trials only about 42% of the time; for customer-facing agents, consistency is what users experience.

🤯 Fun fact · the model that answered its own questions

Early text-parsing agents depended on one fragile line: the stop sequence that halts generation at “Observation:”. Forget it, and the model happily continues the pattern, inventing the tool's output and reasoning from it. Native tool calling ended that failure mode structurally: the model's turn ends at the call, and only your code can write the result.

Check yourself

1. Your model API rate-limits 1% of calls, independently, and an agent run makes 30 model calls. Without retries, roughly what share of runs crash?
P(at least one 429) = 1 − 0.99³⁰ ≈ 1 − 0.74 = 26%. Rare per call is common per run. With 2 retries per call, the per-call failure becomes 0.01³ = one in a million, and the per-run rate ≈ 0.003%.
2. The model calls get_order with {"order_id": 1042} and your tool crashes with a KeyError traceback. What should the harness do?
Bad arguments are the model's mistake, so they belong in the observation bucket: an actionable error lets it fix the call next turn. Dropping the call breaks the message contract (every tool_use needs a tool_result), and crashing loses a run the model could have recovered.
3. After a refactor, your agent sometimes stops including the system prompt after the first turn. Which test catches this most cheaply and reliably?
It's a harness bug: deterministic and visible in the requests. A replay or fake-client test inspects exactly what was sent, in seconds and for free. An end-to-end eval might catch it too, but only indirectly, through a quality drop, at real token cost.
📝 TL;DR
  • The loop is short; production is the error handling. Sort every failure into observation, retry or stop.
  • Native tool calling (typed calls with ids, strict schemas, parallel calls) replaced brittle text parsing; still validate arguments yourself.
  • Append assistant content unchanged; one tool_result per tool_use, all in one message; cap tool output; timeout every tool; cap turns.
  • Retries with backoff turn a 33% crash rate into ~0.02%, but not every 429 is temporary.
  • Test in layers: tool unit tests, a fake-client loop test, recorded-trajectory replays, then multi-trial real-model evals (pass^k).
