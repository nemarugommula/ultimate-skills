Phase 6 · Recap

Recap: Agents & tools

From one model call to systems that act: the agent loop and when to avoid it, tools and MCP, workflow patterns, memory, multiple agents, reliability, and the architectures, code and deployments that make agents real.

🧾 Cheat sheet

🔁

6.1 The agent loop

Model → tool call → observation → repeat, until an answer or a stop. Context grows every turn: total tokens ≈ steps², latency ≈ steps. Max steps = cost ceiling. Workflow (your code picks the steps) beats agent when the steps are known. ReAct, provider SDK tool use, Agents SDK max_turns.

🔧

6.2 Tools & MCP

A tool definition is a prompt. Namespaced names, when-to-use and when-not-to, typed schemas, short outputs, actionable errors. 58 tools ≈ 55K tokens: load on demand. MCP: host → client → server (tools, resources, prompts) over stdio or Streamable HTTP; spec 2026-07-28. MCP SDKs, Inspector.

🧩

6.3 Workflow patterns

Tokens = sum of calls; latency = critical path. Chain + gates, routing (can cut cost), parallel sectioning / voting (N×), orchestrator–workers (subtasks unknown), evaluator–optimizer (reachable threshold, round cap). asyncio.gather, LangGraph.

🧠

6.4 Memory

Write · store · read · forget. Window → window + fact-preserving summary → compaction. Long-term: profile in SQL/KV, episodes in vectors; relevance + recency + importance; supersede conflicts; TTL, decay, consolidation; user control. Sessions, checkpointers, Mem0, Letta, memory tool.

👥

6.5 Multi-agent & frameworks

Agent ≈ 4× chat tokens; multi-agent ≈ 15×. Worth it for valuable, parallel work, not coupled work. Handoffs lose context: pass constraints explicitly. MCP = tools, A2A = agents. LangGraph, OpenAI Agents SDK, Claude Agent SDK, CrewAI, MS Agent Framework, ADK.

🛡️

6.6 Reliable agents

0.95²⁰ ≈ 36%: errors compound. Guardrails in/out, least privilege, approvals for irreversible actions (not everything), sandboxes, timeouts + idempotent retries, loop detection, budgets, tracing. Lethal trifecta: remove a leg. Guardrails, interrupt(), hooks, sandboxes.

🗺️

6.7 Agent architectures

Variations on the loop. Planner–executor: plan once, execute cheaply, replan on failure. DAG plans: run independent steps in parallel. Tree-of-thought: explore and score branches, backtrack. Reflection: critique failures and retry with the lesson. Each buys quality with calls.

🛠️

6.8 Agent from scratch

The raw loop, owned end to end. Parse tool calls (strict schemas), turn malformed output, unknown tools and exceptions into observations, bound steps. Unit-test tools as plain functions; integration-test flows with a scripted model and recorded traces.

🔌

6.9 Building MCP servers

Local (stdio) vs remote (Streamable HTTP). Remote servers need authorization (OAuth 2.1), per-user scopes, input validation, rate limits and sanitised outputs. Version, test with the Inspector, and treat every third-party server as untrusted.

🧑‍💻

6.10 Agents in practice

Same loop, different tools and risks. Coding (edit → test → fix, sandboxed), data analysis (run code over data), browsing and computer use (untrusted pages, VMs, human takeover), assistants (memory + approvals). Pick the guardrails per domain.

🗣️ Teach it back (60 seconds)

🎤 The interviewer asks

“Our support team wants an AI agent that looks up orders, answers policy questions and issues refunds. Walk me through how you'd build it, what it costs per conversation, and how you'd stop it from doing something expensive or embarrassing.”

A strong answer: starts simple (a router plus workflows for the common cases, an agent only for the long tail); designs 4–6 task-level tools with clear descriptions and actionable errors, behind an MCP server if other apps need them; prices it (fixed prefix + growth per step, step caps, caching); handles memory (session + small profile); tiers actions by risk (auto lookups, capped auto refunds, approvals above a threshold, idempotency keys); adds guardrails, least privilege, budgets, tracing; and measures task success, tool-selection accuracy and cost per resolved ticket on a golden set.

🏗️ Build it yourself: a refunds-capable support agent

📋 The brief

An online shop gets 20,000 support conversations a day. About 70% are simple (order status, policy questions); 30% need several steps (a damaged item, a missing parcel, a partial refund). The agent may issue refunds up to $100 on its own; larger ones need a human. Replies within 10 seconds for simple questions. Use only ideas from this phase.

Reveal One good design + the classic mistakes

Requirements. Fast, grounded answers for the simple 70%; correct multi-step handling for the rest; no refund without a matching order; refunds capped and auditable; no repeated refunds on retries; graceful escalation to humans; cost per conversation known and bounded.

Architecture.

  • Router (small model): status / policy / problem / other. Status and policy go to workflows (one tool call + one answer call, Lesson 6.3). Problems go to an agent (6.1) with a step cap of 10 and a $0.25 budget.
  • Tools (6.2): orders_get_status, kb_search_articles, payments_issue_refund(order_id, amount, reason, idempotency_key), tickets_escalate. Clear when-not-to-use text; actionable errors; refund tool annotated destructive. Exposed by an internal MCP server so the agent-assist UI for human staff uses the same tools (6.9).
  • Memory (6.4): session history with compaction for long threads; a small structured profile (name, language, open orders) loaded every turn; no payment details stored.
  • Safety (6.6): refund ≤ $100 auto with idempotency key and a daily per-customer cap; > $100 → human approval with the agent's proposed call shown; credentials scoped to customer-service actions only; guardrail on tool outputs and customer messages for injected instructions; tracing on every run.

Numbers. Simple path ≈ 3,000 input tokens per conversation: 14,000 × 3,000 = 42M tokens/day. Agent path ≈ 6 calls, fixed 3,000 + 1,000 per step: 6 × 3,000 + 1,000 × (0+1+…+5) = 33,000 tokens; 6,000 × 33,000 = 198M tokens/day. Total ≈ 240M input tokens/day, about $720/day at an illustrative $3 per million, before prompt caching of the shared prefix (Lesson 1.4), which cuts much of it. If 5% of conversations end in a refund and 10% of those exceed $100, that's 100 approvals a day, about 100 minutes of staff time.

Eval plan. 300 golden conversations covering every route and edge case; tool-selection accuracy and argument correctness; trajectory checks (did it look up the order before refunding?); refund correctness and duplicate-refund tests (retries); cost and steps per resolved ticket; integration tests with a scripted model (6.8); red-team prompts that try to trigger refunds (Phase R). Run in CI on every prompt or tool change (Lesson 5.6).

Classic mistakes. One agent for everything (slow, costly, hard to test). A single refund tool described as “handles refund questions”. Retrying a refund call without an idempotency key. Approvals on every action (rubber-stamping). Storing full conversation history forever with no deletion. No step or dollar cap. Production credentials in the agent.

👹 Boss quiz

1. An agent's fixed prompt is 2,000 tokens and every step adds 1,500. How many input tokens does an 8-call run send in total?
8 × 2,000 = 16,000 for the fixed part, plus 1,500 × (0+1+…+7) = 1,500 × 28 = 42,000 for the growing history: 58,000. The history costs more than the prompt; that's the steps² effect (Lesson 6.1).
2. Customer emails arrive in many languages with three intents (cancel, change address, complain), each with a different procedure. What's the simplest good design?
Distinct input types with known procedures is the textbook case for routing (Lesson 6.3). It's cheaper and more testable than an agent, and each route can have its own tools and approval rules.
3. You have 5 AI apps and 8 internal systems. How many integrations do you build without a shared protocol, and with MCP?
Without a standard, every app needs a connector to every system: 5 × 8 = 40. With MCP, 8 servers + 5 clients = 13, and a new system adds one server (Lesson 6.2).
4. Where should a user's time zone and dietary restriction live in an assistant's memory?
Stable facts that every request needs belong in typed fields: exact updates (no stale duplicates), always present, easy for the user to view and delete. Vector memory suits open-ended episodes (Lesson 6.4).
5. A research agent reads arbitrary web pages, can query your CRM, and can send emails. Which change most reliably prevents data exfiltration via injected instructions?
Private data + untrusted content + external communication lets injected text leak data. Filters reduce the risk; removing or gating one leg makes the attack fail even when the model is fooled (Lesson 6.6; the attacker's side is in Phase R).
