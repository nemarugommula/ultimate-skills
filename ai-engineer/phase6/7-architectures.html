Phase 6 · Lesson 7

Agent architectures: planner–executor, DAGs, tree-of-thought, reflection

ReAct decides one step at a time. Other shapes plan ahead, run steps in parallel, search over several lines of reasoning, or learn from their own failures. Each one buys something specific, and each one has a bill.

🧰 You'll need (quick reminders)
  • The agent loop and ReAct: the model thinks, calls a tool, reads the observation, repeats; every turn re-reads the whole history (Lesson 6.1).
  • Workflow patterns: chaining, parallel sectioning, orchestrator–workers and evaluator–optimizer, and why latency is the critical path (Lesson 6.3).
  • Tool errors as observations: a failed call goes back into the context so the model can react (Lessons 6.1, 6.2).
🎯 Hook

The Game of 24: use four numbers, say 4 9 10 13, with + − × ÷ to make exactly 24. In 2023, researchers at Princeton and Google DeepMind gave it to GPT-4. Reasoning step by step in one go (chain of thought), it solved 4% of their puzzles. The reason is structural: one early wrong combination dooms the whole line of reasoning, and a single left-to-right pass never goes back.

Same model, different architecture: let it propose several next steps, judge which look promising, keep the best few and backtrack from dead ends. Their Tree of Thoughts solved 74%. Nothing was trained. They changed the shape of the computation around the model, and that's what this lesson is about.

Numbers first: one task, three shapes

“Which of our three warehouses can ship 200 units of SKU-42 to Berlin cheapest by Friday?” That's 3 stock checks and up to 3 shipping quotes, then a comparison. Illustrative costs: each LLM call 1.5 s; a stock check 0.6 s; a quote 1.2 s (0.3 s when it fails fast for low stock); a fixed prompt of 1,800 tokens; each ReAct step adds 250 tokens of history.

Illustrative numbers; the 3,240-token answer call reads the plan (300 tokens) plus six results (190 each). The pattern is what matters, and it matches the published results: ReWOO reported 5× fewer tokens than interleaved reasoning on HotpotQA, and LLMCompiler up to 3.7× lower latency than ReAct by running independent calls in parallel.

ReAct pays for flexibility: a full model call, re-reading everything, for every single step. Planning ahead removes most of those calls, and drawing the plan as a graph lets independent steps run at once. The price is that a plan made before seeing any results can be wrong, so the architecture must say what happens when reality disagrees.

💡 Big idea An agent architecture is a decision about where the thinking happens: before acting (plan), between every action (ReAct), across alternatives (search) or after failing (reflection). More up-front planning means fewer, cheaper calls but brittleness when the world surprises you; more search and reflection means higher quality on hard problems at a multiple of the cost. Pick the cheapest shape that handles the surprises your task actually has.
🧠 Analogy: four ways to cook dinner

ReAct is cooking without a recipe: taste, decide, add something, taste again. Flexible, but you stop to think after every pinch. Planner–executor is writing the recipe first and then following it; fast, until the shop is out of basil and you're stuck mid-recipe unless you rewrite it (replanning). A DAG is the same recipe written so that the rice, the sauce and the salad cook at the same time on three burners. Tree of Thoughts is trying three versions of a sauce on the side, tasting each, and continuing only with the best. Reflection is writing on the recipe card “too salty last time, halve it” so the next attempt is better.

Planner–executor and DAGs, precisely

A planner writes a plan as data, not prose, so code can run it. LLMCompiler's planner emits a numbered task list where later tasks reference earlier results:

1. check_stock("A") 2. check_stock("B") 3. check_stock("C") 4. quote_shipping("A", "Berlin", 200, stock=$1) 5. quote_shipping("B", "Berlin", 200, stock=$2) 6. quote_shipping("C", "Berlin", 200, stock=$3) 7. join()

The $1 references are the edges of the graph. A small scheduler (plain code) starts every task whose inputs are ready: tasks 1–3 at once, then 4–6 as soon as their stock check returns. The joiner reads all results and either answers or says “replan”, and the planner gets another turn with the results so far. Three design rules make this robust:

  • Retry in code, replan in the model. A timeout is an infrastructure problem: retry the node (with backoff) without spending an LLM call. A result that invalidates the plan (“warehouse closed”, “no carrier serves Berlin”) is a reasoning problem: send it to the replanner.
  • Cap replans (say 2), exactly like max steps in Lesson 6.1, or a stubborn failure turns into a planning loop.
  • Make the plan checkable. Validate tool names and arguments before running anything; a plan that references a tool that doesn't exist should fail in milliseconds, not after three tool calls.

Graph agents take the last step: instead of a plan the model invents at run time, you draw the graph (plan node, parallel workers, join node, an edge back to the planner when the join says so, an approval node before anything risky) and the model only fills the nodes. That's what LangGraph's StateGraph is: nodes, edges, conditional edges, a typed shared state and checkpoints, so a run can pause for a human and resume (Lessons 6.5, 6.6).

Tree of Thoughts: search over reasoning paths

Chain of thought commits to the first idea. Tree of Thoughts treats each intermediate step (a “thought”) as a node in a search tree and needs three ingredients:

  • A generator that proposes k candidate next thoughts (“4 + 9 = 13, left 10 13 13”, “13 − 9 = 4, left 4 4 10”…).
  • An evaluator, usually the model again, that scores each partial state (“sure / likely / impossible to reach 24”). In the paper's Game of 24 setup, each state's value was sampled 3 times.
  • A search algorithm: breadth-first with a beam (keep the best b states per level; the paper used b = 5) or depth-first with backtracking when a state scores below a threshold.

What you should see: chain of thought (one proposal, no judge) solves 4 9 10 13 in under 10% of seeds with 3 calls. ToT with b = 5 and a judge solves it about 3 times in 4, at roughly 7× the calls: the same shape as the paper's 4% → 74%, from a toy. Push the pruning threshold up and success collapses, because a noisy judge scores the one good branch below the cut. Crank the judge noise and success falls from about 80% towards 50% for the same number of calls: you pay for the search, but the judge can't steer it. On the hard puzzle (only 1 of 19 first moves can still reach 24), breadth alone doesn't help: if the generator never proposes the right move, the best evaluator can't keep it. Raise k too.

✏️ Worked example: when reflection pays

A coding agent passes the unit tests on its first try 60% of the time. Each attempt costs 8,000 tokens; after a failure, a reflection (“the test failed because I didn't handle empty input”) plus the next attempt cost 9,500. Allow up to 3 attempts.

  • Success within 3 attempts, even if attempts were independent: 1 − 0.4³ = 93.6% (reflection usually makes later attempts better than that).
  • Expected tokens: 8,000 + 0.4 × 9,500 + 0.4² × 9,500 = 8,000 + 3,800 + 1,520 = 13,320, only 1.67× a single attempt, because most runs stop early.
  • Worst case: 8,000 + 2 × 9,500 = 27,000 tokens, so cap the attempts.

The whole calculation rests on one thing: a trustworthy signal that says “failed”. Tests give you one. Without one, the model grades its own work, and a self-judge that wrongly passes bad answers or fails good ones turns reflection into an expensive coin flip (Lesson 5.3 on judges).

Reflexion: learning without changing weights

Reflexion (Shinn et al., 2023) adds three parts to an agent: an evaluator that turns the outcome into a signal (a test result, a success flag, a judge's score), a self-reflection step where the model writes a few sentences on why it failed and what to do differently, and an episodic memory that puts those notes into the next attempt's prompt. On the HumanEval coding benchmark it reached 91% pass@1 (correct on the first submitted answer), against 80% for GPT-4 alone. Self-Refine is the single-attempt cousin: generate, critique, revise, with the same model in all three roles. Both are evaluator–optimizer loops (Lesson 6.3) with memory; both need a round cap and a signal you trust.

Reasoning models (Lesson 1.2) already search and self-correct inside their hidden thinking, which shrinks the gap that ToT and Self-Refine filled in 2023. What stays valuable is everything a model can't do inside one call: running real tools in parallel, retrying in code, checking against real tests, and stopping at a budget.

🧰 Tools you'll actually use

LangGraph (1.x as of 2026) for explicit graphs: StateGraph, conditional edges, Send for dynamic parallel fan-out, per-node RetryPolicy, and checkpointers. LangChain publishes runnable plan-and-execute, ReWOO and LLMCompiler examples; the LLMCompiler authors' own code is on GitHub. Plain asyncio.gather is enough for a fixed fan-out. A plan-execute-join graph with parallel steps and a replan edge:

import operator
from typing import Annotated, TypedDict
from langgraph.graph import StateGraph, START, END
from langgraph.types import Send, RetryPolicy

class State(TypedDict):
    question: str
    plan: list[dict]                              # [{"id": "q_B", "tool": "quote_shipping", "args": {...}}, ...]
    results: Annotated[list[dict], operator.add]  # parallel branches append here
    replans: int
    answer: str

def planner(state):                 # LLM call: the whole plan, as data
    return {"plan": llm_plan(state["question"], state.get("results", [])),
            "replans": state.get("replans", -1) + 1}

def fan_out(state):                 # every step not done yet runs in parallel
    done = {r["id"] for r in state["results"] if r["ok"]}
    return [Send("run_step", {"step": s}) for s in state["plan"] if s["id"] not in done]

def run_step(payload):              # plain code, no LLM
    s = payload["step"]
    try:
        out = TOOLS[s["tool"]](**s["args"])   # transient errors raise → RetryPolicy retries
        return {"results": [{"id": s["id"], "ok": True, "out": out}]}
    except PermanentToolError as e:      # reasoning problem → let the joiner decide
        return {"results": [{"id": s["id"], "ok": False, "out": str(e)}]}

def joiner(state):                  # LLM call: answer, or ask for a new plan
    return {"answer": llm_join(state["question"], state["results"])}

def after_join(state):
    wants_replan = state["answer"].startswith("REPLAN")
    return "planner" if wants_replan and state["replans"] < 2 else END   # cap replans

g = StateGraph(State)
g.add_node("planner", planner)
g.add_node("run_step", run_step, retry_policy=RetryPolicy(max_attempts=3))
g.add_node("joiner", joiner)
g.add_edge(START, "planner")
g.add_conditional_edges("planner", fan_out, ["run_step"])
g.add_edge("run_step", "joiner")               # joins after all parallel branches finish
g.add_conditional_edges("joiner", after_join, ["planner", END])
app = g.compile()

llm_plan, llm_join and TOOLS are yours (one model call each; validate the plan's tool names and arguments before returning it). LangGraph's default retry policy doesn't retry ValueError or TypeError, which are usually bugs, not flakiness. This dependency-free version waits for the whole layer; LLMCompiler's scheduler starts each task the moment its own inputs are ready.

🚀 Startup vs big tech

Week one

A ReAct loop with parallel tool calls enabled covers most needs. When traces show the same fixed sequence every time, freeze it into a plan or a small graph. Add a test-driven retry loop for code generation, capped at 2–3 attempts. Skip tree search unless a measured eval says one pass isn't enough.

At scale

Explicit graphs with checkpoints for every production flow, planners on the strongest model and executors on cheap ones, per-node retry and timeout policies, replan budgets, and dashboards of calls, latency and replans per architecture. Search and reflection are reserved for high-value tasks (code review, complex planning) where an eval proves the extra spend buys success.

🎤 Interview angle

“Our ReAct agent is slow and expensive on comparison questions. What would you change?” A senior answer:

  • Reads traces first: are the tool calls independent? If so, enable parallel tool calls or move to a plan → parallel execute → join graph (latency = longest branch).
  • Moves execution off the big model: code or a small model runs the steps; the big model plans and synthesises.
  • Designs failure handling explicitly: retries with backoff in code for transient errors, a capped replan for errors that change the plan, and partial answers that say what's missing.
  • Mentions when not to: if each step depends on the last, ReAct stays; tree search and reflection only with a scoring signal and a measured win. Measures success, latency and cost per task before and after (Lesson 5.5).
🏭 In the real world
Search over thoughts 🧪 Research · 2023 Tree of Thoughts (Yao et al.)

How: the model proposes candidate intermediate steps, evaluates states (“sure / likely / impossible”), and a breadth-first search keeps the best 5 per level; depth-first search with backtracking was used for crosswords.

Why this method: on Game of 24, GPT-4 with chain of thought solved 4% of tasks; with Tree of Thoughts, 74%, because the search can abandon bad early choices.

A compiler for tool calls 🧪 Research · 2023 LLMCompiler (Kim et al.)

How: a function-calling planner writes tasks with dependencies, a task-fetching unit dispatches whatever is ready, and an executor runs tasks in parallel, with replanning when needed.

Why this method: compared with ReAct, up to 3.7× lower latency, up to 6.7× lower cost and up to about 9% higher accuracy, with open and closed models.

Plan once, observe later 🧪 Research · 2023 ReWOO (Xu et al.)

How: the planner writes every step with placeholders for evidence, workers fill them by calling tools, and a solver answers from the plan plus evidence, so the big model never re-reads observations step by step.

Why this method: 5× token efficiency and 4% higher accuracy on HotpotQA (a multi-hop question benchmark), and more robust when tools fail.

Verbal reinforcement 🧪 Research · 2023 Reflexion (Shinn et al.)

How: after each failed trial, the agent writes a reflection on the feedback and stores it in an episodic memory that's added to the next trial's prompt; no weights change.

Why this method: 91% pass@1 on HumanEval versus 80% for GPT-4, with gains across decision-making, coding and reasoning tasks.

Plan-and-execute in a framework 🏢 LangChain · 2024 Plan-and-Execute Agents

How: LangGraph implementations of plan-and-execute, ReWOO and LLMCompiler as graphs of planner, executor and joiner nodes.

Why this method: faster multi-step runs because the big model isn't consulted after every action, cheaper because sub-tasks can use smaller models, and often better completion because the planner must think through the whole task.

🤯 Fun fact · 74%, or was it 69%?

The Tree of Thoughts repository notes that when the authors re-ran their Game of 24 experiment after the paper, it scored 69% instead of the original 74%, purely from randomness in GPT-4's sampling. Search architectures are stochastic twice over (sampled proposals, sampled judgements), which is why you measure them over many runs, as the “Run 200 seeds” button does.

🌉 How it connects

ReAct is the loop from Lesson 6.1; plan → parallel → join is orchestrator–workers and sectioning (6.3) with the plan written at run time; multi-agent systems (6.5) are often these same graphs with an agent in each node; checkpoints and approval nodes come from 6.6. Lesson 6.8 builds the bare loop by hand, and Lesson 5.5 shows how to measure whether a fancier architecture actually helps. Tree search with a learned value function is the heart of game-playing AI: see Monte Carlo tree search in the RL course, and best-of-n sampling for the simplest “try several, keep the best”.

Check yourself

1. A question needs 8 independent lookups (1 s each). Each LLM call takes 1.5 s. A ReAct agent does one lookup per turn and then answers (9 calls); a DAG agent plans, runs all 8 in parallel, then joins. Roughly how long does the DAG take?
DAG: plan 1.5 + the slowest lookup 1 + join 1.5 = 4 s. ReAct: 9 × 1.5 + 8 × 1 = 21.5 s, and it re-reads a growing history on every one of those 9 calls.
2. You're building an agent that debugs failing deployments: read logs, form a guess, run a command, read the output, refine. Which architecture fits best?
When the next action depends on the latest observation, a plan written in advance is stale after the first step. ReAct's per-step decisions are worth their cost here. Tree search multiplies calls without a clear way to score partial progress on a live system.
3. Your Tree-of-Thoughts solver got worse after you raised the pruning threshold from 0.5 to 0.8 to “save calls”. What's the most likely reason?
Pruning is only as good as the scores it prunes on. With an imperfect judge, aggressive thresholds trade a few saved calls for losing the correct path. Calibrate the evaluator on known states, or sample its judgement several times (the paper used 3) before trusting it.
📝 TL;DR
  • ReAct thinks between every step: adaptive, but a full-context call per step. Planning first cuts calls; a DAG plan also cuts latency to the longest branch.
  • Plans go stale: retry transient errors in code, replan (capped) when results change the plan, and validate plans before running them.
  • Explicit graphs (LangGraph-style) give predictable, resumable, auditable control flow for production.
  • Tree of Thoughts searches over reasoning paths (4% → 74% on Game of 24) at many times the calls; it lives or dies by the proposals and the evaluator.
  • Reflexion turns failures into notes for the next try; worth it when a real checker (tests) exists, with a round cap.
