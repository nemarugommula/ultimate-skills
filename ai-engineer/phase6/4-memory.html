Phase 6 · Lesson 4

Agent memory: short-term, long-term & summarization

Models remember nothing between calls. Everything an agent “remembers” is text you chose to put back into the prompt. Memory design is deciding what to keep, what to compress, what to store for later, and what to forget.

🧰 You'll need (quick reminders)
  • Context window: the maximum tokens a model can read in one call; you pay for all of them, every call (Lesson 0.3).
  • Context engineering: choosing and ordering what goes into the prompt (Lesson 1.4).
  • Embeddings and vector search: store text as vectors and retrieve the most similar ones to a query (Lessons 2.1, 2.3).
  • The agent loop: each step adds a call and an observation to the context (Lesson 6.1).
🎯 Hook

“Just use a bigger context window” sounds like the end of the memory problem. In July 2025, Chroma tested 18 LLMs on simple tasks while growing the input, and found their performance grows increasingly unreliable as input length grows, even on tasks they solved easily with short inputs. They called it context rot.

It echoes a 2023 finding (“Lost in the Middle”): models use information best when it's at the beginning or end of the context, and worse when it's buried in the middle. A long context is a big desk, not a good memory. What you put on it, and where, still matters.

Numbers first: how much is there to remember?

SituationRaw historyFits in one prompt?
A support chat, 40 turns × 200 tokens8,000 tokensEasily; just send it
A coding agent session, 200 tool steps × 1,500 tokens300,000 tokensOver many context windows, and slow and costly long before that: compact
A personal assistant over a year, 300 conversations × 5,000 tokens1,500,000 tokensNo: store it, and retrieve only what matters

So there are two different problems. Short-term memory: keep the current task's context small and sharp. Long-term memory: carry useful facts across sessions without resending everything.

💡 Big idea Memory = write (what to save, when) + store (where) + read (what to pull back into the prompt, when) + forget (what to drop, update or delete). Every memory bug is a bug in one of these four: the fact was never written, was stored stale, wasn't retrieved, or wasn't forgotten.
🧠 Analogy: a doctor's desk and filing cabinet

During an appointment, the doctor has your recent notes open on the desk (the context window). Old pages get summarised into a one-line “history” at the top of the file (summarisation). Facts that matter for years, like your allergies, go on the front cover where they're always seen (semantic memory, a profile). Records of past visits stay in the cabinet and are pulled when relevant (episodic memory, retrieved on demand). When you move house, the old address is crossed out, not kept beside the new one (update, don't append). And some things you only share if you agree they can be written down (consent).

Short-term memory: windows, summaries and compaction

The simplest strategy is to send the full history. It's perfect until it isn't: cost per turn grows, and quality drops as the context gets long. A sliding window keeps only the last N turns: cheap and bounded, but it forgets anything older, including the user's name. Window + summary replaces old turns with a running summary: bounded cost, and it keeps what the summary keeps. That last clause is the whole game: a generic summary (“the user discussed their trip”) silently drops the numbers and allergies that matter. Anthropic calls the agent version compaction: when the context nears its limit, summarise the history into the critical details and continue in a fresh context.

✏️ Worked example: what summarisation saves

A chat where every turn (user + assistant) adds 200 tokens. Option A: full history. Option B: keep the last 10 turns (2,000 tokens) plus a 300-token summary, refreshed every turn once older turns drop out (each refresh reads the old summary plus the dropped turn: ≈500 tokens).

  • Full history, 30 turns: 200 × (1 + 2 + … + 30) = 200 × 465 = 93,000 input tokens.
  • Window + summary, 30 turns: turns 1–10 cost 200 × 55 = 11,000; turns 11–30 cost 20 × (2,000 + 300) = 46,000; summaries 20 × 500 = 10,000. Total 67,000 (28% less).
  • At 100 turns: full = 200 × 5,050 = 1,010,000; window + summary = 11,000 + 90 × 2,300 + 90 × 500 = 263,000 (74% less).

Summaries barely pay off in short chats and win big in long ones. Refreshing every 5 turns instead of every turn cuts the summary cost further.

Long-term memory: write, retrieve, update, forget

  • Write: after a turn or at the end of a session, an LLM call extracts memory-worthy facts (“user is vegetarian”) and episodes (“fixed Kafka lag”). Save the source and a timestamp. Don't save every message: save what will matter later.
  • Read: retrieve by similarity to the current request, plus recency and importance. The Generative Agents paper scored memories as a weighted sum of all three. Always-on facts (a small profile) can simply sit in the system prompt.
  • Update: when a new fact conflicts with an old one (moved city, changed job), supersede the old one. Two contradictory facts in a store means retrieval will sometimes pick the wrong one.
  • Forget: let users see and delete memories; expire time-limited facts; never store secrets; treat health, finance and similar sensitive categories as opt-in. Long-term memory of personal data is regulated data (Lesson 8.5).

Forgetting and aging: memory that doesn't rot

A store that only grows gets worse over time: more stale facts, more near-duplicates, more noise competing at retrieval. Production memory systems age and prune deliberately.

The common production design uses both: a small structured profile (tens of fields, always loaded) plus a vector store of episodes (retrieved when relevant), with an extraction step that decides which one each new fact belongs in.

🧰 Tools you'll actually use

Short-term: your framework's session or checkpointer (OpenAI Agents SDK sessions, LangGraph checkpointers keyed by thread ID) plus compaction. Long-term: a vector store (pgvector, Qdrant, Lesson 2.3) or a key-value profile, or a memory layer such as Mem0, Letta (from the MemGPT authors) or LangGraph's long-term stores. Anthropic's API offers a client-side memory tool (type memory_20250818): the model asks to read and write files under /memories and your code performs the file operations.

# Short-term: the session stores the conversation and replays it each turn
from agents import Agent, Runner, SQLiteSession

agent = Agent(name="Travel assistant", instructions="Be concise. Respect dietary needs.")
session = SQLiteSession("user_42")
await Runner.run(agent, "I'm vegetarian and allergic to peanuts.", session=session)
result = await Runner.run(agent, "Suggest dinner in Kyoto.", session=session)  # remembers

# Long-term: retrieval score = relevance + recency + importance (Generative Agents style)
import math, time
def score(mem, query_vec, now=time.time()):
    hours = (now - mem["last_access"]) / 3600
    recency = 0.995 ** hours                       # exponential decay
    relevance = cosine(query_vec, mem["vec"])
    return relevance + recency + mem["importance"]   # each normalised to [0, 1]

def remember(store, fact, slot=None):
    if slot:                                         # e.g. "home_city": supersede, don't append
        store.mark_superseded(user_id, slot)
    store.add(user_id, fact, slot=slot, vec=embed(fact), importance=rate(fact), last_access=time.time())

cosine, embed, rate (an LLM call returning 0–1 importance) and store are your own helpers. Sessions grow forever: pair them with a trimming or summarising strategy.

🚀 Startup vs big tech

Week one

Full history with a token cap, then window + a fact-preserving summary when chats get long. For cross-session memory, a small per-user profile table (5–20 facts) written by one extraction call per session and shown to users, who can edit and delete it.

At scale

Separate stores for profile facts and episodes, conflict resolution on write, retrieval evals (“did it recall the allergy?”), per-region storage, retention policies, user-facing memory controls and audit logs, and memory poisoning defences (Lesson 8.3): a stored “fact” injected by a malicious document is a persistent prompt injection.

🎤 Interview angle

“Design memory for a personal assistant.” A senior answer:

  • Separates short-term (window + compaction) from long-term (profile facts + episodic store), with numbers for each.
  • Designs the write path: what gets extracted, timestamps, slots for facts that change, conflict resolution, and what is never stored.
  • Designs the read path: always-on profile vs retrieved episodes, relevance + recency, a token budget for memories.
  • Covers user control and privacy (view, edit, delete, consent for sensitive categories) and how to evaluate recall and staleness.
🏭 In the real world
Memory as an operating system 🧪 Research · 2023 MemGPT: Towards LLMs as Operating Systems (Packer et al.)

How: treats the context window like RAM and external storage like disk; the model itself calls functions to move information in and out (page in, page out).

Why this method: borrowed from hierarchical memory in operating systems, it gives the illusion of unbounded memory with a fixed window; the authors went on to found Letta.

Recency + importance + relevance 🧪 Research · 2023 Generative Agents (Park et al.)

How: simulated characters store every observation in a memory stream and retrieve by a weighted sum of recency (exponential decay, factor 0.995), importance (rated by the LLM) and relevance (embedding similarity), each normalised.

Why this method: similarity alone retrieves stale or trivial memories; mixing in recency and importance made the agents' behaviour more believable.

Memory in a consumer product 🏢 OpenAI · 2024–2025 Memory and new controls for ChatGPT

How: saved memories (from Feb 2024), then from April 2025 the option to reference all past conversations, with settings to turn each off, plus temporary chats.

Why this method: users want continuity, but memory of personal data needs visible, user-controlled switches.

Memory and context editing in the API 🏢 Anthropic · 2025 Managing context on the Claude Developer Platform

How: a memory tool that stores files under /memories on the developer's side, plus context editing that clears stale tool results as the context fills.

Why this method: long-running agents need both a persistent notebook and a way to drop bulky, outdated observations; keeping storage client-side leaves the data under the developer's control.

Extract-and-update memory layer 🧪 Research · 2025 Mem0 (Chhikara et al.)

How: extracts salient facts from conversations, then decides per fact whether to add, update, delete or ignore against existing memories.

Why this method: on the LOCOMO long-conversation benchmark it reported a 26% relative gain over OpenAI's memory on an LLM-judge metric, and 91% lower p95 latency and over 90% fewer tokens than sending the full context.

🤯 Fun fact · 0.995

The Generative Agents paper's recency decay factor was 0.995 per sandbox game hour since a memory was last retrieved, so a memory loses half its recency score after about 138 hours (0.995138 ≈ 0.50), a bit under six game days. Tuning that one number changes how “forgetful” an agent feels.

Check yourself

1. Each turn adds 200 tokens and you send the full history every time. How many input tokens does a 30-turn chat send in total?
Turn k sends 200 × k tokens: 200 × (1 + … + 30) = 200 × 465 = 93,000. 6,000 is only the last turn. The total grows with the square of the number of turns.
2. A user told your assistant they moved from Paris to Berlin. A month later it still recommends Paris restaurants. What's the root cause and fix?
Contradictory facts in the store make retrieval a coin flip. Fix the write path (update, don't append) and add recency on the read path. Retrieving both just hands the contradiction to the model.
3. Which of these should a personal assistant save to long-term memory automatically?
Save what will be useful later, in a form you can update and the user can control. Never store secrets, and treat sensitive categories (health, finances) as opt-in.
📝 TL;DR
  • The model remembers nothing; memory is what you put back into the prompt. Bigger windows rot: keep context small and sharp.
  • Short-term: full history → sliding window → window + fact-preserving summary / compaction as sessions grow.
  • Long-term: write (extract facts and episodes), read (relevance + recency + importance), update (supersede conflicts), forget (TTL, decay, importance pruning, consolidation, user deletion; no secrets, consent).
  • Keep stable facts in a small structured profile (SQL/KV, always loaded); keep open-ended episodes in a vector store.
  • Most memory bugs are stale facts, generic summaries, or facts never written. Evaluate recall like retrieval.
