Phase 6 · Lesson 3

Workflow patterns: chaining, routing, parallel, orchestrator-workers

Most “agent” products in production are workflows: a few LLM calls wired together by your code. Five patterns cover nearly all of them, and each has a price in latency and tokens you can compute before you build.

🧰 You'll need (quick reminders)
  • Workflow vs agent: in a workflow your code fixes the steps; in an agent the model picks them (Lesson 6.1).
  • Latency and tokens: each LLM call takes seconds and costs tokens in and out (Lesson 0.3).
  • LLM-as-judge: using a model to score another model's output against a rubric, and its biases (Lesson 5.3).
🎯 Hook

After working with dozens of teams building agents, Anthropic reported something unglamorous: the most successful implementations weren't using complex frameworks or specialized libraries. They were built from simple, composable patterns.

Their December 2024 guide named five: prompt chaining, routing, parallelization, orchestrator–workers and evaluator–optimizer. Learn these five shapes and you can read (and price) almost any LLM system diagram you'll meet.

Numbers first: same work, very different clocks

Review a pull request for four things: security, performance, readability and tests. Each focused review is one LLM call of about 3 s and 1,500 tokens; merging the four reviews takes one more call of 1.5 s and 2,500 tokens.

Typical, illustrative numbers. Real latency depends on output length, model and load.

Two rules fall out. Tokens add up across every call, whatever the shape. Latency is the longest path through the graph (the critical path), so independent calls should run in parallel. Focused calls usually give better quality than one call juggling four jobs, which is why you pay the extra tokens.

💡 Big idea A workflow is a small graph of LLM calls and plain code. Cost = sum over all calls. Latency = the critical path. Pick the pattern that matches the task's shape: a fixed sequence → chain; distinct input types → route; independent parts → parallel; parts you can't know in advance → orchestrator–workers; quality you can check → evaluator–optimizer.
🧠 Analogy: a restaurant kitchen

An order moves from prep to cook to plating: a chain, with the head chef tasting at each pass (a gate). The host sends vegetarians to one menu and kids to another: routing. Starters, mains and desserts are cooked at once by different stations: parallel sectioning. Three cooks taste a new sauce and the majority wins: voting. For a wedding, the head chef first decides which dishes and stations are needed, then hands out the work: orchestrator–workers. And a dish goes back to the stove until the chef approves it: evaluator–optimizer.

The difference between orchestrator–workers and sectioning: in sectioning you wrote the list of subtasks; in orchestrator–workers the model writes it at run time. That's the step towards an agent (Lesson 6.1), and towards multi-agent systems (Lesson 6.5).

Routing is the only pattern that is often cheaper than a single call, because the classifier is small and each handler's prompt is short. Orchestrator–workers is powerful but the most expensive: use it only when you truly can't list the subtasks in advance.

✏️ Worked example: pricing an orchestrator–workers run

A research feature: the orchestrator reads the question and plans (2 s, 1,500 tokens), spawns 5 searchers (each 6 s, 4,000 tokens, they read web pages), then a synthesizer writes the report from all findings (5 s, 6,000 tokens).

  • Tokens: 1,500 + 5 × 4,000 + 6,000 = 27,500.
  • Wall-clock in parallel: 2 + 6 + 5 = 13 s. One by one: 2 + 30 + 5 = 37 s.
  • If the orchestrator decides it needs 12 searchers for a broad question: 1,500 + 48,000 + 6,000 = 55,500 tokens, but still 13 s in parallel (if your rate limits allow 12 concurrent calls).

That's the trade: parallelism keeps latency flat while cost scales with however many workers the model decides to spawn. Cap the worker count, and give each worker a clear, bounded task.

Evaluator–optimizer: when “try again” works

One call writes, another critiques against criteria, and the first revises, until the critic is satisfied or you hit a round limit. It works when the criteria are clear and checkable. Its two failure modes: a threshold the generator can never reach (you pay for every round) and a noisy judge that passes a mediocre draft on a lucky score.

🎮 Playground · Evaluator–optimizer loop

The generator and the judge are scripted stand-ins: the drafts are pre-written, true quality improves with diminishing returns towards a ceiling of 0.9, and the judge's score is the true quality plus random noise. What you should see: with the default threshold the loop stops after a few rounds with a good draft. Above 0.9, it runs to the round limit every time, burning tokens on tiny gains. With a noisy judge, some seeds stop at round 1 or 2 on a lucky score while the true quality is still poor. Fixes: set thresholds from measured judge scores on known-good outputs, make the critique specific (a checklist, tests, a length check in code), and always cap rounds. 🧰 Tools you'll actually use

Plain code is enough for most workflows: asyncio.gather for sectioning and voting, an if for routing and gates, a for loop with a cap for evaluator–optimizer. Graph frameworks such as LangGraph (1.x as of 2026) help when you want the graph explicit, with state, checkpoints, streaming and human approval steps. Durable-execution engines (Temporal, cloud step functions) suit long workflows that must survive restarts.

# Sectioning in plain Python: four focused reviews in parallel, then merge
import asyncio, anthropic
client = anthropic.AsyncAnthropic()

async def ask(prompt: str) -> str:
    r = await client.messages.create(model="claude-haiku-5-5", max_tokens=800,
                                    messages=[{"role": "user", "content": prompt}])
    return r.content[0].text

async def review(diff: str) -> str:
    aspects = ["security", "performance", "readability", "tests"]
    parts = await asyncio.gather(*[ask(f"Review this diff ONLY for {a}:\n{diff}") for a in aspects])
    return await ask("Merge these reviews, remove duplicates, rank by severity:\n\n" + "\n\n".join(parts))
# Evaluator–optimizer as a LangGraph graph with a conditional edge and a round cap
from typing import TypedDict
from langgraph.graph import StateGraph, START, END

class State(TypedDict):
    task: str
    draft: str
    feedback: str
    score: float
    rounds: int

def generate(s: State) -> dict:
    draft = llm(f"{s['task']}\nPrevious draft: {s['draft']}\nFix this feedback: {s['feedback']}")
    return {"draft": draft, "rounds": s["rounds"] + 1}

def evaluate(s: State) -> dict:
    score, feedback = judge(s["draft"])        # rubric + checks in code (length, required words)
    return {"score": score, "feedback": feedback}

def route(s: State) -> str:
    return "done" if s["score"] >= 0.8 or s["rounds"] >= 4 else "revise"

graph = (StateGraph(State)
         .add_node("generate", generate)
         .add_node("evaluate", evaluate)
         .add_edge(START, "generate")
         .add_edge("generate", "evaluate")
         .add_conditional_edges("evaluate", route, {"revise": "generate", "done": END})
         .compile())
out = graph.invoke({"task": "Tagline < 60 chars: waterproof + lightweight",
                    "draft": "", "feedback": "", "score": 0.0, "rounds": 0})

llm() and judge() are your own helpers (one model call each). Node functions return only the state keys they update.

🚀 Startup vs big tech

Week one

Plain Python: a 2–3 step chain with a code check between steps, or a router in front of 2–3 prompts. Parallelize with asyncio.gather. Log every call's latency and tokens so you can see the critical path. Add a framework only when the graph gets hard to read.

At scale

Workflows as versioned graphs (LangGraph or a durable-execution engine) with retries per node, per-node model choice (small models for routing and checks), concurrency limits per provider, cost dashboards per node, and evals per step as well as end to end (Lesson 5.6).

🎤 Interview angle

“Design the LLM part of a support-ticket system.” A senior answer:

  • Starts with the simplest pattern: a router (billing / technical / refund / other) with a small model, then a focused prompt or workflow per route.
  • Adds gates in code (schema validation, required fields) and parallel checks (a guardrail call alongside the answer call).
  • Prices it: calls per ticket, tokens per call, critical-path latency vs the SLO.
  • Reserves an agent or orchestrator only for the long tail where steps can't be predicted, with caps, and says how each step is evaluated.
🏭 In the real world
The five patterns, named 🏢 Anthropic · 2024 Building effective agents

How: catalogues prompt chaining, routing, parallelization (sectioning and voting), orchestrator–workers and evaluator–optimizer, each with when-to-use examples.

Why this method: composable patterns in plain code were what worked across many customer deployments; frameworks can hide the prompts and make debugging harder.

Orchestrator–workers for research 🏢 Anthropic · 2025 How we built our multi-agent research system

How: a lead agent plans the research and spawns subagents that search in parallel, each with its own context, then synthesizes their findings.

Why this method: parallel subagents (and parallel tool calls inside them) cut research time by up to 90% for complex queries, at a much higher token cost (Lesson 6.5).

Voting: self-consistency 🧪 Research · 2022 Self-Consistency (Wang et al.)

How: sample several chain-of-thought answers to the same question and take the most common final answer.

Why this method: different reasoning paths tend to agree on the right answer; on the GSM8K math benchmark it added +17.9% accuracy over a single greedy chain of thought.

Evaluator–optimizer with one model 🧪 Research · 2023 Self-Refine (Madaan et al.)

How: the same LLM writes, gives itself feedback, and refines, over several rounds, with no extra training.

Why this method: across 7 tasks, outputs improved by about 20% absolute on average over one-shot generation, and were preferred by humans and automatic metrics.

🤯 Fun fact · the cheapest pattern can beat the single call

Routing is the one pattern that can lower your bill: send the easy 70–80% of requests (an illustrative share; measure yours) to a small, fast model and only the hard ones to a large model. Lesson 8.2 turns this into model routing for cost.

These patterns build on the agent loop (6.1) and on well-designed tools (6.2). Check yourself

1. A workflow runs 3 chained steps of 2 s each, then 4 parallel workers of 3 s each, then a 1 s merge. What's the wall-clock time?
Critical path: 3 × 2 (chain) + 3 (the slowest parallel worker) + 1 (merge) = 10 s. Run one by one it would be 6 + 12 + 1 = 19 s. The token cost is the same either way.
2. Your support bot uses one giant prompt for billing, technical and refund questions. It's slow and refunds are handled badly. Which pattern fits first?
Distinct input types with different handling is exactly routing. Each handler gets a short, specialised prompt, easy categories can use a cheap model, and the refund path can get its own tools and approval rules.
3. Your evaluator–optimizer loop always runs to the maximum 8 rounds and the drafts barely change after round 3. What's most likely?
Diminishing returns plus an unreachable threshold means you pay for every round. Calibrate the threshold on known-good outputs, turn vague critique into checks (length in code, required facts, tests), and keep the cap.
📝 TL;DR
  • Five patterns: chain (+ gates), route, parallel (sectioning, voting), orchestrator–workers, evaluator–optimizer.
  • Tokens = sum of all calls; latency = critical path. Run independent calls in parallel.
  • Routing can cut cost; voting and orchestrators multiply it. Orchestrator–workers only when subtasks can't be listed in advance.
  • Evaluator loops need reachable thresholds, specific feedback, a calibrated judge and a round cap.
