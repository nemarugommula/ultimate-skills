Phase 6 · Lesson 1

What an agent is: the loop, ReAct & when not to use one

An agent is a model in a loop: it picks a tool, reads what comes back, and decides what to do next until the job is done. That loop is powerful, and it costs more on every turn.

🧰 You'll need (quick reminders)
  • Tokens and context window: the model reads everything you send on every call, and you pay per token (Lesson 0.3).
  • Chat messages: a conversation is a list of messages you resend each time; the model has no memory between calls (Lesson 0.5).
  • Function calling: you describe tools as JSON schemas and the model replies with a structured request to call one (Lesson 1.3).
🎯 Hook

In 2022, researchers at Princeton and Google tried something simple: instead of asking a model to answer in one shot, let it alternate between thinking out loud and taking an action (search, click, look), then read the result and think again. They called it ReAct (Reason + Act).

On two interactive benchmarks, a household-tasks game (ALFWorld) and an online-shopping site (WebShop), ReAct beat imitation-learning and reinforcement-learning methods by an absolute 34% and 10% success rate, while being prompted with only one or two examples. Almost every agent you'll build is a descendant of that loop.

Numbers first: every turn re-reads the whole story

Typical, illustrative numbers. Prompt caching (Lesson 1.4) makes the repeated prefix much cheaper, but the context still grows every turn.

Total tokens grow roughly with the square of the number of steps, because step k re-reads all k − 1 steps before it. That's why the two most important lines in any agent are “what tool next?” and “when do I stop?”.

💡 Big idea An agent is a loop: model decides → tool runs → result is added to the context → repeat, until the model gives a final answer or a stopping condition (max steps, budget, time) fires. A workflow is the opposite design: your code fixes the steps and the model fills them in. Use the simplest one that works.
🧠 Analogy: a new hire with a phone and a notebook

You give a new support hire a customer's question, a phone with three numbers on it (orders, policies, payments), and a notebook. They call one number, write down what they hear, reread the notebook, decide who to call next, and stop when they can answer. A workflow is giving them a checklist instead: “always call orders, then policies, then reply”. The checklist is faster and more predictable; the notebook-and-phone approach handles the cases the checklist never imagined. And if a number is broken and they never give up redialling, you need a manager who says “after 8 calls, come back to me”: that's max steps.

The loop, precisely

messages = [system prompt + tool definitions, user question] loop: reply = model(messages) # the model sees EVERYTHING so far if reply is a final answer: return it for each tool call in reply: # e.g. get_order(order_id="ORD-1042") result = run_tool(call) # your code runs it, not the model messages += [reply, result] # the observation goes back in if steps ≥ MAX_STEPS or cost ≥ BUDGET: stop and escalate

Three things to notice. The model never runs anything: it only asks, and your code decides whether to run it. Tool errors are observations too: “Error 400” or “order_id must look like ORD-1042” goes back into the context, and what it says decides whether the model can recover (Lesson 6.2). And the loop needs a stop that doesn't depend on the model's judgement.

ReAct is this loop with an explicit “Thought:” before each “Action:”: the model writes a short reason (“I need the delivery date first”), then the call, then reads the “Observation:”. Modern APIs do the same thing with native tool-call messages, and reasoning models (Lesson 1.2) do the thinking internally, but the shape is unchanged. Other agent architectures (plan first then execute, explore several branches, reflect on mistakes) are variations on this loop, covered in Lesson 6.7.

✏️ Worked example: budgeting an agent by hand

You're sizing a coding agent. System prompt + 12 tools = 4,000 tokens. Each step adds about 1,500 tokens (file contents are big). A typical task takes 20 steps; you allow up to 40.

  • Typical run, total input: 20 × 4,000 + 1,500 × (0+1+…+19) = 80,000 + 1,500 × 190 = 365,000 tokens.
  • Worst case allowed (40 steps): 40 × 4,000 + 1,500 × 780 = 160,000 + 1,170,000 = 1,330,000 tokens, over 3.6× the typical run, for 2× the steps.
  • Last call of the worst case reads 4,000 + 39 × 1,500 = 62,500 tokens: check it fits your model's context window, or plan for compaction (Lesson 6.4).

So the max-steps cap is not just a safety net, it's your cost ceiling. Set it from measured runs (e.g. the 95th percentile of successful runs plus a margin), not from a guess.

Workflow or agent? (and often: neither)

Anthropic's widely cited guide “Building effective agents” (Dec 2024) draws the line clearly. Workflows are systems where LLMs and tools are orchestrated through predefined code paths. Agents are systems where LLMs dynamically direct their own processes and tool usage. Its advice: find the simplest solution possible, and only add complexity when it measurably helps, because agentic systems trade latency and cost for better task performance.

Pick a task (or answer the questions yourself). The rules below are a rule-of-thumb chooser, the kind of reasoning a senior engineer does out loud, not an oracle.

1. Is one model call (maybe with retrieved documents) enough to do the job?
2. Can you write the steps down in advance?
3. Does the next step depend on what a tool returns?
4. If the system takes a wrong action, can it be undone cheaply?

🧰 Tools you'll actually use

You can write the loop yourself in about 25 lines with any provider SDK (below, Anthropic's Python SDK as of 2026), use the SDK's helper (Anthropic's beta tool_runner, OpenAI's Agents SDK Runner), or a framework (Lesson 6.5). Write it by hand once: it's the best way to understand what frameworks do for you. Lesson 6.8 builds this loop from scratch properly, with output parsing, error handling and tests.

import anthropic

client = anthropic.Anthropic()
MAX_STEPS = 8
tools = [{
    "name": "get_order",
    "description": "Look up an order's status and delivery date. order_id looks like ORD-1042.",
    "input_schema": {"type": "object",
                     "properties": {"order_id": {"type": "string"}},
                     "required": ["order_id"]},
}]
messages = [{"role": "user", "content": "Where's order 1042, and can I still get a refund?"}]

for step in range(MAX_STEPS):
    resp = client.messages.create(model="claude-opus-5-5", max_tokens=1024,
                                  tools=tools, messages=messages)
    messages.append({"role": "assistant", "content": resp.content})
    if resp.stop_reason != "tool_use":      # final answer: done
        break
    results = []
    for block in resp.content:
        if block.type == "tool_use":
            try:
                out, err = run_tool(block.name, block.input), False
            except Exception as e:                # errors become observations
                out, err = f"{type(e).__name__}: {e}", True
            results.append({"type": "tool_result", "tool_use_id": block.id,
                            "content": str(out), "is_error": err})
    messages.append({"role": "user", "content": results})
else:
    escalate_to_human(messages)                  # max steps hit: don't loop forever

Model IDs change often; check the provider's models page. tool_result blocks go back in a user message and must reference the tool_use_id they answer.

🚀 Startup vs big tech

Week one

Start with a single call or a 2-step workflow. If you need an agent, hand-write the loop with 3–5 tools, a max-steps cap, a dollar cap per run, and log every step. Read 20 traces by hand before tuning anything.

At scale

Per-task budgets and step caps from measured percentiles, tracing on every run, offline trajectory evals in CI (Lesson 5.5), prompt caching for the fixed prefix, and fallbacks to a workflow or a human when the agent hits its limits. Agents are a product surface with SLOs, not a demo.

🎤 Interview angle

“Would you build this as an agent?” A senior answer:

  • Asks whether the steps are known in advance: if yes, a workflow is cheaper, faster and easier to test.
  • Explains the cost shape: context grows each turn, so total tokens grow roughly with steps², and latency with steps.
  • Names the stops: max steps, budget, timeouts, and human escalation for irreversible actions.
  • Says how they'd measure it: task success rate over many runs, steps and cost per success (Lesson 5.5).
🏭 In the real world
Reason + act, interleaved 🧪 Research · 2022 ReAct (Yao et al.)

How: prompt the model to alternate “Thought”, “Action” and “Observation” lines, with a real tool (a Wikipedia API, a web shop, a text game) answering each action.

Why this method: grounding each step in real observations reduced hallucination compared with chain-of-thought alone on question answering, and beat imitation and RL baselines by 34% and 10% absolute on ALFWorld and WebShop.

Workflows first, agents when needed 🏢 Anthropic · 2024 Building effective agents

How: distinguishes workflows (predefined code paths) from agents (the model directs its own process), and catalogues the common workflow patterns (Lesson 6.3).

Why this method: across many customer deployments, the successful ones used simple, composable patterns rather than complex frameworks, and agents included stopping conditions such as a maximum number of iterations.

A turn cap by default 🧰 Open source OpenAI Agents SDK: running agents

How: the SDK's Runner runs the loop for you and raises MaxTurnsExceeded when a run passes max_turns (10 by default in the source).

Why this method: the framework authors chose to make an unbounded loop something you opt into (max_turns=None), not something you get by accident.

How long a task can an agent handle? 🧪 Research · 2025 METR: Measuring AI Ability to Complete Long Software Tasks

How: measures the length of tasks (in human time) that agents complete with 50% success, the “time horizon”.

Why this method: one number that tracks agent progress over time; it has been doubling about every seven months since 2019, which is why yesterday's “too hard for an agent” needs re-testing.

🤯 Fun fact · two examples were enough

ReAct needed no training at all for its biggest wins: on ALFWorld and WebShop it was prompted with just one or two worked examples of the Thought–Action–Observation format. The loop, not a new model, did the heavy lifting.

Check yourself

1. The fixed part of your prompt is 3,000 tokens and each step adds 1,000 tokens. How many input tokens does a 5-call agent run send in total?
Call k sends 3,000 + 1,000 × (k − 1): 3,000 + 4,000 + 5,000 + 6,000 + 7,000 = 25,000. The growing history adds 10,000 tokens on top of the 15,000 you'd guess from the fixed part alone.
2. In your traces, an agent calls the same failing tool 40 times in a row with identical arguments. What's the best first fix?
The model can only react to what the observation says: “Error 400” gives it nothing to change, so it retries. An actionable error (“order_id must look like ORD-1042”) lets it fix itself, and a step cap bounds the damage when it can't. Loop detection (Lesson 6.6) catches the rest.
3. Every night you extract fields from invoices, validate them against the purchase order, and post them to the accounting system. The steps never change. What should you build?
The steps are known in advance and don't depend on run-time discoveries, so a fixed code path is cheaper, faster and testable. Use the model where it helps (extraction) and plain code where it's deterministic (validation).
📝 TL;DR
  • Agent = model → tool call → observation → repeat, until a final answer or a stop condition.
  • Context grows every turn: total tokens ≈ steps², latency ≈ steps. Max steps is your cost ceiling.
  • Tool errors are observations; actionable errors let the model recover, vague ones make it loop.
  • Workflow (your code picks the steps) beats agent whenever the steps are known in advance. Start simple.
