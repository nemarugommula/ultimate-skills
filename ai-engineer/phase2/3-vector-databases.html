Phase 2 · Lesson 3

Vector databases: pgvector, Pinecone, Qdrant, Weaviate & friends

An ANN index finds nearby vectors. A vector database also has to filter by tenant and date, survive crashes, handle updates and deletes, and not cost a fortune. That's where most production pain lives.

🧰 You'll need (quick reminders)
  • Embeddings are vectors for text; we search for the nearest ones (Lesson 2.1).
  • HNSW is a graph index; efSearch is how many candidates it collects per query (Lesson 2.2).
  • Memory math: N vectors × d dimensions × 4 bytes (2.2). Basic SQL helps for the pgvector examples.
🎯 Hook

Mem0, a company that gives AI agents long-term memory, kept its vectors in Postgres with pgvector and HNSW indexes. In 2026 its engineers found the indexes showed 0 scans in production. Once queries added selective per-tenant filters, Postgres's planner decided a sequential scan was cheaper, so every vector search scanned a 1,153 GB table. Under load, searches took 8 to 14 seconds.

The fix wasn't a better embedding model. They moved vector search to a dedicated engine (turbopuffer) and kept the records in Postgres: retrieval dropped to about 110 to 120 ms. The index worked fine on its own; it was the filter that broke it.

Plain sentence: a vector database is a normal database whose star feature is “order by similarity”. Judge it like any database: correctness under filters, durability, operations, cost. The ANN algorithm is often the same HNSW everywhere.

💡 Big idea The hard part of vector search in production is combining similarity with ordinary constraints: filters, tenants, permissions, freshness and deletes. A pure ANN index finds “the nearest 40 vectors anywhere”; your user needs “the nearest 10 vectors they're allowed to see”. How a database closes that gap decides whether results are fast, correct, or empty.
🧠 Analogy: the bookshop with a smart assistant

The assistant (the ANN index) can instantly bring you the 40 books most like the one in your hand. But you only want paperbacks in Spanish. Post-filtering: the assistant brings 40, and you throw out the ones that don't match. If only 1 in 50 books is a Spanish paperback, you're left with nothing. Pre-filtering: you first walk to the Spanish paperback shelf and compare every book there yourself: perfect, but slow if the shelf is huge. Filtered search: the assistant knows the filter while walking the shop, and keeps going until it has 10 that match.

Filtering: the empty-results trap

pgvector's own documentation spells out the trap: filters are applied after the approximate index is scanned, so “if a condition matches 10% of rows, with HNSW and the default hnsw.ef_search of 40, only 4 rows will match on average.” You asked for 10 results and got 4, with no error.

StrategyHowGood whenFails when
Post-filterANN top-ef candidates, then drop non-matchingFilter keeps most rowsSelective filters: too few or zero results
Pre-filter (exact)Find matching rows first (normal index), then compare every oneFilter keeps few rows (a tenant with 2,000 docs)Filter keeps millions of rows: back to brute force
Filtered / iterative graph searchWalk the graph, skip non-matching nodes, keep going until k matches (pgvector 0.8.0+ iterative scans; Qdrant's filterable HNSW)Most casesFilter correlated with the vectors can strand the walk; needs a scan limit
Query planner (auto)Estimate how many rows match, then choose exact scan or graph search per query (Qdrant does this)Mixed workloadsBad estimates; still needs payload indexes

Two more structural fixes: partition by the filter (one partition or partial index per tenant or category, which pgvector's README recommends for tenant isolation), and payload indexes on fields you filter by (Qdrant's docs say to create them before ingesting data).

Simulated with 2D points and a toy graph: efSearch = 40; iterative scan doubles the candidate list until 10 matches or a 600-candidate limit (like pgvector's hnsw.max_scan_tuples); the planner switches to an exact scan when fewer than 200 rows match. Real engines differ in details, not in shape.

What you should see: post-filtering at 10% returns about 3 or 4 of 10, at 1% usually none. Pre-filtering is always correct but costs one comparison per matching row, so at 100% it's brute force. Iterative scan fixes random filters, but when the filter is correlated (Acme's documents are far from the query), the graph walk wanders through hundreds of non-matching neighbours and can hit its limit. The planner wins both ways, which is why mature engines have one.

The rest of the database job

  • Multi-tenancy. Options: one index per tenant (clean isolation, painful with 100,000 small tenants), or one shared index with a tenant field (efficient, but every query must filter, and noisy neighbours share resources). Pinecone uses namespaces; Qdrant recommends one collection with a tenant payload index marked is_tenant; Postgres offers partitions and row-level security. Never rely on the application remembering to add the filter: enforce it in one place (Lesson 4.7 covers permissions).
  • Updates and deletes. HNSW graphs don't like deletions: most engines mark a deleted node as a tombstone and clean up later, and graphs degrade until vacuumed or rebuilt. pgvector's README notes that vacuuming HNSW indexes can take a while and suggests reindexing first. Re-embedding changed documents means upsert (delete + insert).
  • Durability. An in-memory Faiss index disappears on restart unless you save and reload it; databases log writes, replicate and snapshot. Ask: what happens to the last minute of writes when a node dies?
  • Freshness. Some systems make new writes searchable in milliseconds, others after a background index build. If your agent writes a memory and reads it a second later, that matters.
  • Cost. The RAM for vectors plus graph usually dominates (Lesson 2.2's calculator). Serverless engines that keep vectors on object storage and cache hot data trade some latency for much lower cost on large, mostly cold, multi-tenant data.
✏️ Worked example: does pgvector on one box fit?

A B2B app: 300 tenants, 5 million chunks in total, 1,536-dim vectors, 20 queries per second at peak.

  • Vectors (vector, float32): 5,000,000 × 1,536 × 4 = 30.7 GB. With halfvec (float16): 15.4 GB.
  • HNSW links (M = 16): about 5M × 128 bytes ≈ 0.64 GB. Text and metadata: say 5M × 2 KB = 10 GB, mostly on disk.
  • Working set with halfvec: about 16 GB of hot index, so a 32 to 64 GB Postgres instance holds it in memory. 20 queries per second is light for one node.
  • Filters: the biggest tenant has 400,000 chunks (8%), the smallest 2,000 (0.04%). With a plain HNSW index and post-filtering, small tenants get empty results. Fix: iterative scans, plus partitioning or an exact scan for small tenants.

Verdict: pgvector is enough, if you design the filtering. Note also that pgvector indexes vector columns up to 2,000 dimensions and halfvec up to 4,000, so a 3,072-dim model needs halfvec or Matryoshka truncation to be indexed at all.

🧰 Tools you'll actually use

pgvector with psycopg and the pgvector Python package; the qdrant-client, pinecone, weaviate-client, pymilvus, chromadb and lancedb SDKs; and framework wrappers in LangChain and LlamaIndex that hide the differences (handy for prototypes, limiting for tuning).

-- pgvector (0.8.x): a table, an HNSW index, and a filtered search
CREATE EXTENSION IF NOT EXISTS vector;
CREATE TABLE chunks (
  id        bigserial PRIMARY KEY,
  tenant_id int NOT NULL,
  body      text,
  embedding vector(1536)
);
CREATE INDEX ON chunks USING hnsw (embedding vector_cosine_ops);  -- defaults m = 16, ef_construction = 64
CREATE INDEX ON chunks (tenant_id);

SET hnsw.ef_search = 100;
SET hnsw.iterative_scan = relaxed_order;   -- keep scanning when the filter drops rows
SELECT id, body, embedding <=> $1 AS distance    -- <=> cosine distance, <-> L2, <#> negative inner product
FROM chunks WHERE tenant_id = 42
ORDER BY embedding <=> $1 LIMIT 10;
# Python + pgvector
import psycopg, numpy as np
from pgvector.psycopg import register_vector

conn = psycopg.connect("dbname=app", autocommit=True)
register_vector(conn)                          # numpy arrays ⇄ vector columns
q = np.array(query_embedding)
rows = conn.execute(
    "SELECT id, body FROM chunks WHERE tenant_id = %s ORDER BY embedding <=> %s LIMIT 10",
    (42, q)).fetchall()

# Qdrant: one collection, tenant field indexed as a tenant key
from qdrant_client import QdrantClient, models

client = QdrantClient(url="http://localhost:6333")
client.create_collection(collection_name="chunks",
    vectors_config=models.VectorParams(size=1536, distance=models.Distance.COSINE))
client.create_payload_index(collection_name="chunks", field_name="tenant_id",
    field_schema=models.KeywordIndexParams(type=models.KeywordIndexType.KEYWORD, is_tenant=True))
client.upsert(collection_name="chunks", points=[
    models.PointStruct(id=1, vector=doc_embedding, payload={"tenant_id": "acme", "body": "Refunds take 5 days."})])
hits = client.query_points(collection_name="chunks", query=query_embedding, limit=10,
    query_filter=models.Filter(must=[models.FieldCondition(key="tenant_id", match=models.MatchValue(value="acme"))]),
    search_params=models.SearchParams(hnsw_ef=128)).points

With relaxed_order, pgvector may return results slightly out of distance order; its README shows re-sorting them in an outer query if you need exact order.

🚀 Startup vs big tech

Week one

Use the database you already have: pgvector if you're on Postgres, or a managed service if you aren't. Put tenant and permission filters in a single data-access function, turn on iterative scans, and write a test that a tiny tenant still gets 10 results.

At scale

Dedicated clusters or serverless engines per workload, vectors sharded by tenant or region, quantized indexes, a sync pipeline from the source of truth (change data capture), recall and latency dashboards per tenant size, and planned re-indexing when models change.

🎤 Interview angle

“Which vector database would you use, and why?” A senior answer:

  • Refuses to answer by brand. Asks about scale, filters and tenancy, update rate, latency target, team ops capacity and what database already exists.
  • Names the filtering strategy explicitly (post vs pre vs filtered graph search) and the empty-results trap.
  • Covers durability, deletes and sync from the source of truth, plus the cost driver (RAM per vector).
  • Proposes a load test with real filters on two candidates before committing.
🏭 In the real world
Vectors next to records, not in them 🏢 Mem0 · 2026 How we cut vector search latency by 70x

How: a two-phase read: the vector engine returns matching memory IDs, then Postgres fetches the full records.

Why this method: with selective tenant filters, Postgres stopped using its HNSW indexes and scanned a 1,153 GB table; separating search from storage brought retrieval to about 110 to 120 ms.

Reuse the search engine you have 🏢 Figma · 2024 The infrastructure behind AI search in Figma

How: embeddings for billions of entries indexed with OpenSearch's k-NN, alongside metadata for faceted filters; quantization and removing drafts and duplicates kept the in-memory index manageable.

Why this method: OpenSearch already ran Figma's keyword search. They also hit a real-world bug: removing embeddings from _source to save space made document updates wipe them, so they re-fetched vectors from DynamoDB on update.

Filters inside the graph 🧰 Open source Qdrant: Filterable HNSW

How: extra graph edges are built within each payload category, so a filtered walk stays connected; a query planner picks exact scan or graph search from the estimated number of matches.

Why this method: plain HNSW with nodes removed by a filter splits into disconnected pieces past a threshold, and search accuracy falls off a cliff.

Iterative index scans 🧰 Open source · 2024 pgvector 0.8.0

How: when filters drop rows, the HNSW or IVFFlat scan continues automatically until enough results are found or a limit (hnsw.max_scan_tuples, 20,000 by default) is hit.

Why this method: it fixes “asked for 10, got 4” without changing queries, while the limit caps the cost of very selective filters.

🤯 Fun fact · the 2,000-dimension wall

pgvector can store vectors of up to 16,000 dimensions, but its indexes only accept vector columns up to 2,000 dimensions (halfvec up to 4,000). Many teams discover this the day they try to index 3,072-dimensional embeddings from a large model. The usual fixes are exactly Lesson 2.1's: store halfvec, or ask the model for fewer Matryoshka dimensions.

Check yourself

1. HNSW with efSearch = 40 and post-filtering. The filter matches 5% of rows, independent of the vectors. About how many results come back when you ask for 10?
The index returns about 40 candidates; 5% of 40 = 2 survive the filter on average. Fixes: iterative/filtered scans, a larger efSearch, pre-filtering for selective filters, or partitioning by the filter field.
2. A SaaS app has 20,000 tenants, most with a few hundred documents. What's usually the best layout?
20,000 tiny indexes waste memory and operations. A shared index with a tenant key (Qdrant's is_tenant, namespaces, partitions) is efficient; filtered search or an exact scan keeps small tenants' results full. App-side post-filtering returns empty pages for small tenants.
3. Your team runs Postgres, has 2 million chunks, a small ops team and per-customer filters. A colleague wants a new managed vector database. What's the strongest first move?
2 million vectors fit comfortably on one Postgres node, and you keep joins, transactions and existing backups. A dedicated system may win later; the load test with your filters will tell you when. An in-process Faiss index lacks filters, durability and updates.
📝 TL;DR
  • A vector database = ANN index + filters, CRUD, durability, tenancy and often hybrid search.
  • Post-filtering with selective filters returns too few or zero results; use filtered/iterative search, a planner, or pre-filtering for small subsets.
  • Multi-tenancy: usually one shared index with an indexed tenant key, enforced in one place.
  • Deletes degrade graphs; plan vacuuming, rebuilds and re-embedding.
  • Start with the database you have (pgvector is enough for millions of vectors) and load-test with real filters before adding a new system.
