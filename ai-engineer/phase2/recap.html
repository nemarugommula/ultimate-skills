Recap: Embeddings & vector search

Text becomes vectors, nearness becomes meaning, indexes make nearness fast, databases make it safe, keywords cover its blind spots, and the same distances power classification, clustering and dedup.

🧾 Cheat sheet

🧭

2.1 Embeddings

memory = N × d × 4 bytes

Similar meaning → nearby vectors. Normalized vectors: cosine = dot product. Pick a model with your own eval; mind query/document prefixes; never mix models in one index; Matryoshka lets you keep fewer dims.

OpenAI text-embedding-3, Gemini, Voyage, Cohere, sentence-transformers, MTEB

🕸️

2.2 ANN indexes

exact = N × d per query

Exact is fine under ~100k vectors. HNSW (graph; efSearch buys recall), IVF (clusters; nprobe), PQ and quantization (4× to 64× smaller). Measure recall@k against exact search.

Faiss, hnswlib, Voyager, ScaNN, DiskANN

🗄️

2.3 Vector databases

post-filter: ef × selectivity results

An index plus filters, CRUD, durability and tenancy. Selective post-filters return too few results: use filtered/iterative search, a planner or partitions. Start with the database you have.

pgvector, Qdrant, Pinecone, Weaviate, Milvus, Chroma, LanceDB, turbopuffer, Elastic/OpenSearch

🔀

2.4 Hybrid search

RRF = Σ 1 / (60 + rank)

Dense wins paraphrases; BM25 wins codes, IDs and names. Run both, fuse ranks with RRF (or normalized weighted scores), then rerank. SPLADE = learned sparse with expansion.

Elasticsearch rrf retriever, Qdrant prefetch + RRF, Weaviate alpha, rank_bm25

🧩

2.5 Beyond search

all pairs = N² ÷ 2; use ANN top-k

Classify by label descriptions, centroids or a small classifier (~100× cheaper than an LLM per item); cluster to discover topics; dedup by threshold + guard rules; recommend by neighbours.

scikit-learn, BERTopic, sentence-transformers utilities, GPTCache

🏗️ Build it yourself: search over a support archive

A B2B help-desk company wants “find similar past tickets” for its agents. 3 million tickets (average 300 tokens), 400 customer companies (tenants) whose data must never mix, agents often paste ticket IDs and error codes, about 50,000 searches a day, p95 latency under 200 ms, a team of four engineers already running Postgres. Design the retrieval: model, dimensions, index, database, filtering, hybrid, evaluation and cost. Write your answer before opening the solution.

Solution One strong design, with numbers

Requirements that drive the design. Strict tenant isolation (filters on every query); exact codes and IDs (keyword search needed); moderate scale (3M vectors fits one node); small team (avoid new infrastructure unless forced).

Pipeline. Ticket text → (strip signatures, dedup exact copies by hash) → embed with a hosted model at 1,024 dims (Matryoshka truncation), storing model name and version → Postgres table tickets(tenant_id, ticket_id, body, embedding halfvec(1024), tsv tsvector) → HNSW index (cosine) + GIN full-text index + index on tenant_id. Query: embed the query, run dense (with WHERE tenant_id = $1, hnsw.iterative_scan on) and full-text search in parallel, fuse with RRF (k = 60), return the top 10. If the query matches an ID pattern, also do an exact lookup and pin it first. Add a reranker later if evals justify it (Lesson 3.4).

Costs. One-off embedding: 3M × 300 = 900M tokens × $0.02 per million ≈ $18. Queries: 50,000 × 15 tokens = 750k tokens ≈ $0.02 a day. Vectors: 3M × 1,024 × 4 bytes = 12.3 GB as float32, 6.1 GB as halfvec; HNSW links (M = 16) about 0.4 GB. A 32 to 64 GB Postgres instance holds the hot index in RAM.

Eval plan. 200 labelled queries sampled from real agent searches, sliced into ID/code queries, paraphrase queries and small vs large tenants. Metrics: recall@10 and MRR for dense-only, BM25-only and hybrid; the ANN index's recall@10 against exact search on a sample; p95 latency under load with tenant filters. A test that a 500-ticket tenant still gets 10 results.

Pitfalls. Post-filtering empties small tenants' results (use iterative scans or exact scans for small tenants); query and document prefixes for the chosen model; vectors from a new model can't mix with old ones (plan re-embedding as a migration, about $18 here); deletes and edits need upserts and periodic reindexing; tenant filter enforced in one data-access function, never left to callers; Postgres's planner may skip the HNSW index for selective filters, so check EXPLAIN ANALYZE.

When to move off Postgres. When the index outgrows a single node's RAM, tenant-filter latency can't be fixed with partitions, or write load hurts the main app. Then a dedicated engine with tenant-aware indexing (Qdrant, turbopuffer, Pinecone…) behind the same data-access function.

🏆 Boss quiz

1. 20 million chunks, 768 dimensions. How much memory do the vectors need as float32, and as int8?
20M × 768 × 4 bytes = 61.4 GB; int8 is one byte per number: 15.4 GB. Add the index structure on top (for HNSW, roughly 2 × M × 4 bytes per vector).
2. Search finds “how do I reset my password?” articles fine, but “SSO error AUTH-4401” returns generic login pages. What's the first fix?
The index is finding the nearest vectors correctly; the embedding just doesn't distinguish “AUTH-4401” from other codes. Keyword retrieval matches the rare token exactly; RRF merges both lists.
3. After adding a WHERE tenant_id = ? filter, small customers get 0 to 3 results from your HNSW index. Why, and what fixes it?
Post-filtering keeps about efSearch × (share of rows matching). A tenant with 0.1% of the rows gets 40 × 0.001 ≈ 0 results. Filter-aware search, a planner that switches to exact scan, or per-tenant partitions fix it.
4. With RRF (k = 60), doc P is rank 1 in dense and rank 10 in BM25; doc Q is rank 3 in both. Which comes first?
RRF rewards consistent agreement. P: 0.0164 + 0.0143 = 0.0307. Q: 0.0159 × 2 = 0.0317. With a smaller k, P's first place would count for more.
5. You must route 5 million tickets a month to 12 teams, and you have 20,000 labelled historical tickets. Which design is the best starting point?
Labelled data plus embeddings gives an accurate, cheap, fast classifier; the uncertainty band keeps quality on hard cases. Clustering is for discovering categories, not matching an existing org chart.
