Phase 0 · Lesson 3

Tokens, context windows, cost & latency math

Every dollar you spend and every second your users wait is counted in tokens. Learn to estimate both on the back of an envelope.

🧰 You'll need (quick reminders)
  • An LLM reads tokens and generates one token per step, so a 500-token answer takes 500 steps (Lesson 0.2).
  • Model prices are quoted per million tokens (MTok), separately for input and output (Lesson 0.1).
🎯 Hook

A 2023 study fed the same text, translated into different languages, through the tokenizers of popular models. The token counts differed by up to 15 times (Petrov et al.).

Same meaning, up to 15× the tokens: up to 15× the bill, a longer wait, and less room in the context window. If your users write in a language the tokenizer saw little of, a cost model built on English test prompts is wrong before launch.

The last row is from Anthropic's models overview (as of October 2026): the same million tokens holds about a quarter fewer words on the newer tokenizer. Token counts depend on which tokenizer, so always count with the model you'll actually use.

💡 Big idea Tokens are the unit of everything: what fits (the context window), what you pay (input and output priced per token), and how long users wait (output is generated one token at a time). Once you can count tokens, you can predict cost and latency before you build.
🧠 Analogy: a taxi meter

Input tokens are the flag fall: you pay for everything you put in the prompt, read once, quickly. Output tokens are the meter running: slower and pricier, ticking with every word the model writes. A cached prompt is a season ticket: you paid for that stretch of road already, so it's heavily discounted the next time.

How text becomes tokens: BPE

Models don't read characters or whole words. They read subword tokens produced by a tokenizer, usually trained with byte-pair encoding (BPE):

  1. Start with single characters (modern tokenizers start from the 256 possible bytes, so any text, emoji or language can be encoded).
  2. Count every adjacent pair across a big training corpus. Merge the most frequent pair into a new token.
  3. Repeat tens of thousands of times. Common words become one token (“ the”, “ refund”); rare words become several pieces.

Consequences you'll hit in production: common English is cheap; rare words, code, numbers and non-Latin scripts take more tokens; leading spaces are part of tokens (“ cat” ≠ “cat”); and models see pieces, not letters, which is why they're bad at counting the r's in “strawberry”.

Context windows: what fits

The context window is the maximum number of tokens a model can handle in one request: input (system prompt + history + documents) + output. As of October 2026, the current Claude models list a 1M-token window with up to 128K output tokens; OpenAI's GPT-6 family lists 1.05M with 128K output.

  • Big windows are not free: you pay for every input token on every call, and long inputs add latency.
  • Some providers charge more for very long prompts: Google's Gemini 3.1 Pro preview, for example, lists $2 per million input tokens up to 200k tokens and $4 beyond.
  • Fitting isn't the same as using well: models can miss details buried in very long contexts. Lesson 1.4 covers ordering, trimming and caching; Phase 3 covers retrieving only what's needed.

Latency: two numbers, not one

  • TTFT, time to first token: network + queueing + reading your whole input (prefill). Typically a few hundred milliseconds to a couple of seconds; more for very long prompts or reasoning models that think first.
  • Output speed, tokens per second: typically tens to a couple of hundred tokens/s per request, depending on model and provider.
  • Total ≈ TTFT + output tokens ÷ speed. Streaming (Lesson 0.5) shows text at TTFT, so perceived latency is TTFT; total time is unchanged.
  • Throughput is different again: how many tokens per minute your whole system processes. Providers cap it with rate limits like TPM (tokens per minute).
✏️ Worked example: a support assistant's monthly bill and wait

20,000 requests a day. Each sends a 2,000-token system prompt (the same every time, so cacheable) + 500 tokens of question and history, and gets 350 tokens back. Mid-tier price: $2 input, $10 output per MTok, cache reads at 10%.

  • Without caching: 2,500 × $2/M + 350 × $10/M = $0.005 + $0.0035 = $0.0085 per request → × 20,000 × 30 = $5,100 a month.
  • With caching: 2,000 × $0.20/M + 500 × $2/M + 350 × $10/M = $0.0004 + $0.001 + $0.0035 = $0.0049 → $2,940 a month (−42%).
  • Notice: after caching, output is 71% of the bill ($0.0035 of $0.0049). The next lever is shorter answers.
  • Latency at TTFT 0.6 s and 80 tokens/s: 0.6 + 350 ÷ 80 ≈ 5.0 s total; with streaming, users see text at 0.6 s.

Cache writes cost a little more than normal input (1.25× for a 5-minute cache on Anthropic), paid only when the cache is refreshed; ignored here.

🧰 Tools you'll actually use

tiktoken (OpenAI's open-source BPE tokenizer), Anthropic's free token-counting endpoint, Hugging Face tokenizers for open models (AutoTokenizer), and, most important, the usage numbers every API response returns. Bill from usage; estimate with counters.

import tiktoken, anthropic

enc = tiktoken.get_encoding("o200k_base")          # an OpenAI encoding
ids = enc.encode("How many r's are in strawberry?")
print(len(ids), [enc.decode([i]) for i in ids])   # see the pieces

client = anthropic.Anthropic()
n = client.messages.count_tokens(                     # counts with this model's tokenizer
    model="claude-opus-5-5",
    system="You are a support assistant.",
    messages=[{"role": "user", "content": "Where is my refund?"}],
)
print(n.input_tokens)

msg = client.messages.create(
    model="claude-haiku-5-5", max_tokens=300,
    messages=[{"role": "user", "content": "Where is my refund?"}],
)
print(msg.usage.input_tokens, msg.usage.output_tokens)  # log these on every call

Anthropic's docs warn not to reuse token counts measured on models before Claude Opus 4.7 for newer ones: the tokenizer changed. Recount whenever you switch models.

🚀 Startup vs big tech

Startup

A spreadsheet: requests/day × (input, output) tokens × price, checked against the real usage numbers after week one. Cost rarely matters before product-market fit, unless one prompt design makes unit economics impossible. Check that early.

Big tech

Token budgets per feature, per-tenant cost attribution in the LLM gateway, caching hit-rate dashboards, latency SLOs (service-level objectives) on TTFT and p95 total time, and negotiated or provisioned capacity because public rate limits aren't enough.

🎤 Interview angle

“Estimate the monthly cost and latency of this feature” is a classic AI-system-design opener. A senior answer:

  • States assumptions out loud: requests/day, input and output tokens, model tier, cache hit rate.
  • Splits input vs output and does the arithmetic; notices which term dominates.
  • Separates TTFT from generation time, and perceived latency (streaming) from total.
  • Names the levers in order of payoff: fewer output tokens, caching, smaller model or routing, batch; and the quality risk of each.
🏭 In the real world
Byte-pair encoding for language models 🧪 Research · 2015 Neural Machine Translation of Rare Words with Subword Units

How: adapted BPE, a compression algorithm, to split words into frequent subword units, so a fixed vocabulary can spell any word.

Why this method: no more “unknown word” tokens: rare names and compounds are built from pieces. Its descendants tokenize the text for most LLMs today.

A fast tokenizer you can run 🧰 Open source openai/tiktoken

How: OpenAI's BPE tokenizer library with its encodings (such as o200k_base), callable from Python.

Why this method: count and inspect tokens locally before you send anything; the README reports it 3–6× faster than a comparable open-source tokenizer.

Tokenizers change between model versions 🏢 Anthropic · 2026 Claude models overview

How: the tokenizer introduced with Claude Opus 4.7 fits about 555k words in 1M tokens, versus about 750k for earlier models.

Why this method: the same prompt can cost more tokens on a newer model. Re-run your cost model and context-fit checks on every model migration.

Output tokens dominate latency 🏢 OpenAI Latency optimization guide

How: OpenAI's guide breaks latency into processing speed, tokens generated and input size.

Why this method: as a heuristic, cutting 50% of output tokens may cut ~50% of latency, while cutting 50% of the prompt may only improve it 1–5%. Optimize the output first.

Paying once for a long prefix 🏢 Anthropic Prompt caching

How: mark a stable prefix (system prompt, documents, tool definitions) as cacheable; later requests that share it read it from cache.

Why this method: cache hits are priced at 0.1× base input on most models (0.05× on Opus 5.5 and Sonnet 5.5), with writes at 1.25× for a 5-minute cache: a big win whenever many calls share a prefix.

🤯 Fun fact · the token that broke GPT-3

In early 2023, researchers Jessica Rumbelow and Matthew Watkins found a set of “anomalous tokens”, such as SolidGoldMagikarp, that sent GPT-2 and GPT-3 into bizarre completions: asked to repeat them, the models said something else entirely, and some even broke determinism at temperature 0. Their best explanation: the tokenizer learned these strings (scraped usernames, e-commerce backend fields) from data that was barely used to train the model itself, so the model had almost no idea what they meant. Tokenizers and models are trained separately, and the seams show.

Check yourself

1. 50,000 requests a day, each 1,000 input and 500 output tokens, at $2 / $10 per MTok, no caching. Monthly (30-day) cost?
Per request: 1,000 × $2/M + 500 × $10/M = $0.002 + $0.005 = $0.007. × 50,000 = $350/day × 30 = $10,500. Output is 71% of it, even though it's a third of the tokens.
2. Users say your report generator is slow: 1.2 s TTFT, then 1,500 output tokens at 60 tokens/s. What helps most?
Total ≈ 1.2 + 1,500 ÷ 60 = 26.2 s, of which 25 s is generation. Streaming makes text appear at 1.2 s; 500 tokens brings the total to ≈ 9.5 s. Halving the input barely moves it.
3. Your chatbot's per-conversation cost is 3× higher in Hindi than in English for the same conversations. Why, and what do you do?
Tokenizers trained mostly on English give other scripts fewer merges, so the same meaning costs more tokens. It's expected, measurable and differs between models, so it belongs in your cost model and model comparison.
📝 TL;DR
  • Tokens are subword pieces from BPE: cheap for common English, expensive for rare words, code, numbers and many non-English scripts.
  • Cost = input × price + output × (≈5× price), minus caching (~90% off repeated prefixes) and batch (~50% off); thinking tokens bill as output.
  • Latency = TTFT + output tokens ÷ speed; streaming hides the second part, fewer output tokens removes it.
  • The context window caps input + output; bigger isn't free. Always count with the model's own tokenizer and log real usage.
