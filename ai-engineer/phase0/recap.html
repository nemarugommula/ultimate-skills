🧾 Cheat sheet

0.1 What an AI engineer does

Build products on pre-trained foundation models and own quality, cost, latency, reliability and safety with numbers. Stack: app → prompt & context (+ retrieval) → gateway → model → tools, wrapped by guardrails and evals. Wrong answers usually cost more than the model bill.

SDKs · LiteLLM · a golden eval set from day one

0.2 How LLMs work

Tokens in → probability for every next token → sample → append → repeat. p ∝ exp(z/T): low T sharp (greedy loops), high T flat (wanders); top-p cuts the tail. Transformers attend to earlier tokens. Pretrain → SFT → preference tuning (RLHF/DPO) → reasoning RL. Hallucination = plausible, ungrounded; fix with context, tools, citations, evals.

transformers · logits → softmax

0.3 Tokens, cost & latency

BPE subwords: ~4 chars of English per token on older tokenizers; code, numbers and many scripts cost more (up to 15× across languages). Cost = in × price + out × ~5× price; cache reads ~10%; batch ~50% off; thinking bills as output. Latency = TTFT + out ÷ tokens/s. Cut output first.

tiktoken · count_tokens · response.usage

0.4 The model landscape

Small / balanced / frontier tiers ~10× apart in price (≈ $0.10/$0.50 → $2/$10 → $10/$50 per MTok, Oct 2026). Closed APIs vs open weights (Llama, Qwen, DeepSeek, Mistral, Gemma, gpt-oss…; read the licence). Choose from requirements, decide with your own eval: n = 50 means ±11 points.

provider model pages · Hugging Face · bake-off script

0.5 Calling models

Role-tagged messages + params → text, stop reason, usage. Stateless: resend history. Always cap tokens and check the stop reason. Frontier models increasingly reject temperature/top_p. Stream for perceived latency. Fix 4xx; retry 429/5xx/529 with backoff + jitter, honor retry-after, cap retries, fall back.

messages.create · responses.create · max_retries · SSE

0.6 When not to use an LLM

If a rule, a regex, a lookup or a classic ML classifier does the job, it's usually cheaper, faster, deterministic and easier to test. Reach for small models next, and large LLMs for open-ended language. Many good systems mix them: rules first, a classifier for the bulk, an LLM for the hard tail.

regex · scikit-learn · small models

🏗️ Build it yourself

The brief

A support team receives 5,000 emails a day in English and Spanish. Build a system that tags each email (billing, shipping, returns, account, other) and drafts a reply from the company's policy docs (about 2,000 tokens of policy). An agent reviews every draft before it's sent. Sending data to a model vendor is allowed under the company's data-processing agreement. Budget: under $1,500 a month. Target: draft visible within 5 seconds of opening an email.

Before revealing: write down the pipeline, which model tier for each step, the monthly cost, the latency, and how you'd know it works.

Reveal One good design, with the numbers

Requirements, restated: 2 tasks (classification, grounded drafting), 2 languages, human in the loop (so precision matters more than full automation), $1,500/month, ~5 s.

Pipeline: (1) rules first: auto-replies, known spam senders and order-number lookups by regex (Lesson 0.6); (2) tag with a small model (or a classic classifier once you have a few thousand labelled emails); (3) draft with a balanced model, policy docs in a cached system prompt, plus the customer's order data from a tool or lookup; (4) stream the draft into the agent's UI; (5) log usage, tags, edits and send/discard decisions.

Costs (list prices as of Oct 2026, illustrative):

  • Tagging, small tier ($0.10 / $0.50): 5,000 × (400 in + 5 out) ≈ $0.21 a day, ~$6 a month.
  • Drafting, balanced tier ($2 / $10, cache reads 10%): per email 2,000 cached × $0.20/M + 1,000 fresh × $2/M + 300 out × $10/M = $0.0004 + $0.002 + $0.003 = $0.0054 → $27 a day → ~$810 a month.
  • If Spanish emails tokenize ~30% longer, drafting rises to roughly $1,035 a month: measure per language before promising the budget.

Latency: TTFT ~0.8 s + 300 tokens ÷ 80 tokens/s ≈ 4.6 s total; streamed, the agent sees text in under a second. Better still, draft when the email arrives (or overnight with the batch API at ~50% off for backlogs), so it's ready before anyone opens it.

Eval plan: 300 real past emails per language with the human-written replies and correct tags. Metrics: tag accuracy (with an error bar), share of drafts sent with no or light edits, policy-fact accuracy (no invented refunds or dates), tone. Run on every prompt or model change; track edit rate in production.

Reliability: SDK retries with backoff and jitter, a fallback model behind a gateway, a timeout, and a “no draft available” state in the UI. Pin model IDs; rerun the eval before upgrading.

Pitfalls: stale policy docs (version and refresh them); drafts promising things policy doesn't allow (ground strictly, eval for it); history bloat in long threads (trim, summarize); prompt injection in customer emails (“ignore your instructions…”, Lesson 8.3); PII in logs; agents rubber-stamping drafts (measure edit rate, sample-review sent replies).

Boss quiz 👾

1. A ticket classifier runs 300,000 times a day with 500 input and 10 output tokens on a small model at $0.10 / $0.50 per MTok. Monthly (30-day) cost?
Per call: 500 × $0.10/M + 10 × $0.50/M = $0.00005 + $0.000005 = $0.000055. × 300,000 = $16.50/day × 30 ≈ $495. Small models make high-volume classification cheap, and a classic classifier could make it cheaper still (0.6).
2. You must check that 2 million form submissions a day contain a validly formatted 16-digit card number with a correct checksum. What do you use?
The task is fully specified, so code does it exactly, in microseconds, for free, and it's trivially testable. An LLM would add cost, latency and occasional wrong answers to a problem that has none (Lesson 0.6).
3. A product manager is surprised that the assistant gives slightly different answers to the identical question. What's the explanation?
Generation samples from the next-token distribution (0.2), and serving infrastructure adds its own nondeterminism. Design for variation: evaluate over many samples, and use structured output and validation where you need exact formats.
4. A new model tops a public leaderboard by 2 points. Your team wants to switch the production assistant to it today. What do you do?
Two leaderboard points can be noise, contamination or style, and say nothing about your task. Your eval decides; check token counts too, since tokenizers change between models (0.3, 0.4).
5. A streamed response starts normally (HTTP 200), then an error event arrives halfway and the connection closes. How should your app behave?
With streaming, errors can arrive after the 200 status. Detect them, don't present half an answer as complete, and apply the same retry rules as any transient failure (0.5).
