Phase 0 · Lesson 5

Calling models: chat APIs, sampling, streaming, SDKs

An LLM call is an HTTP request with a JSON body. Know exactly what's in it, what comes back, and what to do when it fails.

🧰 You'll need (quick reminders)
  • Temperature and top-p change how the next token is chosen (Lesson 0.2).
  • You pay per input and output token; output is generated one token at a time, so TTFT (time to first token) ≠ total time (Lesson 0.3).
  • Providers offer small, balanced and frontier models, some with a reasoning-effort knob (Lesson 0.4).
🎯 Hook

When OpenAI opened the model behind ChatGPT to developers as an API, gpt-3.5-turbo, it was priced at $0.002 per 1,000 tokens, which OpenAI said was 10× cheaper than its existing GPT-3.5 models. Snap, Quizlet, Instacart and Shopify were among the early builders named in the announcement.

Suddenly a chat model was one HTTP request away for any developer. That's the moment AI engineering as a job really starts: the hard part stopped being the model and became everything around the request.

Numbers first: what one call contains

ResponseThe answer + stop_reason + usage (token counts)your output tokens

Chat APIs like Anthropic's Messages API are stateless: the model remembers nothing between calls, so you resend the whole conversation every turn. (OpenAI's Responses API can optionally keep state server-side with previous_response_id; you're still billed for the history as input.)

💡 Big idea A model call is just messages in, message out: a list of role-tagged messages (system, user, assistant), a few parameters, and a response with text, a stop reason and token usage. Everything production-grade (streaming, retries, structured output, tools) is built on that one request shape. Treat it like any remote API that is slow, metered and sometimes unavailable.
🧠 Analogy: a brilliant contractor with no memory

Every morning the contractor arrives with no memory of yesterday. So each job ticket must include the standing instructions (system prompt), the whole email thread so far (history) and today's request (user message). You pay by the word read and the word written. Sometimes the office is too busy and says “come back in 20 seconds” (a 429). A good dispatcher waits, doesn't send the same ticket 50 times, and has a second contractor on call.

Roles and the request shape

  • system: standing instructions and persona. Anthropic takes it as a top-level system field; OpenAI's Responses API as instructions (or a system/developer message).
  • user: what the person (or your code) asks.
  • assistant: the model's earlier replies, which you send back as history.
  • Tool calls and tool results are extra message types (Lessons 1.3 and 6.2).

✏️ Worked example: what statelessness costs

A chat with a 500-token system prompt. Each turn the user writes 100 tokens and the assistant replies with 300.

  • Turn 1 input: 500 + 100 = 600 tokens.
  • Turn 10 input: 500 + 9 × (100 + 300) + 100 = 4,200 tokens.
  • Total input over 10 turns: 600 + 1,000 + … + 4,200 = 24,000 tokens, versus 6,000 if each turn only sent the system prompt and the new message. Long chats cost 4× more input here, and it keeps growing roughly with the square of the number of turns.

That's why prompt caching (the history is a stable prefix), summarizing old turns and trimming history matter (Lessons 1.4, 6.4).

Streaming: server-sent events

  
With stream: true the HTTP response stays open and the server sends server-sent events (SSE), plain-text lines like event: … and data: {json}, as tokens are generated. Anthropic's stream goes message_start → content_block_start → many content_block_delta → content_block_stop → message_delta (stop reason, final usage) → message_stop, with occasional pings. OpenAI's Responses stream sends typed events such as response.created, response.output_text.delta and response.completed.

  
    
    
  • Streaming cuts perceived latency to TTFT; total time is the same.
    • 
    
  • Your server must pass the stream through (don't buffer it in a proxy), and your UI must render partial text.
    • 
    
  • Errors can arrive inside a stream that started with 200 OK; handle an error event and a dropped connection.
    • 
    
  • For very long generations, streaming (or the batch API) also avoids idle-connection timeouts.
    • 
  


  
When calls fail

  

    
StatusMeaning (Anthropic error type)Retry?

    
400invalid_request_error: bad parameter, unsupported setting, too many tokensNo: fix the request

    
401 / 403authentication_error / permission_errorNo: fix keys or access

    
404 / 413not_found_error (wrong model ID or path) / request_too_largeNo

    
429rate_limit_error: too many requests or tokens per minute, or a spend capYes, with backoff and the retry-after header; but a spend-cap 429 has no retry-after and keeps failing

    
500 / 504api_error / timeout_errorYes, with exponential backoff (stream long requests)

    
529 (OpenAI: 503)overloaded_error (OpenAI: server_is_overloaded)Yes, with backoff; consider a fallback model or provider

  

  
The standard fix for transient errors is exponential backoff with jitter: wait 0.5 s, 1 s, 2 s, 4 s… (doubling, with a cap), each wait randomized so thousands of clients don't retry in lockstep, and give up after a few tries. Both the OpenAI and Anthropic SDKs already retry connection errors, 429s and 5xx errors twice by default with backoff; you can raise that with max_retries.


  

    ✏️ Worked example: a backoff schedule
    
Base 0.5 s, factor 2, 5 retries: waits of 0.5, 1, 2, 4, 8 s = 15.5 s worst case before giving up. With full jitter each wait is a random value between 0 and that number, so the average total is about 7.75 s, and twenty clients that failed together spread out instead of hitting the server again at the same instant. If the server sends retry-after: 3, wait at least 3 s instead.

    🧰 Tools you'll actually use
    
The provider SDKs: OpenAI (pip install openai), Anthropic (pip install anthropic), Google Gen AI (pip install google-genai); and provider-agnostic layers such as LiteLLM, which calls 100+ models in the OpenAI format and adds retries and fallbacks. Open models served by vLLM or Ollama expose an OpenAI-compatible endpoint, so the OpenAI SDK works with a different base_url.


import anthropic
from openai import OpenAI

# Anthropic Messages API: system is top-level, history goes in messages
claude = anthropic.Anthropic(max_retries=4)          # default is 2
msg = claude.messages.create(
    model="claude-sonnet-5-5",
    max_tokens=500,
    system="You are a concise support assistant.",
    messages=[{"role": "user", "content": "Where is my refund?"}],
)
text = "".join(b.text for b in msg.content if b.type == "text")  # skip thinking blocks
if msg.stop_reason == "max_tokens":
    raise RuntimeError("answer was cut off")
print(text, msg.usage.input_tokens, msg.usage.output_tokens)

with claude.messages.stream(                           # streaming (SSE) helper
    model="claude-sonnet-5-5", max_tokens=500,
    messages=[{"role": "user", "content": "Where is my refund?"}],
) as stream:
    for chunk in stream.text_stream:
        print(chunk, end="", flush=True)

# OpenAI Responses API
oai = OpenAI(max_retries=4)
r = oai.responses.create(
    model="gpt-6-luna",
    instructions="You are a concise support assistant.",
    input="Where is my refund?",
    max_output_tokens=500,
)
print(r.output_text, r.usage)

for event in oai.responses.create(model="gpt-6-luna", input="Where is my refund?", stream=True):
    if event.type == "response.output_text.delta":
        print(event.delta, end="", flush=True)

# Google Gen AI SDK (Interactions API)
from google import genai
interaction = genai.Client().interactions.create(model="gemini-3.8-flash", input="Where is my refund?")
print(interaction.output_text)

# Provider-agnostic: LiteLLM with retries and a fallback model
import litellm
resp = litellm.completion(
    model="anthropic/claude-haiku-5-5",
    messages=[{"role": "user", "content": "Where is my refund?"}],
    max_tokens=300, num_retries=3, fallbacks=["openai/gpt-6-luna"],
)
print(resp.choices[0].message.content)

    
Model IDs and SDK shapes are current as of October 2026 (official quickstarts). Anthropic's Python SDK 2.0 switches to API version 2026-10-21, which drops temperature, top_p and top_k. Read provider changelogs when you upgrade SDKs.

  


  

    ⚖️ Trade-offs
    

      
Choice✅ Gains❌ Costs

LiteLLM / gateway layerOne interface, fallbacks, cost tracking, easy model swapsNew features arrive later; a translation layer to debug

      
StreamingFast perceived response, no idle timeoutsMore complex client and error handling; harder to post-process

      
Aggressive retriesFewer user-visible failuresAmplifies overload, burns quota, long tail latency

      
Fallback to another modelSurvives provider outagesDifferent behaviour and formats: needs its own evals

    

  


  

    🚀 Startup vs big tech
    

      
Startup
One provider SDK, streaming on, the SDK's built-in retries, a timeout, and logging of usage and request IDs on every call. Add LiteLLM or a fallback provider once an outage has hurt you, or before a big launch.

      
Big tech
All calls go through an internal LLM gateway: auth, quotas per team, retries with jitter, circuit breakers, multi-provider fallbacks, prompt and response logging with PII controls, and cost attribution. Product code calls the gateway, never a provider directly.

    

  


  

    🎤 Interview angle
    
“Your LLM feature starts failing at peak traffic. What do you do?” A senior answer:

    
    
      
  • Reads the errors first: 429 (rate or quota), 529/503 (provider overload), 400 (our bug), timeouts.
    • 
      
  • Transient errors: exponential backoff with jitter, honor retry-after, cap retries, set timeouts; never retry 400s.
    • 
      
  • Capacity: request higher limits or provisioned throughput, smooth bursts with a queue, cut tokens per request (Lesson 0.3).
    • 
      
  • Resilience: a fallback model or provider behind a gateway, streaming for long outputs, alerts on error rates and spend.
    • 
    

  


  

    🏭 In the real world
    

      
The event stream, documented 🏢 Anthropic Streaming messages

      
How: with stream: true, responses arrive as SSE events (message_start, content_block_delta…, message_delta, message_stop), and the SDKs offer helpers that yield text or assemble the final message.

      
Why this method: users see text immediately, and long generations don't hit idle-connection timeouts; the docs recommend streaming or batches for long requests.

    

    

      
Not every 429 is temporary 🏢 OpenAI API deployment checklist

      
How: check the HTTP status and error code before choosing a recovery; follow Retry-After when present; otherwise exponential backoff with jitter and bounded retries.

      
Why this method: billing, spend and quota errors need action, not retries. Classifying errors is what separates resilience from a retry storm.

    

    

      
Why jitter 📜 AWS · 2015 Exponential Backoff and Jitter

      
How: simulated many clients competing for a contended resource and compared backoff variants.

      
Why this method: backoff alone leaves clients retrying in synchronized waves; adding randomness spreads them out, so the work completes with fewer calls. The playground above reproduces it.

    

    

      
One interface, many providers 🧰 Open source LiteLLM

      
How: a Python SDK and proxy that call 100+ LLMs (OpenAI, Anthropic, Vertex AI, Bedrock and more) through the OpenAI request format, with retries, fallbacks and spend tracking.

      
Why this method: swapping or adding a provider becomes a config change, which makes model bake-offs (Lesson 0.4) and outage fallbacks cheap.

    

  


  

    🤯 Fun fact · the knob that disappeared
    
Temperature was the most famous LLM parameter of the early API years. As of October 2026, Anthropic's newest API version (2026-10-21) returns a 400 error if you send temperature at all, even at its default value; its docs note that temperature = 0 never guaranteed identical outputs anyway. On frontier reasoning models, you steer with prompts, effort and structured output instead.

Check yourself

  

    
1. Retries with base 1 s, doubling, no jitter, 4 retries. Worst-case total wait before giving up?

    

    
1 + 2 + 4 + 8 = 15 s. Add the request times themselves, and set a total deadline so a user isn't left waiting forever; with full jitter the average wait halves.

  

  

    
2. After an SDK upgrade, every request fails with a 400 invalid_request_error. Your retry wrapper retries each one 5 times. What's wrong?

    

    
Retrying a 400 can never succeed and multiplies load and cost. Retry only transient errors (429, 5xx, 529, timeouts); surface 400s loudly. A newer API version dropping temperature is exactly this kind of bug.

  

  

    
3. You turn on streaming. What changes?

    

    
Streaming changes delivery, not generation: same tokens, same price, same total time. It fixes perceived latency, and it means errors can arrive mid-stream.

  


  

    📝 TL;DR
    
    
      
  • A call = role-tagged messages (system, user, assistant) + parameters → text + stop reason + usage. The API is stateless: resend history.
    • 
      
  • Always set a max-token cap and check the stop reason; sampling knobs are disappearing on frontier models, so check what your model accepts.
    • 
      
  • Stream for perceived latency; handle errors mid-stream.
    • 
      
  • Classify errors: fix 4xx, retry 429/5xx/529 with exponential backoff + jitter, honor retry-after, cap retries, have a fallback.
    • 
      
  • Use the provider SDKs (built-in retries) or a layer like LiteLLM to switch providers cheaply.
