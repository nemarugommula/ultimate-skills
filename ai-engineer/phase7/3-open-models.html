Phase 7 · Lesson 3

Open models & local inference: Hugging Face, Ollama, llama.cpp

You can download a capable model and run it on your laptop, in a browser tab, or on your own GPUs. Learn where open models live, what their licences allow, how quantization squeezes them into memory, and when running your own beats paying per token.

🧰 You'll need (quick reminders)
  • Parameters: the model's learned numbers. An “8B” model has 8 billion of them (Lesson 0.2).
  • Closed vs open models and how to choose one (Lesson 0.4).
  • Bytes per number: 16-bit = 2 bytes, 8-bit = 1 byte, 4-bit = half a byte (Lesson 7.1's memory maths).
🎯 Hook

The llama.cpp project benchmarks the same model, Llama 3.1 8B, at different precisions. In 16-bit it's 15 GiB and generates about 29 tokens per second on their test machine. Squeezed to about 4.9 bits per weight (a format called Q4_K_M), it's 4.6 GiB and generates about 72 tokens per second.

Same model, a third of the memory, two and a half times faster, and small enough for an ordinary laptop. The reason it gets faster as it gets smaller is the most useful fact in this lesson.

Numbers first: memory is parameters × bits

A model's weights take parameters × bits per weight ÷ 8 bytes. To generate each token, the model reads essentially every weight once, so on a single request generation speed is capped by memory bandwidth ÷ model size.

Model16-bit8-bit (Q8_0, 8.5 bits)4-bit (Q4_K_M, 4.9 bits)
8B16.1 GB8.5 GB4.9 GB: a 16 GB laptop
70B141 GB: two 80 GB GPUs75 GB43 GB: one 48 GB GPU
405B812 GB431 GB248 GB

Speed ceilings for one request: a laptop with 120 GB/s memory bandwidth (the base M4 MacBook Pro) reading a 4.9 GB model can't beat about 120 ÷ 4.9 ≈ 24 tokens/s; in practice you get maybe half to two-thirds of that. An H100 (3.35 TB/s) reading the 16 GB version tops out near 209 tokens/s. Lesson 7.4 shows how batching many requests breaks through this ceiling.

Sizes from the formula match llama.cpp's own table (8B at Q4_K_M: 4.9 GB; 70B: 43.1 GB; 405B: 249 GB). Add memory for the KV cache, which grows with context length (Lesson 7.4).

💡 Big idea Running a model yourself is a memory problem before it's a compute problem. Quantization trades a little quality for a lot of memory and speed. And “open” describes the weights you can download, not what you're allowed to do with them: read the licence.
🧠 Analogy: the photo library

A full-precision model is a library of RAW photos: perfect, huge, slow to flip through. Quantizing is saving them as good JPEGs. At high quality you can't tell the difference and the library fits on your phone; squeeze too hard and faces get blocky. Flipping through a smaller library is faster, too, because there's less to read. And the licence is the photographer's terms: some photos are free for anything, some only for non-commercial use, some require credit.

Where open models live: the Hugging Face Hub

The Hugging Face Hub is the GitHub of models. Each model is a git repository holding the weights (usually .safetensors files), config.json (layers, sizes, context length), the tokenizer and its chat template, and a model card: intended use, training data, evaluation results, limitations and the licence. Some repos are gated: you accept terms before downloading.

Licence (examples, as of 2026)What it means in practice

Open weights means you can download the weights. Open source in the stricter sense also means the training data and code are released (AI2's OLMo and Tülu, for example). Most “open” models are open-weight.

Quantization levels: what you lose

Quantization stores each weight with fewer bits, plus a shared scale per small block of weights so the rounding error stays small. llama.cpp's names read like this: Q4_K_M = about 4 bits, “K-quant” method, medium mix (some sensitive tensors kept at higher precision). Its own benchmark on Llama 3.1 8B:

FormatBits per weightSizeGeneration speedTypical quality impact
F1616.014.96 GiB29 t/sReference
Q8_08.57.95 GiB51 t/sPractically lossless
Q6_K6.66.14 GiB59 t/sVery close to reference
Q5_K_M5.75.33 GiB67 t/sSmall loss
Q4_K_M4.94.58 GiB72 t/sThe popular default: small but measurable loss
Q3_K_M4.03.74 GiB72 t/sNoticeable on hard tasks
Q2_K3.22.95 GiB80 t/sLarge loss; last resort

Sizes, bits and speeds from the llama.cpp quantize README (their test hardware). The quality column is a typical pattern, not a measurement: small models suffer more than large ones, and maths and code suffer before chat. Measure on your own eval (Lesson 5.1) with perplexity or KL divergence against the 16-bit model as a quick check. On GPU servers you'll meet other formats: AWQ and GPTQ (4-bit), FP8, and MXFP4, which OpenAI's gpt-oss models ship in natively.

✏️ Worked example: will a 32B model run on a 24 GB GPU?
  • Qwen3 32B has 32.8 B parameters. At Q4_K_M (4.9 bits): 32.8 × 4.9 ÷ 8 ≈ 20.0 GB of weights.
  • KV cache: 64 layers × 8 KV heads × 128 dims × 2 (keys and values) × 2 bytes = 256 KiB per token. An 8,000-token context: 8,000 × 256 KiB ≈ 2.1 GB.
  • Plus ~0.5–1 GB of runtime buffers: about 23 GB. It fits on a 24 GB card, just, with no room for a longer context or a second user.
  • Speed ceiling on a 300 GB/s card (NVIDIA L4): 300 ÷ 22 ≈ 14 tokens/s at best. Fine for one person; not for a team.

The lesson of the chart: self-hosting has a floor (at least two GPUs for redundancy, plus people) and then grows in steps, while an API grows smoothly from zero. Against a frontier-priced API, self-hosting an open model wins early, if the open model is good enough for the task. Utilization is the lever: a GPU at 20% load costs five times as much per token as one at 100%.

🧰 Tools you'll actually use

Ollama for local development, llama.cpp when you need control or edge devices, Hugging Face Transformers in notebooks, Transformers.js or WebLLM in the browser, and vLLM/SGLang on GPU servers (7.4). Commands as of late 2026:

# Ollama: pull + run a model, then call its local API
ollama run gemma4                         # chat in the terminal; server listens on localhost:11434

from ollama import chat                  # pip install ollama
r = chat(model="gemma4", messages=[{"role": "user", "content": "Why is the sky blue?"}])
print(r.message.content)

from openai import OpenAI                # or reuse your OpenAI-style code unchanged
client = OpenAI(base_url="http://localhost:11434/v1/", api_key="ollama")  # key required but ignored

# llama.cpp: download a GGUF from the Hub and serve an OpenAI-compatible API
llama serve -hf ggml-org/Qwen3.5-0.8B-GGUF      # older builds: llama-server -hf …
llama-quantize model-bf16.gguf model-Q4_K_M.gguf Q4_K_M   # make your own quant

# Transformers: any Hub model in a notebook
from transformers import pipeline
chatbot = pipeline("text-generation", model="Qwen/Qwen3-0.6B")
out = chatbot([{"role": "user", "content": "One sentence on KV caches."}], max_new_tokens=80)
print(out[0]["generated_text"][-1]["content"])
// Transformers.js in the browser (npm i @huggingface/transformers)
import { pipeline } from "@huggingface/transformers";
const gen = await pipeline("text-generation", "onnx-community/Qwen2.5-0.5B-Instruct",
                          { device: "webgpu", dtype: "q4" });   // downloads once, then runs on the user's GPU
const out = await gen([{ role: "user", content: "Hi!" }], { max_new_tokens: 64 });

Model tags change often (new families appear every few months). Browse ollama.com/library or the Hub, and pin an exact tag or file in production rather than “latest”.

🚀 Startup vs big tech

Startup

Prototype with Ollama on laptops, ship on an API, and keep your code OpenAI-compatible so a self-hosted model is a config change away. Self-host only for a hard privacy requirement or when the bill and steady traffic clearly justify a GPU on-call rota.

Big tech

An internal model catalogue with licence review, pinned and security-scanned weights, a shared GPU inference platform with quotas and chargeback, and on-device models (quantized, with adapters) shipped inside apps.

🎤 Interview angle

“Should we self-host an open model?” A senior answer:

  • Starts from the driver: privacy, cost at scale, control or latency, and whether an open model is good enough on our eval.
  • Does the memory maths: parameters × bits ÷ 8, plus KV cache per user, then picks GPUs and a quantization level.
  • Does the break-even maths with utilization, redundancy and engineering time, not just GPU list price.
  • Checks the licence (commercial use, user caps, naming, acceptable-use terms) and plans upgrades as new models ship.
🏭 In the real world
LLMs on ordinary hardware 🧰 Open source llama.cpp

How: plain C/C++ with no dependencies, hand-tuned kernels for Apple silicon, x86, CUDA, Vulkan and more, and 1.5- to 8-bit quantization.

Why this method: memory, not compute, limits local inference; its quantized formats take Llama 3.1 405B from 1,625 GB (32-bit) to 249 GB, and it can split a model across CPU and GPU when it doesn't fit in VRAM.

Open weights, shipped pre-quantized 🏢 OpenAI · 2025 Introducing gpt-oss

How: released gpt-oss-120b and gpt-oss-20b under Apache 2.0, with weights natively quantized in MXFP4.

Why this method: the 120b model runs within 80 GB of memory (one GPU) and the 20b model needs only 16 GB, so developers can run them locally or on their own infrastructure.

Quantized models on a phone 🏢 Apple · 2024 Apple Intelligence foundation models

How: a ~3B on-device model compressed with a mix of 2-bit and 4-bit weights, averaging 3.7 bits per weight, with LoRA adapters to recover quality.

Why this method: Apple reports the same accuracy as the uncompressed model, inside a phone's memory and power budget.

An LLM in a browser tab 🧰 Open source WebLLM (MLC)

How: compiles models to run on WebGPU inside the browser, with an OpenAI-compatible JavaScript API (streaming, JSON mode).

Why this method: no server and no data leaving the device; the cost is a large first download and a small model.

🤯 Fun fact · an evening hack with 130,000 stars

The llama.cpp repository was created on 10 March 2023, about two weeks after Meta announced the first LLaMA models. Its first README said the goal was to run the model with 4-bit quantization on a MacBook, and admitted: “This was hacked in an evening.” By late 2026 it had over 130,000 GitHub stars, and its GGUF format is what Ollama, LM Studio and many other local tools load.

Check yourself

1. Roughly how much memory do the weights of a 32B model take at Q4_K_M (about 4.9 bits per weight)?
32 × 10⁹ × 4.9 ÷ 8 ≈ 19.6 GB, so about 20 GB. 64 GB is the 16-bit size. Remember to add the KV cache for your context length.
2. A hospital wants to summarize patient notes. Policy says the notes may never leave its own data centre. Best first plan?
A hard data-residency rule is the clearest reason to self-host. Check the licence, measure quality on your own eval, and size the GPUs from memory maths. A tiny browser model is private but likely too weak for clinical summaries.
3. On your laptop, the 4-bit version of a model generates text about twice as fast as the 8-bit version. Why?
Single-user generation is memory-bandwidth-bound: speed ≈ bandwidth ÷ bytes read per token. Quantization shrinks the bytes. Same layers, same maths, just less to read.
📝 TL;DR
  • Weight memory = parameters × bits ÷ 8; single-user speed ≲ memory bandwidth ÷ model size.
  • Q8 is practically lossless, Q4_K_M is the usual sweet spot, below ~3 bits quality drops fast; a smaller model at 4–5 bits often beats a bigger one at 2.
  • Hub for models and model cards; Ollama/LM Studio locally; llama.cpp + GGUF for control and edge; Transformers.js/WebLLM in the browser; vLLM/SGLang for servers.
  • “Open” ≠ “anything goes”: read the licence. Self-host for privacy, control and steady high volume; otherwise an API is usually cheaper.
