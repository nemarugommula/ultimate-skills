Serving LLMs at scale: batching, KV cache, vLLM, quantization

One user on one GPU wastes almost all of it. Serving is the art of keeping hundreds of conversations in GPU memory at once without anyone waiting too long. The tricks are batching, the KV cache, and a few clever ideas borrowed from operating systems.

🧰 You'll need (quick reminders)
  • Generation is one token at a time, each new token depending on all the previous ones (Lesson 0.2).
  • Attention: each new token looks back at every earlier token's keys and values (Lesson 0.2; the maths is in Math for AI).
  • Memory maths: weights = parameters × bytes; single-user speed ≲ memory bandwidth ÷ model size (Lesson 7.3).
🎯 Hook

In spring 2023, LMSYS, a small research team with limited compute, was serving Chatbot Arena and the Vicuna demo to the public. A Berkeley team swapped in a new serving engine, vLLM, built around one idea: manage the model's attention memory the way an operating system manages RAM, in pages.

LMSYS cut the number of GPUs serving its traffic by 50% while handling an average of 30,000 requests a day (peaking at 60,000). In the team's benchmarks, vLLM delivered up to 24× the throughput of plain Hugging Face Transformers, with no change to the model.

Numbers first: one user uses 0.3% of an H100

Generating one token with an 8B model takes about 2 × 8B = 16 GFLOP (two operations per weight) and means reading all 16 GB of 16-bit weights.

Memory wins by a factor of 300: at one sequence the compute units sit idle 99.7% of the time, waiting for weights to arrive. But if 64 sequences take their next step together, the weights are read once and used 64 times: up to ~13,000 tokens/s in theory (less in practice, because each sequence's own cached attention data must be read too). Batching is nearly free throughput, and everything in this lesson is about batching more, safely.

💡 Big idea Decoding is memory-bound, so the way to go fast is to share each read of the weights across many requests. What limits how many you can share is the KV cache: per-request memory that grows with every token. Serving engines are, at heart, KV-cache memory managers.
🧠 Analogy: the bus and the lift

Static batching is a tour bus: it leaves when full and only returns when the last passenger is done, so people who finished early sit on the bus. Continuous batching is a lift: at every floor (every token step) people get off and new ones get on, so it's never waiting on one slow passenger. PagedAttention is how the lift saves space: instead of reserving a whole row of seats for each passenger's luggage “just in case”, luggage goes into small lockers allocated as it arrives.

Total latency ≈ TTFT + TPOT × output tokens. With a 300 ms TTFT and 20 ms per token, a 500-token answer takes 0.3 + 500 × 0.020 = 10.3 s, although streaming shows the first words after 0.3 s. Throughput is total tokens/s across all users; goodput is the number of requests per second that meet your latency targets. Pushing batch size up raises throughput and also each user's TPOT, so you choose a point on that curve.

The KV cache: what it is and why it's huge

To generate token 1,001, attention needs the keys and values of tokens 1–1,000 at every layer. Recomputing them each step would be absurdly slow, so they're stored: the KV cache. Its size per token is

KV bytes per token = 2 × layers × KV heads × head dim × bytes per number 2 because there's a key and a value. Modern models use grouped-query attention (GQA): many query heads share a few key/value heads, which shrinks the cache.
✏️ Worked example: how many conversations fit on one H100?
  • Llama 3.1 8B: 32 layers, 8 KV heads, head dim 128, 16-bit: 2 × 32 × 8 × 128 × 2 = 131,072 bytes = 128 KiB per token.
  • An 8,192-token conversation: 8,192 × 128 KiB = 1 GiB of KV cache.
  • H100 80 GB, of which serving engines use ~90%: 72 GB. Minus 16.1 GB of weights = ~56 GB for KV cache.
  • 56 GB ÷ 1.07 GB ≈ 52 concurrent 8k-token conversations. At 32k tokens each: 13. With an 8-bit (FP8) KV cache: 104.

Llama 2 7B, from before GQA, had 32 KV heads: 512 KiB per token, 4× more. Its 4k-token conversation needed 2.1 GB. Architecture choices like GQA are serving decisions.

Batching: static vs continuous

Static batching groups requests, runs them together, and returns when the longest one finishes. Requests that finish early leave their slot idle, and new arrivals wait for the whole batch. Continuous batching (iteration-level scheduling, from the Orca paper, OSDI 2022) re-forms the batch at every token step: finished sequences leave immediately and waiting ones join. Orca reported 36.9× the throughput of NVIDIA's FasterTransformer at the same latency on GPT-3 175B; Anyscale measured up to 23× in its 2023 benchmarks. Every modern engine does it.

PagedAttention, prefix caching and chunked prefill

  • PagedAttention (vLLM paper, 2023) stores each sequence's KV cache in small fixed-size blocks that need not sit next to each other in memory, exactly like virtual-memory pages. Memory is allocated as tokens arrive instead of reserved for the maximum length, so waste drops to near zero and batches get bigger: 2–4× the throughput of the previous state of the art at the same latency.
  • Prefix caching: blocks can be shared. If 1,000 requests start with the same 2,000-token system prompt, its KV cache is computed once and reused, cutting TTFT. SGLang's RadixAttention keeps a tree of cached prefixes, which shines for agents and few-shot prompts (up to 6.4× throughput in its paper).
  • Chunked prefill: a 50,000-token prompt would freeze everyone else's decoding while it's processed. Engines cut it into chunks and mix them into decode steps, so other users' TPOT stays smooth.
  • Disaggregated serving: run prefill and decode on different GPUs, sized and parallelized separately, so they stop interfering (DistServe, 2024; NVIDIA Dynamo).

Speculative decoding: guess, then check in one pass

A small, fast draft model proposes the next γ tokens; the big target model checks all of them in a single forward pass (as cheap as one decode step, since decoding is memory-bound), keeps the longest correct prefix and adds one token of its own. A clever acceptance rule makes the output distribution exactly the target model's: faster, with identical quality (Leviathan et al., Google, 2022).

expected tokens per target pass = (1 − αγ+1) / (1 − α) α = probability the target accepts a drafted token; γ = number of drafted tokens. Speed-up ≈ that number ÷ (1 + γ × draft cost relative to the target).

With α = 0.8 and γ = 5: (1 − 0.8⁶) ÷ 0.2 ≈ 3.7 tokens per pass; if each draft step costs 5% of a target step, speed-up ≈ 3.69 ÷ 1.25 ≈ 2.95×. The original paper showed 2–3× on T5-XXL. It helps most at small batch sizes (spare compute) and on predictable text like code; at very large batches the GPU is already busy. Drafts can be a small model, extra prediction heads (Medusa, EAGLE), or simply n-grams copied from the prompt.

When one GPU isn't enough: parallelism

KindSplitsGood forCost
Tensor parallel (TP)Each weight matrix across GPUs; they exchange partial results every layerModels too big for one GPU, inside one serverNeeds very fast links (NVLink); scales to ~8 GPUs
Pipeline parallel (PP)Groups of layers onto different GPUs or serversSpanning several serversBubbles (idle stages) unless many requests are in flight
Data parallel (replicas)Nothing: whole copies behind a load balancerMore traffic once a copy fitsMemory for every copy
Expert parallelThe experts of a mixture-of-experts model across GPUsLarge MoE modelsAll-to-all traffic between GPUs

Example: Llama 3.1 70B in 16-bit is 141 GB. With TP = 2 on 80 GB H100s, the weights fit but leave only ~3 GB for KV cache: one 8k conversation. TP = 4 leaves ~147 GB: about 54. Or quantize: FP8 weights (native on H100) halve the 141 GB with little quality loss, and an FP8 KV cache doubles the conversations that fit.

Autoscaling GPUs

  • Scale on the right signal: queue depth (requests waiting), KV-cache usage and p95 TTFT, not CPU. vLLM exports these as Prometheus metrics such as vllm:num_requests_waiting, vllm:kv_cache_usage_perc and vllm:time_to_first_token_seconds.
  • Cold starts are slow: a new replica must pull a container, load tens of GBs of weights and warm up, so minutes are normal. Keep a warm minimum, cache weights on local disk, and scale ahead of known peaks.
  • Mix capacity: reserved GPUs for the base load, on-demand or spot for peaks, and an API fallback for overflow (Lesson 8.1).
  • Protect latency: cap --max-num-seqs, rate-limit per tenant, and shed or queue load before TPOT targets break.
🧰 Tools you'll actually use

vLLM or SGLang on your own GPUs or Kubernetes, behind an OpenAI-compatible API so application code doesn't care; load-test with real prompt and output lengths before you trust any throughput number. Commands as of late 2026 (check vllm serve --help for your version):

# vLLM: OpenAI-compatible server on http://localhost:8000
vllm serve Qwen/Qwen2.5-1.5B-Instruct

# A 70B model across 4 GPUs, with the knobs that matter
vllm serve meta-llama/Llama-3.1-70B-Instruct \
  --tensor-parallel-size 4 \            # split every layer over 4 GPUs
  --max-model-len 16384 \             # caps KV cache per request
  --gpu-memory-utilization 0.90 \    # share of GPU memory vLLM may use
  --max-num-seqs 128 \               # max concurrent sequences per step
  --kv-cache-dtype fp8 \               # 2× more tokens of KV cache
  --enable-lora --lora-modules support=./support-lora   # serve a LoRA adapter as model "support"

# Speculative decoding with a small draft model
vllm serve <target-model> --speculative-config \
  '{"method": "draft_model", "model": "<draft-model>", "num_speculative_tokens": 5}'

# SGLang equivalent
sglang serve Qwen/Qwen3-0.6B --host 0.0.0.0 --port 30000
from openai import OpenAI
client = OpenAI(base_url="http://localhost:8000/v1", api_key="EMPTY")  # --api-key to require one
stream = client.chat.completions.create(model="support", stream=True,
                                        messages=[{"role": "user", "content": "Where is my order?"}])
for chunk in stream:                           # stream: users see the first token at TTFT
    print(chunk.choices[0].delta.content or "", end="")

vLLM's --gpu-memory-utilization defaults to about 0.9 (0.92 in current docs), and automatic prefix caching is controlled with --enable-prefix-caching / --disable-prefix-caching. Managed alternatives (dedicated endpoints at inference providers or your cloud) run these same engines for you.

🚀 Startup vs big tech

Startup

Don't run GPUs until you must. When you do: one vLLM deployment per model on a managed GPU platform, FP8 if the hardware supports it, prefix caching for your system prompt, autoscaling on queue depth with a warm minimum of two, and an API fallback.

Big tech

Fleets with disaggregated prefill and decode, KV-cache-aware routing (send a request to the replica that already holds its prefix), speculative decoding tuned per model, custom kernels, and capacity planning measured in tokens per second per dollar per watt.

🎤 Interview angle

“Design the serving layer for a chat product at 1,000 requests per second.” A senior answer:

  • Starts with SLOs (p95 TTFT, TPOT) and the traffic shape (prompt and output lengths), then does KV-cache maths to get concurrent sequences per GPU, and from there GPU count.
  • Explains prefill vs decode, continuous batching and PagedAttention in a sentence each, and why decoding is memory-bound.
  • Picks levers with trade-offs: quantization, prefix caching, speculative decoding, TP vs replicas, chunked prefill.

🏭 In the real world
Paging the KV cache 🏢 LMSYS / UC Berkeley · 2023 vLLM: Easy, Fast, and Cheap LLM Serving

How: PagedAttention plus continuous batching, deployed behind Chatbot Arena and the Vicuna demo.

Why this method: up to 24× the throughput of Hugging Face Transformers and up to 3.5× TGI in their tests; LMSYS halved the GPUs serving its traffic.

Iteration-level scheduling 🧪 Research · 2022 Orca (OSDI '22)

How: schedule the batch one decoding iteration at a time, so finished requests leave and new ones join immediately.

Why this method: 36.9× the throughput of NVIDIA FasterTransformer at the same latency on GPT-3 175B. Every modern engine copied it.

Consumer chat at search-engine scale 🏢 Character.AI · 2024 Optimizing AI Inference at Character.AI

How: model-architecture changes that shrink the attention KV cache, plus caching it between conversation turns.

Why this method: about 20,000 queries per second at under one cent per hour of conversation, and serving costs down at least 33× since 2022.

Speculative decoding in Search 🏢 Google · 2024 Looking back at speculative decoding

How: a draft model proposes tokens and the large model verifies them in parallel, keeping its exact output distribution.

Why this method: Google says it lets AI Overviews in Search produce results faster while keeping the same quality of responses.

🤯 Fun fact · the idea is from the 1960s

PagedAttention's trick, splitting memory into fixed-size pages so a process doesn't need one contiguous block, is the virtual memory found in every operating system since the 1960s. The vLLM paper's title says so plainly: Efficient Memory Management for Large Language Model Serving with PagedAttention. Old systems ideas keep winning in AI infrastructure.

Check yourself

1. A model has 40 layers, 8 KV heads and head dim 128, with a 16-bit KV cache. How much KV cache does one 16,384-token conversation need?
Per token: 2 × 40 × 8 × 128 × 2 = 163,840 bytes (160 KiB). × 16,384 tokens ≈ 2.68 GB, so about 2.7 GB. A 60 GB budget holds about 22 such conversations.
2. Users complain that answers start quickly but then crawl, and get worse at peak hours. GPU compute utilization looks low. Most likely cause and fix?
Good TTFT but slow TPOT points at decode. Decode speed is set by bytes read per step (weights + every sequence's KV cache), not FLOPS. Fewer sequences per replica, more replicas, or fewer bytes (FP8) all help.
3. A draft model's tokens are accepted with probability α = 0.6, and it drafts γ = 3 tokens. Ignoring the draft's own cost, about how many tokens does each target pass produce?
(1 − 0.6⁴) ÷ (1 − 0.6) = (1 − 0.1296) ÷ 0.4 ≈ 2.18. 4.0 would need every draft accepted (γ + 1). Better drafts (higher α) matter more than drafting more tokens.
📝 TL;DR
  • Prefill is compute-bound (sets TTFT); decode is memory-bound (sets TPOT). Batching shares each read of the weights across many requests.
  • KV cache per token = 2 × layers × KV heads × head dim × bytes; it decides how many requests fit. GQA, FP8 KV and shorter max contexts all multiply concurrency.
  • Continuous batching + PagedAttention (vLLM) are the baseline; add prefix caching, chunked prefill and speculative decoding where they fit.
  • TP for models too big for one GPU, replicas for traffic; autoscale on queue depth and KV usage, and plan for slow cold starts.
