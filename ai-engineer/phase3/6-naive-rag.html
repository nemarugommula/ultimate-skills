Build a RAG pipeline end to end

Everything from this phase in one working system: index, retrieve, rerank, prompt, answer, log, and a first eval that tells you which stage to fix next.

  • Retrieve many, rerank few with a cross-encoder (3.4).

🎯 Hook

A team at Deakin University built three RAG systems, for research, education and biomedical documents, and wrote down everything that went wrong. They found seven distinct failure points, from “the answer isn't in the documents” to “the answer was retrieved but the model didn't extract it”.

Their two headline lessons are the reason this lesson ends with an eval: validating a RAG system is only really possible while it runs on real questions, and its robustness evolves through iteration rather than being designed in at the start. So build the simple version, log everything, measure, and fix the worst stage first.

Numbers first: where the time and money go

Stage (per question)Typical latencyTypical cost
Embed the question20–50 ms≈ $0 (a few dozen tokens)
Vector search (+ filters)5–50 msDatabase cost, mostly fixed
Rerank 20–100 candidates50–300 msPer search (hosted) or GPU time
LLM: reading the prompt, to first token0.3–1 sInput tokens: usually the biggest line
LLM: writing ~250 tokens2–5 sOutput tokens: several times dearer per token

Typical orders of magnitude, not benchmarks: they depend on models, hardware, region and load.

Two things follow. Retrieval is cheap and fast; the LLM dominates both latency and cost. And because users see the answer as it streams, the number that feels like “speed” is time to first token (TTFT): everything before the model starts writing.

💡 Big idea A RAG pipeline is a chain, and the answer is only as good as its weakest stage. So build it so that every stage is visible: log what was retrieved, with scores, what prompt was sent, and what came back. Then an eval can tell you which stage failed for each question, instead of just “the answer was wrong”.
🧠 Analogy: a restaurant kitchen

Suppliers deliver (ingestion), prep cooks wash and cut (parsing and chunking), the pantry is organised and labelled (the index), and per order the cook grabs ingredients (retrieval), picks the best (reranking) and plates the dish (generation). When a dish comes back, a good head chef doesn't just say “cook better”: they check whether the fish was off, mislabelled, or overcooked. Tasting every station is your eval; the order tickets are your logs.

The pipeline, in code

A minimal, production-shaped version with an embedding API, a local vector store (Chroma), a hosted reranker and an LLM. About 60 lines, no framework. Swap any piece for its equivalent: pgvector or Qdrant for Chroma (Lesson 2.3), an open cross-encoder for Cohere, any chat model for Claude.

# ---------- index time: run whenever documents change ----------
import json, time, logging, chromadb, anthropic, cohere
from openai import OpenAI
from langchain_text_splitters import RecursiveCharacterTextSplitter

oai, claude, co = OpenAI(), anthropic.Anthropic(), cohere.ClientV2()
col = chromadb.PersistentClient(path="./index").get_or_create_collection("handbook")
splitter = RecursiveCharacterTextSplitter(chunk_size=1600, chunk_overlap=200)   # ≈400 tokens

def embed(texts):
    r = oai.embeddings.create(model="text-embedding-3-small", input=texts)
    return [d.embedding for d in r.data]

def index_document(doc):        # doc: id, markdown text (from 3.2), title, updated, audience
    chunks = splitter.split_text(doc["text"])
    col.upsert(ids=[f"{doc['id']}#{i}" for i in range(len(chunks))],
               documents=chunks, embeddings=embed(chunks),
               metadatas=[{"doc_id": doc["id"], "title": doc["title"],
                           "updated": doc["updated"], "audience": doc["audience"]}] * len(chunks))

# ---------- query time ----------
PROMPT_VERSION = "grounded-v1"
SYSTEM = ("Answer using ONLY the documents. Cite ids like [c1] after each sentence. "
          "If the documents don't contain the answer, say you don't know. "
          "If documents disagree, prefer the most recent and mention the conflict.")
log = logging.getLogger("rag")

def answer(question, audiences=("public",)):
    t, t0 = {}, time.perf_counter()
    res = col.query(query_embeddings=embed([question]), n_results=30,          # 1. retrieve many
                    where={"audience": {"$in": list(audiences)}})              #    permission filter
    docs, metas = res["documents"][0], res["metadatas"][0]
    t["retrieve_ms"] = (time.perf_counter() - t0) * 1000
    rr = co.rerank(model="rerank-v5.0-fast", query=question, documents=docs, top_n=5)  # 2. rerank few
    t["rerank_ms"] = (time.perf_counter() - t0) * 1000 - t["retrieve_ms"]
    top = [(f"c{n + 1}", docs[r.index], metas[r.index], r.relevance_score) for n, r in enumerate(rr.results)]
    if not top or top[0][3] < 0.2:                                            # 3. abstain early (tune 0.2)
        text, usage = "I couldn't find that in our documents.", None
    else:
        context = "\n".join(f'<document id="{cid}" title="{m["title"]}" updated="{m["updated"]}">\n{d}\n</document>'
                            for cid, d, m, _ in top)
        msg = claude.messages.create(model="claude-haiku-5-5", max_tokens=400, system=SYSTEM,  # 4. generate
            messages=[{"role": "user", "content": f"<documents>\n{context}\n</documents>\n\nQuestion: {question}"}])
        text, usage = msg.content[0].text, msg.usage
    t["total_ms"] = (time.perf_counter() - t0) * 1000
    trace = {"q": question, "prompt": PROMPT_VERSION, "retrieved": [m["doc_id"] for m in metas],  # 5. log it all
             "top": [(m["doc_id"], round(s, 3)) for _, _, m, s in top], "answer": text, **t,
             "in_tokens": usage and usage.input_tokens, "out_tokens": usage and usage.output_tokens}
    log.info(json.dumps(trace))
    return text, trace

Offline stand-ins throughout: the toy embedding (Lesson 2.1), the rule-based cross-encoder from 3.4, and a rule-based “model” that answers from the best-matching retrieved sentence, abstains when nothing matches and the prompt allows it, and invents a plausible answer when the prompt doesn't. A real pipeline uses real models; the failure patterns in the table are the real ones.

What you should see: the tutorial defaults (tiny fixed chunks, k = 2, no reranker, a bare prompt) pass only 5 of 12. The eval table says why: four are retrieval misses (two of them answered confidently with the wrong “30 days”), one answer is built from a chunk fragment that lost its “does not”, and both unanswerable questions get invented answers. The reranker rescues two questions; the grounded prompt fixes both unanswerables; sensible chunks fix the rest. That's the loop you'll run on every real system.

✏️ Worked example: reading a first eval of 20 questions

You wrote 20 real questions: 17 with a known answer and source document, 3 the documents can't answer. Results:

  • Retrieval hit rate: the source chunk was in the top k for 14 of 17 → 14 ÷ 17 ≈ 82%.
  • Answers correct: 12 of the 14 hits, 0 of the 3 misses, plus 2 of 3 unanswerables correctly abstained → (12 + 2) ÷ 20 = 70%.
  • By stage: 3 failures are retrieval (fix chunking, hybrid search, reranking), 2 are generation with the right chunk present (fix the prompt or the model), 1 is a missing abstain (abstain instruction or score threshold).

So the next change is retrieval, because it's the biggest bucket. Without the per-stage breakdown, you might have reached for a bigger model, which can fix at most 3 of the 6 failures.

Logging: what to record on every request

Log one structured record per question: the query; retrieved chunk IDs with first-stage and reranker scores; the prompt version and model; input and output tokens; latency per stage; the answer and its citations; and later, user feedback (thumbs, edits, escalations). These logs become your next eval set (real questions!), your cost dashboard, and the first thing you open when someone reports a bad answer. Tracing tools such as Langfuse, LangSmith, Arize Phoenix or OpenTelemetry-based setups record exactly this (Lesson 8.1). Mind privacy: questions can contain personal data, so set retention and redaction rules.

Your first eval

Before tuning anything, write 20 to 50 real questions (from support tickets, search logs, or the people who'll use it), each with the expected answer and the document it lives in, plus a few the documents can't answer. Score three things per question: retrieval hit (was the source in the top k?), answer correct (contains the expected fact, or correctly abstains), and later faithfulness (Lesson 3.5). Run it on every change. Lesson 5.4 turns this into a proper evaluation with LLM judges.

golden = [json.loads(line) for line in open("golden.jsonl")]
# {"q": "How long do Plus members have?", "expect": "60 days", "source": "handbook"}
# {"q": "Do you have a store in Paris?", "expect": null}
rows = []
for g in golden:
    text, trace = answer(g["q"])
    hit = g["expect"] is None or g["source"] in [d for d, _ in trace["top"]]
    ok = ("don't know" in text.lower() or "couldn't find" in text.lower()) if g["expect"] is None \
         else g["expect"].lower() in text.lower()
    rows.append({"q": g["q"], "hit": hit, "ok": ok,
                 "stage": "pass" if ok else ("retrieval" if not hit else "generation")})
print(sum(r["ok"] for r in rows), "/", len(rows))

Illustrative model: query embedding 30 ms; vector search 20 ms; reranking 20 ms + 2 ms per candidate and $2 per 1,000 searches; the LLM reads input at 10,000 tokens/s after a 300 ms start and writes 80 tokens/s; $3 per million input tokens, $15 per million output; embeddings $0.02 per million; 150 tokens of instructions and 20 of metadata per chunk.

What you should see: with the defaults, about 0.7 s to the first token and about 3.8 s for the full answer, of which the LLM writing takes over 3 s. Doubling the chunks barely changes time to first token but raises cost; halving the answer length saves both. Streaming is why users tolerate a 4-second answer: they start reading after 0.7.

🧰 Tools you'll actually use

The same pipeline in the two big frameworks. They save boilerplate (loaders, splitters, store integrations, retries) and make it easy to swap parts; the hand-written version above makes every step explicit. Many teams prototype in a framework and keep or replace it once they know what they need.

# LangChain (v1): components wired by hand
from langchain.chat_models import init_chat_model
from langchain_core.vectorstores import InMemoryVectorStore
from langchain_openai import OpenAIEmbeddings
from langchain_text_splitters import RecursiveCharacterTextSplitter

splits = RecursiveCharacterTextSplitter(chunk_size=1000, chunk_overlap=200).split_documents(docs)
store = InMemoryVectorStore(embedding=OpenAIEmbeddings(model="text-embedding-3-small"))
store.add_documents(documents=splits)
model = init_chat_model(model="anthropic:claude-haiku-5-5")

def rag(question):
    hits = store.similarity_search(question, k=4)
    context = "\n\n".join(f"[c{i + 1}] {d.page_content}" for i, d in enumerate(hits))
    return model.invoke(f"{SYSTEM}\n\n<documents>\n{context}\n</documents>\n\nQuestion: {question}").content

# LlamaIndex: an index and a query engine in four lines
from llama_index.core import Settings, SimpleDirectoryReader, VectorStoreIndex
from llama_index.embeddings.openai import OpenAIEmbedding
Settings.embed_model = OpenAIEmbedding(model="text-embedding-3-small")
# Settings.llm = ...   any LlamaIndex LLM integration (Anthropic, OpenAI, Ollama...)
index = VectorStoreIndex.from_documents(SimpleDirectoryReader("handbook/").load_data())
engine = index.as_query_engine(similarity_top_k=5)
resp = engine.query("How long do Plus members have to ask for a refund?")
print(resp, [n.node.metadata.get("file_name") for n in resp.source_nodes])

The 60-line pipeline above with a managed vector store, a hosted reranker and a small fast model, streaming on. 30 golden questions in a JSONL file and a script that prints the per-stage table. Ship to a few internal users and read every log line for a week.

🎤 Interview angle

“Design a question-answering assistant over our 20,000 support articles.” A senior answer walks the pipeline with numbers:

  • Index: parse to Markdown, chunk by heading at about 400 tokens, metadata (product, date, audience), dedup; incremental re-index on change.
  • Query: hybrid top 50 with permission filters → reranker to 5 → grounded prompt with IDs and dates → streamed, cited answer; abstain on low reranker score.
  • Budget: ~0.7 s to first token, ~1 cent per answer at illustrative prices; where the time goes and what they'd cut.
  • Quality: a golden set with per-stage metrics, logging of every request, feedback loop into the eval set; what they'd try next for each failure bucket.
🏭 In the real world
Seven ways RAG fails 🧪 Research · 2024 Barnett et al., Seven Failure Points When Engineering a RAG System

How: an experience report from three RAG systems in research, education and biomedicine, cataloguing where answers went wrong.

Why it matters: missing content, missed top-ranked documents, context consolidation, extraction, format, specificity and incompleteness each need a different fix, so log and evaluate per stage.

Stacking the stages 🏢 Anthropic · 2024 Introducing Contextual Retrieval

How: contextual chunks, embeddings plus BM25, retrieve the top 150, rerank to 20, measured with recall@20 across several domains.

Why this method: each stage removed a share of the remaining failures (35%, then 49%, then 67% fewer in total): measure, add one stage, measure again.

Evaluating the whole pipeline 🧪 Research · 2023 Es et al., RAGAS: Automated Evaluation of RAG

How: reference-free metrics for retrieval and generation (context relevance, faithfulness, answer relevance) computed with an LLM.

Why this method: lets you score every stage without hand-writing reference answers for every question; the basis of many eval tools (Lesson 5.4).

Frameworks' reference pipelines 🧰 Open source LlamaIndex starter example · LangChain RAG tutorial

How: load, split, embed into a vector store, retrieve and generate in a few lines, with integrations for most databases and models.

Why this method: the fastest way to a working baseline; read their defaults (chunk size, k) and set them deliberately.

🤯 Fun fact · the naive chunker that set a record

The original 2020 RAG paper split Wikipedia into disjoint 100-word chunks: no overlap, no headings, the simplest chunking in Lesson 3.3. It still set the state of the art on three open-domain QA benchmarks. A simple, well-measured pipeline beats a clever, unmeasured one.

Check yourself

1. Query embedding 30 ms, search 20 ms, rerank 150 ms, LLM time to first token 600 ms, then 300 tokens at 75 tokens/s. With streaming, when does the user start reading, and when is the answer complete?
First token: 30 + 20 + 150 + 600 = 800 ms. Writing: 300 ÷ 75 = 4 s, so complete at 0.8 + 4 = 4.8 s. Without streaming the user would stare at a spinner for all 4.8 s.
2. Your eval shows the source chunk in the top 5 for 95% of questions, yet only 60% of answers are correct. Where do you look first?
Retrieval is doing its job; the failures happen after it. Read those logs: is the answer in the chunk but missed, contradicted by another chunk, or badly formatted? That's the prompt (3.5), the context packing, or the generator.
3. A user reports a wrong answer from last Tuesday. What must your logs contain to diagnose it?
With retrieved IDs and scores you can tell a retrieval miss from a generation error; with the prompt version and model you can reproduce it. That record, kept per request, is what makes a RAG system debuggable.
📝 TL;DR
  • Index: parse → chunk → embed → store with metadata. Query: embed → retrieve many (filtered) → rerank few → grounded prompt → streamed, cited answer.
  • The LLM dominates latency and cost; time to first token is what users feel; stream.
  • Log every request with retrieved IDs, scores, prompt version, tokens and per-stage latency.
  • Write 20 to 50 real questions before tuning; score retrieval hits and answers separately, and fix the biggest failure bucket first.
