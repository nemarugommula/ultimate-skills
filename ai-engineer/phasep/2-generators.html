Iterators & generators: lazy pipelines and streaming

How to push a million documents through chunking and embedding without running out of memory, and why every token stream you'll ever read is just a Python iterator.

🧰 You'll need (quick reminders)
  • for x in obj calls special methods on obj (Lesson P.1's data model).
  • Chunking cuts documents into pieces; an embedding is a list of numbers (often 1,000 to 3,000 of them) describing a chunk's meaning, returned by an embeddings API (Lessons 3.3 and 2.1).
  • Streaming: an LLM API can send its answer token by token as it's generated, instead of all at once (Lesson 0.5).
🎯 Hook

The English split of Hugging Face's FineWeb dataset is 45 terabytes. Hugging Face's docs say you can “use it instantly” anyway: pass streaming=True to load_dataset() and you get an IterableDataset that downloads and yields one example at a time as you loop over it.

No laptop holds 45 TB. The trick isn't a bigger machine; it's a Python protocol: iteration. Process one item, let it go, ask for the next. That's this lesson.

Numbers first: a million chunks

You're indexing 1,000,000 chunks of about 1,000 characters each, with 1,536-dimension embeddings (a common size). Sizes measured on CPython 3.13:

Held in memory at onceSize
All 1M chunk texts as Python strings (1,041 bytes each)≈ 1.0 GB
All 1M embeddings as Python lists of floats (≈ 49.6 KB each)≈ 50 GB
All 1M embeddings as a float32 array (6 KB each)≈ 6.1 GB
One batch of 64 chunks + their embeddings as lists≈ 3.2 MB

Plain sentence: a pipeline that only ever holds one batch uses megabytes, whatever the size of the corpus. A pipeline that builds a list at every step needs the whole corpus in RAM, several times over, and its first vector isn't stored until everything has been processed.

💡 Big idea An iterator hands out one item per request. A generator is the easy way to write one: a function with yield that pauses after each item and resumes, locals intact, when the next one is requested. Chain generators and you get a lazy pipeline: work happens only when the last stage asks for an item, so memory is bounded by what's in flight (one batch), and results start flowing immediately. Token streams from LLM APIs are the same shape: an iterator of small pieces you consume as they arrive.
🧠 Analogy: the sushi conveyor

A banquet kitchen cooks every dish, plates every dish, then serves every dish: the kitchen needs a table for all of it, and the first guest eats last. A sushi conveyor makes one plate, puts it on the belt, and makes the next only when there's room. The kitchen never holds more than a few plates, and the first guest eats in a minute. List comprehensions at every stage are the banquet; generators are the belt. Batching is putting four plates on one tray because the walk to the table (an API call) is the slow part.

The iterator protocol in one screen

An iterable is anything you can loop over (a list, a file, a dict, a generator): it has __iter__, which returns an iterator. An iterator has __next__, which returns the next item or raises StopIteration when it's done. A for loop is just:

it = iter(chunks)                # calls chunks.__iter__()
while True:
    try:
        chunk = next(it)         # calls it.__next__()
    except StopIteration:
        break
    process(chunk)
  • Iterators are one-shot. A list can be looped over again; a generator or a file handle can't. gen = (c for c in docs); list(gen); list(gen) gives [...] then []. The classic bug: you count the items with sum(1 for _ in gen), then the “real” loop sees nothing.
  • Generator functions: a def with yield. Calling it runs none of the body; it returns a generator object. Each next() runs to the next yield, hands out the value, and freezes.
  • Generator expressions: (x.text for x in chunks), with round brackets. A list comprehension of a million squares is ≈ 8.4 MB; the equivalent generator expression is ≈ 200 bytes, whatever the length.
  • yield from sub() hands out every item of another iterator: the clean way for a per-document generator to emit all of its chunks.

What you should see: with lists, every stage holds every item before the next stage starts, the memory meter goes red, and the first vector is stored only at the very end. With generators, one document travels the whole pipeline, waits at the embed step until a batch of 3 is full, and is stored while later documents haven't been read yet. Total work is the same; peak memory and time to first result are not.

Pipelines of generators

Each stage takes an iterator and returns an iterator, so stages compose like Unix pipes: store(embed(chunk(clean(read(paths))))). Nothing runs until the outermost loop pulls. Useful tools from itertools, all lazy:

✏️ Worked example: sizing embedding batches against real limits

OpenAI's embeddings endpoint (per its Python SDK documentation, 2026) accepts at most 2,048 inputs per request, at most 8,192 tokens per input, and at most 300,000 tokens summed across a request. Your chunks average 250 tokens.

  • 2,048 × 250 = 512,000 tokens: over the 300,000 cap, so a batch of 2,048 is rejected.
  • Largest safe batch: 300,000 ÷ 250 = 1,200 chunks. Leave headroom for longer chunks: use ~1,000, or batch by token count rather than item count.
  • 1,000,000 chunks ÷ 1,000 per batch = 1,000 requests, versus 15,625 requests at 64 per batch and a million at 1. Fewer requests means far less per-request overhead and fewer rate-limit hits.
  • Memory per in-flight batch of 1,000 (text + vectors as float32): ≈ 1,000 × (1 KB + 6 KB) ≈ 7 MB.

Limits differ by provider and change; read the current API reference. For big offline jobs, providers also offer batch APIs at a discount (Lesson 4.8).

Streaming tokens: the same idea, from the network

When you stream a model's answer, the SDK gives you an iterator of events or text pieces as they arrive over the connection (server-sent events). Python lets you treat it like any other iterator: wrap it in your own generators to accumulate the full text, filter events, or re-chunk tokens into sentences for text-to-speech. Two rules:

  • Use the SDK's context manager (with client.messages.stream(...) as stream:) so the HTTP connection is closed even if you break early or an exception is raised.
  • Keep the full text as you go if you need it afterwards (logging, evals); the iterator won't replay. The SDK helpers also give you the final assembled message.
# Shape from the Anthropic SDK docs; needs an API key. MODEL is whatever model you use.
with client.messages.stream(model=MODEL, max_tokens=1024,
                            messages=[{"role": "user", "content": question}]) as stream:
    for sentence in sentences(stream.text_stream):   # your generator over theirs
        speak(sentence)                               # start talking before the answer is done
    final = stream.get_final_message()               # full message + token usage

🧰 Tools you'll actually use

Standard library: itertools (islice, batched, chain, groupby, pairwise), collections.abc.Iterator for type hints. Libraries: Hugging Face datasets with streaming=True, the OpenAI and Anthropic SDK stream iterators, and FastAPI's StreamingResponse, which accepts a normal or async generator as the response body (Lesson P.6). This runs on Python 3.12+ (for batched; checked on 3.13):

import re
from itertools import batched, islice        # batched: Python 3.12+
from collections.abc import Iterator, Iterable

def read_docs(paths: Iterable[str]) -> Iterator[dict]:
    for p in paths:                              # real code: open(p) and yield one record at a time
        yield {"id": p, "text": f"  Refunds take 5 days.   Plus members get 60 days. ({p})  "}

def clean(docs: Iterator[dict]) -> Iterator[dict]:
    for d in docs:
        yield {**d, "text": " ".join(d["text"].split())}

def chunk(docs: Iterator[dict], size: int = 40) -> Iterator[dict]:
    for d in docs:
        t = d["text"]
        for i in range(0, len(t), size):
            yield {"doc_id": d["id"], "text": t[i:i + size]}

def embed_batch(texts: list[str]) -> list[list[float]]:   # stand-in for one embeddings API call
    return [[len(t) / 100.0] for t in texts]

def embed_all(chunks: Iterator[dict], batch_size: int = 64) -> Iterator[tuple[dict, list[float]]]:
    for batch in batched(chunks, batch_size):              # tuples of up to 64, built lazily
        vectors = embed_batch([c["text"] for c in batch])
        yield from zip(batch, vectors)                     # hand results on one by one

paths = (f"doc{i}.md" for i in range(1_000_000))           # a million docs, nothing read yet
pipeline = embed_all(chunk(clean(read_docs(paths))))       # still nothing has run
for c, v in islice(pipeline, 3):                           # runs only enough work for the first batch
    print(c["doc_id"], repr(c["text"]), v)

def sentences(tokens: Iterable[str]) -> Iterator[str]:     # re-chunk a token stream (e.g. for text-to-speech)
    buf = ""
    for tok in tokens:
        buf += tok
        while (m := re.search(r"[.!?]\s", buf)):
            yield buf[:m.end()].strip()
            buf = buf[m.end():]
    if buf.strip():
        yield buf.strip()

print(list(sentences(["Hel", "lo there", ". How ", "are you", "? Fine", "."])))
# ['Hello there.', 'How are you?', 'Fine.']

🚀 Startup vs big tech

Week one

One script: a generator pipeline from files to vectors, batched at a few hundred chunks, upserts per batch, and a checkpoint (last processed ID) written every batch so a crash resumes instead of restarting. Stream every user-facing answer.

At scale

The same stages become distributed jobs: a queue or workflow engine feeds workers, each running a lazy pipeline over its shard; provider batch APIs for offline re-embeds; backpressure so a slow vector DB doesn't fill memory upstream (Lessons 4.8 and P.4). Streaming goes through a gateway that meters tokens as they flow (8.1).

🎤 Interview angle
  • “How would you embed 50 million documents on one machine?” Lazy generator pipeline, batches sized to the provider's caps (count and tokens), bounded concurrency (P.3), idempotent upserts keyed by chunk ID, checkpoints, retries per batch.
  • “What's the difference between an iterable and an iterator?” Iterable has __iter__ and can be looped many times; an iterator has __next__, holds position, and is exhausted once.
  • “What does this print?” g = (x for x in range(3)); print(sum(g), sum(g)) → 3 0.
  • “How do you stream an LLM answer to the browser?” A generator (or async generator) over the SDK stream, returned via a streaming HTTP response with server-sent events.
🏭 In the real world
Streaming a 45 TB dataset 🧰 Open source Hugging Face Datasets: Stream

How: load_dataset(..., streaming=True) returns an IterableDataset; you next(iter(ds)) or loop, and data is fetched as you go. to_iterable_dataset() streams from local files.

Why this method: you can explore or train on datasets far bigger than your disk without downloading them first.

Batch caps on embeddings 🏢 OpenAI · 2026 openai-python: embeddings.create

How: one request takes a list of up to 2,048 inputs, each under 8,192 tokens, with at most 300,000 tokens across the request.

Why this method: batching amortizes per-request overhead; the caps keep any one request bounded. Your batcher must respect both the count and the token total.

Streams as iterators 🧰 Open source Anthropic Python SDK

How: client.messages.stream(...) is a context manager whose text_stream is an iterator (an async iterator on the async client) of text pieces, plus get_final_message() for the assembled reply.

Why this method: the most familiar interface in Python (a for loop) for incremental output, with cleanup guaranteed by with.

Generators get their keyword 📜 History PEP 255: Simple Generators

How: written in May 2001 by Neil Schemenauer, Tim Peters and Magnus Lie Hetland, and shipped in Python 2.2, it added yield.

Why this method: producers that are naturally written as loops (tokenizers, parsers, tree walks) no longer had to be turned inside-out into callback or state-machine classes.

🤯 Fun fact · a sequence of a quintillion numbers, in 48 bytes

In Python 3, range is lazy: sys.getsizeof(range(10**18)) is 48 bytes, the same as range(10). It stores only start, stop and step, and computes each number when asked. Generators take the same idea from numbers to anything you can compute.

Check yourself

1. Chunks average 400 tokens. An embeddings API allows 2,048 inputs and 300,000 tokens per request. What's the largest batch you can send safely, on average?
The token cap binds first: 300,000 ÷ 400 = 750 chunks. 2,048 × 400 = 819,200 tokens would be rejected. In practice batch by running token count with some headroom, since chunk lengths vary.
2. Your indexing script logs “processed 0 chunks” but no error, right after you added a progress count: total = sum(1 for _ in chunks), followed by for c in chunks: .... chunks comes from a generator. Why?
An iterator can be traversed once. Either count as you go inside the main loop, or (if you really need the total first and it fits) materialize a list. itertools.tee exists but buffers everything not yet consumed by both copies.
3. A nightly job reads 3 million chunks into a list, embeds them all, then upserts them all. It sometimes dies of out-of-memory, and when it does, nothing is saved. What's the best fix?
Memory becomes bounded by one batch instead of the corpus, the first vectors are saved within seconds, and a crash resumes from the checkpoint. More RAM just moves the cliff; a smaller model shrinks vectors but keeps the all-or-nothing design.
📝 TL;DR
  • Iterable → __iter__ → iterator → __next__ until StopIteration. Iterators are one-shot.
  • Generators (yield, (x for …)) pause between items: chain them into lazy pipelines whose memory is one batch, not the corpus.
  • itertools.batched (3.12+) sizes API calls; respect both the item and the token caps.
  • LLM token streams are iterators: wrap them in generators, use the SDK's with, keep the text if you need it later.
