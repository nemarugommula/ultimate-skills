Phase P · Lesson 4

Concurrency & parallelism: the GIL, threads, processes

When Python can do several things at once, when it only looks like it can, and how to pick between asyncio, threads and processes for LLM calls, tokenizing, parsing and embedding.

🧰 You'll need (quick reminders)
  • asyncio overlaps waiting on one thread; it can't speed up computation (Lesson P.3).
  • I/O-bound work waits on the network or disk (LLM calls, vector DB queries). CPU-bound work keeps a processor busy (parsing PDFs, cleaning text, counting tokens in pure Python) (Lesson P.3).
  • A process is a running program with its own memory. A thread is a line of execution inside a process; threads share the process's memory. A CPU core runs one thread at a time.
🎯 Hook

PEP 703, the proposal to make CPython's Global Interpreter Lock optional, was written by Sam Gross and accepted in October 2023. Its motivation is about AI: section titles include “GPU-Heavy Workloads Require Multi-Core Processing” and “The GIL Makes Deploying Python AI Models Difficult”.

Since then, as of late 2026: Python 3.13 shipped an experimental free-threaded build, 3.14 made it officially supported (PEP 779), and 3.15 (October 2026) added a stable ABI so extensions can target it. It is still a separate, optional build; the default python still has a GIL, and whether free-threading ever becomes the default is undecided. So you need to understand both worlds.

Numbers first: same code, three ways

Plain sentence: threads made the waiting parallel but not the computing. Processes made the computing parallel, though not 8×, because starting workers and passing data between them costs time. The reason is the GIL.

💡 Big idea Concurrency is dealing with many things at once (interleaving them); parallelism is doing many things at the same instant (on several cores). In standard CPython, the GIL lets only one thread run Python bytecode at a time per interpreter. It's released while a thread waits on I/O and by many C/Rust extensions (NumPy, PyTorch kernels, fast tokenizers) during heavy work. So: asyncio for many I/O waits, threads for I/O with sync libraries or for GIL-releasing native code, processes for pure-Python CPU work. The free-threaded build changes only the CPU-bound row of that table.
🧠 Analogy: one kitchen, one knife

A kitchen (a process) has several cooks (threads) but only one knife (the GIL). Any cook chopping (running Python code) needs the knife, so adding cooks doesn't chop faster. But cooks waiting on an oven (I/O) don't need the knife, so many cooks can each have something in the oven at once. A cook using the food processor (a C extension that releases the GIL) puts the knife down too. Want more chopping? Open more kitchens (processes), each with its own knife, and accept the cost of carrying ingredients between them (pickling). The free-threaded build hands every cook a knife, and now cooks can collide over the same cutting board (race conditions).

The GIL: what it is and what it protects

  • What: a lock inside CPython. The glossary says it assures “that only one thread executes Python bytecode at a time.”
  • Why: it makes the interpreter's internals, like reference counts (Lesson P.5) and built-in types such as dict, implicitly safe against concurrent access, which keeps CPython simple and single-threaded code fast.
  • Switching: a thread holding the GIL is asked to give it up every 5 ms (sys.getswitchinterval() returns 0.005), so CPU-bound threads take turns instead of running together.
  • Released: during blocking I/O (sockets, files, time.sleep), and by extensions that do long work in C, C++ or Rust and choose to release it.
  • Not a safety guarantee for your code. The GIL protects the interpreter, not your logic: a read-modify-write across two statements can still interleave (see the race playground below).

Two other runtime changes you may hear about: an experimental JIT compiler (in 3.15's docs, a 7–8% geometric-mean speedup on x86-64 Linux; the 3.14 docs say it's not recommended for production), and multiple interpreters in one process, each with its own GIL (concurrent.interpreters and InterpreterPoolExecutor, new in 3.14 via PEP 734).

Threads, processes, asyncio: how each one works

asyncioThreads (ThreadPoolExecutor)Processes (ProcessPoolExecutor)
Runs on1 thread, many coroutinesMany threads, one process, one GILMany processes, each with its own interpreter and GIL
Parallel CPU?NoOnly for code that releases the GIL (or on the free-threaded build)Yes
Cost per workerTiny (a coroutine)An OS thread (default pool: min(32, cpus + 4))A whole interpreter: startup time, memory, imports
Sharing dataEverything shared; switches only at awaitEverything shared; switches can happen almost anywhereNothing shared: arguments and results are pickled (serialized) and copied
Best forHundreds of LLM / HTTP calls with async clientsI/O with sync-only libraries; NumPy/Rust work that releases the GILPure-Python CPU work: parsing, cleaning, custom tokenizing

Process gotchas. Workers start by importing your module, so the pool code must sit under if __name__ == "__main__":. Python picks a start method: spawn (a fresh interpreter; the default on macOS and Windows) or forkserver (the default on Linux since 3.14); fork is no longer the default anywhere because forking a process that has threads is unsafe. Lambdas and open connections can't be pickled, and pickling big objects (a 2 GB DataFrame, a model) per task can cost more than the work: pass file paths or IDs, load heavy things once per worker with initializer=, and use chunksize for many small tasks.

What you should see: for I/O, every concurrent option wins big, and asyncio with 40 tasks in flight wins most: all 40 waits overlap on one thread. For pure-Python CPU work, threads are no faster than sequential (red: waiting for the GIL) until you switch to the free-threaded build; processes win on the standard build. For GIL-releasing native work, plain threads already use all 8 cores. asyncio never helps CPU work: it runs it on one thread and blocks the loop while it does.

✏️ Worked example: planning a CPU-heavy ingest

50,000 PDFs need text extraction and cleaning in a pure-Python library, ~0.4 s of CPU each, before embedding.

  • One core: 50,000 × 0.4 s = 20,000 s ≈ 5.6 hours.
  • 8 threads on the standard build: still ≈ 5.6 hours (one GIL), plus switching overhead.
  • 8 processes: 20,000 ÷ 8 = 2,500 s ≈ 42 minutes ideally; budget ~10–20% extra for startup, pickling and uneven files, so ~50 minutes.
  • Pass paths to workers, not file bytes: pickling a 200-character path is free, pickling a 5 MB PDF 50,000 times is 250 GB of copying.
  • Then embedding is I/O-bound again: feed the extracted text into an async pipeline with a semaphore (Lesson P.3), not into the process pool.

Queues: producer/consumer between stages

Real pipelines mix both kinds of work: download (I/O) → parse (CPU) → embed (I/O) → upsert (I/O). Connect stages with queues: producers put work, consumers get it. Give every queue a maxsize: when consumers fall behind, put blocks, and the slow stage automatically slows the fast one down instead of letting memory fill up. That's backpressure. Use queue.Queue between threads, asyncio.Queue between coroutines, and multiprocessing.Queue (or the executor itself) between processes. A sentinel value like None tells consumers to stop.

Race conditions and locks

A race condition is a bug where the result depends on the timing of threads or tasks. The classic is a read-modify-write: read a shared value, compute, write it back. If another thread writes in between, its update is lost. Two measurements from this lesson's test scripts, on CPython 3.13 with the GIL:

  • 50 threads each doing current = tokens_used; log(...); tokens_used = current + 100, where the log call waits ~1 ms: the total came out 100 instead of 5,000. The GIL was released during the wait, so every thread read the same starting value.
  • The asyncio version (current = budget; await asyncio.sleep(0); budget = current - 10, 50 tasks): 990 instead of 500. In async code, every await is a place another task can run.

Even a bare counter += 1 is three steps in bytecode (load, add, store). In our test it lost about 60% of increments on Python 3.9 and none on 3.13, because of where the interpreter happens to check for thread switches; that's an implementation detail, not a promise, and on the free-threaded build threads really do run simultaneously. The fix is the same everywhere: guard the whole read-modify-write with a lock (with lock: / async with lock:), or avoid shared mutable state (each worker returns its result; one place aggregates).

🧰 Tools you'll actually use

Standard library: concurrent.futures (ThreadPoolExecutor, ProcessPoolExecutor, as_completed; InterpreterPoolExecutor in 3.14+), threading.Lock, queue.Queue, multiprocessing, asyncio.to_thread. In the AI stack: PyTorch's DataLoader(num_workers=…) uses worker processes; Hugging Face datasets.map(num_proc=…) does too; Ray and Dask scale the same ideas across machines. Runnable on Python 3.9+ (checked on 3.13):

import os, queue, threading, time
from concurrent.futures import ThreadPoolExecutor, ProcessPoolExecutor, as_completed

def call_llm_sync(prompt: str) -> str:          # stand-in for a sync SDK call (waits on the network)
    time.sleep(0.5)
    return f"answer to {prompt}"

def clean_and_count(text: str) -> int:          # CPU-bound, pure Python: holds the GIL
    return sum(1 for w in text.lower().split() if w.isalpha())

if __name__ == "__main__":                       # required: process workers re-import this module
    # 1) I/O-bound + a sync-only library → threads (the GIL is released while waiting)
    prompts = [f"q{i}" for i in range(20)]
    with ThreadPoolExecutor(max_workers=10) as pool:
        futures = {pool.submit(call_llm_sync, p): p for p in prompts}
        answers = {futures[f]: f.result() for f in as_completed(futures)}   # ~1 s, not 10 s

    # 2) CPU-bound pure Python → processes (each has its own interpreter and GIL)
    docs = ["Refunds are available within 30 days " * 20_000] * 16
    with ProcessPoolExecutor(max_workers=os.cpu_count()) as pool:
        counts = list(pool.map(clean_and_count, docs, chunksize=2))      # args and results are pickled

    # 3) Producer/consumer with a bounded queue (backpressure) and a lock for shared state
    q: queue.Queue = queue.Queue(maxsize=100)   # producers block when consumers fall behind
    tokens_used, lock = 0, threading.Lock()
    def producer():
        for i in range(500):
            q.put(f"chunk-{i}")
        q.put(None)                              # sentinel: no more work
    def consumer():
        global tokens_used
        while (item := q.get()) is not None:
            with lock:                           # read-modify-write must not interleave
                tokens_used += len(item)
        q.put(None)                              # let the other consumers stop too
    threads = [threading.Thread(target=producer)] + [threading.Thread(target=consumer) for _ in range(4)]
    for th in threads: th.start()
    for th in threads: th.join()
    print("tokens_used", tokens_used)              # 4390, every time

Inside async code, reach for await asyncio.to_thread(fn, ...) for a blocking call and loop.run_in_executor(process_pool, fn, ...) for CPU work, so the event loop keeps serving other requests.

🚀 Startup vs big tech

Week one

asyncio for every model and API call; to_thread for the odd sync library; a ProcessPoolExecutor for the one CPU-heavy step (PDF parsing) with paths in and text out; scale the web tier with several server worker processes. Don't share mutable state between workers: return results.

At scale

Each kind of work gets its own fleet: async API servers, CPU worker pools behind a queue for parsing, GPU servers that batch requests for models (Lesson 7.4). Pipelines run on Ray, Dask or a workflow engine. Teams benchmark the free-threaded build for thread-heavy services once their native dependencies support it, rather than assuming a speed-up.

🎤 Interview angle
  • “What is the GIL, and when does it matter?” One thread runs Python bytecode at a time per interpreter; it matters for pure-Python CPU work, not for I/O or GIL-releasing native code. Mention the free-threaded build (3.13 experimental, 3.14 supported, optional) and its trade-offs.
  • “Threads, processes or asyncio for: 10,000 LLM calls? Parsing 1M HTML pages? Running NumPy similarity on batches?” asyncio (or threads with a sync client); processes; threads (NumPy releases the GIL), or just vectorize.
  • “Why is my ProcessPoolExecutor slower than a for loop?” Tasks too small relative to process startup and pickling; send big objects per task; use chunksize, batch the work, or load data in the worker.
  • “Does the GIL make my code thread-safe?” No. It protects the interpreter's internals; your multi-step updates still need locks.
🏭 In the real world
Making the GIL optional, for AI 🧪 PEP · 2023 PEP 703: Making the GIL Optional in CPython

How: a --disable-gil build with biased and deferred reference counting, per-object locking and other changes so the interpreter is safe without a global lock.

Why this method: the PEP's motivation cites AI/ML: model serving and data loading want threads that share memory and run in parallel, which multiprocessing makes awkward.

Worker processes for data loading 🧰 Open source PyTorch: torch.utils.data

How: DataLoader loads in a single process by default; set num_workers to a positive integer for multi-process loading.

Why this method: the docs say it directly: within a process, the GIL prevents fully parallelizing Python code across threads, so loading in worker processes keeps the GPU fed.

Rust under the hood 🧰 Open source Hugging Face Tokenizers

How: the tokenizers used by Transformers are implemented in Rust; the docs claim under 20 seconds to tokenize a gigabyte of text on a server CPU.

Why this method: moving the hot loop out of Python sidesteps the GIL and interpreter overhead, the same reason NumPy and PyTorch do their heavy lifting in native code.

The current state, documented 🧰 Open source Python support for free threading

How: install the free-threaded build, check sys._is_gil_enabled(), force the GIL with PYTHON_GIL=1 or -X gil, and track package support on community sites.

Why this method: compatibility is gradual; any extension not marked free-threading-safe turns the GIL back on, so you measure before you rely on it.

🤯 Fun fact · 5 milliseconds

Run import sys; sys.getswitchinterval() and you'll get 0.005. That's the “timeslice” CPython aims to give a thread before asking it to hand over the GIL: 200 handovers a second, which is why CPU-bound threads look concurrent but never finish sooner. You can change it with sys.setswitchinterval(), which changes how often threads take turns, not how much work gets done.

Check yourself

1. 40 pure-Python cleaning tasks of 0.2 s CPU each, on 8 cores with the standard (GIL) build. Roughly how long with 8 threads, and with 8 processes?
Total CPU is 40 × 0.2 = 8 s. Threads share one GIL, so they take turns: ~8 s. Processes each have their own GIL: 8 s ÷ 8 ≈ 1 s, plus a bit for startup and pickling. On the free-threaded build, threads would get close to ~1 s too.
2. A vendor's Python SDK for a reranking API is sync-only. You need 2,000 calls of ~0.8 s each inside a batch script. What's the simplest good approach?
It's I/O-bound, and the GIL is released while each thread waits on the network, so threads overlap the waits with no rewrite. Processes waste memory and startup for no CPU gain. Calling a sync SDK inside async def blocks the loop (Lesson P.3) unless you wrap each call in asyncio.to_thread.
3. You moved a step to ProcessPoolExecutor and it got slower. Each task receives a 300 MB pandas DataFrame and does 5 ms of work. What's the best fix?
Each task pickles and copies 300 MB to do 5 ms of work, so serialization dominates. Send small descriptions of work and keep heavy data resident in each worker. (Or check whether a vectorized NumPy/pandas call removes the need for parallelism at all, Lesson P.7.)
📝 TL;DR
  • Concurrency interleaves; parallelism runs at the same instant. The GIL allows one thread of Python bytecode at a time per interpreter, released during I/O and by many native extensions.
  • I/O-bound → asyncio (or threads for sync libraries). Pure-Python CPU → processes (mind pickling, use __main__, chunksize, initializer). Native GIL-releasing code → threads are fine.
  • Free-threaded CPython: officially supported since 3.14, still optional as of 3.15; measure before relying on it.
  • The GIL doesn't make your code thread-safe: lock read-modify-writes, use bounded queues for backpressure, prefer returning results over sharing state.
