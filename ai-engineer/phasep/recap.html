Recap: Python for AI engineers

Seven lessons on one page: the rules and numbers worth memorizing, a “which tool?” game, a pipeline to build yourself, and a boss quiz.

Cheat sheet

🐍

P.1 Pythonic Python

syntax → dunder methods · names are tags, not boxes

Everything is an object; len, for, with call special methods. Mutable defaults, shallow copies and late-binding closures are the bugs that ship. Decorators wrap calls (retry, time, cache) with functools.wraps. Dataclasses inside, Pydantic at boundaries, a type checker in CI.

functools, dataclasses, typing, Pydantic, mypy / Pyright / ty

🔁

P.2 Iterators & generators

memory = one batch in flight, not the corpus

__iter__ → iterator → __next__ until StopIteration; iterators are one-shot. Generators (yield) pause between items, so chained stages make lazy pipelines. itertools.batched (3.12+) sizes API calls. LLM token streams are iterators too.

itertools, collections.abc, HF datasets streaming, SDK stream helpers

⏳

P.3 async/await

in flight ≈ rate × latency (Little's law)

One thread overlaps many I/O waits. gather for batches, TaskGroup (3.11+) for all-or-nothing, a Semaphore to respect rate limits, asyncio.timeout on every call. Never block the loop: async clients, to_thread for sync code.

asyncio, AsyncAnthropic / AsyncOpenAI, httpx, aiohttp

🧵

P.4 Concurrency & the GIL

I/O → asyncio/threads · pure-Python CPU → processes

The GIL lets one thread run Python bytecode at a time per interpreter; it's released during I/O and by many native libraries (NumPy, tokenizers), so threads work there. Processes for pure-Python CPU work. The GIL doesn't make code thread-safe: lock read-modify-writes, use bounded queues. Free-threaded builds exist (3.14+): measure.

concurrent.futures, threading, queue, multiprocessing

🧠

P.5 Memory & GC

refcount 0 → freed now · GC only for cycles

A float in a list costs ~32 bytes, in a float32 array 4. Leaks are forgotten references: unbounded caches, global lists, stored exceptions, task sets. Weak back-pointers break cycles; gc.freeze() before fork keeps pages shared. Find leaks with tracemalloc diffs and memray.

gc, weakref, tracemalloc, memray, np.load(mmap_mode="r")

🚀

P.6 Production Python

worst case = attempts × timeout + backoff

uv + lockfile; Pydantic models at the boundary (422 before you spend); SSE streaming with EventSourceResponse; explicit timeouts (SDK default is 10 min, 2 retries); settings from env with SecretStr; JSON logs; queues for heavy jobs; mocked-LLM unit tests, contract tests, golden evals.

uv, FastAPI, Pydantic, pydantic-settings, pytest, Ruff, Docker

🔢

P.7 NumPy & pandas

scores = emb @ q · top-k with argpartition

Arrays = one dtype, one block, compiled loops: 100–1,000× faster than Python loops. float32 for embeddings, normalize once, watch (N,) vs (N, 1) broadcasting. pandas for eval results: groupby, pivot_table, merge with validate; slice before you trust an average.

NumPy, pandas, pyarrow / Parquet, Polars, matplotlib

🎤 Teach it back

Answer out loud, in two minutes, as if in an interview: “Explain why asyncio speeds up 100 LLM API calls, but doesn't speed up computing 100 embeddings with a model running on our CPU. What would you use for the second case?”

A strong answer touches: an LLM call is I/O-bound, the program spends ~all of its 2 s waiting on the network, and an event loop overlaps those waits on one thread, so 100 calls take about as long as the slowest few batches allowed by your semaphore (P.3). Local embedding is CPU-bound: the work is computation, and a single thread can only do one piece at a time, so awaiting it gives no overlap and can even freeze the loop (P.3). For CPU work you need parallelism: batch the inputs into one big matrix operation (P.7), which native libraries run with the GIL released on several cores, or use threads around GIL-releasing native code, or processes for pure-Python CPU work (P.4), while keeping the event loop free with to_thread or an executor.

🏗️ Build it yourself: a rate-limited batch embedding job

You must embed a 5-million-chunk corpus (a JSONL file, ~300 tokens per chunk) with a hosted embedding API (768-dimension vectors) and write an index your search service can load. The provider allows (illustratively) 3,000 requests and 5 million tokens per minute, accepts up to 64 inputs per request, and returns occasional 429s and timeouts. The job runs on a 4 GB container. Design the script: how data flows, how fast it can go, how it stays under the limits and the memory cap, how it survives failures, and what it costs. Then write it.

Reveal a reference design and code sketch

Requirements. Every chunk embedded exactly once, rows aligned with IDs; never exceed provider limits; peak RAM well under 4 GB; transient errors retried, permanent ones fail loudly; restartable.

Throughput math. 5M × 300 = 1.5 billion tokens. Tokens per minute bind first: 1.5B ÷ 5M/min = 300 min ≈ 5 hours. Requests don't: 5M ÷ 64 = 78,125 requests ÷ 3,000/min ≈ 26 min. Each request carries ~19,200 tokens, so the limit allows ~4.3 requests/s; at ~1.5 s per request, Little's law says ~6.5 in flight: 8 workers is enough (P.3). More workers only buy more 429s.

Pipeline. A generator reads the file line by line (P.2) → itertools.batched into 64s → a bounded asyncio.Queue (backpressure: the reader waits when workers are busy, P.4) → 8 async workers, each passing a token-aware rate limiter, then calling the API with a per-request timeout and jittered retries (P.3, P.6) → vectors normalized as float32 (P.7) → written into a memory-mapped .npy file on disk (P.5).

Memory. The full index is 5M × 768 × 4 B = 15.4 GB: it never sits in RAM, it lives in the memmap, and the OS flushes pages to disk. In flight: ≤ 16 queued + 8 active batches × 64 chunks × ~1.2 KB ≈ 2 MB of text. As Python lists of floats the same vectors would need ~123 GB.

Cost. At an illustrative $0.02 per million tokens: 1.5B tokens ≈ $30 per full run, so a bug that forces a re-run costs another $30 and 5 hours. Checkpointing pays for itself.

Eval plan. Spot-check that row i of the matrix matches ID i (re-embed 100 random chunks and compare cosine ≈ 1.0); check every row has norm 1 (an all-zero row means a batch was never written); run the retrieval eval (Lesson 5.4) on the new index before switching traffic to it.

# build_index.py: embed a JSONL corpus into a float32 matrix on disk (Python 3.12+)
import asyncio, json, random
from itertools import batched
import numpy as np

BATCH = 64            # chunks per embedding request
WORKERS = 8           # concurrent requests (Little's law: rate × latency, plus headroom)
TPM = 5_000_000       # provider tokens-per-minute limit (illustrative)
MAX_ATTEMPTS = 5


class RetryableError(Exception):
    """Raise for 429 / 5xx / connection errors in your client wrapper."""


class TokenRateLimiter:
    """Spaces request starts so tokens/minute stays under the limit."""
    def __init__(self, tokens_per_min: int):
        self.per_token = 60.0 / tokens_per_min
        self.next_free = 0.0
        self.lock = asyncio.Lock()

    async def acquire(self, tokens: int) -> None:
        async with self.lock:
            now = asyncio.get_running_loop().time()
            start = max(now, self.next_free)
            self.next_free = start + tokens * self.per_token
        await asyncio.sleep(start - now)


def read_chunks(path):                       # generator: one line in memory at a time
    with open(path, encoding="utf-8") as f:
        for line in f:
            rec = json.loads(line)
            yield rec["id"], rec["text"]


def est_tokens(texts) -> int:
    return sum(len(t) // 4 + 1 for t in texts)  # ~4 characters per token


async def embed_with_retry(client, texts, limiter):
    for attempt in range(MAX_ATTEMPTS):
        await limiter.acquire(est_tokens(texts))
        try:
            async with asyncio.timeout(30):                  # per-request deadline
                return await client.embed(texts)
        except (RetryableError, TimeoutError):
            if attempt == MAX_ATTEMPTS - 1:
                raise
            await asyncio.sleep(min(20.0, 0.5 * 2 ** attempt) * random.uniform(0.5, 1.5))


async def build(client, corpus: str, out: str, dim: int) -> int:
    n = sum(1 for _ in open(corpus, encoding="utf-8"))      # cheap first pass: row count
    emb = np.lib.format.open_memmap(out, mode="w+", dtype=np.float32, shape=(n, dim))
    queue: asyncio.Queue = asyncio.Queue(maxsize=2 * WORKERS)  # bounded: backpressure
    limiter = TokenRateLimiter(TPM)

    async def producer():
        start = 0
        with open(out + ".ids", "w", encoding="utf-8") as ids:
            for batch in batched(read_chunks(corpus), BATCH):
                ids.writelines(f"{i}\n" for i, _ in batch)  # row order = id order
                await queue.put((start, [t for _, t in batch]))   # waits when queue is full
                start += len(batch)
        for _ in range(WORKERS):
            await queue.put(None)                           # one stop signal per worker

    async def worker():
        while (item := await queue.get()) is not None:
            start, texts = item
            vecs = np.asarray(await embed_with_retry(client, texts, limiter), dtype=np.float32)
            vecs /= np.linalg.norm(vecs, axis=1, keepdims=True)   # normalize once
            emb[start:start + len(texts)] = vecs                  # write to the memmap

    async with asyncio.TaskGroup() as tg:                   # any failure cancels the rest
        tg.create_task(producer())
        for _ in range(WORKERS):
            tg.create_task(worker())
    emb.flush()
    return n

# usage: n = asyncio.run(build(MyEmbedClient(), "corpus.jsonl", "index.npy", dim=768))
# then, in the search service: emb = np.load("index.npy", mmap_mode="r")

Tested on Python 3.13 with a scripted fake client (2,000 chunks, 10% injected 429s): all rows written, unit norms, rate limit respected. MyEmbedClient.embed(texts) is your wrapper around the provider SDK that raises RetryableError for 429/5xx.

Pitfalls. Creating one task per batch up front (the whole corpus's text in RAM before the first request returns); an unbounded queue (same problem); a semaphore sized by guesswork instead of rate × latency; retrying 400s (a too-long chunk fails five times, then kills the job: validate lengths first); building the matrix with np.array(list) (float64, in RAM); writing results in completion order without the row offset (vectors no longer match IDs); no checkpoint, so a failure at hour 4 means starting over (store finished batch offsets and skip them on restart); CPU-heavy tokenization inside a coroutine, which blocks the loop (move it to a process pool, P.4).

Boss quiz

1. You send 100 LLM calls that each take about 2 s, with asyncio.gather behind a Semaphore(10). Roughly how long does the batch take?
At most 10 in flight, so 100 calls ≈ 10 waves × 2 s = 20 s (vs 200 s one at a time). Little's law sizes the semaphore from your rate limit: in flight = rate × latency.
2. A pure-Python BM25 tokenizer over 2 million documents takes 40 minutes. You wrap it in a ThreadPoolExecutor(8) on an 8-core machine and it still takes about 40 minutes. Why, and what helps?
Pure-Python CPU work doesn't overlap under the GIL, with threads or asyncio. Processes give each worker its own interpreter (mind pickling costs and chunksize); native libraries that release the GIL make threads useful again (P.4).
3. Your RAG service's memory grows steadily all day. You find @functools.cache on Retriever.embed_query(self, text). What's going on?
Cached results are reachable forever, so neither refcounting nor the GC can free them; every new user query adds an entry. A method cache also keeps the instance alive (P.5).
4. Your chat endpoint does not stream, and the provider client has a 15 s read timeout. Long answers (~20 s to generate) fail with timeouts, three times each. What's the best fix?
Without streaming the whole answer is one chunk, so a read timeout shorter than generation kills healthy requests, and retries repeat the failure. Streaming fixes both the timeout and the user experience (P.6).
5. chunks = (c for c in read_jsonl("docs.jsonl")). You first compute total = sum(len(c["text"]) for c in chunks), then embed for batch in batched(chunks, 64): …. Nothing gets embedded and no error is raised. Why?
An iterator is exhausted after one pass (P.2). Recreate the generator for each pass (call read_jsonl again), or compute both in a single pass.
