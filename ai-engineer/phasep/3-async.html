Phase P · Lesson 3

async/await: the event loop, gather, semaphores & async streams

An LLM call spends about a second waiting and a few milliseconds computing. asyncio lets one Python thread wait on hundreds of them at once, if you respect rate limits and never block the loop.

🧰 You'll need (quick reminders)
  • A generator pauses at yield and resumes later with its state intact (Lesson P.2). Coroutines pause the same way, at await.
  • A typical LLM call takes around a second or more, mostly network and generation time; you can stream the answer token by token (Lesson 0.5).
  • Providers rate-limit you: send too much and you get HTTP 429. The SDKs retry 429s and 5xx errors twice by default (Lessons 0.5 and P.1).
🎯 Hook

OpenAI's cookbook ships a script for one of the most common jobs in AI engineering: running a huge batch of API requests. Its docstring sums up the whole problem: send a million requests one by one and the job takes days; send them all in parallel and they blow through the rate limits and fail.

Their answer is built on asyncio: make requests concurrently, but throttle them to stay under the limits, and retry the failures. By the end of this lesson you'll be able to write that script yourself, and explain each design choice.

Numbers first: your program is mostly waiting

Plain sentence: LLM calls are I/O-bound: their time is spent waiting on input/output (the network), not computing. The fix for waiting isn't more CPUs; it's not waiting idly. That's concurrency, and in Python the lightest way to get it is asyncio.

💡 Big idea A coroutine (async def) is a function that can pause at every await. An event loop runs many of them on one thread: it runs one until it awaits something slow (a network reply, a timer), parks it, runs another, and resumes the first when its reply arrives. Nothing runs in parallel, yet hundreds of calls overlap their waiting. Two rules follow. Bound how many run at once (a semaphore) to respect rate limits, and never block the loop: one synchronous call inside a coroutine freezes every other coroutine.
🧠 Analogy: one waiter, many tables

A good waiter takes table 1's order, hands it to the kitchen, and goes to table 2 instead of standing at the kitchen window. When a dish is ready, the kitchen rings a bell and the waiter brings it over. One waiter, twenty tables, no one waiting on the waiter. Now imagine the waiter stops to read a newspaper for five minutes (a blocking call): every table stalls, though the kitchen keeps cooking. And if the waiter sends 200 orders at once, the kitchen sends half of them back (429). Await is “go serve someone else”; a semaphore is “at most ten open orders”.

Concurrency limits: semaphores and rate limits

Provider limits are usually measured per minute: Anthropic's docs list requests per minute (RPM), input tokens per minute and output tokens per minute, enforced with a token bucket (capacity refills continuously rather than resetting each minute, so bursts can trip the limit). asyncio.Semaphore(n) doesn't measure rates; it caps how many requests are in flight. The bridge between the two is a one-line formula.

✏️ Worked example: how many in flight? (Little's law)

In-flight requests = arrival rate × time each one takes. Your limit is 500 requests per minute and a call takes about 1.2 s.

  • 500 per minute = 500 ÷ 60 ≈ 8.3 requests per second.
  • 8.3 per second × 1.2 s ≈ 10 requests in flight. That's your semaphore size.
  • With Semaphore(50) you'd send ~42 per second for a few seconds, burst past the bucket, and get 429s. With Semaphore(2) you'd only reach ~100 per minute: safe but 5× slower than allowed.
  • Tokens per minute can bind first: 10 calls in flight × 3,000 input tokens each, completing every 1.2 s, is 1.5 million input tokens per minute. Check every limit, not just RPM.

Timeouts, cancellation and errors

  • Always set a deadline. async with asyncio.timeout(30): (3.11+; asyncio.wait_for before that) cancels the work inside and raises TimeoutError. The SDKs also take a timeout: the Anthropic SDK's default is 10 minutes, far longer than most user-facing requests should wait.
  • Cancellation is an exception. A cancelled task gets asyncio.CancelledError raised at its current await. It subclasses BaseException, so except Exception won't swallow it, and you shouldn't: the docs warn that TaskGroup and timeout() rely on it. Put cleanup in finally.
  • gather vs TaskGroup on failure. By default the first exception in gather propagates, but the other awaitables keep running. return_exceptions=True returns errors in the results list instead, which is ideal for batch jobs (“which of the 1,000 failed?”). TaskGroup cancels the siblings when one fails, which is ideal when the results are only useful together (all three retrievers for one RAG answer).

Async generators: streams that don't block

An async def containing yield is an async generator; you consume it with async for. It's the async version of Lesson P.2's token streams, and what the async SDK clients return when you stream. Because each __anext__ is awaited, ten users' streams can be relayed concurrently on one thread. async with is the async context manager (closing connections, releasing semaphores) and async comprehensions work too: [t async for t in stream].

The blocking-call pitfall

The event loop can only switch at await. Anything slow that doesn't await holds it. The docs' advice: run blocking work in a thread with asyncio.to_thread() (3.9+), and use debug mode (asyncio.run(main(), debug=True) or PYTHONASYNCIODEBUG=1), which logs any callback that takes longer than 100 ms.

Reuse one HTTP client. A client holds a connection pool (httpx2's defaults: up to 100 connections, 20 kept alive), so creating a new client per request throws away connection reuse. The same goes for SDK clients: create one AsyncAnthropic() at startup and share it.

🧰 Tools you'll actually use

Standard library: asyncio (run, gather, TaskGroup, Semaphore, timeout, to_thread, Queue). Clients: AsyncAnthropic, AsyncOpenAI (both can also use aiohttp as their transport), httpx / httpx2, aiohttp. Servers: FastAPI runs async def endpoints on the loop and plain def endpoints in a threadpool (Lesson P.6). Runnable on Python 3.11+ (checked on 3.13), with a fake LLM standing in for the network:

import asyncio, random, time

async def fake_llm(prompt: str) -> str:          # stand-in for: await client.messages.create(...)
    await asyncio.sleep(random.uniform(0.8, 1.2))  # waiting on the network; the loop runs others
    return f"summary of {prompt}"

async def summarize_all(docs: list[str], max_in_flight: int = 10) -> list[str]:
    sem = asyncio.Semaphore(max_in_flight)       # at most 10 requests at once
    async def one(doc: str) -> str:
        async with sem:
            async with asyncio.timeout(30):      # Python 3.11+: cancel if a call hangs
                return await fake_llm(doc)
    return await asyncio.gather(*(one(d) for d in docs))   # results in input order

async def stream_tokens(text: str):              # an async generator: async def + yield
    for word in text.split():
        await asyncio.sleep(0.01)                # a token arriving from the network
        yield word + " "

async def main():
    t = time.perf_counter()
    out = await summarize_all([f"doc{i}" for i in range(50)])
    print(len(out), f"{time.perf_counter() - t:.1f}s")     # 50 calls in ~5 s, not ~50 s

    async with asyncio.TaskGroup() as tg:        # Python 3.11+: if one fails, the rest are cancelled
        a = tg.create_task(fake_llm("question A"))
        b = tg.create_task(fake_llm("question B"))
    print(a.result(), "|", b.result())

    async for tok in stream_tokens("tokens arrive one at a time"):
        print(tok, end="", flush=True)
    print()

    # a blocking call moved off the loop: both sleeps overlap, ~1.0 s total
    await asyncio.gather(asyncio.to_thread(time.sleep, 1), asyncio.sleep(1))

asyncio.run(main())

The same shape with the real async client (from the Anthropic SDK docs; needs an API key, and MODEL is whichever model you use):

from anthropic import AsyncAnthropic
client = AsyncAnthropic(max_retries=2, timeout=30.0)       # one client, shared; 2 retries is the default

async def ask(q: str) -> str:
    msg = await client.messages.create(model=MODEL, max_tokens=512,
                                       messages=[{"role": "user", "content": q}])
    return msg.content[0].text

async def stream(q: str):
    async with client.messages.stream(model=MODEL, max_tokens=1024,
                                     messages=[{"role": "user", "content": q}]) as s:
        async for text in s.text_stream:
            print(text, end="", flush=True)

🚀 Startup vs big tech

Week one

FastAPI with async def endpoints, one shared AsyncAnthropic/AsyncOpenAI client, a module-level semaphore per provider sized with Little's law, timeouts on every call, the SDK's retries, and asyncio.gather for parallel retrieval + generation steps. Turn on asyncio debug mode in development to catch blocking calls.

At scale

Rate limiting moves out of the process: a shared limiter (often Redis-backed) or an LLM gateway that knows the org-wide RPM and token budgets (Lesson 8.1); priority queues so interactive traffic beats batch jobs; offline work goes to provider batch APIs; and loop-lag metrics (how late callbacks run) are on the dashboard next to p95 latency.

🎤 Interview angle
  • “You need to summarize 10,000 documents with an LLM. Write it.” Async client, Semaphore sized from the rate limit (Little's law), timeout per call, retries with backoff on 429/5xx, gather(return_exceptions=True) or a worker pool over an asyncio.Queue, results written incrementally.
  • “Is asyncio parallel?” No: one thread, cooperative switching at await. It overlaps waiting, not computation; for CPU work use processes (P.4).
  • “Our async API got slow under load and CPU is at 5%. Why?” Something blocks the loop: a sync client, requests, time.sleep, or heavy parsing. Find it with debug mode or loop-lag metrics; fix with async libraries or to_thread.
  • “gather or TaskGroup?” TaskGroup when results are all-or-nothing and you want siblings cancelled; gather with return_exceptions=True for best-effort batches.
🏭 In the real world
Parallel requests under rate limits 🏢 OpenAI api_request_parallel_processor.py

How: streams requests from a file, makes them concurrently with asyncio and aiohttp, throttles both requests and tokens per minute, and retries failures.

Why this method: sequential takes days; unthrottled parallel fails. Concurrency capped just under the limits gets the maximum safe throughput.

Token-bucket rate limits 🏢 Anthropic · 2026 Rate limits

How: limits are measured in requests, input tokens and output tokens per minute, enforced with a token bucket; going over returns a 429 that says which limit was hit, often with a retry-after header saying how many seconds to wait.

Why this method: continuous refill smooths load, but means short bursts can trip the limit: exactly why client-side concurrency caps matter.

async def vs def in a web framework 🧰 Open source FastAPI: Concurrency and async/await

How: async def endpoints run on the event loop; plain def endpoints run in an external threadpool so they don't block the server.

Why this method: lets you mix async LLM clients with sync libraries safely, as long as you never call blocking code from inside an async def.

Catching blocking calls 🧰 Open source Developing with asyncio

How: debug mode logs callbacks slower than 100 ms (tunable via loop.slow_callback_duration), un-awaited coroutines and calls from the wrong thread.

Why this method: a blocking call is silent in production; debug mode turns it into a log line with a traceback.

🤯 Fun fact · the tulip and the keywords

asyncio started as Guido van Rossum's PEP 3156 in December 2012; its discussion list was python-tulip, after the project's code name, Tulip. The async and await keywords came later, in Python 3.5, from Yury Selivanov's PEP 492. Before that, coroutines were written as generators with yield from, which is why Lesson P.2's pausing functions feel so familiar here.

Check yourself

1. Your limit is 600 requests per minute and calls take about 2 s. Roughly what semaphore size keeps you near the limit without going over?
Little's law: 600 per minute = 10 per second; 10 per second × 2 s = 20 in flight. 5 would cap you at 150 per minute; 600 would burst straight into 429s. Leave a little headroom, and check token-per-minute limits too.
2. A FastAPI async def /chat endpoint calls OpenAI().chat.completions.create(...) (the sync client). Under 20 concurrent users, latency grows linearly and CPU sits at 3%. What's happening?
Inside async def, a blocking call holds the only thread the loop has. Nothing else, not even other users' requests, can run until it returns. Low CPU plus linear latency growth is the classic signature.
3. A RAG answer needs three parallel calls (vector search, keyword search, a reranker warm-up). If any fails, the answer is useless and the others should stop. Which tool fits best?
TaskGroup cancels the remaining tasks as soon as one fails and raises the errors together, so no orphaned work keeps burning tokens. return_exceptions=True suits best-effort batches; the for loop gives up the concurrency entirely.
📝 TL;DR
  • LLM calls are I/O-bound: asyncio overlaps their waiting on one thread. async def + await + asyncio.run.
  • gather for batches (results in order, return_exceptions=True), TaskGroup (3.11+) for all-or-nothing work.
  • Cap concurrency with a Semaphore sized by Little's law (rate × latency); set timeouts; never swallow CancelledError.
  • Never block the loop: async clients, asyncio.sleep, to_thread for blocking work, debug mode to find offenders.
