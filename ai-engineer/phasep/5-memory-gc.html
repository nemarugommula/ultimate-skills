Phase P · Lesson 5

Memory & garbage collection: references, cycles, leaks

Your RAG service holds documents, chunks, caches and embedding matrices for days at a time. Know how Python decides when memory is freed, and you'll stop leaks before they page you at 3 a.m.

🧰 You'll need (quick reminders)
  • Classes and attributes: doc.chunks = [...] stores a list inside an object; dataclasses (Lesson P.1).
  • Generators process data one item at a time instead of loading it all (Lesson P.2).
  • Processes: a server can start several worker processes by copying (forking) a parent (Lesson P.4).
  • Embeddings: a list of numbers (say 768 of them) that represents the meaning of a text chunk (Lesson 2.1).
🎯 Hook

In 2017 Instagram, whose web servers run Python (Django) across a large fleet, did something that sounds reckless: they turned off Python's garbage collector across their web fleet. Plain gc.disable() didn't even stick, because a third-party library switched it back on, so they used gc.set_threshold(0). The result: about a 10% capacity win.

Why would collecting less garbage make servers faster? Their worker processes were forked from a parent and shared its memory pages, and the collector's bookkeeping kept writing to those shared objects, forcing the operating system to copy the pages for every worker. They later upstreamed gc.freeze() to Python 3.7 so anyone can avoid this. To understand that story, and to keep your own AI services from leaking, you need to know how CPython actually frees memory.

That's an 8× difference for the same numbers. At one million embeddings it is the difference between about 24.6 GB and 3.1 GB: one needs a big machine, the other fits on a laptop. And none of it matters if the memory is never freed, which is the other half of this lesson.

Names point to objects

A Python variable is not a box that holds a value. It's a name (a label) that refers to an object somewhere in memory. Several names, list slots or attributes can refer to the same object:

chunks = ["refunds...", "shipping..."]
batch = chunks              # no copy: a second name for the same list
batch.append("warranty...")
print(len(chunks))          # 3, because there is only one list
batch = chunks.copy()       # now a new list (the strings inside are still shared)

Assigning never copies. That's why a “harmless” debug_log.append(doc) keeps an entire 50 MB document alive: the list holds a reference to it.

Rule 1: reference counting frees most memory instantly

Every CPython object carries a reference count (refcount): how many names, list slots, dict values or attributes currently point at it. Assigning a name adds one; del, reassigning, or a function returning removes one. The moment the count hits zero, the object is freed immediately, and anything it pointed to loses a reference too (which can free them in turn).

import sys
x = []
sys.getrefcount(x)   # 2: the name x + the temporary reference from the call itself
y = x
sys.getrefcount(x)   # 3
d = {"k": x}
sys.getrefcount(x)   # 4
del x, y, d          # count drops to 0: the list is freed right here

The docs warn not to rely on the exact number (only 0 or 1 is meaningful), and some objects like None are “immortal” since Python 3.12, with a huge fake count. It's a teaching tool, not an API.

Rule 2: cycles need the cyclic garbage collector

Reference counting has one blind spot: a reference cycle. If a document points to its chunks and every chunk points back to its parent document, each object always has at least one reference, from the others. Delete every name you have, and the counts never reach zero. The group is unreachable but not freed.

That's what the cyclic garbage collector (the gc module, usually just “the GC”) is for. Every so often it scans container objects (lists, dicts, class instances…), finds groups that are only referenced from inside the group, and frees them. To keep scans cheap it's generational:

  • New container objects start in generation 0. A collection of gen 0 starts when allocations minus deallocations pass threshold0 (700 in older versions, 2,000 in recent CPython; check gc.get_threshold()).
  • Objects that survive move to generation 1, then 2. Older generations are scanned less often, because most objects die young.
  • A full collection of the oldest generation only runs when the objects waiting there exceed 25% of all long-lived objects, so its cost stays bounded.

Two consequences for AI services: cyclic garbage sits in memory until the next collection (so memory shows a sawtooth), and the collector can only free what is unreachable. If your code still holds a reference (a global list, a cache), no collector will help.

💡 Big idea CPython frees an object the moment nothing refers to it. The GC exists only for cycles. So almost every “memory leak” in Python is not the runtime's fault: it's a reference you forgot you were holding (an unbounded cache, a global list, a closure, a task set), or a cycle that waits for the collector. Find the reference, and you've found the leak.
🧠 Analogy: library books and sticky notes

Every book in a library has a tally of who has it checked out. When the tally hits zero, it goes straight back on the shelf: that's reference counting. But two books that are only “checked out” to each other (each one's card says the other has it) never come back on their own. Once in a while a librarian walks the stacks and spots books no actual person holds: that's the cyclic collector. And if you keep a book on your desk “just in case”, no librarian will take it: that's a cache that grows forever.

What you should see: strong parent pointers make a cycle, so memory climbs in a sawtooth and drops only when the collector runs. Disable the GC and it climbs forever. Weak pointers break the cycle, so reference counting frees each document the instant the request ends: a flat line, no collector needed. And the global list leaks no matter what, because those documents are still reachable. That last one is the most common leak in real services.

Tools that break cycles and shrink objects

  • weakref: a weak reference points to an object without adding to its refcount. weakref.ref(doc)() returns the document, or None once it's gone. Use it for back-pointers (chunk → parent) and observers. weakref.WeakValueDictionary makes a cache that never keeps its values alive by itself.
  • Bounded caches: functools.lru_cache(maxsize=1024), not the unbounded @cache, for embedding or prompt caches. Watch out: on a method, the cache holds self (the docs warn about this), so instances live as long as the cache.
  • __slots__: by default each instance carries a dict for its attributes. Declaring __slots__ (or @dataclass(slots=True), Python 3.10+) stores attributes in fixed slots. For 100,000 three-field chunk objects we measured 13.6 MB → 9.6 MB on Python 3.13 (1.4×) and 18.8 → 9.2 MB on 3.9 (2×). Newer Pythons already shrank instance dicts, so measure before bothering.
  • gc.freeze() (3.7+): for servers that load models or indexes then fork workers. The docs' recipe: gc.disable() early in the parent, gc.freeze() right before forking, gc.enable() early in each child. Frozen objects are never scanned, so their pages stay shared.

One more surprise: after a big spike, the process's resident memory (RSS, what your dashboard shows) often doesn't fall all the way back, because Python's allocator keeps freed blocks for reuse and memory can be fragmented. A leak is memory that keeps growing under steady traffic; a high-water mark is memory that went up once and stays flat. Tell them apart before you start debugging.

Big matrices: dtype and memory-mapping

Embedding matrices are where AI services spend most of their RAM. Two levers:

  • dtype (the number format): float64 = 8 bytes, float32 = 4, float16 = 2, int8 = 1 per number. Most embedding models output float32; float16 or int8 quantization (Lesson 2.2) halves or quarters memory again, at a small accuracy cost you should measure.
  • Memory-mapping: np.load("emb.npy", mmap_mode="r") returns an array whose data stays in the file; the operating system pages in only the parts you touch, and several processes can share the same pages. Great for read-only indexes that are larger than you want in each worker's private memory.
✏️ Worked example: will the index fit in the pod?

You have 2 million chunks embedded with a 1,024-dimension model, and a 16 GB container.

  • Numbers: 2,000,000 × 1,024 = 2.048 billion.
  • As Python lists of floats: 2M × (56 + 1,024 × 32) bytes ≈ 65.6 GB. Doesn't fit.
  • NumPy float64 (the accidental default): 2.048 B × 8 = 16.4 GB. Doesn't fit (and the app needs memory too).
  • NumPy float32: 2.048 B × 4 = 8.2 GB. Fits, with half the pod left.
  • float16: 4.1 GB; int8: 2.0 GB, if your recall eval says quality holds.

And with 4 worker processes each loading their own copy, multiply by 4, unless you memory-map one file (shared pages) or move the vectors into a vector database (Lesson 2.3).

Finding a leak: measure, don't guess

  1. Confirm the shape: memory per pod over a day of steady traffic. Steady growth = leak; one step up = high-water mark.
  2. Snapshot twice with tracemalloc (standard library): take a snapshot, serve 1,000 requests, take another, and compare. The top lines show which source lines allocated the memory that's still alive.
  3. Native memory too: NumPy, tokenizers and model runtimes allocate outside Python's allocator. memray (by Bloomberg) tracks Python and native allocations and draws flame graphs; it runs on Linux and macOS.
  4. Ask who holds it: gc.get_referrers(obj) in a debugging session shows what still points at a suspicious object.
🧰 Tools you'll actually use

Standard library: sys, gc, weakref, tracemalloc, functools.lru_cache, collections.deque. Profilers: memray (memray run app.py, then memray flamegraph), and py-spy for CPU. Arrays: NumPy dtypes and mmap_mode.

import gc, tracemalloc, weakref
from collections import deque
import numpy as np

# 1. Break parent/child cycles with a weak back-pointer
class Document:
    def __init__(self, text):
        self.text = text
        self.chunks = [Chunk(self, t) for t in text.split("\n\n")]

class Chunk:
    __slots__ = ("_parent", "text")          # no per-instance __dict__
    def __init__(self, parent, text):
        self._parent = weakref.ref(parent)    # doesn't keep the Document alive
        self.text = text
    @property
    def parent(self):
        return self._parent()                 # None once the Document is gone

# 2. Bounded "recent" buffer instead of an ever-growing global list
RECENT = deque(maxlen=100)

# 3. Find what is still allocated after a batch of work
tracemalloc.start()
before = tracemalloc.take_snapshot()
for i in range(1_000):
    doc = Document("refunds...\n\nshipping...\n\nwarranty..." * 50)
    RECENT.append(doc)                        # only the last 100 stay alive
after = tracemalloc.take_snapshot()
for stat in after.compare_to(before, "lineno")[:3]:
    print(stat)                               # file:line, size and count growth

# 4. Embeddings: float32, and memory-map big read-only matrices
emb = np.asarray(np.random.rand(10_000, 768), dtype=np.float32)
print(emb.nbytes / 1e6, "MB")                 # 30.72 MB (float64 would be 61.44)
np.save("emb.npy", emb)
shared = np.load("emb.npy", mmap_mode="r")  # pages load on demand, shared between processes

# 5. Pre-fork servers (load models, then fork workers): keep shared pages shared
gc.disable()      # early in the parent ...load models / indexes...
gc.freeze()       # right before fork(): move everything to a permanent generation
# ...in each child process, early: gc.enable()

Run with python -X tracemalloc=25 app.py to record 25 frames of traceback per allocation instead of 1.

🚀 Startup vs big tech

Week one

Store embeddings as float32 NumPy arrays (or straight in a vector database), bound every cache with a maxsize, set a memory limit on the container so a leak restarts one pod instead of the whole node, and put memory per pod on a dashboard. When it climbs, take two tracemalloc snapshots.

At scale

Memory is a capacity line item. Teams preload models and indexes in a parent process and fork workers with gc.freeze(), tune or disable the GC per service, run memray in CI on long-running jobs, and treat a 10% memory win like Instagram did: as a fleet-wide cost saving.

🎤 Interview angle

“Our FastAPI RAG service's memory grows about 200 MB an hour until Kubernetes kills it. How do you debug it?” A senior answer:

  • Separates a leak (growth under steady load) from a high-water mark, and checks whether growth tracks unique queries (a cache) or requests (a list, tasks).
  • Explains refcounting vs the cyclic GC: the GC can't free anything still referenced, so look for module-level dicts, lists, lru_cache on methods, stored exceptions, task sets.
  • Uses tracemalloc snapshot diffs for Python objects and memray for native allocations (NumPy, tokenizers).
  • Fixes and guards: bounded caches, weak back-pointers, float32, a memory limit plus an alert, and a soak test that replays an hour of traffic in CI.
🏭 In the real world
Turning the GC off for a 10% win 🏢 Instagram · 2017 Dismissing Python Garbage Collection at Instagram

How: Django workers forked from a parent process; the team found GC activity was turning shared memory pages into private copies, then set gc.set_threshold(0) (because gc.disable() got re-enabled by a library) and skipped cleanup at exit.

Why this method: with less memory per worker they could run more processes per host, a 10% global capacity win.

gc.freeze() goes into Python 🏢 Instagram · 2017 Copy-on-write friendly Python garbage collection

How: instead of disabling the collector everywhere, they added an API that moves all current objects into a permanent generation the GC never scans, and upstreamed it to Python 3.7.

Why this method: objects loaded before the fork stay shared, while the GC keeps working for new objects in each worker.

A new GC, then a rollback 🧰 CPython 3.14.5 What's new in Python 3.14 (gc section)

How: Python 3.14.0–3.14.4 shipped an incremental collector with much shorter pauses on large heaps; 3.14.5 reverted to the 3.13 generational GC after reports of significant memory pressure in production.

Why this method: even the runtime's authors trade pause time against peak memory, and production memory won. Pin and test your Python minor and patch versions.

Memory-mapping a whole Wikipedia 🏢 Hugging Face Datasets 🤝 Arrow

How: the datasets library stores data in Apache Arrow files and memory-maps them instead of loading them.

Why this method: their docs show loading the English Wikipedia dataset using about 50 MB of RAM, because the operating system pages data in from disk only when it's read.

Finding native leaks 🧰 Open source memray (Bloomberg)

How: traces every allocation in Python code, native extension modules and the interpreter itself, then renders flame graphs or tables.

Why this method: AI services allocate most memory in C/C++ libraries (NumPy, tokenizers, runtimes), which tracemalloc can't see.

🤯 Fun fact · objects that never die

On Python 3.13, sys.getrefcount(None) returns 4294967295. Since Python 3.12 (PEP 683), objects like None, True and small integers are immortal: their refcount is set to a special huge value and never changes. Writing to their counts would dirty shared memory pages after a fork; the PEP cites Instagram among the projects hurt by this, alongside the effort to give each interpreter its own GIL (Lesson P.4).

Check yourself

1. You keep 500,000 embeddings of 1,536 dimensions in a NumPy float32 array. About how much memory is that?
500,000 × 1,536 = 768 million numbers × 4 bytes = 3.07 GB. As float64 it would be 6.1 GB, and as Python lists of floats about 24.6 GB (32 bytes per number).
2. A chat service appends every response to a module-level list HISTORY for a debug page. Memory grows all day. A teammate adds gc.collect() after each request. What happens?
The GC frees only unreachable objects. A global list is reachable forever. Bound it (deque(maxlen=100)) or log and drop the responses.
3. Each Chunk stores self.parent = doc, and each document stores its chunks. The service runs with gc.disable() for latency. What do you expect, and what's the cleanest fix?
Doc → chunks → doc is a cycle. With the GC off it's never freed; del doc only removes one name. A weak back-pointer breaks the cycle, so freeing is immediate with or without the GC.
📝 TL;DR
  • Names refer to objects; assignment never copies. Objects die when their refcount reaches zero, immediately.
  • The generational GC exists only for cycles; it can't free anything you still reference.
  • Real leaks are forgotten references: unbounded caches, global lists, closures, stored exceptions, task sets. Find them with tracemalloc diffs and memray.
  • Python floats cost ~32 bytes each in a list; NumPy float32 costs 4. Use float32 (or less), and memory-map big read-only matrices.
  • Pre-fork servers: gc.freeze() before forking keeps shared memory shared.
