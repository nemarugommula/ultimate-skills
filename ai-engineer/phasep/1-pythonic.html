Phase P · Lesson 1

Pythonic Python: the data model, typing, dataclasses and decorators

The Python behind every LLM wrapper you'll write: how objects really behave, the traps that bite in production, and the idioms (decorators, context managers, typed models) that make AI code safe to change.

🧰 You'll need (quick reminders)
  • Basic Python: functions, classes, lists and dicts. This lesson goes deeper, not wider.
  • An LLM API call is an HTTP request: you send a prompt as JSON, you get JSON back, and it can fail with a 429 (rate limited) or a 5xx (server error) (Lesson 0.5).
  • Structured output means asking the model for JSON that matches a schema (Lesson 1.3). Here we look at the Python objects that hold that JSON.
🎯 Hook

By 2019 Dropbox had type-checked 4 million lines of Python with mypy. Their engineering post explains why: at their scale, dynamic typing “made code needlessly hard to understand and started to seriously impact productivity.”

AI code hits the same wall sooner, because it is full of loosely shaped data: prompts, message lists, tool arguments, model JSON. That's why the official SDKs lean on Python's type system today. OpenAI's Python library types nested request parameters as TypedDicts and returns responses as Pydantic models. This lesson is the Python that makes that work.

Numbers first: everything is an object

In C, an integer is 4 or 8 bytes. In Python, it's a full object with a type pointer and a reference count. Measured with sys.getsizeof on 64-bit CPython 3.13 (exact sizes vary a little by version):

ValueSize in memoryWhat it means for AI code
1 (an int)28 bytesEven a number carries a type and a reference count.
1.0 (a float)24 bytesOne embedding dimension stored as a Python float costs 3× a raw 8-byte double.
[] (empty list)56 bytesA list stores pointers to objects, not the objects themselves.
a list of 1,000,000 floats≈ 8.4 MB of pointers + 24 MB of floats ≈ 32 MBThe same numbers as a NumPy array take 8 MB (Lesson P.7).

Plain sentence: every value is an object, every variable is a name pointing at one, and behaviour comes from the object's type. Most Python surprises (and most Python power) follow from that.

💡 Big idea Python is a language of protocols. len(x), for, with, if x:, x[i] and f(x) all just call special methods on the object (“dunder” methods, named for their double underscores, like __len__). Learn the protocols, respect mutability (names share objects, they don't copy them), and the senior tools follow naturally: decorators wrap functions because functions are objects; context managers are objects with __enter__/__exit__; type hints and Pydantic describe the shapes of those objects.
🧠 Analogy: luggage tags, not boxes

A Python variable is not a box that holds a value. It's a luggage tag tied to a suitcase. b = a ties a second tag to the same suitcase; it doesn't pack a new one. If the suitcase can be opened (a list, a dict), anyone holding a tag sees what you put in. If it's sealed (an int, a string, a tuple), “changing” it really means tying your tag to a different suitcase. Almost every Python gotcha in this lesson is two tags on one open suitcase.

Truthiness: None, False, 0, 0.0, "", [], {} are all “falsy”; nearly everything else is “truthy”. That makes x or default tempting and dangerous: temperature or 0.7 turns a deliberate temperature=0 into 0.7. When 0, "" or [] are valid values, test is None instead.

Mutability: the traps that ship to production

Lists, dicts and sets are mutable (can change in place). Ints, floats, strings, tuples and frozensets are immutable; Python 3.15 (released October 2026) added a built-in frozendict too. Four traps follow from luggage tags:

  • Mutable default arguments. def add(msg, history=[]) creates the list once, when the function is defined. Every call without history shares it, so one user's conversation leaks into the next. Use history=None and create the list inside.
  • Shallow copies. config.copy() copies the outer dict only; nested lists are shared. Use copy.deepcopy, or build a new value instead of mutating.
  • Late-binding closures. A function defined in a loop looks up the loop variable when it's called, not when it's defined, so a list of per-tool lambdas can all point at the last tool.
  • is vs ==. == asks “same value?”, is asks “same object?”. Use is only for None (and sentinels).

A context manager is any object with __enter__ and __exit__. The quickest way to write one is a generator with @contextlib.contextmanager: code before yield is setup, code after it (in a finally) is cleanup. You'll use them for timers, tracing spans and HTTP clients, and their async twins (async with) in Lesson P.3.

Decorators: wrap every LLM call without touching it

Functions are objects, so a function can take a function and return a new one. That's a decorator. @timed above def ask_llm is exactly ask_llm = timed(ask_llm). Decorators are how you add retries, timing, caching, logging and tracing to LLM calls in one place. Three rules:

  • Use functools.wraps inside, or the wrapped function loses its name and docstring (and your traces say wrapper).
  • A decorator that takes arguments, like @retry(max_attempts=4), is a function that returns a decorator: three nested levels.
  • Order matters. Decorators apply bottom-up. @timed above @retry measures the whole call with retries (what the user feels); below it, it times each attempt separately.
✏️ Worked example: what a retry policy really costs

An LLM endpoint returns 429 on 30% of calls at peak. You retry up to 4 attempts with exponential backoff: wait 1 s, then 2 s, then 4 s.

  • Chance all 4 attempts fail: 0.3⁴ = 0.81% (versus 30% with no retry).
  • Expected attempts per call: 1 + 0.3 + 0.3² + 0.3³ = 1.417, so about 42% more requests (and cost, if failures are billed; 429s usually aren't).
  • Worst-case extra waiting: 1 + 2 + 4 = 7 s of sleep on top of four call latencies. Your timeout and UX must allow for that.
  • Retrying a 400 Bad Request buys nothing: the same bad request fails 4 times and adds 7 s. Retry only errors that can succeed later (429, 5xx, timeouts, connection errors).

Both official SDKs already retry 429s and 5xx errors 2 times by default with exponential backoff (max_retries). Write your own decorator when you need something they don't do: a different policy, fallbacks to another model, or retries around a whole multi-call step.

Toy rules: about 29% of first attempts get a 429; a retry sent less than 0.5 s after a 429 is still inside the rate-limit window and fails 80% of the time; plain exponential backoff without jitter makes many clients retry in lockstep (45% fail); with jitter, retries spread out (29%). A hung call runs until the client's timeout: the Anthropic SDK's default is 10 minutes.

Retrying “any Exception” against the 400 endpoint wastes every attempt plus the backoff. The hanging endpoint shows why timeouts belong in the stack: with no timeout, p95 latency is measured in minutes.

Typed data: dataclasses, TypedDict and Pydantic

AI code passes around three kinds of structured data: your own internal records (chunks, documents), JSON dicts you send to APIs, and JSON you receive from models and users, which can be wrong. Python has a tool for each.

Pydantic's model_json_schema() is how one class can become a structured-output schema or a tool definition (Lessons 1.3 and 6.2). Its validation core, pydantic-core, is written in Rust, so validating at the boundary is cheap.

Hints do nothing at runtime on their own. A type checker reads them before you run: mypy and pyright are the established ones, and Astral's ty and Meta's Pyrefly are newer, Rust-based options. Frameworks also read hints at runtime: the OpenAI Agents SDK builds a tool's JSON schema from your function's signature (with inspect) and its docstring, using Pydantic. Good hints literally become the tool description the model sees.

Also worth knowing: functools.lru_cache memoises a function (cache repeated embedding or classification calls; arguments must be hashable, and set maxsize or it grows forever); functools.partial pre-fills arguments (partial(call_model, model=CHEAP, max_tokens=256)); enum.StrEnum (3.11+) gives named constants that still compare equal to strings; and match (3.10+) destructures nested data, perfect for routing on response content blocks.

🧰 Tools you'll actually use

Standard library: functools (wraps, lru_cache, partial), dataclasses, typing, contextlib, enum, copy. Libraries: Pydantic for validation; tenacity if you want a ready-made retry decorator. Type checkers: mypy, pyright (also inside VS Code's Pylance), ty, Pyrefly. This runs on Python 3.10+ with pip install pydantic (checked on 3.13):

import functools, random, time
from dataclasses import dataclass, field
from typing import Literal, Protocol
from pydantic import BaseModel, Field, ValidationError

class RateLimitError(Exception): ...          # stand-in for the SDK's 429 error

def retry(max_attempts=4, base=1.0, retry_on=(RateLimitError, TimeoutError)):
    def decorator(fn):
        @functools.wraps(fn)                   # keep fn.__name__, docstring
        def wrapper(*args, **kwargs):
            for attempt in range(1, max_attempts + 1):
                try:
                    return fn(*args, **kwargs)
                except retry_on:
                    if attempt == max_attempts:
                        raise
                    time.sleep(base * 2 ** (attempt - 1) * random.uniform(0.5, 1.5))  # backoff + jitter
        return wrapper
    return decorator

def timed(fn):
    @functools.wraps(fn)
    def wrapper(*args, **kwargs):
        t0 = time.perf_counter()
        try:
            return fn(*args, **kwargs)
        finally:
            print(f"{fn.__name__} took {time.perf_counter() - t0:.2f}s")
    return wrapper

@timed            # outermost: measures the total, retries included
@retry(base=0.01)
def ask_llm(prompt: str) -> str:
    if random.random() < 0.3:
        raise RateLimitError("429")
    return f"answer to {prompt!r}"

@dataclass(frozen=True)
class Chunk:                       # plain container: fast, no validation
    doc_id: str
    text: str
    tags: list[str] = field(default_factory=list)   # never tags=[]

class Answer(BaseModel):           # validated at the boundary (LLM output, API input)
    label: Literal["refund", "shipping", "other"]
    confidence: float = Field(ge=0, le=1)

class Embedder(Protocol):          # any object with this method fits; no inheritance needed
    def embed(self, texts: list[str]) -> list[list[float]]: ...

print(ask_llm("hi"))
print(Answer.model_validate_json('{"label": "refund", "confidence": "0.9"}'))  # "0.9" → 0.9
try:
    Answer.model_validate_json('{"label": "refunds", "confidence": 1.4}')
except ValidationError as e:
    print(e.error_count(), "validation errors")          # 2: bad label, confidence > 1

def describe(block: dict) -> str:  # match (3.10+) on a response content block
    match block:
        case {"type": "text", "text": str(t)}:
            return f"text: {t}"
        case {"type": "tool_use", "name": name, "input": {**args}}:
            return f"call {name}({args})"
        case _:
            return "unknown block"

In production, catch the SDK's own error classes (for example anthropic.RateLimitError) rather than a home-made one, and remember the SDKs already retry twice: your decorator's attempts multiply with theirs unless you set max_retries=0 on the client.

🚀 Startup vs big tech

Week one

Type hints on every function signature, Pydantic models for anything that crosses a boundary (LLM output, request bodies), dataclasses inside, the SDK's built-in retries, and pyright or mypy in the editor. One llm.py module where every model call goes through a single decorated function, so adding timing or a fallback later is a one-line change.

At scale

Type checking in CI as a merge gate, shared typed client libraries owned by a platform team, retries and timeouts set centrally (often in an LLM gateway, Lesson 8.1), tracing decorators that emit spans with token counts, and lint rules that ban mutable defaults and bare except:.

🎤 Interview angle

Python questions in AI-engineer interviews are usually practical. Expect:

  • “What's wrong with def f(x, cache={})?” Defaults are evaluated once at definition time; the dict is shared across calls. Use None.
  • “Write a retry decorator with exponential backoff for an LLM call.” Show functools.wraps, retry only retryable errors, jitter, a max attempt count, re-raise on the last attempt, and mention the SDK's built-in retries.
  • “Dataclass or Pydantic for the model's JSON output?” Pydantic: it's untrusted input and needs runtime validation; a dataclass won't check anything.
  • “is vs ==?”, “shallow vs deep copy?”, “what does @ desugar to?”, “how do context managers guarantee cleanup?” Short, precise answers with a concrete example win.

How: gradually added type hints and ran mypy (whose core team Dropbox employed) across 4 million lines of server and desktop code.

Why this method: gradual typing let them add types file by file instead of a rewrite, and the payoff grows with codebase and team size.

TypedDict in, Pydantic out 🧰 Open source openai-python README

How: nested request parameters are typed as TypedDicts (you pass plain dicts, your editor checks the keys); responses come back as Pydantic models with helpers like to_json().

Why this method: requests stay cheap and JSON-native, while responses get validation, attribute access and autocomplete.

Type hints become tool schemas 🧰 Open source OpenAI Agents SDK: tools

How: @function_tool reads the function signature with Python's inspect module, parses the docstring with griffe and builds the JSON schema with Pydantic.

Why this method: one source of truth. The model sees exactly the argument names, types and descriptions your Python declares, and arguments are validated before your function runs.

A Rust core for validation 🧰 Open source Why use Pydantic?

How: Pydantic's validation logic lives in pydantic-core, implemented mostly in Rust, and it parses and validates JSON in one step.

Why this method: validating every model reply and request body stays cheap enough to do by default.

Check yourself

1. A call fails with 429 on 20% of attempts, independently. You allow 3 attempts in total. Roughly what fraction of calls still fail?
All three attempts must fail: 0.2³ = 0.008 = 0.8%. Expected attempts per call are 1 + 0.2 + 0.04 = 1.24. (Real failures are often correlated, which is exactly why backoff and jitter matter: retrying instantly into the same rate-limit window fails far more often than 20%.)
2. Users report that setting temperature=0 in your API doesn't make answers deterministic. Your code has t = req.temperature or 0.7. What's going on?
a or b returns b whenever a is falsy, and 0, 0.0, "" and [] are all falsy. When zero or empty is a meaningful value, test for None explicitly. (Even at temperature 0, outputs aren't guaranteed identical, but this bug was sending 0.7.)
3. The model returns JSON like {"label": "refund", "confidence": 0.93}, and sometimes invents labels. Which Python type should hold it?
Model output is untrusted input. Dataclasses and TypedDicts are only hints: nothing checks them at runtime. Pydantic validates on the way in, raises a ValidationError you can catch and retry on, and the same class can generate the JSON schema you send as a structured-output format.
📝 TL;DR
  • Everything is an object; syntax calls dunder methods; variables are luggage tags, not boxes.
  • Mutable defaults, shallow copies, late-binding closures and or-defaults are the bugs that reach production. None sentinels and is None fix most of them.
  • Decorators wrap calls (retry, time, cache, trace): use functools.wraps, retry only retryable errors with backoff + jitter, mind the order, and remember the SDKs already retry twice.
  • Dataclasses inside, TypedDicts for request dicts, Pydantic at every boundary; run a type checker.
