Phase P · Lesson 7

NumPy & pandas for AI engineers

Embeddings are matrices and eval results are tables. Two libraries turn “loop over a million things in Python” into one line that runs hundreds of times faster, and turn a pile of JSONL logs into the chart that decides which prompt ships.

🧰 You'll need (quick reminders)
  • Embeddings are vectors; cosine similarity = dot product of two vectors divided by their lengths, 1 = same direction (Lesson 2.1).
  • Python floats in lists cost ~32 bytes each; a NumPy float32 costs 4 (Lesson P.5).
  • Evals: run a fixed set of questions through your system and score each answer (Lesson 5.1).
  • JSONL: a text file with one JSON object per line, the usual format for logs and eval results.
🎯 Hook

In 2020 the core NumPy developers described their library in Nature. Their examples of what it had powered: the software stack behind the first detection of gravitational waves and the first image of a black hole, where NumPy arrays held the data at every step from raw signal through calibration to the final image.

The same few ideas, arrays of one type, operations on whole arrays at once, and broadcasting, are what run your vector search prototype, your embedding dedup job and your eval notebook. Learn them once and you'll read every AI codebase faster, because PyTorch tensors, pandas columns and vector-database clients all speak NumPy.

Numbers first: a loop vs one line

Score one query against 10,000 normalized 384-dimension embeddings (3.84 million multiply-adds), measured on an Apple-silicon laptop with Python 3.13 and NumPy 2.5:

HowTimePer multiply-add
Pure Python: nested for loops over lists74 ms~19 ns
Python loop over rows, np.dot per row4.5 ms~1.2 ns
One matrix-vector product: emb @ query0.08 ms~0.02 ns

At 1 million embeddings the one-liner took 21 ms; the pure-Python loop would take about 7 s. That gap is the difference between a search endpoint and a coffee break. Your machine's numbers will differ; the ratios (roughly 100× to 1,000×) are typical.

Why NumPy is fast: one type, one block, one C loop

A NumPy array (ndarray) is a single block of memory holding numbers of one dtype (data type: float32, int64, bool…) plus a shape, like (10_000, 384): 10,000 rows of 384 columns. A Python list of floats is a list of pointers to separate float objects scattered in memory.

When you write emb @ query, NumPy runs one compiled loop over raw numbers (for matrix products, an optimized BLAS library that uses SIMD instructions and several cores). The Python interpreter does its slow work, figuring out types, unboxing objects, bounds checks, once per operation instead of once per number. Writing code as whole-array operations instead of Python loops is called vectorization.

  • dtype matters: np.array([0.1, 0.2]) is float64 by default. Embeddings rarely need it: float32 halves memory and is usually faster. Convert once with .astype(np.float32).
  • Axis: axis=1 means “along each row” (across columns); emb.sum(axis=1) gives one number per row.

Broadcasting: arithmetic between different shapes

Broadcasting is NumPy's rule for combining arrays of different shapes without copying. Compare shapes from the right; two dimensions are compatible when they're equal, or one of them is 1, and a size-1 dimension is stretched to match.

ExpressionShapesResult
normalize rows: emb / norms(N, d) and (N, 1)(N, d): each row divided by its own length
subtract the mean vector: emb - emb.mean(axis=0)(N, d) and (d,)(N, d)
forgot keepdims: emb / np.linalg.norm(emb, axis=1)(N, d) and (N,)error, unless N happens to equal d
labels minus predictions: y - p(N,) and (N, 1)(N, N): silently, a huge matrix of every pair

The last row is the classic bug: a column from one place has shape (N, 1), a vector from another has (N,), and the “error” you average is meaningless (and N × N can exhaust memory at N = 100,000). Print .shape whenever you combine arrays from different sources.

The AI engineer's one-liners

emb = emb / np.linalg.norm(emb, axis=1, keepdims=True)   # unit-length rows, once at index time
scores = emb @ (q / np.linalg.norm(q))                       # cosine similarity to every chunk
top = np.argpartition(-scores, k)[:k]                        # k best, unordered, O(N)
top = top[np.argsort(-scores[top])]                          # sort just those k

After normalizing, cosine similarity is the dot product, so one matrix-vector product scores everything. np.argsort sorts all N scores (about N log N work); np.argpartition only guarantees the k smallest come first (linear time), which is all top-k needs. On 1M scores we measured 7 ms vs 89 ms. This brute-force (exact) search is what vector databases replace with approximate indexes once N gets large (Lesson 2.2).

💡 Big idea Think in whole arrays and whole columns, not in items. If you're writing a Python for loop over embeddings, rows of results or tokens' scores, there's almost always one NumPy or pandas operation that does the same thing in compiled code, with less code and fewer bugs. Loops are for the few things that genuinely depend on the previous step.
🧠 Analogy: paying a cashier per item vs per cart

A Python loop is a shop where every single item goes to the cashier separately: scan, check the price, take payment, print a receipt, next. NumPy puts the whole cart through once: one transaction, then a conveyor belt that scans everything without stopping. Broadcasting is a “10% off everything” sign: you don't write a discount on each item, the rule stretches over the whole cart.

What you should see: at a few thousand embeddings everything is “fast enough”, which is why loops survive in prototypes. Past 100,000 the Python loop leaves any latency budget, the matrix product stays in milliseconds, and top-k selection starts to matter (argsort costs more than the scoring itself at 10M). Past tens of millions, even the one-liner is too slow and too big for one machine's RAM, and you move to an approximate index (Lesson 2.2).

pandas: eval results are a table

pandas gives you the DataFrame: a table of named, typed columns (each column is essentially a NumPy-style array), with an index for rows. Every eval run you do produces rows like {run, question_id, category, correct, latency_ms, cost_usd}; a DataFrame lets you ask the questions that matter in one line each:

Questionpandas
Load a JSONL logpd.read_json("runs.jsonl", lines=True)
Keep only some rowsdf[df["category"] == "refunds"] (a boolean mask)
Accuracy per prompt versiondf.groupby("run")["correct"].mean()
Accuracy per category × versiondf.pivot_table(index="category", columns="run", values="correct")
Add question metadata (difficulty)df.merge(questions, on="qid", how="left")
Save for later, small and typeddf.to_parquet("runs.parquet")

groupby splits rows into groups by a column's values, applies an aggregate (mean, sum, count) to each group, and combines the results. merge is a SQL-style join on a key. pivot_table turns one column's values into column headers. Parquet is a compressed, columnar file format that keeps dtypes, so it loads much faster than JSONL or CSV for big logs.

pandas 3.0 (January 2026) made Copy-on-Write the default: every indexing result behaves as a copy, so chained assignment like df[df.x > 0]["y"] = 1 never modifies df (use df.loc[df.x > 0, "y"] = 1). It also infers a dedicated str dtype for text columns instead of object.

✏️ Worked example: the average that lies

Two prompt versions, 24 questions each (8 billing, 8 shipping, 8 refunds):

  • Overall: v1 = 18/24 = 75.0%, v2 = 20/24 = 83.3%. Ship v2?
  • By category: billing 62.5% → 100%, shipping 75% → 100%, but refunds 87.5% → 50% (7/8 → 4/8).
  • v2 got better on easy, high-volume topics and much worse on the one where mistakes cost money. The average hid it, because +5 wins elsewhere outweighed −3 losses on refunds.
  • One pivot_table shows it; a pivot by question ID names the four refund questions that flipped from right to wrong (r2, r4, r6, r7): your next debugging session.

Eight questions per slice is also small: a 3-question swing is within noise for some decisions. Lesson 5.11 covers how many cases you need before trusting a difference.

Polars, and plotting

Polars is a DataFrame library whose core is written in Rust, with a lazy API: you describe the whole query (.lazy() … .collect()) and it optimizes and runs it at once, in parallel. It's a strong choice for multi-GB logs that make pandas slow. The concepts (filter, group by, aggregate, join) transfer directly; the syntax is expression-based (pl.col("correct").mean()).

For charts, df.plot() (matplotlib under the hood) is enough for a notebook: accuracy per run as bars, latency as a histogram. For dashboards that others read, eval tools (Lesson 5.6) plot these for you, but they're built on exactly these group-bys.

🧰 Tools you'll actually use

NumPy (arrays, @, argpartition, np.load(..., mmap_mode="r")), pandas (+ pyarrow for Parquet), Polars, matplotlib, and the libraries that hand you NumPy arrays: sentence-transformers, Hugging Face datasets, vector-database clients. Tested with NumPy 2.5, pandas 3.1 and Polars 2.1 on Python 3.13.

import numpy as np

rng = np.random.default_rng(0)
emb = rng.standard_normal((100_000, 384)).astype(np.float32)   # (N, d) chunk embeddings
query = rng.standard_normal(384).astype(np.float32)             # (d,)

# Normalize every row once; broadcasting divides (N, d) by (N, 1)
emb /= np.linalg.norm(emb, axis=1, keepdims=True)
query /= np.linalg.norm(query)

scores = emb @ query                        # (N,) cosine similarities, one line

k = 5
top = np.argpartition(-scores, k)[:k]       # the k best, unordered: O(N)
top = top[np.argsort(-scores[top])]         # sort only those k
print(top, scores[top].round(3))

# Many queries at once: (Q, d) @ (d, N) -> (Q, N)
queries = emb[:3] + 0.01                    # 3 fake queries
sims = queries @ emb.T
print(sims.shape, sims.argmax(axis=1))      # (3, 100000) [0 1 2]

# The silent broadcasting bug: (N,) minus (N, 1) is (N, N), not (N,)
a = np.zeros(4); b = np.zeros((4, 1))
print((a - b).shape)                        # (4, 4)
import pandas as pd

runs = pd.read_json("eval_runs.jsonl", lines=True)      # one JSON object per line
questions = pd.read_json("questions.jsonl", lines=True)
runs.to_parquet("eval_runs.parquet")                    # columnar, typed, compressed (needs pyarrow)
runs = pd.read_parquet("eval_runs.parquet")

# 1. Headline per run: accuracy, median latency, total cost
summary = runs.groupby("run").agg(
    accuracy=("correct", "mean"),
    p50_latency_ms=("latency_ms", "median"),
    cost_usd=("cost_usd", "sum"),
    n=("qid", "count"),
)
print(summary.round(3))

# 2. The slice view: category × run (the regression hides here)
print(runs.pivot_table(index="category", columns="run", values="correct", aggfunc="mean").round(3))

# 3. Join question metadata, then slice by difficulty
merged = runs.merge(questions, on="qid", how="left", validate="many_to_one")
print(merged.groupby(["difficulty", "run"])["correct"].mean().unstack().round(3))

# 4. Which questions flipped from right to wrong?
wide = runs.pivot(index="qid", columns="run", values="correct")
print(wide[(wide["prompt_v1"] == 1) & (wide["prompt_v2"] == 0)].index.tolist())   # ['r2', 'r4', 'r6', 'r7']
import polars as pl

runs = pl.read_ndjson("eval_runs.jsonl")
summary = (
    runs.lazy()                                   # build a query plan, run it once
    .group_by("run", "category")
    .agg(pl.col("correct").mean().alias("accuracy"), pl.col("cost_usd").sum())
    .sort("run", "category")
    .collect()
)
print(summary)

validate="many_to_one" makes the merge raise an error if a question ID appears twice in the metadata, instead of silently duplicating eval rows and skewing every average.

🚀 Startup vs big tech

Week one

Under a few hundred thousand chunks, a normalized float32 NumPy matrix and argpartition is a perfectly good vector search: exact, zero infrastructure, milliseconds. Eval results go to JSONL, a notebook with three group-bys and one pivot table decides what ships.

At scale

Vectors move to an ANN index or vector database (Lessons 2.2–2.3); NumPy stays for offline jobs (dedup, clustering, recall checks against exact search). Eval logs land as Parquet in a warehouse, sliced with Polars, Spark or SQL, and dashboards show accuracy by slice, not just the average.

🎤 Interview angle

“Implement semantic search over 200,000 chunk embeddings, no vector database.” A senior answer:

  • Stores embeddings as one float32 (N, d) matrix, rows normalized once at index time, so cosine = dot product.
  • Scores with one matrix-vector product and selects with argpartition, then sorts only k; batches queries as (Q, d) @ (d, N).
  • Gives numbers: 200k × 768 × 4 B ≈ 614 MB of RAM; a few ms per query; when to switch to ANN (latency budget, N in the tens of millions, filtering needs).
  • Mentions pitfalls: float64 by accident, (N,) vs (N, 1) broadcasting, not normalizing the query, memory-mapping for multiple workers (Lesson P.5).
🏭 In the real world
Arrays behind discoveries 🧪 Research · 2020 Array programming with NumPy (Nature)

How: the paper explains NumPy's core ideas (dtype, shape, strides, vectorized operations, broadcasting) and how other libraries build on them.

Why this method: one shared array format let physics, astronomy and machine-learning tools interoperate; it was part of the stack for the gravitational-wave detection and the first black-hole image.

Copy-on-Write and a real string type 🧰 pandas 3.0 · 2026 What's new in pandas 3.0.0

How: every indexing result now behaves as a copy, chained assignment never works (so the old SettingWithCopyWarning is gone), and text columns get a dedicated str dtype by default.

Why this method: the old “sometimes a view, sometimes a copy” behaviour caused silent bugs and defensive .copy() calls; consistent semantics make data code predictable.

A Rust DataFrame engine with a query planner 🧰 Polars Polars user guide

How: a core written from scratch in Rust, a lazy API that optimizes the whole query before running it, streaming for data bigger than memory, and first-class I/O for Parquet, cloud storage and databases.

Why this method: big eval and log tables are scan-filter-group-by jobs, exactly what a parallel, columnar engine is built for.

Check yourself

1. You hold 2 million chunk embeddings of 768 dimensions as a NumPy array. How much RAM as float32, and as the float64 you get from np.array(list_of_floats)?
2,000,000 × 768 = 1.536 billion numbers. × 4 bytes = 6.1 GB; × 8 bytes = 12.3 GB. Convert with .astype(np.float32) (or np.asarray(x, dtype=np.float32)) right after loading.
2. Your eval script computes np.mean(np.abs(labels - preds)). It runs out of memory (or, on a smaller test set, returns a strange number). labels.shape is (100000,) and preds.shape is (100000, 1). What happened?
(N,) is treated as (1, N); against (N, 1) both stretch to (N, N): 10 billion elements (80 GB as float64). Fix with preds.ravel() or preds[:, 0], and assert shapes before arithmetic.
3. A prompt change raises overall eval accuracy from 75% to 83%. What's the most useful next pandas step before shipping?
An average can rise while an important slice collapses (here refunds 87.5% → 50%). pivot_table(index="category", columns="run", values="correct") shows it; a pivot by question ID names the regressions to fix.
📝 TL;DR
  • A NumPy array = one dtype, one shape, one memory block; operations run as compiled loops: 100–1,000× faster than Python loops.
  • Use float32 for embeddings; normalize rows once; scores = emb @ q; top-k with argpartition.
  • Broadcasting: dims match when equal or 1. Print shapes; (N,) vs (N, 1) silently makes N × N.
  • pandas for eval results: read_json(lines=True), groupby, pivot_table, merge(validate=…), Parquet. Slice before you trust an average.
  • Polars when logs get big; pandas 3.0 uses Copy-on-Write: use .loc for assignment.
