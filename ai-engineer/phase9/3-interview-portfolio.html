Phase 9 · Lesson 3

The senior AI engineer interview & portfolio

Interviews and portfolios test the same thing: can you take a fuzzy AI problem, measure it, make a trade-off with numbers, and explain it? Here's what gets evaluated, how to answer, and which projects prove it.

🧰 You'll need (quick reminders)
  • The AI design framework: requirements with a quality bar and risk tier → estimates → simplest architecture → evals → safety → rollout (Lesson 9.1).
  • Outcome metrics: true resolution and cost per resolved task, not deflection (Lesson 9.2).
  • Golden sets, LLM-as-judge and RAG metrics such as recall@k and faithfulness (Lessons 5.1, 5.3, 5.4).
  • When to fine-tune versus prompt or retrieve (Lesson 7.1).
🎯 Hook

Hamel Husain describes working on Lucy, the AI assistant inside Rechat, a real-estate software product. Prompt engineering made fast early progress, then plateaued: fixing one failure caused another, nobody could see quality beyond vibe checks, and the prompts grew long and unwieldy. The breakthrough wasn't a new model. It was a systematic evaluation process: unit-test-style assertions, logged traces, human and model review, then fast iteration against the numbers.

His conclusion: unsuccessful AI products almost always share one root cause, a failure to build robust evaluation systems. That story (problem, measurement, fix, number) is also the shape of every strong interview answer and every strong portfolio project.

Numbers first: what a loop looks like

Processes differ by company and team, so read each company's published guide. Two that publish theirs:

  • OpenAI's interview guide: skills-based assessments whose format varies by team (pair coding, take-home projects, technical tests), then final interviews of typically 4–6 hours with 4–6 people over 1–2 days. Whether AI tools are allowed varies by interview and is stated in the prep materials.
  • Anthropic's guidance on candidates' AI use: use Claude to prepare and to polish what you wrote yourself; complete take-homes and live interviews without AI unless they say otherwise.

🧠 Analogy: a doctor's case presentation

A junior doctor lists symptoms. A senior one presents a case: what they suspected, which test they ordered to tell the possibilities apart, what the result showed, the treatment and its risks, and what they'll watch for next. Interviewers listen for that structure. “I'd use a vector database” is a symptom list; “recall@5 was 0.71, so the problem was retrieval, not generation; hybrid search took it to 0.78” is a case presentation.

Common question types, with model answers

✏️ Worked example: “Our RAG assistant gives wrong answers. How would you debug it?”

Clarify: “Which questions, how often, and how do we know they're wrong? Do we have traces?”

Split the problem: “For 50 failing questions, check whether the right passage was in the retrieved chunks. If not, it's retrieval; if yes, it's generation.” Suppose 34 of 50 had the answer missing from the context: 68% retrieval failures.

Options for retrieval: chunking that keeps facts together, hybrid search for exact terms, a reranker, query rewriting, metadata filters (Lessons 3.3, 3.4, 4.1, 2.4). For generation: context ordering, instructions to cite or abstain (Lesson 3.5).

Measure: build a 200-question set with expected sources; track recall@5 per change: baseline 0.71 → hybrid 0.78 → + reranker 0.83. Then end-to-end correctness and faithfulness, so a retrieval gain isn't undone in generation.

Risks: overfitting to the eval set (keep a held-out slice), more latency from the reranker (~150 ms), regressions on other question types (track per category).

How precise is 0.83 on 200 questions? Standard error = √(p(1 − p) ÷ n) = √(0.83 × 0.17 ÷ 200) ≈ 0.027, so a 95% interval is about ± 5 points. Gains of 7 and 5 points are believable but not huge; say so, and compare configurations on the same questions (a paired test is more sensitive than comparing two intervals). Writing that sentence in a README is itself a senior signal.

How to write it up

  1. One-paragraph problem with who it's for and why it's hard.
  2. The headline number: baseline → final, on a named eval (“recall@5 0.71 → 0.83 on 200 questions”).
  3. An architecture diagram and the key decisions, each with the alternative you rejected and why.
  4. The eval method: how the set was built, how it's scored, judge calibration if you used one.
  5. Ablations, cost and latency: a table like the one above.
  6. Failure analysis: a categorised sample of what still goes wrong, with examples.
  7. What you'd do next, and how to run it in one command.

Then practise the 2-minute version out loud: it's what you'll say when an interviewer asks “tell me about a project”.

🧰 Tools you'll actually use

GitHub for the code and README; promptfoo, RAGAS, DeepEval or Inspect for the eval suite; Langfuse or similar for traces; Hugging Face Hub and Spaces to publish datasets, models and a demo; a short blog post or video for the write-up. A promptfoo eval over your own pipeline:

# promptfooconfig.yaml  ·  run with: npx promptfoo@latest eval
providers:
  - id: 'file://rag_app.py'        # your pipeline: def call_api(prompt, options, context) -> {"output": ...}
prompts:
  - '{{question}}'
tests:
  - vars: { question: 'How long do Plus members have to return an item?' }
    assert:
      - type: icontains
        value: '60 days'
      - type: llm-rubric
        value: 'Cites the returns policy and does not invent conditions'
  - vars: { question: 'What is the CEO salary?' }   # must abstain
    assert:
      - type: llm-rubric
        value: 'Declines or says the information is not available'
# rag_app.py: promptfoo calls this for every test case
from my_rag import answer          # retrieve → generate, returns text with citations

def call_api(prompt, options, context):
    return {"output": answer(prompt)}

Commit the eval results with the code. A portfolio repo whose README numbers can be reproduced with one command is rare, and reviewers notice.

🚀 Startup vs big tech

Startup interviews

Often a paid trial or take-home: build something end to end in a few days. Founders ask product questions (“would users trust this?”, “what does it cost per customer?”). A shipped project with real users and numbers is the strongest card; speed and taste matter as much as depth.

Big-tech interviews

Structured loops with rubrics and levelling: coding, system design, ML/LLM depth, behavioural. Senior levels are decided by scope and judgement in the design and behavioural rounds. Expect the project deep-dive to probe baselines, ablations and what you'd do differently, for an hour.

🎤 Interview angle

The meta-skills that score in every round:

  • Think out loud and state assumptions with numbers (“assume 5,000 tokens per request”).
  • Compare, then choose: two options, the trade-off, a decision, and what would change your mind.
  • Bring up evals and failure modes before you're asked. It's the single clearest senior signal in AI rounds.
  • Say “I don't know, here's how I'd find out” rather than bluffing about a model, a paper or a benchmark.
  • Go deep on one project rather than skimming five. Know its numbers by heart.
🏭 In the real world
A published interview process 🏢 OpenAI Interview guide

How: résumé review, introductory calls, skills-based assessments whose format varies by team (pair coding, take-homes, technical tests), then 4–6 hours of final interviews with 4–6 people over 1–2 days.

Why this method: the guide says interviews aim to understand how you approach problems, make decisions and communicate your reasoning, which is the spine this lesson teaches.

Clear rules on AI use 🏢 Anthropic · 2025 Guidance on candidates' AI usage

How: candidates are encouraged to use Claude to prepare and to refine drafts they wrote themselves, but not to invent experiences; take-homes and live interviews are done without AI unless stated.

Why this method: assessments are meant to show how you think in real time, so always ask what's allowed for each stage.

Evals as the engine of improvement 🏢 Hamel Husain · 2024 Your AI Product Needs Evals

How: the Lucy case study: scoped unit tests and assertions, logged traces, human and model evaluation, and a fast loop of changes measured against them.

Why this method: it broke a prompt-engineering plateau; the same eval-first story is what a portfolio project should tell.

A year of building with LLMs 🏢 Practitioners · 2024 What We Learned from a Year of Building with LLMs

How: six practitioners (Eugene Yan, Bryan Bischof, Charles Frye, Hamel Husain, Jason Liu, Shreya Shankar) wrote up tactical, operational and strategic lessons from shipping LLM products.

Why this method: it's close to a list of senior interview topics, written by people who hire for them; reading it is excellent interview prep.

The role gets a name 📜 History · 2023 swyx: The Rise of the AI Engineer

How: a June 2023 essay describing a new role building products on top of foundation models, distinct from ML research and ML engineering.

Why this method: it framed product-specific data and evals as the AI engineer's job, which is still what interviews for the role probe.

🤯 Fun fact · an afternoon instead of five years

swyx's 2023 essay argued that a wide range of AI tasks that took 5 years and a research team in 2013 needed only API docs and a spare afternoon in 2023. It also quoted Andrej Karpathy predicting there would probably be significantly more AI engineers than ML engineers, and that you could be quite successful in the role without ever training anything.

Check yourself

1. Your portfolio RAG eval has 50 questions. Version 2 scores 41/50 (82%) and version 1 scored 39/50 (78%). What can you honestly claim?
Standard error ≈ √(0.8 × 0.2 ÷ 50) ≈ 0.057, so ± 1.96 × 5.7 ≈ ± 11 points. A 4-point gap is well inside the noise. Grow the set (200+), and compare on the same questions: which ones flipped from wrong to right, and which the other way?
2. Ten minutes into a design round (“build an AI assistant for our sales team”), you realise you've been comparing vector databases. What's the best recovery?
Interviewers forgive a detour; they score whether you can steer. Requirements, quality bar and risk drive every later choice (Lesson 9.1), and the vector DB is rarely the hard part.
3. You have time for one more portfolio project. Which adds the most senior signal?
It proves a decision (customise only when it pays), a method (distillation, Lesson 7.2) and measurement (same eval, cost, latency). The demo app shows little that a tutorial doesn't; the unmeasured fine-tune shows activity, not judgement.
📝 TL;DR
  • Loops typically mix practical coding, AI system design, LLM depth, a project deep-dive and product/behavioural rounds; read each company's published guide and AI-use rules.
  • Answer with one spine: clarify → options → choose with numbers → measure → risks. Bring up evals and failure modes unprompted.
  • Build 3–4 deep projects that cover the skills map: RAG with evals and ablations, a safe agent, a measured fine-tune or distillation, a production write-up.
  • Publish the numbers (baseline → final, with uncertainty), the failures, and one-command reproducibility.
