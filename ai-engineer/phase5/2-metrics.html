Phase 5 · Lesson 2

Metrics: from exact match to semantic similarity

Before you reach for an LLM judge, know what cheap metrics can and can't tell you. Some are perfect for their job; some will confidently reward the wrong answer.

🧰 You'll need (quick reminders)
  • An eval = inputs + a grading method + a tracked score; small evals have wide error bars (Lesson 5.1).
  • Embeddings map text to vectors; cosine similarity near 1 means “similar meaning” (Lesson 2.1).
  • Structured output: asking the model for JSON that matches a schema (Lesson 1.3).
🎯 Hook

When OpenAI introduced Codex in 2021, the obvious way to score generated code was BLEU, a metric that counts how many word sequences the output shares with a reference solution. They checked it. The BLEU scores of correct and incorrect programs overlapped heavily, and wrong programs often scored higher than correct ones that were written differently.

So they threw it out and ran the code instead: 164 hand-written problems, each with unit tests, scored by whether the code passes. That benchmark, HumanEval, and its metric, pass@k, became the standard way to measure code models. The lesson generalizes: measure the property you care about, not how similar the words look.

Question: “How long do I have to return my boots?” Reference answer: “Refunds are available within 30 days of delivery.” Here's what four common metrics say (computed by this page's code; you can recompute them below):

The correct paraphrase gets the lowest overlap scores. The two wrong answers get the highest, because they share almost every word with the reference. Changing one number or adding “not” flips the meaning and barely moves the metric.

💡 Big idea Every metric measures one specific property. Exact match measures identical strings; overlap metrics measure shared words; embedding similarity measures “roughly the same topic”; unit tests measure “the code works”. Pick the metric whose property is your success criterion, and combine cheap checks so each covers another's blind spot. When none fits (open-ended quality), you need a judge (Lesson 5.3) or humans (5.8).
🧠 Analogy: grading a maths exam

A teacher could grade by comparing each answer sheet to the model solution word by word (overlap metrics): the student who copies the solution's layout but gets the wrong number scores well, and the one who solved it a smarter way scores badly. Or the teacher could just check the final number (exact match on the extracted answer) and, for proofs, check that each step is valid (unit tests, a judge). Good graders check what matters.

✏️ Worked example: token F1 by hand

Reference, normalized: refunds are available within 30 days of delivery (8 words).

  • Candidate “Refunds are available within 60 days of delivery”: 7 of its 8 words are in the reference, so precision = 7/8 and recall = 7/8, F1 = 0.875. Wrong answer, great score.
  • Candidate “You have 30 days after it arrives to send it back for your money” (14 words): only “30” and “days” match. Precision = 2/14 = 0.143, recall = 2/8 = 0.25, F1 = 2 × 0.143 × 0.25 ÷ (0.143 + 0.25) = 0.18. Right answer, terrible score.
  • A task-specific check, “the answer contains the number 30 and no other day count”, gets both right in one line of code.

Classification metrics: when the output is a label

Many LLM features are classifiers in disguise: “is this ticket urgent?”, “which tool?”, “is this answer safe?”. Grade them like classifiers (Lesson 5.9 covers evals for each task type in depth). Precision = of the cases you flagged, how many were right. Recall = of the cases that should be flagged, how many you caught.

✏️ Worked example: an escalation detector

1,000 conversations; 50 truly need a human. Your LLM flags 80, of which 40 really needed one.

  • Precision = 40 ÷ 80 = 50% (half the hand-offs waste an agent's time).
  • Recall = 40 ÷ 50 = 80% (10 angry customers were never handed off).
  • Accuracy = (40 + 910) ÷ 1,000 = 95%, which sounds great and hides both problems. With rare classes, report precision and recall.

The full story (F1, thresholds, calibration) is in the Math for AI course: classification metrics.

pass@k: grading code by running it

For code, the ground truth is behaviour: run the generated function against unit tests. Models are random, so you sample several solutions. pass@k is the probability that at least one of k samples passes. Estimating it naively (generate exactly k, check if any passes) is very noisy, so Chen et al. (2021) generate n ≥ k samples, count the c that pass, and use an unbiased estimator:

pass@k = 1 − C(n − c, k) ÷ C(n, k)    (averaged over problems; C = “n choose k”)

It's the chance that a random set of k from your n samples contains no passing one, subtracted from 1. Plugging the pass rate into 1 − (1 − c/n)k looks equivalent, but the paper shows it underestimates.

✏️ Worked example: pass@5 from 10 samples

n = 10 samples, c = 3 pass, k = 5.

  • C(7, 5) = 21 ways to pick 5 failing samples; C(10, 5) = 252 ways to pick any 5.
  • pass@5 = 1 − 21 ÷ 252 = 0.917.
  • The naive 1 − (1 − 0.3)5 = 0.832: almost 9 points lower for this problem.

Real numbers: Codex-12B solved 28.8% of HumanEval with one sample (pass@1) and 70.2% when allowed 100 samples (pass@100). pass@1 matters when a user takes the first answer; pass@k matters when you can test candidates automatically and keep one that works.

🧰 Tools you'll actually use

Hugging Face evaluate (ROUGE, BLEU, SQuAD EM/F1), sacrebleu for standard BLEU, sentence-transformers for embedding similarity, Pydantic or jsonschema for output validation, and OpenAI's human-eval harness for pass@k. Eval tools wrap the same checks: promptfoo has is-json, regex, rouge-l, similar and javascript/python assertions.

import evaluate, numpy as np
from sentence_transformers import SentenceTransformer, util
from pydantic import BaseModel, ValidationError

ref, out = "Refunds are available within 30 days of delivery.", model_answer

rouge = evaluate.load("rouge")
print(rouge.compute(predictions=[out], references=[ref])["rougeL"])

emb = SentenceTransformer("all-MiniLM-L6-v2")           # small, local embedding model
print(util.cos_sim(emb.encode(out), emb.encode(ref)).item())

class Refund(BaseModel):                                  # task-specific check: valid, typed JSON
    order_id: str
    amount: float
def valid_refund(json_text: str) -> bool:
    try: Refund.model_validate_json(json_text); return True
    except ValidationError: return False

def pass_at_k(n, c, k):                                 # Chen et al. 2021, numerically stable form
    if n - c < k: return 1.0
    return 1.0 - np.prod(1.0 - k / np.arange(n - c + 1, n + 1))

print(pass_at_k(10, 3, 5))   # 0.9167

Run untrusted generated code only in a sandbox (a container with no network and a time limit); the human-eval harness ships with execution disabled until you opt in for that reason.

🚀 Startup vs big tech

Week one

Code checks for everything with a rule (JSON valid, required fact present, length, no PII), exact match on extracted fields, and one LLM judge for overall quality. Skip BLEU and ROUGE unless you're doing translation or must match a published benchmark.

At scale

Layered graders per feature: deterministic checks gate every commit, execution-based harnesses for code and SQL in sandboxes, embedding and judge scores tracked as trends, and every metric validated against human labels before anyone trusts its dashboard.

🎤 Interview angle

“Would you use ROUGE to evaluate your summarization feature?” A senior answer:

  • Explains what ROUGE measures (shared words with a reference) and why that's not quality for abstractive summaries.
  • Proposes checks for what actually matters: faithfulness to the source (no invented facts), coverage of key points, length and format rules.
  • Uses code checks where possible, an LLM judge with a rubric for the rest, and validates both against human ratings.
  • Keeps ROUGE only as a cheap trend line or to compare with published numbers.
🏭 In the real world
Execution-based grading for code 🧪 OpenAI · 2021 Evaluating Large Language Models Trained on Code (HumanEval)

How: 164 hand-written problems with an average of 7.7 unit tests each; pass@k estimated from n = 200 samples per problem with the unbiased formula.

Why this method: BLEU didn't track functional correctness; running the code does.

Exact match and F1 for reading comprehension 🧪 Stanford · 2016 SQuAD: 100,000+ Questions for Machine Comprehension

How: answers are spans of a Wikipedia paragraph; predictions are scored by exact match and by word-overlap F1, ignoring punctuation and articles.

Why this method: for short extractive answers, overlap is a fair proxy, and it's free to compute at scale.

Verifiable instructions 🧪 Google · 2023 Instruction-Following Evaluation (IFEval)

How: about 500 prompts using 25 kinds of instructions that code can verify (“more than 400 words”, “mention AI at least 3 times”).

Why this method: human ratings are slow and LLM judges can be biased; checkable rules make instruction following reproducible.

Embeddings instead of exact words 🧪 Research · 2019 BERTScore

How: matches each candidate token to its most similar reference token using contextual embeddings, then combines into precision, recall and F1.

Why this method: across 363 translation and captioning systems it correlated better with human judgments than overlap metrics, because paraphrases still match.

🤯 Fun fact · why HumanEval was written by hand

The Codex team wrote all 164 HumanEval problems by hand because their model was trained on a big slice of GitHub, which already contains solutions to most public puzzle sets; they note more than ten public repositories with Codeforces solutions. A benchmark your model has seen in training measures memory, not skill. That's why your own eval set should stay out of anything you train or few-shot on.

Check yourself

1. A coding model produced n = 5 samples for a problem and c = 1 passed. What is pass@2?
pass@2 = 1 − C(4, 2) ÷ C(5, 2) = 1 − 6 ÷ 10 = 0.4: a random pair contains the one passing sample 4 times in 10. (The naive 1 − 0.8² = 0.36 underestimates.)
2. Your support bot's ROUGE-L against reference answers rose from 0.41 to 0.52 after a prompt change. What can you conclude?
ROUGE measures overlap, not truth. The new prompt might just copy the reference style, or be longer. Look at a sample of changed answers and use task checks or a calibrated judge for correctness.
3. Your feature extracts invoice fields (number, date, total) into JSON. Best primary metric?
There's a single right value per field, so check it exactly, after normalizing harmless differences. Per-field scores tell you which field is failing (often dates). Overlap and embeddings would reward a JSON with the wrong total.
📝 TL;DR
  • Each metric measures one property: pick the one that matches your success criterion.
  • EM and task checks (schema, regex, unit tests, SQL results) are cheap and exact: use them wherever a rule exists.
  • BLEU/ROUGE/F1 reward shared words: they punish paraphrases and reward wrong answers that copy wording.
  • Embedding similarity handles paraphrase but misses numbers and negation.
  • Code: run it. pass@k = 1 − C(n−c, k)/C(n, k), estimated from n ≥ k samples.
