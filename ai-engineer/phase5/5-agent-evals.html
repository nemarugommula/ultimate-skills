Phase 5 · Lesson 5

Evaluating agents: trajectories, tool calls & benchmarks

An agent doesn't produce one answer; it takes a dozen actions in a world. Grade where it ended up, how it got there, what it cost, and whether it does it every time.

🧰 You'll need (quick reminders)
  • An agent is an LLM in a loop: it picks a tool (search, an API, a shell), sees the result, and decides the next step until the task is done. Phase 6 builds them (Lesson 6.1); here we learn to grade them.
  • Tool calls are structured requests like issue_refund(order_id=1234, amount=89) (Lesson 1.3).
  • pass@k = chance at least one of k attempts succeeds (Lesson 5.2); LLM judges grade open-ended output (5.3).
🎯 Hook

In 2024, Sierra built τ-bench (“tau-bench”): customer-service agents talk to a simulated user and use real-looking APIs for a retail shop or an airline, and succeed only if the database ends up in the right state. A GPT-4o function-calling agent solved 61% of retail tasks on a single try.

Then they ran each task 8 times. The share of tasks it solved all 8 times fell to about 25%. A support agent that handles your refund correctly on Monday and wrongly on Tuesday isn't a 61% agent. The authors introduced a metric for exactly this, pass^k, and it's now a standard way to report agent reliability.

Things that can be wrongThe answerEvery tool choice, every argument, the order, side effects, the final state, the final message

Errors compound, outputs vary run to run, and the agent changes the world as it goes. So you can't grade an agent by reading its last message: “Your refund has been issued!” is worthless if no refund exists in the database.

💡 Big idea Grade agents in layers. Outcome first: inspect the final state of a sandboxed environment (the database row exists, the tests pass). Then the path: right tools, right arguments, required steps in the right order, nothing forbidden. Then efficiency and reliability: steps, tokens and dollars per success, and pass^k across repeated trials. Each layer catches failures the others miss.
🧠 Analogy: the driving test

The examiner checks that you arrived at the destination (outcome). They also watch how you drove: a red light run on the way fails you even if you arrived (trajectory). They notice if you took 40 minutes for a 10-minute route (efficiency). And a licence means you can do it every time, not once in three tries (pass^k). An agent eval is a driving test, run hundreds of times.

Anthropic's agent-eval guidance adds a caution: don't over-specify the path. Capable models find valid routes you didn't anticipate; in one case a model “failed” a τ²-bench task by finding a policy loophole that was actually better for the user. Grade required steps and forbidden actions, not the exact sequence, unless the sequence itself is the requirement.

      Reliability: pass@k vs pass^k

      Run each task n times and count the c successes. Two questions, two metrics, both with unbiased estimators:

      pass@k = 1 − C(n − c, k) ÷ C(n, k)   (at least one of k succeeds)   |   pass^k = C(c, k) ÷ C(n, k)   (all k succeed)

      pass@k rises with k: more shots on goal. Useful when a cheap verifier can pick the winner (code with tests). pass^k falls with k: it's the reliability a user experiences when they come back again and again. For customer-facing agents, pass^k is the honest number.

      ✏️ Worked example: 8 trials, 6 successes
      • pass^3 = C(6, 3) ÷ C(8, 3) = 20 ÷ 56 = 0.36. pass@3 = 1 − C(2, 3) ÷ C(8, 3) = 1 − 0 = 1.0 (you can't pick 3 failures from 2).
      • If every trial were an independent 75% coin, pass^3 would be 0.75³ ≈ 0.42 (Anthropic's example).
      • Why τ-bench fell from 61% to about 25% at k = 8, not to 0.618 ≈ 2%: tasks differ. Some tasks the agent always solves; others it solves now and then. pass^k separates consistently solved tasks from sometimes solved ones, which one average hides.

      Sandboxes: where agent evals run

      Agent evals need an environment that is realistic, isolated and reset for every trial: a container with the repo checked out (SWE-bench), a seeded database behind mock APIs (τ-bench), self-hosted websites (WebArena), or a simulated user played by another LLM. Never run eval agents against production systems or real customer accounts. Reset state between trials, or one run's leftovers will pass or fail the next. Record the full transcript (every message, tool call and result): it's how you debug failures and catch graders that are wrong.

      # Inspect: grade the final state in a sandbox, 5 trials per task.  Run: inspect eval fix_bug.py --model <provider/model>
from inspect_ai import Task, task
from inspect_ai.agent import react
from inspect_ai.dataset import Sample
from inspect_ai.scorer import CORRECT, INCORRECT, Score, Target, accuracy, scorer, stderr
from inspect_ai.solver import TaskState
from inspect_ai.tool import bash, text_editor
from inspect_ai.util import sandbox

@scorer(metrics=[accuracy(), stderr()])
def tests_pass():
    async def score(state: TaskState, target: Target) -> Score:
        result = await sandbox().exec(["pytest", "-q", "tests/"])   # outcome, not the agent's claim
        return Score(value=CORRECT if result.success else INCORRECT, explanation=result.stdout[-500:])
    return score

@task
def fix_bug():
    return Task(
        dataset=[Sample(input="tests/test_dates.py fails. Fix the bug without editing the tests.")],
        solver=react(tools=[bash(), text_editor()]),
        scorer=tests_pass(),
        sandbox="docker",     # isolated container per sample
        epochs=5,             # repeated trials: compute pass@k and pass^k from the 5 results
    )

      🚀 Startup vs big tech

      Week one

      20–50 tasks from real failures, each with a seeded sandbox and a code check on the final state, plus two or three rules (required steps, forbidden calls). Run each task 3–5 times and report pass^k and cost per success, not just one pass rate. Read the transcripts of every failure.

      At scale

      Hundreds of environment-backed tasks per product, simulated users, nightly runs with many trials, trajectory and safety graders, cost and latency budgets as gates, and a regular audit of graders themselves, because a grading bug can hide or invent a regression.

      🎤 Interview angle

      “How would you evaluate a customer-support agent that can issue refunds?” A senior answer:

      • A sandboxed environment (seeded DB, mocked payment API, simulated customer) reset per trial; never production.
      • Outcome checks on the final state (exactly one refund, right order, right amount), plus trajectory rules (policy checked before refund, no refunds above a limit without approval).
      • Repeated trials and pass^k, because customers need consistency; cost and steps per successful task.
      • An LLM judge for the conversation, calibrated on human labels; transcript review of failures to find categories.
      • Public benchmarks (τ-bench) to shortlist models, the private eval to decide.
      🏭 In the real world
      Reliability over repeated trials 🏢 Sierra · 2024 τ-bench: Tool-Agent-User Interaction

      How: a language-model user simulator talks to the agent, which uses domain APIs under written policies; success = final database state matches the annotated goal; pass^k over i.i.d. trials.

      Why this method: database-state checks allow many valid conversations while staying objective; pass^k exposed that a 61% agent solved only about 25% of retail tasks in all 8 tries.

      Auditing a benchmark's own tasks 🏢 OpenAI · 2024 Introducing SWE-bench Verified

      How: 93 developers screened 1,699 SWE-bench samples for underspecified issues and unfair tests; 500 clean tasks became Verified.

      Why this method: bad tasks made models look worse than they were: GPT-4o resolved 33.2% on Verified vs 16% on the original.

      Outcomes, transcripts and grader bugs 🏢 Anthropic · 2026 Demystifying evals for AI agents

      How: defines tasks, trials, graders, transcripts and outcomes; combines code-based, model-based and human graders; reports pass@k and pass^k.

      Why this method: agents act over many turns and can find valid paths a fixed script would reject; grading the outcome and reading transcripts keeps the eval honest.

      Realistic web environments 🧪 CMU · 2023 WebArena

      How: fully working, self-hosted websites (e-commerce, forum, GitLab, CMS) in Docker; 812 long-horizon tasks checked for functional correctness.

      Why this method: reproducible environments make agent results comparable; the 14% vs 78% human gap showed how far agents were from reliable web work.

      🤯 Fun fact · the eval was the bug

      Anthropic reports that Claude Opus 4.5 initially scored 42% on CORE-Bench. A researcher then found grading problems: rigid matching that rejected “96.12” when expecting “96.124991…”, ambiguous task specs, and tasks that couldn't be reproduced exactly. After fixing them and using a less constrained scaffold, the score was 95%. Before you trust a low agent score, read the failed transcripts: some “failures” are the grader's.

      Check yourself

      1. Each task runs 10 times; one task succeeded 8 times. What's its pass^2?
      pass^2 = C(8, 2) ÷ C(10, 2) = 28 ÷ 45 = 0.62: the chance two randomly chosen trials both succeeded. (0.8² = 0.64 is the with-replacement approximation; 0.98 is pass@2.)
      2. Your agent's final message says “Refund issued!” in 95% of runs, but users keep complaining. What should the eval check first?
      Agents can claim success without achieving it. Outcome checks on the environment (the database, the payment mock's recorded calls) are the ground truth; the message is just text.
      3. A new prompt version raises pass@1 from 70% to 74%, but pass^5 drops from 52% to 38%. For a customer-facing agent, ship it?
      Customers repeat tasks; consistency is what they experience. A drop in pass^5 means more tasks now succeed only sometimes. Read those transcripts before shipping (and check error bars on both numbers).
      📝 TL;DR
      • Grade the outcome in a sandbox first (final state), then the trajectory (required steps, forbidden actions, arguments).
      • Don't over-specify the path: rules and in-order matches beat strict sequence equality.
      • Report reliability: pass@k = 1 − C(n−c, k)/C(n, k) rises with k; pass^k = C(c, k)/C(n, k) falls, and is what users feel.
      • Track steps, tokens and cost per successful task.
      • Benchmarks (SWE-bench Verified/Pro, τ-bench, GAIA, WebArena, Terminal-Bench) shortlist models; your own task eval decides. Read transcripts: graders have bugs too.
