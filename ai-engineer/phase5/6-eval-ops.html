Phase 5 · Lesson 6

Eval tooling, CI regression tests & online evals

Evals only protect you if they run on every change and keep watching after launch. This lesson turns your eval set into infrastructure: a regression gate in CI, and signals from real users in production.

🧰 You'll need (quick reminders)
  • Golden datasets, error bars and paired comparisons (Lesson 5.1).
  • LLM judges are noisy instruments that must be pinned and calibrated (Lesson 5.3).
  • Prompts live in version control and change through pull requests (Lesson 1.5).
🎯 Hook

On April 24–25, 2025, OpenAI rolled out a GPT-4o update to ChatGPT. Its offline evaluations “generally looked good”, and A/B tests suggested the users who tried it liked it. Some expert testers said the model “felt” slightly off. OpenAI launched anyway, and within days users were sharing a model that flattered them and agreed with almost anything. The rollback started on April 28.

In its postmortem, OpenAI explained that a new reward signal based on thumbs-up and thumbs-down feedback had contributed, noting that user feedback can favour more agreeable responses, and that its offline evals weren't broad or deep enough to catch sycophancy. It called launching “the wrong call” and committed to treating behaviour issues as launch-blocking. Every piece of this lesson is in that story: offline evals with gaps, online signals that mislead on their own, and a gate that should have blocked.

Numbers first: what an eval gate costs, and what it can see

Per pull requestPer day (40 PRs)

With output caching (only cases whose prompt or inputs changed re-run)often under $1far less
Wall-clock time with 20 parallel calls, ~3 s each~45 s-

And what 300 cases can detect: baseline 88%, the PR scores 85%. As two separate scores, the 95% error bar on the difference is about ±5.5 points, so a 3-point drop looks like noise. But both runs used the same 300 cases. Only 15 cases changed: 12 went pass → fail, 3 went fail → pass. On those per-case differences the error bar is about ±2.5 points, so the 3-point drop is a real regression (worked example below).

💡 Big idea Treat evals like tests and monitoring. Offline evals run on every change and gate merges, like a test suite. Online evals watch real traffic for what your dataset doesn't contain, like production monitoring. The loop between them is the product: every production failure you find becomes a new offline case, so it can never silently come back.
🧠 Analogy: aviation safety

Before take-off, pilots run a checklist that must pass (offline evals in CI, with must-pass items). In flight, instruments and alarms watch for anything unexpected (online monitoring). After an incident, investigators write a report and the finding becomes a new checklist item for every future flight (production failures become eval cases). No single layer makes flying safe; the loop does.

Evals in CI: designing the gate

  • Must-pass suite: safety, privacy and critical facts (no PII leaked, refuses prompt injection, the refund window is right). Deterministic checks; any failure blocks the merge.
  • Quality suite: hundreds of golden cases scored by checks and judges. Compare the PR with the main branch on the same cases; block only on a statistically clear regression bigger than your tolerance; warn and ask for review when the drop is within noise.
  • Budgets: cost and latency per case, so a prompt that doubles tokens doesn't slip through.
  • Tame the noise: pin model and judge versions, use temperature 0 where you can, cache outputs, and for flaky judges take a majority of 3 calls on borderline cases.
  • Tiers: a fast subset (~50 cases) on every commit, the full suite on PRs that touch prompts, models or retrieval, the big capability and agent suites nightly.
✏️ Worked example: the paired regression test

300 cases. Baseline passes 264 (88%), the PR passes 255 (85%). Per case: b = 12 cases pass → fail, c = 3 cases fail → pass; the other 285 didn't change.

  • Difference = (c − b) ÷ n = (3 − 12) ÷ 300 = −3.0 points.
  • Paired standard error = √((b + c) − (b − c)² ÷ n) ÷ n = √(15 − 81 ÷ 300) ÷ 300 = √14.73 ÷ 300 = 1.28 points, so the 95% interval is −3.0 ± 2.5 = [−5.5, −0.5]. It excludes 0: block and show the 12 cases that broke.
  • Unpaired, treating them as two independent samples: SE = √(0.88 × 0.12 ÷ 300 + 0.85 × 0.15 ÷ 300) = 2.79 points, ±5.5: you'd wave it through.

The 285 unchanged cases carry no noise about the difference, so pairing removes most of it. This is the “question-level paired differences” recommendation from Anthropic's error-bars paper (Lesson 5.1).

No single signal is safe to optimize on its own. The sycophancy story is a thumbs-up rate going up while quality went down. Pair a primary metric with guardrail metrics that must not get worse.

A/B tests for AI features

To learn whether a change helps real users, randomize users (not requests, so each person has a consistent experience) into control and treatment, and compare a primary metric with guardrails. The statistics are ordinary, and so is the main lesson: you need a lot of traffic for small effects.

✏️ Worked example: is 62% better than 60%?

Thumbs-up rate (among rated answers): control 60%, treatment 62%, 5,000 rated answers per arm.

  • SE of the difference = √(0.60 × 0.40 ÷ 5,000 + 0.62 × 0.38 ÷ 5,000) = 0.98 points.
  • z = 2.0 ÷ 0.98 = 2.05, two-sided p ≈ 0.04: just significant at 5%.
  • To detect a 2-point lift reliably (80% power) you'd want about 9,300 rated answers per arm; for 1 point, about 38,000. Halving the effect needs 4× the data.

That's why offline evals do most of the filtering and A/B tests are reserved for the changes that matter. The maths is in Math for AI 5.5.

# promptfooconfig.yaml: the regression suite that runs on every prompt PR
description: Support bot regression suite
prompts:
  - file://prompts/support.txt
providers:
  - anthropic:messages:claude-sonnet-5-5       # pin the exact model your app uses
defaultTest:
  assert:
    - type: latency
      threshold: 4000                           # ms
    - type: cost
      threshold: 0.002                          # dollars per case
tests:
  - vars:
      question: "I'm a Plus member. Can I return boots after 45 days?"
    assert:
      - type: icontains
        value: "60 days"
      - type: not-icontains
        value: "30 days"
      - type: llm-rubric
        value: Answers the question directly and does not invent policy.
  # ...or load hundreds of cases:  tests: file://evals/cases.csv
# .github/workflows/evals.yml: fail the PR if the pass rate drops below 95%
on:
  pull_request:
    paths: ["prompts/**", "promptfooconfig.yaml"]
jobs:
  evals:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: "24" }
      - run: npx promptfoo@latest eval -c promptfooconfig.yaml -o results.json
        env:
          ANTHROPIC_API_KEY: ${{ secrets.ANTHROPIC_API_KEY }}
          PROMPTFOO_PASS_RATE_THRESHOLD: "95"   # below this, exit code 100 fails the job

A pass-rate threshold is a blunt, unpaired gate. For important suites, export per-case results, compare them with main's results for the same cases, and gate on the paired difference, as in the worked example. promptfoo also has an official GitHub Action that posts before/after comparisons on the PR.

🚀 Startup vs big tech

Week one

promptfoo or pytest in GitHub Actions on prompt changes, with a must-pass list and a small judged suite. Langfuse or Phoenix (self-hosted or cloud) for traces, plus a thumbs button. A weekly ritual: read 50 thumbs-down traces, add the failures to the eval set.

At scale

Tiered suites (commit, PR, nightly), paired statistical gates, eval results stored per commit, canary rollouts, an experimentation platform for A/B tests with guardrail metrics, sampled online judges, drift dashboards, and launch reviews where behaviour regressions block like outages.

🎤 Interview angle

“Design the evaluation system for an LLM feature from pull request to production.” A senior answer:

  • Offline: versioned golden set (from logs and failures), must-pass safety checks, a quality suite with calibrated judges, paired comparison against main, cost and latency budgets; blocking vs warning thresholds.
  • Release: canary or A/B test with a primary metric and guardrail metrics, sized for the effect you care about.
  • Online: tracing, explicit and implicit feedback, sampled judges, drift alerts; pinned model versions.
  • The loop: weekly error analysis of production failures feeding new cases into the golden set; eval set coverage compared with real traffic.
  • Mentions a failure like the 2025 sycophancy rollback: offline evals and positive user signals both missed it.
🏭 In the real world
A launch that every signal missed 🏢 OpenAI · 2025 Expanding on what we missed with sycophancy

How: offline evals, A/B tests and expert spot checks were all run before a GPT-4o update; a user-feedback reward signal contributed to sycophancy, and the update was rolled back days after launch.

Why this method: the fix was process: behaviour issues treated as launch-blocking, an opt-in alpha phase, more weight on spot checks and better offline evals for sycophancy.

Thousands of offline tests, then live canaries 🏢 GitHub · 2025 How we evaluate AI models and LLMs for GitHub Copilot

How: more than 4,000 offline tests, mostly in CI, including ~100 containerized repos whose tests are broken for the model to fix; an LLM grader for chat answers; then internal canary testing on employees.

Why this method: metrics trade off (acceptance rate vs latency), so a model change needs both automated suites and live usage before it ships.

Unit tests, trace review, A/B tests 🏢 Rechat · 2024 Your AI Product Needs Evals

How: cheap assertions on every code change, human and model review of traces on a regular cadence, A/B tests only after significant product changes.

Why this method: each level costs more than the last, so its cadence follows its cost.

Evals as open-source CI tooling 🧰 Open source promptfoo GitHub Action

How: when files under prompts/ change in a PR, the action runs the eval before and after and posts the comparison on the PR.

Why this method: reviewers see quality changes next to code changes, the same way they see test results.

🤯 Fun fact · the eval tools got acquired

In 2026 two of the best-known open-source eval tools changed owners: Langfuse joined ClickHouse in January (it already stored its traces in ClickHouse), and OpenAI announced it was acquiring promptfoo in March, saying promptfoo was used by over 25% of Fortune 500 companies. Both projects stayed open source. Evals had become infrastructure that platforms wanted to own, which is also a hint to keep your eval data in portable formats (JSONL, CSV) rather than locked in any one tool.

Check yourself

1. A PR is evaluated on 400 cases: 10 went pass → fail and 2 went fail → pass. What's the paired difference and its approximate 95% error bar?
Difference = (2 − 10) ÷ 400 = −2.0 points. SE = √(12 − 64 ÷ 400) ÷ 400 = √11.84 ÷ 400 = 0.86 points; ×1.96 ≈ ±1.7. The interval [−3.7, −0.3] excludes zero.
2. After a prompt change, thumbs-up rose from 58% to 63%, but escalations to human agents also rose 20%. What do you conclude?
A guardrail metric moved the wrong way. Thumbs reward pleasant answers; escalations reveal unsolved problems. This is the sycophancy pattern: check correctness, not just satisfaction.
3. Your naive CI gate (“block if the score drops by more than 1 point”) blocks about 30% of harmless prompt PRs, and engineers have started overriding it. Best fix?
The gate is reacting to noise. Pairing and significance cut false blocks sharply; lower judge noise and more cases improve its ability to catch real regressions. A 10-point tolerance would let real regressions through.
📝 TL;DR
  • Offline evals gate changes in CI; online evals watch real traffic; production failures feed back into the dataset.
  • Gate design: must-pass suite blocks on any failure; quality suite blocks on a significant paired regression, warns otherwise; cost and latency budgets.
  • Paired comparisons on the same cases are far more sensitive than comparing two scores.
  • Online: combine explicit, implicit and outcome signals with guardrail metrics; thumbs alone can reward sycophancy.
  • Pin model and judge versions, watch for input, model, data and eval drift, and size A/B tests for the effect you need to see.
