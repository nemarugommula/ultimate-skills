Phase 1 · Lesson 3

Structured output & function calling

Models write text; your code needs data. Learn the ladder from “please reply in JSON” to schema-constrained decoding, how to validate and retry, and how tool calling lets a model ask your code to act.

🧰 You'll need (quick reminders)
  • JSON (JavaScript Object Notation): text like {"city": "Paris", "days": 3}; a JSON Schema describes which keys and types are allowed.
  • The model picks one token at a time from a probability distribution over its vocabulary (Lesson 0.2).
  • Output format instructions in a prompt (Lesson 1.1); chat messages and roles (Lesson 0.5).
🎯 Hook

In August 2024, OpenAI ran an eval of complex JSON-schema following. Their older GPT-4 model (gpt-4-0613), asked nicely in the prompt, matched the schema less than 40% of the time. Their new model with Structured Outputs switched on scored a perfect 100%.

The difference wasn't a cleverer prompt. With strict mode on, the API restricts which tokens the model is allowed to pick at each step, so output that breaks the schema simply can't be generated. That is now a standard feature at every major provider, and the reason “parse the LLM's JSON” is no longer a source of 3 a.m. pages.

At scale, every failure mode happens every day. Worse, the dangerous ones don't crash: a "quantity": "2" string or a missing email sails through json.loads and corrupts your database quietly. Reliability comes from layers, each removing a class of failure:

LayerGuaranteesDoesn't guarantee
Prompt: “Reply only with JSON like…”Nothing; works most of the timeValid JSON, right keys, right types
JSON modeThe output parses as JSONThat it matches your schema
Schema-constrained output (OpenAI and Anthropic call it Structured Outputs; Gemini, structured output with a response schema)Valid JSON matching your schema: keys, types, enumsComplete output if it hits the token limit; refusals; correct values
Validation (e.g. Pydantic) + retryYour business rules (email format, totals add up); failures are caught, not silentThat the values are true; that needs evals (Phase 5)
💡 Big idea Treat the model's output as untrusted input from an external service. Constrain it at the source when you can (schema-constrained decoding), validate it at the boundary always (a typed model with your rules), and decide in advance what happens on failure (retry with the error, fall back, or flag for a human).
🧠 Analogy: a blank page vs a paper form

Ask a hundred people to “write down your contact details” on a blank page and you'll get a hundred layouts, some with a phone number missing. Hand them a form with labelled boxes, a box that only takes digits and tick-boxes for the options, and almost everything comes back usable. Constrained decoding is the form. Validation is the clerk who checks the form before filing it. Neither checks that the phone number is actually theirs.

How constrained decoding works

At every step the model produces a probability for every token in its vocabulary. The API turns your schema into a grammar (a small state machine) and, before sampling, masks every token that would make the output invalid. Halfway through {"name": "Ada", "quantity": the model's preferences might be:

Candidate next tokenModel probabilityAllowed by schema (quantity: integer)?
"two"0.46❌ masked: a string, not an integer
20.41✅ renormalized to 0.91
null0.09❌ masked: field is required, not nullable
30.04✅ renormalized to 0.09

Illustrative probabilities. Libraries like Outlines, XGrammar and llguidance do the same for open models served with vLLM or SGLang.

So the output always fits the schema, but the model may be pushed off its first choice. Two consequences: put any free-text reasoning before the strict fields (or reason first, then format), and remember that a schema can't stop a well-formed wrong answer.

✏️ Worked example: what retries cost

Suppose 4% of responses fail validation and a retry with the error message fixes 90% of them.

  • Extra model calls: 4% of requests × 1 retry = +4% cost.
  • Still failing after one retry: 4% × 10% = 0.4%, handled by a fallback or a human queue. A second retry would cut it to 0.04% for another +0.4% calls.
  • Latency: those 4% take about twice as long. Your p95 (95th-percentile latency) is unchanged, because 96% of requests never retry, but your p99 roughly doubles.

Retries are cheap insurance on cost and expensive on tail latency, which is one more reason to remove failures at the source with constrained decoding.

Function calling (tool use): the model asks, your code acts

Structured output answers “give me data”. Function calling, also called tool use, answers “do something”. You describe tools (a name, a description, and a JSON Schema for the arguments). The model can reply with a request to call one, with arguments. The model never runs anything. Your code checks the request, runs the function, and sends the result back; the model then continues, perhaps calling another tool, until it answers.

  1. You send messages + tool definitions.
  2. The model returns a tool call: get_weather({"city": "Paris"}) (Anthropic: a tool_use block with stop_reason: "tool_use"; OpenAI: a function_call item).
  3. Your code validates the arguments, runs the function, and appends the result (tool_result / function_call_output) to the messages.
  4. You call the model again; it uses the result to answer or to call the next tool.

That loop, repeated with the model choosing which tool to call next, is the beginning of an agent (Phase 6).

🧰 Tools you'll actually use

Pydantic for schemas and validation; provider structured outputs (Anthropic messages.parse, OpenAI responses.parse, Gemini response_format with a schema); Instructor for validation + retries across 15+ providers; Outlines or vLLM's structured outputs for open models.

from typing import Literal
from pydantic import BaseModel, EmailStr, Field, ValidationError
import anthropic

class Ticket(BaseModel):
    customer: str
    email: EmailStr                       # pip install "pydantic[email]"
    quantity: int = Field(ge=1)
    priority: Literal["low", "normal", "high"]

client = anthropic.Anthropic()

# 1) Schema-constrained output: the SDK sends the schema, validates, returns a Ticket
resp = client.messages.parse(
    model="claude-opus-5-5", max_tokens=1024,       # check current model IDs
    messages=[{"role": "user", "content": f"Extract the ticket:\n<email>{raw}</email>"}],
    output_format=Ticket,
)
ticket = resp.parsed_output               # a Ticket; still check stop_reason for max_tokens / refusal

# 2) Validate + retry with the error (for any provider or plain-text output)
def extract(raw, call_model, retries=1):
    msgs = [{"role": "user", "content": f"Return JSON for Ticket:\n{raw}"}]
    for _ in range(retries + 1):
        text = call_model(msgs)
        try:
            return Ticket.model_validate_json(text)
        except ValidationError as e:      # bad JSON or bad fields: tell the model exactly what broke
            msgs += [{"role": "assistant", "content": text},
                     {"role": "user", "content": f"Invalid: {e}. Return corrected JSON only."}]
    return None                           # caller flags it for review instead of crashing

# OpenAI: client.responses.parse(model=..., input=..., text_format=Ticket).output_parsed
# Instructor: instructor.from_provider("anthropic/...").create(response_model=Ticket, max_retries=2, messages=...)

Provider schema support is a subset of JSON Schema (some keywords like numeric ranges are moved into descriptions or rejected), so keep schemas simple and validate your own rules in Pydantic. The older Anthropic output_format request field is deprecated in favour of output_config.format; the SDK's parse() helper handles that for you.

🚀 Startup vs big tech

Week one

One Pydantic model per output, provider structured outputs on, a try/except around every parse, and failures logged with the raw text. Tools: a handful, with clear names and descriptions, strict schemas, and arguments validated before anything runs.

At scale

Schemas versioned with the prompt (Lesson 1.5), failure and retry rates on a dashboard per schema version, constrained decoding on self-hosted models via vLLM, dead-letter queues for records that fail twice, and evals that check values, not just shapes. Tool calls go through permission checks and audit logs.

🎤 Interview angle

“We extract invoices with an LLM into our billing database. How do you make it reliable?” A senior answer:

  • Layers: schema-constrained output, a typed model with business rules (totals add up, dates valid), retry with the validation error, then a human queue.
  • Handles the edges the schema can't: max_tokens truncation, refusals, empty documents.
  • Separates shape from truth: a labelled eval set measures field-level accuracy (Phase 5); confidence or cross-checks route doubtful records to review.
  • For tools: least-privilege tools, arguments validated before execution, idempotent actions, and confirmation for anything irreversible.
🏭 In the real world
Structured Outputs: 100% schema match 🏢 OpenAI · 2024 Introducing Structured Outputs in the API

How: developer-supplied JSON Schemas enforced with constrained decoding (strict: true), for both response formats and function arguments, plus training the model on complex schemas.

Why this method: on their complex-schema eval, gpt-4o-2024-08-06 with Structured Outputs scored 100%, against under 40% for gpt-4-0613 with prompting alone.

Constrained decoding for JSON and strict tools 🏢 Anthropic · 2026 Structured outputs docs

How: a JSON Schema sent in output_config.format, or strict: true on a tool definition, compiled into a grammar that constrains generation; SDK helpers take a Pydantic or Zod model and return a parsed object.

Why this method: schema-compliant responses by construction, so no JSON.parse() errors and no missing required fields.

Guided generation as a state machine 🧰 Open source · 2023 Willard & Louf: Outlines

How: turns regular expressions and grammars into a finite-state machine and pre-indexes which vocabulary tokens are valid in each state.

Why this method: enforcing structure adds little overhead per token and works with any open model; it's the idea behind structured outputs in vLLM and friends.

Format restrictions can cost reasoning 🧪 Research · 2024 Tam et al.: Let Me Speak Freely?

How: compared models answering freely versus under JSON/XML format constraints on reasoning and knowledge tasks.

Why this method: they saw a significant drop in reasoning under strict formats, larger for stricter constraints. Hence: reason first (or in a free-text field placed first), then emit the structured answer.

🤯 Fun fact · the model never presses the button

“The AI booked my flight” is never literally true. In every function-calling API, the model only produces a JSON request; some ordinary code decides whether to run it. That boundary is where you put validation, permissions and confirmations, and it's why tool safety is an engineering problem you control (Lesson 6.6).

🌉 How it connects

Output formats started as prompt instructions (Lesson 1.1); the final answer of a reasoning chain (1.2) is easiest to vote on when it's a schema field. Tool results become part of the context window (1.4), and schemas are versioned with prompts (1.5). Tool calling grows into agents and MCP, the Model Context Protocol for sharing tools across apps (Lessons 6.1–6.2); text-to-SQL is structured output with a grammar (4.6); validating values is Phase 5's job. Masking tokens is just renormalizing a softmax.

Check yourself

1. Your extractor fails validation on 5% of 200,000 daily requests. One retry fixes 80% of those. How many records a day still need a fallback?
5% × 200,000 = 10,000 retried; 20% of them still fail: 2,000. The retries also add 10,000 calls (+5% cost) and double latency for those requests.
2. With JSON mode on, your pipeline stores {"amount": "12,50"} and later reports crash on the string. What's the best fix?
JSON mode only guarantees parseable JSON, not your types. A schema constrains the type at generation time; validation at the boundary stops anything else from reaching storage.
3. A model with a refund_order(order_id) tool returns a call for an order the user doesn't own. What should happen?
The model only proposes calls. Authorization, validation and confirmation live in your code; return failures as tool results (with an error flag) so the conversation can recover.
📝 TL;DR
  • Prompt-only JSON fails a few percent of the time; at scale that's thousands of bad records a day, many of them silent.
  • JSON mode guarantees parseable JSON; schema-constrained decoding guarantees your schema by masking invalid tokens.
  • Always validate at the boundary (Pydantic), retry with the error, and handle truncation and refusals. Shape is not truth: evals check values.
  • Function calling: the model proposes a call, your code validates and runs it, the result goes back as a message. Two model calls per tool use; parallel calls share one round trip.
