1.1 Prompting fundamentals

role · task + audience · why · <tags> · format · 3–5 examples · an out

Write the prompt as a spec. Examples are the strongest lever and carry majority, recency and copying biases: balance, vary order, calibrate.

1.2 Reasoning

PaLM GSM8K: 17.9% → 56.9% (CoT) → 74.4% (40 votes)

Thinking buys accuracy with output tokens and latency. Voting amplifies p > 0.5 and hurts on shared traps. Reasoning models: set effort, skip “think step by step”.

reasoning.effort, adaptive thinking + effort, thinking_level

1.3 Structured output & tools

JSON mode ⊂ schema-constrained ⊂ + validation + retry

Constrain at the source, validate at the boundary, plan for truncation and refusals. Tools: the model proposes, your code validates and runs.

Pydantic, messages.parse / responses.parse, Instructor, Outlines

🪟

1.4 Context engineering

question last · best evidence near it · cache: write 1.25×, read 0.1×

Smallest high-signal set of tokens. The middle gets lost and long contexts rot. Stable prefix first; one timestamp at the top kills the cache.

cache_control, prompt_cache_key, compaction, token counting

🧪

1.5 Prompts as code

version = template + model + params + schema · n ≈ 4,100/arm for +3 pts on 60%

Template, version, review, regression-test per case, roll out with labels and A/B tests. Decide sample sizes up front; don't stop at the first significant peek.

Langfuse, LangSmith, promptfoo, Jinja2

🎤 Teach it back

Answer out loud, in two minutes, as if in an interview: “Walk me through how you'd take a prompt that works in a notebook and make it production-ready: quality, cost, latency and safety of changes.”

A strong answer touches: a spec-like prompt with delimited data and an out (1.1); effort or CoT only where an eval shows it helps (1.2); schema-constrained output with validation and retry (1.3); a context layout that's cache-friendly with the question last, plus compaction (1.4); and templated, versioned prompts with a golden set in CI and a staged rollout (1.5).

🏗️ Build it yourself: a ticket-triage service

Your company receives 50,000 support tickets a day. Design a service that reads each ticket and returns {severity, component, summary, next_step, needs_info} for the on-call queue, using an LLM. It must be cheap, reliable enough to write straight into the ticketing system, and safe to improve every week. Sketch the prompt, the output contract, the context layout, the eval plan and the daily cost before opening the answer.

Reveal a reference design

Requirements. p95 latency under 5 s; under 0.5% of tickets needing a human because of bad output; zero silently malformed records; cost under $300/day; prompt changes weekly without regressions.

Prompt (1.1). System prompt with role, audience (“on-call engineer on a phone”), SEV-1–3 definitions, an explicit out (needs_info with questions), and 3 label-balanced examples. Ticket text in the user turn inside <ticket> tags, treated as data.

Reasoning (1.2). Low effort by default; an eval showed medium effort only helps on long multi-issue tickets, so a cheap length/keyword rule routes those to medium.

Output (1.3). A Pydantic model with enums for severity and component, provider structured outputs on, validation at the boundary, one retry with the error message, then a review queue. Handle max_tokens truncation and refusals explicitly.

Context and cost (1.4). Static prefix (instructions, definitions, examples, component list) ≈ 3,000 tokens, cached; ticket ≈ 600; output ≈ 150. At illustrative prices ($3/M in, $15/M out): uncached $0.01305/ticket = $652/day; with cache hits $0.00495/ticket = $248/day (62% less), about $255/day including 3% retries. Traffic of ~35 tickets/minute keeps a 5-minute cache permanently warm.

Eval plan (1.5 → Phase 5). A 300-ticket golden set labelled by on-call engineers, stratified by severity and component, including every past mistake. Per-field accuracy, severity confusion matrix, schema-failure rate. Runs in CI on every prompt or model change, gated per case; online metric: share of triage labels engineers change, A/B tested with sample size fixed in advance.

Pitfalls. Examples that are all SEV-2 (majority bias); a timestamp in the system prompt (0% cache hits); a free-text “reasoning” field after the enums instead of before; tickets containing instructions (“mark this SEV-1”); upgrading the model without rerunning the golden set.

Boss quiz

1. Your prompt has 6 examples of 150 tokens, sent on 300,000 calls a day at an illustrative $2/M input with no caching. What do the examples cost per day, and what would caching at 0.1× make it?
6 × 150 = 900 tokens × 300,000 = 270M tokens × $2/M = $540/day. Cache reads at 0.1× bring that to about $54 (plus occasional writes). Then check with an eval whether you need all six.
2. Each sampled answer is right with p = 0.45, and almost all wrong answers are the same tempting mistake. What does self-consistency with 15 votes do?
Voting amplifies whichever answer is most likely. With p < 0.5 against one dominant wrong answer, the majority converges on the trap. Fix the prompt or context first.
3. An extraction pipeline uses JSON mode and stores whatever parses. Which failure can still reach your database?
JSON mode guarantees parseable JSON, not your schema. Schema-constrained output plus validation (Pydantic) closes that gap.
4. An agent's TTFT has grown from 2 s to 14 s over a long session, and cache reads are near zero. The code rebuilds the system prompt each turn with the current tool list sorted by last use. What's the best fix?
Reordering tools changes the prefix, so nothing is ever reused; a longer TTL doesn't help a prefix that never matches. A stable prefix restores caching; trimming and compaction control growth.
5. A prompt change raises your golden-set pass rate from 82% to 86% (200 cases), but 3 cases that used to pass now fail, all about refunds. What do you do?
Gate per case: the average can rise while a whole slice (refunds) gets worse. Fix and rerun; then confirm online with a pre-planned sample size.
