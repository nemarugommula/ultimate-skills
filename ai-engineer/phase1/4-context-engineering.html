Phase 1 · Lesson 4

Context engineering: long context, ordering, caching, memory

Prompt engineering is the words; context engineering is everything else in the window: which documents, which tool results, how much history, in what order, and which part you pay full price for. It decides quality, cost and latency at once.

🧰 You'll need (quick reminders)
  • The context window is the maximum number of tokens a model can read in one call, prompt plus output (Lesson 0.3).
  • Time to first token (TTFT) grows with input length, because the model must process every input token before writing (Lesson 0.3).
  • RAG (retrieval-augmented generation) means fetching relevant documents and putting them in the prompt; Phase 3 covers it in depth.
  • Prompt elements and XML tags (Lesson 1.1); tool results (Lesson 1.3).
🎯 Hook

In 2023, a Stanford-led team gave GPT-3.5-Turbo a question plus 20 retrieved documents, exactly one of which held the answer. When that document was first or last, the model did well. When it sat in the middle, accuracy fell so far that it was lower than answering with no documents at all (56.1%, the model's closed-book score).

Same model, same documents, same question; only the order changed. The paper, “Lost in the Middle”, made something obvious that every RAG and agent builder has to design around: a model with a big context window does not read all of it equally well.

The question is 0.2% of the window. Three levers move the other 99.8%: what you include (and trim), where you put it, and caching the part that doesn't change.

💡 Big idea Context is a finite attention budget, not free storage. Anthropic's engineering team puts it as: find the smallest set of high-signal tokens that maximizes the chance of the outcome you want. Every extra token costs money and latency, and can make the model worse at using the tokens that matter.
🧠 Analogy: the desk and the filing cabinet

The context window is your desk; retrieval is the filing cabinet. A bigger desk lets you spread out more papers, but if you pile 200 pages on it, the one page you need gets buried in the middle of the stack. Good engineers keep the instructions pinned at the top, put the most relevant page right next to the question, summarize old notes into one sheet, and leave the rest in the cabinet until it's needed. Caching is leaving the pinned pages on the desk between meetings instead of re-reading them.

In practice you combine them: retrieve generously, then pack carefully. And whatever you include, order matters.

Lost in the middle, context rot, and why needle tests mislead

  • Position: recall is usually best near the start (primacy) and end (recency) of the context, and worst in the middle (Liu et al. 2023: drops of more than 20 points).
  • Length: “context rot”: as input grows, accuracy falls even on simple tasks. Chroma tested 18 models in 2025 and found performance grows “increasingly unreliable” with input length, in non-uniform ways.
  • Needle-in-a-haystack (NIAH) tests hide one sentence in a long text and ask for it back. Most models now ace it, but that's a lookup. The RULER benchmark (NVIDIA, 2024) added multi-hop and aggregation tasks: of 17 models all claiming 32K+ windows, only half held up at 32K.

Ordering rules that follow: instructions first; long documents near the top with the question at the end (Anthropic reports queries at the end can improve quality by up to 30% on complex multi-document inputs); the most relevant document next to the question; and if the context is very long, repeat the key constraint just before the question.

Prompt caching: pay full price only for what changed

Before writing anything, the model computes internal state (the KV cache, keys and values for every token) for the whole input. If the first 20,000 tokens are identical to a recent request's, the provider can reuse that work. That's prompt caching, and it only works on an exact prefix: change one token and everything after it is recomputed.

TTL (time to live): how long an unused entry survives. Each read refreshes it. Check the pricing pages; these numbers change.

Design rule: stable things first, volatile things last. Tools → system prompt → examples → long static documents → conversation history → the new question. The classic silent bug is a timestamp or request id at the top of the system prompt: a 0% hit rate and nobody notices until the bill.

✏️ Worked example: caching a 20,000-token prefix

Static prefix 20,000 tokens, dynamic suffix 500, output 300. Illustrative prices: $3/M input, $15/M output; Anthropic-style multipliers.

  • No cache: 20,500 × $3/M + 300 × $15/M = $0.0615 + $0.0045 = $0.066 per request.
  • Cache write (first request): 20,000 × 1.25 × $3/M + 500 × $3/M + $0.0045 = $0.075 + $0.0015 + $0.0045 = $0.081.
  • Cache hit: 20,000 × 0.1 × $3/M + $0.0015 + $0.0045 = $0.006 + $0.006 = $0.012: 82% cheaper.
  • Break-even: one write plus one read (0.081 + 0.012 = $0.093) already beats two uncached requests ($0.132).

Latency improves too: Anthropic's launch example cut time to first token on a 100,000-token cached book from 11.5 s to 2.4 s.

The timestamp bug turns caching into a cost increase: every request pays the 1.25× write and never reads it back.

Memory: when the conversation outgrows the window

Long chats and agents accumulate history and tool output until they hit the window, get slow and start to rot. The standard toolkit, from Anthropic's 2025 context-engineering guide:

TechniqueHowTrade-off
Compaction (summarization)Near the limit, summarize the conversation so far and start a fresh window with the summary. Some APIs now do this server-side.Details can be lost; summaries must keep decisions, open tasks and facts
Context editing / tool-result clearingDrop old, already-used tool outputs (keep a short note that they happened)Cheap and safe; the model can re-fetch if needed
Structured notesThe agent writes a notes or to-do file outside the window and reads it back when neededNeeds a tool and discipline in the prompt
Sub-agentsHand a focused task to a fresh context; get back only a short resultMore calls; coordination overhead (Phase 6)
Sliding windowKeep only the last N turnsSimple; forgets early facts unless they're pinned

Compaction rewrites the prefix, so it also resets your prompt cache; do it rarely and deliberately, not every turn.

🧰 Tools you'll actually use

Provider token counters and caching controls; LangChain/LangGraph message trimming and summarization; LlamaIndex and Haystack for packing retrieved context; your own logging of cached vs uncached tokens per request.

import anthropic
client = anthropic.Anthropic()

# Stable first: tools → system → static docs. Volatile last: history, then the question.
SYSTEM = [
    {"type": "text", "text": INSTRUCTIONS},                      # no timestamps, no request ids!
    {"type": "text", "text": f"<handbook>{HANDBOOK}</handbook>",
     "cache_control": {"type": "ephemeral"}},                  # breakpoint: cache everything up to here (5-min TTL)
]
msgs = history + [{"role": "user", "content": f"<question>{q}</question>"}]   # question last

n = client.messages.count_tokens(model="claude-opus-5-5", system=SYSTEM, messages=msgs)
if n.input_tokens > 150_000:
    msgs = compact(msgs)                     # your summarizer, or the API's server-side compaction

r = client.messages.create(model="claude-opus-5-5", max_tokens=1024, system=SYSTEM, messages=msgs)
u = r.usage
log(cache_read=u.cache_read_input_tokens, cache_write=u.cache_creation_input_tokens,
    uncached=u.input_tokens)                 # if cache_read stays 0, something in the prefix is changing

# OpenAI: caching is automatic; keep the prefix identical and pass prompt_cache_key="support-v3"

Watch the cache_read_input_tokens number on your dashboard. Manus, which builds agents, calls the KV-cache hit rate the single most important metric for a production agent.

🚀 Startup vs big tech

Week one

A fixed order (instructions, docs, history, question), one cache breakpoint after the static part, a token count logged on every request, and a hard cap that trims the oldest turns. Check the cache-read numbers after your first deploy.

At scale

A context assembler service with per-source token budgets, relevance-ordered packing, compaction policies tested against evals, cache hit rate and cost per request as SLOs (service-level objectives), and prompt-prefix changes reviewed because they invalidate every cache at once.

🎤 Interview angle

“Our agent gets slower, pricier and dumber the longer a session runs. Why, and what do you do?” A senior answer:

  • Explains the mechanics: history and tool results grow every turn, input cost and TTFT grow with them, and quality falls with length and middle positions.
  • Fixes the window: trim tool outputs, clear old results, compact with a tested summary, move long-term facts to notes or memory (Lesson 6.4).
  • Fixes cost: a frozen prefix, cache breakpoints, append-only history, cache hit rate monitored.
  • Measures it: quality versus session length on an eval set, before and after.
🏭 In the real world
The U-shaped curve 🧪 Research · 2023 Liu et al.: Lost in the Middle

How: moved the answer-bearing document through 10, 20 and 30-document contexts in multi-document QA and key-value retrieval.

Why this method: isolating position showed accuracy highest at the start and end and down by more than 20 points in the middle, even for extended-context models.

Context rot across 18 models 🏢 Chroma · 2025 Context Rot

How: held task difficulty fixed and varied only input length, including needle-question similarity and distractor tests.

Why this method: even on simple tasks, performance degraded with length in non-uniform, model-specific ways. Long windows are capacity, not a guarantee.

Prompt caching: up to 90% cheaper, 85% faster 🏢 Anthropic · 2024 Prompt caching with Claude

How: cache a long, reused prefix (a book, many-shot examples, a long system prompt) and read it back on later calls.

Why this method: their “chat with a book” example (100K cached tokens) went from 11.5 s to 2.4 s to first token at 90% lower cost.

Design the agent around the KV cache 🏢 Manus · 2025 Context Engineering for AI Agents

How: a stable prompt prefix, append-only context, deterministic serialization, and no tool-list changes mid-task.

Why this method: their agents average about 100 input tokens per output token, so prefill dominates; cached input was 10× cheaper than uncached ($0.30 vs $3 per million at the time).

Compaction, notes and sub-agents 🏢 Anthropic · 2025 Effective context engineering for AI agents

How: treat context as a finite attention budget; compact near the limit, keep structured notes outside the window, give focused tasks to sub-agents with clean contexts.

Why this method: lets agents work over long horizons without drowning in their own history.

🤯 Fun fact · one sentence, 27% → 98%

In 2023, Anthropic tested Claude 2.1 on a needle-in-a-haystack task across its 200K window and got 27%. The model was reluctant to answer from a single out-of-place sentence. Starting its reply with “Here is the most relevant sentence in the context:” raised the score to 98%. Context engineering and prompt engineering are the same job seen from two sides.

Check yourself

1. A 50,000-token cached prefix, input $3/M, read 0.1×. You serve 100,000 requests a day, all cache hits. How much do you save per day on the prefix versus no caching?
Uncached: 50,000 × 100,000 = 5 billion tokens × $3/M = $15,000. Cached reads: 10% of that = $1,500. Savings: $13,500/day (ignoring the small cost of occasional writes).
2. After a deploy, cache reads drop to zero and your input bill rises 15%. The diff added “Current time: {now}” as the first line of the system prompt. What's the fix?
Caching matches exact prefixes. A value that changes every request at the very top invalidates everything after it, and you now pay the write premium every time. Volatile content goes last.
3. Your RAG prompt has 30 retrieved chunks, sorted most relevant first, then the question. Answers miss facts that appear in chunks 10–20. What's the cheapest thing to try first?
The window isn't full; the middle is under-read and the noise is high. Fewer, better-ordered chunks fix both and cut cost. Reranking is Lesson 3.4.
📝 TL;DR
  • Everything in the window costs money and latency and competes for attention: include the smallest high-signal set.
  • Models read the start and end best and lose the middle; quality falls with length even on simple tasks. Put the question last and the best evidence next to it.
  • Prompt caching reuses an exact prefix: stable content first, volatile last, watch the hit rate. Anthropic-style: write 1.25×, read 0.1×.
  • For long sessions: trim tool output, clear old results, compact with a tested summary, keep notes outside the window.
