Phase 1 · Lesson 5

Prompts as code: templates, versioning & experiments

A one-line prompt edit can fix two bugs and silently create a third. Treat prompts like code: templated, versioned, reviewed, regression-tested and rolled out with experiments.

🧰 You'll need (quick reminders)
  • The elements of a good prompt (Lesson 1.1) and structured outputs (Lesson 1.3).
  • Git, pull requests and CI (continuous integration: tests that run on every change).
  • The idea of an eval: a set of inputs with a check for each output, scored automatically. Phase 5 goes deep; here we use simple pass/fail checks.
🎯 Hook

In 2023, a research team led by Melanie Sclar changed only the formatting of few-shot prompts: separators, spacing, capitalization, nothing that changed the meaning. On LLaMA-2-13B, accuracy on the same task moved by up to 76 percentage points.

Worse, the best format for one model was often not the best for another. If whitespace can do that, then every prompt edit, and every model upgrade, is a change to production behaviour that needs a test, not a vibe check.

Numbers first: how big is a prompt change?

Two lessons hide in that table. A prompt change has a blast radius like any deploy. And a tiny eval set can't see small regressions: with 50 cases, one case is 2 points, so you also need to look at which cases changed, not just the average.

💡 Big idea A prompt is code that runs on a probabilistic interpreter. Give it the same lifecycle as code: a template separate from data, a version that pins template + model + parameters + schema together, a review, a regression suite that runs on every change, a staged rollout, and a production metric that tells you whether it worked.
🧠 Analogy: the recipe at a restaurant chain

A chain doesn't let a cook in one branch quietly change the burger recipe for all 900 branches. A change goes to the test kitchen, gets tasted against the standard dishes (the regression suite), runs in a few branches first (an A/B test), and only then becomes the official recipe card with a new version number. Prompts deserve the same process, because they change what every customer gets.

Templates: separate the prompt from the data

A template is the prompt with holes: {{ customer_name }}, {{ ticket }}, a loop over examples. Use Jinja2 (or f-strings for simple cases), keep templates in files, and fill them in one place. Rules of thumb: untrusted values go inside delimiters in the user turn (Lesson 1.1); keep the stable parts at the top for caching (Lesson 1.4); and never assemble prompts by string concatenation scattered across the codebase, because then nobody knows what the model actually sees.

Versioning: git or a prompt registry?

Deploying a changeA code releaseMove the production label: no redeploy, instant rollback
RiskSlower iterationA change can skip code review and CI unless you wire them in

Either way, a “prompt version” must pin the model ID, parameters (temperature, effort, max tokens) and output schema too. The same text on a new model is a new version. Log the version id with every request so you can tie metrics and bugs back to it.

Regression tests: the CI gate for prompts

Keep a golden set: real inputs (especially past bugs) with a check for each. Checks range from cheap and exact (contains, regex, valid JSON, schema) to graded (an LLM-as-judge rubric, Lesson 5.3). On every pull request that touches a prompt, run the set against the old and new versions and compare case by case.

🎮 Playground · Prompt diff + regression run

Version 1 of a support-bot prompt passes 7 of 10 golden cases. A teammate's pull request adds two edits. Run the suite, read the per-case diff, and decide whether to merge. Then try to write a version 2 that fixes everything without breaking anything.

The “model” is a rule-based stand-in that reacts to each instruction the way real models typically do, so results are repeatable; a real model is used in practice. With variation on, case 8 passes only about two runs in three under every version: real outputs vary from run to run, so run each case several times and look at rates.

What you should see: the pull request takes the pass rate from 7/10 to 8/10, which looks like a win, but case 3 (return instructions) regressed because “one sentence” can't hold numbered steps. An average-only gate merges it; a per-case gate blocks it. B′ plus C gets 10/10. Turn on variation and case 8 shows up as flaky, not as a regression: a reason to run cases more than once.

Online experiments: does it work for real users?

Offline tests catch regressions on cases you thought of. An A/B test sends a random share of real traffic to the new version and compares a product metric: thumbs-up rate, issue resolved, escalation to a human, conversion. The catch is sample size.

n per arm ≈ (zα/2 + zβ)² · [pA(1 − pA) + pB(1 − pB)] / (pB − pA)²

zα/2 = 1.96 for a 5% false-positive rate (two-sided); zβ = 0.84 for 80% power (the chance of detecting a real effect of that size).

✏️ Worked example: detecting a 3-point lift

Thumbs-up rate today pA = 60%. You hope the new prompt gets pB = 63%.

  • (1.96 + 0.84)² = 2.80² = 7.85
  • pA(1 − pA) + pB(1 − pB) = 0.24 + 0.2331 = 0.4731
  • (pB − pA)² = 0.03² = 0.0009
  • n ≈ 7.85 × 0.4731 / 0.0009 ≈ 4,126 rated conversations per arm, about 8,250 in total.

If 5% of your 200,000 daily conversations get a rating, that's 10,000 ratings a day: under a day. If only 500 a day are rated, it's 17 days. Halve the effect you want to detect and you need 4× the sample.

🎮 Playground · A/B test simulator

Set the baseline rate, the true effect of the new prompt (which you never know in real life) and the sample size. Run one experiment, then run 200 to see how often a real lift is detected. Finally run 200 A/A tests (no real difference) where you check the results every day and stop as soon as it looks significant: count the false winners.

Two-proportion z-test at α = 0.05. Each simulated user is a coin flip with the arm's true rate (simulated with a normal approximation to the binomial). “Peeking” checks after each of 20 equal daily batches and stops at the first p < 0.05.

What you should see: at 2,000 users per arm, a real 3-point lift is detected only about half the time; at the ~4,100 the formula asks for, about 80%. With 200 A/A tests checked once at the end, about 5% show a false winner, as designed. Peek every day and stop early, and it's several times that. Decide the sample size up front, or use a sequential test designed for peeking.

🧰 Tools you'll actually use

Jinja2 templates in a prompts/ folder; a registry such as Langfuse or LangSmith (versions plus environment labels or tags); promptfoo for regression suites in CI (it has a GitHub Action that comments eval results on pull requests); OpenAI Evals, DeepEval or your own pytest for checks; feature-flag or experimentation tools (GrowthBook, Statsig, LaunchDarkly) to split traffic.

# prompts/support.j2 (in git; reviewed like code)
# You are Acme Gear's support assistant. ... {% for ex in examples %}<example>{{ ex }}</example>{% endfor %}
from jinja2 import Environment, FileSystemLoader, StrictUndefined
env = Environment(loader=FileSystemLoader("prompts"), undefined=StrictUndefined)  # missing variable = error, not ""
system = env.get_template("support.j2").render(examples=EXAMPLES)

🚀 Startup vs big tech

Week one

Prompts as Jinja files in the repo, a 30–50 case golden set built from real conversations and every bug report, a script (or promptfoo) that runs it on each PR, and the prompt version logged on every request. Ship changes behind a simple percentage flag.

At scale

A registry with environments and approvals, eval suites of hundreds to thousands of cases per feature, CI gates per case and per slice (language, customer tier), canary rollouts with automatic rollback on metric drops, and a standing A/B framework. Every model upgrade is treated as a new prompt version and re-evaluated (Lesson 5.6).

🎤 Interview angle

“A PM wants to tweak the system prompt in production every day. How do you make that safe?” A senior answer:

  • Versioned prompts (registry or git) with template, model, parameters and schema pinned together, and the version logged per request.
  • A golden set that runs automatically on every change, compared per case against the current version, with a block on regressions.
  • Staged rollout: staging label, then a small traffic percentage, then everyone; instant rollback by moving the label.
  • Online metrics with a sample size decided up front, and an honest note that small effects need large samples.
🏭 In the real world
Formatting alone moves accuracy 76 points 🧪 Research · 2023 Sclar et al.: Quantifying sensitivity to prompt formatting

How: sampled many meaning-preserving prompt formats and measured the spread of accuracy (their FormatSpread method).

Why this method: spreads of up to 76 points on LLaMA-2-13B, persisting with bigger models and instruction tuning; they recommend reporting a range across formats, not one number.

Versions and labels for production prompts 🧰 Open source Langfuse prompt version control

How: every save creates a numbered version; labels like production and staging point at versions, and the SDK fetches by label.

Why this method: deploy or roll back a prompt by moving a label, with no code release.

Environments and commit tags for prompts 🏢 LangChain · 2026 LangSmith: manage prompts

How: prompts are committed like code; tags such as production point at a commit and code pulls name:production.

Why this method: moving a tag changes what production runs without changing code, and every version stays addressable for comparison.

Prompt evals on every pull request 🧰 Open source promptfoo GitHub Action

How: a workflow triggered on pull requests that change files under prompts/ runs the eval suite and comments a link to the before/after results.

Why this method: reviewers see the per-case effect of a prompt change in the same place they review code.

🤯 Fun fact · the best prompt doesn't transfer

Sclar et al. found that how well a prompt format performs only weakly correlates between models. The format you lovingly tuned for one model may be mediocre on the next. That's why a model upgrade is a prompt change, and why your golden set is worth more than any single clever prompt.

Check yourself

1. Your golden set has 40 cases and passes at 85%. A change moves it to 87.5%. What does that one-case difference tell you?
Standard error ≈ √(0.85 × 0.15 / 40) ≈ 0.056, so ±5.6 points. A one-case change is noise unless you look at which case flipped and why. Per-case diffs and bigger sets beat averages.
2. A new prompt raises the eval pass rate from 80% to 84%, but two previously-passing safety cases now fail. What should the CI gate do?
Gate per case (or per critical slice), not just on the average. Fix the instruction that caused the regression, then rerun.
3. You upgrade to a newer model ID but keep the prompt text identical. How should you treat it?
Behaviour depends on text and model together; good formats don't transfer reliably between models. Pin both in the version and evaluate before switching.
📝 TL;DR
  • Prompts are code: templates in files, versions that pin text + model + parameters + schema, the version logged on every request.
  • Git gives review and CI; a registry gives fast edits and label-based rollback. Wire evals into whichever you use.
  • Run a golden set on every change and compare per case: an average can rise while a critical case breaks. Run flaky cases several times.
  • A/B tests need sample sizes decided up front: a 3-point lift on a 60% rate needs ~4,100 per arm. Don't stop at the first significant peek.
