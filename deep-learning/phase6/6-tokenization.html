Phase 6 · Lesson 6

Tokenization: BPE and friends

A language model never sees letters or words. It sees integers from a fixed vocabulary of word pieces, learned by a 1990s compression trick. That choice quietly sets your context length, your bill and some of the model's strangest mistakes.

🧰 You'll need (quick reminders)
  • Each token id picks one row of the embedding table (V rows × d columns), and the output layer scores all V entries (Lessons 5.1 and 6.4).
  • Attention cost grows with the square of the number of tokens n (Lesson 6.1).
🎯 Hook

Translate the same text into different languages and run each through the same tokenizer. A 2023 study found the token counts can differ by up to 15 times. Since APIs charge per token and context windows are counted in tokens, some languages pay more and fit less, before the model has done anything.

And when Meta built Llama 3, one of its upgrades wasn't in the network at all: a bigger tokenizer (128K tokens instead of Llama 2's) packed English into 3.94 characters per token instead of 3.17, so the model “reads” more text for the same compute.

How does a model decide what a “token” is, and why not just use letters or words? You're about to run the algorithm by hand, merge by merge.

Numbers first: letters are too long, words are too many

Take the sentence “the tokenizer learns which pieces of text are common” (52 characters, 9 words).

Characters make sequences long (and attention is quadratic in length). Words make the vocabulary enormous and still fail on typos, names and new words. Subwords sit in between: common words stay whole, rare words split into reusable pieces.

🤔 Why this? Subword tokens
  1. The problem before Word-level translation models had a fixed vocabulary and mapped everything else to an unknown token; Sennrich et al. (2015) note translation is an “open-vocabulary problem” (names, compounds, new words).
  2. What people tried Back-off dictionaries for unknown words; character-level models, which handle anything but make sequences several times longer (about 4× versus a modern tokenizer's ~4 characters per token).
  3. Why this works Learn a vocabulary of frequent pieces from data: “the” is one token, “tokenizers” is two or three. No word is ever unknown (in the worst case it's spelled out in small pieces) and typical English needs about 4 characters per token in modern tokenizers.
  4. What it costs, when it fails The model sees pieces, not letters, so spelling, counting letters and character-level edits get harder. Pieces depend on the training data: languages and domains underrepresented there split into many more tokens.
  5. What refined it BPE (below), WordPiece, Unigram/SentencePiece, and byte-level fallback so nothing is unknown.
💡 Big idea A tokenizer is compression learned from data: start from single characters (or bytes), and repeatedly glue together the pair that appears most often. Frequent strings become single tokens; rare ones stay in pieces. The vocabulary size is the dial between short sequences and a big embedding table.
🧠 Analogy: texting shorthand

If you text “see you later” fifty times a day, you start typing “cu l8r”. You didn't plan a code; you noticed what repeats and shortened it. BPE does that systematically: count every adjacent pair of symbols, invent a new symbol for the most common pair, repeat. After enough rounds, frequent words are a single symbol and the rest are spelled with common chunks.

Byte-pair encoding, by hand

BPE (Sennrich, Haddow and Birch, 2015, borrowing a 1994 compression algorithm by Gage) trains like this:

  1. Split every word in the corpus into characters, plus an end-of-word marker “_”.
  2. Count every adjacent pair across the corpus (weighted by how often each word occurs).
  3. Merge the most frequent pair into one new symbol and record the merge rule. Repeat until the vocabulary is the size you want.

To tokenize new text, apply the recorded merges in the same order. The AI Engineer course runs the original paper's corpus (AI Engineer 0.3); here you can edit the corpus, pick merges yourself and break things.

🤔 Why this? Byte-pair encoding (BPE)
  1. The problem before A fixed word list can't cover an open vocabulary; character models make sequences long.
  2. What people tried Hand-made morphology rules; dictionaries for rare words; character n-grams.
  3. Why this works Merging the most frequent pair is the greedy way to shorten the corpus fastest (in the playground, each merge saved as many tokens as the pair's count: 105 → 94 → 85 → 76…). It's simple, deterministic and language-agnostic, and the vocabulary size is exactly the number of merges plus the base symbols.
  4. What it costs, when it fails It's greedy: it never asks which pieces mean something, so splits can be odd (“lower_” before “lowest”). Merges reflect the training corpus, so other languages and domains get fewer merges and more tokens. Tokenizing must apply merges in order, which is slower than a lookup.
  5. What refined it Byte-level BPE (GPT-2) for full coverage; WordPiece (BERT), which scores pairs by frequency relative to their parts; Unigram (SentencePiece), which starts big and prunes; pre-tokenization rules (splitting digits, not merging across letters and punctuation).

Bytes, so nothing is unknown

Basic BPE starts from characters. But Unicode has a huge number of characters; GPT-2's paper notes that covering them all would mean a base vocabulary “of over 130,000” before a single merge. Their answer: run BPE on UTF-8 bytes. There are only 256 possible bytes, every string is a sequence of them, and the merges are learned on top. “ï” becomes two byte-tokens, an emoji four, and nothing is ever [UNK].

🤔 Why this? Byte-level fallback
  1. The problem before Character-level BPE either needs every Unicode character in its base vocabulary (over 130,000) or maps unseen characters (emoji, rare scripts, binary junk) to [UNK], losing information.
  2. What people tried Huge base vocabularies; an [UNK] token and hope.
  3. Why this works Any text is UTF-8 bytes, so a base of 256 byte tokens covers everything; frequent byte sequences still merge into normal subwords. GPT-2 also stopped merges across character categories, so “dog”, “dog.” and “dog!” don't each eat a vocabulary slot (it allowed spaces to stick to the next word).
  4. What it costs, when it fails Rare characters cost several tokens each (an emoji is 4 bytes); a token can be half a character, so some token sequences aren't valid text on their own.
  5. What refined it The same idea everywhere: Qwen3 uses byte-level BPE (151,669 tokens); Gemma 3's SentencePiece tokenizer adds “byte-level encodings” as a fallback; pre-tokenizers that cap number chunks (below).

The friends: WordPiece and Unigram (SentencePiece)

AlgorithmHow it builds the vocabularyUsed by
BPEStart small, merge the most frequent pairGPT-2 and later GPTs, Llama 3, Qwen3 (byte-level)

Vocabulary size: the dial

More merges → shorter sequences (cheaper attention, more text per context window) but a bigger embedding table and output layer, and rarer tokens that the model sees less often in training.

At real scale, a 262k vocabulary with d = 2,048 is 537 million parameters: over half of a 1B model even when tied (double that untied), which is why small models keep vocabularies modest and tie the tables.

✏️ Worked example: what a bigger vocabulary buys
  • Llama 3's paper: moving to a 128K vocabulary raised English compression from 3.17 to 3.94 characters per token. The same 8,000-word document (about 48,000 characters) drops from ≈ 15,100 tokens to ≈ 12,200: 19% fewer.
  • Attention on that document: 15,100² ≈ 228 million scores vs 12,200² ≈ 149 million, about 35% fewer.
  • The price: the embedding table goes from 32,000 × 4,096 ≈ 131 million to 128,000 × 4,096 ≈ 524 million parameters (and the same again for an untied output layer). For an 8B model that's affordable; for a 100M model it would be most of the network.

Quirks you'll actually hit

  • Numbers. Pre-tokenizers decide how digits group. OpenAI's cl100k_base and o200k_base encodings split runs of digits into chunks of at most 3 (the \p{N}{1,3} rule in tiktoken's source); Gemma 3 splits every digit. Arithmetic is harder when “1234567” is “123” “456” “7”.
  • Spaces are part of tokens. In GPT-style tokenizers “ cat” (with a leading space) and “cat” are different tokens; trailing spaces in prompts change the tokens the model sees.
  • Letters are hidden. A word that is one token gives the model no direct view of its letters, which is why “how many r's in this word?” trips models up.
  • Languages and code cost differently. Measure with the real tokenizer on real traffic; the cost side is AI Engineer 0.3.

🧰 Tools you'll actually use

Hugging Face tokenizers trains a real byte-level BPE in a second, no downloads:

from tokenizers import Tokenizer, models, trainers, pre_tokenizers, decoders

corpus = ["low lower slow slower slowest newest widest fast fastest"] * 50
tok = Tokenizer(models.BPE())
tok.pre_tokenizer = pre_tokenizers.ByteLevel(add_prefix_space=True)   # GPT-2 style: bytes, space glued to the word
tok.decoder = decoders.ByteLevel()
trainer = trainers.BpeTrainer(vocab_size=300, initial_alphabet=pre_tokenizers.ByteLevel.alphabet())
tok.train_from_iterator(corpus, trainer)

print(tok.get_vocab_size())
for text in ["lowest", "slowest!", "naïve 🙂"]:
    enc = tok.encode(text)
    print(enc.tokens, "->", tok.decode(enc.ids))

# What we got (tokenizers 0.22):

“Ġ” is how byte-level BPE displays a space; “ï” became two byte tokens and the emoji four, and decoding still gives the exact text back. To count tokens for a real model, use its own tokenizer. These download the vocabulary files on first use, so we didn't run them here:

import tiktoken
enc = tiktoken.get_encoding("o200k_base")          # or tiktoken.encoding_for_model("gpt-4o")
print(len(enc.encode("How many tokens is this?")))

from transformers import AutoTokenizer
tok = AutoTokenizer.from_pretrained("openai-community/gpt2")
print(tok.tokenize("Tokenizers split rare words"))

Gotcha: a model only works with the exact tokenizer it was trained with. Swapping tokenizers (or adding tokens) means new embedding rows that must be trained.

🎤 Interview angle

“How does BPE work, and how would you choose a vocabulary size?” A strong answer:

  • Start from bytes or characters; repeatedly merge the most frequent adjacent pair; record merges; tokenize by applying them in order.
  • Byte-level base (256) means no unknown tokens; pre-tokenization rules (no merges across letters/punctuation, digit splitting) shape the result.
  • Vocabulary size trades sequence length (attention ∝ n², context capacity) against embedding/output parameters and rare-token training; typical 2024–25 choices are 128K–262K for large models.
  • Mentions consequences: language unfairness (up to 15× token counts), letter-level blindness, number splitting, and that WordPiece and Unigram/SentencePiece are the alternatives.
🏭 In the real world
Subword units for open-vocabulary translation 📜 History · 2015 Sennrich, Haddow & Birch: Neural Machine Translation of Rare Words with Subword Units

How: adapted the byte-pair-encoding compression algorithm to learn word pieces from the training corpus.

Why this method: rare and unknown words (names, compounds) can be translated piece by piece, beating a back-off dictionary.

Byte-level BPE 🏢 OpenAI · 2019 Radford et al.: GPT-2

How: BPE over UTF-8 bytes (base vocabulary 256), with merges blocked across character categories; 50,257 tokens.

Why this method: any string can be modelled, with no unknown token and no lowercasing or other preprocessing.

A tokenizer that doesn't need spaces 🧰 Open source Kudo & Richardson: SentencePiece

How: trains BPE or Unigram directly from raw sentences, treating whitespace as a normal symbol.

Why this method: works the same for languages without spaces between words (Japanese, Chinese); used by T5 and Gemma.

A bigger vocabulary for a better model 🏢 Meta · 2024 The Llama 3 Herd of Models

How: 100K tokens from tiktoken plus 28K tokens for non-English languages.

Why this method: 3.17 → 3.94 characters per token on English, and the extra tokens improved both compression and downstream results in other languages “with no impact on English tokenization”.

Measuring the language gap 🧪 Research · 2023 Petrov et al.: Language Model Tokenizers Introduce Unfairness Between Languages

How: tokenized the same parallel text in many languages with many tokenizers.

Why this method: found differences of up to 15× in token count, even for tokenizers trained to be multilingual, which means different costs and context limits per language.

🤯 Fun fact · dog. dog! dog?

When OpenAI first ran plain BPE on bytes for GPT-2, the greedy merges filled the vocabulary with many copies of common words glued to punctuation, like “dog.”, “dog!” and “dog?”. Their fix was one rule: never merge across character categories (letters, digits, punctuation), except to let a space stick to the following word. That's why “ dog” is a token and the “!” after it is separate.

Check yourself

1. A document is 40,000 characters. Tokenizer A averages 3.2 characters per token, tokenizer B 4.0. Roughly how much less attention work (∝ n²) does B need for one pass?
A gives 40,000 / 3.2 = 12,500 tokens, B gives 40,000 / 4.0 = 10,000 (20% fewer). Attention scores scale with n²: 10,000² / 12,500² = 0.64, so about 36% less work. Fewer tokens also leave more room in a fixed context window.
2. Your chatbot works well in English but users writing in Hindi complain that long messages get cut off and replies are slower. The model is fine. What's the likely cause?
Tokenizers learn merges from their training text. Scripts that were rare there get few merges, so each word becomes many small (often byte-level) tokens. Studies found up to 15× differences for the same content. Measure token counts per language; a tokenizer with multilingual merges (like Llama 3's added 28K tokens) narrows the gap.
3. You're designing a 120M-parameter model with d = 768. A colleague wants a 256,000-token vocabulary “because big models use it”. What's the main problem?
Embedding parameters are V × d: 256,000 × 768 = 196.6M, already above 120M before a single transformer block (and doubled if the output layer is untied). Large models can afford 128K–262K vocabularies because the table is a small share of billions of parameters. GPT-2 small, at 124M, uses 50,257 tokens and still spends 31% of its parameters on the table.
📝 TL;DR
  • Characters make sequences long; words need huge vocabularies and still meet unknown words. Subword tokens sit in between.
  • BPE: start from characters or bytes, repeatedly merge the most frequent pair, apply merges in order to tokenize.
  • Byte-level BPE (GPT-2, base 256) means nothing is ever unknown; WordPiece (BERT) and Unigram/SentencePiece (T5, Gemma) are the main alternatives.
  • Vocabulary size trades sequence length against embedding size: GPT-2 50,257; Llama 3 128K (3.17 → 3.94 chars/token); Qwen3 151,669; Gemma 3 262k.
  • Quirks: languages can differ up to 15× in token count; digits get chunked or split; spaces are part of tokens; models don't see letters.
