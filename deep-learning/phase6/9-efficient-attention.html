Phase 6 · Lesson 9

Efficient attention: KV cache, FlashAttention, GQA

A GPU that can do 312 trillion operations a second spends most of a chatbot's reply waiting for memory. Three tricks fix the waiting: remember instead of recompute, share instead of copy, and never write the big matrix down.

🧰 You'll need (quick reminders)
  • Attention: each query is compared with every key (QKᵀ / √d), softmaxed, then used to average the values V (Lesson 6.1). Several heads do this in parallel (6.2).
  • A decoder generates one token at a time, and a causal mask means a token only looks left (6.4, 6.7).
  • A model with N parameters costs about 2·N FLOPs per generated token (6.8).
🎯 Hook

An NVIDIA A100 does 312 trillion bf16 operations per second and reads its memory at about 2 TB/s. Generating one token with an 8-billion-parameter model needs about 16 billion operations: 0.05 ms of math. But it also has to read all 16 GB of weights from memory: 7.8 ms. The math units sit idle about 99% of the time.

Meanwhile every chatbot, coding assistant and agent you use generates text exactly this way, token by token, for millions of users. And the memory problem gets worse with every token of conversation, because the model has to remember the whole conversation in a structure called the KV cache.

Where does the memory go, and how do Llama, DeepSeek and FlashAttention claw it back? You'll size real caches, fit a 70B model's long context onto one GPU, and watch a 4,096 × 4,096 matrix never get written.

Numbers first: decoding is memory-bound

Arithmetic intensity is “FLOPs per byte read”. An A100 can do 312 × 10¹² ÷ 2.04 × 10¹² ≈ 153 FLOPs for each byte it reads. Generating one token for one user does 2 FLOPs per weight and reads 2 bytes per weight (bf16): 1 FLOP per byte. That's 150× too little work to keep the GPU busy.

The fix everyone uses: batching. Read the weights once, apply them to many users' tokens at the same time. But each user also brings their own cached memory of the conversation, and that has to be read too.

🔮 Predict: going from 1 user to 100 users at once (1,000-token conversations), does throughput go up 100×, 50×, or barely at all? And what happens with 8,000-token conversations?

The KV cache: remember, don't recompute

To generate token 1,001, the new token's query must be compared with the keys of tokens 1 to 1,000 and average their values. Those keys and values don't change (the causal mask means old tokens never look at new ones). So compute each token's K and V once, store them, and reuse them for every later step. That store is the KV cache.

KV bytes = 2 (K and V) × layers × kv_heads × head_dim × tokens × batch × bytes per value
✏️ Worked example: Llama 3 8B

From the Llama 3 paper: 32 layers, 32 query heads, 8 key/value heads, model width 4,096 → head_dim = 4096 ÷ 32 = 128. In bf16 (2 bytes):

2 × 32 × 8 × 128 × 2 bytes = 131,072 bytes = 128 KiB per token

An 8,192-token conversation: 128 KiB × 8,192 = 1 GiB. At 128k tokens (its maximum): 16 GiB, as much as the model's own weights. With 32 K/V heads instead of 8 it would be 4× that: 64 GiB.

The 70B model (80 layers, 8 K/V heads, head_dim 128): 2 × 80 × 8 × 128 × 2 = 320 KiB per token, so 40 GiB at 128k.

🤔 Why this? KV cache
  1. The problem before Without a cache, generating token t means rerunning the whole model over all t tokens. A 1,000-token answer costs about 1 + 2 + … + 1,000 ≈ 500,000 token-passes instead of 1,000: 500× the work.
  2. What people tried RNNs carry a fixed-size state instead (Lesson 5.2), which is cheap but forgets; recomputing attention from scratch each step, which is exact but quadratic.
  3. Why this works With a causal mask, a token's K and V depend only on itself and earlier tokens, so they never change. Store them: each new step computes K, V and Q for one token and attends to the stored ones. Work per step stays proportional to the model, not to t times the model.
  4. What it costs, when it fails Memory that grows linearly with tokens × batch × layers (128 KiB per token for Llama 3 8B) and must be read every step, which makes long-context decoding memory-bound. It fragments GPU memory when requests have different lengths.
  5. What refined it Shrinking each entry (GQA, MQA, MLA below, FP8/INT4 cache), paging it like virtual memory (vLLM's PagedAttention; AI Engineer 7.4), sharing cached prefixes across requests, and windowed caches (6.11).

MQA and GQA: share keys and values across heads

Multi-head attention (6.2) gives every head its own Q, K and V. But only K and V get cached. In 2019 Noam Shazeer asked: what if all heads share one K and V? That's multi-query attention (MQA): the cache shrinks by the number of heads (32× for 32 heads). Quality dropped a little, and training could be unstable.

Grouped-query attention (GQA, Ainslie et al. 2023) is the middle ground: split the query heads into groups, and each group shares one K/V head. Llama 3 uses 32 query heads in 8 groups of 4: a 4× smaller cache, with quality close to full multi-head attention.

🤔 Why this? GQA (and MQA)
  1. The problem before Shazeer's MQA paper put it exactly: incremental decoding is limited by “the memory-bandwidth cost of repeatedly loading the large ‘keys’ and ‘values’ tensors”. With 64 K/V heads, Llama 3 70B's cache would be 2.5 MiB per token.
  2. What people tried MQA (one K/V head for all): huge savings, but some quality loss and instability; plain MHA: best quality, biggest cache.
  3. Why this works Heads mostly need their own queries (what to look for); keys and values can be shared by a few heads with little loss. G groups → cache ÷ (heads ÷ G). The GQA paper also showed you can convert an existing MHA checkpoint by mean-pooling its K/V heads per group and “uptraining” with only 5% of the original pretraining compute.
  4. What it costs, when it fails Fewer K/V parameters, so a small quality cost that grows as groups shrink; one more hyperparameter. It shrinks the cache but not the attention math, and with tensor parallelism you can't split fewer K/V heads across more GPUs.
  5. What refined it Multi-head latent attention (MLA, DeepSeek-V2, 2024): cache one small compressed latent vector per token and rebuild per-head K and V from it. DeepSeek reported a 93.3% smaller KV cache than their earlier 67B dense model.

How small is MLA? DeepSeek-V3 caches a 512-number latent plus one 64-number rotary key per layer: 61 layers × 576 × 2 bytes = 68.6 KiB per token, for a 671B model. Full multi-head attention with its 128 heads of size 128 would need 3.8 MiB per token, 57× more.

FlashAttention: never write the big matrix down

So far, decoding. During training and when reading a long prompt (“prefill”), attention handles all n tokens at once, and the naive version builds the full n × n score matrix S = QKᵀ. At 4,096 tokens that's 16.8 million scores per head, written to the GPU's main memory (HBM), read back for the softmax, written again as probabilities P, read again to multiply by V.

The GPU has a tiny, fast scratchpad on each compute unit (SRAM). On an A100: 192 KB per unit, 108 units, about 19 TB/s, vs 40–80 GB of HBM at 1.5–2.0 TB/s. FlashAttention (Dao et al., 2022) cuts Q, K and V into tiles that fit in SRAM, computes each tile's scores, softmax and output contribution right there, and only writes the final output O. The n × n matrix never exists in HBM.

The clever bit is the softmax: you need the max and the sum over a whole row, but you only see one tile at a time. The fix is an online softmax: keep a running max m and running sum ℓ, and when a new tile has a bigger max, rescale what you had.

✏️ Worked example: online softmax over two tiles

One row of scores, seen as tile 1 = [1, 2] then tile 2 = [3].

  • Tile 1: m = 2, ℓ = e1−2 + e2−2 = 0.368 + 1 = 1.368.
  • Tile 2 has 3 > 2. New m = 3; rescale the old sum by e2−3 = 0.368: ℓ = 1.368 × 0.368 + e0 = 0.503 + 1 = 1.503.
  • Check against the whole row at once: e−2 + e−1 + e0 = 0.135 + 0.368 + 1 = 1.503. Identical.

The partial outputs (weights × V) get the same rescaling. So FlashAttention is exact: same answer as the naive version, up to floating-point rounding. Numerics of softmax: math 8.5.

What you should see: at n = 4,096, standard attention moves about 35 million numbers through HBM (writing and re-reading the score matrix twice dominates), and needs 32 MiB per head just to hold the scores. Flash with 128-wide tiles moves about 9 million and stores no scores at all (3.8× less traffic). With 64-wide tiles it re-reads K and V twice as often and the gain halves. Bigger tiles mean fewer passes over K and V, but a 256 tile needs 224 KB of SRAM, more than the A100's 192 KB per unit: it doesn't fit. At n = 65,536 the standard method needs 8 GiB per head per sequence for the scores; that, not the math, is why long-context training was impossible before. Same FLOPs, far fewer bytes: speed comes from not waiting on memory.

🤔 Why this? FlashAttention
  1. The problem before Naive attention reads and writes the n × n matrix several times: at n = 4,096 that's tens of millions of numbers per head through slow HBM, and O(n²) memory that rules out long sequences. The GPU's math units wait on memory.
  2. What people tried Approximate attention (sparse patterns, low-rank, linear kernels) to reduce the FLOPs. Many cut FLOPs on paper but weren't faster in wall-clock time, and they changed the model's output.
  3. Why this works Be IO-aware: count bytes, not FLOPs. Tile Q, K, V into SRAM-sized blocks, fuse scores, mask, softmax and P·V into one kernel with an online softmax, and recompute small pieces in the backward pass instead of storing S. Exact output, O(n) extra memory. The paper reported 3× faster training on GPT-2 (1k tokens) and 15% on BERT-large vs the MLPerf record.
  4. What it costs, when it fails Hand-written kernels per GPU generation (A100, H100, B200 differ); FLOPs are still O(n²), so very long contexts remain expensive (6.11). Custom attention variants need kernel support.
  5. What refined it FlashAttention-2 (2023: better work split, ~2× faster, up to 73% of A100 peak), FlashAttention-3 (2024: H100 asynchrony and FP8, up to 740 TFLOPs/s in FP16), FlashAttention-4 (2026: Blackwell B200, up to 1,613 TFLOPs/s in BF16). In PyTorch you get these through F.scaled_dot_product_attention.

🧰 Tools you'll actually use

F.scaled_dot_product_attention (SDPA) picks the fastest backend for your hardware (FlashAttention, memory-efficient, cuDNN or plain math on CPU). is_causal=True applies the causal mask; enable_gqa=True lets K/V have fewer heads than Q. Here it is checked against attention written by hand, plus a KV-cache size helper.

import torch, torch.nn.functional as F

torch.manual_seed(0)
B, Hq, Hkv, T, d = 2, 8, 2, 16, 64                 # 8 query heads share 2 K/V heads (GQA, groups of 4)
q = torch.randn(B, Hq, T, d)
k = torch.randn(B, Hkv, T, d)
v = torch.randn(B, Hkv, T, d)

# By hand: repeat each K/V head for its 4 query heads, then masked softmax(QK^T / sqrt(d)) V
k4, v4 = k.repeat_interleave(Hq // Hkv, dim=1), v.repeat_interleave(Hq // Hkv, dim=1)
s = q @ k4.transpose(-2, -1) / d**0.5
s = s.masked_fill(torch.triu(torch.ones(T, T, dtype=torch.bool), 1), float("-inf"))
manual = s.softmax(-1) @ v4

fused = F.scaled_dot_product_attention(q, k, v, is_causal=True, enable_gqa=True)
print("max difference:", (manual - fused).abs().max().item())

def kv_cache_bytes(layers, kv_heads, head_dim, seq, batch, bytes_per_value=2):
    return 2 * layers * kv_heads * head_dim * seq * batch * bytes_per_value   # 2 = one K and one V

print("Llama 3 8B, 8k tokens, bf16: %.2f GiB" % (kv_cache_bytes(32, 8, 128, 8192, 1) / 2**30))
print("same, if it had 32 K/V heads: %.2f GiB" % (kv_cache_bytes(32, 32, 128, 8192, 1) / 2**30))

# What we got (torch 2.8, CPU):
# max difference: 4.470348358154297e-07
# Llama 3 8B, 8k tokens, bf16: 1.00 GiB

On a GPU, with torch.nn.attention.sdpa_kernel(SDPBackend.FLASH_ATTENTION): forces the flash backend (it errors if your shapes or dtype aren't supported, a handy check). In Hugging Face, the cache is a DynamicCache passed as past_key_values; serving engines (vLLM, SGLang, TensorRT-LLM) manage it in pages for you.

🎤 Interview angle

“Why is LLM inference memory-bound, and what would you do about it?” A strong answer:

  • Decoding does ~2 FLOPs per weight per token but reads every weight: ~1 FLOP/byte vs a GPU's ~150. Batching amortizes the weights; the KV cache is the per-user memory that limits batch size.
  • Computes the cache: 2 · layers · kv_heads · head_dim · tokens · bytes (Llama 3 8B: 128 KiB/token in bf16).
  • Fixes: GQA/MQA/MLA, FP8 cache, paged memory, prefix caching, sliding windows; quantized weights.
  • Separates prefill (compute-bound, FlashAttention helps most) from decode (memory-bound, cache size matters most), and knows FlashAttention is exact, not an approximation.
🏭 In the real world
FlashAttention 🧪 Research · 2022 Dao et al.: FlashAttention: Fast and Memory-Efficient Exact Attention with IO-Awareness

How: tiling + online softmax + recomputation in the backward pass; later v2, v3 (H100) and v4 (B200). Code: flash-attention.

Why this method: exact attention that is faster and fits long sequences; it became the default kernel in PyTorch and most training stacks.

GQA in Llama 3 🏢 Meta · 2024 The Llama 3 Herd of Models

How: 8 key/value heads in every model size (8B: 32 query heads; 405B: 128).

Why this method: in their words, “to improve inference speed and to reduce the size of key-value caches during decoding”.

Multi-head latent attention 🏢 DeepSeek · 2024 DeepSeek-V2

How: cache a compressed latent per token instead of per-head K and V; reused in DeepSeek-V3.

Why this method: KV cache reduced by 93.3% and maximum generation throughput up 5.76× vs DeepSeek 67B.

Multi-query attention 📜 History · 2019 Shazeer: Fast Transformer Decoding: One Write-Head is All You Need

How: one shared K and V for all heads.

Why this method: decoding speed is limited by memory bandwidth for K and V, so shrink them; GQA (Ainslie et al. 2023) later recovered most of the quality.

🤯 Fun fact · the fastest memory is the smallest

An A100's on-chip SRAM adds up to about 20 MB (192 KB × 108 units), roughly 4,000× smaller than its 80 GB of HBM, but around 10× faster. FlashAttention's whole trick is to treat that 20 MB like a workbench and HBM like a warehouse across town: carry over only what you need, finish the job on the bench, ship back only the result. The paper also proves a lower bound: no exact attention algorithm can asymptotically beat its number of HBM accesses across all SRAM sizes.

Check yourself

1. A model has 40 layers, 8 K/V heads of dimension 128, and caches in bf16. How much KV cache does one 16,384-token conversation need?
Per token: 2 × 40 × 8 × 128 × 2 bytes = 163,840 bytes = 160 KiB. × 16,384 tokens = 2,684,354,560 bytes = 2.5 GiB. (1.25 forgets that both K and V are stored; 20 uses 64 heads instead of 8.)
2. Your chat service runs fine with short chats, but when users paste long documents, throughput collapses and you hit out-of-memory errors at much smaller batch sizes. The GPU's math units show low utilization. What's the main culprit?
Weights don't change with input length; the per-user KV cache does (e.g. 128 KiB per token for Llama 3 8B). Long documents fill memory, so fewer users fit per batch, and decoding stays memory-bound (low math utilization). Fixes target the cache: GQA/MLA models, FP8 caches, paged allocation, prefix caching, or limiting context.
3. A colleague says “FlashAttention is fast because it approximates attention with fewer FLOPs.” What's right?
FlashAttention is IO-aware, not approximate. It keeps tiles of Q, K, V in fast on-chip SRAM, fuses softmax and P·V with a running max and sum, and never materializes the n × n matrix in HBM. Output equals standard attention up to rounding. The KV cache is a separate (decoding) trick.
📝 TL;DR
  • Decoding reads every weight for ~2 FLOPs each: ~1 FLOP/byte vs the GPU's ~150, so it's memory-bound. Batching helps until memory runs out.
  • KV cache: store each token's K and V once. Bytes = 2 · layers · kv_heads · head_dim · tokens · batch · bytes/value (Llama 3 8B: 128 KiB/token bf16, 16 GiB at 128k).
  • MQA shares one K/V head; GQA shares one per group (Llama 3: 8 K/V heads); MLA caches a compressed latent (DeepSeek: −93%).
  • FlashAttention: tiles in SRAM + online softmax; exact, O(n) memory, far less HBM traffic. v2, v3 (H100), v4 (B200). Use F.scaled_dot_product_attention.
  • Sparse and linear attention change the model; FlashAttention and the KV cache don't.
