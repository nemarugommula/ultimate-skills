Phase 2 · Lesson 6

Debugging training: read the loss curve, overfit one batch

Most broken training runs don't crash. They just learn a little worse, quietly, forever. This lesson is a field guide: the five-minute checks that catch most bugs, a gallery of loss curves and what they mean, and a game to train your eye.

🧰 You'll need (quick reminders)
  • Cross-entropy loss is −ln(probability of the right class) (Lesson 1.1, math 6.3).
  • The PyTorch loop: zero_grad → forward → loss → backward → step (Lesson 1.3); the learning rate and how to choose it (1.6).
  • This phase's failure modes: vanishing/exploding gradients (2.1), train/eval modes (2.3, 2.4), overfitting (2.4).
🎯 Hook

In 2019 Andrej Karpathy wrote a blog post that thousands of engineers have bookmarked: “A Recipe for Training Neural Networks”. Its central warning: “Neural net training fails silently.” Normal code throws an exception when you plug an integer where a string belongs. A network with flipped labels, a forgotten zero_grad() or a broadcasting mistake still trains. It just gets a bit worse, and nothing tells you.

His antidote is a set of paranoid habits: look at your data, check the loss before training, overfit a single batch, visualize what goes in just before the network. Practitioners at every lab use some version of them.

How do you tell a bug from a bad hyperparameter from a model that's simply too small, by looking at a few curves? You'll diagnose ten loss curves against the clock, hunt hidden bugs with the overfit-one-batch test, and run a learning-rate finder.

Numbers first: the loss you should see at step 0

Before any training, a sensibly initialized classifier is clueless: it gives each of the K classes about the same probability, 1/K. Cross-entropy is −ln(probability of the right class), so the very first loss should be about ln(K):

Classes KUniform probabilityExpected initial loss ln(K)
2 (cat / dog)0.50.693
10 (CIFAR-10, digits)0.12.303
1,000 (ImageNet)0.0016.908
50,257 (GPT-2's vocabulary)0.0000210.825

Karpathy's recipe: “Verify that your loss starts at the correct loss value”, e.g. −log(1/n_classes) on a softmax. A first loss of 40 instead of 2.3 means the network starts out confidently wrong: the final layer's weights or the inputs are badly scaled. A first loss far below ln(K) before training is even more suspicious: the answer may be leaking into the input. It costs one forward pass to check.

💡 Big idea Debug a network like a scientist, from the cheapest check to the most expensive: look at the data, check the initial loss, overfit one tiny batch, then train for real while watching training loss, validation loss and gradient norms. Each check rules out a whole family of bugs before you burn hours of compute. And read loss curves like an X-ray: their shape tells you what's wrong.
🧠 Analogy: a mechanic's checklist

A car that won't start: a good mechanic doesn't rebuild the engine first. Is there fuel? Does the battery turn the starter? Does it run on the stand with the wheels off the ground? Overfitting one batch is “running on the stand”: if the network can't even memorize 12 examples, the problem is the engine (code), not the road (data, hyperparameters).

Which bug is it?

What you should see: with no bugs, the first loss is 1.099 (= ln 3, check 2 passes) and it is down to about 0.01 by step 50. Each bug leaves a fingerprint. Inputs ×100: first loss 17.1, far above ln 3, then everything dies. Biases at −3: every ReLU is off, the gradient is about 10⁻¹⁷ and the loss sits at exactly 1.099. LR ÷1000: 1.099 → 1.045 in 300 steps. LR ×100: loss jumps to 9+ and units die. Forgot zero_grad: the gradients pile up, so the loss hits 0 in 10 steps and then explodes to about 10 as the accumulated push keeps going. (In real PyTorch on one batch the loss can even stay at 0; the giveaway is a gradient norm that keeps growing, which you'll measure in Lab 2.) And the sneaky one: two swapped labels pass the test. The network happily memorizes the wrong labels too (loss 0.03 by step 300, under the 0.05 bar). Only looking at the data catches it: two dots have the wrong color for their cluster. That's why check 1 comes first. (Scramble many labels and memorizing takes much longer, but networks can eventually memorize even random labels.)

🤔 Why this? Overfit a single batch first
  1. The problem before A full training run takes hours, and a bad result has a hundred possible causes: data, model size, learning rate, a bug. You can't tell which by staring at a 70% accuracy.
  2. What people tried Launching full runs and tweaking hyperparameters until something works, which wastes compute and can hide a bug for weeks.
  3. Why this works A network with thousands of parameters can memorize a handful of examples, so on one tiny batch the loss must reach about 0 (Karpathy: “as little as two” examples). If it doesn't, the pipeline is broken, and it's broken in seconds instead of hours. It isolates the code (forward, loss, backward, optimizer wiring) from the hard questions (generalization, hyperparameters).
  4. What it costs, when it fails It only proves the model can fit; it says nothing about generalization. It can't catch bugs that are self-consistent: misaligned labels, leakage and wrong preprocessing all memorize fine, and so can a loop that never zeroes its gradients (watch the gradient norm for that one). Turn off augmentation and dropout for the test, or the loss won't reach 0 for innocent reasons.
  5. What refined it The rest of the recipe: visualize data just before the model, input-independent baselines, monitoring gradient norms and dead units, LR range tests (below), fixed seeds and small ablations (Lesson 10.6 on experiment tracking).

Playground: the learning-rate range test

Leslie Smith (2015) proposed a one-run way to find a sensible learning rate: train briefly while the learning rate grows exponentially from tiny to huge, and plot loss against learning rate. The loss doesn't move at first (too small), drops fastest in the useful range, then blows up. A common rule of thumb: pick a value about 10× below where the loss is lowest, inside the steepest-descent region.

✏️ Worked example: five bugs you can find by printing shapes
  • pred is (32, 1), target is (32,): (pred - target) is (32, 32). The MSE averages 1,024 meaningless differences and trains anyway. Fix: pred.squeeze(-1).
  • nn.CrossEntropyLoss expects raw logits. Adding softmax before it applies softmax twice: for K = 10 the loss can never go below about 1.46 (even a perfectly confident model gets e/(e + 9) ≈ 0.23 for the right class), and the gradients are squashed.
  • Labels as floats (tensor([3.0, 1.0])) instead of class indices: CrossEntropyLoss raises “expected scalar type Long but found Float”. The tempting “fix” of casting the model output instead hides the real mistake; convert labels with .long(). (Float targets are only valid as full probability rows, the soft labels of Lesson 2.5.)
  • x.view(B, C, H, W) on data stored as (B, H, W, C) scrambles pixels without error. Use permute to reorder axes.
  • total_loss += loss instead of loss.item() keeps every step's graph alive: memory grows until the run dies.
🧰 Tools you'll actually use

Three checks in plain PyTorch: initial loss, overfit one batch, per-layer gradient norms, plus the classic broadcasting trap. For monitoring real runs, log the same numbers to TensorBoard, Weights & Biases or MLflow (Lesson 10.6); torch.autograd.set_detect_anomaly(True) points to the operation that produced a NaN (slow: debugging only).

import math, torch, torch.nn as nn

torch.manual_seed(0)
K = 10
model = nn.Sequential(nn.Linear(20, 64), nn.ReLU(), nn.Linear(64, K))
x, y = torch.randn(32, 20), torch.randint(0, K, (32,))     # ONE fixed batch
loss_fn = nn.CrossEntropyLoss()                             # expects raw logits

# Check 1: loss at init ≈ ln(K)
print(f"initial loss {loss_fn(model(x), y).item():.3f}  vs ln(K) = {math.log(K):.3f}")

# Check 2: overfit one batch (it must reach ~0, or the pipeline is broken)
opt = torch.optim.Adam(model.parameters(), lr=1e-2)
for step in range(300):
    opt.zero_grad()                     # forget this and gradients pile up
    loss = loss_fn(model(x), y)
    loss.backward()
    opt.step()
print(f"after 300 steps on one batch: {loss.item():.4f}")

# Check 3: per-layer gradient norms (vanishing? exploding?)
for name, p in model.named_parameters():
    if p.dim() == 2:
        print(f"{name:9s} grad norm {p.grad.norm():.1e}")

# A classic silent bug: broadcasting (N, 1) against (N,)
pred, target = torch.randn(32, 1), torch.randn(32)
print("silent broadcast:", (pred - target).shape)          # (32, 32), not (32,)

# What we got on a laptop CPU (torch 2.8):
# initial loss 2.425  vs ln(K) = 2.303
# after 300 steps on one batch: 0.0003
# 0.weight  grad norm 3.6e-04
# 2.weight  grad norm 5.2e-04
# silent broadcast: torch.Size([32, 32])

2.425 vs 2.303 is close enough (random init isn't exactly uniform); 25 would not be. The gradient norms are tiny at the end because the batch is memorized. Gotchas: run the overfit test with augmentation and dropout off; keep the exact same batch every step; when validating, wrap in model.eval() and torch.no_grad().

🎤 Interview angle

“Your model isn't learning. Walk me through how you debug it.” A strong answer:

  • Starts cheap: look at samples and labels right before the model, check shapes and dtypes, check the initial loss against ln(K).
  • Overfits a tiny batch to separate code bugs from generalization; knows what it can't catch (misaligned labels, leakage).
  • Reads curves: flat at ln(K) (not learning), slow linear (LR low), jagged then NaN (LR high or explosion), U-shaped val (overfitting), val bad from the start (eval-mode or preprocessing mismatch), sawtooth (no shuffling), too good (leakage).
  • Monitors per-layer gradient norms and dead units, uses an LR range test, changes one thing at a time with a fixed seed.
🏭 In the real world
The recipe 🧰 Blog · 2019 Karpathy: A Recipe for Training Neural Networks

How: become one with the data; set up end-to-end training with dumb baselines; verify the loss at init; overfit one batch; visualize just before the net; then regularize and tune.

Why this method: “neural net training fails silently”, so each step is designed to make a whole class of silent bugs visible before it costs a full run.

Sanity checks and babysitting 🧪 Course Stanford CS231n: Neural Networks Part 3

How: expect −ln(0.1) = 2.302 at init for CIFAR-10, overfit a tiny subset, and read loss, accuracy and update-to-weight ratios during training.

Why this method: the same checks, taught to a generation of practitioners alongside example curves of good and bad learning rates.

The LR range test 🧪 Research · 2015 Smith: Cyclical Learning Rates for Training Neural Networks

How: run a few epochs while the learning rate increases between a low and a high value, and read off where accuracy starts rising and where it falls apart.

Why this method: “enormously valuable whenever you are facing a new architecture or dataset”: one run replaces a grid search over learning rates.

Monitoring giant runs 🏢 Google · 2022 Chowdhery et al.: PaLM

How: watch the loss for spikes; when one appears, restart from a checkpoint about 100 steps earlier and skip the 200 to 500 batches around it.

Why this method: at that scale you can't rerun from scratch, so reading the loss curve live is part of the training system (Lesson 2.1).

🤯 Fun fact · the most dangerous curve looks perfect

A run that gets 99.9% validation accuracy in two epochs on a hard problem is more likely broken than brilliant. The usual culprits: the same images appear in both training and validation sets (near-duplicates count), or some input feature secretly encodes the label (a file name, a timestamp, the hospital a scan came from). The network takes the shortcut, the curves look wonderful, and the model fails in the real world. Karpathy's first step, “become one with the data”, is the defence.

Check yourself

1. A 100-class classifier's first logged loss is 4.6. Is that a problem?
Uniform guessing gives each class probability 0.01, and −ln(0.01) = 4.605. That's the healthy starting point. 0.693 is the value for 2 classes; a start near 0 before training would suggest leakage.
2. On a single batch of 8 examples, your loss drops to 0.3 and then stays there for 2,000 steps. What does that tell you?
Overfitting one batch should be trivial. A plateau above 0 points to a bug: softmax before CrossEntropyLoss, duplicate inputs with conflicting labels, frozen layers, dropout still on, or a learning rate far too small. Fix it before training on the full set.
3. Your training loss falls smoothly. Validation loss is 3× higher from the very first epoch, jumps around a lot, and never improves. The model has BatchNorm and dropout. Most likely?
Overfitting starts with validation improving, then rising. A gap from epoch 1 that never closes points to a mismatch between how training and validation are computed: BN batch statistics and active dropout in eval, or different normalization/resizing in the val transforms (Lessons 2.3, 2.4).
📝 TL;DR
  • Training fails silently. Debug cheapest-first: look at the data, check the initial loss (≈ ln K: 0.693, 2.303, 6.908), overfit one batch, then train while monitoring.
  • Overfit one batch to ~0 loss: if it can't, the code is broken. It can't catch self-consistent data bugs (misaligned labels, leakage): visualize the batch right before the model.
  • Curve shapes: flat at ln K = not learning; slow line = LR too low; jagged → NaN = LR too high or explosion; val U-shape = overfitting; val bad from epoch 1 = eval-mode/preprocessing mismatch; sawtooth = no shuffling; too good = leakage.
  • The LR range test sweeps the learning rate in one short run; pick about 10× below the loss minimum.
  • Usual PyTorch suspects: missing zero_grad(), softmax before CrossEntropyLoss, broadcasting (N, 1) vs (N,), view vs permute, forgetting model.eval(), accumulating loss tensors instead of .item().
