Backprop and autograd: how every weight learns its blame

A billion weights, and each one needs to know how it should change. Nudging them one by one would take decades per step. Backpropagation gets all billion answers for the price of about three forward passes.

🧰 You'll need (quick reminders)
  • The loss is one number; its gradient on a weight says how fast the loss changes if you nudge that weight (Lesson 1.1, math 3.3).
  • The chain rule: if a affects b and b affects c, then (effect of a on c) = (effect of a on b) × (effect of b on c) (math 3.2).
  • ReLU passes its input if positive, else outputs 0; its slope is 1 or 0 (Lesson 0.4).
🎯 Hook

Here's the obvious way to find a weight's gradient: nudge it by a tiny amount, run the network again, see how much the loss moved. It works. Now do it for a model with 1 billion weights. That's 1 billion extra forward passes per training step. At one second per pass, a single step takes about 32 years.

Yet PyTorch's loss.backward() returns all billion gradients in a time that is a small constant multiple of one forward pass: the theory guarantees under 6×, and it's typically 2–3×. How can you get a billion answers for the price of three?

Who uses this: every neural network you have ever heard of was trained this way. Backpropagation is the engine; autograd (automatic differentiation) is the machine in PyTorch and JAX that runs it for you on any code you write.

Numbers first: one neuron, by hand

One ReLU neuron with two inputs, scored by squared error. Inputs x₁ = 2, x₂ = −1; weights w₁ = 1.5, w₂ = 0.5, b = 0.5; target y = 1.

Forward: z = 1.5·2 + 0.5·(−1) + 0.5 = 3 → a = ReLU(3) = 3 → L = (3 − 1)² = 4

Now go backwards, asking at each step “how much does L change per unit change of this thing?”:

Backward: ∂L/∂a = 2(a − y) = 4 → ReLU is on, so ∂L/∂z = 4 × 1 = 4 → ∂L/∂w₁ = 4 × x₁ = 8, ∂L/∂w₂ = 4 × x₂ = −4, ∂L/∂b = 4

Every step is the same move: local derivative × the gradient that arrived from above. Nobody needs to know the whole formula; each piece only knows its own little derivative. That's backpropagation. PyTorch prints exactly 8, −4 and 4 for this neuron (Tools box).

💡 Big idea Write the computation as a graph of tiny operations. Run it forward once and remember every intermediate value. Then walk the graph backwards once, multiplying each node's local derivative by the gradient flowing in from above. One backward walk gives the gradient for every input at once, because all the weights share the same path back from the loss.
🧠 Analogy: blame flowing back through a company

A product launch failed by $4M (the loss). The CEO asks each division head “how much of this is yours?”. Each head only knows their own local relationships (“my team's output feeds 100% into the launch; Ana's code was 2× as influential as Bo's”) and passes blame down proportionally. Nobody needs the whole org chart; blame arrives at every employee after one sweep down the hierarchy. Asking each employee “what if you had done slightly differently?” and re-running the whole launch each time is finite differences.

Now drag b to −3: z goes negative, the ReLU outputs 0, the loss is 1 and every gradient behind the ReLU is exactly 0. That's a dead ReLU (Lesson 0.4) seen from the inside.

A real network is millions of these nodes (a matrix multiply is just many multiplies and adds), but backprop never needs anything cleverer. When one weight feeds several paths (the same weight used twice, or a value used by two later layers), the gradients from all paths add up.

Why one backward pass is enough

Count the work. Forward: each node computed once. Backward: each node does one small multiply per input. So the backward pass costs roughly the same as the forward pass (a bit more, because a matrix multiply needs two gradient matrix multiplies). In total the gradient costs a small constant times one forward pass, no matter how many weights there are.

What you should see: at GPT-2 small's 117 million weights nudging needs 234 million passes, about 7.4 years per step; backprop takes about 3 seconds. At a billion weights nudging needs 63 years per step. Training needs hundreds of thousands of steps. Without reverse-mode differentiation there would be no deep learning.

🤔 Why this? Reverse-mode autodiff (backpropagation)
  1. The problem before Training needs ∂loss/∂w for every weight. Finite differences cost 2 forward passes per weight: 2 × 10⁹ passes for a billion-weight model, every step. Deriving the formula by hand for each new architecture is slow and error-prone.
  2. What people tried Finite differences (fine for checking, hopeless for training); symbolic differentiation (expressions explode in size); forward-mode autodiff, which pushes derivatives forward alongside values but needs one pass per input, so a billion passes again.
  3. Why this works A loss is a function from many numbers (weights) to one number. Reverse mode starts at that one output and walks back, so it needs one sweep per output: just one. The AD survey by Baydin et al. puts the cost at c × (one evaluation), with c guaranteed below 6 and typically 2–3. Rumelhart, Hinton & Williams (1986) made it famous for neural nets as “backpropagation”.
  4. What it costs, when it fails Memory: the backward pass needs the forward pass's intermediate values, so every activation is stored until it's used; for big models activations, not weights, often fill the GPU. Gradients only exist where the function is differentiable: argmax, sampling and rounding give zero or no gradient (tricks like the reparameterization trick, Lesson 7.2, work around that).
  5. What refined it Autograd libraries that record any Python code as it runs (PyTorch, JAX); activation checkpointing, which stores fewer activations and recomputes them during backward, trading about one extra forward pass for much less memory (Chen et al. 2016); mixed precision to shrink what's stored (Lesson 10.2).

Autograd: PyTorch builds the graph while your code runs

You never draw the graph yourself. When a tensor has requires_grad=True, every operation on it is recorded on a tape: “this came from a multiply of these two”, each result carrying a grad_fn. Call loss.backward() and PyTorch walks that tape in reverse, exactly like the playground, and stores each leaf's gradient in its .grad.

You writeWhat autograd does
w = torch.tensor(1.5, requires_grad=True)Marks w as a leaf whose gradient you want (nn.Module parameters already are)
L = (torch.relu(w * x + b) - y) ** 2Runs the math and records each op; L.grad_fn is PowBackward0
L.backward()One reverse sweep; frees the recorded graph afterwards
w.gradThe gradient, added to whatever was already there
opt.zero_grad()Clears .grad (sets it to None by default) before the next backward
with torch.no_grad():Records nothing: for evaluation and manual weight updates

The “added to” is the most famous trap in PyTorch. Gradients accumulate on purpose (it lets you sum gradients over several small batches, Lesson 1.7), so if you forget zero_grad() each step's gradient includes every previous step's. Lesson 1.3 shows the loss curve that produces.

🤔 Why this? Define-by-run autograd (a tape recorded as code runs)
  1. The problem before Early frameworks (Theano, TensorFlow 1) made you declare a static graph first and run it later. Debugging meant inspecting a graph object, not your code; loops and if-statements needed special graph operations.
  2. What people tried Static graphs with clever compilers; hand-written backward functions per layer (Caffe-style).
  3. Why this works Record operations as ordinary Python runs. Any loop, branch or print just works, because the graph for this run is whatever actually happened. Chainer built its whole design around this “define-by-run” idea (as opposed to “define-and-run”), and PyTorch made it the mainstream way deep learning is written.
  4. What it costs, when it fails Python overhead per operation and no global view for optimizing, so small ops are slow; recorded graphs hold memory until backward() or until you drop the reference.
  5. What refined it torch.compile traces your eager code into an optimized graph, keeping define-by-run ergonomics with compiled speed (Lesson 10.5).

Gradient checking: trust, but verify

When you write a backward function yourself (a custom layer, a from-scratch engine, an interview question), compare it with nudging on a few numbers. The relative error |analytic − numeric| ÷ max(|analytic|, |numeric|) should be tiny: around 10⁻⁷ or less in float64 (CS231n's rule of thumb: above 10⁻² is almost certainly a bug). Nudge in both directions, (f(x + h) − f(x − h)) ÷ 2h, with h around 10⁻⁵.

What you should see: correct gradients agree to about 10⁻¹¹ relative error with h = 0.00001. The buggy ones are off by a factor (the mean's gradient is 4× too big: it forgot the ÷ 4) or by a whole term. Try the tanh one at x = 0: the bug hides, because 1 − tanh(0) and 1 − tanh²(0) are both 1. Always check a few random points. With h = 0.1 even correct gradients show errors around 10⁻⁴ to 10⁻³ (the plain square is the exception: centered nudging is exact for it); with h = 10⁻¹² rounding noise pushes them to around 10⁻⁵ to 10⁻⁴. Neither is a bug in your formula, which is why you fix h ≈ 10⁻⁵ and use float64 when checking.

🤔 Why this? Gradient checking
  1. The problem before A wrong gradient rarely crashes: the network still trains, just worse, and you blame the learning rate for weeks.
  2. What people tried Staring at the derivation; watching whether the loss goes down (a buggy gradient often still points vaguely downhill).
  3. Why this works Nudging is slow but needs no calculus, so it's an independent second opinion. The centered difference's error shrinks like h², so h = 10⁻⁵ gives about 10 correct digits in float64.
  4. What it costs, when it fails 2 forward passes per checked number, so check a handful of weights on a tiny input, not a real model. Kinks (ReLU at exactly 0, max ties) produce false alarms; float32 is too imprecise for strict checks.
  5. What refined it torch.autograd.gradcheck does it for any function in float64; framework code is gradient-checked in its test suites, which is why you rarely need to.
🧰 Tools you'll actually use 
import torch

# The graph from the worked example: L = (relu(w1*x1 + w2*x2 + b) - y)^2
x1, x2, y = torch.tensor(2.0), torch.tensor(-1.0), torch.tensor(1.0)
w1 = torch.tensor(1.5, requires_grad=True)
w2 = torch.tensor(0.5, requires_grad=True)
b = torch.tensor(0.5, requires_grad=True)

z = w1 * x1 + w2 * x2 + b          # PyTorch records every op as it runs
a = torch.relu(z)
L = (a - y) ** 2
print("L =", L.item(), "| L was made by", L.grad_fn.name())

L.backward()                        # one reverse pass fills .grad for every leaf
print("grads:", w1.grad.item(), w2.grad.item(), b.grad.item())

# Gradients ACCUMULATE: a second forward+backward adds to .grad
L2 = (torch.relu(w1 * x1 + w2 * x2 + b) - y) ** 2
L2.backward()
print("after a 2nd backward, w1.grad =", w1.grad.item())
w1.grad = None                      # what optimizer.zero_grad() does (set_to_none=True)

# No graph is recorded under no_grad (evaluation, weight updates)
with torch.no_grad():
    print("inside no_grad, requires_grad =", (w1 * x1).requires_grad)

# Gradient check of a built-in op, in float64
t = torch.randn(3, dtype=torch.float64, requires_grad=True)
print("gradcheck:", torch.autograd.gradcheck(lambda v: torch.sigmoid(v).sum(), t))

# L = 4.0 | L was made by PowBackward0

Also handy: tensor.detach() (a copy cut off from the graph), torch.autograd.grad(L, [w]) (returns gradients instead of writing .grad), and L.backward(retain_graph=True) if you really must go backwards twice through the same graph.

🎤 Interview angle

“Explain backpropagation” or “implement backward for this layer.” A strong answer:

  • Describes the graph, the forward pass that caches values, and the backward pass of local derivative × upstream gradient, with gradients summed where paths merge.
  • Knows the patterns: add copies, multiply swaps, ReLU gates, and for a linear layer y = Wx: ∂L/∂W = (∂L/∂y)·xᵀ, ∂L/∂x = Wᵀ·(∂L/∂y).
  • Explains why reverse mode: many inputs, one output; cost ≈ a small constant times a forward pass; the price is activation memory.
  • Mentions PyTorch specifics: .grad accumulates (hence zero_grad), no_grad for eval, and gradient checking in float64.
🏭 In the real world
Autograd in PyTorch 🧰 Open source PyTorch docs: Autograd mechanics

How: records a graph of Function objects as tensors are combined, then evaluates it in reverse on backward(); the graph is rebuilt from scratch each iteration.

Why this method: rebuilding per run is what lets you use arbitrary Python control flow and change shapes or branches between iterations.

Backprop in 150 lines 🧰 Open source Karpathy: micrograd

How: a scalar-valued autograd engine (a Value class that records its parents and a local backward function) plus a tiny neural-net library on top.

Why this method: small enough to read in one sitting; the same idea as PyTorch, minus tensors and GPUs. Lab 1 has you build a few nodes of it.

Trading compute for memory 🧪 Research · 2016 Chen et al.: Training Deep Nets with Sublinear Memory Cost

How: keep only some layers' activations during forward; recompute the rest during backward.

Why this method: activation memory, not weights, limits how deep or wide you can train; the paper trains an n-layer network with O(√n) memory for the cost of an extra forward pass. PyTorch exposes it as torch.utils.checkpoint.

The survey that connects it all 🧪 Research · 2015/2018 Baydin et al.: Automatic Differentiation in Machine Learning: a Survey

How: explains forward and reverse mode, their costs, and backprop as a special case of reverse mode.

Why this method: the source for the “c < 6, typically 2–3” cost and for the history below.

🤯 Fun fact · older than you think

The famous 1986 backprop paper by Rumelhart, Hinton and Williams wasn't the first. The AD survey notes that Seppo Linnainmaa's work (1970) “is often cited as the first published description of the reverse mode”, and that Paul Werbos described it in 1974. Deep learning's core algorithm was waiting for computers (and ReLUs, and data) to catch up.

Check yourself

1. A node computes m = w · x with w = 3, x = −2. The gradient arriving from above is ∂L/∂m = 5. What is ∂L/∂w?
Multiply “swaps”: the local derivative of w · x with respect to w is x, so ∂L/∂w = 5 × (−2) = −10. (x would receive 5 × w = 15.) Copying the gradient unchanged is what an add node does.
2. Your training loop calls loss.backward() and optimizer.step() every iteration but never optimizer.zero_grad(). What happens?
.grad accumulates by design (that's how gradient accumulation over small batches works). Without clearing it, step k's update is the sum of k gradients: ever-larger steps that remember old directions, like a runaway momentum. No error is raised. Lesson 1.3 shows the loss curve.
3. Why do deep-learning frameworks use reverse mode rather than forward mode for training?
Both modes compute exact derivatives. Forward mode needs a separate pass for every input direction (a billion passes for a billion weights); reverse mode starts from the single loss and gets every weight's gradient in one backward sweep, at a cost of a few forward passes. The price is storing activations.
📝 TL;DR
  • Any network is a graph of tiny ops. Forward computes (and caches) values; backward multiplies local derivative × upstream gradient node by node, summing where paths merge.
  • Patterns: add copies, multiply swaps, ReLU gates (0 when off: dead units get no gradient).
  • Reverse mode gets every weight's gradient for ≈ 2–3 forward passes (guaranteed < 6); nudging needs 2 passes per weight. The price is activation memory.
  • PyTorch records ops on tensors with requires_grad; backward() fills .grad, which accumulates: call zero_grad() every step; use no_grad() for evaluation.
  • Check hand-written gradients with centered differences (h ≈ 10⁻⁵, float64, relative error ≲ 10⁻⁷).
