PyTorch: tensors, modules and the training loop

Five lines train almost every network on Earth. Get one of them wrong and nothing crashes: the loss just quietly refuses to go down. Here's how the pieces fit, and how to see the bugs that don't raise errors.

🧰 You'll need (quick reminders)
  • nn.CrossEntropyLoss takes raw logits; its push on each logit is p − y (Lesson 1.1).
  • loss.backward() fills each weight's .grad, and .grad accumulates (Lesson 1.2).
  • A layer computes h = Wx + b; a weight matrix has one row per output unit (math 2.2, tensors in math 2.3).
🎯 Hook

Andrej Karpathy (founding member of OpenAI, former head of AI at Tesla) opens his famous guide A Recipe for Training Neural Networks with a warning: neural net training “fails silently”. Wrong code usually raises an exception. A wrong training loop usually runs perfectly and produces a model that's a bit worse, or useless, with no error at all.

Below you'll run three real PyTorch bugs we recorded. One makes the loss explode. One gets stuck at exactly the accuracy of guessing one class. And one still reaches 99.6%, just with a loss four times higher than the correct run's at the same epoch, so you'd never know it was a bug. Can you tell which bug produces which curve before you look?

Who uses this: Hugging Face's Trainer, PyTorch Lightning and Karpathy's nanoGPT all wrap exactly the loop you'll learn here, and so does every PyTorch model in this course.

Numbers first: everything is a tensor with a shape

A tensor is an n-dimensional array (like a NumPy array) that can live on a GPU and remember how it was computed. Three things describe it: its shape, its dtype and its device.

ThingTypical shapedtypeWhy
A batch of 64 points with 2 features(64, 2)float32batch first, features last: the convention everywhere
64 RGB images, 224×224(64, 3, 224, 224)float32batch, channels, height, width (Phase 3)
64 class labels(64,)int64 (long)CrossEntropyLoss wants class indices, not one-hot
Weight of nn.Linear(2, 32)(32, 2)float32(out, in): one row per output unit
Its output for the batch(64, 32)float32x @ Wᵀ + b, the batch dimension rides along

Device is where the numbers live: "cpu", "cuda" (NVIDIA GPU) or "mps" (Apple GPU). Every tensor in one operation must be on the same device; model.to(device) and x.to(device) move them. Most PyTorch errors you'll actually see are shape or device mismatches, and those are the good errors: they're loud.

💡 Big idea A PyTorch program has three parts: tensors (the data, with shapes), modules (layers that own their weights as parameters) and the loop (forward, loss, zero_grad, backward, step). Shapes are checked loudly; the loop's logic is not. So you trace shapes on paper and you watch the loss curve, because the curve is the only place most loop bugs show up.

Modules: layers that own their weights

An nn.Module is a Python object with a forward() method. Any nn.Parameter (or sub-module) you assign to it is registered: model.parameters() finds every weight, model.to("cuda") moves them all, model.state_dict() saves them. nn.Sequential is a module that just runs its children in order.

🤔 Why this? nn.Module and registered parameters
  1. The problem before A network has dozens of weight tensors. Passing each one by hand to the optimizer, moving each to the GPU, saving each to disk, is a bug factory: forget one and it silently never trains.
  2. What people tried Global lists of weights; layer libraries with their own save formats (Torch7, Caffe prototxt).
  3. Why this works Assigning self.fc = nn.Linear(2, 32) registers its weight (32 × 2 = 64 numbers) and bias (32) automatically. Then one call, model.parameters(), hands all of them to the optimizer, and modules nest: a transformer is modules of modules.
  4. What it costs, when it fails Weights kept in a plain Python list (instead of nn.ModuleList) or as plain tensors (instead of nn.Parameter) are not registered: no error, they just never train and never get saved.
  5. What refined it nn.ModuleList/nn.ModuleDict for dynamic structures, torch.compile(model) for speed (Lesson 10.5), and the Hugging Face PreTrainedModel wrapper for saving and sharing.

✏️ Worked example: what a model costs in memory

The Tools model below: Linear(2, 32) has 2 × 32 + 32 = 96 parameters, Linear(32, 32) has 1,024 + 32 = 1,056, Linear(32, 2) has 64 + 2 = 66. Total 1,218, about 4.9 KB in float32. PyTorch prints the same count.

Scale up: a 7-billion-parameter model is 7 × 10⁹ × 4 bytes = 28 GB in float32 just to hold the weights. Training it with AdamW needs weights + gradients + two moment buffers = 16 bytes per weight = 112 GB, before a single activation. That's why Phase 10 is about mixed precision and splitting models across GPUs.

The loop: five lines

Every epoch (one pass over the data), the DataLoader hands you shuffled mini-batches (Lesson 1.7 explains why batches). For each batch:

  1. logits = model(xb): forward (autograd records the graph)
  2. loss = loss_fn(logits, yb): one number for “how wrong”
  3. opt.zero_grad(): clear last step's gradients
  4. loss.backward(): backward, fills every .grad
  5. opt.step(): the optimizer moves every weight using its .grad

Around it: model.train() before training and model.eval() plus torch.no_grad() when evaluating.

What you should see: forward must come before the loss, the loss before backward, backward before step. zero_grad() can go anywhere before backward(): first, second or third. Putting it between backward and step erases the gradient you just computed, and the step does nothing.

🤔 Why this? DataLoader with shuffle=True
  1. The problem before Datasets are often stored sorted (all cats, then all dogs; or by date). Batches taken in order give the model 300 cats in a row: it learns “always say cat”, then gets yanked to “always dog”.
  2. What people tried Shuffling once on disk; hand-written batching loops with off-by-one bugs at the last batch.
  3. Why this works DataLoader(ds, batch_size=64, shuffle=True) draws a new random order every epoch, so each batch is a fair sample of the whole dataset and its gradient points roughly where the full-data gradient points. It also batches, and with num_workers loads data in parallel with training.
  4. What it costs, when it fails Random order makes runs less reproducible (seed the generator). For time series you usually must not shuffle across the train/validation split, or the model sees the future.
  5. What refined it Samplers for class balance (WeightedRandomSampler), distributed samplers that give each GPU a different shard (Lesson 10.3), and streaming datasets for data that doesn't fit on disk.
🤔 Why this? model.train() / model.eval() and torch.no_grad()
  1. The problem before Some layers must behave differently during training and testing: dropout randomly zeroes units while training but must not at test time; batch norm uses batch statistics while training but stored averages at test time (Phase 2). And evaluating with autograd on wastes memory recording a graph nobody will use.
  2. What people tried Separate “train” and “test” network definitions sharing weights.
  3. Why this works model.train()/model.eval() flip a flag on every sub-module at once; layers that care read it. torch.no_grad() turns off graph recording, so evaluation uses less memory and runs faster.
  4. What it costs, when it fails They're independent: eval() does not stop gradients, and no_grad() does not switch dropout off. Forgetting model.train() after a validation pass trains the rest of the run with dropout disabled, silently.
  5. What refined it torch.inference_mode(), a stricter and slightly faster no_grad for pure inference.

🧰 Tools you'll actually use

A complete, correct loop on synthetic XOR-style data (runs in about a second on a laptop CPU):

import torch, torch.nn as nn
from torch.utils.data import TensorDataset, DataLoader

torch.manual_seed(0)
# 1. Tensors: shape, dtype, device
x = torch.randn(1000, 2)                                  # 1,000 points, 2 features
y = (x[:, 0] * x[:, 1] > 0).long()                        # XOR-style labels: class 0 or 1
print(x.shape, x.dtype, y.dtype, x.device)

# 2. A model is an nn.Module; Sequential chains layers
model = nn.Sequential(nn.Linear(2, 32), nn.ReLU(), nn.Linear(32, 32), nn.ReLU(), nn.Linear(32, 2))
print("parameters:", sum(p.numel() for p in model.parameters()))

# 3. Data in mini-batches, reshuffled every epoch
train = DataLoader(TensorDataset(x[:800], y[:800]), batch_size=64, shuffle=True)
loss_fn = nn.CrossEntropyLoss()                           # takes raw logits: no softmax in the model!
opt = torch.optim.AdamW(model.parameters(), lr=1e-2)

for epoch in range(20):
    model.train()                                         # dropout/batchnorm in training mode
    for xb, yb in train:
        logits = model(xb)                                # 1. forward
        loss = loss_fn(logits, yb)                        # 2. loss
        opt.zero_grad()                                   # 3. clear old gradients
        loss.backward()                                   # 4. backprop
        opt.step()                                        # 5. update the weights
    model.eval()                                          # evaluation mode
    with torch.no_grad():                                 # no graph, less memory
        acc = (model(x[800:]).argmax(1) == y[800:]).float().mean().item()
    if epoch % 5 == 4:
        print(f"epoch {epoch + 1:2d}  last batch loss {loss.item():.3f}  val acc {acc:.1%}")

# The classic shape bug: (N, 1) minus (N,) broadcasts to (N, N)
pred, target = torch.zeros(4, 1), torch.zeros(4)
print("broadcast:", (pred - target).shape)

# What we got (torch 2.8, CPU):
# torch.Size([1000, 2]) torch.float32 torch.int64 cpu
# parameters: 1218
# epoch  5  last batch loss 0.039  val acc 95.0%
# epoch 10  last batch loss 0.024  val acc 96.5%
# epoch 15  last batch loss 0.013  val acc 97.5%
# epoch 20  last batch loss 0.066  val acc 99.0%
# broadcast: torch.Size([4, 4])

On a GPU add device = "cuda", model.to(device) and xb, yb = xb.to(device), yb.to(device) inside the loop. nn.MSELoss does print a UserWarning: Using a target size … different to the input size for the broadcast bug: read your warnings. Note the last-batch loss bounces around (0.013 → 0.066): one batch is noisy; plot a running average.

🎤 Interview angle

“Write a PyTorch training loop” or “this model doesn't train, what would you check?” A strong answer:

  • Writes the five lines from memory, with train()/eval() and no_grad() in the right places, and explains why zero_grad exists (gradients accumulate).
  • Checks shapes and dtypes first (labels int64 of shape (B,), logits (B, K); no (B, 1) vs (B,) broadcasting) and the loss at step 0 (≈ ln K for K classes).
  • Lists the silent bugs: softmax before CrossEntropyLoss, missing zero_grad, unshuffled sorted data, forgetting model.train() after evaluation, unregistered parameters.
  • Knows the next debugging move: overfit one small batch to near-zero loss (Lesson 2.6).
🏭 In the real world
The framework itself 🧪 Research · 2019 Paszke et al.: PyTorch: An Imperative Style, High-Performance Deep Learning Library

How: models are ordinary Python classes, executed eagerly, with autograd recording operations as they run.

Why this method: the paper's argument is usability: code you can debug with print statements and a normal debugger, while still running fast on GPUs.

A GPT-2 training loop you can read 🧰 Open source Karpathy: nanoGPT train.py

How: the same five lines, plus gradient accumulation over 40 micro-batches, gradient clipping and a warmup-then-cosine learning rate (Lessons 1.6 and 1.7). Its README notes it's now deprecated in favour of the newer nanochat (Nov 2025).

Why this method: a roughly 300-line loop that reproduces GPT-2 (124M), small enough to read every line.

The loop, packaged 🧰 Open source Hugging Face Transformers: Trainer

How: you pass a model, datasets and TrainingArguments; it runs the loop, evaluation, logging, checkpointing and multi-GPU training.

Why this method: fine-tuning thousands of models should not mean writing thousands of loops; knowing the five lines underneath is how you debug it when it misbehaves.

🤯 Fun fact · the loss at step 0 is a free unit test

Every run in the bug playground started at 1.083, almost exactly ln 3 = 1.099. Karpathy's recipe calls this “verify loss @ init”: with K classes and a sensible initialization, the first loss should be about −log(1/K). If yours starts at 8 or 0.001, something is wired wrong, before you've trained a single step.

Check yourself

1. How many parameters does nn.Linear(512, 256) have?
Weights: 512 × 256 = 131,072, plus one bias per output: 256. Total 131,328. (768 = 512 + 256 would be the number of input plus output units, not parameters.)
2. A teammate's classifier trains to 97% but noticeably slower than a reference implementation. Their model ends with nn.Softmax(dim=1) and they use nn.CrossEntropyLoss. What's going on?
CrossEntropyLoss = log-softmax + negative log-likelihood on raw logits. Feeding it probabilities (all between 0 and 1) means the “logits” barely differ, so the loss can't get small and the gradients are weak. It still trains, slowly, which is why it's a silent bug (our recorded run: loss 0.452 vs 0.108 after 10 epochs).
3. A regression model outputs shape (64, 1); the targets have shape (64,). You compute ((pred - target) ** 2).mean(). What happens?
PyTorch broadcasting stretches (64, 1) and (64,) to (64, 64). The loss is then the average error of each prediction against all targets, which is minimized by predicting the mean of the targets for everyone. Fix with target.unsqueeze(1) or pred.squeeze(1), and assert shapes.
📝 TL;DR
  • Tensors have a shape, dtype and device; batch dimension first; class labels are int64 of shape (B,); weights of Linear(in, out) are (out, in).
  • nn.Module registers parameters automatically; parameters per linear layer = in × out + out.
  • The loop: forward, loss, zero_grad, backward, step (zero_grad anywhere before backward). train()/eval() switch layer behaviour; no_grad() stops graph recording. They're independent.
  • Silent bugs: missing zero_grad (explodes), unshuffled sorted data (stuck), softmax before CrossEntropyLoss (slow), (B, 1) vs (B,) broadcasting (predicts the mean).
  • Check the loss at step 0 (≈ ln K), trace shapes on paper, and compare curves.
