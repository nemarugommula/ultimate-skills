Phase 10 · Lesson 3

Parallelism: DDP, FSDP/ZeRO, tensor and pipeline

A 7-billion-parameter model doesn't fit on the biggest single GPU you can rent, once you count what training really stores. Here are the four ways to split the work across many GPUs, what each one splits, and what it costs in communication.

🧰 You'll need (quick reminders)
  • Mixed precision with Adam stores 16 bytes per parameter: 2 (bf16 weight) + 2 (bf16 gradient) + 4 (fp32 master) + 8 (Adam's two moments) (Lesson 10.2).
  • Backprop needs the forward pass's activations, so they're kept in memory until the backward pass uses them (Lesson 1.2).
  • A transformer is a stack of identical blocks, each mostly matmuls (Lesson 6.4; FLOPs vs bandwidth: 10.1).
🎯 Hook

Meta pre-trained Llama 3 405B on up to 16,384 H100 GPUs at once. Each GPU has 80 GB. Their paper describes splitting the model four different ways at the same time (“4D parallelism”): at the 8K-token stage, 8-way tensor, 16-way pipeline and 128-way data parallelism.

Why so complicated? Do the arithmetic for a much smaller 7B model: 7 × 10⁹ parameters × 16 bytes = 112 GB before a single activation is stored. It doesn't fit on one 80 GB GPU, and copying it onto 8 GPUs doesn't help either: each copy is still 112 GB.

So how do you train a model bigger than any one GPU? By the end you'll plan the memory of a 70B training run yourself and know which split to reach for first.

The activation numbers use Korthikanti et al.'s count of about 34 · s · h bytes per layer for a sequence of s tokens and hidden size h (their formula's attention-score term is left out because FlashAttention doesn't store the scores). For the 7B shape (32 layers, h = 4,096): 34 × 4,096 × 4,096 × 32 ≈ 18 GB.

Three things can be split: the data (each GPU sees different examples), the model states (each GPU stores a slice) and the layers' math (each GPU computes part of a layer or some of the layers). Every technique in this lesson is one of those splits plus the communication it forces.

💡 Big idea Parallelism trades memory and compute for communication. Data parallelism copies the model and syncs gradients; sharding (ZeRO/FSDP) stops the copies and gathers weights on demand; tensor parallelism splits each matmul and talks inside every layer; pipeline parallelism splits the stack of layers and pays in idle time.

1. Data parallelism (DDP): many copies, one average

Give each of N GPUs a full copy of the model and a different slice of the batch. Each computes its own gradients, then all GPUs average their gradients with an operation called all-reduce, so every copy takes exactly the same step and stays identical. PyTorch's DistributedDataParallel (DDP) does this, overlapping the all-reduce with the backward pass in “buckets” so communication hides behind compute.

✏️ Worked example: the cost of one all-reduce

7B model, 8 GPUs, bf16 gradients: 14 GB of gradients per GPU. The standard ring all-reduce passes chunks around a ring of GPUs; each GPU sends (and receives) about 2 × (N − 1)/N of the data:

2 × 14 GB × 7/8 = 24.5 GB sent per GPU, every step

At the H100's listed NVLink bandwidth (900 GB/s) that's roughly 30 ms; across a 50 GB/s network link it would be about half a second per step. That's why the GPUs inside one server, wired with NVLink, are so much easier to parallelize over than GPUs in different racks.

🤔 Why this? DDP (distributed data parallel)
  1. The problem before One GPU processes maybe a few thousand tokens per second on a 7B model; a 1-trillion-token run would take decades on one GPU.
  2. What people tried A single process driving several GPUs (PyTorch's old DataParallel), which bottlenecks on one Python process and one GPU gathering everything; parameter servers that collect gradients centrally.
  3. Why this works Examples in a batch are independent, so N GPUs can each do 1/N of the batch. Averaging gradients across GPUs gives exactly the gradient of the full batch, so training is mathematically the same as one big GPU. One process per GPU and overlapped bucketed all-reduces keep it near-linear.
  4. What it costs, when it fails Every GPU stores the whole model state: 112 GB for 7B, so DDP alone can't even start. The all-reduce moves about 2× the gradient size per step. The global batch grows with N, which may need learning-rate changes (Lesson 1.7).
  5. What refined it Sharding the redundant copies (ZeRO/FSDP, next). Gradient accumulation when the batch must grow without more GPUs.

2. ZeRO and FSDP: stop storing N copies of everything

With DDP, 8 GPUs hold 8 identical copies of the optimizer states, gradients and weights. ZeRO (“Zero Redundancy Optimizer”, Rajbhandari et al., 2019) removes the copies in three stages. Each GPU keeps only its 1/N shard and fetches the rest just in time.

Model states only. The ZeRO paper's own example: a 7.5B model needs 120 GB per GPU with plain data parallelism and 1.9 GB with all three stages on 64 GPUs.

🧠 Analogy: a book club with one copy of each chapter

DDP is eight friends each buying the whole encyclopedia. ZeRO-3 is the club buying one copy and giving each friend a few chapters. When the group reads chapter 12, its owner photocopies it for everyone (all-gather), they read, and the copies are thrown away. More passing of paper, a lot less shelf space.

🤔 Why this? ZeRO / FSDP (sharded data parallel)
  1. The problem before With DDP, memory per GPU doesn't shrink as you add GPUs: 16 bytes per parameter on every one. The ZeRO paper notes that a 1.5B model already needs at least 24 GB of model states, though its bf16 weights are only 3 GB.
  2. What people tried Model parallelism (splitting layers, below), which needs model code changes; offloading to CPU memory.
  3. Why this works Each GPU only updates its own shard, so it only needs that shard's optimizer states (stage 1) and reduced gradients (stage 2) for free: the all-reduce becomes a reduce-scatter plus all-gather with the same total volume. Stage 3 also shards the weights and all-gathers each layer just before it's used, then frees it. Memory per GPU becomes 16Ψ/N: add GPUs, fit bigger models.
  4. What it costs, when it fails Stage 3 moves about 1.5× DDP's data (the paper's 3Ψ vs 2Ψ), and the all-gathers sit on the critical path unless prefetched. Activations are not sharded: they still grow with sequence length and batch (use checkpointing, below). Across slow networks the traffic hurts.
  5. What refined it PyTorch FSDP (2023) and FSDP2's fully_shard, which shards each parameter on dim 0 as a DTensor; ZeRO-Offload, which puts optimizer states in CPU RAM and trained 13B parameters on one V100; hybrid sharding (shard within a node, replicate across nodes).

3. Tensor parallelism: split every matmul

Sharding still runs each layer on one GPU (with gathered weights). If a single layer is too big or too slow, split the matmul itself. Megatron-LM (Shoeybi et al., 2019) found a neat split for the transformer MLP: cut the first weight matrix by columns and the second by rows. Each GPU then computes its half of the hidden layer independently (the GELU works per column), and the two halves only meet once, in a single all-reduce at the end.

What you should see: the column split gives each GPU two complete outputs (gather them to get all four). The row split gives each GPU all four outputs but only part of each sum: an all-reduce adds them. Megatron chains the two so the nonlinearity happens between them on local data, and only the final row-split result needs one all-reduce, in the forward pass (one more in backward).

🤔 Why this? Tensor parallelism (Megatron-style)
  1. The problem before Sharding stores a slice, but each layer's full weights and activations still pass through one GPU at a time; the activations of one huge layer, or the latency of one huge matmul, can be too much.
  2. What people tried Hand-partitioned models; general “mesh” frameworks that were hard to use with existing code.
  3. Why this works Column-then-row splitting needs only one all-reduce per MLP (and per attention block, splitting by heads) per pass, and each GPU holds 1/t of the weights and of the activations (with sequence parallelism). Megatron-LM trained an 8.3B model on 512 GPUs at 76% scaling efficiency with only a few added communication ops in PyTorch.
  4. What it costs, when it fails The all-reduces happen inside every layer, on the critical path, so tensor parallelism needs very fast links: in practice it stays within one server's NVLink (t ≤ 8). Small per-GPU matmuls also lower arithmetic intensity (Lesson 10.1).
  5. What refined it Sequence parallelism (shards LayerNorm and dropout activations along the sequence), context parallelism for very long sequences, and combining TP with pipeline and data parallelism (3D, below).

4. Pipeline parallelism: an assembly line of layers

Put layers 1–20 on GPU 1, 21–40 on GPU 2, and so on. Only the activations at the boundaries travel between GPUs, so it works across slower links. The problem: GPU 4 has nothing to do until GPU 1 to 3 finish their part, and during backward the order reverses. That idle time is the pipeline bubble. GPipe (Huang et al., 2018) shrinks it by cutting each batch into M micro-batches that flow through like cars on an assembly line.

What you should see: with 4 stages and 1 micro-batch, each GPU is idle 75% of the time. With 16 micro-batches the bubble is 16%; you need 27 to get it to 10%. It never reaches zero: filling and draining the line always costs (p − 1) slots. Both schedules have the same bubble, but GPipe holds the activations of all M micro-batches at once, while 1F1B starts backward passes early and never holds more than p. GPipe's paper found the bubble negligible once M ≥ 4 × stages, partly because recomputation overlaps it.

🤔 Why this? Pipeline parallelism (GPipe, 1F1B)
  1. The problem before Tensor parallelism needs NVLink-class speed and stops at one server (8 GPUs). A model whose layers need 16+ GPUs' worth of memory must cross slower network links.
  2. What people tried Naive model parallelism: layers on different GPUs, one batch at a time. With p stages, each GPU is busy only 1/p of the time.
  3. Why this works Only boundary activations cross GPUs (a few MB per micro-batch), so slow links are fine. Micro-batches keep several stages busy at once; the idle share falls to (p − 1)/(M + p − 1). 1F1B (from PipeDream, 2018) interleaves forward and backward so each stage frees activations early.
  4. What it costs, when it fails The bubble never vanishes. More micro-batches need a larger global batch. Stages must be balanced (the last stage also computes the loss and output layer; Llama 3's paper calls this out). Debugging a pipeline is notoriously painful.
  5. What refined it Interleaved schedules (each GPU holds several smaller chunks, shrinking the bubble), zero-bubble schedules, and combining PP with TP and DP.

5. Activation checkpointing: forget, then recompute

All of the above split model states. Activations still grow with layers × sequence length × batch. Activation checkpointing (also called gradient checkpointing or rematerialization) keeps only each layer's input during the forward pass and throws away everything inside. During backward, it reruns that layer's forward to get the activations back, just in time.

🤔 Why this? Activation checkpointing
  1. The problem before A 7B model with one 4,096-token sequence stores about 18 GB of activations; longer sequences or bigger batches grow it linearly. Model-state sharding doesn't touch it.
  2. What people tried Smaller batches and shorter sequences (worse training), offloading activations to CPU (slow).
  3. Why this works Chen et al. (2016) showed you can train an n-layer network with O(√n) memory for the cost of one extra forward pass per batch. Per transformer layer, you store just its 2·s·h-byte input instead of ≈ 34·s·h bytes: for our 7B shape, 18 GB becomes under 2 GB.
  4. What it costs, when it fails Recomputing the forward costs about one extra forward pass. Since backward is about 2× forward, that's roughly 33% more compute. Code with randomness (dropout) must replay the same random numbers, which frameworks handle.
  5. What refined it Selective recomputation (recompute only the cheap but memory-hungry parts, like attention internals: Korthikanti et al.), FlashAttention (never stores the scores), and offloading checkpoints to CPU.

For 70B, even FSDP across 8 GPUs leaves 140 GB of model states per GPU (1,120 GB ÷ 8): full training simply can't fit on one 8-GPU server. Full 70B training needs at least 16 GPUs: try 8-way TP with 2 pipeline stages, or TP 8 with FSDP.

3D parallelism, and which split to use when

Big runs nest the splits by link speed: tensor parallel inside a server (NVLink), pipeline across a few servers, data parallel (often FSDP) across everything. Llama 3 405B at 8K context on 16,384 GPUs: TP 8 × PP 16 × DP 128 = 16,384, plus context parallelism for its 128K-token stage.

🧰 Tools you'll actually use

DDP and FSDP2 both run with torchrun, one process per GPU. This exact script ran on a laptop CPU with 2 processes and the gloo backend (on GPUs use "nccl" and init_device_mesh("cuda", …)):

# torchrun --nproc_per_node=2 train.py
import torch, torch.nn as nn, torch.distributed as dist
from torch.nn.parallel import DistributedDataParallel as DDP
from torch.distributed.fsdp import fully_shard
from torch.distributed.device_mesh import init_device_mesh

dist.init_process_group("gloo")
rank, world = dist.get_rank(), dist.get_world_size()
make = lambda: nn.Sequential(nn.Linear(64, 256), nn.ReLU(), nn.Linear(256, 1))

# DDP: full copy per rank, gradients all-reduced during backward
torch.manual_seed(0)
ddp = DDP(make())
x = torch.randn(32, 64) + rank                  # each rank: a different slice of data
ddp(x).pow(2).mean().backward()
print(f"rank {rank}: DDP grad[0,0] = {ddp.module[0].weight.grad[0, 0].item():.6f}")

# FSDP2: shard each layer, then the root
mesh = init_device_mesh("cpu", (world,))
torch.manual_seed(0)
model = make()
for layer in model:
    if isinstance(layer, nn.Linear):
        fully_shard(layer, mesh=mesh)
fully_shard(model, mesh=mesh)
w = model[0].weight                               # a DTensor sharded on dim 0
print(f"rank {rank}: full {tuple(w.shape)}, local shard {tuple(w.to_local().shape)}")
model(x).pow(2).mean().backward()
dist.destroy_process_group()

# Output (torch 2.8, CPU, 2 processes):
# rank 0: DDP grad[0,0] = 0.004942     rank 1: DDP grad[0,0] = 0.004942   ← identical after all-reduce
# rank 0: full (256, 64), local shard (128, 64)   ← each rank stores half

Other knobs: fully_shard(..., mp_policy=MixedPrecisionPolicy(param_dtype=torch.bfloat16, reduce_dtype=torch.float32)) for mixed precision; torch.utils.checkpoint.checkpoint(block, x, use_reentrant=False) for activation checkpointing. For TP and PP at scale, people use Megatron-LM, DeepSpeed or PyTorch's torchtitan.

🎤 Interview angle

“You need to fine-tune a 70B model on 8 H100s. Walk me through the memory.” A strong answer:

  • Does the math: 16 bytes/param × 70B = 1,120 GB of model states; ÷ 8 = 140 GB per GPU even with full sharding, so full Adam fine-tuning doesn't fit.
  • Offers options with their costs: CPU optimizer offload (slow, needs ~840 GB RAM), more GPUs, or LoRA/QLoRA (frozen 2-byte or 4-bit weights: 140 GB or ~35 GB total, sharded).
  • Handles activations separately: checkpointing, shorter sequences, FlashAttention; and knows TP stays inside the NVLink domain.
  • Mentions communication: DDP ≈ 2× gradient bytes per step, FSDP ≈ 1.5× that, TP talks every layer.
🏭 In the real world
Sharding the optimizer, gradients and weights 🏢 Microsoft · 2019 Rajbhandari et al.: ZeRO

How: three stages of partitioning model states across data-parallel GPUs; the basis of DeepSpeed and of PyTorch FSDP.

Why this method: memory per GPU falls from 16Ψ to 16Ψ/N at no more than 1.5× the communication; with 1,024 GPUs the paper projects trillion-parameter models.

Splitting transformer layers across GPUs 🏢 NVIDIA · 2019 Shoeybi et al.: Megatron-LM

How: column-then-row splits of MLP and attention weights with one all-reduce per block, inside a server.

Why this method: only a few communication ops added to PyTorch; 8.3B parameters on 512 GPUs at 76% scaling efficiency.

Micro-batch pipelines 🏢 Google · 2018 Huang et al.: GPipe

How: splits a network into stages and a batch into M micro-batches, with re-computation of activations.

Why this method: works over slower links; the paper found the bubble negligible once M ≥ 4 × the number of stages.

All of it at once 🏢 Meta · 2024 The Llama 3 Herd of Models

How: 4D parallelism (tensor, context, pipeline, and FSDP-style data parallelism) on up to 16,384 H100s.

Why this method: each split goes where its communication fits the hardware: TP within a server's NVLink, PP and DP across the network.

🤯 Fun fact · a trillion parameters at 502 petaFLOP/s

In 2021, NVIDIA, Stanford and Microsoft combined tensor, pipeline and data parallelism (“PTD-P”) to run training iterations of a 1-trillion-parameter model on 3,072 GPUs at 502 petaFLOP/s, 52% of the GPUs' theoretical peak (Narayanan et al.). Their interleaved pipeline schedule alone improved throughput by over 10%.

Check yourself

1. A 13B model trains with mixed-precision Adam (16 bytes/param) and ZeRO-3 across 16 GPUs. Roughly how much model-state memory does each GPU hold?
16 × 13 × 10⁹ = 208 GB in total. ZeRO-3 shards weights, gradients and optimizer states, so each of 16 GPUs holds 208 ÷ 16 = 13 GB. Activations come on top and aren't sharded by ZeRO. (26 GB would be the bf16 weights alone, unsharded.)
2. Your 32-GPU job (4 servers of 8) uses 32-way tensor parallelism and runs at a fraction of the expected speed. GPU utilization is low and the network is saturated. What's the likely fix?
Tensor parallelism all-reduces inside every layer, on the critical path, so it needs NVLink-class bandwidth. Spanning servers sends those all-reduces over the much slower network. Standard practice: TP ≤ 8 inside a node, then PP and/or (sharded) data parallelism across nodes.
3. A pipeline has 8 stages. With M micro-batches the bubble is (p − 1)/(M + p − 1). How many micro-batches bring it to about 10%?
7 / (M + 7) = 0.1 gives M + 7 = 70, so M = 63. With M = 8 the bubble is 7/15 ≈ 47%. It shrinks toward 0 but never reaches it: filling and draining the pipeline always costs p − 1 slots. Interleaved and zero-bubble schedules attack exactly that.
📝 TL;DR
  • Training memory = model states (16 bytes/param with mixed-precision Adam: 7B → 112 GB) + activations (≈ 34·s·h bytes per layer).
  • DDP: full copy per GPU, gradients all-reduced (≈ 2× gradient bytes per step). Scales compute, not memory.
  • ZeRO-1/2/3 = FSDP: shard optimizer states, gradients, then weights: 16Ψ/N per GPU for 1.5× communication.
  • Tensor parallel: split each matmul (column then row, one all-reduce per block); keep it inside NVLink. Pipeline parallel: split layers; bubble (p − 1)/(M + p − 1); 1F1B holds ≤ p micro-batches.
  • Activation checkpointing: store layer inputs, recompute the rest (~33% more compute). Big runs nest TP × PP × DP by link speed.
