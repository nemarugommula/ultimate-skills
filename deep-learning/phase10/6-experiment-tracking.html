Phase 10 · Lesson 6

Experiment tracking and reproducibility

Deep learning is an experimental science run on noisy hardware. Learn what to record so any result can be rebuilt, how many seeds it takes to trust a difference, and why random search beats a neat grid.

🧰 You'll need (quick reminders)
  • Training starts from random initial weights and sees data in a random order, so two runs differ (Lessons 1.3, 1.4).
  • The learning rate is the hyperparameter that matters most (Lesson 1.6).
  • A mean of a few noisy numbers is itself noisy; a confidence interval says how noisy (math 5.5, RL 0.5).
🎯 Hook

In 2017, a DeepMind and Oxford team re-ran years of “new state-of-the-art” language models with the same large-scale automatic hyperparameter tuning for all of them. Their “somewhat surprising conclusion”: standard LSTMs, properly regularised, outperformed the more recent models (Melis et al.).

A year later, Google Brain did the same for GANs and found that “most models can reach similar scores with enough hyperparameter optimization and random restarts”, and no tested algorithm consistently beat the original 2014 GAN (Lucic et al.).

Many published gains were really tuning budgets and lucky seeds. How do you make sure your own “improvement” is real, and that you can rebuild the exact model you shipped six months from now?

Numbers first: the same code, different answers

We trained a tiny network (2 → 4 → 4 → 1, ReLU) on a noisy two-moons dataset 20 times, changing only the random seed for the initial weights. Test accuracy ranged from 85.3% to 91.2%. A 6-point spread, from nothing but the seed.

Now picture an ablation that claims “+2%”. With one run per side, the seed alone can produce that. Sources of run-to-run variation include:

💡 Big idea Two separate goals. Reproducibility: fix every seed and record everything, so the same run can be rebuilt. Reliability: vary the seeds on purpose, so you know whether a difference between runs is real. You need both.

What to log, every run

run: 2026-11-01_lr3e-4_w8_seed2 status: finished code: git 9f2c1ab (clean) env: torch 2.8.0, CUDA 12.x, 8×H100 data: moons-v3 (sha256 4be1…), split seed 0 config: {lr: 3e-4, width: 8, batch: 256, steps: 30000, warmup: 500, seed: 2} metrics: train/loss, val/loss, val/acc every 100 steps; final val/acc 0.912 system: GPU util, memory, tokens/s, step time artifacts: best.pt, last.pt, config.yaml, eval predictions

That card answers the three questions everyone eventually asks: what exactly produced this model (code, data, config, environment), how did training go (curves, not just the final number) and where is it (checkpoints). Tracking tools store these cards for you and let you compare runs side by side.

🤔 Why this? Config-as-code
  1. The problem before Hyperparameters scattered across command-line flags, notebook cells and hard-coded constants. Weeks later nobody knows which learning rate produced the good checkpoint.
  2. What people tried Writing settings in a spreadsheet or the run's name (run_final_v2_lr3e-4_REAL).
  3. Why this works One typed object (a dataclass, a YAML file, a Hydra config) holds every knob. Training reads only from it, and the whole object is logged with the run, so the config is the record. Diffing two configs shows exactly what changed between two runs.
  4. What it costs, when it fails A little discipline: no “just this once” constants in the code. It records settings, not code or data: you still need the git commit and a data version.
  5. What refined it Config systems with overrides and sweeps (Hydra, ml_collections), and trackers that log the config automatically (W&B's config=, MLflow's params and autologging).

What you should see: in experiment 1, one seed each says B wins by 4.0 points. By 5 seeds the gap has shrunk to 0.75 with an interval from about −1.4 to +2.9: can't tell. At 10 seeds it still just touches zero; from 11 seeds per side it clears zero and stays clear, settling near a gain of 1.5 points. In experiment 2, one seed says +2.25 points; with 10–20 seeds the difference sits at about 0 with the interval straddling it. Same code, same “result” at n = 1, opposite truths.

🤔 Why this? Multiple seeds and confidence intervals
  1. The problem before One run per config. Seed-to-seed spread is often as large as the effects people report (6 points across seeds in our toy), so single-run comparisons crown lucky seeds.
  2. What people tried Reporting the best of several runs (which inflates the result), or eyeballing curves.
  3. Why this works The mean of n runs has noise shrinking like 1/√n. A confidence interval for the difference turns “B looks better” into “B is better by 0.7 to 2.3 points, 95% of the time”. Bouthillier et al. (2021) showed that data sampling, initialization and hyperparameter choice all markedly affect benchmark results, and recommend randomizing all of them across trials.
  4. What it costs, when it fails n× the compute: impossible for a frontier pre-training run, where people instead rely on small-scale ablations and scaling trends. Intervals assume runs are independent and roughly normal; a single collapsed run (one of our width-3 runs got stuck at 50%) can dominate a mean, so look at the dots, not just the summary.
  5. What refined it Reporting means with intervals over 3–10 seeds; bootstrap intervals; statistical-power planning before running. In RL, where variance is wilder, the same story is told in RL 9.3.

Ablations: take it apart to see what matters

An ablation removes or changes one component at a time and measures the effect, holding everything else fixed. “Our model gets 91%” says little; “without the new normalization it gets 89.5 ± 0.4%, without the augmentation 90.8 ± 0.3%” says which idea did the work. Good ablations: one change per row, the same tuning budget for every row, several seeds each, and the baseline re-run in your setup rather than copied from another paper (Melis et al.'s lesson).

Hyperparameter search: grid vs random

You have budget for 9 training runs to tune the learning rate and weight decay. A neat 3 × 3 grid feels thorough. Bergstra and Bengio (2012) explained why it isn't: for most problems “only a few of the hyper-parameters really matter”. If weight decay barely matters, the grid's 9 runs test only 3 different learning rates; random search tests 9.

What you should see: the 3 × 3 grid's learning rates (10⁻³·⁵, 10⁻²·⁵, 10⁻¹·⁵) all straddle the good band at 10⁻², so its best run scores about 64%. Nine random trials try nine different learning rates and almost always land one near the band: about 80–90%. Over 20 re-rolls random wins nearly every time. A 4 × 4 grid still only tries 4 learning rates.

🤔 Why this? Random search over grid search
  1. The problem before Grid search spends its budget evenly over every dimension, including ones that don't matter. With k hyperparameters and m values each it needs mᵏ runs, and still tries only m values of the one that matters.
  2. What people tried Manual tuning by intuition (unreproducible, biased toward the baseline you already like) and coarse-to-fine grids.
  3. Why this works Random points project onto every axis as n distinct values, so whichever hyperparameter turns out to matter gets n tries. Bergstra and Bengio found random search finds models “as good or better within a small fraction of the computation time” than grid search. Sample scale-type knobs (learning rate, weight decay) on a log scale.
  4. What it costs, when it fails Uneven coverage by chance (quasi-random sequences fix this; Google's Deep Learning Tuning Playbook prefers quasi-random search for exploration). It doesn't learn from earlier trials, so it's wasteful when runs are expensive.
  5. What refined it Bayesian optimization and TPE (try promising regions next), early stopping of bad trials (Hyperband, ASHA), and libraries such as Optuna (define-by-run search spaces with pruning). For huge models, tune on small proxies and transfer (Lessons 1.6, 6.8).

🧰 Tools you'll actually use

Seeds, deterministic mode, config-as-code and the smallest possible tracker (a JSON-lines file). This ran on a laptop CPU:

import json, random, dataclasses, torch, torch.nn as nn

@dataclasses.dataclass
class Config:                      # config-as-code: every knob in one typed, loggable object
    seed: int = 0
    lr: float = 0.05
    width: int = 32
    steps: int = 200

def set_seed(seed):
    random.seed(seed)
    torch.manual_seed(seed)        # seeds the CPU and all CUDA devices
    torch.use_deterministic_algorithms(True)   # error out on known non-deterministic kernels

def run(cfg):
    set_seed(cfg.seed)
    x = torch.randn(256, 8)
    y = (x[:, :1] * x[:, 1:2] > 0).float()
    net = nn.Sequential(nn.Linear(8, cfg.width), nn.ReLU(), nn.Linear(cfg.width, 1))
    opt = torch.optim.SGD(net.parameters(), lr=cfg.lr)
    for _ in range(cfg.steps):
        loss = nn.functional.binary_cross_entropy_with_logits(net(x), y)
        opt.zero_grad(); loss.backward(); opt.step()
    return loss.item()

a, b, c = run(Config(seed=0)), run(Config(seed=0)), run(Config(seed=1))
print(f"seed 0 twice: {a:.10f} {b:.10f} identical={a == b}")
print(f"seed 1:       {c:.10f}")
with open("runs.jsonl", "a") as f:
    f.write(json.dumps({"config": dataclasses.asdict(Config(seed=0)), "final_loss": a}) + "\n")

🎤 Interview angle

“Your teammate's new augmentation improved validation accuracy from 91.0% to 91.6%. Do you ship it?” A strong answer:

  • Asks how many seeds per side and what the seed-to-seed spread is; 0.6 points from one run each is within typical noise.
  • Asks whether both sides got the same tuning budget and the same data split, and whether the baseline was re-run in the same setup.
  • Proposes 3–10 seeds each, a confidence interval on the difference, and a check on a held-out test set touched only once.
  • Checks that the run is reproducible: config, commit, data version and environment logged, checkpoint saved.
🏭 In the real world
Old models, properly tuned, win 🏢 DeepMind / Oxford · 2017 Melis, Dyer & Blunsom: On the State of the Art of Evaluation in Neural Language Models

How: re-evaluated popular architectures with the same large-scale automatic hyperparameter tuning.

Why this method: different code bases and tuning budgets were uncontrolled sources of variation; with them controlled, standard LSTMs set a new state of the art on Penn Treebank and WikiText-2.

Most GANs are equal 🏢 Google Brain · 2018 Lucic et al.: Are GANs Created Equal?

How: a large, neutral study with many hyperparameter settings and random restarts per model.

Why this method: improvements “can arise from a higher computational budget and tuning more than fundamental algorithmic changes”.

Random search 🧪 Research · 2012 Bergstra & Bengio: Random Search for Hyper-Parameter Optimization (JMLR)

How: compared random and grid search for neural networks and deep belief networks; analysed which hyperparameters matter.

Why this method: low effective dimensionality: only a few hyperparameters matter, and which ones differs by dataset.

Variance in benchmarks 🧪 Research · 2021 Bouthillier et al.: Accounting for Variance in Machine Learning Benchmarks

How: modelled the whole benchmarking process across five deep-learning tasks.

Why this method: data sampling, initialization and hyperparameter choice all markedly change results; randomizing more of them gives better comparisons at a fraction of the cost.

🤯 Fun fact · “reproducible” has an expiry date

PyTorch's own reproducibility notes state that completely reproducible results are not guaranteed across PyTorch releases, individual commits or platforms, and may differ between CPU and GPU even with identical seeds. Bit-identical reruns need the same hardware and software, which is why serious teams log the environment and keep container images, not just seeds.

Check yourself

1. Config A over 4 seeds: 90.1, 89.3, 90.6, 89.8 (mean 89.95). Config B: 90.4, 91.0, 89.9, 90.5 (mean 90.45). Seed-to-seed standard deviation is about 0.5 on each side. Roughly, is the 0.5-point difference clearly real?
Each mean has standard error 0.5/√4 = 0.25; the difference has √(0.25² + 0.25²) ≈ 0.35. With so few runs the t multiplier is about 2.5, giving roughly 0.5 ± 0.9. More seeds (or a bigger effect) are needed. This is the playground's lesson in four numbers.
2. You tune 3 hyperparameters with a 4 × 4 × 4 grid (64 runs). Later analysis shows only the learning rate mattered. How many distinct learning rates did you actually try, and what would 64 random trials have tried?
A grid's points share coordinates: projected onto the learning-rate axis, 64 points collapse onto just 4 values. Random points have 64 distinct values on every axis, so the one that matters gets 64 tries. That's Bergstra and Bengio's argument.
3. Six months after launch, a regression appears and you need to retrain the exact shipped model. Your tracker has the final metrics and the checkpoint. What's most likely missing?
A checkpoint lets you use the model, not rebuild it. Rebuilding needs the code at that commit, the exact data (version or hash), every config value and seed, and the software environment, since results aren't guaranteed identical across library versions or hardware.
📝 TL;DR
  • Log every run: config (as code), git commit, data version, seeds, environment, metric curves, system stats, checkpoints. Use W&B, MLflow or TensorBoard (or a JSON file).
  • Reproducibility: torch.manual_seed, seeded data order, torch.use_deterministic_algorithms(True), cudnn.benchmark = False, CUBLAS_WORKSPACE_CONFIG; bit-identical only on the same hardware and versions.
  • Reliability: seed noise is often as large as the effects people claim. Compare means over several seeds with a confidence interval; look at every run.
  • Ablations: change one thing, same tuning budget, several seeds, re-run the baseline yourself.
  • Random (or quasi-random) search beats grid search because few hyperparameters matter; then Bayesian methods and early stopping (Optuna).
