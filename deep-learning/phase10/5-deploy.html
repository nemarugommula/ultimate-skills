Export and deploy: torch.compile, ONNX, TensorRT

A trained model is a Python object in a notebook. A product is a fast, predictable service or an app on a phone. This lesson covers the bridge: compiling the model into a graph, exporting it to a portable format, and serving it so that many users get answers quickly.

🧰 You'll need (quick reminders)
  • Memory-bound ops get faster when fused; small batches leave a GPU idle (Lesson 10.1).
  • Quantized and pruned models need kernels that understand their formats (Lesson 10.4).
  • A PyTorch model is an nn.Module whose forward is ordinary Python (Lesson 1.3).
🎯 Hook

With PyTorch 2 (announced in late 2022), the PyTorch team added one line to the library: model = torch.compile(model). Their paper reports that its compiler gave a 2.27× inference and 1.41× training speed-up (geometric mean) on an NVIDIA A100 across more than 180 real-world models, with no change to the models' code.

We ran it on this course's laptop CPU on a small block. It was slower: 13.7 ms compiled vs 12.3 ms eager, after 3–8 seconds of compiling.

Both results are real. What does a compiler actually do to a network, when does it help, and how do you get a model out of Python and onto a server or a phone?

Numbers first: eager mode pays three taxes

Plain PyTorch runs in eager mode: Python executes your forward line by line, and each operation launches its own kernel. That's wonderful for debugging and costs you three ways:

TaxWhere it hurtsGraph-mode fix
Memory round trips: every op reads and writes HBMchains of elementwise ops, norms (Lesson 10.1)fuse them into one kernel
Launch and Python overhead per opsmall models, small batches, decodingfewer, bigger kernels; CUDA graphs replay a whole step
No global viewcan't plan memory, pick kernels for exact shapes, or drop unused worksee the whole graph, then optimize it

A graph is the list of operations and the tensors flowing between them, captured once so a compiler can rewrite it. The rest of this lesson is about capturing graphs (torch.compile, torch.export), moving them between tools (ONNX) and running them fast (ONNX Runtime, TensorRT, ExecuTorch).

Fusion, counted

🤔 Why this? Graph compilation (torch.compile: TorchDynamo + TorchInductor)
  1. The problem before Eager mode launches every op separately and round-trips every intermediate through memory. Hand-fusing kernels doesn't scale to every new model.
  2. What people tried Static-graph frameworks (TensorFlow 1's sessions: fast but painful to debug); TorchScript, which the PyTorch 2 paper reports works only about half the time on real-world models when scripting; tracing with example inputs, which silently misses Python control flow; lazy tensors, which recompile whenever the traced graph changes.
  3. Why this works TorchDynamo watches Python bytecode as it runs and captures the PyTorch operations into a graph, falling back to normal Python for anything it can't capture (a “graph break”). AOTAutograd also traces the backward pass. TorchInductor then fuses and generates kernels: Triton code for GPUs, C++ for CPUs. You keep eager-mode Python and get graph-mode speed: 2.27× inference and 1.41× training geomean on an A100 in the PyTorch 2 paper.
  4. What it costs, when it fails Compile time (seconds to minutes) on the first call and on new shapes (recompiles); graph breaks from data-dependent Python (if x.sum() > 0:, .item(), printing) cut the graph into pieces; harder debugging. If time is dominated by one big matmul that's already optimal, there's little to gain; on our laptop CPU it was about 10% slower.
  5. What refined it mode="reduce-overhead" (CUDA graphs to remove launch overhead), mode="max-autotune" (benchmark kernel choices), regional compilation of repeated blocks, and torch.export for ahead-of-time deployment (next).

Getting out of Python: export

torch.compile is just-in-time: it runs inside your Python program and can fall back to Python. Deployment usually needs ahead-of-time export: one complete graph with no Python left, saved to a file that a C++ server or a phone can load.

  • torch.export traces the model into an ExportedProgram: a single full graph of core ATen operations, with no graph breaks allowed (it errors instead), plus declared dynamic dimensions (for example a variable batch size). It's the entry point for ExecuTorch and AOT compilation.
  • ONNX (Open Neural Network Exchange) is an open standard: “a common set of operators” and a common file format, so a model trained in one framework can run in many engines. PyTorch's exporter is torch.onnx.export(model, args, "model.onnx", dynamo=True), built on torch.export; dynamo=True is the default since PyTorch 2.9.
🤔 Why this? ONNX as an interchange format
  1. The problem before N training frameworks × M inference engines and hardware vendors = N × M converters, each with its own bugs. A model trained in PyTorch couldn't easily run on a phone runtime, a browser or a vendor's accelerator.
  2. What people tried Framework-specific runtimes (TensorFlow Serving, TorchScript), rewriting models by hand in C++ for each target.
  3. Why this works One shared operator set and file format turns N × M into N + M: every framework exports to ONNX, every engine imports ONNX. ONNX Runtime then splits the graph across “execution providers” (CPU, CUDA, TensorRT, Core ML, DirectML and others) and optimizes it for the hardware it finds.
  4. What it costs, when it fails New or custom ops may be missing from the standard (or from a given engine); numerical results can differ slightly between engines; export can fail on dynamic Python control flow; version mismatches between opsets bite. You must test the exported model against the original.
  5. What refined it The dynamo-based exporter built on torch.export; PyTorch-native paths that skip ONNX entirely (ExecuTorch, AOTInductor, coremltools' direct PyTorch conversion).

Serving: many users, one GPU

A model server receives requests one at a time, but GPUs love batches (a 4096 × 4096 layer is memory-bound until about 345 tokens share the weights, Lesson 10.1). Dynamic batching holds requests in a queue for a few milliseconds and runs them together. Two numbers describe a server: throughput (requests per second) and tail latency, usually p99: the time 99% of requests beat. Users feel the tail.

✏️ Worked example: why batching is nearly free

Suppose a batch of b requests takes 10 + 0.5·b ms (mostly the fixed cost of reading the weights, because it's memory-bound). One at a time, the GPU finishes 1 request per 10.5 ms: 95 requests/s at most. In batches of 32: 32 requests per 26 ms ≈ 1,230 requests/s, 13× more from the same GPU, while each request waits at most a few tens of milliseconds.

What you should see: with max batch 1 the GPU tops out near 95 req/s; at 150 req/s the queue grows without limit and p99 shoots into seconds. Batching lets the same GPU serve about 1,100 req/s with p99 under 50 ms (max batch 32 or 64). At 50 req/s, a 20 ms timeout adds latency (p50 goes from about 10 to 30 ms) because it holds requests waiting for company that rarely comes. Real servers (NVIDIA Triton Inference Server's max_queue_delay_microseconds, for example) expose exactly these two knobs.

🤔 Why this? Dynamic batching
  1. The problem before One request at a time leaves a memory-bound model at a tiny arithmetic intensity: the GPU reads all the weights for one input. In our toy it caps out at 95 req/s and latency explodes beyond that.
  2. What people tried More GPUs (expensive), client-side batching (clients don't know about each other), fixed batch sizes (requests wait for a full batch even at night).
  3. Why this works The server sees all clients. Waiting a millisecond or two to group requests reuses each weight load across the batch, so throughput rises almost linearly while latency grows only a little. A timeout bounds the extra wait when traffic is light.
  4. What it costs, when it fails Extra queueing latency (bad timeouts hurt quiet periods); padding when inputs have different lengths; memory for bigger batches. For LLMs, requests finish at different times, so static batches waste slots.
  5. What refined it Continuous batching for LLMs (add and remove sequences every decoding step) and paged KV caches, in vLLM and similar servers (AI Engineer 7.4). Autoscaling and load balancing across replicas: System Design 1.2.

🧰 Tools you'll actually use

Eager vs torch.compile, then torch.export, on a laptop CPU (torch 2.8). Notice the honest result:

import time, torch, torch.nn as nn

class Block(nn.Module):                       # the memory-bound glue around a matmul
    def __init__(self, d=1024):
        super().__init__()
        self.lin, self.norm = nn.Linear(d, d), nn.LayerNorm(d)
    def forward(self, x):
        h = torch.nn.functional.gelu(self.lin(x) * 0.5 + 1.0)
        return self.norm(h + x)

torch.manual_seed(0)
model, x = Block().eval(), torch.randn(4096, 1024)

def bench(f, reps=20):
    with torch.no_grad():
        f(x)                                  # warm-up (compiles the first time)
        t = time.perf_counter()
        for _ in range(reps):
            f(x)
    return (time.perf_counter() - t) / reps * 1e3

compiled = torch.compile(model)
print(f"eager:    {bench(model):.2f} ms")
print(f"compiled: {bench(compiled):.2f} ms")

ep = torch.export.export(model, (x,))       # one full graph, no Python left
print([n.target.__name__ for n in ep.graph.nodes if n.op == "call_function"])

# Output on our laptop CPU (compile took 3–8 s on the first call):
# eager:    12.32 ms
# compiled: 13.70 ms        ← slower here: the matmul dominates and eager already uses a fast CPU BLAS
# ['linear.default', 'mul.Tensor', 'add.Tensor', 'gelu.default', 'add.Tensor', 'layer_norm.default']

ONNX export and inference (not run here: the onnx, onnxscript and onnxruntime packages aren't installed on this laptop, and we don't download packages for lessons):

torch.onnx.export(model, (x,), "block.onnx", dynamo=True)   # needs onnx + onnxscript

import onnxruntime as ort
sess = ort.InferenceSession("block.onnx", providers=["CPUExecutionProvider"])
out = sess.run(None, {sess.get_inputs()[0].name: x.numpy()})[0]
# always compare: assert abs(out - model(x).detach().numpy()).max() < 1e-4

Gotchas: call model.eval() before exporting (dropout and BatchNorm behave differently in training mode); declare dynamic dimensions (dynamic_shapes) or the export bakes in your example's batch size; and always measure on the real target hardware, as our CPU result shows.

🎤 Interview angle

“Your image model's p99 latency in production is 400 ms; the target is 100 ms. What do you look at?” A strong answer:

  • Separates queueing from compute: if the GPU is saturated, latency is queue time; add replicas or raise throughput (batching, quantization). If the GPU is idle, look at batching timeouts, preprocessing, network and data loading.
  • Profiles the model: fuse/compile (TensorRT or torch.compile), lower precision (fp16/int8), tensor-core-friendly shapes.
  • Tunes dynamic batching: max batch and max queue delay against the p99 target; checks padding waste.
  • Verifies numerics after every conversion, and watches p99 (not the mean) on real traffic.
🏭 In the real world
torch.compile 🧰 Open source · PyTorch 2 Ansel et al.: PyTorch 2 (ASPLOS 2024)

How: TorchDynamo captures graphs from Python bytecode; TorchInductor generates Triton (GPU) and C++ (CPU) kernels.

Why this method: keeps eager-mode flexibility; 2.27× inference and 1.41× training geomean speed-ups on an A100 over 180+ models.

On-device AI across Meta's apps 🏢 Meta · 2025 Introducing ExecuTorch 1.0

How: torch.export → a compact program run by a small C++ runtime with hardware backends; used in Instagram, WhatsApp, Messenger, Facebook and Ray-Ban Display glasses, per the announcement.

Why this method: no conversion to another format, so fewer numerical mismatches between the trained and the deployed model.

Dynamic batching in a production server 🏢 NVIDIA Triton Inference Server: Batchers

How: a per-model dynamic_batching block with max_queue_delay_microseconds and optional preferred batch sizes.

Why this method: the same throughput-vs-latency dial you just played with, made a config line.

One format, many engines 🧰 Open source · ONNX ONNX Runtime execution providers

How: assigns graph nodes or subgraphs to hardware-specific providers (CUDA, TensorRT, Core ML, CPU…).

Why this method: export once, run on whatever hardware the customer has.

🤯 Fun fact · the compiler writes Triton for you

On GPUs, TorchInductor doesn't call a fixed library of fused kernels: it generates new Triton programs for the exact chain of ops in your model. Set the environment variable TORCH_LOGS="output_code" before running a compiled model and PyTorch prints the kernels it wrote (on our CPU it prints C++ instead).

Check yourself

1. A chain of 4 elementwise ops runs on a 200 MB tensor. Unfused, each op reads its input and writes its output. Fused, the kernel reads once and writes once. How much HBM traffic does fusion save?
Unfused: 4 ops × (200 MB read + 200 MB write) = 1,600 MB. Fused: 200 MB in + 200 MB out = 400 MB. For memory-bound ops, time ≈ bytes ÷ bandwidth, so this is close to a 4× speed-up for that chain.
2. You wrap your model in torch.compile and training gets slower. The logs show dozens of graph breaks, many from a line that prints loss.item() inside forward. What's going on?
.item() needs the actual value on the CPU, so Dynamo must stop the graph, run Python, and start a new graph. Many breaks mean little fusion and extra overhead (and possibly recompiles). Keep compiled regions free of prints, .item() and data-dependent branches.
3. Your server's GPU sits at 30% utilization, and p99 latency is fine, but cost per request is too high. Requests arrive steadily at high volume. What do you change first?
Low utilization with steady traffic means the GPU runs small batches. Larger batches raise arithmetic intensity and throughput per GPU, cutting cost per request; watch that p99 stays within target. More replicas would raise cost; a zero timeout makes batches even smaller.
📝 TL;DR
  • Eager mode pays for memory round trips, per-op overhead and no global view. Graph mode captures the ops and optimizes them together (fusion: 11 → 3 passes in our chain).
  • torch.compile = TorchDynamo (capture, graph breaks fall back to Python) + TorchInductor (Triton/C++ kernels). Big wins on GPUs; measure on your hardware (our CPU: slower).
  • torch.export gives one Python-free graph for deployment; ONNX is the cross-engine format; ONNX Runtime, TensorRT, ExecuTorch (1.0, 2025) and Core ML run it.
  • Serving: dynamic batching trades a little queueing for much more throughput; watch p99. LLMs use continuous batching (AI Engineer 7.4).
  • Before shipping: eval mode, numerics check after every conversion, dynamic shapes declared, p99 measured on target hardware.
