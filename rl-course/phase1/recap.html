🧾 Cheat sheet

The bandit problem

k actions, random rewards, no states. True value q*(a) = 𝔼[R | a]. Estimate Q(a) from samples. Goal: maximize total reward ⇔ minimize regret.

The update rule

Q ← Q + α(R − Q).
α = 1/N → exact average. Fixed α → tracks a changing world (recent rewards count more).

ε-greedy

With probability ε pick a random action, else argmax Q. Simple and robust, but explores blindly, so regret grows linearly.

UCB

argmax [ Q(a) + c√(ln t / N(a)) ]. Optimism in the face of uncertainty. Regret ∝ log t.

Thompson sampling

Belief Beta(W+1, L+1) per arm. Sample a guess from each, play the max, update W or L. Regret ∝ log t. Often the best in practice.

LLM links

RLHF ≈ contextual bandit. Advantage = reward − baseline: how much better than average (GRPO: the group's average). Temperature = the T in softmax exploration. Entropy collapse and the pass@k debate = explore/exploit at scale.

🗂️ Case files: five real problems, one phase later

The same five problems follow you through the course (meet them). Here's what this phase changes for each.

🌡️ The cooling plant

Now: treat a handful of fixed settings as arms and keep each one's average energy use, exploring with ε-greedy or UCB. But no single setting is best: the right one depends on the weather and the load, so at most it's a contextual bandit (context = weather + load).

Still breaks: the setting you pick now changes the temperatures you start from an hour later, and a bandit can't see that actions have consequences.

📱 The feed

Now: a good fit. Arms = thumbnails or articles, reward = a click or a play, Thompson sampling or a contextual bandit per user, as MSN and Netflix do (Lessons 1.1 and 1.4).

Still breaks: what you show today changes what the user wants tomorrow, and the bandit only counts the next click.

🦾 The robot hand

Now: not yet. A bandit has no state, but a grasp needs different motor commands for every camera view, and those commands are continuous numbers, not a few arms.

Still breaks: it needs states and sequences of actions, where each movement changes what the camera sees next.

♟️ The board game

Now: a whole game isn't a bandit: a move's worth depends on the position and on every move after it. But UCB already appears inside game search, choosing which move to look at next (Lesson 1.4).

Still breaks: you still need a way to value positions and to plan several moves ahead.

🧑‍💻 The coding agent

Now: treat one attempt at a task as one pull: sample several fixes, run the tests, and keep the average pass rate per task as its Q. “Reward − average” (Lesson 1.2) is the signal LLM training uses later.

Still breaks: one reward is spread over thousands of tokens, and the “arms” (every possible program) are effectively endless.

🧩 Frame it yourself

🧩 New problem

A language-learning app sends each user one reminder a day. It can go out at 8 am, 12 pm, 6 pm or 9 pm. Some users open it within an hour, others ignore it, and a few turn notifications off. The team wants the time slot that gets the most lessons started.

Before you open the answer, write down: the state, the action, the reward, episodic or continuing (and γ), and which method from this phase (or earlier) you'd try first.

Reveal One good framing + the classic mistakes

State: none at first (a plain bandit); then a context such as the user's time zone and when they usually practise (a contextual bandit). Action: one of the 4 time slots. Reward: 1 if a lesson starts within an hour of the reminder, 0 if not, and a clear penalty (say −5) if the user turns notifications off. Episodic? Each reminder is a one-step episode, so γ doesn't matter yet.

Method: Thompson sampling with a Beta belief per slot: the rewards are win/lose, there's no exploration setting to tune, and it stops wasting reminders on bad slots quickly. If habits drift (holidays, exam season), update with a fixed α so old data fades.

Classic mistakes: rewarding opens only, so a version that also chose how many reminders to send would spam (and lose users for good); a 50/50 test run for months, which wastes reminders on the losing slot; plain greedy after day one, which locks onto whichever slot got lucky first; and one global answer when the best slot clearly depends on the user's time zone.

📏 Reading the error bands in Lab 1

Each curve in the Lab 1 plot is the mean over 200 runs. The shaded band around it is mean ± 1.96 × standard error (1.96 ≈ the "2 standard errors" rule from Phase 0), a 95% confidence band: "if we repeated the whole experiment, the mean would land inside this band about 95% of the time." (Mean, std and standard error are explained with a playground in Lesson 0.5.)

  • Bands far apart → the difference between the algorithms is real, not luck.
  • Bands overlapping a lot → you can't claim one is better yet. Run more seeds, or accept they're about the same.

Rough rule, not a formal test. You'll do proper statistics for experiments in Phase 9.

🔬 Researcher habit #2: hypothesis → experiment → conclusion

Before running anything, write down what you expect and why. Then run it. If you were wrong, that's the interesting part, so work out why. This is the research loop you'll use for the rest of your career. The lab has a template for it at the bottom.

Boss quiz 👾

Q = 2, α = 0.25, rewards arrive: 6, then 6. What's Q after both?
After the first: 2 + 0.25·4 = 3. After the second: 3 + 0.25·3 = 3.75. It closes 25% of the remaining gap each time.
You're building a news recommender that must work well from day 1, with no tuning. Which algorithm would you try first?
Thompson sampling has no exploration setting to tune, handles uncertainty well, and is the industry favorite for this kind of problem.
In GRPO, all 8 sampled answers to a prompt get reward 1. What's the learning signal for that prompt?
No answer was "better than expected", so nothing to learn. That's why recent methods (like DAPO) filter out prompts that are all-correct or all-wrong. You'll meet this again in Phase 8.
