The slot machine problem

The simplest RL problem there is. It still contains the hardest question in RL.

🧰 You'll need (quick reminders)
  • Action and reward (Lesson 0.2). That's all: bandits have no states and no future, which is why we start here.
🎯 Hook

A slot machine is nicknamed a "one-armed bandit": it has one arm (the lever) and it takes your money. Now picture a row of them, each paying out at a different hidden rate. Which ones should you play?

Statistician Peter Whittle wrote that during WWII this problem so sapped the energies and minds of Allied analysts that someone suggested dropping it over Germany "as the ultimate instrument of intellectual sabotage."

Did you notice yourself wrestling with this?

🧭

Explore

"I've only tried machine 4 twice. It might be the best… let me try it again."

💰

Exploit

"Machine 2 has been paying well. Why waste pulls on the others?"

Every pull spent exploring is a pull not spent on the best machine you've found. But if you never explore, you might be stuck with a mediocre machine forever. This is the exploration–exploitation dilemma, and it shows up in nearly every RL problem.

💡 Big idea A multi-armed bandit is RL with no states and no future: just k actions, each giving a random reward from its own hidden win rate (the "distribution" of its payoffs). Each machine is called an "arm", after the lever on old slot machines. The goal: get the most total reward while you're still finding out which action is best.
🧠 Analogy: restaurants in a new city

You've just moved to a new city. Each restaurant is an "arm". You found one that's pretty good. Do you keep going there (exploit), or try new places that might be better, risking a bad meal (explore)? Every evening is one pull. That tension is the whole lesson, and it never fully goes away in RL.

Why start here? Bandits remove two hard parts of RL (states and delayed rewards) so you can focus on two core skills:

  1. Estimating how good an action is from noisy rewards (Lesson 1.2)
  2. Balancing exploration and exploitation (Lessons 1.3 and 1.4)
Math refresher Probability & expected value (the "long-run average")

Probability = how often, in the long run

A probability is a number from 0 (never) to 1 (always). "This machine has a 0.3 win rate" means that if you pulled it a huge number of times, about 30% of pulls would win.

Expected value = the long-run average

Multiply each outcome by how likely it is, then add them up.

Fair die: 1·⅙ + 2·⅙ + 3·⅙ + 4·⅙ + 5·⅙ + 6·⅙ = 3.5. You'll never actually roll 3.5, but it's what you average if you roll forever.

Mathematicians write that same computation compactly (𝔼 = "expected value of", P(x) = "probability of outcome x", Σ = "add up over all outcomes"):

𝔼[X] = Σx P(x) · x "Expected value = sum over outcomes of (probability × value)"

Slot machine with 30% win rate: 0.3 × 1 coin + 0.7 × 0 coins = 0.3 coins per pull.

The running average wobbles a lot at first, then settles down to 3.5. This is the Law of Large Numbers: averages of more samples get closer to the expected value. It's the reason we can learn action values from experience at all.

Talking about bandits like a researcher

Each action a has a true value: the reward you'd get on average if you chose it forever.

q*(a) = 𝔼[ R | A = a ] "the true value of action a = the expected reward, given that I pick a"

We don't know q*. (The * means "true, optimal".) So we keep an estimate, Q(a), the average reward we've seen so far from a:

Q(a) = (sum of rewards from a) / (number of times we picked a) That's exactly the "avg" number under each machine in the game above.

Measuring how well you did: regret

Regret = how much reward you lost compared to someone who knew the best machine from the start.

Regret = Σt ( q*(best) − q*(at) ) "for each pull, add up how much worse my choice was than the best choice"

A good bandit algorithm keeps regret low. In the best algorithms, regret grows only like log(t) (log t grows incredibly slowly: doubling the number of pulls adds only a constant amount; more in 1.4): after a while they almost never make a bad pull. You'll build one in Lesson 1.4.

Wait, how can you compute regret without knowing q*? You can't, in real life. Regret is a researcher's scorecard: you can only compute it in a simulation, where you made up the true win rates yourself. The agent never sees it.

🌍 Where it's used
A bandit instead of test-then-commit 🧪 Research · 2018 Yahoo: testing news headlines

How: arms = different headlines for the same story · reward = a click · no state: every visitor faces the same choice.

Why this method: Yahoo split traffic equally for a fixed test, then sent everyone to the winner. A bandit shifts traffic to the better headline while still testing; in their evaluation it got 3.69% more clicks.

Explore vs exploit, with patients 📜 History · 2011 The BATTLE lung-cancer trial

How: arms = four targeted drugs · reward = the cancer is under control after 8 weeks · 255 patients. The choice also used each tumour's markers (a “context”, Lesson 1.4).

Why this method: the first patients were split equally (explore); later ones were sent more often to drugs that were working for tumours like theirs (exploit). Regret here is counted in patients.

🤯 Fun fact

Bandits run real products. Microsoft's Decision Service (a bandit system that also reads who the user is) beat MSN's editor-picked ordering by more than 25% in clicks on one homepage section, and became the default for all logged-in MSN users in early 2016 (Agarwal et al.). Netflix uses the same kind of bandit to pick which artwork to show you for each title (Netflix Tech Blog). The trick: a bandit sends traffic toward the winner while it's still testing, instead of wasting half the users on the losing option.

🌉 LLM bridge · RLHF is (almost) a bandit

The InstructGPT paper (the method behind ChatGPT) describes its RL environment as a bandit: show a random prompt, the model gives a response, and a reward model returns a single score. There's one decision and one reward.

Because the prompt changes each time, it's a contextual bandit (the best "arm" depends on the context). And the "arms" here are every possible response, which is an astronomically large number. Sampling several answers to the same prompt and comparing their scores, which GRPO does (Phase 8), is like pulling an arm several times to estimate its value.

✏️ Worked example: counting regret

Three machines with true average payouts 0.5, 0.7 (the best) and 0.3. You pull the 0.5 machine, then the 0.7 machine, then the 0.3 machine.

Regret = (0.7 − 0.5) + (0.7 − 0.7) + (0.7 − 0.3) = 0.2 + 0 + 0.4 = 0.6. That's how much expected reward you gave up compared with always pulling the best machine. Learning well means this number grows slowly.

Check yourself ✅

1. A machine pays 5 coins with probability 0.2, otherwise 0. What's its expected value?
0.2 × 5 + 0.8 × 0 = 1 coin per pull on average.
2. What's the difference between q*(a) and Q(a)?
Lowercase q* = truth (hidden). Capital Q = our running estimate. With enough samples, Q → q* (Law of Large Numbers).
3. You pulled machine A once and won. You pulled machine B 20 times and won 12. Which estimate should you trust more?
One sample tells you very little. How sure you are about an estimate matters, not only the estimate itself. Lesson 1.4 turns this into a smarter exploration strategy (UCB).
📝 TL;DR
  • Bandit = k actions, random rewards, no states. Maximize total reward.
  • q*(a) = true expected reward; Q(a) = our sample-average estimate.
  • Expected value = long-run average. More samples → better estimates.
  • Explore vs exploit is the core dilemma. Regret measures how well you handle it.
