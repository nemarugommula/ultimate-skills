Phase 7 · Lesson 1

An LLM is a policy: the token-level MDP

Everything from Phases 0–6 now gets pointed at language. Here's the precise mapping.

🧰 You'll need (quick reminders)
  • Policy π(a|s) = the probability of each action in each state (Lesson 0.2).
  • Softmax with temperature: scores → probabilities, flatter or sharper (Lesson 5.1).
  • MDP = states, actions, transitions, rewards, γ (Lesson 2.2).
🎯 Hook

Every time ChatGPT writes a word, it is choosing one action out of roughly 100,000 (GPT-4's tokenizer has about 100k tokens; Llama 3's has 128k). A 500-token answer is a 500-step episode. RL for LLMs is the same RL you've learned, at that scale.

💡 Big idea An LLM is a stochastic policy πθ(token | text so far). State = prompt + tokens generated so far. Action = the next token. Transition = append it. Reward = usually one score at the end. RL adjusts θ so that high-reward responses become more likely.
🧠 Analogy: autocomplete as a game

Picture your phone's autocomplete playing a game: at every step it picks the next word (an action), the message so far is its situation (the state), and only when the message is finished does someone rate it (the reward). Writing one reply = playing one episode of hundreds of moves. RL teaches it to pick words that lead to better-rated messages.

🔧 How an LLM writes, in 4 steps
  1. Text → token IDs. A tokenizer chops the text into word pieces and replaces each with a number: "Paris." might become two IDs, one for "Paris" and one for ".".
  2. One forward pass reads all the IDs and outputs, at every position, a score (logit) for each of the ~100k tokens: "what comes next after this prefix?". The vector the network computes just before those scores is the hidden state (its summary of the text so far; reward models reuse it in 7.3).
  3. Generate: take the last position's scores → softmax with temperature T → sample one token → append it → repeat until the end token. So writing 500 tokens takes 500 passes, but scoring an answer that already exists takes just 1 pass (every position is scored at once). That's why RL, which must generate fresh answers, costs far more than DPO (7.5), which only scores existing ones.
  4. Base vs chat model. A base model only continues text. A chat model was then fine-tuned (SFT, 7.2) on conversations wrapped in a chat template, with special role tokens marking who speaks (user, assistant). That template-wrapped prompt is the x in every formula of this phase.

The core difficulty: one score arrives for ~500 choices. Which tokens earned it? That's the credit-assignment problem (which earlier move deserves the praise? Lessons 0.1, 5.5), at its most extreme, and every method in Phases 7–8 is a different answer to it.

🎮 Playground · A tiny "LLM" choosing the next token

Prompt: "The best way to learn RL is to". Here are the model's logits for a few candidate next tokens: the raw scores the network outputs for each token, before softmax turns them into probabilities. Adjust the temperature and top-p, then sample.

  • Temperature divides the logits before softmax: low means nearly greedy, high means flatter and more random (Lesson 5.1).
  • Top-p (nucleus sampling) keeps only the most likely tokens whose probabilities add up to p, cutting off the long tail of weird tokens.
  • During RL training, responses are usually sampled with temperature ≈ 1 and no top-p, so the samples come from πθ itself. Otherwise it's like grading a student on answers someone else edited: the policy-gradient math (which assumes samples come from πθ) is subtly wrong.
Math refresher The probability of a whole response

The probability of a response is the product of its token probabilities (chain rule of probability):

π(y | x) = π(y1|x) · π(y2|x, y1) · …   ⇒   log π(y|x) = Σt log π(yt | x, y<t) Products of many small numbers underflow to 0 in a computer, so we always work with the sum of log-probabilities.

Example: 3 tokens with probabilities 0.5, 0.2, 0.9 → probability 0.09 → log-probability ln 0.5 + ln 0.2 + ln 0.9 ≈ −0.69 − 1.61 − 0.11 = −2.41. A 500-token answer can have log-probability around −300, a probability of about 10−130. That's normal.

logits = model(input_ids).logits                      # (batch, seq, vocab)
logp   = logits.log_softmax(-1)
# Position t's scores predict token t+1. So drop the LAST prediction (nothing to check it against)
# and the FIRST token (nothing predicted it), which lines each prediction up with the token it guessed.
token_logp = logp[:, :-1].gather(-1, input_ids[:, 1:, None]).squeeze(-1)  # log π of each actual next token
seq_logp = (token_logp * response_mask).sum(-1)      # sum over RESPONSE tokens only (not the prompt)

That snippet is the core of every RLHF, DPO and GRPO implementation. You'll write it in Labs 7 and 8.

✏️ Worked example: scoring a 3-token answer in one pass

Prompt "…capital of France? A:", answer = " Paris" "." ⟨end⟩. Feed prompt + answer through the model once and read off three predictions:

  • at the prompt's last token ("A:"), the score for " Paris": π = 0.8 → ln 0.8 ≈ −0.22
  • at " Paris", the score for ".": π = 0.7 → ln 0.7 ≈ −0.36
  • at ".", the score for ⟨end⟩: π = 0.9 → ln 0.9 ≈ −0.11

log π(answer | prompt) = −0.22 − 0.36 − 0.11 ≈ −0.69, so probability 0.8 × 0.7 × 0.9 ≈ 0.50. Each prediction sits one position before the token it scores: that's the shift-by-one in the code. The prompt's own tokens are never added in, because the policy didn't choose them.

🎬 Animation · One reply = one episode, token by token

Watch an (illustrative) model answer a question. Each step is one RL step: the state is all the text so far, the action is the next token, chosen from the policy's probabilities. The running log-probability adds up as it goes. The reward only arrives when the reply ends.

Two views: token-level vs sequence-level

🔤

Token-level MDP

Each token is an action. Lets you assign per-token credit (PPO + GAE with a critic, Phase 5). Thousands of steps per episode.

📜

Sequence-level bandit

The whole response is one action, scored once (Lesson 1.1: "RLHF is almost a bandit"). GRPO, RLOO and DPO mostly think this way.

🌍 Where it's used
An LLM as a policy over tokens 🏭 In production · 2022 OpenAI: Introducing ChatGPT

How: state = the conversation so far · action = the next token · reward = a learned score for the finished reply · policy = the chat model itself.

Why this method: copying demonstrations only teaches what trainers wrote. Treating the model as a policy lets RL push it toward replies people rank higher (the same recipe as InstructGPT).

The whole answer as one action (a bandit) 🏭 In production · 2025 DeepSeek-R1 (2025)

How: state = a maths or code problem · action = the full written answer · reward = a rule checks the final answer and the format. No critic: answers are compared with other answers to the same problem.

Why this method: the only signal arrives at the end, so scoring each token would mean training a value model as big as the LLM. One reward per answer skips that.

🤯 Fun fact

Tokens are often word pieces, and tokenization causes famously strange failures. Models long struggled with "how many r's are in strawberry?" partly because "strawberry" is a few multi-letter tokens, so the model never directly "sees" individual letters. The policy acts on tokens, not characters.

1. In the token-level MDP, what is the transition function?
The "world" is trivial for text generation. The hard parts are the enormous state space and the sparse reward.
2. Token probabilities 0.5 and 0.1. What's the sequence log-probability (natural log)?
ln 0.5 + ln 0.1 ≈ −0.693 − 2.303 = −2.996 (= ln 0.05).
3. Why sample at temperature 1 without top-p during RL training?
The on-policy math needs the samples' distribution to match the policy being differentiated (or an importance-sampling correction).
📝 TL;DR
  • LLM = stochastic policy over ~100k tokens. State = text so far. Deterministic transitions. Reward at the end. γ = 1.
  • log π(y|x) = Σ token log-probs, summed over response tokens only.
  • Temperature and top-p shape sampling. RL samples at T ≈ 1 so the samples match πθ.
  • Token-level MDP (PPO + critic) vs sequence-level bandit (GRPO, DPO).
