Method chooser 🧭

Answer one plain question at a time about your problem. You'll get the method family to start with, why, what to try if it fails, and the lessons that teach it.

💡 How to read the answer

This is a starting point, not a law. Real systems mix families: AlphaZero is search + learned values + self-play; a chatbot is copied examples first, then RL. Start with the suggestion, keep a simple baseline to beat, and use the “if it fails” line when it does. The first questions come from Lesson 0.6: Is it an RL problem?

Could a few rules you can write down do the job well enough?

e.g. “lock the account after 5 wrong passwords”.

  • Yes

    📝 Plain rules / code (no learning)

    Why: rules are cheap, testable and easy to explain. Google's Rules of ML start with “don't be afraid to launch without machine learning”.

    If it fails: when exceptions pile up, collect examples with the right answer and learn from them (supervised learning), and keep the rules as the baseline.

        • No, one answer per prompt

          🧩 RLVR with GRPO (verifiable rewards)

          Why: the reward is a cheap, honest check. GRPO samples several answers per prompt and scores each against the group's average, so it needs no separate value network.

      • No, quality is judged by people

        Do you have pairs of answers where a person marked the better one?

        • Yes, preference pairs

          💬 DPO first, RLHF if you need more

          Why: DPO learns straight from “A beats B” pairs with an ordinary training loop: no reward model and no RL loop. RLHF (a learned reward model + PPO with a KL leash) explores beyond your pairs but is harder to run.

          If it fails: if the model drifts into odd, over-long answers, tighten the KL leash (β); if DPO plateaus, collect fresh pairs on the current model's own answers, or move to RLHF.

            Why: an AI judge with clear principles or a per-task checklist gives feedback far more cheaply than people, so you can produce preference pairs or rewards at scale.

            If it fails: judges have biases (length, style, their own answers); spot-check with people and make rubric items specific and checkable.

            🏷️ Copy good examples first (supervised fine-tuning)

            Why: with no checker, no pairs and no rubric, the most reliable signal is a set of good example answers to imitate. Best-of-N (sample several, keep the best) can improve it cheaply.

            If it fails: collect preference pairs on the model's own answers (then DPO), or write a rubric (then AI feedback).

      Do you have the right answer for each decision?

      Labelled data, or an expert whose actions you can copy.

      • Yes, for one-off predictions (spam or not, a price estimate)

        🏷️ Supervised learning (not RL)

        Why: each decision stands alone and comes with its right answer. Copying the answers uses all that information; a reward would throw most of it away.

        If it fails: if your predictions start changing the data you see later (a recommender shaping what people click), choices carry over and you're back on the RL path.

        Learn it: 0.6 Is it an RL problem? · 4.2 Neural nets refresher

      • Yes, an expert's actions over time (driving logs, robot demos)

        🧑‍🏫 Imitation learning (behaviour cloning, DAgger, inverse RL)

        Why: copying an expert's actions is far cheaper than discovering them by trial and error, and needs no reward at all.

        If it fails: small mistakes drift off the expert's path into situations they never showed, so ask the expert to label those (DAgger); to beat the expert, fine-tune with RL or offline RL.

        Learn it: 6.7 Imitation & inverse RL · 6.4 Offline RL

        Does your choice change what happens or what you see next?

        Does today's action change tomorrow's situation, or is every choice a fresh start?

        • No, every choice is a fresh start

          🎰 Bandits (explore vs exploit)

          Why: with nothing carried over there's no future to plan for. The whole problem is trying options often enough to find the best while mostly using it. ε-greedy, UCB and Thompson sampling do this well.

          If it fails: if the best option depends on who or what you're choosing for, use a contextual bandit; if choices turn out to carry over, move on to the RL path.

          Learn it: 1.1 The slot machine problem · 1.3 ε-greedy · 1.4 UCB & Thompson

        • Yes, choices carry over

          Do you know the model exactly: every rule and every probability of what happens next?

          • Yes, and I could list every state in a table

            🗺️ Dynamic programming (value iteration, policy iteration)

            Why: with the full model you can compute the best policy directly from the Bellman equation, with no trial and error at all.

            If it fails: too many states to sweep: plan only from the current state with search, or learn values with a neural net.

            Learn it: 2.2 MDPs · 2.4 The Bellman equation · 2.5 Policy iteration · 2.6 Value iteration

          • Yes, but far too many states to list (like Go or chess)

            Is there an opponent (a two-player game)?

            • Yes

              ♟️ Search + self-play (the AlphaZero recipe)

              Why: MCTS uses the known rules to look ahead from the current position only; a network learned by playing against copies of itself guides the search and judges positions.

              If it fails: self-play can go in circles (A beats B beats C beats A), so play against a pool of past versions; if you can't simulate the rules, learn a model (MuZero).

              Learn it: 6.3b MCTS & AlphaZero · 6.6 Self-play & multi-agent RL

            • No, a single agent

              🌲 Planning by search (MCTS) with learned values

              Why: you can't list every state, but you can simulate from the one you're in. Search looks ahead a few moves; learned values estimate the rest.

              If it fails: if search is too slow at decision time, train a policy network to copy the search's choices and use it alone.

              Learn it: 6.3b MCTS & AlphaZero · 6.3 Model-based RL

          • No, I don't know the model

            Can you try things and see what happens?

            • Yes, cheaply (a fast simulator or a safe system)

              Could you list every state in a table (thousands, not billions)?

              • Yes, it's small

                👣 Tabular Monte Carlo, TD learning, SARSA, Q-learning

                Why: one value per state (or state–action) learned from experience: simple, exact enough and easy to debug. Q-learning is the usual first try.

                If it fails: learning is slow when the reward comes late, so use n-step returns; if the table gets too big, switch to a neural net.

                Learn it: 3.1 Monte Carlo · 3.2 TD learning · 3.3 SARSA · 3.4 Q-learning · 3.5 n-step & traces

              • No, too many (images, sensor readings)

                Are the actions a few buttons, or continuous knobs?

                Buttons: left / right / fire. Knobs: a steering angle, a motor force, a temperature setting.

                • A few discrete buttons

                  🧠 DQN family (DQN, Double, Dueling, Rainbow)

                  Why: a neural net estimates the value of each button from the raw state, and it reuses past experience from a replay memory, so it's sample-efficient.

                  If it fails: it's sensitive to seeds and settings, so check several seeds first; if the reward is rare, add an exploration bonus; PPO is the robust alternative.

                  Learn it: 4.1 Why tables fail · 4.3 DQN · 4.4 Rainbow · 6.5 Exploration

                • Continuous knobs

                  Are samples so cheap you can use millions of fresh ones (a fast, parallel simulator)?

                  • Yes, millions are fine

                    🎯 Policy gradients: PPO

                    Why: it learns the policy directly (so any kind of action works), and its clipping keeps each update small and stable. It's the robust default when data is cheap.

                    If it fails: normalise advantages, check the clip fraction and KL; if each sample is expensive, reuse old data with SAC instead.

                    Learn it: 5.1 Why policies? · 5.2 REINFORCE · 5.4 Actor-Critic · 5.5 GAE · 5.6 PPO

                  • No, each sample costs real time

                    🚀 Off-policy actor-critic: SAC or TD3

                    Why: they reuse every past sample from a replay memory, so they need far fewer. SAC also keeps its actions varied on purpose, which helps exploration.

                    If it fails: if real tries are still too expensive, learn a model of the world and practise inside it (model-based RL).

                    Learn it: 6.1 DDPG & TD3 · 6.2 SAC

            • Yes, but each try is slow or costly (a real robot, a real plant)

              🔮 Model-based RL (Dyna, Dreamer, MuZero)

              Why: learn a model of how the world responds from a few real tries, then practise and plan inside that model instead of the real thing.

              If it fails: the agent exploits the model's mistakes, so keep imagined rollouts short and check them against reality; or use SAC, which also squeezes a lot from each real sample.

              Learn it: 6.3 Model-based RL · 6.2 SAC

            • No, I only have logs from an old system

              📼 Offline RL (CQL, IQL)

              Why: you can't explore, so the method must learn from the logs alone and stay close to actions the logs actually contain, instead of trusting guesses about untried ones.

              If it fails: if the logs show one narrow behaviour, imitate the best episodes instead; estimate the new policy's value from the logs (with importance weights) before trying it for real.

              Learn it: 6.4 Offline RL · 6.7 Imitation · 5.6 Importance sampling (in PPO)
