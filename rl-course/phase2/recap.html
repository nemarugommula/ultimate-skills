🧾 Cheat sheet

Markov property

The current state holds everything needed to predict the future. Not Markov? Add the missing info (velocity, frame stack, memory).

MDP

(S, A, P, R, γ). P(s'|s,a) = transition probabilities. Code: P[s][a] = [(p, s', r, done), …]. Knowing P and R = having a model.

Value functions

Vπ(s) = 𝔼[G | s]: "how good is this place?"
Qπ(s,a) = 𝔼[G | s, a]: "how good is this move?"
V = Σa π(a|s) Q(s,a).

Bellman expectation

Vπ(s) = Σa π(a|s) Σs' P(s'|s,a) [r + γVπ(s')]

Bellman optimality

V*(s) = maxa Σs' P [r + γV*(s')]
Q*(s,a) = Σs' P [r + γ maxa' Q*(s',a')]

Algorithms (need a model)

Policy evaluation: repeat Bellman sweeps until converged.
Policy iteration: evaluate ↔ greedy improve until stable.
Value iteration: repeat max-sweeps → V* → greedy policy.

Two limits of DP

Needs the model P, R (→ Phase 3: learn from experience).
Sweeps every state (→ Phase 4: neural networks generalize).

LLM links

LLM = MDP with trivial P and ~105000 states. Critic = learned V. GRPO's group mean = Monte Carlo V. Process reward models ≈ V(partial answer). Test-time search = local Bellman backups.

🗂️ Case files: five real problems, one phase later

The same five problems follow you through the course (meet them). Here's what this phase changes for each.

🌡️ The cooling plant

Now: if you had a perfect simulator of how temperatures react to each fan, pump and chiller setting, you could plan: chop sensor readings into buckets and run value iteration to get the best setting for every state.

Still breaks: nobody hands you that transition table for a real building, and every extra sensor multiplies the states to sweep.

📱 The feed

Now: the user becomes a state (recent interests, how tired of the feed they are), so what you show today changes tomorrow. Bellman says the value of a recommendation = click now + γ × value of the user you leave behind, so clickbait that annoys people scores low.

Still breaks: you don't know P (how a person's tastes shift after each video), and users × items are far too many states to sweep.

🦾 The robot hand

Now: not yet. You can write the MDP down, but DP needs an exact table of what each motor command does to the object, and no physics model of fingers, friction and contact is that good.

Still breaks: joint angles are continuous (the curse of dimensionality from Lesson 2.6), so even a perfect model couldn't be swept.

♟️ The board game

Now: the rules are a perfect model, so in principle value iteration solves the game exactly: back the win/loss values up from finished positions with the Bellman max.

Still breaks: Go has about 10170 positions, so one sweep would outlast the universe.

🧑‍💻 The coding agent

Now: it's an MDP: state = repo + conversation, action = next token or tool call, reward = tests pass at the end. V(half-finished attempt) = the chance it ends with passing tests.

Still breaks: the state space is astronomically large and running a tool has no transition table, so you must learn from sampled attempts instead of sweeping.

🧩 Frame it yourself

🧩 New problem

A home has rooftop solar and a 10 kWh battery. Electricity from the grid is cheap at night and expensive from 5 to 9 pm, and you have a year of hourly records of solar output and household use. Every hour the controller decides what the battery should do. Your goal: the lowest power bill.

Before you open the answer, write down: the state, the action, the reward, episodic or continuing (and γ), and which method from this phase (or earlier) you'd try first.

Reveal One good framing + the classic mistakes

State: battery charge (0–10 kWh, in 1 kWh steps) + hour of day: 11 × 24 = 264 states. Action: charge from the grid, discharge to the house, or idle. Reward: −(cost of grid power bought that hour). Episodic? Continuing (the house never stops), with γ ≈ 0.99, or treat each day as an episode and keep some charge at midnight.

Method: value iteration (or policy iteration). The tariff is known and the year of records gives you P: the chance of each amount of solar and use at each hour. With only 264 states, a full sweep takes milliseconds, so this is exactly where DP shines.

Classic mistakes: leaving the hour out of the state (then it isn't Markov: the price and the sun depend on the time); a reward that ignores battery wear, so the optimal policy cycles it all day; treating solar as certain instead of using probabilities; and a one-day episode with nothing for charge left at midnight, so it always empties the battery before the end.

Boss quiz 👾

γ = 1, deterministic. Three cells in a row: A → B → 💎. Every ordinary step costs −1; the step onto 💎 gives +10 instead (its −1 is already folded into the +10). Under "always go right", what are V(B) and V(A)?
Work right to left with Bellman. V(B) = +10 + 1×V(💎) = 10 + 0 = 10 (the step onto 💎 gives +10, and a terminal state is worth 0). V(A) = −1 + 1×V(B) = 9.
You run value iteration and the robot's "optimal" policy avoids the goal forever. Most likely cause?
The 😴 Lazy robot: +2 per step with γ = 0.9 is worth 20 forever, which beats the gem's 10. Fix the rewards, not the algorithm.
Which of these does dynamic programming need that a real robot usually doesn't have?
The robot gets rewards by acting, and you choose γ. But nobody gives it P. Phase 3 learns without P, from experience alone.
🚀 What's next: Phase 3

🏁 Phase 2 done: you can now write a small problem down as an MDP, compute exact values with Bellman sweeps, and read off the optimal policy. Next payoff: doing the same without being handed P.

Throw away the rulebook. The agent doesn't know P or R; it can only act and observe. You'll learn values from experience with Monte Carlo (you've already seen it in Lesson 2.3), TD learning (Bellman + the one-line update rule from Phase 1, together at last), and Q-learning, the algorithm that later scaled up to Atari.
