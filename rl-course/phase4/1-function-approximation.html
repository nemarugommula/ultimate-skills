Function approximation: why tables fail

Swap the giant lookup table for a small function that can guess values for states it has never seen.

🧰 You'll need (quick reminders)
  • V and Q tables: one stored number per state (or state-action pair), as in Phases 2–3.
  • TD error δ = reward + γ × next value − current value: the "surprise" (Lesson 3.2).
🎯 Hook

An Atari screen is 210 × 160 pixels, each one of 128 colors. The number of possible screens is a number with about 70,000 digits. A Q-table with one row per screen could never be filled, and you'd almost never see the same screen twice anyway. Every serious RL success since the 1990s has had to solve this.

The problem with tables

💾

Too big

Backgammon ~1020 states, Go ~10170, an LLM's possible conversations roughly 105000. No memory can hold them.

🙈

No generalization

A table learns nothing about state 1,001 from state 1,000, even if they're nearly identical (the ball moved one pixel).

🐢

Too slow

Every single state must be visited many times. You'd need more experience than the universe has time for.

💡 Big idea Replace the table with a function with adjustable weights w: v̂(s, w) ≈ V(s). Updating w for one state also changes the guesses for similar states. That's generalization, and it's what lets an agent handle situations it has never seen.
🧸 Analogy · house prices

A table approach would memorize the price of every house ever sold, and have no idea about a new one. A function approach learns a rule, like "price ≈ ₹8,000 × square feet + ₹20 lakh × good location + …". It has only a few numbers to learn, and it works for houses it has never seen.

Features and a linear value function

Describe each state with a list of numbers called features x(s), for example "distance to the gem", "distance to the lava", "is there a wall to the right?". Then the simplest function is a weighted sum:

v̂(s, w) = w1x1(s) + w2x2(s) + … = w · x(s) "value = weights × features, added up" (a dot product). The hat on v̂ means "our estimate".

And learning is the same TD update you know, now nudging weights instead of table cells. (It's called semi-gradient TD: the target r + γv̂(s') also depends on w, but we pretend it doesn't. That's faster and usually works, but it's exactly the ingredient that can blow up in Lesson 4.3. Differentiating through the target too is stable but slow.)

w ← w + α · δ · x(s) δ = r + γv̂(s') − v̂(s), the TD error: how surprised we were (what happened minus what we predicted). Each weight moves in proportion to how "active" its feature was in this state.
Math refresher Vectors, dot products and gradients (for programmers)

A vector is just a list of numbers: x = [3.0, 0.5, 1.0].

The dot product w · x = sum(w[i] * x[i] for i in range(n)): multiply matching entries and add them up.

The gradient ∇v̂ is a vector saying "if I nudge each weight up a little, how much does the output change?". For a linear function, the gradient with respect to w is simply x(s): weight i matters exactly as much as feature i is switched on. That's why the update above multiplies by x(s).

✏️ Worked example: one update to a linear value function

Describe each gridworld cell with 2 features: x₁ = steps to the gem, x₂ = 1 if next to lava else 0. Weights w = [−1.2, −5]. For a cell 3 steps away, not near lava: v̂ = −1.2 × 3 + (−5) × 0 = −3.6.

The agent steps from it and the TD error is δ = +0.6 (better than predicted). With α = 0.1: w₁ += 0.1 × 0.6 × 3 = +0.18 → −1.02. w₂ += 0.1 × 0.6 × 0 = 0 (that feature wasn't active, so it doesn't change).

The magic: every cell 3 steps from the gem now gets a better estimate too, including ones the agent has never visited. That's generalization.

A 100-cell corridor. The true value (dashed) is a smooth curve. The agent only sees a few noisy samples (dots). The table (orange) knows only the cells it visited. The function (teal) is a sum of k smooth "bump" features, fitted to the samples.

Try it: with 20 samples the table covers about a fifth of the corridor, but the function already draws a decent curve everywhere. Then slide k:

  • k = 2–3: too simple. It can't bend enough (underfitting).
  • k ≈ 8: just right.
  • k = 40 with few samples: it wiggles through every noisy dot (overfitting). Add more samples and it calms down.

🌍 Where it's used
Features + a linear value (shared weights) 🧪 Research · 2010 Yahoo!: picking the front-page news story (LinUCB)

How: state = features of you and of each candidate story · action = which story to feature · reward = a click. Predicted click rate = weights · features, plus a UCB-style exploration bonus (Lesson 1.4).

Why this method: users and stories change daily, so a table per story never fills; shared weights generalize. On 33 million logged visits it got 12.5% more clicks than a feature-blind bandit.

Features that generalize: overlapping tiles 🧪 Research · 2019 DiDi: how valuable is a driver's next location?

How: state = a driver's place and time · action = which ride request to give each driver · reward = the fare. Features = which hexagon map tiles (several sizes) contain the place; values learned by TD.

Why this method: DiDi's earlier, deployed table of place-and-time values couldn't generalize beyond its historical data. Overlapping tiles let nearby places share what they learn; it won live A/B tests.

🤯 Fun fact

Arthur Samuel's 1959 checkers program already did this. It scored boards with a weighted sum of hand-picked features (piece advantage, mobility, center control…) and tuned the weights by playing itself. In 2013, DQN replaced the hand-picked features with a neural network that learns its own features from pixels. That's the next three lessons.

🌉 LLM bridge · value heads are linear function approximation

The value model in RLHF (Phase 7) is usually an LLM with its word-prediction layer swapped for a single linear "value head": v̂ = w · h, where h is the model's last hidden state. That's exactly this lesson: a linear function on features, except the features are learned by a huge transformer. Reward models are built the same way.

Check yourself ✅

1. What's the main advantage of function approximation over a table?
Generalization is the whole point. It's also the source of new problems: a change made for one state can mess up another (lesson 4.3).
2. Linear v̂ = w · x with w = [2, −1] and x(s) = [3, 4]. What's v̂(s)?
2 × 3 + (−1) × 4 = 6 − 4 = 2.
3. Your function fits the training samples perfectly but is wildly wrong between them. What's happening?
More data, fewer features, or regularization helps. The same trade-off as in all of machine learning.
📝 TL;DR
  • Tables can't scale: too many states, and no generalization.
  • Function approximation: v̂(s, w). Learn the weights, not table cells.
  • Linear: v̂ = w · x(s). Semi-gradient TD: w ← w + α δ x(s).
  • Watch out for underfitting vs overfitting. Neural networks learn the features themselves (next lesson).
