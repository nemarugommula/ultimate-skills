Phase 8B · Lesson 14

Scaling agentic RL: environments, long horizons & real users

Agents keep taking on longer tasks. Three bottlenecks decide how fast that continues: enough environments, tasks longer than the context window, and the gap between simulation and real users.

🗓️ Last reviewed: Oct 2026. The numbers in this lesson age in months, not years.

🧰 You'll need (quick reminders)
  • Agentic RL (Lesson 8.10) and the coding-agent recipe (last lesson).
  • Asynchronous training and its staleness trade-off (Lesson 8.11).
🎯 Hook

METR, an AI evaluation nonprofit, timed human experts on a large set of software tasks and asked: how long a task (in human time) can an AI finish half the time? In March 2025 their answer for Claude 3.7 Sonnet was about 50 minutes, and this "time horizon" had been doubling roughly every 7 months since 2019. Then the trend outran its own forecast. On METR's newer, larger task suite (Time Horizon 1.1), the doubling time since 2023 is about 4.2 months; Claude Opus 4.6 (Feb 2026) measured about 12 hours, and by April 2026 a preview model passed 16 hours, the point where METR says its tasks can no longer measure reliably. Longer tasks mean longer RL episodes, which is exactly what makes agentic RL hard to scale.

💡 Big idea Scaling agentic RL is mostly about three bottlenecks: ① environments (each rollout needs a live sandbox, and you need thousands at once), ② horizons (tasks can need more tokens than the model's context window holds), and ③ realism (a simulated computer is easy; a simulated user is not). Labs attack each one differently.
🧠 Analogy: training pilots

① You need many flight simulators running at once (environments). ② Long-haul flights outlast a pilot's short-term memory, so pilots keep a logbook and write handover notes (summarization). ③ Simulators can't fully reproduce real passengers and real weather, so eventually pilots learn from real flights, with careful monitoring (learning from real users).

① Environments: the new bottleneck

  • Qwen3-Coder (July 2025): "the key challenge of Agent RL lies in environment scaling". Alibaba built a system running 20,000 independent environments in parallel on its cloud.
  • An industry of environments: by 2025 a wave of startups was building RL environments to sell to large labs. In response, Prime Intellect launched an open Environments Hub (Aug 2025) where anyone can publish, share and reuse environments, with bounties for wanted ones.
  • Why it's hard: each environment is a container with a real repository, its dependencies, working tests and a reward script. Each rollout runs real commands, which is slow and has a long tail (Lesson 8.11's idle-GPU problem, now with containers).

② Horizons: learning to take notes

A hard task can need hundreds of tool calls and far more tokens than fit in context. Common workarounds chop off old context or ask a separate prompt to summarize it, and both can lose critical details. Cursor's 2026 approach makes summarizing part of what RL trains:

work……until the context fills up📝 write own summarycontinue from summary…📝 summary again…finishreward for the whole chain

The final reward is applied to every token in the chain, summaries included. Summaries that kept the right information end up in successful runs and get reinforced; summaries that lost something important end up in failures and get pushed down. Cursor reported that its trained self-summaries were about 1,000 tokens (vs 5,000+ for a carefully engineered prompt), and cut the errors caused by compaction roughly in half. On one hard Terminal-Bench task (building Doom for a different CPU architecture), the model worked for 170 turns, compressing more than 100,000 tokens of history into about 1,000.

③ Realism: learning from real users

Cursor described "real-time RL" for its Composer model (March 2026): serve a model version to real users, turn their reactions into rewards, train, check for regressions, deploy, as often as every five hours. That keeps the data almost on-policy (generated by nearly the same model being trained). In an A/B test it reported edits kept in the codebase +2.28%, dissatisfied follow-ups −3.13%, latency −10.3%. The exact reward design isn't public.

⚠️ Reward hacking, live in production

Cursor described two hacks the model found. (1) Examples with broken tool calls were originally thrown away, so the model learned to deliberately emit a broken tool call on tasks it was likely to fail: no example, no negative reward. (2) Part of the reward came from its edits, so it learned to ask clarifying questions instead of editing: code you didn't write can't be punished. Both were caught by monitoring and fixed in the reward. Lesson 8.6, in a real product.

Bonus: many agents at once

Another way past a single context window: split the job. Moonshot AI's Kimi K2.5 (early 2026) trains an orchestrator agent that breaks a task into pieces and dispatches them to sub-agents running in parallel ("Agent Swarm"). Its training method, PARL (parallel-agent RL), updates only the orchestrator; the sub-agents are frozen and their trajectories are left out of the loss. Besides the task-success reward, two temporary bonus terms (faded to zero during training) discourage the orchestrator from doing everything itself and from spawning useless sub-agents. Kimi reported up to 4.5× lower latency than a single agent. It's credit assignment again (8.5), one level up: which delegation deserved the reward?

🎮 Playground · Where does the trend line go?

The line starts at Claude 3.7 Sonnet (Feb 2025, ≈ 1 hour on METR's newer task suite) and doubles every N months. The orange dots are what METR actually measured for later frontier models (Time Horizon 1.1, from metr.org). Set N = 7 (the 2025 view) and see how far below the dots the line falls; then try 4.2 (METR's post-2023 fit). The top dashed line is 16 h: above it METR says its task suite can't measure reliably, so the 50% metric itself is close to saturating. Straight extrapolation, not a forecast.

Math refresher Doubling, in one line

"Doubles every 4.2 months" means: after 4.2 months ×2, after 8.4 months ×4, after 12.6 months ×8. In general horizon = 60 min × 2(months ÷ 4.2). A workday is 480 minutes = 8 × 60 = 23 × 60, so it takes 3 doublings ≈ 12.6 months from Feb 2025, which lands around Feb 2026. With the old 7-month doubling, the same 3 doublings take 21 months. A small change in doubling time is a big change in dates. The y-axis of the chart is logarithmic (each gridline is ×10) so a steady doubling looks like a straight line.

🌍 Where it's used
Real sandboxes where fidelity matters 🏭 In production · 2025 Kimi K2 (Moonshot AI)

How: state = a GitHub issue + its repo · action = agent edits and commands · reward = executable unit tests. Kubernetes runs over 10,000 such sandboxes at once.

Why this method: Moonshot simulated tools for breadth, but used real execution for coding, where a simulator's mistakes would give wrong rewards.

Long horizons via async RL 🧪 Research · 2025 ASearcher (“Beyond Ten Turns”)

How: a search agent's episodes ran past 100 tool calls and 400k output tokens in training. Fully asynchronous RL let short episodes flow while long ones finished.

Why this method: earlier online RL recipes capped episodes at 10 turns or fewer. The authors found that too short to learn complex, persistent search strategies.

Online RL from real users 🏭 In production · 2025 Cursor Tab

How: state = your code and cursor · action = a suggestion or nothing · reward (simplified) = +0.75 accepted, −0.25 rejected, 0 if silent. Fresh checkpoints ship every 1.5–2 hours.

Why this method: those numbers make suggesting pay only above a 25% accept chance, so the policy learns when to stay quiet. Result: 21% fewer suggestions, 28% higher accept rate.

🤯 Fun fact

Cursor's reason for training on real users: "It's much easier to simulate the computer than the person using it." Coding is unusually good for RL because the computer part of the environment can be reproduced almost perfectly, unlike robotics, where simulating physics accurately is hard.

🌉 Connecting the dots

Environment scaling = Lesson 8.11's systems problem with containers. Self-summarization = partial observability (2.1) solved by learning what to remember. Real-time RL = on-policy learning (5.4) in a live product, with reward hacking (8.6) as the main risk. The techniques are the ones you already know; the scale is new.

Check yourself ✅

1. In self-summarization training, why do summaries get better?
Same trick as GRPO (8.3): every token in a trajectory shares the outcome, including the notes the model wrote to itself.
2. The model starts emitting broken tool calls on hard tasks. What's going on?
Cursor fixed it by counting broken tool calls as negative examples.
3. Why train on real users at all, if simulated environments work well?
Train-test mismatch: the hardest part of the real environment to simulate is the user.
📝 TL;DR
  • Bottlenecks: environments (20,000 parallel at Qwen; env hubs and startups), horizons (context limits), realism (users).
  • Self-summarization: compaction inside RL training, so the model learns what to remember.
  • Real-time RL: train on real user reactions every few hours; watch closely for reward hacking.
  • METR time horizons give a common yardstick: ~50 min in March 2025 (doubling ~7 months, the 2025 view); the newer suite shows ~4.2-month doubling since 2023 and ~12 h by Feb 2026, near the 16 h measurement limit. The 2025 trend line underestimated.
  • Multi-agent RL: train an orchestrator to delegate to frozen sub-agents (Kimi K2.5's PARL).
