Phase 8B · Lesson 13

RL for coding agents: the 2025–26 recipe

How do you get thousands of realistic, checkable coding tasks to train on? You build a factory that breaks working code on purpose.

🧰 You'll need (quick reminders)
  • Agentic RL: multi-turn episodes with tools, reward at the end (Lesson 8.10).
  • RLVR (Lesson 8.2) and reward hacking (Lesson 8.6).
🎯 Hook

In early 2025, Meta's SWE-RL trained Llama 3 70B to fix real GitHub issues and reached 41% on SWE-bench Verified (500 real bug-fix tasks checked by hidden tests). The surprising part: during training it never ran a single test. Its reward was simply "how similar is your fix to the fix the real developer wrote?" And it got better at math and general reasoning too, even though it only practised on software history.

💡 Big idea Coding is the ideal RL domain because the world is easy to simulate (a computer in a container) and success is easy to check (tests). The recipe has four steps: ① get many real repositories running in containers, ② manufacture tasks with known answers, ③ run multi-turn RL (Lesson 8.10) with "hidden tests pass" as the reward, ④ at test time, try several times and let a verifier pick the best attempt.
🧠 Analogy: a fire-drill factory

A fire brigade can't wait for real fires to practise. So it builds a training ground, sets controlled fires, and knows exactly what "put out" looks like. Coding-agent labs do the same: take working code, break it in a controlled way, keep the original tests as the judge, and let the agent practise fixing it, thousands of times, in parallel.

① EnvironmentsA Docker container per repository with dependencies installed and the test suite runnable. The unglamorous, expensive part.
② Task factoryCreate bugs or reuse real history, keeping only tasks where tests can tell broken from fixed.
③ Agentic RLThe agent explores, edits and runs commands for many turns; reward at the end (8.10).
④ Test-time selectionSample several attempts; run tests, then let a judge model rank the survivors.

Step ②: where do the tasks come from?

🎮 Playground · The bug factory

Here's a working function and its 4 tests. Click a "mutation" to break the code in one specific way. If at least one test now fails, the broken version becomes a training task ("make the failing tests pass again"). If every test still passes, no test can detect the bug, so the task is useless and gets discarded.

That "discarded" case is a real lesson: a bug no test catches makes no training task at all. And if you trained with weak tests, the agent could "pass" while leaving bugs like that in place: reward hacking (8.6). Task factories therefore lean on repositories with good test suites, or generate extra tests.

Math refresher The reward, precisely

For a bug-fix task, the reward usually checks two lists of tests (names from SWE-bench):

  • Fail-to-pass: tests that fail on the broken code and must pass after the fix ("did you fix the bug?").
  • Pass-to-pass: tests that already passed and must still pass ("did you break anything else?").

reward = 1 if both lists pass, else 0. The tests are hidden from the agent, which can run its own tests but can't read or edit the grading ones (otherwise it would learn to edit them, Lesson 8.6).

Step ③ in practice: DeepSWE

In mid-2025, the open DeepSWE project trained a coding agent from Qwen3-32B using only RL: about 4,500 real GitHub-style tasks (from R2E-Gym), 64 H100 GPUs, six days. It reached 42.2% pass@1 on SWE-bench Verified (59% with test-time scaling), at the time the best open-weight result. The reward: did the repository's hidden tests pass at the end? Everything from Lesson 8.10 (masking tool output, one outcome reward for a long episode) applies unchanged.

Step ④: try several times, pick the best

A strong trick at test time: run the agent, say, 26 times on the same issue, then choose one patch to submit. R2E-Gym found the best way to choose was a hybrid: first run tests to throw out patches that clearly don't work, then let a trained judge model rank the survivors. That took their 32B agent from 34.4% (one attempt) to 51%. DeepSWE's jump from 42% to 59% (above) came from the same kind of test-time selection.

⏳ How fast a benchmark ages: SWE-bench

2023: the original SWE-bench paper's best model, Claude 2, resolved 1.96% of its 2,294 GitHub issues. Aug 2024: SWE-bench Verified, a cleaner 500-task subset checked by humans, became the standard. Feb 2025: Claude 3.7 Sonnet reported 70.3% on Verified (with a scaffold that samples several attempts). Once a benchmark is near the top, and its tasks have been public for years (so they may have leaked into training data), its numbers stop separating models. Attention moved to harder sets such as SWE-bench Pro (Scale AI: 1,865 tasks from 41 actively maintained repositories, designed to resist contamination) and Terminal-Bench. Lesson: always check which benchmark, and when, before trusting a score.

🌍 Where it's used
RL on real repositories 🏭 In production · 2025 OpenAI Codex (codex-1)

How: state = your repository in its own cloud sandbox + the task · action = edits and commands, rerunning tests until they pass · exact reward not public.

Why this method: passing tests isn't all a reviewer wants. OpenAI's stated targets also included human-like PR style and following instructions precisely, which only training on real tasks reaches.

Train with the production tools 🏭 In production · 2025 Cursor Composer

How: state = a codebase in Cursor's own agent harness · action = its real tools (edit, grep, semantic search, terminal) · reward also favors efficient, parallel tool use and no unsupported claims.

Why this method: identical tools mean no gap between training and use. It took hundreds of thousands of concurrent sandboxes, and speed is rewarded because people use it interactively.

A learned verifier to pick the best attempt 🧪 Research · 2024 SWE-Gym

How: 2,438 real Python tasks, each a repo with a runnable environment and unit tests. A verifier trained on agent trajectories ranks several attempts at test time.

Why this method: the hidden tests aren't available when the agent works on a new issue, so a learned judge picks the patch. It reached 32.0% on SWE-bench Verified.

🤯 Fun fact

R2E-Gym's judge models could be fooled by confident language. Agents that ended with "Great! The fix works" or "Successfully implemented" were more likely to be rated correct, even when the patch was wrong. The judge was grading the agent's tone, not its code. That's why they paired it with real test execution.

🌉 What's public and what isn't

Open projects (SWE-smith, R2E-Gym, SWE-RL, DeepSWE, Qwen3-Coder) publish their recipes. The big closed labs (OpenAI's Codex models, Anthropic's Claude) publish benchmark results and safety reports but not their coding-RL recipes, so treat any detailed claim about how they train as a guess. The four-step pattern in this lesson is what the public evidence supports.

Check yourself ✅

1. In the bug factory, a mutation leaves all 4 tests passing. What happens to it?
A task is only useful if the tests can distinguish "fixed" from "broken". Better tests → more usable tasks.
2. Why must the grading tests be hidden and read-only?
Classic reward hacking (8.6): change the judge instead of doing the work.
3. What is "pass-to-pass" checking for?
Fail-to-pass = the bug is fixed; pass-to-pass = nothing else broke.
📝 TL;DR
  • Recipe: containers per repo → task factory → multi-turn RL with hidden tests → test-time selection.
  • Task factories: break working code (SWE-smith), reverse real commits (R2E-Gym), learn from project history (SWE-RL), auto-generate tests (Qwen3-Coder).
  • Reward = fail-to-pass and pass-to-pass tests, hidden from the agent.
  • Picking the best of many attempts with tests + a judge adds a lot (34% → 51% in R2E-Gym).
