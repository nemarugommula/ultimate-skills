Phase 5 · Lesson 2

Kubernetes core: pods, deployments, services

You tell Kubernetes what you want running (“5 copies of this image, reachable at this name”), and it keeps making it true: placing containers on machines, replacing the ones that die, and rolling out new versions without downtime.

🧰 You'll need (quick reminders)
  • Images and containers: an image is the packaged app, a container is one running copy of it (Lesson 5.1).
  • Load balancers and health checks: spread requests over healthy servers only (Lesson 1.2).
  • etcd: a small, strongly consistent key-value store kept in sync with the Raft consensus algorithm (Lesson 3.4).
🎯 Hook

Google's 2015 paper on Borg, its internal cluster manager, describes a system that runs “hundreds of thousands of jobs, from many thousands of different applications, across a number of clusters each with up to tens of thousands of machines”. Nobody places those by hand.

Engineers who knew Borg started an open-source cousin: the first commit of Kubernetes went to GitHub on June 6, 2014. Version 1.0 shipped on July 21, 2015, and Google donated it to the new Cloud Native Computing Foundation (CNCF). Ten years later the project counted over 88,000 contributors from more than 8,000 companies.

Numbers first: why you need an orchestrator

A mid-size company runs 30 services × 10 copies = 300 containers on 40 machines. Suppose each machine fails on average once every three years (an illustrative number). With 40 machines that's a failure every month or so. With 1,000 machines it's about one a day (1,000 ÷ 1,095 days).

Each failure means someone has to notice, pick a machine with spare CPU and memory, start the containers again, and tell the load balancer the new addresses. Plus about 30 deploys a day, each replacing 10 containers without dropping requests. Doing that by hand at 3 a.m. doesn't scale. An orchestrator does it for you, continuously.

💡 Big idea: desired state + reconciliation You don't tell Kubernetes what to do (“start a container on machine 7”). You tell it what should be true (“5 copies of api:v2 should be running”). Small programs called controllers loop forever: observe what's actually running, compare it with what you asked for, act to close the gap. A crash, a dead machine, or a deleted pod is just another gap to close.
🧠 Analogy: the thermostat

You don't switch the heater on and off yourself. You set the thermostat to 21 °C. It measures the room, compares, and switches the heater as needed, forever. Open a window (a machine dies) and it simply works harder. Kubernetes is a building full of thermostats: one for replica counts, one for node health, one for load-balancer endpoints, and so on.

The parts of a cluster

A cluster is a set of machines called nodes, plus a control plane that makes the decisions. Press the button to follow what happens when you run kubectl apply:

Each step is a separate component reacting to a change it watches for.

The objects you'll actually write

ObjectWhat it isYou use it for
PodThe smallest unit: one or a few containers that share a network address and are always placed together.Almost never directly. Pods are disposable; something else creates them.
ReplicaSet“Keep N pods matching this template running.”Created for you by a Deployment.
DeploymentManages ReplicaSets so you can change the image and roll out gradually, or roll back.Every stateless service. This is your daily driver.
ServiceA stable name and virtual IP in front of a changing set of pods, chosen by labels.How other services and load balancers find your pods.

Labels are key-value tags on objects (app: api, tier: web). A selector is a query over labels. A Deployment owns the pods whose labels match its selector; a Service sends traffic to the pods whose labels match its selector. Nothing is wired by name or IP: labels are the glue.

Services come in three main types:

  • ClusterIP (the default): a virtual IP reachable only inside the cluster. Service-to-service traffic.
  • NodePort: also opens the same port (by default from the range 30000–32767) on every node.
  • LoadBalancer: also asks your cloud for an external load balancer pointing at the nodes. The simplest way to expose one service to the internet (Lesson 5.3 shows the better way for many services).
✏️ Worked example: will my pods fit?

3 nodes, each with 3.5 vCPU and 15 GiB left for pods after the system's own needs (typical numbers). Each pod requests 500m CPU (“m” = millicores, so 500m = half a CPU) and 1 GiB of memory. The scheduler only places a pod where its requests fit.

  • Per node: CPU fits 3,500 ÷ 500 = 7 pods; memory fits 15 ÷ 1 = 15. CPU is the limit: 7 per node, 21 in the cluster.
  • You ask for 20 replicas: all run, with 1 slot spare.
  • One node dies: capacity drops to 2 × 7 = 14. The ReplicaSet recreates the lost pods, but 6 of them have nowhere to go and stay Pending until you add a node.

Lesson: plan for losing a node. 20 replicas on 3 nodes needs a 4th node's worth of headroom (or a cluster autoscaler, Lesson 5.3).

Rolling updates: new version, no downtime

Change the image in a Deployment and it creates a new ReplicaSet, then shifts pods over step by step. Two knobs control the pace:

  • maxSurge: how many extra pods may exist above the desired count during the rollout (more speed, more temporary cost). Percentages round up.
  • maxUnavailable: how many pods may be missing below the desired count (more speed, less capacity). Percentages round down.

Both default to 25%. With 10 replicas: surge = ⌈2.5⌉ = 3, unavailable = ⌊2.5⌋ = 2. So during the rollout there are always between 8 and 13 pods. They can't both be 0, or the rollout could never move. A new pod only counts once its readiness check passes (Lesson 5.3), which is what keeps a broken version from taking all your traffic.

The safe production setting for a service that must never lose capacity is maxUnavailable: 0 with a small surge: a broken version just stalls, while every old pod keeps serving. Then you run kubectl rollout undo. Kubernetes won't roll back by itself: after progressDeadlineSeconds (600 s by default) it only marks the rollout as stuck. Automatic rollback is the job of your CD tooling (Lesson 6.2).

🔥 Real outage · Monzo, October 2017

UK bank Monzo ran several hundred microservices in Docker containers on Kubernetes. Their postmortem describes a chain: an etcd cluster change days earlier triggered a bug that made service-discovery updates time out. A routine deploy then left the service mesh (linkerd) routing to pod IPs that no longer existed, and payments started failing. Restarting every linkerd instance exposed a second bug: a version incompatibility made linkerd fail to parse a Service with no endpoints (one a team had scaled to 0 the day before). It became a full platform outage until engineers deleted that empty Service.

Lesson: the control plane's data (etcd, endpoints) is on the critical path of every request routed by service discovery, and “restart everything” is a risky fix when you don't yet know the cause.

🧰 Tools you'll actually use

kubectl (the CLI), managed clusters (Amazon EKS, Google GKE including Autopilot, Azure AKS), local clusters (kind, minikube, k3d), and terminal UIs like k9s. A Deployment and its Service:

# deployment.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: api
spec:
  replicas: 5                        # desired state
  selector:
    matchLabels: { app: api }        # "my pods are the ones labelled app=api"
  strategy:
    type: RollingUpdate
    rollingUpdate: { maxSurge: 1, maxUnavailable: 0 }
  template:                          # the pod to stamp out
    metadata:
      labels: { app: api }
    spec:
      containers:
        - name: api
          image: registry.example.com/api:3f9c2e1   # an immutable tag (Lesson 5.1)
          ports: [{ containerPort: 3000 }]
          resources:
            requests: { cpu: "500m", memory: "512Mi" }   # what the scheduler reserves
---
# service.yaml
apiVersion: v1
kind: Service
metadata:
  name: api                          # other pods call http://api (DNS)
spec:
  type: ClusterIP
  selector: { app: api }             # send traffic to pods with this label
  ports: [{ port: 80, targetPort: 3000 }]
kubectl apply -f deployment.yaml -f service.yaml   # declare the desired state
kubectl get pods -l app=api -o wide                # which pods, on which nodes
kubectl describe pod api-7d9c-xk2p                 # events: scheduling, pulls, probe failures
kubectl logs -f deploy/api                         # follow logs
kubectl set image deploy/api api=registry.example.com/api:a81b7c0
kubectl rollout status deploy/api                  # watch the rolling update
kubectl rollout undo deploy/api                    # back to the previous ReplicaSet
kubectl get events --sort-by=.lastTimestamp        # what the controllers have been doing

Try it locally: kind create cluster (Kubernetes inside Docker), then kubectl create deployment web --image=nginx --replicas=3, delete a pod with kubectl delete pod …, and watch a new one appear with kubectl get pods -w.

⚖️ Trade-offs
✅ Kubernetes pays off when…❌ Think twice when…
Many services and teams share infrastructureYou have one or two services: a PaaS or Cloud Run does the same with no cluster to run
You need portability across clouds or on-premNobody on the team can own the cluster: upgrades every few months, networking, security, add-ons
You want one standard way to deploy, scale and observe everythingYour workload is mostly a managed database plus a few functions
The ecosystem matters (Helm, Argo CD, operators, autoscalers)You'd be adopting it because big companies do: their scale isn't yours yet
🚀 Startup vs big tech

Founding engineer (0 → 1)

Don't run Kubernetes yourself on day one. Ship containers to Cloud Run, ECS Fargate, Render or Fly.io (Lesson 5.5). If you do pick Kubernetes, use a fully managed flavour (GKE Autopilot, EKS with managed nodes) and keep it boring: Deployments, Services, one ingress.

Big tech (1 → 100)

A platform team runs many clusters (per region, per environment), upgrades them on a schedule, and gives product teams a paved road: templates, GitOps (Lesson 5.4), policies, quotas. Some run Kubernetes at extreme scale; others keep internal systems that predate it, like Google's Borg.

🎤 Interview angle

“Deploy it on Kubernetes” is not a design. A senior answer says:

  • The shape: Deployment + Service per stateless service, how many replicas, spread across nodes and zones (Lesson 5.5).
  • Capacity: requests per pod × replicas vs. node size, and headroom for losing a node.
  • Rollouts: maxSurge/maxUnavailable, readiness checks, and how you roll back.
  • What the control plane is (API server, etcd, scheduler, controllers) and that running pods keep serving if it's briefly down, but nothing new gets scheduled.

Common follow-ups: “What happens when a node dies?” (pods are evicted after a timeout, recreated elsewhere if there's room). “Why is my pod Pending?” (no node has room for its requests, or constraints don't match). “Pod vs container?”

🏭 In the real world
Borg, the ancestor 🏢 Google · 2015 Large-scale cluster management at Google with Borg (EuroSys)

How: a cluster manager running hundreds of thousands of jobs across clusters of up to tens of thousands of machines, with admission control, efficient task-packing and over-commitment.

Why this method: packing many workloads per machine gives high utilization; Kubernetes' pods, labels and controllers grew from these lessons.

From one commit to a CNCF giant 📜 History · 2014–2024 10 Years of Kubernetes (Kubernetes blog)

How: first commit June 6, 2014; 1.0 on July 21, 2015, donated to the CNCF; over 88,000 contributors from 8,000+ companies a decade later.

Why this method: a vendor-neutral foundation let competing clouds all offer the same API, which is why every cloud now has a managed Kubernetes.

One very big cluster 🏢 OpenAI · 2021 Scaling Kubernetes to 7,500 nodes

How: OpenAI describes running Kubernetes clusters of 7,500 nodes for training large models like GPT-3, CLIP and DALL·E, and the API-server, networking and monitoring changes that size required.

Why this method: one scheduler and one API for research jobs of every size; the post notes clusters this big are rarely run and need special tuning.

Hundreds of microservices on Kubernetes 🏢 Monzo · 2017 Monzo outage postmortem (27/10/2017)

How: several hundred services in Docker containers on Kubernetes on AWS, with etcd spread over three zones and linkerd routing calls using Kubernetes' service discovery.

Why this method: small, frequent deploys of many services, with automated reaction to node and app failures. The outage shows the cost: the control plane becomes critical infrastructure.

Check yourself

1. Nodes have 3,500m CPU free each. Pods request 700m. You want 24 replicas. What's the fewest nodes that still runs all 24 if any one node dies?
3,500 ÷ 700 = 5 pods per node. 24 pods need ⌈24 ÷ 5⌉ = 5 nodes, with no room to spare. To survive losing one node you need 5 nodes after the loss, so 6. Always size for N + 1.
2. A payment service must never drop below full capacity during deploys, even if the new version is broken. Which rolling-update setting fits?
With maxUnavailable 0, an old pod is removed only after a new one is ready. If v2 never becomes ready, the rollout stalls and all old pods keep serving. You pay for one or a few extra pods during the rollout.
3. You delete a pod by hand and a new one appears seconds later. Why?
That's reconciliation: the controller compares actual (4 pods) with desired (5) and closes the gap. To really remove pods, change the desired state: scale the Deployment down or delete the Deployment.
📝 TL;DR
  • Declare the desired state; controllers observe → compare → act, forever. Failures are just gaps to close.
  • Control plane: API server, etcd, scheduler, controller manager. Each node: kubelet + networking.
  • Deployment → ReplicaSet → Pods; a Service finds pods by labels. ClusterIP inside, LoadBalancer outside.
  • The scheduler places pods by their requests; size the cluster for N + 1 nodes.
  • Rolling updates: maxSurge rounds up, maxUnavailable rounds down, both default 25%; maxUnavailable 0 makes a broken release stall instead of hurting users.
