Phase 5 · Lesson 1

Docker: images, layers & containers

Package your app with everything it needs into one image that runs the same on your laptop, in CI and on a thousand servers. Every modern deployment, from a two-person startup to Google, starts here.

🧰 You'll need (quick reminders)
  • Stateless app servers: any copy can serve any request, so you scale by running more copies (Lesson 1.1).
  • Back-of-the-envelope math: rough sizes and times, multiplied out (Lesson 0.3).
  • A process is just a running program. Your laptop runs hundreds of them at once.
🎯 Hook

In March 2013, Solomon Hykes gave a 5-minute lightning talk at PyCon called “The future of Linux Containers”. He showed a tool called Docker. According to the Kubernetes project's own history, that talk inspired a small team at Google to start the project that became Kubernetes.

Google wasn't new to the idea. Its own site says it has used containers since the early 2000s: “from Gmail to YouTube and Search, everything at Google operates in containers.” Docker made the same trick easy for everyone else. By the end of this lesson you'll be able to write a small, fast, safe image, and explain what a container really is.

Numbers first: why “works on my machine” stops working

Your app runs on your laptop with Node 22, a certain version of OpenSSL, and a few libraries you installed months ago. The server has Node 20 and different libraries. It crashes. Multiply that by 50 engineers and 200 servers and you get the oldest bug in software: “works on my machine”.

A container image fixes this by shipping the app together with its whole user-space: the runtime, the libraries, the config. Here's what the official base images weigh (compressed download size on Docker Hub, amd64, October 2026):

Base imageCompressed sizeWhat's inside

Size matters at scale. When traffic spikes and 50 new servers each download a 560 MB image, that's 28 GB pulled at the exact moment you need speed. A 100 MB image is about 5 GB. We'll work this out below.

💡 Big idea An image is a read-only, layered snapshot of a filesystem plus a start command. A container is an ordinary Linux process started from that image, which the kernel fences off so it sees only its own files, network and process list (namespaces) and can only use its share of CPU and memory (cgroups). No virtual hardware, no second operating system: that's why containers start in about a second instead of a minute.
🧠 Analogy: the shipping container

Before the 1950s, ships were loaded crate by crate, each one a different shape. The steel shipping container made every load look the same to cranes, trucks and ships. A Docker image does that for software: whatever is inside (Node, Python, Go, a database), every server, CI runner and orchestrator handles it the same way: pull, run, stop.

And the image is built like a stack of transparent sheets: the base OS on the bottom, then your libraries, then your code on top. Change the top sheet and the ones below are reused.

Containers vs virtual machines

A virtual machine (VM) pretends to be a whole computer: virtual CPU, virtual disk, its own operating-system kernel. A container shares the host's kernel and is isolated by two Linux kernel features:

  • Namespaces give a process its own view of the system. The Linux manual lists eight kinds: PID (process IDs: your app thinks it's process 1), network (its own IP and ports), mount (its own filesystem), UTS (its own hostname), IPC, user, cgroup and time.
  • cgroups (control groups) put processes in groups whose CPU, memory and I/O can be limited and monitored. This is how “this container gets 0.5 CPU and 512 MB” is enforced (you'll set these in Kubernetes in Lesson 5.3).

In practice you use both: the cloud gives you VMs, and you run many containers on each VM. When strong isolation matters (running strangers' code), people add a sandbox layer such as gVisor or Firecracker micro-VMs.

Images are made of layers, and layers are cached

You build an image from a Dockerfile: a list of instructions run top to bottom. Each instruction that changes files (RUN, COPY, ADD) creates a layer, a diff on top of the layer before. When you rebuild, Docker checks each step: has the instruction or its input files changed? If not, it reuses the cached layer instantly.

The one rule that matters, straight from Docker's docs: once a layer changes, every layer after it must be rebuilt, even if those steps would produce exactly the same result. So the order of your Dockerfile decides how fast every build is.

✏️ Worked example: same Dockerfile, two orders

A Node app. Typical step times: installing dependencies (npm ci) takes about 45 s, compiling (npm run build) about 15 s, copying the source about 1 s. You change one line of code.

  • Bad order: COPY . . then RUN npm ci then build. Your code changed, so COPY . . misses, and everything after it reruns: 1 + 45 + 15 = 61 s.
  • Good order: copy only package.json + lock file, run npm ci, then COPY . . and build. The dependency files didn't change, so npm ci is cached: 1 + 15 = 16 s.
  • A team of 10 engineers doing 200 builds a day saves 45 s × 200 = 9,000 s = 2.5 hours of build time per day, from moving one line.

Dockerfile habits that pay off at scale

HabitWhy
Copy dependency files first, install, then copy the codeCode changes daily, dependencies weekly: keep the slow step cached.
Multi-stage builds: build in one FROM, copy only the result into a small final FROMCompilers, dev dependencies and caches stay behind. Docker's docs: you “selectively copy artifacts from one stage to another, leaving behind everything you don't want”.
Small base images (-slim, -alpine, distroless, or scratch for a static Go binary)Faster pulls, fewer packages that can carry security holes. Docker notes Alpine is under 6 MB.
Run as a non-root user (USER node)If someone breaks into your app, they don't get root inside the container.
A .dockerignore fileKeeps .git, node_modules and secrets out of the build context and the image.
Pin versions (node:22.11-alpine, or a @sha256: digest)Tags move. Pinning makes builds repeatable; a bot (e.g. Dependabot) bumps them on purpose.
RUN apt-get update && apt-get install … in one lineSeparate lines cache a stale package list (Docker's docs call this out).
Exec-form CMD ["node", "server.js"]Your app becomes process 1 and receives the stop signal, so it can shut down gracefully.

🧰 Tools you'll actually use

Docker / Docker Desktop, BuildKit (Docker's modern builder), Podman (daemonless, Docker-compatible), registries like Amazon ECR, Google Artifact Registry, GitHub Container Registry, and scanners like Trivy or Docker Scout. A production-style multi-stage Dockerfile for Node:

# syntax=docker/dockerfile:1
# ---- stage 1: build (has dev dependencies and the compiler) ----
FROM node:22-alpine AS build
WORKDIR /app
COPY package.json package-lock.json ./      # dependency files first: cached until they change
RUN npm ci
COPY . .                                     # code last: changes every commit
RUN npm run build && npm prune --omit=dev     # drop dev dependencies after building

# ---- stage 2: run (only what production needs) ----
FROM node:22-alpine
WORKDIR /app
ENV NODE_ENV=production
COPY --from=build /app/node_modules ./node_modules
COPY --from=build /app/dist ./dist
USER node                                    # non-root user that ships with the image
EXPOSE 3000
CMD ["node", "dist/server.js"]               # exec form: node is PID 1 and gets SIGTERM

A .dockerignore next to it (.git, node_modules, *.md, .env), and a compose.yaml to run the app with its database locally:

services:
  api:
    build: .
    ports: ["8080:3000"]                # host:container
    environment:
      DATABASE_URL: postgres://app:secret@db:5432/app   # "db" = the service name below
    depends_on: [db]
  db:
    image: postgres:17
    environment:
      POSTGRES_USER: app
      POSTGRES_PASSWORD: secret
    volumes: ["pgdata:/var/lib/postgresql/data"]   # data survives container restarts
volumes:
  pgdata: {}
docker build -t api:3f9c2e1 .          # build and tag with the git commit
docker run -d -p 8080:3000 --name api api:3f9c2e1
docker ps                              # what's running
docker logs -f api                     # follow its stdout/stderr
docker exec -it api sh                 # a shell inside the running container
docker image history api:3f9c2e1       # every layer and its size
docker compose up -d                   # start everything in compose.yaml

Try it locally: docker run --rm -it alpine:3.21 sh, then run ps inside. You'll see your shell as PID 1: that's a PID namespace at work.

⚖️ Trade-offs
✅ Containers shine when…❌ Think twice when…
Many services, languages or versions share the same serversYou run untrusted code from strangers: a shared kernel is weaker isolation than a VM
You want the exact same artifact in dev, CI, staging and prodOne small app on a platform that already builds for you (Heroku-style buildpacks, Vercel)
You need fast start and dense packing (scale out in seconds)Heavy stateful systems (big databases) where a managed service is simpler (Lesson 5.5)
You'll use an orchestrator later (Kubernetes, ECS, Cloud Run all run images)Your team can't yet maintain images: base images need regular rebuilds for security patches

Alpine uses a different C library (musl) from Debian (glibc). Most apps don't notice; some native libraries and Python wheels do. If Alpine causes trouble, -slim is the safe middle ground.

🚀 Startup vs big tech

Founding engineer (0 → 1)

One multi-stage Dockerfile per service, a compose.yaml for local dev, images built in CI and pushed to your cloud's registry, tagged by commit. Run them on a managed platform (Cloud Run, ECS Fargate, Fly.io, Render: Lesson 5.5) long before you think about Kubernetes.

Big tech (1 → 100)

Golden base images owned by a platform team and rebuilt on every security patch, image scanning and signing in CI, internal registry mirrors near every cluster, strict size budgets, and policies that refuse images running as root or without a pinned digest (Lesson 6.1 covers the pipeline).

🎤 Interview angle

Few interviews ask you to write a Dockerfile, but “how would you deploy this?” comes up constantly. A senior answer covers:

  • The artifact: one immutable image per commit, promoted unchanged from staging to production.
  • Image hygiene: multi-stage, small base, non-root, no secrets baked in (pass them at runtime: Lesson 5.3).
  • Where state lives: containers are disposable, so data goes in volumes or managed databases.
  • Containers vs VMs: what isolation you actually get from namespaces and cgroups.

Common follow-ups: “Why is our build slow?” (layer order). “Why is our image 2 GB?” (single stage, full base, caches). “What happens to files written inside the container?” (gone when it's removed).

🏭 In the real world
Everything in containers 🏢 Google · 2000s–today Google Cloud: Containers at Google

How: Google says it has run on containers since the early 2000s, with Gmail, YouTube and Search all running in them, managed by its internal cluster system Borg (Lesson 5.2).

Why this method: packing many isolated workloads onto shared machines uses hardware far better than one app per server.

Namespaces and cgroups 📜 Linux kernel namespaces(7) · cgroups(7)

How: the manual pages list the namespace types (PID, network, mount, UTS, IPC, user, cgroup, time) and describe cgroups as grouping processes so their resource use can be limited and monitored.

Why this method: Docker didn't invent isolation; it packaged existing kernel features behind a simple build-ship-run workflow.

The build cache rule 🧰 Open source Docker docs: Docker build cache

How: each instruction becomes a layer; when one layer changes, all the layers after it rerun. The docs show exactly the “copy dependency files first” trick from the simulator.

Why this method: layers are diffs on top of their parent, so a changed parent makes every later diff invalid.

Distroless images 🧰 Google open source GoogleContainerTools/distroless

How: base images that contain only your app's runtime dependencies: no package manager, no shell, none of the usual Linux programs.

Why this method: nothing to exploit that isn't needed, and nothing extra to patch or download.

🤯 Fun fact · smaller than a photo

The alpine:3.21 image is about 3.6 MB compressed on Docker Hub: a complete Linux user-space smaller than a typical phone photo. And the smallest possible base, FROM scratch, is empty: a statically compiled Go binary can be the only file in the image.

🌉 How it connects

Images are the unit everything else in this phase moves around: Kubernetes schedules them (Lesson 5.2) and limits their CPU and memory with the same cgroups (Lesson 5.3), Helm and GitOps decide which image tag runs where (Lesson 5.4), and Cloud Run or Lambda can run them without servers (Lesson 5.5). CI/CD builds and scans them (Lesson 6.1). In AI systems, model-serving images often weigh several GB because of GPU libraries, which makes layer order and pull time even more important.

Check yourself

1. Your image is 600 MB. A traffic spike makes the autoscaler add 40 servers, each downloading at about 100 MB/s. Roughly how much data is pulled, and how long does each server wait for the image?
40 × 600 MB = 24,000 MB = 24 GB, and 600 MB ÷ 100 MB/s = 6 s per server before the app can even start. A 100 MB multi-stage image would be 4 GB and 1 s. Image size is part of your scale-out speed.
2. Every build reinstalls all dependencies (60 s) even when only one line of code changed. What's the fix?
A changed layer invalidates every layer after it. If COPY . . comes before the install, any code change reruns it. Copy package.json and the lock file first so the install stays cached until dependencies actually change.
3. You must run code uploaded by anonymous users (an online code playground). Which is the safest way to isolate each run?
Containers share the host's kernel, so a kernel bug can let hostile code escape. For untrusted code you add a stronger boundary: a lightweight VM (e.g. Firecracker) or a sandboxed kernel (gVisor). For your own trusted services, plain containers are fine.
📝 TL;DR
  • Image = layered, read-only filesystem + start command. Container = a normal process, isolated by namespaces and limited by cgroups.
  • A changed layer rebuilds everything after it: copy dependency files, install, then copy code.
  • Multi-stage + small base + non-root + .dockerignore = small, fast, safer images.
  • Image size × servers pulling = scale-out cost: 560 MB × 50 = 28 GB vs 104 MB × 50 = 5 GB.
  • Containers are disposable: state goes in volumes or managed databases.
