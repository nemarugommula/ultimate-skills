Phase 5 · Recap

Recap: containers, Kubernetes & the cloud

You can now package an app into a small image, run it on Kubernetes with autoscaling and health checks, describe the whole platform in git, and choose cloud building blocks that survive a zone failure. Here's the phase on one page, a diagnosis game, and a design to try yourself.

🧾 Cheat sheet

🐳

5.1 Docker

changed layer ⇒ every later layer rebuilds

Image = layered filesystem + start command; container = a process isolated by namespaces, limited by cgroups. Copy dependency files, install, then copy code. Multi-stage, small base, non-root. Size × servers pulling = scale-out cost.

Docker, BuildKit, Compose, ECR / Artifact Registry, Trivy

☸️

5.2 Kubernetes core

observe → compare → act, forever

API server, etcd, scheduler, controllers; kubelet per node. Deployment → ReplicaSet → Pods; Services find pods by labels. Scheduler packs by requests: size for N + 1 nodes. Rolling update: maxSurge rounds up, maxUnavailable rounds down (25% each).

kubectl, kind, EKS / GKE / AKS, k9s

📈

5.3 K8s in production

desired = ⌈current × metric ÷ target⌉

Requests reserve, limits cap (CPU throttled, memory OOMKilled). HPA every 15 s, 10% tolerance, 300 s scale-down window. Readiness gates traffic, liveness restarts, startup protects slow boots. Gateway API in, PDBs for maintenance.

metrics-server, HPA, Cluster Autoscaler / Karpenter, KEDA, Gateway API

📜

5.4 IaC & GitOps

read every −/+ before you apply

Terraform: write → plan → apply; remote, locked state; modules. Replacement can mean downtime (create_before_destroy) or data loss (prevent_destroy, deletion protection). Helm = values, Kustomize = overlays. GitOps agents pull from git and self-heal drift.

Terraform / OpenTofu, Helm, Kustomize, Argo CD, Flux

☁️

5.5 Cloud & serverless

≈ $1 per million 100 ms / 512 MB Lambda calls

AZ = failure domain (≥ 3 per AWS region, within 100 km). Spread over AZs, size N+1, Multi-AZ database (failover typically 60–120 s). Most managed block that fits. Serverless wins at low or bursty traffic; servers at high steady load.

VPC, IAM, Cloud Run / Fargate / Lambda, RDS / DynamoDB / S3, SQS

🗣️ Teach it back

“Walk me through what happens, step by step, from the moment you merge a pull request that changes your API, to the moment users are served by the new version, on Kubernetes with GitOps. Then tell me what happens if the new version is broken, and what happens if an availability zone dies halfway through.”

A strong answer mentions: CI builds and tags an image by commit (5.1), a PR bumps the tag in the deploy repo, Argo CD notices and syncs (5.4), the Deployment rolls out with maxSurge/maxUnavailable (5.2), readiness gates traffic so a broken version stalls instead of serving errors (5.3), rollback is a git revert, and a zone loss is absorbed by N+1 sizing across AZs while the database fails over (5.5).

🏗️ Design it yourself

✏️ The problem

You're the founding engineer of a photo-sharing app. Launch target: 1 million daily active users, each making about 50 API calls a day; 10% of users upload one 2 MB photo a day. Traffic peaks at about 3× the average in the evening. The team is 4 engineers. Investors want “it doesn't go down when AWS has a bad day”, and the CFO wants to know the bill. Design the deployment: packaging, where it runs, how it scales, how it's described, and how it survives a zone failure. Use only this phase's ideas.

Reveal a strong answer

1. Requirements. Stateless JSON API + photo uploads and downloads. Availability: survive one AZ failing with no manual action; a full-region outage is accepted for now (written down as a known risk). Deploys several times a day with no downtime. Small team: minimize what you operate.

2. Numbers.

  • API: 1M × 50 = 50M calls/day ÷ 86,400 ≈ 580 req/s average, ≈ 1,750 req/s at the 3× peak.
  • Uploads: 100,000 photos × 2 MB = 200 GB/day ≈ 6 TB/month of new storage, only about 1–3 uploads per second.
  • Compute: if a call needs ~20 ms of CPU and servers run at a 60% target, one vCPU handles ~30 req/s, so the peak needs ~60 vCPUs, ~90 with N+1 headroom across 3 AZs.
  • Sanity check on functions: at 580 req/s average, 100 ms and 512 MB each, Lambda would be about 1.5 billion calls ≈ $1,570/month in compute and requests (Lesson 5.5 rates): not crazy, but this is steady, high traffic where containers usually win.

3. Architecture.

  • Packaging: one multi-stage, non-root image per service, tagged by commit, pushed to the cloud registry (5.1).
  • Compute: the API on ECS Fargate or Cloud Run, spread over 3 AZs, autoscaling on CPU at a ~60% target with min 6 tasks (2 per AZ). No Kubernetes cluster to run yet (5.2 trade-offs).
  • Photos: clients upload directly to S3 with pre-signed URLs (Lesson 2.7); a queue event triggers a function to make thumbnails: bursty, short, perfect for serverless (5.5). A CDN serves images (Lesson 1.4).
  • Data: managed Postgres (RDS/Aurora) with Multi-AZ and automated backups; deletion protection on.
  • Health and rollout: load-balancer health checks equivalent to readiness; rolling deploys that never drop below full capacity (maxUnavailable 0 style), automatic rollback on failed health checks.
  • As code: everything in Terraform (VPC with private subnets, security groups, IAM roles per service with least privilege, database, buckets, services), remote state with locking, plan on every PR (5.4).

4. Trade-offs. Fargate/Cloud Run cost more per vCPU than raw VMs, but save the team from running servers or a cluster; revisit when the bill or the number of services makes Kubernetes worth a platform engineer. Multi-AZ doubles the database cost and adds cross-AZ traffic charges, in exchange for surviving the most common large failure. Multi-region is deliberately postponed.

5. Classic mistakes. Putting photos through the API servers (they should go straight to S3). One AZ “for now”. Liveness-style health checks that call the database, so a DB blip restarts every task. Sizing exactly for peak with no N+1 headroom. Clicking resources together in the console, so staging and prod drift apart. A Lambda for the main API “because serverless is cheap” without doing the cost math.

🏆 Boss quiz

1. Your 1.2 GB image takes 12 s to pull on each new node, and autoscaling events add 30 nodes at once. A multi-stage build gets it to 150 MB. What changes?
Pull time scales with size: 150 ÷ 1,200 × 12 s = 1.5 s. Total: 30 × 1.2 GB = 36 GB vs 30 × 0.15 GB = 4.5 GB. New nodes have no local copy, so every scale-out pays it (Lesson 5.1).
2. After a deploy, the new pods show CrashLoopBackOff. Logs show the app is still loading a 2-minute cache when it's killed. Old pods are still serving. What's the right fix?
The liveness probe is killing pods that are just slow to start. A startup probe holds liveness off until the app is up. Readiness is what's protecting users right now, since the rollout stalled instead of sending traffic to broken pods (Lessons 5.2 and 5.3).
3. An HPA targets 70% CPU. 10 pods average 98%. Pods take 3 minutes to start because the cluster also needs new nodes. What will users see?
The decision is fast; the capacity is slow. That gap is why you keep headroom (a lower target), spare node capacity, or queues in front of the work (Lessons 5.3 and 3.1).
4. A Terraform PR titled “tidy up names” shows -/+ aws_db_instance.main. What should the reviewer do?
−/+ is replacement. For stateful resources that's data loss or a restore from backup. Protect them with prevent_destroy and deletion_protection, and read the # forces replacement line to see which attribute caused it (Lesson 5.4).
5. A service runs 2 servers in each of 3 AZs and needs 5 servers' worth of capacity at peak. Its only database is in AZ A. AZ A fails at peak. What's the biggest problem?
All three are true, but the single-AZ database turns a capacity dip into a full outage. A Multi-AZ database fails over in about 60–120 s; N+1 sizing (3 per AZ here) handles the rest (Lesson 5.5).
