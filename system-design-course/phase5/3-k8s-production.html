Phase 5 · Lesson 3

Kubernetes in production: autoscaling, config, ingress

The settings that separate a demo cluster from one that survives real traffic: how much CPU and memory each pod gets, how it scales itself, how Kubernetes knows a pod is healthy, and how traffic gets in. Most Kubernetes outages are one of these set wrong.

🧰 You'll need (quick reminders)
  • Pods, Deployments, Services and the scheduler placing pods by their CPU/memory requests (Lesson 5.2).
  • cgroups: the Linux feature that limits a container's CPU and memory (Lesson 5.1).
  • Health checks: a load balancer only sends traffic to servers that answer “I'm OK” (Lesson 1.2).
🎯 Hook

Airbnb moved almost all of its online services from hand-managed EC2 servers to Kubernetes, and by 2022 ran thousands of nodes across nearly a hundred clusters. Their engineers wrote that traffic “fluctuates heavily every day”, and that the cloud bill should follow it, up and down, automatically.

That's the job of this lesson's machinery: pods that scale with load, clusters that add and remove machines, and health checks that keep traffic away from pods that can't serve it. Set them well and you pay for what you use. Set them badly and the same features take your site down.

Numbers first: requests, limits and the money in between

Each container declares two numbers per resource:

  • A request: what the scheduler reserves on a node. cpu: 500m means half a CPU core (“m” = millicores, 1000m = 1 core).
  • A limit: the most it may use. Over the CPU limit, the kernel throttles it (it just runs slower). Over the memory limit, the kernel kills it: the pod shows OOMKilled (OOM = out of memory) with exit code 137, and restarts.

Now the money. 50 pods each request 1 CPU “to be safe” but actually use about 0.2. The cluster reserves 50 CPUs and uses 10: 80% of what you pay for sits idle, about 10 four-core machines' worth. Set requests too low instead and the scheduler crams too many pods onto a node; under load they fight for CPU and everything slows down.

Request too highRequest ≈ real use (p90-ish)Request too low / no limit
CostIdle reserved capacityPaid ≈ usedCheap… until it isn't
Under loadFineFine; autoscaler adds podsNoisy neighbours, throttling, OOM kills

A common pattern: set memory request = memory limit (memory can't be throttled, so surprises mean kills), set a CPU request from measured usage, and be careful with tight CPU limits, which throttle bursty apps even when the node has spare CPU.

💡 Big idea Kubernetes automates decisions from the numbers you give it. Requests drive scheduling and autoscaling, probes decide which pods get traffic and which get restarted. The automation is only as good as those numbers: a wrong request wastes money, a wrong probe can restart every pod at the worst moment.
🧠 Analogy: the restaurant

Requests are table reservations: the host (scheduler) won't seat more parties than tables. Limits are the kitchen's rule that one table can't order more than it can eat. The autoscaler is the manager calling in more waiters as the queue grows. Probes are the manager checking on staff: a readiness check asks “can you take customers right now?” (if not, stop seating people in your section), a liveness check asks “are you completely stuck?” (if so, send you home and call in someone fresh). Mix those two up and you send home a waiter who was just busy.

The Horizontal Pod Autoscaler

The HPA (Horizontal Pod Autoscaler) changes a Deployment's replica count based on a metric, usually average CPU as a percentage of the request. Every 15 seconds by default it computes:

desiredReplicas = ⌈ currentReplicas × currentMetric ÷ targetMetric ⌉ “The new replica count is the current count, times how far the metric is from its target, rounded up.” Twice the target load means twice the pods.
replicas nowmeasured average (e.g. 90% CPU)your target (e.g. 60%)

Three details from the docs that matter in practice:

  • Tolerance: if the ratio is within 10% of 1.0, it does nothing (no flapping over small wiggles).
  • Scale up fast: by default it may add up to 100% more pods or 4 pods (whichever is more) every 15 seconds.
  • Scale down slowly: it uses the highest recommendation of the last 300 seconds (the stabilization window), so a brief dip doesn't remove pods you'll need again in a minute.
✏️ Worked example: the HPA by hand

Target: 60% CPU. Each pod requests 1 CPU.

  • 4 pods at an average of 90%: ⌈4 × 90 ÷ 60⌉ = ⌈6⌉ = 6 pods.
  • Load drops, 6 pods now average 40%: ⌈6 × 40 ÷ 60⌉ = 4 pods, but only after the 5-minute window shows nothing higher.
  • 6 pods at 63%: ratio 63 ÷ 60 = 1.05, inside the 10% tolerance, so no change.

Why target 60% and not 95%? New pods take time to start (often 30 s to several minutes, plus new nodes if the cluster is full). The gap between your target and 100% is the headroom that absorbs traffic while help is on the way.

When there's no room: the cluster autoscaler

The HPA adds pods. If no node has room for them they sit Pending (Lesson 5.2). A node autoscaler watches for that. The Kubernetes Cluster Autoscaler checks for unschedulable pods every 10 seconds by default, asks the cloud for more machines, and removes nodes that stay unneeded. Karpenter is the other node autoscaler sponsored by Kubernetes' autoscaling group; both provision nodes for pending pods and consolidate underused ones to save cost. A new node typically takes a minute or more to boot and join, so that time adds to your startup lag. Some teams keep a few low-priority “placeholder” pods running as spare room that real pods can push out instantly.

Probes: how Kubernetes knows a pod is OK

The kubelet runs up to three kinds of probe on each container (an HTTP request, a TCP connect, or a command). Defaults: every 10 s, 1 s timeout, 3 failures in a row to count as failed.

ProbeQuestionWhen it failsTypical check
ReadinessCan you take traffic right now?Pod is removed from the Service's endpoints. Not restarted./ready: warmed up, can reach what it needs
LivenessAre you stuck beyond repair?Container is killed and restarted./healthz: the process itself responds. Nothing else.
StartupHave you finished starting?Killed after its own budget. Until it passes, the other two don't run.Same as liveness, with a long budget: 30 × 10 s = 5 minutes

The Kubernetes docs warn that liveness probes “must be configured carefully” to indicate truly unrecoverable failure, because a bad one causes cascading failures: restarts under high load, failed requests, and more load on the pods that are left. And a container that keeps dying waits longer each time before restarting: 10 s, 20 s, 40 s… capped at 5 minutes. That's the famous CrashLoopBackOff.

Things to try, one change at a time from the defaults:

  • Rolling deploy, no readiness probe: the Deployment thinks each new pod is ready the moment its process starts, replaces all three within seconds, and every request fails for about 40 s while they warm up.
  • Rolling deploy, no startup probe: the liveness probe kills each new pod before its 40 s warm-up finishes. It never gets ready: CrashLoopBackOff. (With readiness on, the old pods keep serving and the rollout just stalls.)
  • Traffic doubles, 1 s liveness timeout: overloaded pods answer /healthz slowly, get killed, and the survivors take even more load. Switch the timeout to 5 s.
  • Database down, deep liveness: the DB outage “fails” every pod's liveness check, so all of them restart, and you stay down long after the database is back. A shallow check would have kept them alive.

🧰 Tools you'll actually use

metrics-server (feeds CPU/memory to the HPA and kubectl top), Cluster Autoscaler or Karpenter, KEDA (scale on queue length or any metric, even to zero), VPA (suggests requests), Gateway API implementations (Envoy Gateway, Istio, Cilium, cloud gateways), External Secrets Operator. Probes, resources, an HPA and a PDB:

# in the Deployment's container spec
resources:
  requests: { cpu: "500m", memory: "512Mi" }
  limits:   { memory: "512Mi" }        # memory limit = request; no tight CPU limit
startupProbe:                          # up to 30 × 10 s = 5 min to boot
  httpGet: { path: /healthz, port: 3000 }
  failureThreshold: 30
  periodSeconds: 10
livenessProbe:                         # "is the process stuck?" only, no dependencies
  httpGet: { path: /healthz, port: 3000 }
  periodSeconds: 10
  timeoutSeconds: 5
  failureThreshold: 3
readinessProbe:                        # "send me traffic?": warmed up, deps reachable
  httpGet: { path: /ready, port: 3000 }
  periodSeconds: 5
---
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata: { name: api }
spec:
  scaleTargetRef: { apiVersion: apps/v1, kind: Deployment, name: api }
  minReplicas: 3
  maxReplicas: 50
  metrics:
    - type: Resource
      resource:
        name: cpu
        target: { type: Utilization, averageUtilization: 60 }   # % of the CPU request
  behavior:
    scaleDown: { stabilizationWindowSeconds: 300 }
---
apiVersion: policy/v1
kind: PodDisruptionBudget
metadata: { name: api }
spec:
  maxUnavailable: 1
  selector: { matchLabels: { app: api } }

kubectl get hpa api -w                 # current vs target metric, replicas
kubectl describe hpa api               # why it did (or didn't) scale

🚀 Startup vs big tech

Founding engineer (0 → 1)

If you're on Kubernetes at all: requests from real measurements, memory limit = request, a readiness probe on every service, a startup probe for slow boots, an HPA on CPU with min 2–3 replicas, and one Gateway or managed load balancer. On Cloud Run or Fargate most of this is a few settings (Lesson 5.5).

Big tech (1 → 100)

Autoscaling on business metrics (queue lag, req/s), node autoscaling with spare headroom, PDBs everywhere so cluster upgrades never take a service below quorum, request right-sizing reports that save real money, and policies that reject pods without requests or probes. SRE reviews probes during launches (Lesson 6.4).

🎤 Interview angle

When you say “it autoscales”, interviewers ask “on what, how fast, and what happens in the meantime?”. Cover:

  • The metric and target, and the headroom it leaves for the startup lag (pod start + node start).
  • min/max replicas: min for availability across zones, max to protect downstream databases from your own autoscaler.
  • Readiness vs liveness: readiness gates traffic, liveness restarts; never put dependencies in liveness.
  • How config and secrets are injected, and how traffic enters (Gateway/Ingress + TLS).

Common follow-ups: “Your pods keep getting OOMKilled, what do you check?” (limit vs real usage, memory leaks, JVM heap vs container limit). “Traffic triples in 30 seconds: will the HPA save you?” (not alone: headroom, pre-scaling, queueing, load shedding from Lesson 4.4).

🏭 In the real world
Clusters that follow the traffic 🏢 Airbnb · 2022 Dynamic Kubernetes Cluster Scaling at Airbnb

How: thousands of nodes in nearly a hundred clusters, sized by the Kubernetes Cluster Autoscaler, to which Airbnb contributed a custom gRPC “expander” to choose which node group to grow.

Why this method: traffic swings every day, and cloud spend should scale with demand both up and down without humans resizing clusters.

The HPA algorithm 🧰 Kubernetes docs Horizontal Pod Autoscaling

How: desired = ⌈current × metric ÷ target⌉, every 15 s, with a 0.1 tolerance, fast default scale-up policies and a 300 s scale-down stabilization window.

Why this method: a proportional rule is simple to reason about; the tolerance and window stop it from oscillating.

Probes and their failure modes 🧰 Kubernetes docs Liveness, Readiness, and Startup Probes

How: readiness removes a pod from Service endpoints; liveness restarts it; a startup probe holds the other two off until the app has started.

Why this method: separating “not ready now” from “broken forever” lets Kubernetes route around slow pods without killing them, which is exactly what the docs' cascading-failure warning is about.

From Ingress to Gateway API 📜 Kubernetes · 2023–2026 Gateway API v1.0: GA Release · Ingress NGINX retirement

How: Gateway, GatewayClass and HTTPRoute reached v1 in October 2023, written by engineers from Kong, Isovalent and Google; in November 2025 Kubernetes announced the retirement of Ingress NGINX.

Why this method: one standard, role-oriented API for traffic entry (platform team owns the Gateway, app teams own their routes) instead of controller-specific annotations.

🤯 Fun fact · the back-off resets

A crash-looping container waits 10 s, 20 s, 40 s… up to 5 minutes between restarts. But once it runs for 10 minutes without trouble, the kubelet forgets its history and the next crash starts from 10 s again.

🌉 How it connects

Readiness probes are the in-cluster version of load-balancer health checks (Lesson 1.2), and cascading restarts are the same death spiral as retry storms (Lesson 4.4). The HPA's lag is why you also need queues to absorb bursts (Lesson 3.1). Lesson 5.4 puts all this YAML in git so nobody edits it by hand, and Lesson 6.3 gives you the metrics to choose targets. AI inference services often scale on GPU utilization or queue length instead of CPU, and their startup lag (loading a model) can be minutes, so headroom matters even more.

Check yourself

1. An HPA targets 50% CPU. There are 8 pods averaging 85%. How many pods will it ask for?
⌈8 × 85 ÷ 50⌉ = ⌈13.6⌉ = 14. The ratio 1.7 is far outside the 10% tolerance, and the default scale-up policy allows doubling every 15 s, so it can jump straight there.
2. Every time the database has a hiccup, all your API pods restart at once and the site stays down for minutes after the DB recovers. What's the most likely cause?
Liveness should only ask “is this process stuck?”. Put dependency checks in readiness (stop sending traffic) or nowhere. Restarting healthy pods can't fix a database, and it adds warm-up time to the outage.
3. A pod requests 256Mi of memory with a 256Mi limit. Under load it needs 400Mi. What happens?
CPU over the limit is throttled, but memory can't be taken back, so going over the memory limit gets the container killed. Raise the limit to real peak usage (and the request with it), or fix the memory use.
📝 TL;DR
  • Requests = reserved (scheduling, cost, HPA %); limits = maximum (CPU throttled, memory OOMKilled). Size requests from real usage.
  • HPA: desired = ⌈current × metric ÷ target⌉ every 15 s; 10% tolerance; 300 s scale-down window. Target below 100% = headroom for startup lag.
  • HPA adds pods; a node autoscaler (Cluster Autoscaler, Karpenter) adds machines when pods are Pending.
  • Readiness gates traffic, liveness restarts, startup protects slow boots. Never put dependencies in liveness.
  • ConfigMaps/Secrets for config (Secrets unencrypted in etcd by default), Gateway API for traffic in, PDBs for safe maintenance, StatefulSets for sticky identity.
