Phase 5 · Lesson 4

Infrastructure as code: Terraform, Helm & GitOps

Describe your servers, networks, databases and Kubernetes apps in files kept in git, and let tools make reality match. It's how you rebuild an environment in minutes, review infrastructure changes like code, and stop “someone clicked something in prod” incidents.

🧰 You'll need (quick reminders)
  • Desired state + reconciliation: declare what should be true; a loop keeps making it true (Lesson 5.2).
  • Deployments, Services, HPAs are YAML objects you apply to a cluster (Lessons 5.2 and 5.3).
  • Images tagged by git commit, so a tag says exactly what code runs (Lesson 5.1).
🎯 Hook

On August 1, 2012, trading firm Knight Capital switched on new code. The SEC's order describes what had happened days earlier: during a manual deployment, one technician did not copy the new code to one of the eight servers, and nobody else reviewed it. That eighth server still held old, unused code, which the new release accidentally re-activated.

In about 45 minutes it sent millions of orders, got over 4 million executions in 154 stocks, and Knight lost more than $460 million. Seven servers matched the plan; one had drifted. Infrastructure as code exists so that “what's deployed” is written down, reviewed, and enforced by a machine.

Numbers first: clicking vs code

A small product has 3 environments (dev, staging, prod), each with a network, a database, a cache, a load balancer, DNS records, 2 buckets, a Kubernetes cluster and 15 apps. That's well over 100 things to configure, three times, consistently.

💡 Big idea Write the desired state of your infrastructure in files. A tool compares those files with the real world, shows you the diff, and applies only that. With GitOps you go one step further: git is the single source of truth, and an agent inside the cluster keeps pulling and reconciling, so a manual change in prod is detected and undone. It's Kubernetes' reconcile loop (Lesson 5.2), applied to everything.
🧠 Analogy: the architect's blueprint

Builders don't rebuild a house from memory; they follow the blueprint. To add a window you change the blueprint first, the change is reviewed, and the builder works out the steps: some changes are a quick job (paint), some mean knocking down a wall and rebuilding it (move a load-bearing wall). terraform plan is the builder telling you which is which before picking up a hammer. GitOps adds an inspector who walks the house every few minutes and puts back anything that doesn't match the blueprint.

Terraform in five words: write, plan, apply, state, modules

  • Write resources in HCL (HashiCorp Configuration Language): “an S3 bucket called acme-assets”, “a t3.small server”. Providers are plugins that talk to each API (AWS, GCP, Cloudflare, GitHub, Datadog…).
  • Plan: Terraform refreshes what really exists, compares it with your code, and prints the actions: + create, ~ update in-place, − destroy, and −/+ destroy and then create replacement.
  • Apply executes the plan, in dependency order.
  • State is Terraform's record mapping your code to real resource IDs. Keep it in a remote backend with locking (e.g. an S3 bucket or HCP Terraform) so two people can't apply at once, and protect it: it can contain secrets.
  • Modules are reusable bundles (“a VPC”, “a service with its database”), called with different inputs per environment.

The scary symbol is −/+. Some settings can't be changed on a live resource because the cloud API doesn't allow it (a server's machine image, a bucket's name), so Terraform destroys the old one and creates a new one. For a server that's downtime unless you add create_before_destroy; for a bucket or a database it can mean data loss. Reading the plan is the whole skill.

✏️ Worked example: read this plan

You change three lines in one pull request: the web server's instance_type from t3.small to t3.medium, its ami (machine image) to a new one, and the assets bucket's name.

  • instance_type alone would be ~ update in-place: the AWS provider stops and starts the instance (a minute or two of downtime for that one server, typically).
  • But the ami change forces replacement, so the instance line becomes −/+: a new server with a new IP. One replacement covers both changes.
  • The bucket rename also forces replacement. The old bucket would be destroyed, so its files go with it, or (by default) the apply fails because the bucket isn't empty.
  • Summary line: Plan: 2 to add, 0 to change, 2 to destroy. Two “destroys” in a PR titled “bump instance size” is exactly what reviewers are there to catch.

GitOps: git is the source of truth

  
With plain CI, a pipeline pushes changes into the cluster (kubectl apply from a CI job). With GitOps, an agent running inside the cluster, like Argo CD or Flux, pulls from git and reconciles:

  
    
    
  • You change the desired state with a pull request (e.g. bump image: api:3f9c2e1 → api:a81b7c0 in envs/prod/). Review and merge.
    • 
    
  • Argo CD polls the repository every three minutes by default (or reacts to a webhook in seconds), sees the cluster is OutOfSync, and applies the change.
    • 
    
  • With self-heal on, Argo CD also syncs when the live cluster drifts from git, so someone's manual kubectl edit is put back.
    • 
    
  • Rollback = git revert. Audit log = git log. The CI system never needs credentials to production.
    • 
  

  
Promotion between environments is just more pull requests: the same image tag moves from envs/dev to envs/staging to envs/prod, often automated for dev and gated by approval for prod (Lesson 6.2 covers canaries and progressive delivery).

    🧰 Tools you'll actually use
    
Terraform and its open-source fork OpenTofu (created after HashiCorp moved Terraform to the BUSL licence), Pulumi and AWS CDK (infrastructure in TypeScript/Python), Helm, Kustomize, Argo CD, Flux, and policy checkers like Checkov or OPA. A small main.tf:


terraform {
  backend "s3" {                                 # remote, shared, locked state
    bucket       = "acme-terraform-state"
    key          = "prod/terraform.tfstate"
    region       = "us-east-1"
    use_lockfile = true
  }
}
provider "aws" { region = "us-east-1" }

module "vpc" {                                    # a reusable module with inputs
  source = "terraform-aws-modules/vpc/aws"
  name   = "prod"
  cidr   = "10.0.0.0/16"
  azs    = ["us-east-1a", "us-east-1b", "us-east-1c"]
}

resource "aws_s3_bucket" "assets" {
  bucket = "acme-assets"                          # renaming forces replacement!
}

resource "aws_db_instance" "main" {
  engine              = "postgres"
  instance_class      = "db.t3.medium"            # changes in place
  allocated_storage   = 100
  multi_az            = true                      # standby in another zone (Lesson 5.5)
  deletion_protection = true                      # AWS refuses to delete it
  lifecycle { prevent_destroy = true }            # Terraform refuses to plan its destruction
  # credentials from a secret manager, never in the file
}


terraform init                       # download providers, connect to the backend
terraform plan -out=release.plan     # show the diff (post it on the PR)
terraform apply release.plan         # apply exactly what was reviewed
terraform plan -refresh-only         # just show drift: what changed outside Terraform

    
Per-environment Helm values, and an Argo CD Application that keeps prod in sync with git:


# envs/prod/values.yaml (overrides the chart's defaults)
image: { repository: registry.example.com/api, tag: "a81b7c0" }
replicaCount: 6
autoscaling: { enabled: true, minReplicas: 6, maxReplicas: 60, targetCPUUtilizationPercentage: 60 }
---
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata: { name: api-prod, namespace: argocd }
spec:
  project: default
  source:
    repoURL: https://github.com/acme/deploy.git
    targetRevision: main
    path: charts/api
    helm: { valueFiles: [../../envs/prod/values.yaml] }
  destination: { server: https://kubernetes.default.svc, namespace: api }
  syncPolicy:
    automated:
      prune: true       # delete objects that were removed from git
      selfHeal: true    # undo manual changes to the live cluster

    
Try it locally: helm template my-api ./charts/api -f envs/prod/values.yaml renders the YAML without touching any cluster, and terraform plan against a free-tier account (or LocalStack) is the safest way to learn the symbols.

    🚀 Startup vs big tech
    

      
Founding engineer (0 → 1)
Even at two people, put the cloud account in Terraform from week one: one repo, remote state, modules for “a service” and “a database”, terraform plan in CI on every PR. If you're on Cloud Run or ECS, a GitHub Action that deploys on merge is plenty; add Argo CD when you adopt Kubernetes.

      
Big tech (1 → 100)
A platform team publishes vetted modules and charts, state is split per team and environment to limit the blast radius of a bad apply, policy-as-code blocks risky plans (public buckets, deletes in prod), and GitOps manages hundreds of clusters with ApplicationSets, with promotions flowing through environments automatically.

    

  


  

    🎤 Interview angle
    
Infrastructure as code comes up in “how do you deploy and operate this?” and in behavioural questions about outages. A strong answer:

    
    
      
  • All infrastructure and app config in git; changes via reviewed PRs with the plan attached.
    • 
      
  • How you prevent destructive changes: reading −/+ lines, prevent_destroy, deletion protection, policies.
    • 
      
  • Drift: how it's detected (scheduled plan, GitOps self-heal) and why manual prod changes are banned or temporary.
    • 
      
  • Environments: same modules/charts, different inputs; promote the same artifact.
    • 
    

    
Common follow-ups: “Two engineers apply at once?” (state locking). “Someone hotfixed prod by hand during an incident?” (allowed in emergencies, then written back to git, or self-heal reverts it). “How do you roll back infra?” (revert the commit; some changes, like deleted data, can't be rolled back, so backups matter).

  


  

    🏭 In the real world
    

      
The cost of one drifted server 🏢 Knight Capital · 2012 SEC order, File No. 3-15570

      
How: new code was deployed by hand in stages; one of eight servers was missed and no second technician reviewed the deployment. The old code on that server ran wild for about 45 minutes.

      
Why this method matters: repeatable, automated, verified deploys make “7 of 8 servers updated” impossible to miss.

    

    

      
Argo CD 🏢 Intuit · 2017–2022 CNCF: Argo has graduated

      
How: Argo was created and open-sourced in 2017 by Applatix, which Intuit acquired; it joined the CNCF in 2020 and graduated in December 2022, used in production by over 350 organizations including Adobe, Capital One, Google and Tesla.

      
Why this method: declarative, git-driven delivery to many Kubernetes clusters, with a UI that shows exactly what's out of sync.

    

    

      
The word “GitOps” 📜 Weaveworks · 2017 GitOps: Operations by Pull Request (archived)

      
How: Alexis Richardson described Weaveworks' practice of driving operations through pull requests to declarative config in git, with tools that converge the cluster to it.

      
Why this method: developers already knew git review; making it the path to production gave operations the same history, review and rollback.

    

    

      
Plan before you apply 🧰 Terraform docs terraform plan · Manage resource drift

      
How: the plan lists every create, in-place update, destroy and replacement (with # forces replacement next to the culprit), and -refresh-only shows what changed outside Terraform.

      
Why this method: separating “what will happen” from “do it” turns infrastructure changes into reviewable diffs.

    🌉 How it connects
    
GitOps is the reconcile loop from Lesson 5.2 with git as the dial. The YAML it syncs is Lesson 5.3's. Terraform creates the cloud pieces of Lesson 5.5 (VPCs, managed databases, buckets). CI/CD (Lesson 6.1) builds the image and opens the PR that bumps its tag; progressive delivery (Lesson 6.2) decides how fast it rolls out. In AI systems the same pattern manages GPU node pools and model-serving deployments, where a wrong apply is an expensive mistake.

Check yourself

  

    
1. A plan says: Plan: 3 to add, 1 to change, 3 to destroy. There are 3 web servers and a load balancer in the config. What most likely happened?

    

    
Each −/+ counts once as “add” and once as “destroy”. 3 replacements = 3 to add + 3 to destroy. Check which attribute says # forces replacement, and use create_before_destroy (or roll them one at a time) to avoid all three disappearing together.

  

  

    
2. During an incident an engineer runs kubectl scale --replicas=20 in prod. Argo CD has auto-sync and self-heal on, and git says 6. What happens, and what should the engineer do?

    

    
Self-heal treats live changes as drift and re-applies git. In an emergency, either commit the change (a fast PR) or deliberately pause auto-sync for that app, then write the fix back to git. (An HPA owning the replica count is the usual long-term answer.)

  

  

    
3. Argo CD polls git every 3 minutes by default. You merge 40 times a day. Roughly how long does a merge wait before Argo CD notices it, on average, without webhooks?

    

    
A merge lands at a random moment within the 3-minute polling interval, so the average wait is half of it: about 90 seconds (worst case 3 minutes). A webhook from your git host cuts it to seconds.

  


  

    📝 TL;DR
    
    
      
  • Infrastructure as code: desired state in git, a tool diffs it against reality and applies only the diff.
    • 
      
  • Terraform: write → plan → apply; state (remote, locked) maps code to real IDs; modules for reuse.
    • 
      
  • Read every −/+: replacement means downtime (fix: create_before_destroy) or data loss (protect: prevent_destroy, deletion protection).
    • 
      
  • Helm = templated packages with values; Kustomize = base + overlays.
    • 
      
  • GitOps (Argo CD, Flux): an in-cluster agent pulls from git and reconciles; self-heal reverts manual drift; rollback = git revert.
