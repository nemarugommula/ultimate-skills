Recap: designing real systems

Eight designs, one method: clarify, estimate, then spend your time on the one problem that makes each system hard. This page is your cheat sheet, a matching game, a fresh design problem with a full answer, and a boss quiz.

🧾 Cheat sheet: the key decision of each design

🧭

7.1 The design framework

6 steps · ~45 min: clarify → estimate → API + data → high-level → deep dives → wrap-up. QPS = daily actions ÷ 86,400; peak ≈ 2–3×. Every box needs a number or a requirement behind it.

Tools: a design doc, Excalidraw / draw.io / Mermaid, a Python REPL for estimates
🔗

7.2 URL shortener

~116k redirects/s vs ~1,160 writes/s. Key decisions: how to generate short codes (counter ranges + base62, or random + conditional insert), and a cached redirect path; 302 if you count clicks.

Tools: Redis, PostgreSQL / DynamoDB / Cassandra, Kafka for click events
📰

7.3 News feed

~58k feed reads/s vs ~230 posts/s. Key decision: fan-out on write (precomputed timelines) vs on read; hybrid for celebrities: push for most, pull for the few with huge followings.

Tools: Redis lists / sorted sets, Kafka or SQS, Cassandra / PostgreSQL
💬

7.4 Chat (WhatsApp)

~230k messages/s · ~150M open WebSockets. Key decision: stateful gateways hold the sockets and a registry routes each message to the right one; store first with a per-conversation sequence number, deliver at least once with acks and dedupe, push to offline devices.

Tools: ws / Socket.IO / Phoenix, Cassandra / ScyllaDB / DynamoDB, Redis pub/sub or Kafka, APNs / FCM
🎬

7.5 Video streaming

~4.7 GB per hour of video for a 5-rung ladder. Key decision: small segments × a bitrate ladder, chosen per segment by the player (ABR), delivered from a CDN; encode in a chunked, retryable DAG; tier storage.

Tools: FFmpeg, MediaConvert / Mux, HLS / DASH, hls.js, CloudFront / Open Connect
🚗

7.6 Ride sharing

1M drivers ÷ 4 s = 250k writes/s of ephemeral data. Key decision: keep current locations in memory in a cell index (H3/geohash), search expanding rings, rank by ETA; a conditional write stops double dispatch.

Tools: H3, S2, Redis GEO, PostGIS, Kafka, OSRM
💳

7.7 Payments

~116 payments/s: small traffic, high stakes. Key decision: a persisted state machine with an UNKNOWN state, idempotency keys end to end, an append-only double-entry ledger, deduped webhooks, daily reconciliation.

Tools: Stripe / Adyen, PostgreSQL, TigerBeetle / Modern Treasury
🔔

7.8 Notifications

11.6k/s average, 167k/s bursts. Key decision: gates before sending (dedupe, preferences, quiet hours, caps, digests), separate priority queues, retries + provider failover; the inbox is the durable copy.

Tools: APNs, FCM, SES / SendGrid, Twilio, Kafka, Redis

🏗️ Design it yourself: a concert ticket drop

✏️ The prompt

A superstar announces a tour. One stadium show has 50,000 reserved seats. Sales open at 10:00, and about 2,000,000 fans arrive in the first minute. Each fan may buy up to 4 seats. Design the system so the site stays up, no seat is ever sold twice, nobody is charged twice, and fans are treated fairly.

Try it with the framework from Lesson 7.1 before opening the answer: questions, numbers, API, architecture, the two hardest problems, and what you'd say in the wrap-up.

Reveal a senior-level answer

1. Clarifying questions (and the answers we assume)

  • Reserved seats or general admission? Reserved (each seat is unique, so it's an inventory-locking problem).
  • How long may a fan hold seats while paying? 10 minutes, then they're released.
  • Fairness: first come first served, or a randomised queue for everyone who arrived before 10:00? Randomise the early arrivals, then first come first served (so refreshing at 09:59:59 doesn't matter).
  • Bots and resellers? In scope: per-account limits and a check at queue entry.

2. Numbers

  • Arrivals: 2,000,000 ÷ 60 s ≈ 33,000 per second. If each refreshed the seat map every 2 s: 1,000,000 requests/s on the most contended data you own. That can't reach the database.
  • Orders: at least 50,000 ÷ 4 = 12,500; with an average of 2.5 seats, about 20,000 orders.
  • Admit 2,000 fans per minute into the store, with about 5 minutes each to choose and pay: about 10,000 concurrent shoppers, a load one inventory service handles. If 80% buy, the show sells out in about 20,000 ÷ (2,000 × 0.8) = 12.5 minutes.
  • So queue positions beyond roughly 20,000 ÷ 0.8 = 25,000 will probably get nothing: tell them early and offer the waitlist or another date.

3. API

POST /v1/events/e_1/queue                     → { "queue_token": "…", "position": 18234 }   (static page polls a CDN-cached status)
POST /v1/events/e_1/holds   Authorization: admission-token
     { "seats": ["A-12-7", "A-12-8"] }        → 201 { "hold_id": "h_9", "expires_at": "10:14:02" } | 409 seat taken
POST /v1/orders  Idempotency-Key: h_9         → pays via the PSP (Lesson 7.7), converts the hold to SOLD

4. Architecture

  • Waiting room on the CDN (Lesson 1.4): a static page; the queue service hands out signed tokens and a position. Early arrivals get a random order; later ones join the end. Admission is a rate limiter (Lesson 1.5): 2,000 tokens per minute.
  • Gateway (Lesson 1.6) rejects any store request without a valid admission token, so the 2 million never touch the inventory.
  • Seat inventory: the source of truth in a strongly consistent store, sharded by section. A hold is a conditional write: UPDATE seats SET status='HELD', hold_id=?, hold_until=now()+'10 min' WHERE seat_id IN (…) AND status='AVAILABLE' inside a transaction (Lesson 2.5); all requested seats or none. Expired holds are swept back to AVAILABLE.
  • Seat map reads come from a cache refreshed every second or two, plus pushed updates over a connection (Lesson 7.4). The map may be slightly stale; the hold is never wrong, because the conditional write decides.
  • Orders and payments: the hold id is the idempotency key (Lesson 7.7). Authorize, mark SOLD, then capture; if payment fails or the hold expires, release.
  • Notifications (Lesson 7.8): order confirmations on a high-priority queue, “you're nearly at the front” on a normal one, and the waitlist announcement as a throttled bulk send.

5. The two hardest problems

  • Contention on a few hot rows: everyone wants the front rows. Conditional writes make it correct; sharding by section and showing “best available” suggestions spreads the load.
  • Protecting the core from the crowd: the waiting room plus admission tokens turn a 1,000,000 requests/s spike into a steady 2,000 shoppers a minute.

6. Trade-offs to say out loud

  • Hold length: longer is kinder to slow payers, but seats sit idle and sell-out takes longer.
  • Fairness: randomised early queue vs pure first come first served; lotteries are fairer but feel less transparent.
  • Consistency: strong for inventory and orders (availability can wait); eventual for the seat map and queue position display.
  • Startup: a hosted queue product plus Postgres with conditional updates gets you surprisingly far. Big tech: dedicated queue infrastructure, bot detection, multi-region active-passive for the inventory.

7. Classic mistakes

  • Letting every fan query the seat database directly, or keeping seat holds only in app-server memory.
  • Using the cache as the source of truth for inventory.
  • Holds with no expiry (seats locked forever by abandoned carts).
  • Retrying payment without an idempotency key, or sending “you got tickets!” before the seat is marked SOLD.

🏆 Boss quiz

1. An interviewer says: “Design a search system for a social network.” What should the first few minutes sound like?
Lesson 7.1's framework: clarify, then estimate, before any box. Freshness (seconds or hours?) and scale decide whether you need a streaming indexer or a nightly batch, and whether one node or hundreds.
2. A platform receives 10,000 hours of video uploads a day and stores a ladder that totals about 10.4 Mbps. Roughly how much new ladder storage is that per day?
10.4 Mbps × 3,600 s ÷ 8 ≈ 4.68 GB per hour; × 10,000 hours ≈ 46.8 TB per day, about 17 PB a year. Storage tiering and lazy renditions (Lesson 7.5) are budget decisions.
3. A user with 80 million followers posts, and timeline workers fall an hour behind writing it into every follower's feed. What's the standard fix?
Lesson 7.3: push for normal accounts keeps reads cheap; pulling the few celebrity accounts at read time avoids 80 million writes per post. Pure fan-out on read would make every feed read slow.
4. A client retries a payment with the same idempotency key, but the amount changed from $50 to $500. What should the payment API do?
A key identifies one specific operation. Stripe's idempotency layer compares incoming parameters with the original request and errors if they differ. Silently returning the old result would hide the bug; charging $500 would defeat the key (Lesson 7.7).
5. During a stadium event, the location shard that holds one city melts while the others are idle. Which change fixes it at the root?
Lesson 7.6 (and Lesson 2.4's hot keys): a city is too coarse a shard key because one city can be a big share of all traffic. Cells split it. A bigger machine or fewer updates only buys time until the next, bigger event.
