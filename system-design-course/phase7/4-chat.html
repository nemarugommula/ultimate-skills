Phase 7 · Lesson 4

Design a chat system (WhatsApp)

Deliver every message once, in order, within a fraction of a second, to whichever of a billion phones is online, and to the rest as soon as they come back. Chat turns stateless request/response on its head: the servers hold live connections.

🧰 You'll need (quick reminders)
  • WebSockets: one long-lived connection the server can push messages down at any time (Lesson 0.4).
  • Consistent hashing maps a key (a user, a channel) to one server so everyone agrees who owns it (Lesson 2.4).
  • Idempotency: if a retry can deliver something twice, give it a unique ID and drop the duplicate (Lesson 3.3).
🎯 Hook

In January 2012, WhatsApp posted a blog entry titled “1 million is so 2011”. A few months earlier one of their servers had held a million TCP connections; now a single FreeBSD box running Erlang showed 2,277,845 open sockets, “with plenty of CPU and memory to spare”.

Two million people connected to one machine, each able to receive a message at any instant. Building chat is mostly about those connections: how many fit on a server, how a message finds the right one, and what happens when one disappears.

Step 1 · Requirements

Functional: 1:1 and group chats (assume groups up to a few hundred members); messages sync across a user's devices with full history; delivery and read receipts; presence (online / last seen); offline users get a push notification and the messages when they reconnect; photos and voice notes (stored as files, Lesson 2.7).

Non-functional: low latency (well under a second end to end); no lost messages; per-conversation ordering (everyone sees a chat in the same order); high availability; and privacy: end-to-end encryption (E2E, only the devices in the chat can read messages, not the server).

Step 2 · Estimates (by hand)

✏️ Worked example: chat at WhatsApp-like scale
  • Messages: 500M × 40 = 20B a day ÷ 86,400 ≈ 231,000/s, peak (×2) ≈ 460,000/s.
  • Storage at about 100 bytes per text message: 20B × 100 B = 2 TB a day, 730 TB a year, about 2.2 PB with 3 copies. Media goes to object storage, not here.
  • Concurrent connections: if 30% of daily users are online at peak = 150M open WebSockets.
  • At 500,000 connections per gateway server: 150M ÷ 500k = 300 servers, ×1.5 headroom to survive losing a zone ≈ 450.
  • Memory at about 20 KB per connection (buffers, TLS state, session): 500k × 20 KB = 10 GB per server. WhatsApp's 2012 box showed 35 GB active for 2.28M sockets, roughly 15 KB each.
  • Heartbeats every 30 s to detect dead connections: 150M ÷ 30 = 5M tiny messages/s, more than the chat messages themselves.

Step 3 · API (over the WebSocket)

// client → server
{"type":"send", "client_msg_id":"a1b2…", "conv":"c42", "body":"<ciphertext>"}
// server → sender: stored durably, here is its place in the conversation
{"type":"ack", "client_msg_id":"a1b2…", "msg_id":1790…, "seq":318}
// server → recipient device, which answers {"type":"delivered","msg_id":…}, later {"type":"read",…}
{"type":"msg", "conv":"c42", "seq":318, "msg_id":1790…, "from":"alice", "body":"…"}
// on reconnect: “give me everything after what I have”
{"type":"sync", "since":{"c42":317, "g7":1204}}

Plus plain HTTPS for the rest: GET /v1/conversations/{id}/messages?before_seq=… for scrolling history, and media upload URLs.

Wide-column stores (Lesson 2.1) are built on log-structured storage (LSM trees, Lesson 2.2) that make writes cheap and sequential, which suits a firehose of 460,000 small writes per second that are read back by conversation.

Step 5 · High-level design: following one message

Alice's phone holds a WebSocket to gateway 1. She sends; the chat service gives the message the next sequence number for that conversation, writes it to the message store, and acks Alice (“✓ stored”). Then it asks the session registry where Bob is connected, and pushes the message to gateway 2, which sends it down Bob's socket. Bob's phone acks (“✓✓ delivered”). If Bob is offline, a push notification goes out through Apple's or Google's push service, and his phone syncs when it reconnects.

🎮 Playground · Message delivery across gateways

Bob is on gateway 2, Carol on gateway 3, Dan is offline. Send messages, take Bob offline, crash his gateway mid-delivery, and turn delivery acks off to see what they protect against. Ticks: ✓ stored on the server, ✓✓ delivered to the device, 👁 read.

Delivery acks + retry:
messages stored 0
device deliveries done 0
waiting for offline device 0
lost 0
duplicates dropped 0

Things to try: send to Bob, then take him offline and send two more: they wait, with a push notification, and arrive in order when he's back. Now crash his gateway with acks off: the server handed the message to a gateway that died, assumed it was delivered, and Bob never sees it. With acks on, the missing ack triggers a resend after Bob reconnects, and because the device had actually received the first copy, the duplicate is dropped by its message ID.

💡 Big idea Store first, then deliver, then confirm. A message is safe the moment it's written to the store with a sequence number; delivery is at least once (retry until the device acks), and the device makes it look like exactly once by dropping duplicates by message ID. Anything can crash in between and nothing is lost.
🧠 Analogy: a post office with tracking numbers

The gateways are mail carriers who each know a few streets. The session registry is the address book saying which carrier serves Bob's street today. Every letter gets a tracking number (sequence) and a copy at the post office (the store) before it's sent. The recipient signs for it (the ack). No signature? The post office sends it again. And if Bob has moved to a new street (reconnected to another gateway), the address book is updated and the next attempt goes to the new carrier. Bob's “I already have letter 318” stops a double delivery.

Deep dive 1 · Connections: how many, where, and when they all drop

Gateways are stateful: each one holds hundreds of thousands of live sockets, so you can't treat them like stateless web servers (Lesson 1.1). Three rules:

  • Keep gateways dumb. They hold sockets and forward frames. Chat logic lives in services behind them, so a gateway deploy only drops connections, never data.
  • A registry maps user → gateway. Written on connect, refreshed by heartbeats, expired by TTL. Slack's design hashes channels to stateful “channel servers” with consistent hashing, and gateways subscribe to the channels their users are in.
  • Plan for reconnect storms. When a gateway dies, all its users reconnect at once, and each reconnect also costs a session lookup and a history sync. Clients must retry with exponential backoff and jitter (random delays that double each time, Lesson 4.4).

Notice the trade: packing 2 million connections per server (as WhatsApp did) means fewer machines, but each failure throws 2 million clients at the session service. Instant retries make it collapse and recovery takes many minutes; backoff with jitter spreads the herd and recovers far sooner.

Deep dive 2 · Ordering, delivery guarantees and receipts

  • Order per conversation, not globally. Phone clocks disagree, so never sort by client timestamps. One owner per conversation (the chat service instance that the conversation ID hashes to) hands out seq 1, 2, 3… Everyone sorts by seq. A global order across all chats is unnecessary and would be a bottleneck.
  • At least once + dedupe. The client generates client_msg_id; if Alice's send times out and she retries, the server sees the same ID and returns the same seq instead of storing twice (Lesson 3.3). Recipients dedupe by msg_id.
  • Gaps tell you something's missing. If Bob's device has seq 316 and receives 318, it asks for 317. On reconnect it sends “since 317” for each conversation, and the server replies with everything newer.
  • Receipts are just more messages. “Delivered” and “read” flow back to the sender as small events, and in groups are aggregated (“read by 12”). They are cheap individually and huge in total, so batch them.

Deep dive 3 · Storage, groups, presence and encryption

  • Storage. Partition by conversation, sort by sequence or a time-sortable ID, bucket by time. Discord reached trillions of messages with exactly this key shape: ((channel_id, bucket), message_id).
  • Group fan-out. One send becomes one delivery per member device: a 200-member group turns 1 message into 199 deliveries. With E2E encryption, WhatsApp's whitepaper describes “sender keys”: the sender encrypts once and transmits a single ciphertext, and “the server … does server-side fan-out to all group participants”.
  • Presence is expensive. “Bob is online” changes constantly and is interesting to many people. Send it only to contacts who currently have the app open, debounce flapping (a phone switching networks), and derive “last seen” from heartbeats with a TTL rather than writing on every change.
  • Offline delivery. Phones kill background sockets, so offline delivery means a push notification through APNs (Apple Push Notification service) or FCM (Firebase Cloud Messaging): “you have a new message”, then the app wakes, connects and syncs. Notifications at scale get their own design in Lesson 7.8.
  • End-to-end encryption. Clients exchange keys (WhatsApp uses the Signal Protocol); the server only ever sees ciphertext. Trade-off: the server can't search, index, preview or moderate message contents, and a new device can't read old history unless it's transferred from another device.

🧰 Tools you'll actually use

WebSocket servers: ws / Socket.IO (Node.js), Phoenix Channels (Elixir), Netty (Java); managed: AWS API Gateway WebSockets, Pusher, Ably. Stores: Cassandra, ScyllaDB, DynamoDB. Registry and fan-out between servers: Redis pub/sub or Kafka. Push: APNs and FCM. A gateway in Node.js, plus the message table in CQL (Cassandra's query language):

// gateway.js: hold sockets, register users, forward frames
import { WebSocketServer } from "ws";
import Redis from "ioredis";
const redis = new Redis(), sub = new Redis(), ME = process.env.GATEWAY_ID;
const sockets = new Map();                          // userId → socket
new WebSocketServer({ port: 8080 }).on("connection", (ws, req) => {
  const user = authenticate(req);                      // token from the URL or a header
  sockets.set(user, ws);
  redis.set(`user:${user}`, ME, "EX", 90);              // registry entry, refreshed by heartbeats
  ws.on("message", m => chatService.handle(user, JSON.parse(m)));
  ws.on("close", () => { sockets.delete(user); redis.del(`user:${user}`); });
});
sub.subscribe(`gw:${ME}`);                               // the chat service publishes here
sub.on("message", (_, frame) => { const f = JSON.parse(frame); sockets.get(f.to)?.send(frame); });
CREATE TABLE messages (
  conv_id bigint, bucket int, seq bigint,
  msg_id bigint, sender bigint, body blob,            -- ciphertext
  PRIMARY KEY ((conv_id, bucket), seq)
) WITH CLUSTERING ORDER BY (seq DESC);
SELECT * FROM messages WHERE conv_id = 42 AND bucket = 2031 AND seq > 317;  -- sync

Try it locally: npx wscat -c ws://localhost:8080 to talk to a WebSocket server by hand, and docker run -p 6379:6379 redis for the registry. A single-node Cassandra (docker run -p 9042:9042 cassandra) wants a few GB of RAM, so treat it as optional.

🚀 Startup vs big tech

Founding engineer (0 → 1)

Buy or keep it in one box: a managed real-time service (Pusher, Ably, Firebase), or Socket.IO/Phoenix with Redis pub/sub and Postgres. Get the protocol right from day one, because it's the part that's hard to change later: client message IDs, per-conversation sequence numbers, acks, and “sync since”.

Big tech (1 → 100)

Dedicated gateway fleets in many regions, a registry and presence service, a sharded chat tier, ScyllaDB/Cassandra clusters with dedicated teams, region draining for failures, and E2E multi-device key management. Discord replaced 177 Cassandra nodes with 72 ScyllaDB nodes; that kind of migration is a multi-quarter project at this scale.

🎤 Interview angle

What's evaluated: connection management (gateways, registry, capacity math), message flow with acks, ordering (per-conversation sequence), offline delivery, storage choice with a partition key, and group fan-out.

  • Common mistakes: “use WebSockets” without saying how one server finds another's user; ordering by timestamps; no acks (“fire and forget”); storing messages in one giant relational table with no partitioning plan; forgetting multiple devices; ignoring reconnect storms.
  • Likely follow-ups: “How do you scale to 100,000-member channels?” (pub/sub, members pull), “How does presence work without melting the system?”, “What happens when a region fails?”, “How do you sync a new laptop?”, “How do you do search with E2E encryption?” (on the device).
🏭 In the real world
Millions of connections per box 🏢 WhatsApp · 2012 1 million is so 2011

How: FreeBSD 8.2 with tuned kernel limits (max sockets 2.4 million, max files 3 million) and Erlang, on a 24-core Xeon box with about 100 GB of RAM, holding 2,277,845 TCP connections at about 42% idle CPU.

Why this method: Erlang's lightweight processes make one process per connection cheap, so very few servers could serve a huge user base.

Messages partitioned by channel and time 🏢 Discord · 2017 & 2023 How Discord Stores Trillions of Messages

How: after outgrowing MongoDB (around 100 million stored messages in 2015), Discord moved to Cassandra with key ((channel_id, bucket), message_id), buckets of about 10 days to stay under ~100 MB per partition (2017 post). In May 2022 it switched from 177 Cassandra nodes to 72 ScyllaDB nodes.

Why this method: every read is “recent messages in a channel”, so one bounded partition per channel and time range keeps reads to a single sorted scan.

Gateways, channel servers, presence servers 🏢 Slack · 2023 Real-time Messaging

How: stateful Channel Servers are mapped to channels with consistent hashing (about 16 million channels per host at peak); Gateway Servers in multiple regions hold users' WebSocket subscriptions; Presence Servers track who is online. Messages reach users worldwide in about 500 ms.

Why this method: splitting connection-holding (gateways near users) from channel ownership (one server per channel) lets each scale and fail independently; a replaced channel server is serving again in under 20 seconds.

Fan-out to every connected session 🏢 Discord · 2017 How Discord Scaled Elixir to 5,000,000 Concurrent Users

How: each user's WebSocket gets a session process; each server (“guild”) is a process on a remote Erlang node; anything published in a guild is fanned out to every connected session, including presence updates.

Why this method: “most of it boils down to pub/sub”. The Erlang VM's cheap processes map naturally onto one process per session and per guild.

End-to-end encryption by default 🏢 WhatsApp · 2016 WhatsApp Encryption Overview (whitepaper)

How: built on the Signal Protocol (rollout completed in April 2016). For groups, the sender encrypts once with a “Sender Key” and the server does server-side fan-out of that single ciphertext.

Why this method: the server can route and store messages without being able to read them, while group sends stay efficient.

🤯 Fun fact · fewer nodes, faster tail

When Discord moved its message store from Cassandra to ScyllaDB, it went from 177 nodes to 72, and reading historical messages went from a p99 of 40–125 ms to about 15 ms; inserts went from 5–70 ms p99 to a steady 5 ms. Same data model, same partition key: the storage engine underneath made the difference.

Check yourself

1. 100M users are online at peak, each gateway holds 500,000 connections, and you want 50% headroom. How many gateway servers?
100M ÷ 500k = 200 servers; × 1.5 headroom = 300. Then check memory: 500k × ~20 KB ≈ 10 GB per server, which fits comfortably.
2. A message arrives for Bob while his phone is offline. What should the system do?
Store first, deliver later. Gateways are disposable and Bob may reconnect anywhere, so the durable store plus “sync since seq” is the source of truth; APNs/FCM just wakes the app.
3. How do you make sure everyone in a group sees messages in the same order?
Phone clocks drift and can be wrong by minutes, and a global lock would serialise the whole planet. Ordering only needs to hold within a conversation, so one sequencer per conversation is enough, and it shards naturally by conversation ID.
📝 TL;DR
  • 500M users → ~230k messages/s, ~2 TB/day of text, ~150M open WebSockets → hundreds of gateway servers at ~500k connections each.
  • Stateful gateways hold sockets; a registry (user → gateway, TTL by heartbeat) routes messages; chat logic lives behind the gateways.
  • Store first with a per-conversation sequence number, deliver at least once with device acks, dedupe by message ID, sync “since seq” on reconnect, push notifications for offline devices.
  • Wide-column store keyed by (conversation, time bucket); server-side group fan-out; presence only to those watching; E2E means the server sees only ciphertext.
