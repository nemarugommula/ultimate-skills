Phase 7 · Lesson 2

Design a URL shortener

Turn a long link into sho.rt/4c92 and redirect billions of clicks in milliseconds. It looks like a toy, but it packs ID generation, caching, read-heavy scaling and async analytics into one small design.

🧰 You'll need (quick reminders)
  • The design framework: clarify → estimate → API + data → high-level → deep dives → wrap up (Lesson 7.1).
  • Caching: keep hot answers in Redis; average latency = hit rate × cache time + misses × (cache + database) (Lesson 1.3).
  • Sharding splits data across machines by key; Kafka is a durable log you can write events to and process later (Lessons 2.4 and 3.2).
🎯 Hook

In 2018 Google stopped creating new goo.gl links but kept the old ones working. In July 2024 it announced that all of them would stop working after August 25, 2025, noting that more than 99% had no activity in the last month. People pushed back: those links were “embedded in countless documents, videos, posts”. In August 2025 Google changed course and kept the actively used links alive.

That's the real requirement of a URL shortener: a link printed on a poster today must still work in ten years. Writing the code is easy. Keeping a promise that long is the design.

Step 1 · Requirements

Functional (what it does):

  • Given a long URL, return a short code. Visiting sho.rt/{code} redirects to the long URL.
  • Optional custom aliases (sho.rt/summer-sale) and expiry dates.
  • Analytics: clicks per link per day, country, referrer.

Non-functional (how well):

  • Redirects are fast (a few milliseconds on our side) and highly available: a dead redirect breaks every place the link was shared.
  • Links are durable for years. Codes are short. Analytics may lag by a minute; redirects may not.

Step 2 · Estimates (by hand)

✏️ Worked example: sizing the shortener
  • Writes: 100M ÷ 86,400 ≈ 1,160 new links per second.
  • Reads at 100:1: ≈ 116,000 redirects per second on average, more at peak.
  • Links over 10 years: 100M × 365 × 10 = 365 billion.
  • Storage at about 500 bytes per link (code, long URL, owner, dates): 365B × 500 B ≈ 183 TB. Too much for one database: shard by code (Lesson 2.4).
  • Code length in base62 (the characters 0–9, a–z, A–Z: 62 symbols): 626 ≈ 56.8 billion is too few; 627 ≈ 3.5 trillion is about 10× what we need. 7 characters.
  • Cache: if 10% of redirects miss, the database sees 116,000 × 0.1 ≈ 11,600 reads/s. With a 1.5 ms hit and 5 ms extra on a miss (typical numbers), average latency = 0.9 × 1.5 + 0.1 × (1.5 + 5) = 2 ms.

Step 3 · API

Creating links needs an API key and a rate limit (Lesson 1.5): shorteners are a favourite tool for hiding spam and phishing links.

The access pattern is pure key lookup, no joins. That's why many teams pick a key-value store (DynamoDB, Cassandra) here, while a sharded Postgres works too (Lesson 2.1).

💡 Big idea A URL shortener is a giant, read-heavy lookup table: write a link once, read it thousands of times. So the design is about two things: making unique short codes cheaply, and serving redirects from a cache so the database barely notices the traffic.
🧠 Analogy: the coat check

You hand over a long coat and get a small numbered ticket. Handing out tickets has to be fast and never give two people the same number (generating codes). Most of the work is at the end of the night, when everyone shows a ticket and wants their coat back right now (redirects). A good coat check keeps the most-asked-for coats near the counter (the cache).

Things to try: set the cache to “none” at 100k redirects/s: the database melts. A cache holding just 1% of links (10,000) catches about two thirds of clicks within seconds. Bigger caches barely help in the first 30 seconds: most remaining misses are links nobody has clicked yet since the restart. Switch analytics to “sync DB write” and every click also writes a row: the database dies even with a big cache. Switch to 301: your traffic drops (browsers remember the redirect) but so do the clicks you can count.

Deep dive 1 · Generating the short code

This is the question interviewers care most about. Four common options:

MethodHow✅❌
Counter + base62A global counter (1, 2, 3…) written in base62Shortest codes, zero collisionsGuessable (next code = +1); one counter is a bottleneck → hand each server a range (server A gets 1–1M, B gets 1M–2M)
Hash + truncateHash the long URL (MD5, SHA-256), keep the first 7 base62 charactersSame URL → same code (free dedupe); no coordinationCollisions (birthday math, below): must check the database and retry
Random + check7 random base62 characters; insert only if the code is unusedUnguessable; no coordinationSame collision maths; every insert is a conditional write
Snowflake-style ID64 bits = timestamp + machine ID + sequence (Twitter, 2010)No coordination, roughly time-sorted, no collisionsA 64-bit number is 11 base62 characters: too long for a short link

Base62 works like decimal with 62 digits. Repeatedly divide by 62; the remainders, read backwards, are the digits. 125 = 2 × 62 + 1, so 125 becomes 21.

The birthday problem is why hashes collide sooner than you'd think. In a room of 23 people, two probably share a birthday, even though there are 365 days. With N possible codes and n links:

P(at least one collision) ≈ 1 − e−n²/(2N) “The chance that some two links share a code is about one minus e to the minus n squared over two N.” Collisions grow with the square of the number of links.

With 7 characters and one million links there's already a 13% chance of some collision. At our 365 billion links, about 1 in 10 new inserts would hit a used code. That's fine with “insert if absent, else retry with a new random code”, and a disaster if you forget the check and overwrite someone's link.

A good answer for our numbers: random 7-character codes (unguessable) with a conditional insert and retry, or counter ranges per server run through a reversible shuffle so codes don't look sequential. Some teams pre-generate unused codes in a key generation service and hand them out in batches.

Deep dive 2 · 301 vs 302, and caching the hot links

301 Moved Permanently302 Found
Meaning (RFC 9110, the HTTP standard)“Assigned a new permanent URI”; clients may replace referencesThe target “resides temporarily under a different URI”
CachingHeuristically cacheable: browsers may remember it and skip you next timeNot cached unless you send cache headers
Your loadLower (repeat visits never arrive)Every click reaches you
Analytics and editsMiss repeat clicks; can't reliably change or expire the linkCount every click; change or delete any time

Most shorteners that sell analytics answer with 302 (or 301 plus Cache-Control: private, max-age=… to limit how long browsers keep it). Then caching is your job: Redis in front of the database, and for the very hottest links, a tiny in-process cache in each redirect server (Lesson 1.3).

Deep dive 3 · Analytics, custom aliases and expiry

  • Analytics, asynchronously. The redirect service writes a small event to Kafka (about a millisecond, batched) and returns. A stream processor (Lesson 3.6) groups events by (code, minute) and writes one counter update per link per minute instead of one row per click. If Kafka is slow, drop or buffer events; never slow the redirect.
  • Custom aliases. Same table, same uniqueness rule: INSERT … IF NOT EXISTS. Reserve words (api, admin, login) and block lookalike phishing aliases.
  • Expiry. Check expires_at on every read (lazy expiry, so an expired link never redirects), and clean up in the background later. Set the cache TTL no later than the link's expiry.

Bottlenecks and the scaling path

StageDesignWhat forces the next step
v1: startup (thousands of links/day)One app, one Postgres with code as primary key, random codes with a unique constraint, 302s, a clicks tableClick inserts and reads crowd the one database
v2 (millions of clicks/day)Redis cache-aside for links, click events to a queue, a worker that aggregates counts, read replicasStorage heads toward terabytes; one primary can't hold it
v3 (100M links/day, 100k+ redirects/s)Key-value store sharded by code (consistent hashing, Lesson 2.4), Kafka + stream processing for analytics, redirect servers in several regions with regional caches, abuse scanning on createGlobal latency, regulations, abuse at scale

Writes are only ~1,160/s even at the top. The redirect path is the bottleneck at every stage, so every stage adds read capacity: cache first, then replicas, then shards and regions.

🧰 Tools you'll actually use

Redis (cache, plus INCR for counters), PostgreSQL or DynamoDB / Cassandra for the links table, Kafka (or AWS Kinesis, Google Pub/Sub) for click events, and libraries like Sqids for short, non-sequential-looking IDs. Base62 plus a counter range in Python:

import redis
ALPHA = "0123456789abcdefghijklmnopqrstuvwxyzABCDEFGHIJKLMNOPQRSTUVWXYZ"
r = redis.Redis()

def base62(n):
    s = ""
    while n:
        n, rem = divmod(n, 62)
        s = ALPHA[rem] + s
    return s or "0"

def next_range(size=1000):           # each server grabs 1,000 ids at a time
    end = r.incrby("link:counter", size) # atomic, so ranges never overlap
    return range(end - size + 1, end + 1)

print(base62(125), base62(1_000_000))    # 21 4c92
-- the links table: the primary key makes "insert if absent" safe
CREATE TABLE links (
  code       varchar(16) PRIMARY KEY,
  long_url   text NOT NULL,
  owner_id   bigint,
  created_at timestamptz DEFAULT now(),
  expires_at timestamptz
);
INSERT INTO links (code, long_url) VALUES ('aZ3k9Qx', 'https://…')
  ON CONFLICT (code) DO NOTHING;   -- 0 rows inserted? pick a new random code and retry

🚀 Startup vs big tech

Founding engineer (0 → 1)

One Postgres table with a unique constraint and random 7-character codes. 302 redirects. A clicks table, or better, count clicks in Redis and flush every minute. Put the redirect servers behind a CDN-friendly domain. A weekend of work; spend the rest of the time on abuse prevention, because a public shortener gets abused fast.

Big tech (1 → 100)

Multi-region redirect fleets with local caches, a replicated key-value store, click streams feeding a data warehouse, malware and phishing scanning on create, legal takedown tooling, and a durability promise measured in decades (the goo.gl story). The redirect has an SLO (service level objective, Lesson 0.5) of its own.

🎤 Interview angle

What's evaluated: a clean estimate that justifies 7 characters, a reasoned ID scheme (with collision handling), a fast cached read path, and knowing 301 vs 302.

  • Common mistakes: hashing and truncating without handling collisions; a single global counter with no plan for its failure; writing analytics synchronously in the redirect; forgetting abuse and expiry.
  • Likely follow-ups: “How do you make codes unguessable?”, “What if the same long URL is submitted twice?”, “The cache cluster restarts at peak: what happens?”, “How would you serve users in Asia and Europe with low latency?”, “How do you stop phishing links?”
🏭 In the real world
Snowflake: IDs without coordination 🏢 Twitter · 2010 Snowflake (GitHub, 2010 README)

How: each ID is 64 bits: 41 bits of milliseconds since a custom epoch (“gives us 69 years”), a 10-bit machine ID (up to 1,024 machines) and a 12-bit sequence (4,096 per machine per millisecond). Requirements listed: at least 10k IDs per second per process, roughly time-ordered, uncoordinated.

Why this method: Twitter was moving from MySQL to Cassandra, which has no auto-increment, and machines in several datacenters had to create IDs without talking to each other.

IDs generated inside the database 🏢 Instagram · 2012 Sharding & IDs at Instagram

How: 41 bits of time, 13 bits of logical shard ID and a 10-bit sequence, computed by a PL/pgSQL function inside each Postgres shard, so 1,024 IDs per shard per millisecond. The post compares UUIDs, ticket servers and Snowflake first.

Why this method: no extra ID service to run; the ID itself says which shard holds the row, and IDs sort by time.

Snowflake IDs as a sort key 🏢 Discord · 2017 How Discord Stores Billions of Messages

How: “every ID on Discord is actually a Snowflake (chronologically sortable)”, so the message table's key became (channel_id, message_id) and range scans by time come for free.

Why this method: two messages can share a timestamp; a time-ordered unique ID can't collide and still sorts like one.

What 301 and 302 promise 🧰 Web standard RFC 9110: HTTP Semantics, §15.4

How: 301 means the resource “has been assigned a new permanent URI” and is heuristically cacheable; 302 means it “resides temporarily under a different URI”, so clients keep using the original link.

Why this method: the status code is a promise to every browser and cache on the internet. Pick the one whose promise you can keep.

Shutting down a shortener 🏢 Google · 2018–2025 Google URL Shortener links will no longer be available [updated]

How: new links stopped in 2018. Inactive links were first redirected to a warning page, and in 2025 only those were deactivated; links that still redirect without a message keep working.

Why this method: you can turn off creation, but links live in documents and printed media forever. Durability is a product promise.

🤯 Fun fact · same 41 bits, different years

Twitter's README says its 41-bit millisecond timestamp “gives us 69 years”. Instagram's post says its 41 bits give “41 years”. Do the math: 241 ms ÷ (1000 × 86,400 × 365.25) ≈ 69.7 years. Twitter is right. Even good engineering blogs have typos: always check the numbers yourself.

Check yourself

1. You expect 300 billion links over the service's lifetime. How many base62 characters do the codes need?
626 ≈ 56.8 billion is too few. 627 ≈ 3.5 trillion fits 300 billion with room to spare (fewer collisions for random codes). 11 is what a 64-bit Snowflake ID needs, which is why those aren't used directly.
2. Marketing wants every click counted, and link owners can change a link's target later. Which redirect?
A 301 is heuristically cacheable, so repeat clicks may never reach you (missed analytics) and old targets can stick. A 302 says “temporary”: each click comes back, so you can count it and change it.
3. You truncate a hash to 7 base62 characters (3.5 trillion codes) and store 1 million links. Chance of at least one collision?
Birthday maths: 1 − e−n²/2N = 1 − e−(106)²/(2 × 3.5×1012) ≈ 1 − e−0.14 ≈ 13%. The naive guess n/N (0.00003%) ignores that every pair can collide. Always check and retry.
📝 TL;DR
  • 100M links/day → ~1,160 writes/s, ~116k redirects/s, 365B links and ~183 TB over 10 years; 7 base62 characters.
  • Code generation: counter ranges + base62 (short, guessable) or random/hash + conditional insert (unguessable, must handle birthday collisions).
  • The redirect path is everything: cache-aside Redis in front of a store sharded by code; 302 if you count clicks or allow edits.
  • Analytics go async through Kafka and get aggregated; expiry is checked lazily on read; abuse prevention is part of the design.
