Phase 2 · Lesson 2

Indexes & query performance (B-trees, LSM trees)

An index turns “read every row” into “walk down a small tree”. It's the cheapest, biggest performance win in most systems, and every index you add makes every write a little more expensive.

🧰 You'll need (quick reminders)
  • Memory is far faster than SSD, and SSD far faster than spinning disk (Lesson 0.3).
  • Tables, rows and the access-patterns-first mindset (Lesson 2.1).
  • p99 = the latency 99% of requests beat (Lesson 0.3).
🎯 Hook

In 2016 Uber explained why it moved core data from Postgres to MySQL. One reason was write amplification: one logical change turning into many physical writes. In Postgres as Uber described it, a table had 12 indexes, and an update to a field covered by just one of them still had to be written into all 12, because the new version of the row lived at a new physical address. Every extra write also travelled over replication to other servers.

Indexes are why your queries take a millisecond instead of a second. They're also a bill you pay on every write. This lesson is about getting the first without being surprised by the second.

Numbers first: find one user among 10 million

SELECT * FROM users WHERE email = 'ana@example.com' on a table of 10,000,000 rows. Typical numbers: about 100 rows fit in one 8 KB page (Postgres stores tables and indexes in pages of usually 8 kB), and a B-tree page holds about 300 keys.

💡 Big idea An index is a second copy of some columns, kept sorted, with a pointer back to each row. Sorting is what lets the database jump straight to the right place. Keeping that copy sorted is the cost you pay on every insert, update and delete.
🧠 Analogy: the index at the back of a book

To find “replication” in a 600-page book you don't read every page. You flip to the index, find the word in alphabetical order, and jump to page 213. A phone book sorted by (last name, first name) is a composite index: great for “Smith, Ana”, useless for “everyone named Ana”. And every time the author adds a page, someone has to update the index too.

How a B-tree finds a row

A B-tree (balanced tree) is the default index in Postgres, MySQL and most relational databases. The root page holds a few hundred keys that split the key space into ranges. Each range points to a child page that splits it further, down to the leaf pages, which hold every key with a pointer to its row. The tree stays balanced: every leaf is the same distance from the root.

Composite indexes: column order matters

A composite index covers several columns, like (user_id, status, created_at). It's sorted by the first column, then by the second within each first value, and so on, exactly like a phone book.

The rule from the Postgres docs: the index is most efficient with conditions on the leading (leftmost) columns. Equality conditions on leading columns, plus at most one range condition on the next column, narrow the part of the index that's read. This is the leftmost-prefix rule.

Postgres 18 added a “skip scan” that can sometimes use an index whose first column has no condition, when that column has few distinct values. Treat it as a bonus, not a design rule.

✏️ Worked example: what do indexes cost on writes?

An events table takes 2,000 inserts per second and has 5 indexes.

  • Each insert writes the row once, plus one entry into each index: 1 + 5 = 6 structures touched.
  • Per second: 2,000 × 6 = 12,000 sorted inserts, each into a different place in a different tree. Those trees also need memory to stay fast.
  • Dropping two indexes nobody queries (Postgres tracks this: idx_scan = 0 in pg_stat_user_indexes) cuts that to 2,000 × 4 = 8,000, a third less work.

Rule of thumb: index the columns your hot queries filter, join and sort on. Every other index is a cost with no benefit.

When writes dominate: LSM trees

B-trees update pages in place: an insert finds its leaf and rewrites that page. With heavy random writes, that's a lot of scattered I/O. LSM trees (log-structured merge trees) flip it around. They're used by Cassandra, ScyllaDB, RocksDB, LevelDB and HBase:

  1. Append the write to a write-ahead log (WAL, Cassandra calls it the commit log) on disk, so it survives a crash.
  2. Insert it into the memtable, a sorted structure in memory.
  3. When the memtable is full, write it out in one sequential pass as an immutable, sorted file: an SSTable (sorted string table).
  4. In the background, compaction merges SSTables, dropping overwritten and deleted values.

Writes become cheap and sequential. The price: data is rewritten several times by compaction (write amplification again), and a read may have to check several SSTables. A Bloom filter per SSTable (a tiny structure that answers “definitely not here” or “maybe here”) lets reads skip most files.

With compaction on, the file count stays at 4 or fewer and a read for an existing key checks about one file, but every key gets written to disk about 4 times (log, flush, merges). Turn compaction off and write 20,000 keys: write amplification halves to about 2×, files pile up to 19, and with Bloom filters also off an average read checks about 14 of them. Bloom filters rescue most of that, which is why LSM stores use them. Discord's Cassandra cluster suffered from exactly this: it was “prone to falling behind on compactions”.

🧰 Tools you'll actually use

EXPLAIN ANALYZE runs a query and prints the plan the database chose with real timings. It's the first thing to run on a slow query. In MySQL, EXPLAIN / EXPLAIN ANALYZE; in MongoDB, .explain("executionStats"). Output below is illustrative; your numbers will differ.

EXPLAIN ANALYZE SELECT * FROM users WHERE email = 'ana@example.com';
--  Seq Scan on users  (actual time=0.03..812.55 rows=1 loops=1)
--    Filter: (email = 'ana@example.com')
--    Rows Removed by Filter: 9999999          <- read everything to find one row

CREATE INDEX CONCURRENTLY users_email_idx ON users (email);  -- doesn't block writes while building

--  Index Scan using users_email_idx on users  (actual time=0.04..0.04 rows=1 loops=1)
--    Index Cond: (email = 'ana@example.com')

CREATE INDEX users_email_lower ON users (lower(email));          -- expression index
CREATE INDEX orders_user_created ON orders (user_id, created_at) INCLUDE (total); -- covering

-- indexes that are never used: candidates to drop
SELECT indexrelname, idx_scan FROM pg_stat_user_indexes WHERE idx_scan = 0;

Why CONCURRENTLY: a normal CREATE INDEX locks out writes (not reads) until it's done, which on a big table can mean minutes of failed writes. With CONCURRENTLY, Postgres scans the table twice and waits for running transactions, so it takes longer but the app keeps writing. LSM stores to know: RocksDB (an embedded library), Cassandra/ScyllaDB (nodetool compactionstats shows compaction backlog).

Try it locally: start Postgres with docker run -e POSTGRES_PASSWORD=dev -p 5432:5432 postgres, fill a table with INSERT INTO t SELECT g, md5(g::text) FROM generate_series(1, 1000000) g; and compare EXPLAIN ANALYZE before and after CREATE INDEX.

⚖️ Trade-offs
✅ Add an index when…❌ Think twice when…
A hot query filters, joins or sorts on the columnThe column has few distinct values and queries match a big share of rows (a boolean, a status with 3 values on its own)
The query returns a small fraction of the tableThe table is tiny (a few thousand rows): a scan is already fast
Reads far outnumber writesThe table is write-heavy and nobody reads by that column
A composite or covering index can serve a top query entirelyYou'd be adding the 10th index “just in case”: each one slows writes and needs memory

B-tree or LSM? Read-heavy with complex queries: B-tree (the relational default). Massive write rates of simple key-based data: LSM. Most teams don't choose this directly; they choose the database, and it comes with one.

🚀 Startup vs big tech

Founding engineer (0 → 1)

Most early “the database is slow” problems are one missing index. Turn on slow-query logging (log_min_duration_statement in Postgres), run EXPLAIN ANALYZE on the worst offenders, add the index CONCURRENTLY. That's often a bigger win than any cache (Lesson 1.3).

Big tech (1 → 100)

Index changes go through review like code: estimated build time, write cost, memory. Online schema-change tools build indexes on huge tables without locking. Write-heavy services choose LSM-based stores and tune compaction; teams watch compaction backlog and p99 read latency (Lesson 6.3).

🎤 Interview angle

When you draw a database in a design, say which indexes it has and why. A senior answer covers:

  • The key and indexes for each hot query, including composite column order (equality columns first, then the range or sort column).
  • The write cost: how many indexes per table, and whether the write rate can afford them.
  • For write-heavy data, why an LSM-based store fits, and what compaction costs.

Common follow-ups: “Your query has ORDER BY created_at DESC LIMIT 20, which index serves it?” “How would you add an index to a 2 TB table without downtime?”

🏭 In the real world
When the index stops fitting in RAM 🏢 Discord · 2017 How Discord Stores Billions of Messages

How: messages lived in MongoDB with one compound index on channel_id and created_at. Around 100 million stored messages, the data and the index no longer fit in RAM and latency became unpredictable.

Why this method: the compound index matched the query perfectly (“messages in this channel, by time”). What broke was size: an index has to live mostly in memory to be fast. That pushed Discord toward a store that spreads data across machines.

The write cost of indexes 🏢 Uber · 2016 Why Uber Engineering Switched from Postgres to MySQL

How: the post walks through how Postgres stored rows and indexes at the time: indexes pointed at a row's physical location, so a new row version meant new entries in every index, which then flowed into replication as well.

Why this method: for Uber's update-heavy tables with many indexes, that amplification mattered more than Postgres's other strengths. It's a good read on why storage internals change architecture decisions.

An LSM engine as a library 🧰 Open source · Meta RocksDB Overview

How: RocksDB's three building blocks are the memtable, SST files and the log file (WAL). A full memtable is flushed to a sorted SST file; multi-threaded compaction removes overwritten and deleted keys. It started as a fork of LevelDB.

Why this method: embedding a fast write-optimized engine lets other databases reuse it instead of writing their own storage layer.

The LSM write path, documented 🧰 Open source · Apache Cassandra Cassandra storage engine

How: each write goes to the commit log, then the memtable, which is flushed to immutable SSTables; compaction merges them. The docs say plainly that every write is rewritten multiple times, which they call write amplification.

Why this method: turning random writes into sequential ones is what lets Cassandra accept very high write rates per node.

Indexes that don't block writes 🧰 Open source · PostgreSQL CREATE INDEX (Postgres docs)

How: CONCURRENTLY builds an index without locks that block inserts, updates and deletes, at the cost of two table scans and more total time.

Why this method: on a live production table, a slower build that keeps the app writing beats a fast build that causes an outage.

🤯 Fun fact · four levels for eight billion rows

With about 300 keys per page, a B-tree 4 levels deep can index 300⁴ ≈ 8.1 billion rows, and the top levels are small enough to stay in memory. So finding one row among billions usually costs one or two actual disk reads. That's why indexed lookups feel instant on enormous tables, until the index itself no longer fits in RAM.

🌉 How it connects

Indexes are a kind of cache you never have to invalidate yourself (Lesson 1.3). When one machine can't hold the index any more, you shard (Lesson 2.4), and each shard keeps its own smaller index. Search engines are built on a different index, the inverted index, and vector databases on approximate nearest-neighbour indexes (Lesson 2.7). Prometheus's storage engine (Lesson 6.3) uses the same write-ahead-log-plus-immutable-blocks idea as an LSM tree.

Check yourself

1. A table has 1 billion rows and its B-tree index holds about 500 keys per page. Roughly how many pages does one lookup by key read?
log₅₀₀(1,000,000,000) ≈ 3.3, so the tree is 4 levels deep, plus one page for the row itself: about 5. The top levels are usually cached, so only one or two of those are real disk reads.
2. You have an index on (user_id, created_at). Which query can't use it to narrow the search?
The index is sorted by user_id first. Without a condition on the leading column, the dates you want are scattered across every user's section of the index (leftmost-prefix rule). If this query matters, add a separate index on created_at.
3. An ingestion table takes 30,000 inserts per second and has 9 indexes. Inserts are slow. What's the best first step?
Each insert writes the row plus 9 index entries. Indexes with idx_scan = 0 are pure cost. A cache helps reads, not writes. If the write rate keeps growing, an LSM-based store or sharding (Lesson 2.4) is the next step.
📝 TL;DR
  • An index is a sorted copy of columns: lookups cost about logf(N) pages instead of N ÷ rows-per-page.
  • Composite indexes follow the leftmost-prefix rule: equality columns first, then one range or sort column. Covering indexes (INCLUDE) skip the table entirely.
  • Every index costs every write. Drop unused ones; build new ones with CREATE INDEX CONCURRENTLY; check plans with EXPLAIN ANALYZE.
  • LSM trees (memtable → SSTables → compaction) make writes cheap and sequential, at the price of compaction work and multi-file reads.
