Phase 2 · Lesson 7

Object storage, search, time-series & vector stores

Some data has a shape your main database handles badly: huge files, free-text search, millions of metrics per second, “find things like this”. Specialized stores do one of these jobs far better, and most large systems run several next to their main database.

🧰 You'll need (quick reminders)
  • An index is a sorted structure that avoids reading everything; LSM trees turn writes into sequential appends (Lesson 2.2).
  • Big data is split into shards with replicas (Lessons 2.3 and 2.4).
  • A CDN caches files close to users (Lesson 1.4).
🎯 Hook

Amazon S3 is designed to exceed 99.999999999% (“11 nines”) durability, and by default stores data redundantly across at least 3 Availability Zones (separate datacenters in a region).

What does 11 nines mean? Store 10 million files and the expected loss is 10,000,000 × 0.00000000001 = 0.0001 files a year: one file every 10,000 years. You couldn't build that yourself with a few servers and RAID. It's why nearly every company stores its photos, videos, backups and logs in object storage instead of in a database.

The same pattern repeats for every specialized store: the main database keeps the source of truth for small structured records; a specialized store holds the big, searchable or fast-changing part.

💡 Big idea Pick storage by the shape of the question. “Give me file X” → object storage. “Which documents mention these words, best first?” → a search engine's inverted index. “What was CPU every 15 s for a week?” → a time-series database. “What's most similar to this?” → a vector index. Each one is built around one question.
🧠 Analogy: a city's specialist buildings

A town hall (your relational database) keeps the official records. But you don't store furniture in the town hall: there's a warehouse (object storage). You don't find a book by walking the shelves: the library has a catalog by subject and word (search). The weather station logs a reading every minute in a compact notebook (time-series). And a perfume shop can find “something that smells like this” (vector search). Each building is bad at the others' jobs.

Object storage: files at any scale

Object storage (Amazon S3, Google Cloud Storage, Azure Blob Storage, Cloudflare R2, MinIO to self-host) stores objects: a blob of bytes plus metadata, under a key like photos/u42/2025/beach.jpg inside a bucket. You read and write over HTTP. You don't edit an object in place; you replace it.

  • Big files: S3 objects can be very large, but a single PUT is limited to 5 GB; for objects over about 100 MB AWS suggests multipart upload (upload parts in parallel, then combine).
  • S3 gives strong read-after-write consistency: once a write succeeds, reads return the new object.
  • Presigned URLs let a browser upload or download directly, without your servers in the middle and without AWS credentials on the client. Your API signs a URL that's valid for one object, one action and a limited time (up to 7 days, less if it was signed with temporary credentials).

Search: the inverted index

A B-tree on a description column can find “descriptions starting with ‘red’” but not “descriptions containing ‘red’ and ‘shoes’, best match first”. LIKE '%red%' scans every row. Search engines (Elasticsearch, OpenSearch, Apache Solr, all built on the Lucene library; also Meilisearch, Typesense, and Postgres full-text search for smaller needs) use an inverted index: a map from each word to the list of documents containing it (a posting list).

  • An analyzer splits text into terms and normalizes them: lowercasing, removing very common words, stemming (“replicas” → “replica”).
  • A query looks up each term's posting list and intersects (AND) or merges (OR) them. Then results are ranked; OpenSearch uses the BM25 algorithm, which favours rare words and documents where they appear often.
  • It's near real-time: Elasticsearch makes new documents searchable within about 1 second by default. Indexes are split into shards with replicas.

Time-series: metrics and events

Metrics are a stream of (series, timestamp, value) samples: cpu{host="web-7"} at 10:00:15 = 0.62. Queries are almost always “this series, this time range, aggregated”. Time-series databases (Prometheus, InfluxDB, TimescaleDB, VictoriaMetrics, and cloud ones like Amazon Timestream) exploit that:

  • Prometheus keeps the newest data in memory, protected by a write-ahead log, and writes immutable two-hour blocks to disk, later compacted into bigger ones (very like an LSM tree, Lesson 2.2).
  • Compression is extreme because consecutive samples are similar: Prometheus averages only 1–2 bytes per sample. Facebook's Gorilla paper reported 16 bytes per point compressed to 1.37 bytes.
  • Prometheus's sizing rule: disk = retention seconds × samples per second × bytes per sample. Default retention is 15 days.
✏️ Worked example: sizing Prometheus

1,000,000 active series, scraped every 15 s.

  • Samples per second: 1,000,000 ÷ 15 ≈ 66,700.
  • 15 days = 1,296,000 s. At 2 bytes per sample: 66,700 × 1,296,000 × 2 ≈ 173 GB. At Gorilla's 1.37 bytes: about 118 GB.
  • Uncompressed at 16 bytes (an 8-byte timestamp + an 8-byte value) it would be about 1.4 TB. Compression is the whole game.

The thing that blows this up is cardinality: a label like user_id turns one series into millions (Lesson 6.3).

Vector search: “find things like this”

An embedding is a list of numbers (say 1,536 of them) produced by a machine-learning model, placed so that similar meanings end up close together. Semantic search, recommendations and RAG (retrieval-augmented generation: fetching relevant text to feed an LLM) all ask the same question: which stored vectors are nearest to this one?

  • Exact search compares against every vector. 10 million vectors × 1,536 dimensions = 15.4 billion multiply-adds per query, over 61 GB of 4-byte floats. Too slow for live traffic.
  • Approximate nearest neighbour (ANN) indexes trade a little recall (the share of true nearest neighbours found) for huge speedups. pgvector, a Postgres extension, offers two: HNSW (a layered graph you walk toward the query; better speed–recall, slower builds, more memory) and IVFFlat (vectors grouped into lists; search only the nearest lists; faster builds, less memory).
  • Dedicated vector databases (Pinecone, Weaviate, Milvus, Qdrant) and search engines (Elasticsearch, OpenSearch) offer the same idea at larger scale.

And graph stores (Neo4j, Amazon Neptune, Facebook's TAO) answer “who's connected to whom, within N hops?”, which is slow as repeated joins in SQL (Lesson 2.1).

-- pgvector: store embeddings next to your data, find the 5 nearest
CREATE EXTENSION vector;
CREATE TABLE docs (id bigserial PRIMARY KEY, body text, embedding vector(1536));
CREATE INDEX ON docs USING hnsw (embedding vector_cosine_ops);
SELECT id, body FROM docs ORDER BY embedding <=> '[0.12, -0.03, ...]' LIMIT 5;

🚀 Startup vs big tech

Founding engineer (0 → 1)

Day one: files go to S3 (or R2) with presigned uploads and a CDN in front. Use Postgres for everything else, including full-text search and pgvector, until a measured need appears. Use managed Prometheus/Grafana for metrics. Every extra store is one more thing to back up, secure and keep in sync.

Big tech (1 → 100)

Dedicated clusters per job: search fed by change-data-capture streams from the main databases (Lesson 3.2), large time-series platforms for metrics, vector indexes for search and recommendations, object storage as the data lake for analytics. Dedicated teams own each one, with SLOs on freshness (how far the copy lags the source).

🎤 Interview angle

Most design problems have a blob, a search box or a metric in them. A senior answer covers:

  • Files: object storage + presigned URLs + CDN, with metadata in the database. Never stream big uploads through app servers without a reason.
  • Search: an inverted index fed from the source of truth, how stale it may be, and what happens if indexing falls behind.
  • Metrics: a time-series store, retention and cardinality.
  • Similarity: embeddings + ANN index, and the recall vs latency trade-off.

Common follow-ups: “How do you keep search in sync with the database?” (change events, or the outbox pattern, Lesson 3.5). “How do you stop people uploading 10 GB files?” (size limits in the presigned policy, then validate after upload).

🏭 In the real world
Photos straight to object storage 🏢 Instagram · 2011 What Powers Instagram

How: the photos themselves went straight to Amazon S3, with CloudFront as the CDN, while Postgres held the structured data.

Why this method: a tiny team could store several terabytes of photos (at the time) without running any storage servers, and keep its databases small.

Inverted index and BM25 🧰 Open source · OpenSearch OpenSearch: intro to concepts

How: the docs show an inverted index mapping each word to the documents it occurs in, and explain that results are ranked with BM25.

Why this method: looking up a few posting lists is vastly cheaper than scanning every document, and BM25 ranks rare, repeated terms higher.

A time-series database on local disk 🧰 Open source · Prometheus Prometheus storage

How: samples are grouped into two-hour blocks; the current block lives in memory, protected by a write-ahead log; blocks are compacted in the background. Average cost: 1–2 bytes per sample.

Why this method: metrics are append-only and read by time range, so immutable, compressed time blocks fit perfectly.

Compressing metrics 12× 🏢 Facebook · 2015 Gorilla: A Fast, Scalable, In-Memory Time Series Database (VLDB)

How: delta-of-delta encoding for timestamps and XOR encoding for floating-point values brought points from 16 bytes to an average of 1.37 bytes.

Why this method: at 12× smaller, recent monitoring data fit in memory, so dashboards and alerts queried RAM instead of disk.

Vectors inside Postgres 🧰 Open source · pgvector pgvector

How: a vector column type with exact search by default, plus HNSW and IVFFlat indexes for approximate search; the README notes that adding an approximate index can change query results.

Why this method: embeddings sit next to the rows they describe, with transactions, joins and backups for free; many teams never need a separate vector database.

🤯 Fun fact · a second is “real time”

Elasticsearch calls its search “near real-time” because new documents become searchable at the next refresh, every second by default, and only on indices that received a search in the last 30 seconds. Writing a document and searching for it in the same millisecond can miss it. It's eventual consistency (Lesson 2.6) hiding in a search box.

🌉 How it connects

Search indexes and caches are kept in sync with the database through change streams and Kafka (Lessons 3.2 and 3.5). Prometheus is the metrics half of observability (Lesson 6.3). Object storage + CDN is the backbone of video streaming (Lesson 7.5). In AI systems, a RAG pipeline is exactly this lesson: documents in object storage, chunks and embeddings in a vector index, metadata in Postgres.

Check yourself

1. You keep 500,000 series, scraped every 30 s, for 30 days, at about 2 bytes per sample. Roughly how much disk?
500,000 ÷ 30 ≈ 16,700 samples/s × 2,592,000 s (30 days) × 2 bytes ≈ 86 GB. Doubling the scrape rate or adding a high-cardinality label is how this quietly turns into terabytes.
2. Users upload videos of up to 2 GB from their phones. How should uploads work?
Direct uploads keep gigabytes of traffic off your servers, and multipart lets big files upload in parallel parts that can be retried individually. The database keeps only the key, owner, size and status.
3. After adding an HNSW index to a pgvector column, a few searches return slightly different neighbours than before. Why?
Without an index, pgvector does exact search (perfect recall). ANN indexes skip most vectors, so they occasionally miss a true neighbour. You can tune the trade-off (for HNSW, hnsw.ef_search) based on measured recall.
📝 TL;DR
  • Files go to object storage (11 nines durability by design), uploaded with presigned URLs and served through a CDN; metadata stays in the database.
  • Search engines use an inverted index (word → documents), analyzers and BM25 ranking; they're near real-time copies of your data.
  • Time-series stores compress samples to 1–2 bytes; size them as retention × samples/s × bytes/sample, and watch cardinality.
  • Vector search finds nearest embeddings; ANN indexes (HNSW, IVFFlat) trade recall for speed. Start with Postgres extensions until scale demands more.
