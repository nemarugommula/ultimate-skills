Phase 2 · Lesson 4

Sharding & consistent hashing

Split one database into many smaller ones, each holding a slice of the data, so writes and storage can grow past one machine. It's the most powerful scaling move for data, and the hardest to undo.

🧰 You'll need (quick reminders)
  • Replicas spread reads but every write still goes to one leader (Lesson 2.3).
  • An index has to fit mostly in memory to stay fast (Lesson 2.2).
  • A hash function turns any key into a number that looks random, the same way every time (like md5("user42")).
🎯 Hook

In 2021 Notion took its app down for five minutes of scheduled maintenance. Behind that was months of work: splitting a single Postgres database into 480 logical shards spread over 32 physical databases, 15 shards each, with all of a workspace's data kept together.

Why 480? Because it divides evenly by 2, 3, 4, 5, 6, 8, 10, 12, 15, 16, 20, 24, 30, 32, 40, 48, 60, 80, 96, 120, 160 and 240, so they could later move to many different numbers of machines and keep shards evenly spread. Sharding is full of decisions like that, made early, that are expensive to change.

Numbers first: when one leader isn't enough

A typical growing product: 40 TB of data, 40,000 writes/s at peak. Suppose one primary comfortably handles about 5,000 writes/s and about 2 TB before backups, index builds and vacuums get painful. (Notion's own limits were 500 GB per table and 10 TB per physical database.)

Replicas can't fix either row: each replica stores all the data and replays every write. Only splitting the data helps.

💡 Big idea Sharding (also called partitioning) gives each machine a slice of the rows, chosen by a shard key. Pick the key so that the hot queries need only one shard and the load spreads evenly. Get the key wrong and you get hot shards, or queries that must ask every shard.
🧠 Analogy: the post office sorting room

One clerk can't sort a city's mail, so you hire 26 and give each a letter of the alphabet by surname. That's range sharding. It's lovely until you notice that far more people are named Smith than Xu, and the “S” clerk drowns (a hot shard). So you sort by a scrambled code instead (hash sharding): even work for everyone, but “all surnames from Sa to Sm” now means asking every clerk. And if you hire a 27th clerk, almost everyone's pile has to be redealt, unless you planned for it (consistent hashing).

Choosing a shard key

StrategyHow it routesGood atBad at
Hash of the keyshard = hash(user_id) mod N, or a ring (below)Even spread of data and loadRange queries (“all orders this week”) hit every shard
Range of the keyUsers A–F on shard 1, G–M on shard 2… or by dateRange scans stay on one shardHot spots: sequential IDs and timestamps pile new writes onto the last shard
Directory (lookup table)A small service maps key → shardMove any customer anywhere; isolate a giant customerOne more lookup and one more system to keep available

Good shard keys come from your access patterns (Lesson 2.1). Notion and Slack shard by workspace, because almost every query is inside one workspace. Instagram shards by user. Discord partitions messages by channel and time bucket.

What you give up: joins and transactions across shards. Notion notes that transaction guarantees apply only within each database, so a change that touches two shards can half-succeed. Queries without the shard key become scatter-gather: ask every shard and merge.

Resharding, and why mod N hurts

With shard = hash(key) mod N, changing N changes almost every answer. Going from 4 to 5 shards, a key stays put only if h mod 4 = h mod 5, which is true for 1 key in 5. So 80% of the data has to move. For a cache cluster that's 80% misses at once (Lesson 1.3); for a database it's moving 80% of your terabytes while serving traffic.

Consistent hashing fixes this. Put both servers and keys on a ring of hash values (0 to 2³²). Each key belongs to the first server clockwise from it. Add a server and it only takes keys from its neighbour on the ring: about 1/N of the keys move, the minimum possible. To even out the slices, each physical server gets many points on the ring, called virtual nodes. The Dynamo paper uses this, and notes you can give bigger machines more virtual nodes.

Things to try: with 1 virtual node per server, the slices are wildly uneven; the busiest server often holds twice its fair share. Slide virtual nodes to 100 or more and the busiest server comes within about 10–20% of average. Now, with 50 or more virtual nodes, add a 5th server: consistent hashing moves about 20% of keys (with 1 virtual node it depends on where the new point happens to land). Switch to mod N and do the same: about 80% move.

✏️ Worked example: logical shards, the practical trick

Many companies skip the ring and use a fixed, large number of logical shards mapped to fewer machines. Instagram used several thousand logical shards in Postgres; Notion used 480.

  • Route a key: logical = user_id mod 2000. Instagram's own example: user 31341 → 31341 mod 2000 = shard 1341.
  • Map logical to physical with a small table: shards 0–124 on machine 1, 125–249 on machine 2… 2,000 shards on 16 machines is 125 per machine.
  • To grow to 32 machines, move whole logical shards (62 or 63 per machine), with no rehashing of any key. Each move is copy, catch up, switch: the same as building a replica (Lesson 2.3).

The logical-shard count is the one number you can't change cheaply, so pick it big, and (Notion's tip) with lots of divisors.

🔥 Resharding pain · Google's ad backend

The Spanner paper (2012) describes F1, Google's advertising backend, which had been on a MySQL database that was manually sharded many ways. Resharding that revenue-critical database as it grew was extremely costly: the last resharding took over two years of intense effort, with coordination and testing across dozens of teams. One reason F1 moved to Spanner was that Spanner reshards data across machines automatically.

🧰 Tools you'll actually use

Sharding layers for existing databases: Vitess for MySQL (YouTube, Slack; managed as PlanetScale) and Citus for Postgres. Databases that shard themselves: DynamoDB, Cassandra/ScyllaDB, MongoDB (sharded clusters), and distributed SQL like Spanner, CockroachDB and TiDB, which split ranges automatically.

-- Citus (Postgres extension): shard a table by user_id
SELECT create_distributed_table('orders', 'user_id');
SELECT * FROM orders WHERE user_id = 42;          -- routed to one shard
SELECT count(*) FROM orders WHERE created_at > now() - interval '1 hour';  -- fans out to all

// Vitess VSchema: shard orders by a hash of user_id
{ "sharded": true,
  "vindexes": { "hash": { "type": "hash" } },
  "tables": { "orders": { "column_vindexes": [ { "column": "user_id", "name": "hash" } ] } } }

# DynamoDB: the partition key IS the shard key
aws dynamodb create-table --table-name Orders \
  --attribute-definitions AttributeName=user_id,AttributeType=S AttributeName=order_id,AttributeType=S \
  --key-schema AttributeName=user_id,KeyType=HASH AttributeName=order_id,KeyType=RANGE \
  --billing-mode PAY_PER_REQUEST

Try it locally: docker run -p 8000:8000 amazon/dynamodb-local and add --endpoint-url http://localhost:8000 to the command above.

⚖️ Trade-offs
✅ Shard when…❌ Don't shard (yet) when…
Writes or data size exceed what one primary can take, with headroomA bigger machine, better indexes, or archiving old rows would do (vertical scaling, Lesson 1.1)
A natural shard key exists: tenant, workspace, userYour hot queries join across many users (a social graph, global leaderboards)
You can live without cross-shard transactions, or handle them with sagas (Lesson 3.5)The team is small and the cost of operating 32 databases would dominate

Costs you sign up for: cross-shard queries, rebalancing, per-shard backups and migrations, IDs that must be unique across shards (Instagram packed time, shard and a sequence into one 64-bit ID), and uneven tenants.

🚀 Startup vs big tech

Founding engineer (0 → 1)

Don't shard. One Postgres primary with replicas goes a very long way. But put a tenant_id (or workspace_id) on every table, include it in your keys and queries, and avoid global auto-increment IDs. That makes sharding a project instead of a rewrite when the day comes.

Big tech (1 → 100)

Many logical shards on fewer machines, a routing layer (Vitess, an in-house proxy, or a directory service), automatic shard moves, hot-tenant isolation (a giant customer gets its own shard), and IDs that carry the shard number. Or a database that shards itself, so teams never write routing code.

🎤 Interview angle

Interviewers want the shard key and its consequences, not the word “shard”. A senior answer covers:

  • Why sharding is needed, with numbers (writes/s or TB beyond one machine).
  • The shard key, which queries stay on one shard and which fan out.
  • Hot keys (a celebrity, a giant tenant) and how you'd handle them.
  • How you add capacity: consistent hashing or logical shards, and moving data online.

Common follow-ups: “How do you generate unique IDs across shards?” “How do you query by something other than the shard key?” (a secondary index table keyed by that field, or a search index fed by change events).

🏭 In the real world
Logical shards and IDs with the shard inside 🏢 Instagram · 2012 Sharding & IDs at Instagram

How: several thousand logical shards mapped in code to far fewer physical Postgres servers. Each 64-bit ID holds 41 bits of milliseconds since a custom epoch, 13 bits of logical shard ID and 10 bits of a per-shard sequence.

Why this method: moving logical shards is easy, and every ID says where its row lives and sorts by time, with no central ID service.

Sharding by workspace 🏢 Notion · 2021 Herding elephants: sharding Postgres at Notion

How: 480 logical shards (Postgres schemas) over 32 physical databases, partitioned by workspace ID, with all tables reachable from a block sharded together.

Why this method: almost every query lives inside one workspace, so it stays on one shard, and related rows stay together for transactions.

From hand-rolled shards to Vitess 🏢 Slack · 2020 Scaling Datastores at Slack with Vitess

How: Slack's MySQL shards were partitioned by workspace ID, with a metadata cluster to look up which shard holds a workspace. It migrated to Vitess from 2017; by the post, Vitess served 99% of its query load.

Why this method: a sharding layer handles routing and resharding in one place, instead of in every service's code.

The ring with virtual nodes 🏢 Amazon · 2007 Dynamo (SOSP 2007)

How: Dynamo partitions keys with consistent hashing on a ring, and each node owns many virtual nodes; the count can follow a machine's capacity.

Why this method: adding or losing a node only moves its neighbours' keys, and virtual nodes spread that work over many machines instead of one.

A database that reshards itself 🏢 Google · 2012 Spanner (OSDI 2012)

How: Spanner automatically reshards data across machines as the data or the number of servers changes, and migrates data across machines, even across datacenters, to balance load and respond to failures.

Why this method: after a manual MySQL reshard that took over two years, removing that work entirely was worth a more complex database.

🤯 Fun fact · why it's called a shard

Notion's post says the word is thought to come from the game Ultima Online, whose developers needed a story for running several copies of the game world on separate servers: the world had been shattered into shards.

🌉 How it connects

Each shard is usually replicated (Lesson 2.3). Cross-shard updates need sagas or two-phase commit (Lesson 3.5). Kafka partitions topics by key for the same reasons (Lesson 3.2), and cache clusters use consistent hashing so adding a node doesn't empty the cache (Lesson 1.3). The URL shortener and chat designs both start with “what's the shard key?” (Lessons 7.2 and 7.4).

Check yourself

1. A cache cluster uses hash(key) mod N and grows from 9 to 10 nodes. About what share of keys now map to a different node?
A key stays only if h mod 9 = h mod 10, true for about 1 in 10 keys, so ~90% move and the cache is effectively cold. With consistent hashing only about 1/10 move.
2. A B2B app (thousands of companies, each with users, projects and tasks) must shard. What's the best shard key?
Almost every query is “within this company”, so tenant ID keeps them on one shard and keeps related rows together for transactions. Task ID spreads evenly but turns every project page into a scatter-gather. Watch for giant tenants and give them their own shard.
3. Orders are hash-sharded by user_id. One celebrity seller generates 30% of all writes and their shard is overloaded. What helps?
One key always hashes to one place, so more shards don't help it. Splitting (salting) the hot key spreads its writes; reads of that seller then gather from the sub-keys. Big tenants often get their own shard.
📝 TL;DR
  • Shard when writes or data size outgrow one primary; replicas can't help either.
  • The shard key decides everything: keep hot queries on one shard, spread load evenly, and plan for hot keys.
  • mod N moves about N/(N+1) of keys on resize; consistent hashing moves about 1/N; virtual nodes even out the slices.
  • Practical pattern: many logical shards (Instagram thousands, Notion 480) mapped to fewer machines, moved whole.
