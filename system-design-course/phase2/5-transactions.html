Phase 2 · Lesson 5

Transactions, ACID & isolation levels

A transaction makes several reads and writes behave like one safe step, even when thousands of requests run at once. At scale, “at once” happens every second, and the gaps between isolation levels turn into real money.

🧰 You'll need (quick reminders)
  • SQL tables and rows (Lesson 2.1); a write goes to a WAL (write-ahead log) first (Lesson 2.2).
  • On a sharded database, a transaction usually covers only one shard (Lesson 2.4).
  • Web servers handle many requests concurrently: at the same time, on different threads or machines (Lesson 1.1).
🎯 Hook

On 2 March 2014, the Flexcoin Bitcoin exchange was attacked through a concurrency bug: by sending thousands of simultaneous transfer requests, the attacker “moved” coins from one account to another until the sending account was overdrawn, before balances were updated, then withdrew them. Every Bitcoin stored at Flexcoin was stolen and the exchange was forced to shut down.

A 2017 study (“ACIDRain”, SIGMOD) then checked 12 popular open-source e-commerce apps, deployed on over 2 million websites, and found 22 similar attacks, like buying one gift card and spending it an unlimited number of times with concurrent checkouts. All 22 worked under the databases' default isolation settings.

Numbers first: the double withdrawal

An account holds $100. Two requests to withdraw $80 arrive 5 ms apart (a double-click, or an attacker). Each request runs the obvious code: read the balance, check it's enough, write the new balance.

This is a lost update: request 2's write silently overwrote request 1's. Wrapping each request in BEGIN … COMMIT does not fix it at the default isolation level of Postgres. The two requests are each correct alone; it's their overlap that's wrong.

💡 Big idea A transaction promises to behave as if it ran alone. How strictly the database keeps that promise is the isolation level. Weaker levels are faster and allow certain anomalies; you must know which ones, and protect the few places (money, stock, seats) where they hurt.

🧠 Analogy: the shared whiteboard

Two people update a shared whiteboard tally. If both glance at “12”, both walk off to think, and both come back and write “13”, one update vanished. You can take the marker before you look and keep it until you're done (pessimistic locking). Or you can write “13, if it still says 12” and start over if it doesn't (optimistic). Or the board itself can refuse anything that wouldn't have happened in some one-at-a-time order (serializable).

Isolation levels and the anomalies they allow

Most databases use MVCC (multi-version concurrency control): a write creates a new version of the row instead of overwriting it, so readers see a consistent snapshot without blocking writers. Locks are still used between writers. The SQL standard defines four levels; here's what each allows in Postgres:

Two things to remember. Stronger levels don't make the conflict disappear: they abort one transaction with a serialization error, and your code must retry it. And level names differ between databases: Jepsen's 2020 analysis showed that Postgres's “repeatable read” is really snapshot isolation, which allows write skew.

Write skew example: a hospital rule says at least one doctor must be on call. Alice and Bob are both on call and both feel ill. Each transaction checks “is someone else on call?” (yes), and each takes itself off. Each change was safe alone; together they leave zero doctors. Only serializable isolation, or an explicit lock, catches this.

Pessimistic vs optimistic concurrency

Two families of fixes for read-modify-write:

  • Pessimistic locking: lock the row when you read it (SELECT … FOR UPDATE), so others wait. No wasted work, but waiting, and with several rows a risk of deadlock (two transactions each waiting for the other's lock; Postgres detects it and aborts one).
  • Optimistic concurrency control (OCC): don't lock; keep a version number on the row, and update only WHERE version = the one I read. If zero rows changed, someone beat you: re-read and retry. No waiting, but conflicts waste the work done so far.
✏️ Worked example: how hot can one row get?

A flash sale: every purchase decrements one row, stock for a single product.

  • With a row lock held for 5 ms per transaction (read, check, write, commit), the row can do at most 1,000 ÷ 5 = 200 purchases per second, however many servers you add.
  • If 2,000 buyers per second arrive, the queue grows by 1,800 per second; after 10 s, the last buyer waits about 18,000 ÷ 200 = 90 s.
  • Shrink the lock time to 1 ms with a single atomic statement (UPDATE … SET stock = stock - 1 WHERE stock > 0): 1,000 per second. Or split the stock into 10 rows of 100 units each (like splitting a hot key, Lesson 2.4): about 10× more.

The throughput of a hot row is roughly 1 ÷ lock time. That's the number to estimate whenever many users update the same thing.

Things to try: with 1,000 rows, optimistic edges ahead: about 2% of attempts conflict and it skips the lock overhead. At 100 rows with 64 clients, about 40% of optimistic attempts conflict and locks win. Drop to 1 row with 16 clients: both cap near 1,000 ÷ 5.5 ≈ 180 commits/s, but optimistic throws away over 90% of its work and its p99 latency (the slowest 1% of transactions) passes a second, because some clients keep losing the race. That's the rule of thumb: optimistic for low contention, pessimistic (or a single atomic statement) for hot rows.

🧰 Tools you'll actually use

Every relational database (Postgres, MySQL, SQL Server, Oracle) and distributed SQL (Spanner, CockroachDB) gives you these. DynamoDB offers conditional writes and transactions; MongoDB has multi-document transactions. Your ORM wraps them: Django select_for_update(), Rails with_lock and the lock_version column for optimistic locking.

-- 1. Simplest and best when it fits: one atomic, conditional statement
UPDATE accounts SET balance = balance - 80
WHERE id = 1 AND balance >= 80;        -- 0 rows updated = insufficient funds

-- 2. Pessimistic: lock the row you're about to change
BEGIN;
SELECT balance FROM accounts WHERE id = 1 FOR UPDATE;   -- others wait here
UPDATE accounts SET balance = 20 WHERE id = 1;
COMMIT;

-- 3. Optimistic: a version column
UPDATE accounts SET balance = 20, version = version + 1
WHERE id = 1 AND version = 7;              -- 0 rows = someone changed it: re-read and retry

-- 4. Let the database check everything; be ready to retry
BEGIN ISOLATION LEVEL SERIALIZABLE;
import psycopg
def run_with_retry(conn, fn, tries=5):
    for attempt in range(tries):
        try:
            with conn.transaction():
                return fn(conn)
        except psycopg.errors.SerializationFailure:   # SQLSTATE 40001: safe to retry
            continue
    raise RuntimeError("too much contention")

Try it locally: open two psql sessions against docker run -e POSTGRES_PASSWORD=dev -p 5432:5432 postgres, run BEGIN ISOLATION LEVEL REPEATABLE READ; in both, and replay the withdrawal by hand. Seeing the 40001 error yourself makes it stick.

🚀 Startup vs big tech

Founding engineer (0 → 1)

Keep money, credits, inventory and bookings in Postgres, inside one transaction, with constraints (CHECK (balance >= 0), unique keys) as a safety net. Use atomic conditional updates wherever you can and FOR UPDATE elsewhere. Add idempotency keys so a retried request can't charge twice (Lesson 3.3).

Big tech (1 → 100)

Data is sharded, so transactions stay within one shard by design (put an account's rows on the same shard). Cross-service work uses sagas and the outbox pattern instead of distributed transactions (Lesson 3.5). Some teams pay for distributed SQL (Spanner, CockroachDB) to get serializable transactions across shards. Isolation bugs are tested for with tools like Jepsen.

🎤 Interview angle

Whenever a design has money, inventory or seats, the interviewer is waiting for you to mention concurrency. A senior answer covers:

  • Where the read-modify-write races are, and which fix you'd use (atomic update, lock, version, serializable).
  • The throughput of hot rows (≈ 1 ÷ lock time) and how you'd split them.
  • Retries: which errors are safe to retry, and idempotency so retries don't double-charge.
  • What happens across shards or services, where a single ACID transaction no longer exists.

Common follow-ups: “Two users book the last seat at the same moment. Walk me through it.” “Why not make everything serializable?”

🏭 In the real world
Concurrency attacks on real stores 📜 Research · SIGMOD 2017 ACIDRain: Concurrency-Related Attacks on Database-Backed Web Applications

How: the authors analysed 12 popular e-commerce apps and found 22 attacks, including the Flexcoin case. 17 of the 22 came from using transactions incorrectly, so even the strongest isolation level wouldn't have stopped them without code changes.

Why this method: the paper's lesson is that isolation levels only help when the whole read-check-write sits inside one correctly used transaction (or uses explicit locks like SELECT … FOR UPDATE).

The isolation levels, as implemented 🧰 Open source · PostgreSQL Postgres: Transaction Isolation

How: Read Committed is the default. Repeatable Read aborts a transaction that tries to modify a row changed since it started; Serializable uses Serializable Snapshot Isolation, which adds checks for anomalies. Apps at those levels must be prepared to retry.

Why this method: MVCC lets readers never block writers; aborting on conflict, instead of locking everything up front, keeps throughput high when conflicts are rare.

Testing isolation claims 🧰 Jepsen · 2020 Jepsen: PostgreSQL 12.3

How: Jepsen's checker (Elle) found that Postgres 12.3's serializable level could occasionally allow a non-serializable anomaly under normal operation (a bug fixed in the next minor release), and that its repeatable read is snapshot isolation.

Why this method: isolation is hard to get right even for mature databases. Generating concurrent histories and checking them against a formal model finds bugs no one would find by reading code.

Optimistic locking in a NoSQL store 🏢 Amazon Web Services DynamoDB: optimistic locking with version number

How: each item carries a version attribute; an update succeeds only if the version on the server hasn't changed since you read it. On a mismatch the update fails and you retry with fresh data.

Why this method: a distributed key-value store can't hold long locks for clients, but a conditional write is cheap and works on every partition.

🤯 Fun fact · even “serializable” needed a patch

Jepsen's PostgreSQL report was done independently and without payment, and a patch for the serializability bug it found was scheduled for the very next minor release. Postgres has one of the most careful concurrency implementations around, and a randomized tester still found a hole. If your design depends on an isolation guarantee, test it under real concurrency.

🌉 How it connects

A transaction is safe on one database; across shards (Lesson 2.4) or services it becomes a distributed transaction, handled with two-phase commit or sagas (Lesson 3.5). Retries need idempotency so they don't apply twice (Lesson 3.3). The payment system design (Lesson 7.7) puts all of this together: ledgers, locks, idempotency keys and reconciliation.

Check yourself

1. Every ticket sale for a concert locks one seats_left row for about 4 ms. What's the most sales per second that row can handle?
One transaction at a time × 4 ms each = 1,000 ÷ 4 = 250 per second, regardless of how many app servers you add. To go faster, shorten the lock (one atomic statement) or split the counter into several rows.
2. Code does SELECT stock, checks it's above 0, then UPDATE … SET stock = :new, inside BEGIN/COMMIT on Postgres defaults. During a sale, stock goes negative. Why?
That's the lost-update anomaly. Fix with UPDATE … SET stock = stock - 1 WHERE stock > 0, or SELECT … FOR UPDATE, or a higher isolation level with retries. A CHECK (stock >= 0) constraint is a good safety net too.
3. Users edit long wiki pages for minutes at a time, and two people rarely edit the same page at once. Which approach fits?
Holding a lock for minutes would block everyone else and leak locks when browsers close. Conflicts are rare, so optimistic concurrency fits: cheap when it succeeds, and a clear “someone else edited this” message when it doesn't.
📝 TL;DR
  • ACID = all-or-nothing, rules hold, transactions don't see each other's half-done work, commits survive crashes.
  • Postgres defaults to read committed, which allows lost updates on read-modify-write. Higher levels abort one transaction; you must retry (SQLSTATE 40001).
  • Fixes, in order of preference: one atomic conditional UPDATE, SELECT … FOR UPDATE, a version column, serializable.
  • A hot row's throughput ≈ 1 ÷ lock time. Optimistic for low contention, pessimistic or atomic for hot rows.
