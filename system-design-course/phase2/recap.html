Recap: data at scale

Seven lessons on choosing, speeding up, copying, splitting and protecting data. Here they are on one page, plus a diagnosis game, a design problem and a boss quiz.

🧾 Cheat sheet

🗂️

2.1 SQL vs NoSQL

top queries × rate → store + key

Relational for joins and transactions; key-value / wide-column for huge known key-based access; denormalize only the hottest reads.

Postgres · MySQL · DynamoDB · Cassandra/ScyllaDB · MongoDB
🌲

2.2 Indexes

pages ≈ logf(N) + 1 vs N ÷ rows/page

Composite indexes follow the leftmost prefix; every index costs every write; LSM trees make writes sequential.

EXPLAIN ANALYZE · CREATE INDEX CONCURRENTLY · RocksDB
🪞

2.3 Replication

lost on failover ≈ write rate × lag

Async is fast but stale; sync costs a round trip. Read-your-writes, fencing against split brain, W + R > N for quorums.

Streaming replication · Patroni · Orchestrator · Cassandra CL
🧩

2.4 Sharding

mod N moves N/(N+1); ring moves ~1/N

The shard key keeps hot queries on one shard and spreads load; watch hot keys; logical shards move whole.

Vitess · Citus · DynamoDB partitions · Spanner
🔒

2.5 Transactions

hot row ≈ 1 ÷ lock time per second

Read committed allows lost updates. Prefer an atomic conditional UPDATE, then FOR UPDATE, a version column, or serializable + retry.

BEGIN ISOLATION LEVEL … · SQLSTATE 40001 · Jepsen
🌍

2.6 CAP & PACELC

strong write ≈ local + RTT to a quorum

During a partition: refuse or diverge. Otherwise: latency or consistency. Choose per operation; plan how AP data merges.

ConsistentRead · LOCAL_QUORUM · writeConcern majority · Spanner
🧰

2.7 Specialized stores

disk = retention × samples/s × bytes

Files to object storage via presigned URLs; search with an inverted index; metrics in a TSDB; similarity with ANN indexes.

S3 · OpenSearch · Prometheus · pgvector
🗣️ Teach it back

Answer out loud, as if an interviewer asked: “Our single Postgres primary is at 90% CPU and the data will triple next year. Walk me through your options, in the order you'd try them, and what each one costs.”

A strong answer: measure first (which queries, reads or writes?), then indexes and query fixes (2.2), a cache for hot reads (1.3), read replicas with read-your-writes (2.3), a bigger machine, archiving old data to object storage (2.7), and only then sharding by a key that keeps hot queries on one shard (2.4), noting that cross-shard transactions disappear (2.5).

🏗️ Design it yourself: the data layer of a photo-sharing app

You're the founding engineer of a photo app that's taking off: 10 million daily active users. Each uploads about one photo every two days (about 2 MB), views about 100 photos a day, and leaves about 10 likes a day. Users follow each other; there's a search box for people and captions. Design the storage: which stores, what keys, how it scales, and what consistency each part needs. Use only Phase 2 ideas, plus caching and CDNs from Phase 1. Try it on paper before opening the answer.

Reveal a strong answer

1. Requirements

  • Upload photos; view a feed of followed users' photos; like; follow; search people and captions.
  • Uploads must never be lost once acknowledged. Feeds may be a few seconds stale. Usernames must be unique.

2. Numbers

  • Uploads: 10M × 0.5 = 5M/day ≈ 58/s average, ~175/s at a 3× peak.
  • Photo bytes: 5M × 2 MB = 10 TB/day ≈ 3.65 PB/year. Object storage, not a database.
  • Photo metadata: ~500 bytes × 5M = 2.5 GB/day ≈ 0.9 TB/year. Fits one Postgres primary for a year or two.
  • Feed reads: 10M × 100 ÷ 86,400 ≈ 11,600/s, ~35,000/s at peak. Read-heavy: replicas and caches.
  • Likes: 100M/day ≈ 1,160 writes/s. Counting them with COUNT(*) on every view is out.
  • CDN egress: 1 billion views/day × ~200 KB (feed-sized versions) ≈ 200 TB/day. That's what the CDN is for.

3. Architecture

  • Photos: the app gets a presigned URL, uploads straight to S3, then the API writes a metadata row. Resized versions are generated in the background and served via a CDN (2.7, 1.4).
  • Core data in Postgres: users, photos (id, owner_id, s3_key, caption, like_count, created_at), follows, likes. Indexes: photos (owner_id, created_at DESC) for profiles, unique (user_id, photo_id) on likes (2.2).
  • Likes: insert into likes and bump like_count with an atomic UPDATE … SET like_count = like_count + 1; for viral photos, split the counter into several rows (2.1, 2.5).
  • Scaling reads: a semi-sync standby in another zone for failover, async read replicas for feeds and profiles, Redis for hot photos' metadata (2.3, 1.3). Own-profile reads go to the primary for a few seconds after a write (read-your-writes).
  • Scaling writes later: IDs that sort by time and embed a shard number (like Instagram), and every table keyed by owner_id, so you can move to, say, 2,048 logical shards by user on a handful of machines when needed (2.4). follows is stored twice, by follower and by followee, so both lists are single-shard queries.
  • Search: OpenSearch, fed from database change events, eventually consistent within seconds (2.7).
  • Metrics: Prometheus for upload latency, replication lag and shard load (2.7, Lesson 6.3).

4. Trade-offs

  • Feeds read from replicas and caches are seconds stale, which is fine; usernames and uploads go through the primary (strong).
  • Denormalized like_count makes every like two writes, and saves ~billions of row reads a day.
  • Single region at first: CAP barely applies. A second region later means deciding per table what's homed where (2.6).

5. Classic mistakes

  • Storing images in the database, or streaming uploads through app servers.
  • Sharding by created_at (every new photo hits one shard) or by photo ID (profile pages become scatter-gather).
  • SELECT COUNT(*) FROM likes on every page view.
  • Reading your own fresh upload from a lagging replica (“where's my photo?”).
  • A mod N cache cluster that goes cold every time you add a node.

🏆 Boss quiz

1. An orders table grows by 1 million rows a day at about 2 KB per row. How big is it after 3 years?
1,000,000 × 2 KB = 2 GB/day; × 365 × 3 ≈ 2.2 TB, before indexes. Big but still one machine's worth; archiving old orders to object storage or partitioning by month buys time before sharding.
2. A query filters WHERE tenant_id = ? AND status = 'open' ORDER BY created_at DESC LIMIT 50. Which index serves it best?
Equality columns first, then the sort column: the database jumps to one tenant's open items, already in date order, and reads just 50 entries. With created_at first, it would walk the whole table's recent history.
3. You run N = 3 replicas with W = 2. Which R gives consistent reads, and what does it cost?
With W + R > N, every read set shares at least one replica with every write set. R = 2 is the minimum; R = 3 also works but makes reads fail if any one replica is down and wait for the slowest one.
4. A coupon can be redeemed once. Two redemption requests arrive 3 ms apart and both succeed. What's the most robust fix?
The check and the change must be one atomic step. Reading from the leader still leaves a read-then-write race; a cache adds another stale copy. A conditional update and a unique constraint let the database settle the race.
5. A global app keeps user profiles in three regions. A user in Sydney edits their bio; most readers are in their region. Which design fits best?
Writes stay local and fast (PACELC: low latency), the owner sees their edits immediately (read-your-writes in the home region), and other regions see them within a second or so, which is fine for a bio. Global quorums would add a long round trip to every edit; multi-leader LWW can silently drop edits.
