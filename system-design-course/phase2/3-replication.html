Replication: leaders, followers & replication lag

Keep copies of the same data on several machines, so the database survives a dead server and can serve more reads. The catch: copies are never perfectly in sync, and the gap is where the bugs live.

🧰 You'll need (quick reminders)
  • Availability and the nines: 99.9% allows about 8.8 hours of downtime a year (Lesson 0.5).
  • A cache can serve stale (out-of-date) data; replicas have the same problem (Lesson 1.3).
  • Databases write changes to a write-ahead log (WAL) before applying them (Lesson 2.2).
🎯 Hook

On 21 October 2018, routine maintenance on GitHub's network cut the link between its US East Coast network hub and its primary US East Coast data center for 43 seconds. That was enough for its failover tooling to promote database servers on the West Coast as the new primaries.

When the link came back, the East Coast databases held writes that had never reached the West Coast, and the West Coast had taken new writes since. GitHub couldn't simply fail back. The result was 24 hours and 11 minutes of degraded service. Replication is what keeps your data alive, and it's also a distributed system with its own failure modes.

Numbers first: why copy the data at all?

A shop's Postgres server handles 30,000 reads/s and 3,000 writes/s (a typical 10:1 read/write ratio). Say one server comfortably serves about 12,000 queries/s for this workload. One machine is drowning, and if it dies, the shop is down.

Replicas are a cache that holds the whole database (Lesson 1.3). They spread reads and survive failures, but a read from a replica can be a little behind the truth.

💡 Big idea Replication copies every change from one machine to others. The one decision that shapes everything else: does a write wait for the copies before saying “done”? Waiting (synchronous) is safer and slower. Not waiting (asynchronous) is fast, but a crash can lose the last few writes and readers can see old data.
🧠 Analogy: the head chef and the line cooks

The head chef (the leader) is the only one who changes the recipe book. Line cooks (the followers) each keep a copy and answer diners' questions, so the chef isn't swamped. When the chef changes a recipe, a runner carries the update to each cook. Until the runner arrives, a cook gives the old answer (that's replication lag). If the chef faints, one cook takes over as chef (failover), but any change the runner hadn't delivered yet is gone.

Leader–follower replication

The most common setup, used by Postgres, MySQL, MongoDB, Redis and most managed databases:

  • All writes go to one leader (also called primary or master).
  • The leader streams its change log to followers (replicas, standbys), which replay it in order. Postgres streams WAL records as they're generated.
  • Reads can go to followers. That's a read replica.

Postgres lets you pick per transaction with synchronous_commit: remote_apply even waits until the standby has applied the change, so a read there sees it.

What lag does to your users

Three classic anomalies with async replicas, and the guarantee that fixes each (names from Werner Vogels' “Eventually Consistent”):

  • You don't see your own write. You rename your profile, the page reloads from a replica that hasn't caught up, and the old name is back. Fix: read-your-writes consistency. Read your own recent changes from the leader, or wait until the replica has reached your write's log position.
  • Time goes backwards. Two reloads hit two replicas with different lag; a comment appears, then disappears. Fix: monotonic reads. Pin each user to one replica.
  • Answers before questions. You see a reply before the message it answers. Fix: causal consistency (Lesson 2.6).

Failover: when the leader dies

Failover means promoting a follower to be the new leader. It has four steps, and each can go wrong:

  1. Detect the leader is dead, usually by missed heartbeats for some seconds. Too eager, and a brief network blip triggers a failover nobody needed (GitHub's 43 seconds). Too slow, and you're down longer.
  2. Choose the follower with the most data. With async replication, even the best one may be missing the last writes.
  3. Promote it and point every client at it.
  4. Fence the old leader so it can't come back and accept writes. Two leaders accepting writes at once is called split brain, and it creates conflicting data that has to be repaired by hand.

Tools like Patroni (Postgres) and Orchestrator (MySQL) automate this, using a consensus system so that only one of them decides (Lesson 3.4).

🔥 Real outage · GitHub, 21 October 2018

GitHub ran MySQL clusters with a primary for writes and replicas for most reads, managed by Orchestrator, which uses Raft consensus for its decisions. During the 43-second partition, the Orchestrator nodes on the West Coast and in a public cloud region formed a quorum and failed clusters over to the West Coast.

The East Coast primaries had accepted a short window of writes that weren't replicated; one of the busiest clusters had 954 such writes. With different writes on each side, GitHub chose to restore from backups and resynchronize rather than lose data, and paused webhooks and Pages builds to protect what users had already sent: in its words, it prioritized data integrity over site usability. Lesson: async replication plus automatic cross-region failover can turn a 43-second blip into a day.

More than one leader, or none

Multi-leader: each region has its own leader, and leaders replicate to each other. Writes are fast everywhere, but two regions can change the same row at once, so you need a conflict rule (often “last write wins”, which silently drops one of them; Lesson 2.6).

Leaderless (Amazon's Dynamo, Cassandra, Riak): the client, or a coordinator node, sends each write to N replicas and waits for W of them to confirm; a read asks R replicas and takes the newest answer. If W + R > N, every read set overlaps every write set, so at least one replica in the read has the latest write.

W + R > N “If the number of replicas a write waits for, plus the number a read asks, is more than the total number of replicas, the two groups must share at least one replica.”
N: copies of each itemW: write acknowledgements to wait forR: replicas each read asks
✏️ Worked example: choosing N, W and R

The Dynamo paper says its common configuration is (N, R, W) = (3, 2, 2). Assume each replica is up 99% of the time, independently.

  • Overlap: W + R = 2 + 2 = 4 > 3 ✅. Every read touches a replica with the latest write.
  • Writes succeed if at least 2 of 3 replicas are up: 0.99³ + 3 × 0.99² × 0.01 = 0.970299 + 0.029403 ≈ 99.97%.
  • Compare W = 3: all three must be up: 0.99³ ≈ 97.0%. Writes fail 100× more often.
  • Compare W = 1, R = 1: very available and fast, but 1 + 1 = 2 is not more than 3, so reads can miss the latest write.

Quorums let you dial consistency, availability and latency per use case.

Things to try: N = 3, W = 1, R = 1 is the fastest and most available setting, and about 2 in 3 reads right after a write are stale. Bump R to 3: zero stale reads, slower reads. Finally raise W to N and watch the p99 latency: waiting for every replica means waiting for the slowest one.

🧰 Tools you'll actually use

Postgres streaming replication (managed: AWS RDS and Aurora read replicas, Google Cloud SQL, Azure), Patroni for automatic Postgres failover, MySQL replication with Orchestrator (what GitHub used), Redis replicas with Sentinel, and tunable quorums in Cassandra.

🚀 Startup vs big tech

Founding engineer (0 → 1)

Turn on your managed database's high-availability option (a synchronous standby in another availability zone, with automatic failover) on day one. It's a checkbox. Add a read replica only when the primary's CPU is busy with reads, and send it only reads that tolerate a second of staleness (dashboards, search pages), never “show me what I just saved”.

Big tech (1 → 100)

Semi-sync replicas across zones, many async replicas for reads, cross-region replicas for disaster recovery, and failover tooling backed by consensus (Lesson 3.4). Applications track log positions to get read-your-writes on replicas. Teams rehearse failovers regularly, because the first real one is the wrong time to learn (Lesson 8.4).

🎤 Interview angle

“Add read replicas” is the easy part. A senior answer covers:

  • Sync vs async, and what's lost on failover (RPO, the recovery point objective: how much data you can afford to lose).
  • How long failover takes (RTO, the recovery time objective) and how you avoid split brain.
  • Which reads can go to replicas, and how you give users read-your-writes.
  • For leaderless stores, the N, W, R choice and why.

Common follow-ups: “A user updates their address and the order page shows the old one. Why, and how do you fix it?” “What happens to in-flight writes when the leader dies?”

🏭 In the real world
Cross-region failover gone wrong 🏢 GitHub · 2018 October 21 post-incident analysis

How: MySQL primaries took writes, replicas served most reads, and Orchestrator (Raft-based) handled automatic failover. A 43-second partition triggered failover to the West Coast while the East Coast held unreplicated writes.

Why this method: automatic failover is right for a single dead server. GitHub's write-up shows why the failover rules must match what the application can support, especially across regions.

Quorums instead of a leader 🏢 Amazon · 2007 Dynamo: Amazon's Highly Available Key-value Store (SOSP)

How: each key is stored on N nodes; writes wait for W and reads for R, with R + W > N giving quorum-like behaviour. The common configuration was (3, 2, 2). During failures it uses a “sloppy quorum”: the first N healthy nodes.

Why this method: services like the shopping cart had to accept writes even while disks failed and network routes flapped. No single leader meant nothing to fail over.

Replicas in another zone from early on 🏢 Instagram · 2011 What Powers Instagram

How: the main Postgres shard cluster ran on 12 large-memory instances with twelve replicas in a different availability zone, using Postgres streaming replication, plus frequent snapshots for backup.

Why this method: a whole zone can fail. Replicas elsewhere mean a failed zone costs a failover, not the data.

A replica for reads, then a whole system 🧰 Open source · Vitess (YouTube) Vitess history

How: when YouTube's MySQL approached its limits, the first step was a primary for writes and a replica for reads, then more replicas. When writes outgrew the primary, YouTube had to shard (Lesson 2.4), and Vitess (2010) moved the shard-routing logic out of the app into a proxy.

Why this method: read replicas are the cheapest first scaling step for a read-heavy site. They don't help writes, which is what eventually forces sharding.

Three replicas and consensus per partition 🏢 Amazon · 2022 Amazon DynamoDB (USENIX ATC '22)

How: each partition has a replication group of three replicas that use Multi-Paxos to elect a leader; the write-ahead log is stored on all three.

Why this method: consensus-based leader election (Lesson 3.4) gives automatic failover without split brain, which a managed service running millions of partitions needs.

🤯 Fun fact · the world's biggest eventually consistent system

In “Eventually Consistent” (2008), Amazon's CTO Werner Vogels points out that the most popular system implementing eventual consistency is DNS. When you change a DNS record, servers around the world pick it up over time through caches with TTLs (Lesson 0.2). Billions of people rely on stale-for-a-while data every day without noticing.

🌉 How it connects

Replicas spread reads; sharding spreads writes (Lesson 2.4), and real systems replicate every shard. Choosing between waiting for replicas and staying available during a network split is the CAP trade-off (Lesson 2.6). Safe leader election needs consensus (Raft, etcd: Lesson 3.4). Change logs that feed replicas also feed Kafka and search indexes (Lessons 3.2 and 2.7).

Check yourself

1. A leader takes 2,000 writes/s with async replication, and replicas run about 500 ms behind. The leader's disk dies and a replica is promoted. Roughly how many acknowledged writes are lost?
Writes in flight ≈ write rate × lag = 2,000/s × 0.5 s = 1,000. Users were told those writes succeeded. If that's unacceptable (payments), make at least one standby synchronous.
2. Users complain: “I changed my shipping address, refreshed, and the old one was back.” Reads go to async replicas. What's the targeted fix?
Only the writer needs to see the write instantly. Routing their reads for a short window to the leader, or waiting until a replica has replayed their write's log position, fixes it without slowing every write. A cache would make staleness worse.
3. A leaderless store keeps N = 5 copies. Which setting guarantees every read sees the latest successful write?
You need W + R > N. 3 + 3 = 6 > 5 ✅. 2 + 2 = 4 and 1 + 4 = 5 are not greater than 5, so a read could ask only replicas that missed the write.
📝 TL;DR
  • Leader–follower: writes to one leader, changes streamed to followers, reads spread over them.
  • Async = fast but stale reads and lost writes on failover (≈ write rate × lag). Sync = safe but a round trip per write.
  • Fix lag anomalies with read-your-writes and monotonic reads; make failover detect, choose, promote and fence to avoid split brain.
  • Leaderless quorums: W + R > N means reads overlap writes; Dynamo's common setting was (3, 2, 2).
