Phase 2 · Lesson 1

SQL vs NoSQL & data modeling

Pick the kind of database whose shape matches the questions your app asks most often. At millions of users, a wrong fit shows up as slow pages, runaway costs and a painful migration.

🧰 You'll need (quick reminders)
  • QPS = queries per second; p99 = the latency that 99% of requests beat (Lesson 0.3).
  • A cache keeps copies of popular answers in memory so the database does less work (Lesson 1.3).
  • You've written SQL: a SELECT with a WHERE and maybe a JOIN.
🎯 Hook

Discord launched in 2015 with every message in one MongoDB replica set. At about 100 million stored messages, its data and index no longer fit in RAM and latency became unpredictable, so it moved messages to Cassandra. In 2017 that was 12 Cassandra nodes holding billions of messages.

By early 2022 it was 177 nodes holding trillions of messages, and on-call engineers were paged often. Discord then moved to 72 ScyllaDB nodes. Fetching old messages went from a p99 of 40–125 ms to 15 ms. Same data, a different store and a data model built for how it's read.

Numbers first: one question, two shapes of data

A social app shows a feed page: 20 posts, each with the author's name and a like count. Traffic is 10,000 feed loads per second. Posts get about 50 likes each on average.

Store it the textbook way, in three tables (posts, users, likes), and every page load reads 20 post rows, joins 20 user rows, and counts likes for each post:

Normalized (3 tables, join + count)Denormalized (name and like count copied into each post)
Rows read per page20 + 20 + 20 × 50 = 1,04020
Rows read per second10.4 million200,000
Cost of one like1 row (insert into likes)2 rows (insert + bump the counter)
Cost of an author renaming1 row1 row per post they ever wrote

Copying data makes reads 50× cheaper and makes some writes much more expensive. Neither shape is “right”. The right one depends on which operations happen most.

💡 Big idea In system design you model data for your access patterns. Write down the top five queries and how often each runs, then choose the store and the layout that make those queries cheap. Schema first, queries later is how a startup ends up rewriting its data layer at 10 million users.

The five families of databases

“NoSQL” just means “not the relational model”. It covers several very different designs. Here's the map:

FamilyData looks likeGreat atWeak atExamples
Relational (SQL)Tables of rows with fixed columns, linked by keysJoins, ad-hoc queries, multi-row transactionsWrites beyond one machine (needs sharding, Lesson 2.4)PostgreSQL, MySQL, SQL Server
Key-valueA giant dictionary: key → blobLookups by key at huge scale, predictable latencyAnything not by keyDynamoDB, Redis
DocumentJSON-like documents with nestingData read as one nested object (a profile, an order)Relationships across documentsMongoDB, Firestore
Wide-columnRows grouped by a partition key, sorted inside itHuge write rates; “latest N items for key X”Joins, ad-hoc queries, anything not by partition keyCassandra, ScyllaDB, Bigtable, HBase
GraphNodes and edgesMany-hop relationships (friends of friends)Bulk scans and aggregatesNeo4j, Facebook's TAO

A few terms you'll meet everywhere:

  • Schema: the declared shape of your data (tables, columns, types). Relational databases enforce it on write. Document stores let each document differ, so the shape is enforced by your code instead.
  • Join: combining rows from two tables that share a key, like posts.author_id = users.id.
  • Normalize: store each fact once and point to it. Denormalize: copy facts to where they're read, so reads skip the join.
  • Partition key: in Cassandra and DynamoDB, the part of the key that decides which machine holds the row. Every efficient query names it.
🧠 Analogy: the library vs the lunch boxes

A relational database is a library with a careful catalog: each book is shelved once, and cross-references let you answer any question, but answering means walking between shelves (joins). A denormalized NoSQL table is a stack of pre-packed lunch boxes: grab one and everything you need is inside. Fast at lunchtime, but if the recipe changes you have to repack every box.

    Modeling for access patterns: a worked example

    ✏️ Worked example: a chat app's message table

    Typical numbers for a growing chat app: 200 million messages a day, about 1 KB each with metadata.

    • Storage: 200,000,000 × 1 KB = 200 GB per day, × 365 = 73 TB per year. Too big for one comfortable database server within a year or two.
    • Write rate: 200,000,000 ÷ 86,400 s ≈ 2,300 writes/s on average; with a typical 3× peak, about 7,000 writes/s.
    • The hot query: “the latest 50 messages in channel X”. Almost nothing joins messages with other tables.

    So the access pattern is append by channel, read recent by channel. In Cassandra you make channel_id the partition key and sort by message ID inside it: one query reads one partition, already in order. Discord did this, and added a time bucket to the key (((channel_id, bucket), message_id)) so one busy channel can't grow a single partition forever.

    Postgres could also serve this query with an index on (channel_id, id) (Lesson 2.2). The decider isn't the query. It's that 73 TB a year and thousands of writes per second mean splitting data across machines, which Cassandra does built-in and Postgres needs extra work for (Lesson 2.4).

    Normalize or denormalize?

    Normalizing keeps each fact in one place, so it can never disagree with itself. Denormalizing copies facts to make reads cheap. Most real systems do both: normalized tables as the source of truth, plus a few denormalized copies (a counter column, a cached feed, a search index) for the hottest reads.

    🧰 Tools you'll actually use

    PostgreSQL (the default choice for a new product; managed as AWS RDS/Aurora, Google Cloud SQL, Supabase, Neon), MySQL (RDS, PlanetScale), DynamoDB (serverless key-value), MongoDB (Atlas), Cassandra/ScyllaDB (wide-column), Neo4j (graph). The same data three ways:

    -- PostgreSQL: normalized, with one denormalized counter (the hybrid)
CREATE TABLE users (id bigint PRIMARY KEY, name text NOT NULL);
CREATE TABLE posts (
  id bigint PRIMARY KEY, author_id bigint REFERENCES users(id),
  body text, like_count int NOT NULL DEFAULT 0,
  extra jsonb                                  -- flexible fields without a migration
);
SELECT p.id, p.body, p.like_count, u.name
FROM posts p JOIN users u ON u.id = p.author_id
ORDER BY p.id DESC LIMIT 20;

-- Cassandra (cqlsh): one partition per channel per time bucket
CREATE TABLE messages (
  channel_id bigint, bucket int, message_id bigint, author_id bigint, content text,
  PRIMARY KEY ((channel_id, bucket), message_id)
) WITH CLUSTERING ORDER BY (message_id DESC);
SELECT * FROM messages WHERE channel_id = 42 AND bucket = 1931 LIMIT 50;

    ⚖️ Trade-offs
    Choose relational when…Choose a NoSQL store when…
    You don't yet know all your queries (true of almost every new product)The access pattern is known, simple and huge (“get by key”, “latest N for key”)
    Correctness across rows matters: payments, inventory, bookingsWrite volume or data size is beyond one machine and you want sharding built in
    You need reports and joinsYou need predictable single-digit-millisecond latency at any scale (DynamoDB's design goal)
    Your team knows SQL (almost every team does)You're willing to design the table around the queries, and redesign it when queries change

    Hidden costs. NoSQL stores make you do joins and some integrity checks in application code. Relational stores make you do sharding yourself once you outgrow one primary. “Polyglot persistence” (several stores) means several things to back up, monitor and keep in sync.

    🚀 Startup vs big tech

    Founding engineer (0 → 1)

    Use one managed Postgres. It does relational, JSON documents (jsonb), full-text search and even vectors (Lesson 2.7) well enough for a long time. Normalize, add a counter column when a count gets hot, and write down your top queries. Discord's early approach is a good model: build fast, but keep a path to a sturdier store.

    Big tech (1 → 100)

    Several stores, each matched to a workload: a sharded relational core for money and accounts, wide-column or key-value stores for messages, events and sessions, a graph cache for social data, search and analytics copies fed by change streams (Lesson 3.2). Migrations between stores are planned projects that take months, with dual writes and verification.

    🎤 Interview angle

    “I'd use NoSQL because it scales” is a red flag. What a senior answer covers:

    • The access patterns first: the top queries, their rates and the read/write ratio.
    • Size and growth: bytes per item × items per day → TB per year. That says whether one machine is enough.
    • Where you need transactions (Lesson 2.5) and where eventual consistency is fine (Lesson 2.6).
    • The key design: primary key, partition key, and how it avoids hot spots (Lesson 2.4).

    Common follow-ups: “What if you need a new query next year?” “How do you keep the denormalized copy in sync?” “Why not just Postgres?”

    🏭 In the real world
    Wide-column store for messages 🏢 Discord · 2023 How Discord Stores Trillions of Messages

    How: messages moved from 177 Cassandra nodes to 72 ScyllaDB nodes (a Cassandra-compatible database). Historical message fetches went from a p99 of 40–125 ms to 15 ms, and inserts from 5–70 ms to a steady 5 ms.

    Why this method: the workload is append-heavy and read per channel, which fits a partition-key design. Discord also added services in front of the database to shield it from “hot partitions” (one channel getting huge traffic).

    Designing the key around the query 🏢 Discord · 2017 How Discord Stores Billions of Messages

    How: after MongoDB's index stopped fitting in RAM, the team measured their reads and writes (about 50/50, very random) and chose Cassandra with primary key ((channel_id, bucket), message_id), a bucket being about 10 days of messages.

    Why this method: every query names a channel, so the channel is the partition key. The bucket keeps each partition under about 100 MB, even for channels that live for years.

    Staying relational and sharding it 🏢 Instagram · 2012 Sharding & IDs at Instagram

    How: Instagram ran Django on PostgreSQL. When it had to split data across machines, it evaluated NoSQL options and decided to shard across PostgreSQL servers instead.

    Why this method: the team knew Postgres well and kept its features. Sharding is extra work, but it's work on a database you already trust (Lesson 2.4 shows how they did it).

    Key-value at extreme scale 🏢 Amazon · 2022 Amazon DynamoDB (USENIX ATC '22)

    How: during the 66-hour Prime Day 2021, Amazon systems made trillions of DynamoDB calls, peaking at 89.2 million requests per second, with single-digit-millisecond latency.

    Why this method: a simple key-based interface lets the service split tables into partitions and spread them over many machines without the application noticing.

    A graph store over MySQL 🏢 Facebook · 2013 TAO: Facebook's Distributed Data Store for the Social Graph

    How: TAO exposes objects and associations (a graph) and keeps MySQL for persistent storage, with its own graph-aware cache. The paper reports a billion reads and millions of writes per second.

    Why this method: the social graph is read far more than written, and it's always read as “this node's edges”. A graph API with a cache built for that pattern beat raw SQL plus a generic cache.

    🤯 Fun fact · stuck at 99.9999%

    Discord's final migration copied trillions of messages at up to 3.2 million messages per second. When the team gathered to watch it hit 100%, it got stuck at 99.9999%: the migrator was timing out on the last few ranges, which were full of tombstones (markers for deleted data) that Cassandra had never compacted away. Compacting that range finished the job in seconds. Data migrations always have a long tail.

    Whatever store you pick, the next lessons are how you make it fast and big: indexes make queries cheap (Lesson 2.2), replicas spread reads (2.3), sharding spreads writes and data (2.4), and transactions keep rows correct (2.5).     Check yourself

    1. An events table gets 50 million rows a day at about 2 KB each. Roughly how much data is that per year?
    50,000,000 × 2 KB = 100 GB a day; × 365 ≈ 36.5 TB a year. That's why this kind of table usually lands in a store that splits data across machines, or gets old rows moved to cheap storage.
    2. A new marketplace has buyers, sellers, listings, orders and payments, and the founders will want new reports every week. Which store do you start with?
    Orders and payments need multi-row transactions, and unknown future queries need joins and ad-hoc SQL. A wide-column store forces you to know your queries up front. Scale can come later with replicas and sharding (Lessons 2.3 and 2.4).
    3. You copied each author's display name into every post to skip a join. What's the new cost?
    Denormalizing moves work from reads to writes, and gives up “one fact in one place”. That's often worth it for hot reads of data that rarely changes (names), and a bad deal for data that changes constantly.
    📝 TL;DR
    • List the top queries and their rates first; choose the store and key layout that make those cheap.
    • Relational = joins, ad-hoc queries, transactions. Key-value / wide-column = huge scale for known key-based access. Document = nested objects. Graph = many-hop relationships.
    • Normalize for correctness; denormalize the few hottest reads (counters, feeds) and accept the write cost.
    • Default for a new product: one managed Postgres. Add specialized stores when a measured workload needs one.
