Phase 1 · Lesson 1

Vertical vs horizontal scaling & stateless services

When one server isn't enough you can buy a bigger one or add more of them. Only the second keeps working when a machine dies, and it only works if your servers forget everything between requests.

🧰 You'll need (quick reminders)
  • QPS / RPS = queries (or requests) per second, how much load a server sees (Lesson 0.3).
  • Availability = the share of time a system works; “three nines” is 99.9%, about 8.8 hours down a year (Lesson 0.5).
  • HTTP is request → response: each request can, in principle, be answered by any machine (Lesson 0.2).
🎯 Hook

On 9 February 2016, Stack Overflow's load balancers handled 209 million HTTP requests, about 2,400 every second on average. The web tier behind them was just 9 primary web servers.

Its architect, Nick Craver, wrote that the whole Q&A network could actually run on a single server. So why nine? His short answer: “rolling builds, headroom, and redundancy.” Those three words are this lesson.

Numbers first: bigger box or more boxes?

Your app runs on one cloud server with 2 virtual CPUs (vCPUs). It copes with about 100 requests per second. Next month you expect 2,000. You have two options.

  • Scale vertically (scale up): move to a machine 20× bigger.
  • Scale horizontally (scale out): run 20 copies of the small machine behind a load balancer.

Look at the last column. In the cloud, a core costs the same in a big box or a small one. So the real costs of scaling up are not the price. They are three other things:

  1. A ceiling. The biggest box in this family has 192 vCPUs. Past that, there is nothing to buy.
  2. A single point of failure (SPOF): one part whose failure takes everything down. One box dies, the site dies.
  3. Downtime to grow. Resizing usually means stopping the machine and starting a bigger one.

Scaling out has no ceiling in practice and survives a dead machine, but it adds a load balancer (Lesson 1.2) and one strict rule: the servers must be stateless. More on that below.

💡 Big idea Scale up until it hurts; scale out to survive. Vertical scaling is the simplest fix for performance. Horizontal scaling is the only fix for availability, and it requires that any server can answer any request.
🧠 Analogy: one superstar cashier vs many checkout lanes

A supermarket could hire one superhuman cashier who scans 20× faster. It works, until she takes a lunch break and the whole store stops. Or it can open 20 normal lanes. One closes, the queue shifts and nobody notices. The lanes only work because any cashier can serve any customer: your shopping is in your basket, not in one cashier's head. That basket is the “shared state” of this lesson.

The math of “what happens when one dies”

Say one server is up 99.9% of the time. Alone, that's about 8.8 hours of downtime a year.

Now run two, where either one can carry all the traffic. The site is down only if both are down at once. If failures are independent, that's 0.001 × 0.001 = one in a million:

availability with n spares = 1 − (1 − a)n “The chance everything is down is the chance one is down, multiplied n times.” With a = 0.999 and n = 2: 1 − 0.000001 = 99.9999%, about 32 seconds a year.
a: availability of one servern: servers, any one of which can carry the load

The catch is “independent”. Two servers in the same rack share power and a network switch. That's why big systems spread copies across availability zones (separate data centers in one region) and regions (Lesson 5.5).

✏️ Worked example: sizing a fleet with N+1

Peak traffic is 6,000 requests/s. Load tests show one server is comfortable at 800 requests/s (you never plan to run servers at 100%; queues explode near full load).

  • Servers needed at peak: 6,000 ÷ 800 = 7.5, round up to 8.
  • Add one spare so a dead server (or one being deployed) doesn't hurt: N+1 = 9 servers.
  • Losing one leaves 8 × 800 = 6,400 requests/s of capacity, still above the peak. ✅
  • With a single big box sized for 6,000, losing it leaves 0.

Stack Overflow's 9 primary web servers are this idea in real life: more than they strictly need, so they can deploy one at a time and lose one without anyone noticing.

Stateless: the rule that makes scaling out work

A server is stateless when it keeps nothing between requests that another server would need. Every request carries (or points to) everything needed to answer it.

That doesn't mean your app has no state. It means the state lives somewhere shared, not in one server's memory or disk:

State you might keep on the serverWhy it breaks with 2+ serversWhere it goes instead
Login sessions in memoryThe next request lands on another server: “who are you?”Redis / Memcached, the database, or a signed cookie / token (Lesson 4.6)
Uploaded files on local diskOnly one server has the fileObject storage like S3 (Lesson 2.7)
In-memory cacheEach server has a different copy; fine for speed, never as the truthShared cache (Lesson 1.3)
Background jobs / cron on “the” serverRun twice, or never, when servers come and goA job queue (Lesson 3.1)
Open WebSocket connectionsTruly tied to one machineAccept it; use pub/sub so any server can push to it (Lesson 7.4)

Once your servers are stateless they become cattle, not pets: identical, replaceable, and you can add ten more at 3 am without anyone touching them. That's what autoscaling (Lesson 5.3) and safe deploys (Lesson 6.2) need.

Notice what “Shared Redis” really did: it didn't remove the state, it moved it to one place built to hold it. Kill Redis and everyone is logged out at once. That's why production Redis runs with a replica and automatic failover (Lesson 2.3), and why some teams use signed tokens that need no lookup at all (Lesson 4.6).

🧰 Tools you'll actually use

Redis or Memcached as a session store (managed: AWS ElastiCache, Google Memorystore, Upstash), framework session backends, and a cloud autoscaling group (AWS Auto Scaling, GCP managed instance groups, Kubernetes HPA in Lesson 5.3) to run N identical servers. Moving Django sessions from the local process to Redis is two settings:

# settings.py: sessions in Redis, so any server can read them
CACHES = {
    "default": {
        "BACKEND": "django.core.cache.backends.redis.RedisCache",
        "LOCATION": "redis://sessions.internal:6379",
    }
}
SESSION_ENGINE = "django.contrib.sessions.backends.cache"     # or "...cached_db" to also write to the DB

If you must use sticky sessions on AWS, it's one block on the target group (Terraform):

resource "aws_lb_target_group" "web" {
  # ...
  stickiness {
    type            = "lb_cookie"
    cookie_duration = 86400   # seconds; users stay pinned for a day
  }
}

Try it locally: docker run -p 6379:6379 redis, log into your app, then redis-cli KEYS '*session*' to see your session sitting outside the app. Restart the app: you're still logged in.

⚖️ Trade-offs: up vs out
⬆️ Scale up (bigger box)➡️ Scale out (more boxes)
Code changesNoneServers must be stateless
LimitBiggest machine you can buyUsually the database behind them (Phase 2)
One machine failsEverything is downLose 1/N of capacity
GrowingRestart into a bigger boxAdd a box, no downtime; can be automatic
OperationsOne thing to watchLoad balancer, deploys, more moving parts
Best forDatabases and other stateful parts (for a long time)Web and API servers, workers

The usual real-world answer is both: scale the stateless tier out, and scale the database up as far as it goes before you shard it (Lesson 2.4).

🚀 Startup vs big tech

Founding engineer (0 → 1)

Make the app stateless from day one (it's cheap now, painful later): sessions in Redis or signed cookies, files in S3. Then run 2 small servers behind a managed load balancer, not one. That's your availability story. Scale the database up; don't shard.

Big tech (1 → 100)

Thousands of identical instances in autoscaling groups across zones and regions, with capacity plans like “survive losing a whole zone” (N+1 at the zone level). Stateful systems (databases, caches, queues) are run by dedicated teams as platforms. Machines are cattle; nobody logs into one to fix it.

🎤 Interview angle

When you draw “a few app servers behind a load balancer”, a senior answer adds:

  • “The app tier is stateless: sessions in Redis, files in object storage, so I can autoscale it.”
  • A quick capacity estimate: peak QPS ÷ per-server QPS, plus a spare (N+1), spread across zones.
  • What's still a single point of failure (the database, the session store) and how it's protected.

Common follow-ups: “What happens to logged-in users during a deploy?” · “Why not just buy a bigger server?” (Good answer: often you should, for the database, until the ceiling or availability forces you out.) · “Sticky sessions: yes or no?”

🏭 In the real world
A few powerful servers, deliberately over-provisioned 🏢 Stack Overflow · 2016 Stack Overflow: The Architecture, 2016 Edition

How: 4 HAProxy load balancers in front of 11 IIS web servers (9 primary), 4 SQL Servers and 2 Redis servers, handling 209 million HTTP requests on the measured day. The SQL servers had 384 GB to 768 GB of RAM each (hardware post).

Why this method: big machines keep the system simple; a handful of extra web servers buys rolling builds, headroom and redundancy.

Scaling one database up instead of out 🏢 Let's Encrypt · 2021 The Next Gen Database Servers Powering Let's Encrypt

How: its certificate authority runs against a single MariaDB primary. The upgrade moved it to 64 cores, 2 TB of RAM and 24 NVMe drives, and average query time fell from about 0.45 ms to 0.15 ms.

Why this method: “to minimize complexity”: sharding would add risk, and hardware advances let them avoid it so far. Vertical scaling is still the right call for many databases.

Stateless, share-nothing processes 📜 Twelve-Factor App (Heroku) The Twelve-Factor App: VI. Processes

How: “Twelve-factor processes are stateless and share-nothing”; anything that must persist goes to a backing service such as a database. It explicitly calls sticky sessions a violation.

Why this method: its authors watched hundreds of thousands of apps run on Heroku; stateless processes can be started, killed and multiplied freely.

Pluggable session stores 🧰 Open source · Django Django: How to use sessions

How: one setting switches sessions between the database, a cache like Redis, a write-through “cached_db” mode, or signed cookies that store the data on the client.

Why this method: the app code never changes; you pick the trade-off (speed vs durability vs no server state at all) per deployment.

Sticky sessions as a managed feature 🏭 AWS ALB ALB target group attributes: sticky sessions

How: the load balancer sets a cookie (AWSALB for duration-based stickiness) and routes that browser to the same target until it expires.

Why this method: a pragmatic bridge for legacy apps that keep state in memory, at the cost of uneven load and lost sessions when a target dies.

🤯 Fun fact · a world-famous site on one server

In the same 2016 post, Nick Craver noted that Stack Overflow's Q&A application is multi-tenant, and that they could “run the entire Q&A network off of a single application pool on a single server.” The other eight were never about raw speed. They were about surviving deploys and failures.

🌉 How it connects

Scaling out needs something to spread requests over the servers: load balancers (Lesson 1.2). Stateless servers lean on shared stores: caches (1.3), replicated databases (2.3) and object storage (2.7). Autoscaling comes back with Kubernetes (5.3), and N+1 capacity planning with load tests (6.5). In AI systems the same split appears: stateless inference servers scale out behind a load balancer, while the conversation history lives in a shared store.

Check yourself

1. Peak traffic is 4,500 requests/s and one server is comfortable at 600 requests/s. Using N+1, how many servers do you run?
4,500 ÷ 600 = 7.5, round up to 8 for the peak, then add one spare: 9. With one down (or being deployed) you still have 8 × 600 = 4,800 requests/s.
2. You add a second app server behind a round-robin load balancer. Users start getting logged out at random. What's the best fix?
Sessions live in each server's memory, so half the requests land on a server that has never seen the user. A shared store makes the servers stateless. Sticky sessions would also hide it, but users still get logged out whenever their server restarts.
3. Each server is up 99% of the time, failures are independent, and either of two servers can carry all the traffic. What's the availability of the pair?
Down only when both are down: 0.01 × 0.01 = 0.0001, so 1 − 0.0001 = 99.99%. (98% would be the answer if you needed both up, which is what happens when two servers can't each carry the full load.)
📝 TL;DR
  • Vertical = bigger box: simple, but has a ceiling, is a single point of failure, and needs downtime to grow.
  • Horizontal = more boxes behind a load balancer: no practical ceiling, survives failures, needs stateless servers.
  • Size with N+1: peak ÷ per-server capacity, rounded up, plus a spare. Redundancy multiplies: 1 − (1 − a)n.
  • Keep sessions, files and jobs off the app server: Redis, object storage, queues. Sticky sessions are a crutch.
