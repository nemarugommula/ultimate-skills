Phase 1 · Lesson 6

Reverse proxies & API gateways (Nginx, Envoy, Kong)

One front door for all your services: it decrypts traffic, checks who you are, enforces limits, caches, and routes each request to the right place. It turns 30 services into one API, and done badly, into one bottleneck.

🧰 You'll need (quick reminders)
  • L7 load balancers read HTTP requests and can route by path (Lesson 1.2).
  • Rate limiting with token buckets, and caching with hit ratios (Lessons 1.5 and 1.3).
  • TLS encrypts HTTP; setting it up costs round trips and CPU (Lesson 0.2).
🎯 Hook

When you open Netflix, nearly every request from your TV or phone first goes through Zuul, Netflix's open-source gateway. In 2018, Netflix ran more than 80 Zuul clusters, routing over 1 million requests per second to about 100 backend clusters.

Zuul's job is in its filters: some run before the request is proxied (authentication, routing), some after (compressing the response, adding headers). That “chain of filters at the front door” is what every API gateway is.

Numbers first: the cost of not having a front door

You have 30 services. Every one of them needs TLS certificates, token checks, rate limits, request logging and compression.

  • Without a gateway: 30 teams build these 5 things, 150 implementations in different languages. One team forgets the auth check and you have a security hole.
  • With a gateway: build them once, at the edge. Each costs a little time per request, typically well under a millisecond to a couple of milliseconds (a local token check is fast; a call to Redis for a rate limit is about 1 ms).
  • And it can save time: a cache hit at the gateway skips a backend call of, say, 40 ms. Gzip shrinks a typical JSON response several times over, which matters on a phone.
💡 Big idea A reverse proxy stands in front of your servers and speaks to clients on their behalf. An API gateway is a reverse proxy that also handles API concerns: authentication, rate limits, routing, transformation. Put cross-cutting work (the same for every service) at the gateway, and keep business logic in the services.
🧠 Analogy: an office building's reception desk

Visitors don't wander the floors looking for the person they're meeting. Reception checks their ID (authentication), turns away people who've been in ten times today (rate limiting), answers common questions itself (caching: “the cafeteria is on floor 2”), and sends everyone else to the right floor (routing). The departments upstairs never deal with any of that. But if reception starts deciding salaries, something has gone wrong.

The lines blur: Envoy can be all of the last four. What matters is the job: “north-south” traffic (users coming in) goes through the gateway, “east-west” traffic (services calling each other) goes through the mesh.

The filter chain

A gateway processes each request through a chain of steps. Order matters:

  1. TLS termination: decrypt HTTPS here, so certificates live in one place. Traffic inside your network may be re-encrypted (Lesson 4.6).
  2. Authentication: check the API key or token (for example a JWT, a signed token, Lesson 4.6). Reject with 401 before doing anything expensive.
  3. Rate limiting: per key or user, 429 when over (Lesson 1.5). After auth, so you know who to count.
  4. Caching: answer repeated public GETs without touching a service. After auth, or you'll hand cached data to strangers.
  5. Routing: /orders/* to the orders service, /v2/* to the new version, 5% of traffic to a canary (Lesson 6.2).
  6. On the way back: compress, add security headers, log and measure every request (Lesson 6.3). CORS headers and preflights belong here too, answered once at the edge (Lesson 4.6b).

Things to try: turn off the cache and the services run at 96% of capacity; latency jumps more than tenfold, because queues explode near full load (Lesson 1.2). Turn off the rate limiter as well and you're over capacity: one runaway client is now causing errors for everyone. Turn off auth and the gateway forwards invalid requests, so every service must reject them itself, and any service that forgets is open.

Backend for frontend: one call instead of five

A phone's home screen needs data from five services: profile, feed, notifications, recommendations, cart. On a phone network each round trip costs 50 to 300 ms, and inside your data center it's about 1 ms. So the trick is to make the many small calls where they're cheap.

A BFF is a small service made for one client type. The phone sends one request; the BFF calls the five services in parallel next door, trims the fields this screen doesn't need, and returns one response. Netflix built this in 2012 for its 800+ device types: device teams write adapters on the server that fan one request out into many internal calls.

✏️ Worked example: the home screen on 4G

Phone round trip 100 ms, 5 Mbps of bandwidth. Server times: profile 30 ms, feed 120, notifications 25, recommendations 180, cart 40. Feed, recommendations and cart need the profile first. Each raw response is 30 KB; the BFF's trimmed response is 25 KB in total.

  • One by one from the phone: 5 × 100 ms + (30 + 120 + 25 + 180 + 40) ms + 150 KB at 5 Mbps (240 ms) ≈ 1,135 ms.
  • Phone in parallel (profile first, then the rest at once): (100 + 30) + (100 + 180) + 240 ≈ 650 ms.
  • BFF: 100 ms to reach it; inside, profile (1 + 30 ms) then the rest in parallel (1 + 180 ms), +2 ms to assemble; 25 KB takes 40 ms: ≈ 354 ms, and one request instead of five.

🧰 Tools you'll actually use

Self-hosted: nginx (and OpenResty), Envoy (and gateways built on it), Kong (plugins for auth, rate limiting, transformations, logging), HAProxy, Traefik. Managed: AWS API Gateway, Google Cloud API Gateway / Apigee, Azure API Management, Cloudflare. In Kubernetes, an Ingress or Gateway API controller (Lesson 5.3). A small gateway in nginx:

limit_req_zone $binary_remote_addr zone=perip:10m rate=20r/s;
proxy_cache_path /var/cache/nginx keys_zone=api_cache:50m;

server {
    listen 443 ssl;                           # 1. TLS terminates here
    ssl_certificate     /etc/ssl/api.crt;
    ssl_certificate_key /etc/ssl/api.key;
    gzip on;  gzip_types application/json;       # 6. compress JSON on the way out

    location /orders/ {
        auth_request /_auth;                    # 2. ask an auth service: 2xx = allow, 401/403 = deny
        limit_req zone=perip burst=40 nodelay;   # 3. rate limit
        limit_req_status 429;
        proxy_pass http://orders;               # 5. route by path
    }
    location /catalog/ {
        proxy_cache api_cache;                  # 4. cache public GETs for a minute
        proxy_cache_valid 200 1m;
        proxy_pass http://catalog;
    }
    location = /_auth {
        internal;
        proxy_pass http://auth/verify;
        proxy_pass_request_body off;
        proxy_set_header Content-Length "";
    }
}

auth_request lives in a module that isn't built by default when compiling nginx from source; check nginx -V. Try it locally: put this in a file and run docker run -p 8443:443 -v $PWD/gw.conf:/etc/nginx/conf.d/default.conf:ro nginx (with your own self-signed certificate and upstreams).

⚖️ Trade-offs
✅ A gateway buys you…⚠️ …and costs you
One place for TLS, auth, limits, loggingA critical component: if it's down, everything is down. Run several instances behind a load balancer.
Services that are simpler and saferAn extra hop on every request (usually a millisecond or two)
Freedom to move and split services behind a stable URLA tempting place to dump logic. A gateway full of business rules becomes a shared monolith every team must change.
BFFs: fast screens, small payloads, partial responsesOne more service per client type to build and own; duplicated logic between BFFs
🚀 Startup vs big tech

Founding engineer (0 → 1)

Your “gateway” is the managed load balancer plus middleware in your one app: TLS at the balancer, auth and rate limits as framework middleware. Add a real gateway (managed, or Kong/nginx) when you have several services or a public API with keys. Build a BFF only when two clients genuinely need different shapes of data.

Big tech (1 → 100)

A fleet of edge gateways (Zuul, Envoy-based) owned by a platform team, configured as code, with per-team routes and filters; BFFs owned by the client teams (web, iOS, TV); a service mesh for east-west traffic; and the gateway's logs and metrics as the main view of what users experience.

🎤 Interview angle

Most designs start “client → API gateway → services”. A senior answer says what the gateway does:

  • TLS termination, authentication, per-client rate limits, routing, maybe caching, and the order of those steps.
  • That it's horizontally scaled and stateless (Lesson 1.1), with limits in Redis (Lesson 1.5).
  • For mobile-heavy products, a BFF that aggregates calls, with timeouts and partial responses.
  • What does not belong there: business logic.

Common follow-ups: “Isn't the gateway a single point of failure?” · “Where do you validate the JWT, and do services trust the gateway?” · “How would you roll out v2 of an endpoint?” (route by version or header, Lesson 4.5).

🏭 In the real world
A filter-based edge gateway 🏢 Netflix · 2018 Open Sourcing Zuul 2

How: Netty handles the networking; inbound filters do authentication, routing and decoration, endpoint filters proxy to the backend (or answer directly), outbound filters do things like gzipping and adding headers. More than 80 clusters, over 1 million requests per second.

Why this method: Zuul's behavior is almost entirely the filters you load, so the same core can run in different places doing different jobs.

From front proxy to every host 🏢 Lyft · 2016 Announcing Envoy: C++ L7 proxy and communication bus

How: Lyft first used Envoy as its front proxy, then gradually replaced its AWS ELBs with local Envoys on every service node.

Why this method: with about 30 services, failures were so hard to trace that developers were wary of high-volume calls in critical paths. One proxy with good stats at the edge and between services made the network observable.

One backend per user experience 📜 Pattern · SoundCloud Sam Newman: Backends For Frontends

How: instead of one general-purpose API for every client, each user experience (mobile, web) gets its own backend; Newman credits ex-SoundClouder Phil Calçado with the name and saw it used at REA and SoundCloud.

Why this method: mobile screens show less data and suffer from many round trips and battery drain, so their backend should be shaped for them.

Device adapters on the server 🏢 Netflix · 2012 Embracing the Differences: Inside the Netflix API Redesign

How: a device sends one request to its own server-side adapter, which fans it out into many internal API calls (concurrently when possible), prunes unwanted fields and formats the response for that device.

Why this method: one-size-fits-all REST didn't fit 800+ device types; moving “client code” to the server cut chattiness and let device teams move independently.

A plugin-based open-source gateway 🧰 Open source · Kong Kong Gateway on GitHub

How: proxying, routing, load balancing and health checks, with plugins for traffic control, rate limiting, request/response transformation and logging. Its rate limiter can keep counters locally, in the cluster, or in Redis.

Why this method: teams switch features on per route with configuration instead of writing proxy code.

🤯 Fun fact · 800 kinds of screens

When Netflix redesigned its API in 2012, its streaming service ran on more than 800 different device types, almost all talking to its private APIs. That's why it let device teams write their own server-side endpoints: a single API couldn't be ideal for a game console and a phone at the same time.

🌉 How it connects

A gateway combines this whole phase: L7 balancing (1.2), caching (1.3), edge delivery (1.4) and rate limiting (1.5), in front of stateless services (1.1). Its inside-the-network twin is the service mesh (4.3); token checks are covered in auth at scale (4.6); routing by version supports API evolution (4.5) and canary deploys (6.2). In AI systems, “AI gateways” sit in front of LLM providers to route between models, cache answers and enforce token budgets.

Check yourself

1. A phone with a 150 ms round trip makes 5 calls one after another, each taking 50 ms on the server. A BFF would make the same 5 calls in parallel inside the data center (1 ms away). Roughly how long does the screen take, before vs after?
Before: 5 × (150 + 50) = 1,000 ms. After: one phone round trip (150) + one parallel internal call (1 + 50) ≈ 200 ms. Round trips on slow networks dominate; a BFF moves them to where they're cheap.
2. You have 30 microservices, and an audit finds two of them never check access tokens. What's the best structural fix?
Cross-cutting rules belong in one place every request passes through. Services can still check what the user is allowed to do, but nothing unauthenticated reaches them.
3. Which of these does not belong in an API gateway?
Discounts are business logic: they belong to the orders (or pricing) service and its team. A gateway that accumulates business rules turns into a shared monolith that every team has to change and nobody owns.
📝 TL;DR
  • A reverse proxy fronts servers; an API gateway adds auth, rate limits, routing and transformation; a service mesh does it between services.
  • Filter order matters: TLS → auth → rate limit → cache → route; compress and log on the way out.
  • A BFF turns many phone round trips into one, trims payloads, and can return partial results on timeout.
  • Keep gateways stateless, redundant and free of business logic.
