Rate limiting: token buckets & friends

A rate limiter caps how many requests each client may send, so one runaway script or abusive user can't eat the capacity everyone else needs. Every public API has one; the algorithm decides how fair and how bursty it feels.

🧰 You'll need (quick reminders)
  • RPS = requests per second; capacity is finite, and queues explode near it (Lessons 0.3 and 1.2).
  • Redis: a fast shared in-memory store with atomic counters and key expiry (TTL) (Lesson 1.3).
  • HTTP status codes: 2xx success, 4xx “client did something wrong”, 5xx “server failed” (Lesson 0.4).
🎯 Hook

In 2017, Stripe wrote that its basic request rate limiter is constantly triggered: it had “rejected millions of requests this month alone”, often from a user's test script that had gotten out of hand.

Stripe runs four different limiters, built on token buckets in Redis. Without them, one customer's buggy loop could slow down payments for everybody. By the end of this lesson you'll be able to build one.

Numbers first: why “100 per minute” is trickier than it sounds

Your API allows each user 100 requests per minute. That's an average of 1.67 per second. The simplest implementation keeps a counter per user per clock minute and resets it at :00.

Now a client sends 100 requests at 0:59 and 100 more at 1:01. Each burst lands in a different minute, so both are allowed. That's 200 requests in about 2 seconds: 100 per second, 60× the rate you meant to allow, and double the per-minute limit.

This is the fixed-window boundary burst, and it's why most production limiters use something smoother.

💡 Big idea A rate limit has two numbers, whether you say so or not: a sustained rate (how much on average) and a burst (how much at once). The token bucket makes both explicit: tokens drip in at the rate, the bucket's size is the burst, and each request spends one token.
🧠 Analogy: an arcade token jar

You get one arcade token every 10 seconds, dropped into a jar that holds 20. Play slowly and the jar fills up, so you can later play 20 games in a row (a burst). Play nonstop and you're limited to one game every 10 seconds (the rate). An empty jar means “come back later”: that's an HTTP 429.

Things to try: with “Bursts of 25” and capacity 20, the first 20 of each burst pass and the rest bounce. Raise the capacity to 25 and the bursts fit, because the bucket refills between them. With the runaway script, no capacity helps for long: after the bucket drains, the script gets exactly the refill rate and nothing more. That's the point.

✏️ Worked example: the sliding window counter

Cloudflare needed a limiter that worked across its whole network using only simple counter operations. Its trick, with a limit of 50 requests per minute:

  • The current minute started 15 s ago and has 18 requests so far. The whole previous minute had 42.
  • The last 60 seconds include the current 15 s plus the last 45 s of the previous minute, so weight the previous count by 45/60 = 0.75.
  • Estimate = 42 × 0.75 + 18 = 49.5. One more request and the user is over the limit.

It assumes the previous minute's requests were spread evenly. Cloudflare measured it on 400 million requests from 270,000 sources: only 0.003% were wrongly allowed or limited.

Notice the trade-offs. The fixed window lets 200 through in 2 seconds at the boundary. The log and sliding counter hold the line at about 100. The token bucket allows a short burst (its capacity) and then exactly the rate, so in a 60-second stretch it can let through its burst plus a minute of refill. The leaky bucket never exceeds the rate but makes requests wait in line, which is great for protecting a fragile backend and bad for a user staring at a spinner.

Where to enforce it, and per what

  • Key: per API key or user (fair), per IP address (for logged-out traffic; shared offices and phone networks put many users behind one IP), per endpoint (search is costlier than reading a profile).
  • Place: at the edge or CDN (cheap rejection of floods, Lesson 1.4), at the API gateway (Lesson 1.6, the usual home), inside a service for expensive operations.
  • Kind: Stripe also runs a concurrency limiter (“only 20 requests in progress at a time”) for expensive endpoints, and load shedders that drop low-priority traffic when the whole system is struggling. A rate limiter protects you from one client; a load shedder protects you from everyone at once.

Distributed limits: when you have 20 gateways

Say each of your 20 gateway servers enforces “100 per minute” in its own memory. The load balancer spreads a user's requests across all of them, so the user really gets up to 20 × 100 = 2,000 per minute. Two fixes:

  • A shared counter in Redis: every gateway increments the same key. Costs about one Redis round trip (~1 ms) per request, and Redis must be fast and available.
  • Split the limit: each gateway allows 100 ÷ 20 = 5. No shared state, but only fair if traffic is spread evenly. Some systems do this locally and sync counters every so often.

Two details bite people. Atomicity: “read the counter, then write it back” from two gateways at once loses updates; use INCR or a Lua script that runs as one step inside Redis. Failure: if Redis is down, should requests be blocked or let through? Stripe's advice is to fail open: a broken limiter shouldn't take the API down with it.

Saying no politely: 429 and Retry-After

Return 429 Too Many Requests (a 4xx, because the client can fix it by slowing down), with a Retry-After header saying how many seconds to wait. Tell clients where they stand on every response; GitHub sends x-ratelimit-limit, x-ratelimit-remaining and x-ratelimit-reset. Good clients back off with exponential delays plus randomness (Lesson 3.3), so they don't all retry at the same instant.

🧰 Tools you'll actually use

nginx limit_req (a leaky bucket), Envoy local and global rate limiting (the global one calls a rate limit service; Envoy provides a reference one in Go backed by Redis), Kong's rate-limiting plugin (counters local, in the cluster, or in Redis), managed ones in AWS API Gateway (token bucket: a rate plus a burst) and Cloudflare. nginx, per client IP, 10 requests/s with a burst of 20:

limit_req_zone $binary_remote_addr zone=api:10m rate=10r/s;
server {
    location /api/ {
        limit_req zone=api burst=20 nodelay;   # nodelay: serve the burst now instead of queueing it
        limit_req_status 429;                # the default is 503!
        proxy_pass http://api;
    }
}

A fixed window in Redis, straight from the Redis docs' rate-limiter pattern:

MULTI
INCR   rate:user42:2026-10-31T14:05     # one key per user per minute
EXPIRE rate:user42:2026-10-31T14:05 60  # old windows clean themselves up
EXEC                                     # if the INCR result is over 100: reject

And a token bucket as a Redis Lua script, so the read-refill-spend runs as one atomic step:

-- KEYS[1] = bucket key;  ARGV = rate (tokens/s), capacity, now (ms)
local rate, cap, now = tonumber(ARGV[1]), tonumber(ARGV[2]), tonumber(ARGV[3])
local b = redis.call("HMGET", KEYS[1], "tokens", "ts")
local tokens = tonumber(b[1]) or cap
local ts = tonumber(b[2]) or now
tokens = math.min(cap, tokens + (now - ts) / 1000 * rate)   -- refill for the time that passed
local ok = tokens >= 1
if ok then tokens = tokens - 1 end
redis.call("HSET", KEYS[1], "tokens", tokens, "ts", now)
redis.call("PEXPIRE", KEYS[1], math.ceil(cap / rate * 1000))  -- idle buckets vanish
return ok and 1 or 0

Try it locally: docker run -p 6379:6379 redis, save the script as bucket.lua, and run redis-cli --eval bucket.lua bucket:me , 1 5 $(date +%s000) a few times quickly: five 1s, then 0s.

🚀 Startup vs big tech

Founding engineer (0 → 1)

Turn on your gateway's or CDN's built-in limiter per IP and per API key, generous limits, 429 + Retry-After. Add a stricter limit on login and signup (password guessing) and on anything that costs you money per call (SMS, emails, LLM calls). That's most of the value.

Big tech (1 → 100)

Layered limits: edge floods, per-customer token buckets in a global rate-limit service, per-endpoint concurrency limits, priority-aware load shedding, quotas sold as part of pricing tiers, and dashboards showing who is being limited, because a limiter that fires by mistake is an outage.

🎤 Interview angle

“Design a rate limiter” is a classic question. A senior answer covers:

  • Requirements: limit per what (user, API key, IP), how strict, how many requests per second overall.
  • The algorithm and why: token bucket for APIs, with the rate and burst stated; the fixed-window boundary problem.
  • Distributed state: Redis with atomic INCR or Lua, latency cost, and failing open.
  • The client contract: 429, Retry-After, remaining-quota headers, and clients backing off with jitter.

Common follow-ups: “How would you limit across regions?” (local limits with periodic sync, accept small overshoot) · “Rate limiter vs load shedder?” · “What happens when Redis is down?”

🏭 In the real world
Four limiters, token buckets in Redis 🏢 Stripe · 2017 Scaling your API with rate limiters

How: a request rate limiter, a concurrent-requests limiter, a fleet usage load shedder (reserving capacity for critical calls like creating charges) and a worker utilization load shedder. Every user has a token bucket, implemented in Redis.

Why this method: each protects against a different failure; their tips include failing open, dark-launching limiters first, and clear 429 vs 503 errors.

A sliding window counter at network scale 🏢 Cloudflare · 2017 How we built rate limiting capable of scaling to millions of domains

How: only GET, SET and atomic INCR were available, so they blend the previous window's count with the current one. Across 400 million requests, 0.003% were wrongly allowed or limited.

Why this method: two counters per client is cheap enough for millions of domains, and far more accurate than a fixed window.

Public limits with headers 🏢 GitHub Rate limits for the REST API

How: 60 requests per hour for unauthenticated calls (per IP), 5,000 per hour for an authenticated user, reported on every response via x-ratelimit-* headers; secondary limits answer 403 or 429, sometimes with retry-after.

Why this method: anonymous traffic is cheap to abuse, so it gets a tiny limit; identified users get a generous one and can see exactly where they stand.

The leaky bucket in your web server 🧰 Open source · nginx ngx_http_limit_req_module

How: limits the processing rate per key (often the client IP) using the “leaky bucket” method; burst sets how many excess requests may wait, nodelay serves them immediately.

Why this method: it runs in the process that already handles every request, with a shared memory zone and no extra network hop.

Token buckets as a managed setting 🏭 AWS API Gateway Throttle requests to your REST APIs

How: API Gateway throttles with the token bucket algorithm: you set a rate (tokens added per second) and a burst (the bucket size), per account, stage, method or usage plan; clients get 429 when throttled.

Why this method: the two-number contract (rate + burst) is easy to explain to customers and to sell as pricing tiers.

🤯 Fun fact · a surprisingly young status code

HTTP status 429 Too Many Requests was only standardized in April 2012, in RFC 6585. Its example response tells the client Retry-After: 3600: please come back in an hour.

🌉 How it connects

Rate limits usually live in the API gateway (Lesson 1.6) or at the edge (1.4), with counters in Redis (1.3). Clients pair them with retries, backoff and idempotency (3.3), and services pair them with circuit breakers and load shedding (4.4). They're also a DDoS layer (6.6). In AI products, limits are often counted in tokens per minute, not requests, because one request can cost a thousand times more than another.

Check yourself

1. A token bucket refills 5 tokens/s and holds 20. It's full, and a client sends requests as fast as it can. About how many are allowed in the first 10 seconds?
The full bucket gives a burst of 20, then 5 more per second: 20 + 5 × 10 = 70. That's the b + r × T rule.
2. Each of your 20 API servers enforces “100 requests per minute per user” in its own memory, behind a round-robin load balancer. What can a determined user actually get?
Each server counts only what it sees, and the user's requests are spread over all 20: 20 × 100 = 2,000. A shared atomic counter in Redis enforces one global limit, at the cost of a fast extra hop.
3. A client is over its limit. What should your API send back?
429 says “you, slow down” (a client-side condition), and Retry-After says for how long. A 500 blames your server and invites instant retries; a fake 200 hides the problem and corrupts the client's data.
📝 TL;DR
  • A limit has a rate and a burst. Token bucket: allowed in T seconds ≤ b + r × T.
  • Fixed windows allow up to 2× at boundaries; sliding window counters fix that with two numbers; leaky buckets smooth output but add waiting.
  • Many servers need a shared, atomic counter (Redis INCR or Lua) or a split limit; fail open if the limiter breaks.
  • Reply 429 + Retry-After, expose remaining quota, and make clients back off with jitter.
