Phase 1 · Lesson 2

Load balancers: L4 vs L7, algorithms, health checks

A load balancer spreads requests over many servers and quietly steers around dead ones. How it picks a server decides whether one slow machine ruins everyone's latency.

🧰 You'll need (quick reminders)
  • Stateless app servers: any server can answer any request (Lesson 1.1).
  • TCP vs HTTP: TCP is the connection; HTTP is the request/response inside it (Lesson 0.2).
  • p99 latency = the time 99% of requests beat; the slowest 1% are what users complain about (Lesson 0.3).
🎯 Hook

GitHub serves tens of thousands of requests every second from its own data centers. The simplest way to spread that over many proxy servers is to let the network routers do it, by hashing each packet's addresses to pick a server.

The catch, as GitHub's engineers explained in 2018: add one proxy server and the router reshuffles its hash, moving about a third of connections to the new machine, which has never seen them. Those in-progress connections simply fail. Avoiding that is a core goal of GitHub's own load balancer, GLB, which they open-sourced. Picking a server sounds trivial; it isn't.

Numbers first: why “take turns” isn't enough

You have four servers, but they aren't equal. Server 4 is an older machine:

Server1234Total
Can handle (requests/s)1201008040340

Traffic is 272 requests/s, 80% of the total. A load balancer that simply takes turns (round robin) gives each server a quarter: 68 requests/s. Server 4 can do 40. Every second, 28 more requests pile up in its queue. After one minute that's 1,680 requests waiting, and anyone unlucky enough to land there waits for many seconds.

The fleet as a whole has 20% spare capacity. It's just in the wrong place. A smarter algorithm sends fewer requests to the server that's falling behind.

💡 Big idea A load balancer does three jobs: spread requests (the algorithm), notice dead or sick servers (health checks), and remove servers gracefully (draining). The best algorithms react to how busy each server actually is, not to a fixed rota.
🧠 Analogy: picking a supermarket checkout

Round robin is a store employee sending shoppers to lanes 1, 2, 3, 4 in turn, even if lane 4's cashier is slow. Least connections is scanning every lane and joining the shortest; great, but in a huge store it takes a while to look at all of them, and if everybody does it at once, everybody rushes the same lane. Power of two choices is glancing at two random lanes and joining the shorter one. It sounds lazy. It's almost as good as checking every lane.

Layer 4 vs layer 7

“Layer” refers to the network layers from Lesson 0.2. A load balancer either looks only at the connection (layer 4, the transport layer: TCP or UDP) or opens up the HTTP request inside it (layer 7, the application layer).

L4 (TCP/UDP)L7 (HTTP)
SeesIP addresses and portsURL path, host, headers, cookies
Can doForward packets or connections, very fastRoute /api and /images to different pools, retries, sticky cookies, compression, terminate TLS (decrypt HTTPS)
BalancesWhole connectionsIndividual requests (many per connection)
ExamplesAWS NLB, Google Maglev, GitHub GLB Director, Linux IPVSnginx, HAProxy, Envoy, AWS ALB

Big sites use both, stacked: a fast L4 tier spreads connections over a fleet of L7 proxies, which then route each HTTP request. GitHub calls its tiers the “director” (L4) and the “proxy” (L7, running HAProxy).

Health checks: noticing a dead server

A server dies. Until the load balancer notices, it keeps sending it a share of traffic, and every one of those requests fails. Two ways to notice:

  • Active checks: the balancer calls something like GET /healthz on every server every few seconds. After a number of failures in a row (the unhealthy threshold), it takes the server out. After some successes in a row (the healthy threshold) it puts it back.
  • Passive checks (outlier detection): the balancer watches real traffic. If requests to a server fail, it stops using it for a while, and usually retries the failed request on another server.

Defaults vary a lot. AWS ALB checks every 30 s and needs 2 failures (with a 5 s timeout). HAProxy checks every 2 s and needs 3. Open-source nginx only has passive checks: one failure (max_fails=1) takes a server out for 10 s (fail_timeout), and by default it retries the request on the next server.

time to notice ≈ wait for the next check + (threshold − 1) × interval + timeout “You wait for the next check, then for enough checks in a row to fail, and each failing check waits for its timeout.” The first wait is anywhere from 0 to one interval.
✏️ Worked example: what do default settings cost?

1,000 requests/s over 4 servers = 250 requests/s each. One server freezes (it stops answering, so each check waits for the timeout).

  • AWS ALB defaults (30 s, 2 failures, 5 s timeout): 0 to 30 s for the next check, + 30 s, + 5 s = 35 to 65 s, about 50 s on average. That's 250 × 50 ≈ 12,500 failed requests.
  • HAProxy defaults (2 s, 3 failures, with a 1 s timeout): 0 to 2 s + 4 s + 1 s = 5 to 7 s. About 250 × 6 = 1,500 failed requests.
  • Plus retries (passive checks): the balancer retries each failed request on a healthy server. Users see almost no errors, just a slower response.

So why not check every 100 ms with a threshold of 1? Because healthy servers hiccup too (a garbage-collection pause, a slow disk), and you'd keep kicking healthy servers out. Try it:

The sweet spot for most services is a few seconds between checks and a threshold of 2 or 3, plus passive detection with retries for the gap. And make the health endpoint shallow: if /healthz also checks the database, one database blip makes every server look dead at once, and the balancer has nowhere to send anything.

Removing servers gracefully: connection draining

Deploys remove servers on purpose. If you pull a server while it's halfway through 50 requests, those 50 fail. Draining (AWS calls it the deregistration delay) means: stop sending new requests, let the in-flight ones finish, then remove it. AWS waits 300 seconds by default; for an API with sub-second requests, 30 seconds is plenty and makes deploys ten times faster.

Who balances the balancer?

A single load balancer is a new single point of failure. Small setups run a pair that share one virtual IP address and fail over. Managed balancers (AWS ALB/NLB, Google Cloud Load Balancing) run as a fleet for you. At the largest scale, routers spread packets over many L4 balancer machines that all answer for the same IP (equal-cost multi-path routing, ECMP), which is exactly what GitHub's GLB and Google's Maglev do.

🧰 Tools you'll actually use

nginx and HAProxy (classic self-hosted L7), Envoy (modern L7 proxy, also used inside service meshes, Lesson 4.3), cloud balancers AWS ALB (L7) / NLB (L4), Google Cloud Load Balancing, and in Kubernetes an Ingress controller (Lesson 5.3). An nginx balancer:

upstream api {
    least_conn;                          # or: random two least_conn;  (power of two choices)
    server 10.0.0.11:8080 max_fails=3 fail_timeout=10s;   # passive health check
    server 10.0.0.12:8080 max_fails=3 fail_timeout=10s;
    server 10.0.0.13:8080 weight=2;      # a bigger machine gets twice the share
}
server {
    listen 80;
    location / {
        proxy_pass http://api;
        proxy_next_upstream error timeout;  # retry on another server (the default)
    }
}

The same idea in HAProxy, with active checks:

backend api
    balance leastconn
    option httpchk GET /healthz
    server app1 10.0.0.11:8080 check inter 2s fall 3 rise 2
    server app2 10.0.0.12:8080 check inter 2s fall 3 rise 2

And an AWS ALB target group in Terraform:

resource "aws_lb_target_group" "api" {
  port                          = 8080
  protocol                      = "HTTP"
  vpc_id                        = var.vpc_id
  load_balancing_algorithm_type = "least_outstanding_requests"   # default is round_robin
  deregistration_delay          = 30                             # drain 30 s, not the 300 s default
  health_check {
    path                = "/healthz"
    interval            = 10
    unhealthy_threshold = 2
    healthy_threshold   = 3
  }
}

Try it locally: start two tiny servers (python3 -m http.server 8001 and 8002 in different folders), point an nginx upstream at them, run docker run -p 8080:80 -v $PWD/nginx.conf:/etc/nginx/conf.d/default.conf:ro nginx, and kill one while curling in a loop.

🚀 Startup vs big tech

Founding engineer (0 → 1)

Use your cloud's managed L7 balancer (ALB, Google Cloud LB) or your platform's built-in one. Switch the algorithm to least outstanding requests, add a cheap /healthz, shorten the deregistration delay. You should spend about an hour on load balancing in year one.

Big tech (1 → 100)

Layers of balancing: DNS or anycast across regions (Lesson 1.4), an L4 tier on ECMP (like Maglev or GLB), L7 proxies (Envoy) with P2C, outlier detection and retry budgets, and client-side balancing inside the service mesh (Lesson 4.3). Load balancing is a team, not a setting.

🎤 Interview angle

Drawing a box labelled “LB” is expected. What lifts the answer:

  • Say L4 or L7 and why (“L7, because I route /api and /static differently and terminate TLS here”).
  • Name the algorithm: least connections or P2C for uneven work; consistent hashing only when you need affinity.
  • Health checks + draining: how fast a dead server is removed, and how deploys avoid dropping requests.
  • The balancer isn't a single point of failure: managed, redundant pair, or ECMP.

Common follow-ups: “What happens to WebSocket connections when you add a server?” · “How would you route 5% of traffic to a new version?” (weighted target groups, Lesson 6.2) · “A server is slow but not dead. What notices?” (passive checks / outlier detection).

🏭 In the real world
An L4 director tier in front of HAProxy 🏢 GitHub · 2018 GLB: GitHub's open source load balancer

How: routers spread packets over stateless “director” servers (L4), which pick a primary and a secondary proxy for each connection using rendezvous hashing. If a packet lands on a proxy that doesn't know the connection, it's forwarded to the secondary: a “second chance”.

Why this method: adding or removing proxies no longer breaks the in-progress connections that plain router hashing would move.

Software load balancing on commodity servers 🏢 Google · 2016 Maglev (NSDI 2016)

How: routers send packets to Maglev machines via ECMP; each Maglev machine uses consistent hashing and connection tracking to pick a backend. One machine can saturate a 10 Gbps link with small packets, and it has served Google's traffic since 2008.

Why this method: software on ordinary servers scales out by adding machines, unlike pairs of expensive hardware appliances.

Power of two choices by default 🧰 Open source · Envoy Envoy: supported load balancers

How: Envoy's “least request” balancer picks 2 random hosts by default and sends the request to the one with fewer active requests, citing Mitzenmacher's result that this is nearly as good as scanning every host.

Why this method: each Envoy only sees its own traffic; P2C works well with that partial view and doesn't herd everyone onto one host.

The math behind “pick two” 📜 History · 2001 Mitzenmacher: The Power of Two Choices in Randomized Load Balancing

How: in the “supermarket model”, each arriving customer samples d random servers and joins the shortest queue. Going from d = 1 to d = 2 gives an exponential improvement in time spent in the system.

Why this method: it showed that a tiny amount of information (two samples) captures most of the benefit of perfect information.

HAProxy terminating TLS and routing by host 🏢 Stack Overflow · 2016 Stack Overflow: The Architecture, 2016 Edition

How: HAProxy load balancers terminate TLS and route to backends mostly by the host header, with some rate limiting and header capture for per-request performance logs.

Why this method: one L7 layer handles encryption, routing and measurement, so the web servers only do application work.

🤯 Fun fact · two is magic, three is just nice

Mitzenmacher's paper found that letting each request sample two servers instead of one gives an exponential improvement, while sampling three is only a constant factor better than two. That's why so many balancers stop at two.

🌉 How it connects

Load balancers make stateless scaling (1.1) work. They often also cache (1.3), rate-limit (1.5) and act as a gateway (1.6). Consistent hashing gets a full lesson in 2.4, service meshes move balancing into every client (4.3), and canary deploys use weighted balancing (6.2). AI inference servers use the same ideas: least-outstanding-requests routing matters a lot when one request can take 50 ms and the next 30 s.

Check yourself

1. 600 requests/s are spread over 3 servers behind an ALB with default health checks (every 30 s, 2 failures, 5 s timeout). One server freezes, and there are no retries. Roughly how many requests fail before it's removed?
Each server gets 200 requests/s. Detection takes 35 to 65 s (wait for a check, one more interval, plus the timeout). 200 × 35 to 65 ≈ 7,000 to 13,000, so about 10,000. Faster checks or retries on another server cut that dramatically.
2. You want /api/* to go to one pool of servers and /images/* to another, and HTTPS should be decrypted once, at the edge. What do you need?
Only an L7 balancer reads the HTTP request (the path), so only it can route by URL. It also terminates TLS. An L4 balancer sees just IPs and ports.
3. You run 50 proxy instances, each balancing over the same 200 servers. Why is power of two choices often better than least connections here?
Least connections assumes a fresh, global view. Many balancers acting on similar stale information herd onto the same server. P2C's randomness avoids that and still captures most of the benefit, which is why Envoy uses it by default.
📝 TL;DR
  • L4 balances connections (fast, blind to HTTP); L7 balances requests (routing, TLS, retries). Big sites stack both.
  • Round robin fails with uneven servers or requests; least connections and power of two choices adapt to live load.
  • Time to notice a dead server ≈ next check + (threshold − 1) × interval + timeout. Add passive checks and retries for the gap.
  • Drain before removing a server; keep health endpoints shallow; make sure the balancer itself is redundant.
