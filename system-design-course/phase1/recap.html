Phase 1 · Recap

Recap: scaling the request path

Everything between a user's click and your code: stateless servers, load balancers, caches, CDNs, rate limiters and gateways. Here's the whole phase on one page, a game to test your instincts, and a design problem to put it together.

🧾 Cheat sheet

⚖️

1.1 Scaling out

N+1: ⌈peak ÷ per-server⌉ + 1 spare. Redundancy: 1 − (1 − a)n.

Scale up until it hurts, scale out to survive. Out needs stateless servers: sessions in Redis, files in object storage.

🧰 Redis session store, autoscaling groups, Django/Express session backends

🔀

1.2 Load balancers

Time to notice ≈ next check + (threshold − 1) × interval + timeout.

L4 = connections, L7 = HTTP requests. Least connections or power of two beat round robin on uneven work. Drain before removing.

🧰 nginx, HAProxy, Envoy, AWS ALB/NLB

⚡

1.3 Caching

avg = h·tcache + (1 − h)(tcache + tdb); DB load = (1 − h) × QPS.

Cache-aside + LRU + delete-on-write + TTL. Watch for stale data, hot keys and stampedes (locks or serve-stale).

🧰 Redis, Memcached, ElastiCache

🌍

1.4 CDNs

~1 ms of RTT per 100 km of fiber; origin traffic = (1 − hit) × total.

Move answers near users. Fingerprinted assets cached for a year; public HTML briefly; anything personal private.

🧰 Cloudflare, CloudFront, Fastly, Cache-Control

🚦

1.5 Rate limiting

Token bucket: allowed in T seconds ≤ b + r × T.

Every limit has a rate and a burst. Fixed windows leak 2× at boundaries. Share counters atomically (Redis INCR/Lua), fail open, reply 429 + Retry-After.

🧰 nginx limit_req, Envoy, Kong, API Gateway

🚪

1.6 Gateways

TLS → auth → rate limit → cache → route; compress and log on the way out.

Cross-cutting work at the front door, business logic in services. A BFF turns many phone round trips into one.

🧰 nginx, Envoy, Kong, Zuul, AWS API Gateway

🗣️ Teach it back

Answer out loud, like in an interview: “A user in Sydney opens our app, whose servers are in Virginia. Walk me through every component the request passes on the way to our code and back, what each one does, and what would go wrong without it.”

A strong answer mentions: DNS or anycast to the nearest CDN edge (cached assets return in ~30 ms), the edge's warm connection to the origin, the gateway (TLS, auth, rate limit, cache, routing), the L7 load balancer picking a healthy, not-busy server, a stateless app server that finds the session in Redis, and a cache in front of the database. Then: what fails if any one of them dies?

🏗️ Design it yourself: the ticket drop

✏️ The problem

A concert's tickets go on sale at 10:00. About 500,000 fans will have the event page open, and many will hit refresh every few seconds. The page shows the event details, a seat map with live availability, and a Buy button. Your origin is one region. Using only this phase's ideas (stateless servers, load balancers, caches, CDN, rate limits, a gateway), design the request path so the site stays up and buying stays fair.

Sketch it first, with numbers. Then open the reveal.

Reveal: one good answer

Requirements

  • The page must load for everyone, even at the peak; seat availability can be a second or two stale; Buy must never be served from a cache.
  • No single user or bot gets an unfair share of Buy attempts.
  • Losing any one server (or a zone) during the sale must not take the site down.

Numbers

  • Page views: 500,000 fans refreshing every 5 s ≈ 100,000 requests/s. That is a CDN's job, not your servers'.
  • With the event HTML cached at the edge for 2 s (s-maxage=2) and an origin shield, the origin sees about one request per 2 s for that page, instead of 100,000/s. Without a shield, at most one per PoP per 2 s: still only around 150/s if you had 300 PoPs.
  • Assets (JS, CSS, images, say 2 MB per first visit) are fingerprinted and cached for a year: 500,000 × 2 MB ≈ 1 TB, nearly all from the CDN.
  • Buy clicks: if 20% of fans click within 10 s, that's 100,000 ÷ 10 = 10,000 requests/s. At 500 requests/s per server: 20 servers + 1 spare = 21, spread across zones.

Architecture

  1. CDN in front of everything: assets for a year, event HTML for 2 s with stale-while-revalidate, origin shield on.
  2. Seat-map API: one cached JSON document per event in Redis, rebuilt by a single worker every second (single-flight, Lesson 1.3), and also cached at the CDN for 1 s. The database sees about one availability query per second per event.
  3. API gateway: TLS, auth (you must be logged in to buy), and a token bucket per user on Buy (say 1/s with a burst of 3) plus a looser one per IP; a 429 with Retry-After, and a client that backs off with jitter.
  4. L7 load balancer with least outstanding requests, health checks every 2 to 5 s, retries on another server for idempotent reads only, short draining.
  5. Stateless app servers (21+, autoscaled ahead of time, because autoscaling reacts too late for a spike that arrives at 10:00:00), with sessions in replicated Redis.

Trade-offs

  • A 1 to 2 s stale seat map means some fans click seats that just sold; the Buy call is the source of truth and says so politely.
  • Per-user limits are fair but need logins; per-IP limits catch bots but also hit fans behind one office or mobile carrier IP, so keep them loose.
  • Pre-scaling costs money for an hour; under-scaling costs the launch.

Classic mistakes

  • Caching the Buy response, or caching personalized pages publicly.
  • Sticky sessions: a server dies mid-sale and thousands of fans are logged out with seats in their basket.
  • A fixed-window limiter that resets at 10:00:00, letting a double burst through.
  • Returning 500 instead of 429, so every client retries instantly and the retry storm becomes the outage.
  • A health check that queries the database: one database hiccup and the balancer pulls every server at once.
  • Relying on autoscaling to react to a spike you knew the exact time of.

What this design doesn't solve yet: making sure two fans can't buy the same seat. That's transactions and locking in Phase 2, and putting purchases on a queue in Phase 3.

🏆 Boss quiz

1. Peak traffic is 12,000 requests/s and one server is comfortable at 900 requests/s. With N+1, how many servers?
12,000 ÷ 900 = 13.3, round up to 14 for the peak, plus one spare: 15 (Lesson 1.1).
2. Your CDN delivers 1,000 TB a month with a 98% hit ratio. About how much does your origin send?
Misses are 2%: 0.02 × 1,000 = 20 TB. Going from 98% to 99% would halve it again (Lesson 1.4).
3. Your API's requests take anywhere from 2 ms to 5 s, and your servers are different sizes. Which load-balancing algorithm?
Uneven work and uneven servers need an algorithm that looks at live load. Round robin keeps feeding the server that's stuck on slow requests; IP hash ignores load entirely (Lesson 1.2).
4. A hot product's cache key expires during a sale and hundreds of identical database queries fire at once. What's the fix?
That's a cache stampede. Single-flight rebuilding (Facebook's leases) or serve-stale-while-revalidate turn hundreds of queries into one (Lesson 1.3).
5. In your gateway, why must the response cache run after authentication?
A cache before auth answers anyone who asks. Order the chain TLS → auth → rate limit → cache → route, and never cache personal responses in a shared cache (Lessons 1.4 and 1.6).
