Phase 1 · Lesson 3

Caching: the fastest request is the one you don't make

Keep a copy of popular answers somewhere fast, so most requests never reach the slow database. It's the single biggest lever for scaling reads, and the source of some famous outages.

🧰 You'll need (quick reminders)
  • Latency = how long one request takes. Memory is roughly 100× faster than a disk-backed database query (Lesson 0.3).
  • Stateless app servers behind a load balancer, so you can add more of them (Lessons 1.1 and 1.2).
  • QPS = queries per second, how much load a component sees (Lesson 0.3).
🎯 Hook

One day in February 2016, Stack Overflow served 505 million SQL queries. Those took 168 hours of combined database time. The same day it served 5.8 billion reads from its Redis cache, more than 11× as many, and those took 2.8 hours in total.

Most of the site's reads never touched the database. That's caching, and by the end of this lesson you'll be able to size a cache, pick its rules, and explain how it can take a whole site down.

Numbers first: what a cache buys you

Your product page reads from Postgres. A query takes about 10 ms, and the database starts to struggle above 2,000 queries per second. Traffic is 10,000 reads per second. Without help, the database melts.

Now put a Redis cache in front. Asking Redis takes about 1 ms. Suppose 90% of requests find their answer there (a hit) and 10% don't (a miss, so we also ask the database):

No cacheCache with 90% hit rate
Database load10,000 QPS (melts)10% × 10,000 = 1,000 QPS ✅
Average latency10 ms0.9 × 1 ms + 0.1 × (1 + 10) ms = 2 ms

Five times faster, and the database does a tenth of the work. Every extra point of hit rate counts: at 99% the database sees only 100 QPS.

avg latency = h × tcache + (1 − h) × (tcache + tdb) “The average time is: hit rate h times the cache time, plus the miss rate (1 − h) times the cache time plus the database time.” On a miss you pay for both trips.
h: hit rate (share of requests answered by the cache)t: time for one trip
💡 Big idea A cache keeps copies of popular answers somewhere much faster than where they really live. Because real traffic is lopsided (a few items get most of the requests), a small cache can absorb most of the load.
🧠 Analogy: the kitchen counter

Your pantry (the database) has everything, but it's a walk away. So you keep salt, oil and coffee on the counter (the cache). Most of the time what you need is right there. The counter is small, so when something new goes on it, something you haven't used lately goes back (that's eviction). And if you refill the oil bottle in the pantry, the one on the counter is now old (that's invalidation, the hard part).

The rules of the cache

Three decisions define any cache: how data gets in, what gets thrown out when it's full, and how long a copy is trusted.

1. How data gets in: the four patterns

PatternHow it worksGood for
Cache-aside (lazy loading)App checks the cache; on a miss it reads the DB and writes the answer into the cache.The default. Only caches what's actually asked for. A cache crash just means more misses.
Read-throughSame, but the cache library fetches from the DB for you.Cleaner app code (e.g. a caching layer in front of DynamoDB).
Write-throughEvery write goes to the cache and the DB together.Data that's read right after it's written. Writes get slower.
Write-behind (write-back)Write to the cache now, flush to the DB later in batches.Very write-heavy counters (likes, views). Risk: lose recent writes if the cache dies.

2. What gets thrown out: eviction

  • LRU (least recently used): evict whatever hasn't been touched for longest. The usual default.
  • LFU (least frequently used): evict whatever is used least often. Better when popularity is stable; slow to react when it changes.
  • FIFO: evict the oldest entry, however popular. Simple, usually worse.

Fun detail: Redis doesn't track exact LRU order, which would cost memory. It samples a handful of random keys and evicts the best candidate among them, which is close enough and much cheaper.

3. How long a copy is trusted: TTL

A TTL (time to live) says “throw this copy away after 60 seconds”. Short TTL = fresher data, more misses. Long TTL = more hits, staler data. Many systems also delete the key on write so the next read fetches the new value.

✏️ Worked example: sizing a cache

An online shop has 1,000,000 products, each cached as a 2 KB JSON blob. Analytics show the top 5% of products get 80% of views.

  • Caching the hot 5% = 50,000 × 2 KB = 100 MB. That fits in the smallest Redis instance, and gives roughly an 80% hit rate.
  • Caching everything = 1,000,000 × 2 KB = 2 GB. Still small, but the last 95% of products only add the remaining 20% of hits.
  • At 5,000 reads/s and 80% hits, the database sees 1,000 QPS instead of 5,000.

This is why caches work: popularity is lopsided. Try it below.

The hard part: when the cache bites back

Caches fail in famous ways. Three to know cold:

  • Stale data: the database changed but the cache still holds the old copy. Fix: delete or update the key on every write, plus a TTL as a safety net.
  • Hot key: one key (a celebrity's profile, a viral product) gets so much traffic that the single cache server holding it melts. Fix: copy the hot key to several servers, or keep a tiny in-process cache in each app server.
  • Cache stampede (thundering herd): a hot key expires, and in that instant thousands of requests all miss and all hit the database at once. Try it:

🧰 Tools you'll actually use

Redis (the most common choice; also does counters, queues, rate limits), Memcached (simpler, multi-threaded, pure cache), managed versions like AWS ElastiCache, Google Memorystore or Upstash. Cache-aside in Python with redis-py:

import json, redis
r = redis.Redis(host="localhost", port=6379)

def get_product(pid):
    key = f"product:{pid}"
    cached = r.get(key)                          # 1. ask the cache (~1 ms)
    if cached:
        return json.loads(cached)                #    hit: done
    row = db.query("SELECT * FROM products WHERE id=%s", pid)  # 2. miss: ask the DB (~10 ms)
    r.set(key, json.dumps(row), ex=300)      # 3. store a copy for 5 minutes (TTL)
    return row

def update_product(pid, fields):
    db.update(pid, fields)
    r.delete(f"product:{pid}")                  # invalidate: next read fetches the new value

Try it locally: docker run -p 6379:6379 redis, then redis-cli SET greeting hi EX 10 and redis-cli TTL greeting. For browsers and CDNs, the equivalent knob is the HTTP header Cache-Control: public, max-age=300.

⚖️ Trade-offs: when a cache helps and when it hurts
✅ Add a cache when…❌ Think twice when…
Reads far outnumber writes (10:1 or more)Data changes on almost every read
Popularity is lopsided (a few hot items)Every request wants something different (low skew)
Slightly stale data is fine (product pages, feeds, profiles)Staleness is dangerous (account balances, stock levels at checkout)
The answer is expensive to compute (joins, rankings, ML scores)The database is already fast enough. A cache is one more system to run, monitor and keep consistent.
🚀 Startup vs big tech

Founding engineer (0 → 1)

Don't add a cache on day one. Add database indexes first (Lesson 2.2). When the DB CPU runs hot on reads, add one managed Redis with cache-aside and short TTLs. Cache whole API responses for anonymous users and let a CDN do the rest.

Big tech (1 → 100)

Several cache layers: CDN, regional Redis/Memcached clusters spread with consistent hashing (Lesson 2.4), copies of hot keys, leases or locks against stampedes, and invalidation driven by database change streams (Lesson 3.2). Teams track hit rate as a key metric (Lesson 6.3).

🎤 Interview angle

Saying “add a cache” earns nothing. What a senior answer covers:

  • What exactly you cache (key and value), and an estimated hit rate from the access pattern.
  • The pattern (cache-aside is the safe default) and the invalidation plan: delete on write + TTL.
  • What happens when the cache dies or restarts cold: can the database survive the full load for a few minutes?
  • Hot keys and stampedes, and how you'd prevent them.
🏭 In the real world
A cache in front of everything 🏢 Facebook · 2013 Scaling Memcache at Facebook (NSDI)

How: web servers use cache-aside against huge Memcached pools; the paper reports billions of requests per second and trillions of items. It also introduces leases: the cache hands out a token so only one client refills a missing key, which stops stampedes and stale writes.

Why this method: the social graph is read far more than it's written, so serving reads from memory let the databases handle a fraction of the traffic.

Redis absorbing most reads 🏢 Stack Overflow · 2016 Stack Overflow: The Architecture, 2016 Edition

How: on the day the post measured, Redis served 5.8 billion hits against 505 million SQL queries, and the Redis hits took 2.8 hours of combined time against 168 hours for SQL.

Why this method: a small number of servers could handle one of the busiest sites on the web, because most reads never reached SQL Server.

A distributed cache built for the cloud 🏢 Netflix · 2013 Announcing EVCache

How: EVCache is a distributed in-memory cache based on Memcached, integrated with Netflix's AWS setup, with copies of the data kept in multiple zones.

Why this method: keeping copies in several availability zones means losing one zone doesn't turn into a cold cache and a database overload.

Caching in the browser and at the edge 🧰 Web standard HTTP Cache-Control (MDN)

How: one response header tells browsers and CDNs how long they may reuse a response (max-age), and whether shared caches may store it (public vs private).

Why this method: a request answered by the browser or a CDN never reaches your servers at all, which is the cheapest request there is.

🤯 Fun fact · the most quoted line in software

“There are only two hard things in Computer Science: cache invalidation and naming things.” It's attributed to Phil Karlton, an engineer at Netscape. After this lesson you know why the first one is on the list: keeping copies in sync with the truth, across many machines, at high speed, is genuinely hard.

Check yourself

1. A cache takes 1 ms, the database 20 ms, and the hit rate is 95%. What's the average latency?
0.95 × 1 + 0.05 × (1 + 20) = 0.95 + 1.05 = 2 ms. Misses pay for both trips, which is why the last few percent of hit rate matter so much.
2. A celebrity posts and their profile key expires at peak traffic. Thousands of requests miss at once and the database falls over. What's the best fix?
This is a cache stampede. Single-flight locks (Facebook calls theirs leases) or serve-stale-while-revalidate turn hundreds of identical rebuild queries into one. A longer TTL only delays the problem.
3. Which data is the worst fit for a cache with a 5-minute TTL?
A 5-minute-old balance could approve a payment the account can't cover. Data where staleness causes real harm should be read from the source of truth (Lesson 2.5 covers transactions).
📝 TL;DR
  • A cache keeps copies of popular answers in fast memory. Lopsided traffic means a small cache can catch most reads.
  • avg latency = h·tcache + (1 − h)·(tcache + tdb); database load = (1 − h) × QPS.
  • Defaults: cache-aside, LRU eviction, delete-on-write + a TTL safety net.
  • Know the failure modes: stale data, hot keys and stampedes (fix with locks/leases or serve-stale).
