Phase 4 · Recap

Recap: microservices architecture

When to split, where to draw the lines, how services talk and survive each other, how their APIs change safely, and how every call proves who it's from. One page to review it all, a game, a design problem and a boss quiz.

🧾 Cheat sheet

4.1 Monolith vs microservices

Split to scale teams, not traffic.

Chains multiply availability (0.99910 ≈ 99.0%); fan-out makes the tail common: 1 − (1 − p)N. Default to a modular monolith.

Packwerk, ArchUnit, Spring Modulith, Backstage

4.2 Boundaries & DDD

Bounded contexts, not tables. Never split an aggregate.

Score: Σ rate × (services touched − 1). Each service owns its data. Migrate with the strangler fig.

Event Storming, Debezium (change data capture), Nginx/Envoy routing

4.3 Communication & mesh

Sync only when you need the answer now.

Everything else is an event. Discovery: client-side (Eureka) or server-side (Kubernetes Services). Mesh sidecars add mTLS, retries, metrics, at a CPU and latency cost.

gRPC, Kafka, Kubernetes DNS, Consul, Istio, Linkerd, Envoy

4.4 Resilience

Threads busy = rate × time held.

Every call gets a timeout and a deadline; retries at one layer with backoff, jitter and a budget (35 = 243× otherwise); breakers, bulkheads, fallbacks, load shedding.

Resilience4j, Envoy/Istio policies, Toxiproxy

4.5 API evolution

Additive changes, tolerant readers.

Never remove, rename, retype or change meaning in place. Version when you must (URL, header, Stripe-style pinning). Expand → migrate → contract.

OpenAPI, buf breaking, Pact, schema registries, Flyway

4.6 Auth at scale

Centralize authn, enforce authz near the data.

Short-lived JWTs (5–15 min) + refresh; verify alg, signature, exp, iss, aud. OAuth code + PKCE; OIDC for login; mTLS and zero trust inside.

Keycloak/Auth0/Okta, jose, SPIFFE/SPIRE, OPA

4.6b CORS, CSRF & cookies

CORS decides who may read; SameSite + tokens decide whose writes count.

Exact origin allowlist (never reflect + credentials), Vary: Origin, Max-Age 7,200 s, or same-origin routing at the gateway. Cookie: __Host-, Secure, HttpOnly, SameSite=Lax. No state changes on GET.

Express cors, nginx/Kong, Django/Rails CSRF, Go CrossOriginProtection

🗣️ Teach it back

Answer out loud, as if an interviewer just asked: “Our company has a 6-year-old monolith and 120 engineers who keep blocking each other’s releases. The CTO wants to move to microservices. What would you do, and what would you warn them about?”

A strong answer covers: why (deploy conflicts, team autonomy) and the costs (network, consistency, ops, tail latency); modular boundaries first; picking the first service by business capability and different scaling needs; strangler-fig migration with canaries; sync vs async between the new services; timeouts, retry budgets and breakers from day one; API compatibility rules; and identity between services.

🏗️ Design it yourself: split FoodNow

✏️ The problem

FoodNow is a food-delivery company. Everything runs in one Django monolith with one Postgres database. Facts:

  • 60 engineers today, 200 planned in 18 months. Deploys are blocked several times a week by other teams' broken changes.
  • 2 million orders a day, with a dinner peak about 3× the daily average. Menus are viewed about 50 times for every order placed.
  • Twice this year a slow SMS (text message) provider made checkout time out for everyone.
  • Restaurants' point-of-sale (POS) systems integrate through a public API. Mobile apps can't be force-updated.

Design the target architecture and the migration path using only Phase 4 ideas: boundaries, communication, resilience, API evolution and auth. Write your answer first, then open the reveal.

🔓 Reveal a strong answer

1. Requirements and numbers

  • Orders: 2,000,000 ÷ 86,400 s ≈ 23/s on average, ≈ 70/s at the dinner peak.
  • Menu views: 50 × 70 ≈ 3,500/s at peak. Reads dominate by far, and they need a different scaling profile than ordering.
  • Teams: 200 engineers ≈ 25–30 teams of 6–8. The deploy-train math from Lesson 4.1 says a shared train will keep getting worse.

2. Boundaries (Lesson 4.2)

  • Contexts: Menus (restaurants, items, prices), Ordering (cart, order + lines as one aggregate), Payments, Dispatch (couriers, assignment), Notifications, Identity, and a Partner API for restaurant systems.
  • Each owns its data. Ordering keeps an event-fed copy of the menu items and prices it needs, so placing an order doesn't call Menus 3,500 times a second.

3. Communication (Lesson 4.3)

  • Sync: Ordering → Payments (authorize the card; we need the answer). Everything else is an event: OrderPlaced → Dispatch, Notifications, analytics; OrderPicked → Notifications.
  • Critical path for checkout: gateway, Ordering, Payments, Kafka ≈ 4 services, instead of 7+ in a chain.
  • Discovery via Kubernetes Services; add a mesh only once there are many services and mTLS is required everywhere.

4. Resilience (Lesson 4.4)

  • SMS moves behind a queue: a slow provider now delays texts, not checkouts (this alone fixes both outages).
  • Timeouts on every call from the callee's p99.9; retries only at the edge or mesh, with jitter and a 10% budget; a breaker plus fallback on the maps/ETA (estimated time of arrival) provider (“ETA unavailable” beats a failed order); bulkheads so Dispatch can't starve Ordering.
  • Load shedding at dinner peak: drop analytics and recommendation calls first.

5. API evolution (Lesson 4.5)

  • Partner API: /v1/, additive-only changes, contract tests with the biggest POS integrations, Deprecation/Sunset headers and usage dashboards per partner key.
  • Mobile: tolerant readers, a minimum-supported-version check, expand–contract for every rename. Event schemas in a registry with compatibility checks.

6. Auth (Lesson 4.6)

  • Customers and couriers log in via OIDC; short-lived access tokens (≈15 min) + refresh. Restaurant systems use OAuth client credentials with scopes like orders.read.
  • Gateway verifies tokens; each service checks aud and permissions; mTLS workload identities between services.

7. Migration plan (strangler fig)

  1. Make the monolith modular first (enforce boundaries in CI) and put a routing layer in front.
  2. Extract Notifications (async, low risk, fixes the SMS outages).
  3. Extract Menus (read-heavy, scales differently): CDC copy, shadow traffic, 5% canary, ramp.
  4. Then Dispatch, then Payments (highest risk, last, with idempotency keys). Ordering may stay in the slimmed monolith for a long time, and that's fine.

Trade-offs to say out loud

More services means more ops: budget for a platform team (CI/CD, Kubernetes, tracing). Event-fed copies mean menu prices can be a second stale; Ordering must re-check the price at payment. Each extraction takes weeks to months.

Classic mistakes

  • A big-bang rewrite into 40 services.
  • Splitting Order and OrderLine, or services sharing the old Postgres tables (a distributed monolith).
  • A synchronous chain Ordering → Dispatch → Notifications → SMS (the same outage, now distributed).
  • Retries at every layer; no timeouts on third-party calls.
  • Renaming partner API fields in place; trusting all internal traffic.

🏆 Boss quiz

1. A search page fans out to 40 shards in parallel. Each shard is slow on 0.5% of requests. Roughly what share of searches wait on at least one slow shard?
1 − 0.99540 ≈ 1 − 0.818 = 0.18. The fixes from Lesson 4.1: fewer shards per query, tight timeouts, or hedged requests (a call is then slow only if both copies are).
2. Three services must always be deployed together, and two of them write to the same orders table. What is this, and what's the first fix?
Lockstep deploys and shared tables are the signature of a distributed monolith (Lesson 4.2). Data ownership is the first boundary to fix; stable APIs then let each service deploy alone.
3. Service A gets 300 requests/s, each calling B. B's latency jumps from 20 ms to 4 s. A has 400 threads and no timeout. What happens?
Little's law (Lesson 4.4). A timeout (say 200 ms → 60 threads), a bulkhead around B, and a circuit breaker with a fallback would each keep A alive.
4. You need to rename zip to postal_code in a public API used by partners and old mobile apps. Which plan is right?
Expand, migrate, contract (Lesson 4.5). In-place renames break every client you can't update; changing a field's meaning breaks them silently.
5. A security review finds that internal services accept any request from inside the cluster, and access tokens last 7 days. What's the best set of changes?
Zero trust (Lesson 4.6): every call proves its identity, and stolen tokens die quickly. A firewall is the perimeter model BeyondCorp moved away from; encrypting the payload doesn't stop a stolen token from working.
