Phase 4 · Lesson 6

Auth at scale: OAuth2, OIDC, JWT, mTLS

Who is calling, and are they allowed to do this? With millions of users and hundreds of services, answering both questions on every request, quickly and safely, is its own piece of architecture.

🧰 You'll need (quick reminders)
  • TLS encrypts a connection and proves the server's identity with a certificate (Lesson 0.2).
  • API gateways sit at the edge and handle cross-cutting work for every request (Lesson 1.6).
  • Service mesh sidecars can encrypt and authenticate service-to-service traffic with mTLS (Lesson 4.3).
🎯 Hook

For decades, company security meant a wall: a firewall around the office network, and anyone inside was trusted. In 2014 Google published BeyondCorp, describing the problem bluntly: once that perimeter is breached, an attacker has relatively easy access to the privileged intranet.

Google's answer was to remove the privileged intranet entirely and move its corporate apps onto the Internet, checking every request by who the user is and which device they're on, never by which network they came from. That idea, now called zero trust, is how modern systems treat calls between their own services too.

Numbers first: checking identity on every request

Your app has 1 million active users, each making a request about every 10 seconds: 100,000 requests per second. Every one must carry proof of who sent it. Two classic designs:

Server-side sessionSigned token (JWT), 15-minute lifetime
What the client holdsA random session ID in a cookieA signed token listing who the user is and when it expires
Lookups in a central storeEvery request: 100,000/s to Redis or the databaseNone per request; only refreshes: 1,000,000 ÷ 900 s ≈ 1,111/s
Cost per checkA network round trip (~1 ms)A signature check in memory (microseconds)
Log out / ban a userDelete the session: instantThe token keeps working until it expires: up to 15 minutes

Tokens trade instant revocation for scale and independence: any service can check a token without calling anyone. Most big systems use both: short-lived tokens for speed, plus a refresh step where the central system can say no.

Two questions: authentication and authorization

  • Authentication (often “authn”): who are you? Proven with a password, a passkey, a certificate, a token. Failing it should give HTTP 401 Unauthorized.
  • Authorization (“authz”): what may you do? “Alice may read order 42 but not refund it.” Failing it gives 403 Forbidden.
💡 Big idea Centralize authentication (one identity provider issues short-lived, signed tokens), but enforce authorization close to the data (each service checks what this caller may do). Trust nothing because of where it comes from on the network: every call, from a user or a service, carries a verifiable identity.
🧠 Analogy: the hotel

At check-in you show your passport once (authentication at the identity provider). You get a key card (a token) that opens your room and the gym until Friday (scopes and expiry). Doors check the card themselves without phoning the front desk (local token verification). If you lose the card, the front desk can cancel it, but some doors only learn about that when they next sync (the revocation problem).

OAuth is the valet key: you let the parking attendant drive your car without handing over your house keys. A third-party app gets limited access to your photos without ever seeing your password.

JWT: a signed note anyone can read

A JWT (JSON Web Token, RFC 7519) is three base64url-encoded parts joined by dots: header.payload.signature.

  • Header: the signing algorithm, for example HS256 (a shared secret) or RS256/ES256 (a private key signs, a public key verifies).
  • Payload: “claims”: iss (who issued it), sub (the user), aud (which service it's for), exp (expiry time), plus your own (roles, scopes).
  • Signature: proves nobody changed the header or payload. It is not encryption: anyone holding the token can read the payload. Never put secrets in it.

With public-key algorithms, the identity provider publishes its public keys at a JWKS (JSON Web Key Set) URL, so every service can verify tokens on its own. That is what makes JWTs scale.

The strict verifier does four things every service must do: accept only the algorithms it expects (never the one the token asks for), check the signature, check exp, and check aud so a token minted for the photo service can't be replayed against the payments service. Then look at the lifetime slider: 5-minute tokens mean a stolen token dies fast but the auth server handles 3,333 refreshes a second for a million users; 24-hour tokens mean 12 a second, and a stolen token works all day.

🔥 Real vulnerability · JWT libraries trusting “alg”, 2015

The JWT standard includes an algorithm called none, meaning “no signature”, intended for tokens whose integrity is already checked some other way. Researcher Tim McLean found that some libraries treated a token with "alg": "none" as validly signed. Anyone could write their own token with any payload. A second flaw let attackers sign with a server's public RSA key using HS256. (Auth0 write-up.)

Lesson: never let the token choose how it's verified. Pin the expected algorithm in the verifier, and use a well-maintained library.

OAuth 2.0 and PKCE: letting an app act for you

OAuth 2.0 (RFC 6749, 2012) is about delegated authorization: you let an app access your data at some service without giving the app your password. Four roles: the resource owner (you), the client (the app), the authorization server (where you log in), and the resource server (the API with your data).

The recommended flow is the authorization code flow with PKCE (Proof Key for Code Exchange, RFC 7636, which says it is pronounced “pixy”). PKCE stops an attacker who intercepts the one-time code from trading it for tokens. The 2025 OAuth security best practice (RFC 9700) says public clients like mobile and single-page apps must use PKCE, and that the old “implicit” flow should not be used.

The core trick of PKCE: the app proves at step 5 that it's the same app that started the flow at step 1, using a secret (the verifier) that never travelled through the browser. Only its hash did. An intercepted code is useless without it.

OIDC and SSO: logging in, not just granting access

OAuth answers “may this app access the API?”. It doesn't say who the user is. OpenID Connect (OIDC) is an identity layer on top of OAuth 2.0: the same flow also returns an ID token, a JWT describing the user (sub, email, name). That's what “Sign in with Google” is. Single sign-on (SSO) uses OIDC or the older SAML (Security Assertion Markup Language) standard so employees log in once at an identity provider (Okta, Microsoft Entra ID, Google Workspace) and reach every internal app.

Service to service: mTLS, zero trust and policy

  • mTLS (mutual TLS): in normal TLS only the server shows a certificate; in mTLS the client does too. Each workload gets its own identity, for example a SPIFFE (Secure Production Identity Framework for Everyone) ID like spiffe://shop.example/ns/prod/sa/orders, issued and rotated automatically by the mesh or by SPIRE.
  • Zero trust: being inside the network proves nothing. The payments service accepts calls only from identities that are allowed to call it, and still checks the end user's token for what they may do.
  • Passing the user along: the gateway verifies the user's token at the edge, then forwards it (or a narrower token issued for the downstream service) so each service can make its own authorization decision.

A policy engine like Open Policy Agent (OPA) moves these rules out of application code into one place: the service asks “allow?” with the request details, and the engine answers from policies written in a language called Rego.

✏️ Worked example: picking a token lifetime

2 million active users. Each access token lives T minutes; when it expires, the app calls the auth server with its refresh token.

Lifetime TRefreshes per second (2,000,000 ÷ 60T)Stolen token window
5 min2,000,000 ÷ 300 ≈ 6,667/s5 min
15 min2,000,000 ÷ 900 ≈ 2,222/s15 min
60 min2,000,000 ÷ 3,600 ≈ 556/s1 hour

A few thousand refreshes per second is easy for a replicated auth service, and the refresh is your chance to check for bans and password changes. That's why 5–15 minutes is a common default. For emergencies, keep a small deny-list of revoked token IDs (jti) that services check; it only needs to hold entries until they would have expired anyway.

🧰 Tools you'll actually use

Identity providers: Keycloak (open source), Auth0 / Okta, AWS Cognito, Microsoft Entra ID, Google Identity Platform. Token libraries: jose (Node), PyJWT / Authlib (Python), Nimbus (Java). Workload identity: SPIFFE / SPIRE, or your mesh (Istio, Linkerd issue mTLS certificates automatically). Policy: Open Policy Agent; Zanzibar-style systems for relationship-based checks.

// Node: verify an access token at a service, the strict way (jose library)
import { createRemoteJWKSet, jwtVerify } from "jose";
const JWKS = createRemoteJWKSet(new URL("https://auth.example.com/.well-known/jwks.json"));

const { payload } = await jwtVerify(token, JWKS, {
  issuer: "https://auth.example.com",   // who must have issued it
  audience: "orders-api",               // it must be meant for THIS service
  algorithms: ["RS256"],                // never trust the token's own "alg"
});                                        // exp is checked automatically
# orders.rego: an OPA policy, kept outside the service's code
package orders.authz

default allow := false

allow if {                                 # customers may read their own orders
  input.method == "GET"
  input.order.owner == input.user.sub
}
allow if {                                 # support staff may read any order
  input.method == "GET"
  "support" in input.user.roles
}

Try it cheaply: docker run --rm -it openpolicyagent/opa:latest version, then paste the policy into OPA's online Rego playground with a sample input. To read any test token's payload in a terminal: echo "$TOKEN" | cut -d. -f2 | base64 -d (it isn't encrypted).

🚀 Startup vs big tech

Founding engineer (0 → 1)

Don't build auth. Use a managed identity provider (or your framework's battle-tested sessions), offer “Sign in with Google” via OIDC, store sessions in Redis or use short-lived tokens, and check permissions in one well-tested module. Add SSO (SAML/OIDC) when your first enterprise customer asks; they will.

Big tech (1 → 100)

A central identity platform issuing short-lived tokens, mTLS for every workload with automatic rotation, zero-trust access for employees (BeyondCorp-style), authorization as a service (Zanzibar-style systems or OPA), and security reviews for any new token type or scope.

🎤 Interview angle

Most designs need one or two sentences on auth. A senior version:

  • Users authenticate with an identity provider via OIDC; the API gets short-lived access tokens (5–15 min) plus refresh tokens.
  • The gateway verifies tokens; services still authorize each action (and check aud).
  • Service-to-service calls use mTLS identities from the mesh; nothing is trusted for being “inside”.
  • You can explain the revocation trade-off and how you'd ban a user right now (deny-list, short lifetime, refresh checks).

Common follow-ups: “Why not just use the user's session cookie between services?” · “How does a mobile app do OAuth safely?” · “Where do permissions live, and how do you change them without a deploy?”

🏭 In the real world
Zero trust for employees 🏢 Google · 2014 BeyondCorp: A New Approach to Enterprise Security

How: Google removed the requirement for a privileged corporate network and moved its corporate applications to the Internet, granting access based on the user and device rather than the network location.

Why this method: with mobile and cloud work, the perimeter was becoming impossible to enforce, and a breached perimeter gave attackers easy access to everything inside.

Authorization code + PKCE 📜 IETF · 2012 / 2015 / 2025 RFC 7636: PKCE

How: OAuth 2.0 (RFC 6749) defines the roles and grants; PKCE adds a one-time verifier whose SHA-256 hash is sent first. The OAuth security best practice (RFC 9700) requires PKCE for public clients.

Why this method: public clients like mobile apps can't keep a secret, and their redirect can be intercepted; PKCE binds the code to the app that asked for it.

Authorization for billions of users 🏢 Google · 2019 Zanzibar (USENIX ATC)

How: one global system stores access-control relationships for services like Calendar, Cloud, Drive, Maps, Photos and YouTube. The paper reports trillions of access control lists, millions of checks per second, 95th-percentile latency under 10 ms and over 99.999% availability across 3 years.

Why this method: one consistent authorization service means every product shares the same sharing model and nobody reinvents permission checks.

Policy as code 🧰 Open source · CNCF graduated Open Policy Agent

How: OPA decouples policy decisions from enforcement: services, Kubernetes, CI pipelines and API gateways send structured input and get decisions back, evaluated from Rego policies.

Why this method: one policy language for many systems makes rules reviewable, testable and changeable without redeploying every service.

Identity for workloads 🧰 Open source · SPIFFE SPIFFE overview

How: SPIFFE defines identities for services and short-lived identity documents (SVIDs, SPIFFE Verifiable Identity Documents, as X.509 certificates or JWTs); SPIRE issues them, and meshes like Envoy can use them for mTLS.

Why this method: services move between machines constantly, so identity is tied to the workload, not to an IP address.

🤯 Fun fact · say it right

Check yourself

1. 3 million active users; access tokens last 10 minutes and are refreshed on expiry. Roughly how many refresh requests per second hit the auth server?
3,000,000 ÷ 600 s = 5,000/s. Shorter lifetimes mean more refreshes but a smaller window for stolen tokens; that's the dial you're choosing.
2. A single-page web app needs to call your API on behalf of logged-in users. Which approach is recommended?
RFC 9700 says public clients must use PKCE and the implicit flow should not be used, because tokens in redirects can leak. Sharing passwords with apps is exactly what OAuth exists to avoid.
3. Your services verify JWTs at the API gateway and then trust all internal traffic. An attacker gets into one internal service. What's the best improvement?
“Inside the network” isn't proof of anything. With workload identities and per-service authorization, a compromised service can only make the calls its own identity is allowed to make.
📝 TL;DR
  • Authentication = who you are (401); authorization = what you may do (403). Centralize the first, enforce the second near the data.
  • Sessions: instant revocation, a lookup per request. JWTs: local verification, revocation delayed by the lifetime. Use short-lived access tokens + refresh.
  • Verify strictly: pinned algorithm, signature, exp, iss, aud. A JWT is signed, not encrypted.
  • OAuth 2.0 authorization code + PKCE for apps; OIDC adds login (ID token); SSO for employees.
  • Zero trust between services: mTLS workload identities, policy engines (OPA), relationship-based checks at scale (Zanzibar).
