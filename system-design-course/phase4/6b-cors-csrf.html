Phase 4 · Lesson 6b

Browser security for backends: CORS, CSRF & cookies

Browsers run code from every website you visit, and they attach your cookies to requests on their own. Three backend decisions, your CORS headers, your cookie flags and your CSRF defence, decide whether some other website can read your users' data or act as them.

🧰 You'll need (quick reminders)
  • Sessions vs tokens: a session ID in a cookie, or a short-lived signed token (JWT) sent in an Authorization header (Lesson 4.6).
  • API gateway: the front door that runs the same checks for every service (Lesson 1.6).
  • HTTP basics: methods (GET, POST, PUT, DELETE), headers, and HTTPS = HTTP inside TLS encryption (Lessons 0.2 and 0.4).
🎯 Hook

In October 2016, James Kettle of PortSwigger published research on misconfigured CORS headers. One bitcoin exchange's API took whatever website was calling it and echoed it back as allowed, with cookies allowed too. So any web page a logged-in user visited could quietly call the exchange's “give me my API key” endpoint and read the answer.

With that key, he wrote, he could turn off the user's notifications, lock them out with two-factor login, and move their bitcoins. In his words: “That's pretty severe for a header misconfiguration.” He reported it instead, and the exchange fixed it within 20 minutes. By the end of this lesson you'll know exactly which header did it, and the three settings that stop that whole family of attacks.

Numbers first: what CORS costs before it protects anything

Your single-page app (an SPA: one page whose JavaScript calls APIs) lives at https://app.shop.example. Its API lives at https://api.shop.example. Different hostnames, so the browser treats every call as cross-origin. Calls that send JSON or an Authorization header need permission first: an extra OPTIONS request called a preflight.

Setup (typical numbers: 100 ms phone round trip)Requests on the wire per API callExtra wait per call
Same origin: the gateway serves app.shop.example/api/…10 ms
Cross-origin, “simple” request (plain GET, no custom headers)10 ms
Cross-origin JSON + Authorization, no Access-Control-Max-Age2 almost every time+100 ms
Same, with Access-Control-Max-Age: 72002 the first time per URL, then 1+100 ms once per URL per 2 h

Without a max-age, the Fetch standard caches a preflight for just 5 seconds. At 5,000 API calls per second, your gateway then answers up to 5,000 extra OPTIONS requests per second: double the requests, for work that returns no data. The preflight cache is also per URL, so /orders/1 and /orders/2 each need their own.

gateway load ≈ API calls/s × (1 + share of calls that need a fresh preflight) “Every call that isn't covered by a cached preflight costs a second request, and a second round trip for the user.”

The rule underneath everything: the same-origin policy

An origin is three things together: scheme (https), host (app.shop.example) and port (443). The same-origin policy (SOP), built into every browser, decides what JavaScript from one origin may do with another. Compared with https://app.shop.example:

URLSame origin?Same site?Why
https://app.shop.example/orders✅ yes✅The path doesn't count
http://app.shop.example❌❌Different scheme
https://app.shop.example:8443❌✅Different port
https://api.shop.example❌✅Different host, same registrable domain
https://evilshop.example❌❌Looks similar, totally different site

A site is looser than an origin: the scheme plus the registrable domain (the part you buy, like shop.example). All subdomains of shop.example are “same-site”. Cookies' SameSite rule (below) works on sites, CORS works on origins. Remember that difference; attackers do.

MDN sums up the policy in three lines, and they explain this whole lesson:

  • Cross-origin writes are typically allowed: links, redirects, form submissions.
  • Cross-origin embedding is typically allowed: images, scripts, stylesheets.
  • Cross-origin reads are typically disallowed: your JavaScript can't read another origin's response… unless that server says so with CORS.
💡 Big idea The browser lets any page send requests almost anywhere, but stops it reading the answers. CORS (Cross-Origin Resource Sharing) is how your server lifts the read block for specific origins. CSRF (Cross-Site Request Forgery) abuses the send half: another site makes the browser send a request, and the browser attaches your user's cookies. So: CORS decides who may read; cookie flags and CSRF defences decide whose writes you accept. Neither one is authentication.
🧠 Analogy: an assistant carrying your ID badge

Your browser is an assistant who wears your company badge (cookies) everywhere. Any stranger (a website) can hand the assistant an envelope to deliver to your bank, and the assistant flashes your badge at the bank's door automatically. That's CSRF. The assistant won't hand the bank's reply back to the stranger unless the bank wrote “OK to show this to X” on it: that's CORS. SameSite teaches the assistant to hide the badge for strangers' envelopes. A CSRF token is the bank asking for a code that's printed only on its own forms.

CORS: how a server says “this origin may read”

When JavaScript calls another origin, the browser adds an Origin header saying who's asking. What happens next depends on whether the request is simple. Per MDN and the Fetch standard, a request is simple when:

  • the method is GET, HEAD or POST, and
  • it sets only safelisted headers (like Accept, Content-Language), with no Authorization and no custom X-… headers, and
  • any Content-Type is one an HTML form could send: application/x-www-form-urlencoded, multipart/form-data or text/plain. application/json is not on the list.

Simple requests go straight to the server. The browser only checks the response headers afterwards to decide whether JavaScript may read it. Everything else is preflighted: the browser first sends OPTIONS with Access-Control-Request-Method and Access-Control-Request-Headers, and only sends the real request if the server's answer allows it. Preflights never carry cookies.

Response headerWhat it saysGotcha
Access-Control-Allow-OriginWhich origin may read: one exact origin, or ** is refused when the request includes cookies
Access-Control-Allow-Credentials: trueReads are allowed even when cookies were sentCombined with a sloppy origin check, this is the dangerous one
Access-Control-Allow-MethodsMethods allowed beyond GET/HEAD/POST (preflight)Forget PUT and every update fails
Access-Control-Allow-HeadersRequest headers allowed (preflight)Authorization and JSON's Content-Type must be listed
Access-Control-Max-AgeSeconds the preflight may be cachedDefault 5 s; Chromium caps it at 7,200, Firefox at 86,400
Vary: OriginTells caches and CDNs (content delivery networks, Lesson 1.4) the answer depends on OriginWithout it, a CDN can serve one origin's headers to another

One more thing the CORS error hides: for security, JavaScript only learns “it failed” (TypeError: Failed to fetch). The reason is printed only in the browser's DevTools console. That's why CORS bugs feel mysterious: always look at the console and the network tab.

The misconfigurations attackers look for

  
    
    
  • Reflect any Origin + Allow-Credentials: true: every website on the internet can read logged-in users' data. Common because it “makes the CORS error go away”.
    • 
    
  • Sloppy matching: endsWith("shop.example") or a regex without a dot and anchors also matches evilshop.example. The cors package for Express documents this exact example: /example\.com$/ reflects any origin ending in example.com.
    • 
    
  • Allowing null: sandboxed iframes and some redirects send Origin: null, and any attacker can create one. Never allow it.
    • 
    
  • Believing CORS protects the API. It doesn't: curl, Postman and servers ignore it entirely. The cors README says it plainly: CORS is not access control. You still need authentication and authorization (Lesson 4.6).
    • 
  


  
CSRF: when the request itself is the attack

  
Look again at the simple-request rule: a form POST goes straight to the server, cookies and all. CORS only stops the attacker reading the reply. For a money transfer, the reply doesn't matter: the money already moved. PortSwigger's Web Security Academy lists three conditions for CSRF: an action worth inducing, cookie-only session handling, and no unpredictable parameters in the request. Remove any one and the attack dies.

  
<!-- on https://evil.example: the victim only has to visit the page -->
<form action="https://bank.example/transfer" method="POST">
  <input type="hidden" name="to" value="mallory">
  <input type="hidden" name="amount" value="1000">
</form>
<script>document.forms[0].submit()</script>

SameSite cookiesStrict: never sent on requests started by another site. Lax: sent on cross-site top-level navigations with safe methods (clicking a link), not on cross-site POSTs, images or fetches. None (needs Secure): always sent.Lax still sends cookies on cross-site GET links, so a state-changing GET is exploitable. And all subdomains are same-site.

Chrome made SameSite=Lax the default for cookies that don't say (Chrome 80, rolled out during 2020), with a 2-minute exception that still lets brand-new cookies ride on top-level POSTs. MDN notes that only some browsers default to Lax, and OWASP calls SameSite defence in depth, not a replacement. So: set SameSite explicitly, never change state on GET, and still use your framework's CSRF protection.

Where should a token live: cookie or localStorage?

  
XSS (cross-site scripting: an attacker's JavaScript running on your page) is the other half of this story (Lesson 6.6). A token in localStorage is readable by any script on the page, so XSS can copy it and use it from anywhere, for as long as it lives. An HttpOnly cookie can't be copied, but it rides along automatically, so you need CSRF defences. OWASP's warning applies to both: XSS can defeat all CSRF defences, because the attacker's script runs as you while the page is open. The 2026 best practice for browser apps from the IETF (Internet Engineering Task Force, the internet's standards body), RFC 10017, strongly recommends a backend for frontend (BFF, Lesson 1.6) for business and personal-data apps: the SPA holds only an HttpOnly, Secure cookie, and the BFF keeps the OAuth tokens server-side.


  
Do CORS once, at the gateway

  
Thirty services each writing their own CORS rules means thirty chances to reflect any origin. Put it at the gateway (Lesson 1.6): one reviewed allowlist, preflights answered at the edge without touching services, Vary: Origin on every response so the CDN (Lesson 1.4) keeps per-origin copies, and a long Max-Age. Better still, avoid CORS: route app.shop.example/api/* to the API through the same gateway, and the browser sees one origin. In development, the same trick is a dev-server proxy (Vite's server.proxy, for example), instead of loosening production CORS.


  

    ✏️ Worked example: what preflights cost a dashboard
    
An analytics SPA makes 200 API calls in a 30-minute session, across 40 distinct URLs, all JSON with an Authorization header. Phone round trip: 100 ms. Across all users: 5,000 calls/s.

    
    
      
  • No Max-Age (5 s cache): almost every call is preflighted: 200 preflights × 100 ms = 20 s of extra waiting per session; the gateway sees 5,000 + 5,000 = 10,000 requests/s.
    • 
      
  • Max-Age 7,200: one preflight per URL per session: 40 × 100 ms = 4 s; preflights are 40 ÷ 200 = 20% of calls, so the gateway sees 5,000 × 1.2 = 6,000 requests/s.
    • 
      
  • Same origin via the gateway: 0 preflights, 0 s, 5,000 requests/s.
    • 
    

    
One header saves 16 seconds per session and 4,000 requests per second. One routing rule saves all of it.

  


  

    🧰 Tools you'll actually use
    
Express's cors package, nginx / Envoy / Kong CORS settings, AWS API Gateway and Cloudflare CORS options; built-in CSRF protection in Django, Rails, ASP.NET Core, Spring Security, and Go 1.25's http.CrossOriginProtection; Burp Suite (PortSwigger) for testing. An exact allowlist in Express:


import cors from "cors";
const allowed = ["https://app.shop.example", "https://admin.shop.example"];
app.use(cors({
  origin: (origin, cb) => cb(null, allowed.includes(origin)), // exact match: never endsWith, never reflect
  credentials: true,
  methods: ["GET", "POST", "PUT", "DELETE"],
  allowedHeaders: ["Content-Type", "Authorization"],
  maxAge: 7200,                                       // Chromium's cap
}));

    
The same at an nginx gateway, answering preflights at the edge:


map $http_origin $cors_origin {             # exact allowlist; anything else gets ""
    default                     "";
    "https://app.shop.example"  $http_origin;
}
location /api/ {
    if ($request_method = OPTIONS) {
        add_header Access-Control-Allow-Origin      $cors_origin always;
        add_header Access-Control-Allow-Credentials "true" always;
        add_header Access-Control-Allow-Methods     "GET, POST, PUT, DELETE" always;
        add_header Access-Control-Allow-Headers     "Content-Type, Authorization" always;
        add_header Access-Control-Max-Age           7200 always;
        add_header Vary Origin always;
        return 204;                              # never reaches the service
    }
    add_header Access-Control-Allow-Origin      $cors_origin always;
    add_header Access-Control-Allow-Credentials "true" always;
    add_header Vary Origin always;
    proxy_pass http://api;
}

    
The session cookie, and CSRF protection in Go 1.25+ (it checks Sec-Fetch-Site and Origin, and lets safe methods through):


Set-Cookie: __Host-session=9f8a…; Path=/; Secure; HttpOnly; SameSite=Lax; Max-Age=86400

// Go: reject cross-origin unsafe requests, no tokens needed
cop := http.NewCrossOriginProtection()
cop.AddTrustedOrigin("https://admin.shop.example")
http.ListenAndServe(":8080", cop.Handler(mux))

    
Try it locally: ask your API what it would tell a hostile origin. If the answer echoes evil.example with Allow-Credentials: true, you've found the 2016 bug: curl -si -X OPTIONS https://api.yours.example/me -H 'Origin: https://evil.example' -H 'Access-Control-Request-Method: GET' | grep -i access-control.

    🚀 Startup vs big tech
    

      
Founding engineer (0 → 1)
Serve the SPA and the API from one origin, so CORS never comes up. Use your framework's sessions with a __Host-, HttpOnly, Secure, SameSite=Lax cookie, keep its built-in CSRF protection on, and never change state on GET. If you must use CORS, write an exact allowlist once, at the edge.

      
Big tech (1 → 100)
A central edge policy: CORS allowlists per API, reviewed like firewall rules; Fetch Metadata checks for every unsafe request; user-generated content on a separate registrable domain (GitHub moved Pages to github.io for exactly this); BFFs for web apps (RFC 10017); and automated scanners that probe every endpoint with hostile Origin headers.

    

  


  

    🎤 Interview angle
    
This rarely gets its own question, but it comes up in any web-facing design. A senior answer:

    
    
      
  • Separates the jobs: CORS controls reads by other origins, SameSite + tokens/Origin checks control forged writes, authn/authz still protect the API from everything else.
    • 
      
  • Avoids CORS where it can (same-origin routing at the gateway), and otherwise uses an exact allowlist with Vary: Origin and a long Max-Age.
    • 
      
  • Names the session cookie flags, and the cookie vs localStorage trade-off against XSS.
    • 
      
  • Knows why SameSite=Lax isn't enough alone: GET endpoints, sibling subdomains, older browsers.
    • 
    

    
Common follow-ups: “Your API is called from a partner's website with the user's session. How?” · “Why doesn't CORS protect against CSRF?” · “Where would you put CORS in a 50-service system?”

  


  

    🏭 In the real world
    

      
Reflected origin + credentials 📜 PortSwigger · 2016 Exploiting CORS misconfigurations for Bitcoins and bounties

      
How: a bitcoin exchange's API echoed any Origin back with Access-Control-Allow-Credentials: true, so a few lines of attacker JavaScript could read a visitor's private API key. Another site trusted any origin ending in its domain (so definitelynotadvisor.com got in), a second exchange any origin starting with its domain, and a third exchange allowed null. The first exchange patched within 20 minutes of the report.

      
Why this method: dynamically generating CORS headers from the request is the easy way to make errors disappear, which is why it's so common; the fix is a fixed allowlist with exact matching.

    

    

      
SameSite=Lax by default 🏢 Google Chrome · 2020 SameSite updates (Chromium)

      
How: Chrome 80 (stable on February 4, 2020) began treating cookies without SameSite as Lax and rejecting SameSite=None without Secure. The rollout was paused in April 2020 because of COVID-19, resumed on July 14, and on August 11 the target became 100% of Chrome 80+ users. web.dev explains the change.

      
Why this method: changing the browser's default protected millions of sites that never set the flag, without anyone deploying code.

    

    

      
User content off the main domain 🏢 GitHub · 2013 New GitHub Pages domain: github.io

      
How: GitHub Pages sites ran users' JavaScript on github.com subdomains, which could write (not read) github.com cookies, enough to fixate a user's CSRF token or lock them out. GitHub moved all Pages to a dedicated github.io domain.

      
Why this method: SameSite and cookie scope stop at the registrable domain. A separate domain makes untrusted content cross-site, so none of the main site's cookies apply.

    

    

      
Tokens, Fetch Metadata, built-ins 🧰 OWASP · Go OWASP CSRF Prevention Cheat Sheet

      
How: OWASP's guide says to use your framework's built-in protection first, recommends synchronizer tokens or the signed double-submit cookie, and describes Sec-Fetch-Site as the primary signal for a Fetch Metadata policy. Go 1.25 shipped http.CrossOriginProtection, which uses those headers with no tokens or cookies.

      
Why this method: hand-rolled token schemes are easy to get subtly wrong; letting the browser report where a request came from removes the shared secret entirely.

    

    

      
Tokens out of the browser 📜 IETF · 2026 RFC 10017: OAuth 2.0 for Browser-Based Applications

      
How: the best current practice describes three architectures and strongly recommends the backend-for-frontend for business, sensitive and personal-data apps. Its BFF cookies must be Secure and HttpOnly, and should be SameSite=Strict with no Domain.

      
Why this method: if tokens never reach the browser, XSS has nothing to steal; the remaining risk is an attacker acting through the open page.

    

  


  

    🤯 Fun fact · why “simple” requests skip permission
    
CORS lets a cross-origin form-style POST through without asking the server first. That looks like a hole, but it's deliberate. MDN explains that HTML forms could already send these requests to any origin long before fetch() existed, so servers had to defend against CSRF anyway. CORS was designed not to make the web any less safe than it already was. That's also exactly why CSRF still exists: the old hole was never closed, only fenced.

Check yourself

  

    
1. Your SPA on app.example makes 6,000 calls per second to api.example, all JSON with an Authorization header, and the API sends no Access-Control-Max-Age. Roughly how many requests per second reach the gateway?

    

    
JSON and Authorization make every call preflighted, and the default preflight cache lasts only 5 seconds per URL, so nearly every call costs an extra OPTIONS: ≈ 12,000/s, half of them returning no data. A long Max-Age cuts that; same-origin routing removes it.

  

  

    
2. To make a CORS error go away, a teammate set the API to copy the request's Origin into Access-Control-Allow-Origin and to send Access-Control-Allow-Credentials: true. What should you change it to?

    

    
Reflecting any origin with credentials lets every website read your logged-in users' data: the 2016 bitcoin-exchange bug. Browsers refuse * with credentials anyway, and curl was never the threat: CORS only constrains browsers. Match exact origins and add Vary: Origin so caches don't mix them up.

  

  

    
3. A bank's session cookie is SameSite=Lax and its POST /transfer requires a CSRF token. But GET /settings/email?new=… changes the account email. Which attack works?

    

    
Lax still sends cookies on cross-site top-level GET navigations, and token checks usually cover only unsafe methods. Changing the email lets the attacker reset the password: account takeover. The form POST is blocked by Lax and the token; the JSON fetch is preflighted and refused. Rule: never change state on GET.

  


  

    📝 TL;DR
    
    
      
  • Origin = scheme + host + port. The same-origin policy allows cross-origin sends but blocks reads; CORS lets a server allow reads for chosen origins.
    • 
      
  • Simple requests (GET/HEAD/POST with form-like bodies) skip the preflight; JSON or Authorization costs an OPTIONS round trip unless Max-Age caches it (default 5 s, Chromium cap 7,200 s).
    • 
      
  • Never reflect any origin with credentials, never suffix-match, never allow null; do CORS once at the gateway, or avoid it with same-origin routing.
    • 
      
  • CSRF: the browser attaches cookies to forged requests. Defend with SameSite, framework CSRF tokens or Origin/Sec-Fetch-Site checks, and no state changes on GET.
    • 
      
  • Session cookie: __Host-, Secure, HttpOnly, SameSite=Lax or Strict, no Domain. Tokens in localStorage trade CSRF for XSS risk; a BFF keeps tokens off the browser.
    •
