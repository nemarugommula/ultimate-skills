Phase 4 · Lesson 5

API design, versioning & backward compatibility

You can deploy your server in minutes, but you can't update the apps on people's phones or the code your partners wrote three years ago. Changing an API without breaking them is a core senior skill.

🧰 You'll need (quick reminders)
  • APIs, REST, gRPC and protocol buffers (protobuf): how programs call each other, and gRPC's compact binary format with a schema (Lessons 0.4 and 4.3).
  • Rolling deploy: replace servers a few at a time, so old and new code run side by side for a while (Lesson 6.2 goes deeper).
  • Events in Kafka are stored for days or forever, so new code must read messages written by old code (Lesson 3.2).
🎯 Hook

In 2017, Stripe wrote that it had maintained compatibility with every version of its API since the company started in 2011. Code written against Stripe years earlier still worked unchanged.

The trick: every account is pinned to the API version that was current on its very first request. When Stripe makes a breaking change, it ships a small “version change module” that can transform new responses back into the old shape. Requests walk back through those modules until they match the caller's version. Today Stripe releases a new API version monthly. This lesson is how to evolve an API without breaking the people who depend on it.

Numbers first: who is still running old code?

A typical consumer app with 2 million monthly users. App stores let you ship an update, not force one. Suppose (typical shape, your numbers will differ):

ClientShare of trafficCan you make them update?
App versions from the last month60%They'll update soon
App versions 1–12 months old30%Only with a “please update” screen, which annoys people
Partner integrations10%No: they shipped once and moved on

Rename one field in a response and up to 40% of traffic, about 800,000 people, may see errors. Even your own services aren't safe: during a rolling deploy of 6 servers, old and new code serve traffic together for minutes. Every change must work with both.

Two directions of compatibility

Backward compatible
New server, old clients still work. “I can upgrade the server without anyone updating.” This is the one you must never break.
Forward compatible
Old code copes with data from newer code, for example by ignoring unknown fields. This is what makes rolling deploys and stored events safe.
💡 Big idea An API is a promise. Make changes additive (new optional fields, new endpoints) and make readers tolerant (ignore what they don't know). For anything else, run the old and new forms side by side, move everyone over, then remove the old one.
🧠 Analogy: the electrical socket

Houses built decades ago still take today's appliances because the socket shape didn't change. Manufacturers add things (a USB port next to the socket) without changing the holes. When a country really does switch standards, it sells adapters and lets both shapes coexist for years. Removing the old socket on a Tuesday would break every lamp in town.

Safe changes vs breaking changes

These rules come from Google's API guidelines (AIP-180; AIPs are “API Improvement Proposals”) and the protobuf docs:

✅ Usually safe❌ Breaking
Add a new endpoint or methodRemove or rename a field, endpoint or enum value
Add an optional field to a responseChange a field's type (integer → string) or format
Add an optional request field whose default keeps the old behaviorAdd a required request field, or make an optional one required
Add an enum value (⚠️ wire-safe, but breaks clients that switch over every value and crash on unknown ones)Change the meaning of a field (cents → dollars) even if the type stays the same
Protobuf: delete a field and mark its number reservedProtobuf: change a field's number, or reuse an old one

Protobuf sends field numbers, not names, on the wire, so a rename doesn't break binary data, but it does break JSON clients and generated code. A semantic change is the worst kind: nothing errors; everyone silently gets wrong answers.

Deprecating something old: announce it, add response headers (Deprecation, RFC 9745, and Sunset, RFC 8594, which gives the shutdown date), measure who still calls it (log by API key and client version), contact them, and only then turn it off. Without usage data, “deprecated” lasts forever.

Contract tests catch breaks before deploy. With Pact, each consumer's tests record what it expects from a provider (a “pact”); the provider's CI (the automated build and test on every change) checks every change against all its consumers' pacts. For protobuf, buf breaking compares your schema with the last released one and fails the build on breaking changes.

Changing the database under a running system: expand and contract

The same problem hits your own database. Renaming a column in one step breaks every server still running the old code. The fix is parallel change, also called expand and contract: expand (add the new form alongside the old), migrate (move readers and writers over, backfill old rows), contract (remove the old form). Each step is safe with both the previous and next version of the code.

✏️ Worked example: the cost of a one-step rename

Rename users.fullname to display_name. The service runs 6 servers at 1,000 requests/s; a rolling deploy replaces one server every 30 s, so it takes 3 minutes.

  • The rename runs first. Old servers still query fullname and fail.
  • Old servers left in each 30-s slice: 6, 5, 4, 3, 2, 1 (out of 6).
  • Failed requests ≈ 1,000 × 30 × (6 + 5 + 4 + 3 + 2 + 1) ÷ 6 = 1,000 × 30 × 3.5 = 105,000.

That's over half of the 180,000 requests during the deploy. Expand and contract takes 6 small steps and fails zero. Run both below.

🧰 Tools you'll actually use

Schemas: OpenAPI for REST, .proto files for gRPC, schema registries for events (Confluent Schema Registry checks Avro/protobuf compatibility). Break detection: buf breaking, Pact contract tests, OpenAPI diff tools. Migrations: Flyway, Liquibase, Rails/Django migrations, plus online schema-change tools such as GitHub's gh-ost for big MySQL tables.

// order.proto: evolving a message safely
message Order {
  reserved 4;                    // field 4 (old "coupon_code") was deleted: never reuse the number
  reserved "coupon_code";
  string id = 1;
  int64 amount_cents = 2;         // the unit is in the name, so nobody guesses
  string currency = 3;
  optional string discount_id = 5;  // added later: old readers just ignore it
}

# CI: fail the build if this schema breaks what's on main
$ buf breaking --against '.git#branch=main'
-- expand and contract, as separate migrations shipped days apart
ALTER TABLE users ADD COLUMN display_name text;            -- 1. expand (nullable, instant)
-- 2. deploy code that writes both columns
UPDATE users SET display_name = fullname                 -- 3. backfill, in batches
 WHERE display_name IS NULL AND id BETWEEN 1 AND 10000;
-- 4. deploy code that reads display_name   5. stop writing fullname
ALTER TABLE users DROP COLUMN fullname;                   -- 6. contract

On deprecated endpoints, send Deprecation: @1688169599 and Sunset: Sat, 31 Dec 2026 23:59:59 GMT, and log the caller's API key so you know whom to email.

Approach✅ Good❌ Costs
Additive-only, no versionsSimplest for everyone; no migrations for clientsOld fields pile up; needs strict review discipline

Date versions + pinningClients upgrade when they want, in small stepsThe provider maintains and tests a growing chain of transformations

🚀 Startup vs big tech

Founding engineer (0 → 1)

Put /v1/ in public URLs from day one (it's free), make every change additive, put units in field names (amount_cents), and use expand-and-contract for any rename. Ship a minimum-supported-version check in your mobile app early, so you can force an update in an emergency.

Big tech (1 → 100)

API review boards and style guides (Google's AIPs), linters and breaking-change checks in CI, schema registries enforcing compatibility for events, usage dashboards per client version, and formal deprecation policies measured in months or years for external APIs.

🎤 Interview angle

When you sketch an API in an interview, add one sentence on evolution. A senior answer covers:

  • Which changes are additive and safe, and that readers ignore unknown fields.
  • A versioning choice with a reason (URL version for a public API; additive-only for internal gRPC).
  • How you'd make a breaking change: side by side, measure usage, migrate, deprecate, remove.
  • For storage: expand and contract, and that rolling deploys mean two code versions run at once.

Common follow-ups: “You need to change a field's type. Walk me through it.” · “How do you know when it's safe to remove v1?” · “What about the events already in Kafka?”

🏭 In the real world
Date-based versions with pinning 🏢 Stripe · 2017 APIs as infrastructure: future-proofing Stripe with versioning

How: versions are named by release date; an account is pinned to the latest version on its first request; a Stripe-Version header can override per request; breaking changes live in version change modules that transform responses back to older versions. Since 2024-09-30.acacia, monthly releases have no breaking changes and two major releases a year carry them (Stripe docs).

Why this method: businesses run on Stripe as infrastructure; forcing them to rewrite integrations would break their revenue, so the cost of compatibility is carried by Stripe.

Compatibility rules for every Google API 🏢 Google · AIP-180 AIP-180: Backwards compatibility

How: within a major version, existing components must not be removed or renamed, and new required fields must not be added to existing requests; new fields must default to the old behavior.

Why this method: users write code against an API and ship it to production expecting it to keep working; written rules let thousands of engineers review changes the same way.

Updating a protobuf message 🧰 Open source · Protocol Buffers Language guide: updating a message type

How: adding fields is safe (old binaries ignore them); removing fields is safe if the number is never reused (mark it reserved); changing a field number is not safe; int32 → int64 is “compatible” but can silently truncate.

Why this method: the wire format identifies fields by number, so numbers are the real contract.

Parallel change 📜 Danilo Sato · 2014 ParallelChange (expand, migrate, contract)

How: split a backward-incompatible interface change into three phases: expand to support old and new, migrate the clients, then contract by removing the old.

Why this method: each phase is independently deployable and reversible, which is exactly what rolling deploys and many independent clients need.

Consumer-driven contract tests 🧰 Open source · Pact Pact docs

How: consumers record the requests they send and the responses they expect; providers verify against those contracts in CI.

Why this method: without it, the only way to know two services still work together is to deploy them both and test end to end.

🤯 Fun fact · still on v1

Stripe's URLs carry a major version, /v1/charges. In its 2017 post, Stripe said it reserves the right to use that prefix someday but found it hard to imagine a redesign important enough to justify the user impact. Small, dated versions did the job instead. And in protobuf, field numbers 19,000 to 19,999 are reserved for the protobuf implementation itself; the compiler rejects them.

Check yourself

1. 25% of your traffic comes from app versions that read the customer_email field. You rename it to email in one deploy. At 4 million requests a day, roughly how many requests may break daily?
25% × 4,000,000 = 1,000,000 requests a day from clients that can't be updated quickly. The safe path: add email alongside customer_email, move clients over, measure, then remove the old field.
2. In a protobuf message, field 7 is no longer needed. What should you do?
Old data and old binaries still use number 7 with the old meaning. Reusing it makes old messages decode as the new field: silent corruption. reserved makes the compiler refuse any reuse.
3. You must change price from an integer (cents) to a decimal string. Public partners use the API. Which plan is best?
That's expand, migrate, contract for an API. Changing the type breaks every partner at once; changing the meaning silently corrupts their numbers, which is even worse.
📝 TL;DR
  • You can't update every client: old apps, partners, stored events, and the other half of a rolling deploy.
  • Safe: add endpoints and optional fields; readers ignore unknown fields. Breaking: remove, rename, retype, make required, change meaning, reuse protobuf numbers.
  • When you must break: version (URL, header, or Stripe-style pinned dates), deprecate with data, then remove.
  • Expand → migrate → contract for APIs and databases; catch breaks in CI with contract tests and buf breaking.
