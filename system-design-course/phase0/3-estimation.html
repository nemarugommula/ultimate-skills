Phase 0 · Lesson 3

Latency numbers & back-of-the-envelope estimation

A handful of memorised numbers and five minutes of arithmetic tell you how many servers, how much storage and how much bandwidth a design needs. It's how seniors know which part of a system will break first, before anyone writes code.

🧰 You'll need (quick reminders)
  • QPS = requests per second; peak QPS ≈ daily users × requests each ÷ 86,400 × peak factor (Lesson 0.1).
  • RTT = round-trip time over the network; distance sets a floor (Lesson 0.2).
🎯 Hook

On August 3rd, 2013, people in Japan watched an airing of the film Castle in the Sky. At one moment, fans tweeted so hard that Twitter hit 143,199 tweets in a single second.

Twitter's average at the time: about 500 million tweets a day, which is 5,700 a second. The spike was about 25× the steady state, and Twitter says users didn't notice a blip. If you'd sized the system for the average, it would have fallen over twenty-five times. This lesson is the arithmetic that tells you that in advance.

Numbers first: the latency ladder

Jeff Dean of Google made this list famous in a 2009 talk as “numbers everyone should know”. The hardware is older now and some steps got faster, but the ratios are what you design with. (1 ns = a billionth of a second; 1 µs = a millionth; 1 ms = a thousandth.)

OperationTimeIf an L1 cache hit took 1 second…
L1 cache reference (memory inside the CPU)0.5 ns1 second
Main memory (RAM) reference100 ns3.3 minutes
Send 2 KB over a 1 Gbps network20 µs11 hours
SSD random 4 KB read (from a later, widely shared version of the list)150 µs3.5 days
Read 1 MB sequentially from memory250 µs5.8 days
Round trip within the same data center500 µs11.6 days
Disk seek (spinning disk)10 ms7.6 months
Read 1 MB sequentially from disk20 ms1.3 years
Packet California → Netherlands → California150 ms9.5 years

Four rules fall out of that table: memory is fast (a cache hit costs microseconds), a network hop inside the data center is about half a millisecond, disk is slow, and a trip across the world is forever. A request that makes 100 database calls in a loop pays 100 round trips; a request that calls another continent pays 150 ms before doing anything.

💡 Big idea You don't need exact numbers to design well; you need the right order of magnitude (the power of ten). Is it 10 QPS or 10,000? 10 GB or 10 TB? Being right within a factor of a few is enough to know whether you need one server or a hundred.
🧠 Analogy: the chef and the ingredients

A chef needs salt. On the counter (CPU cache): reach out, 1 second. In the fridge (RAM): a few minutes. In the shop down the street (SSD): a few days' trip at this scale. A different city (the data center network): a couple of weeks. Another country (a cross-ocean request): nine and a half years. Good chefs, like good systems, keep what they use most within arm's reach.

Typical sizes to assume, then say out loud as assumptions: a numeric ID is 8 bytes; a short text post with its metadata is a few hundred bytes; a JSON API response is a few KB (Stack Overflow's 2016 numbers work out to about 5.9 KB per HTTP request on average); a phone photo is a few MB; a minute of compressed video is a few tens of MB.

The recipe

  1. Traffic: daily users × requests each ÷ 86,400 = average QPS. Multiply by a peak factor (2–3× for normal daily swings is a common assumption; events can spike far higher, as Twitter saw).
  2. Split reads and writes. They scale differently (Lesson 0.1).
  3. Storage: writes per day × size per write × days kept × 3 (data is usually kept in about three copies for safety).
  4. Bandwidth: QPS × response size. Convert bytes to bits (× 8) for network links.
  5. Servers: peak QPS ÷ what one server handles, plus headroom. That per-server number must come from a load test of your code (Lesson 6.5), never from a blog.
storage per year = writes/day × bytes per write × 365 × copies “Writes per day times how big each one is, times the days in a year, times how many copies you keep.”
✏️ Worked example: a photo-sharing app with 10 million daily users

Assumptions (say them out loud): each user views 50 photos a day and uploads one every 10 days (0.1/day). An original photo is 2 MB; the feed shows a 200 KB version. Peak = 3× average.

  • Views: 10,000,000 × 50 ÷ 86,400 ≈ 5,800/s average, ≈ 17,400/s at peak.
  • Uploads: 10,000,000 × 0.1 ÷ 86,400 ≈ 12/s. Writes are tiny; reads are the problem (again).
  • Storage: 1,000,000 uploads/day × 2 MB = 2 TB per day → 730 TB per year → about 2.2 PB with 3 copies. That's object storage (Lesson 2.7), not a database.
  • Bandwidth: 5,800 views/s × 200 KB ≈ 1.16 GB/s ≈ 9.3 Gbps average, ~28 Gbps at peak. That's a CDN's job (Lesson 1.4).
  • App servers: if one handles ~1,000 requests/s (measure it!), peak needs 18, so run about 23 with 30% headroom (17,400 × 1.3 ÷ 1,000).

In five lines you've learned the design's real shape: object storage for petabytes, a CDN for tens of gigabits, and a modest fleet of app servers.

The lesson of the budget: dozens of memory reads cost nothing; a loop of database calls quietly costs tens of milliseconds; one cross-ocean call eats most of the budget by itself. That's why the fixes are “batch the calls”, “cache it in memory” and “keep the data in the same region as the code”.

🧰 Tools you'll actually use

Estimates are done in a notebook, a spreadsheet or a Python prompt. The per-server number comes from a load test: k6 (Grafana), wrk, Locust or JMeter locally, or managed versions like Grafana Cloud k6 and Azure Load Testing.

# estimate.py: the worked example, so you can change one assumption and rerun
dau, views, uploads = 10e6, 50, 0.1
photo, thumb, peak, copies = 2e6, 200e3, 3, 3          # bytes, bytes, ×, copies
read_qps = dau * views / 86400
print(f"reads: {read_qps:,.0f}/s avg, {read_qps*peak:,.0f}/s peak")
print(f"storage: {dau*uploads*photo*365*copies/1e15:.2f} PB/year")
print(f"egress: {read_qps*thumb*8/1e9:.1f} Gbps avg")
// load.js: how many requests/s can ONE server really take? (k6)
import http from 'k6/http';
export const options = { vus: 50, duration: '30s' };   // 50 virtual users for 30 s
export default function () { http.get('http://localhost:8080/photos/42'); }

Try it locally: python3 estimate.py, then start your app and run docker run --rm -i grafana/k6 run - <load.js. k6 prints requests per second and latency percentiles; raise vus until p99 latency climbs. That knee is your per-server capacity.

⚖️ Trade-offs: how precise should an estimate be?
✅ Rough (order of magnitude) is right when…❌ Get real numbers when…
Choosing between designs (one database or sharded? CDN or not?)Buying hardware, signing a cloud contract or setting autoscaling limits
In an interview or an early design docYou're within 2–3× of a known limit: measure with a load test
The answer is 100× away from any limitCost is a big part of the business (video, storage-heavy products)

Overestimating wastes money; underestimating causes outages. Most teams size for the expected peak plus headroom (often 30–50%), then let autoscaling (Lesson 5.3) handle the rest.

🚀 Startup vs big tech

Founding engineer (0 → 1)

Do the estimate once on a napkin to know when your single database will run out (“at 20× today's users”), then stop worrying. Spend the time on the product. Re-run the numbers when growth or a launch event (a TV spot, a big customer) changes the inputs.

Big tech (1 → 100)

Capacity planning is a job: teams forecast peak QPS and storage per quarter, load-test before big events, and budget hardware in advance (Lesson 6.5). Estimates are reviewed in design docs and checked against dashboards afterwards.

🎤 Interview angle

Interviewers don't check your arithmetic to the digit; they watch your process. A senior estimate:

  • States assumptions first (“say 100 M daily users, 10 reads each”) and rounds hard (86,400 ≈ 100,000).
  • Computes reads and writes separately, average and peak, then storage and bandwidth, keeping units.
  • Draws a conclusion from each number: “12 writes/s: one database is fine. 28 Gbps out: we need a CDN.”
  • Sanity-checks the result against something known.

Common follow-ups: “What if each user uploads 10× more?” “How much does a year of storage cost?” “Which number worries you most?”

🏭 In the real world
Numbers everyone should know 📜 Google · 2009 Jeff Dean, LADIS 2009 keynote (slides)

How: the slide lists L1 0.5 ns, main memory 100 ns, a data center round trip 500 µs, a disk seek 10 ms and a California–Netherlands–California packet 150 ms, followed directly by worked back-of-the-envelope calculations.

Why this method: at Google's scale, being able to estimate a design's cost in your head lets you discard bad designs before building them.

The original “approximate timings” 📜 Peter Norvig Teach Yourself Programming in Ten Years

How: the essay's answers section lists approximate timings for a typical PC: fetch from main memory 100 ns, read 1 MB sequentially from disk 20 ms, a packet US → Europe and back 150 ms.

Why this method: Norvig's advice is that a programmer should know these ratios, because they decide which code is fast more than clever algorithms do.

Peak is not average 🏢 Twitter · 2013 New Tweets per second record, and how!

How: 500 M tweets a day ≈ 5,700/s on average, and a one-second peak of 143,199/s, about 25× the steady state. The post explains the re-architecture that let Twitter absorb it.

Why this method: real traffic follows events (TV, sports, news), so systems must be sized and tested for spikes, not means.

Publishing your own numbers 🏢 Stack Overflow · 2016 Stack Overflow: The Architecture, 2016 Edition

How: a full day of stats: 209 M HTTP requests, 1.24 TB of HTTP traffic sent, 505 M SQL queries, 5.8 B Redis hits, on a small, listed set of servers.

Why this method: knowing your real per-day numbers is what lets you say with confidence that 9 web servers are enough, and spot the next limit early.

🤯 Fun fact · nine and a half years

On the human scale where an L1 cache hit takes one second, a single packet from California to the Netherlands and back takes about 9.5 years (150 ms ÷ 0.5 ns = 300 million). A CPU waiting on a cross-ocean network call is waiting the equivalent of a decade.

Check yourself

1. A chat app stores 2 billion messages a day, 200 bytes each, kept forever in 3 copies. Roughly how much new storage per year?
2 × 109 × 200 B = 400 GB per day. × 365 ≈ 146 TB per year. × 3 copies ≈ 438 TB. Order of magnitude: hundreds of terabytes a year, so plan for a database that partitions data across many machines (Lesson 2.4).
2. Which is slowest?
1 MB from memory ≈ 0.25 ms. 100 round trips in a data center ≈ 100 × 0.5 ms = 50 ms. One California–Netherlands round trip ≈ 150 ms. Distance beats almost everything.
3. Your API averages 3,000 QPS. One server handles 1,000 QPS. A big launch is next week and marketing expects a 10× spike for an hour. What do you do?
Peak = 10 × 3,000 = 30,000 QPS ÷ 1,000 = 30 servers, + 30% headroom ≈ 39. Autoscaling helps, but it takes minutes to react and needs limits and database capacity that allow it, so you still do the arithmetic and test it.
📝 TL;DR
  • Memorise the ladder: memory ~100 ns, SSD read ~150 µs, data center round trip ~0.5 ms, disk seek ~10 ms, cross-ocean round trip ~150 ms.
  • 1 M requests/day ≈ 12/s. Peak = average × a peak factor (2–3× daily, far more for events).
  • Storage = writes/day × size × days × copies. Bandwidth = QPS × response size × 8 bits.
  • Servers = peak ÷ measured per-server capacity + headroom. Always draw a conclusion from each number.
