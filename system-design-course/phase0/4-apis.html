Phase 0 · Lesson 4

APIs: REST, gRPC, GraphQL, WebSockets

An API is the contract for how clients and services talk to you: what they can ask, in what shape, and how updates reach them. The choice decides how many requests you serve, how fast users see changes, and how painful it is to change later.

🧰 You'll need (quick reminders)
  • HTTP = request (method, path, headers, body) → response (status code, body), over a connection that can be reused (Lesson 0.2).
  • RTT = one network round trip; every extra request a screen needs adds latency, especially on mobile (Lesson 0.2).
  • QPS = requests per second; clients × requests each ÷ time (Lesson 0.3).
🎯 Hook

In 2016 GitHub wrote that its REST API was responsible for over 60% of the requests made to its database tier. Part of the reason: to build one screen, a client had to call one endpoint, follow the links in the response, call again, and again. Responses were bloated with fields nobody asked for.

GitHub's answer was a new API in GraphQL, where a client asks for exactly the fields it needs in one request. The API style you choose isn't cosmetic: it directly sets how many requests hit your servers.

Numbers first: one screen, three ways

A mobile profile screen shows a user, their 10 latest posts, and each post's like count. The phone is 100 ms round trip from your servers.

API designRequests for one screenTime on the network
Naive REST: /users/7, then /posts/{id} for each post1 + 10 = 11 (if made one after another)~1,100 ms
REST with a screen-shaped endpoint: /users/7?include=posts1~100 ms
GraphQL: one query naming exactly the fields1~100 ms

Multiply by a million users opening the screen a few times a day, and the naive version sends 11× the requests to your servers and database. That's the 60% GitHub saw.

💡 Big idea Design an API around what clients actually need per screen or per call, and around how updates must reach them. Request count, payload size and freshness are all decided by the contract, long before any server is tuned.
🧠 Analogy: ordering food

REST is a menu of numbered dishes: simple, everyone understands it, but you get the whole dish. GraphQL is telling the waiter exactly what you want on one plate. gRPC is the kitchen's ticket shorthand that front and back of house agreed on: fast and compact, not meant for customers. For “is my food ready?”: polling is walking to the counter every minute to ask; long polling is waiting at the counter until it's ready; WebSockets and SSE are the buzzer they hand you; a webhook is them phoning you when it's done.

REST: resources and verbs

REST (REpresentational State Transfer) models your system as resources (nouns with URLs: /users/7, /orders/123) and uses HTTP methods as verbs. Responses are usually JSON.

MethodMeaningIdempotent?
GET /orders/123ReadYes
POST /ordersCreate (the server picks the ID)No
PUT /orders/123ReplaceYes
PATCH /orders/123Change some fieldsNot guaranteed
DELETE /orders/123DeleteYes

Idempotent means doing it twice has the same effect as once, so a client can safely retry it after a timeout. POST isn't: retrying “create payment” could charge twice. Payment APIs like Stripe's fix this with an idempotency key: the client sends a unique ID with the request, and the server remembers the first result for that key, so a retry returns the same answer instead of doing the work again (Lesson 3.3 goes deep).

Pagination: offset vs cursor

Lists must come in pages. Offset pagination says “skip 40, give me 20” (?offset=40&limit=20). It's simple and lets users jump to page 7, but the database still reads all the skipped rows, and if new items arrive between pages, everything shifts: you see duplicates or miss items. Cursor pagination says “give me 20 items after the one with ID abc” (Stripe calls it starting_after). It stays fast at any depth and is stable while items are added. Try both below.

gRPC: fast, typed calls between services

gRPC is an RPC framework (remote procedure call: call a function on another machine as if it were local). Google created it and open-sourced it in 2015 as the next version of Stubby, the internal RPC system that connected its microservices for over a decade. You define the service and messages in a .proto file using Protocol Buffers (protobuf), a binary format that's smaller and faster than JSON; code for client and server is generated from it. It runs on HTTP/2, so many calls share one connection, and supports streaming in either or both directions. It's the usual choice between your own services; browsers need a proxy to call it.

GraphQL: one endpoint, ask for exactly what you need

GraphQL was built at Facebook from 2012, when its new native mobile apps needed News Feed as data instead of HTML. The client sends a query listing the fields and nested objects it wants; one request returns exactly that. It's great for many different clients (web, iOS, Android) with different needs. The costs: caching is harder (everything is a POST to one URL), and a single clever query can ask the server for a huge amount of work, so you need query cost limits.

Getting updates to clients: real time

TechniqueHow it worksGood for

✏️ Worked example: what polling costs at a million users

A messaging app has 1,000,000 users online. Each gets about 1 message a minute.

  • Short polling every 5 s: 1,000,000 ÷ 5 = 200,000 requests/s. Messages: 1,000,000 ÷ 60 ≈ 16,700/s. So about 92% of requests come back empty, and users wait 2.5 s on average to see a message.
  • Poll every 1 s to make it feel live: 1,000,000 requests/s. You've built a denial-of-service attack against yourself.
  • WebSockets: 1,000,000 open connections, and only the ~16,700 messages/s actually travel, each arriving in about half a round trip. The new cost is memory and long-lived connections (Lesson 7.4 designs this).

🎮 Playground · Offset vs cursor pagination

A feed shows the newest posts first, 5 per page. Two readers scroll the same feed: one asks by offset (“skip 5×page”), the other by cursor (“5 posts older than the last one I saw”). Read a page, then make new posts arrive or delete one, then read the next page.

The feed right now (newest first):

Offset: ?offset=N&limit=5

Cursor: ?starting_after=ID&limit=5

offset: seen twice 0
offset: skipped 0
cursor: seen twice 0
cursor: skipped 0
rows read for page 10,000 –

The offset reader goes wrong the moment the feed changes under it: new posts push old ones down, so they reappear on the next page; a deletion pulls them up, so one is skipped forever. The cursor reader remembers where it was, not how far it was, so neither happens. And at page 10,000 the offset query makes the database walk past 50,000 rows to return 5.

🧰 Tools you'll actually use

curl and Postman for REST; OpenAPI (formerly Swagger) to describe a REST API and generate docs and clients; protoc / buf and grpcurl for gRPC; Apollo or GraphQL Yoga for GraphQL; Socket.IO, or managed services like Pusher, Ably and AWS API Gateway WebSockets for real-time. Snippets:

# REST with cursor pagination and an idempotent POST (Stripe-style)
curl "https://api.example.com/v1/posts?limit=20&starting_after=post_8f3a"
curl -X POST https://api.example.com/v1/payments \
  -H "Idempotency-Key: 5b1d3c2e-9f6a-4c1e-8e7a-2f0d9b4c6a11" \
  -d amount=2000 -d currency=usd

# Watch a Server-Sent Events stream (-N = don't buffer)
curl -N https://api.example.com/v1/events
# openapi.yaml: the contract for one endpoint
openapi: 3.1.0
info: { title: Posts API, version: "1" }
paths:
  /posts:
    get:
      parameters:
        - { name: limit, in: query, schema: { type: integer, maximum: 100 } }
        - { name: starting_after, in: query, schema: { type: string } }
      responses:
        "200": { description: A page of posts, plus has_more }
// posts.proto: a gRPC service between your own services
syntax = "proto3";
service Posts {
  rpc GetPost (GetPostRequest) returns (Post);
  rpc WatchFeed (WatchRequest) returns (stream Post);   // server streaming
}
message GetPostRequest { string id = 1; }
message Post { string id = 1; string author_id = 2; string text = 3; int64 likes = 4; }

Try it locally: with a gRPC server that has reflection on, grpcurl -plaintext localhost:50051 list shows its services. For SSE, curl -N against any endpoint that returns text/event-stream prints events as they arrive.

⚖️ Trade-offs
Style✅ Use when…❌ Avoid when…
REST + JSONPublic APIs, browsers, simple create/read/update/delete (CRUD); HTTP caching and tooling for freeScreens need many related objects (chatty), or service-to-service calls are very hot
gRPC + protobufInternal service-to-service calls; strict contracts; streamingBrowsers or third parties are the main clients (needs a proxy; binary is harder to debug)
GraphQLMany client types with different data needs; product teams iterating fastSimple APIs; you need easy HTTP caching; you can't afford to build query-cost limits
PollingUpdates are rare (minutes) and clients are fewMany clients want near-instant updates
SSEServer → client only: feeds, notifications, AI token streamsThe client sends a lot too (use WebSockets)
WebSocketTwo-way, low latency: chat, games, live docsYou can't run stateful long-lived connections (some serverless platforms), or updates are rare
🚀 Startup vs big tech

Founding engineer (0 → 1)

One REST/JSON API with cursor pagination from day one (changing it later breaks clients), idempotency keys on anything that charges money, and an OpenAPI file. For live features, start with SSE or a managed WebSocket service rather than running your own fleet.

Big tech (1 → 100)

Public REST APIs with strict versioning and long deprecation windows, gRPC between hundreds of internal services, often a GraphQL layer for the apps, and dedicated real-time gateways holding millions of WebSocket connections (Lessons 4.3, 4.5, 7.4).

🎤 Interview angle

Most designs include an “API” step. A senior answer:

  • Writes 3–5 key endpoints with methods, paths, request and response fields, e.g. POST /v1/messages, GET /v1/chats/{id}/messages?cursor=….
  • Uses cursor pagination for feeds, idempotency keys for writes that matter, and says how the API is versioned.
  • Picks the real-time mechanism from the numbers (users online, update rate, one-way or two-way) and mentions the cost of holding connections.
  • Says why gRPC internally and REST/GraphQL externally, if the design has both.

Common follow-ups: “What happens if the client retries this POST?” “How do you add a field without breaking old apps?” “How does a user who was offline catch up?”

🏭 In the real world
Cursors, idempotency keys and dated versions 🏢 Stripe Stripe API: pagination · idempotent requests · versioning

How: list endpoints take limit and starting_after; writes accept an Idempotency-Key header so they can be safely retried; and API versions are released monthly without breaking changes, with breaking changes only in twice-yearly major releases.

Why this method: payments must never double-charge on a retry, and thousands of businesses' integrations must keep working while the API evolves.

Moving from offsets to cursors 🏢 Slack Evolving API Pagination at Slack

How: endpoints that once returned hundreds of records grew to hundreds of thousands. Slack moved from no pagination, to offsets, to cursor-based pagination.

Why this method: as they explain, LIMIT … OFFSET … makes the database read offset + count rows, and when items are written frequently the page window shifts, skipping or duplicating results.

REST to GraphQL 🏢 GitHub · 2016 The GitHub GraphQL API

How: GitHub's REST API was responsible for over 60% of requests to its database tier, partly because hypermedia navigation makes clients call repeatedly; they launched a GraphQL API where one query fetches what a client needs.

Why this method: fewer, better-shaped requests cut load on the servers and round trips for clients.

A WebSocket gateway for real-time events 🏢 Discord Discord Gateway docs

How: apps open a WebSocket to Discord's Gateway to receive events (a message posted, a channel updated). After connecting, the app sends a heartbeat at the interval the server gives it, and can resume a dropped connection.

Why this method: pushing events over one open connection is how millions of clients see messages instantly without polling; heartbeats detect dead connections.

WebSockets instead of polling 🏢 Stack Overflow · 2016 Stack Overflow: The Architecture, 2016 Edition

How: about 500,000 concurrent WebSocket connections at peak push live updates: notifications, vote counts, new answers and comments.

Why this method: in their words, WebSockets are “tremendously more efficient than polling” at their scale: more data with fewer resources, and more instant for users.

🤯 Fun fact · the 18-month tab

Stack Overflow's architecture post notes that some of the browsers holding its WebSocket connections had been open for over 18 months. Long-lived connections really are long-lived, which is why servers must handle reconnects, heartbeats and deploys without dropping everyone at once.

Check yourself

1. 500,000 users keep a dashboard open that polls for updates every 2 seconds. How many requests per second does that cost?
500,000 ÷ 2 = 250,000 requests/s, whether or not anything changed. If updates are rare, SSE or WebSockets would send only the actual changes over 500,000 open connections.
2. An infinite-scroll feed gets new posts every second. Users complain they see the same post twice while scrolling. What's the fix?
New posts at the top shift every offset, so items slide into the next page. A cursor anchors on the last item seen, so inserts above it don't matter. It's also faster deep into the feed, since the database doesn't read and discard skipped rows.
3. A mobile app's “Pay” request times out. The app retries, and the customer is charged twice. Which API design prevents this?
Timeouts are ambiguous: the first request may have succeeded. With an idempotency key (as Stripe's API uses), the retry is recognised and returns the original result. Never retrying means real failures leave customers stuck.
📝 TL;DR
  • REST: resources + HTTP verbs + status codes. GET/PUT/DELETE are idempotent; make POSTs safe with idempotency keys.
  • Use cursor pagination for anything that changes or gets deep; offset skips, duplicates and slows down.
  • gRPC + protobuf between services; GraphQL when many clients need differently shaped data in one round trip.
  • Real time: polling costs clients ÷ interval requests/s; long polling, SSE (one-way) and WebSockets (two-way) push instead.
