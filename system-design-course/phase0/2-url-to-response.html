Phase 0 · Lesson 2

What happens when you hit Enter: DNS, TCP, TLS, HTTP

Before your server does any work, a request makes several trips across the network to find the server, connect, and set up encryption. At scale, those round trips, not your code, are often most of the time a user waits.

🧰 You'll need (quick reminders)
  • Latency = how long one request takes, in milliseconds (ms, thousandths of a second). p99 = the time 99% of requests beat (Lesson 0.1).
  • Non-functional requirements like “under 200 ms for users worldwide” decide where servers must live (Lesson 0.1).
🎯 Hook

On October 4th, 2021, Facebook and the rest of Meta's platforms vanished from the internet. During routine maintenance, a command meant to check backbone capacity accidentally took down every connection in Meta's backbone network.

Then it got worse. Meta's DNS servers, the machines that tell the world which IP address “facebook.com” lives at, are built to stop announcing themselves if they can't reach the data centers. They did exactly that. In Meta's own words, the DNS servers became unreachable even though they were still operational, so nobody on the internet could find Meta's servers at all. Every request starts with that lookup. Let's walk through what happens after you hit Enter.

Numbers first: where 630 ms goes

A round trip (RTT, round-trip time) is the time for a message to go to the server and the reply to come back. Light in fiber covers roughly 200 km per millisecond, so distance sets a floor nobody can engineer away: New York ↔ London is at least 56 ms round trip, New York ↔ Sydney at least 160 ms, and real routes are longer.

A user in Sydney opens your site, hosted in New York, for the first time. Assume a full DNS lookup of about 100 ms and a server that takes 50 ms to build the page:

Your code was 50 ms of the 630. The other 580 ms was the network setting up. Two fixes follow directly: reuse connections so you only pay the setup once, and move the server closer to the user (a CDN, Lesson 1.4).

first-request time ≈ DNS + (number of round trips × RTT) + server time “The DNS lookup, plus how many round trips the protocols need times the round-trip time, plus the time your server spends.” Cut the round trips or cut the RTT.
💡 Big idea Far-away users mostly wait on round trips × distance, not on your server. Each protocol upgrade (TLS 1.3, HTTP/3) is about removing round trips, and each CDN is about shrinking the distance.
🧠 Analogy: calling a shop

You want to ask a shop if they have your size. First you find their number: in your phone's contacts (a cached DNS answer), or by calling directory assistance, which may have to ask around (a full DNS lookup). You dial and wait for “Hello?” before talking (the TCP handshake). You check it's really the shop and agree to speak in a code nobody else understands (TLS). Only then do you ask your question (HTTP). If you stay on the line for your next question, you skip all of that (connection reuse). And calling a shop across the world takes longer per sentence no matter how fast they answer (the RTT).

Step 1: DNS, the internet's address book

Computers connect to IP addresses like 104.20.23.154, not names. DNS (the Domain Name System) turns a name into an address. It's a chain of servers, each knowing a bit:

  • Your browser and operating system keep a small cache of recent answers. If it's there, the lookup takes 0 ms.
  • Otherwise they ask a recursive resolver: your internet provider's, or a public one like Cloudflare's 1.1.1.1 or Google's 8.8.8.8. It does the hard work, and caches answers for everyone it serves.
  • On a miss, the resolver asks a root server (“who handles .com?”), then the TLD server for the top-level domain (“who handles example.com?”), then the domain's authoritative server, which holds the real answer.

Each answer comes with a TTL (time to live): how many seconds everyone may cache it. Long TTL = fewer lookups and more resilience. Short TTL = you can move your site to a new IP quickly. Common record types: A (IPv4 address), AAAA (IPv6 address), CNAME (an alias to another name).

Things to try: with a 1-day TTL, move the site and look up again: you get the old address for up to a day. That's why teams lower the TTL a day before a migration. Then break the authoritative servers: lookups still work while the cached copy lasts, and the site vanishes the moment it expires. Meta's resolvers worldwide hit exactly that wall.

Step 2: TCP, opening a reliable connection

TCP (Transmission Control Protocol) gives you a reliable, in-order stream of bytes over an unreliable network: lost packets are re-sent, and the receiver puts them back in order. It starts with a three-way handshake: the client sends SYN, the server answers SYN-ACK, the client sends ACK. That costs one round trip before any data moves.

The catch of “in order”: if one packet is lost, everything behind it waits until it's re-sent. That's called head-of-line blocking, and it matters for HTTP/2 below.

Step 3: TLS, encryption and identity

TLS (Transport Layer Security, the “S” in HTTPS) does two jobs. The server proves it's really shop.example with a certificate signed by an authority your browser trusts, and both sides agree on encryption keys. TLS 1.2 needed two extra round trips for this; TLS 1.3 (2018) cut it to one. Reconnecting to a server you've seen before can be even faster.

Step 4: HTTP, the actual request

HTTP (HyperText Transfer Protocol) is the request itself: a method and path like GET /products/42, headers, and a response with a status code (200 OK, 404 Not Found…) and a body. A web page is rarely one request: the HTML points to CSS, scripts and images, each its own request.

VersionRuns onHow many requests at once per connectionMain idea
HTTP/1.1TCPOne at a timeKeep-alive: reuse the connection for the next request instead of reconnecting.
HTTP/2TCPMany, interleaved (multiplexing)One connection carries all the page's files. But one lost TCP packet stalls them all.
HTTP/3QUIC over UDPMany, independent streamsConnection + encryption setup in one round trip, and a lost packet only stalls its own stream. Falls back to TCP if a network blocks UDP.

UDP (User Datagram Protocol) is TCP's bare-bones sibling: just send packets, no handshake, no ordering. QUIC builds its own reliability and encryption on top of it, so it can fix TCP's head-of-line problem without waiting for every router on the internet to be upgraded.

Step 5: the response

The request usually lands on a load balancer (Lesson 1.2), which picks an app server; the server reads from a cache or database and sends the response back along the same connection. The browser starts drawing as bytes arrive. The time until the first byte of the response arrives is called TTFB (time to first byte), a standard thing to measure.

✏️ Worked example: what a CDN buys a user in Sydney

Same user, same New York server, round trip 160 ms, server time 50 ms.

  • First visit, TLS 1.3, HTTP/2: 100 (DNS) + 3 × 160 + 50 = 630 ms.
  • Same, but TLS 1.2: one more round trip → 100 + 4 × 160 + 50 = 790 ms.
  • HTTP/3: connection + TLS in one round trip → 100 + 2 × 160 + 50 = 470 ms.
  • Next request on the same connection: 160 + 50 = 210 ms.
  • A CDN edge in Sydney (RTT about 5 ms) with the page cached there, DNS cached: 3 × 5 + 5 (edge lookup) = 20 ms.

Protocol upgrades saved 160–320 ms. Moving closer saved 600. That's why every large site uses a CDN.

🧰 Tools you'll actually use

dig for DNS, curl -w to time each phase of a request, openssl s_client to inspect TLS, and your browser's DevTools Network tab (its “Timing” view is this waterfall). Managed side: Cloudflare, AWS Route 53 and Google Cloud DNS host your DNS records. Example output below; your numbers will differ.

# What does a name resolve to, and for how long may it be cached? (the number is the TTL in seconds)
$ dig +noall +answer example.com
example.com.   232   IN   A   104.20.23.154

# Watch the whole chain: root → .com → authoritative
$ dig +trace example.com

# Time every phase of one HTTPS request (seconds, cumulative from the start)
$ curl -s -o /dev/null -w 'dns=%{time_namelookup} tcp=%{time_connect} tls=%{time_appconnect} ttfb=%{time_starttransfer} total=%{time_total} http=%{http_version}\n' https://www.google.com/
dns=0.004 tcp=0.005 tls=0.158 ttfb=0.428 total=0.502 http=2

# Which TLS version and certificate does a server use?
$ openssl s_client -connect example.com:443 -servername example.com -brief </dev/null

# Try HTTP/3 if your curl was built with it
$ curl -sI --http3 https://cloudflare.com/ | head -1

Try it locally: run the curl -w line twice against a site far away and once against one nearby. The gap between tcp and tls is roughly one round trip.

🚀 Startup vs big tech

Founding engineer (0 → 1)

Put your DNS and static files behind a managed provider with a CDN on day one (many have free tiers), host in the region where most users are, and let the platform handle TLS certificates (for example with Let's Encrypt). Turn on HTTP/2 and HTTP/3 where it's a setting.

Big tech (1 → 100)

Runs its own authoritative DNS and edge network, uses DNS and anycast (the same IP address announced from many cities) to send each user to the nearest healthy site, tunes TLS and QUIC, and measures TTFB per country. And, as Meta learned, makes sure DNS doesn't depend on the thing it's meant to point to.

🎤 Interview angle

“What happens when you type a URL and press Enter?” is a classic. A senior answer goes beyond listing steps:

  • DNS with its caches and TTLs; TCP's handshake; TLS's certificate check and key exchange; the HTTP request; a load balancer and app server; the response.
  • Counts the round trips and ties them to latency: “across an ocean that's 3–4 RTTs before the first byte”.
  • Names the fixes: connection reuse, TLS 1.3, HTTP/2 and 3, CDNs, DNS caching.
  • Mentions failure: DNS as a single point of failure, certificate expiry, lost packets.

Common follow-ups: “Why is the second request faster?” “What's the difference between HTTP/2 and HTTP/3?” “How would you make this fast for users in Asia?”

🏭 In the real world
DNS as a single point of failure 🏢 Meta · 2021 More details about the October 4 outage

How: Meta's authoritative DNS servers withdraw their BGP route announcements (BGP is how networks tell each other which addresses they can reach) when they can't reach the data centers. When the backbone went down, they all did, so the DNS servers became unreachable.

Why this method: normally it's a smart safety rule: an unhealthy DNS location takes itself out so users go elsewhere. When every location was unhealthy at once, it removed the whole company from the internet.

A fast, private recursive resolver 🏢 Cloudflare · 2018 Announcing 1.1.1.1

How: a public resolver running across Cloudflare's global network. They committed to never writing querying IP addresses to disk and to wiping logs within 24 hours.

Why this method: resolvers see every site you visit, and default ones are often slow; running the resolver close to users makes the first step of every request faster.

QUIC, the transport under HTTP/3 🏢 Google · 2017 The QUIC Transport Protocol (SIGCOMM)

How: an encrypted, multiplexed, low-latency transport built on UDP, deployed on thousands of Google servers for Chrome and YouTube. The paper estimated that 7% of internet traffic was already QUIC.

Why this method: building on UDP let Google evolve the transport in software, without waiting for operating systems and network gear to change TCP.

One round trip to connect 🏢 Cloudflare · 2018 The Road to QUIC

How: QUIC combines the TCP-style handshake with the TLS 1.3 handshake, so a new connection takes a single round trip instead of the two needed for TCP plus TLS 1.3. Its streams are delivered independently, so a lost packet usually affects only one stream.

Why this method: for far-away and mobile users, every removed round trip is directly visible as a faster page.

HTTP/3 with a TCP fallback 🧰 Standard · RFC 9114 RFC 9114: HTTP/3

How: HTTP/3 is selected during the TLS handshake with the token h3. If a network blocks UDP, the standard says clients should try the TCP-based versions of HTTP instead.

Why this method: the internet is full of old middleboxes. A fast path with a safe fallback lets a new protocol roll out without breaking anyone.

🤯 Fun fact · DNS on the walls

In March 2014, Turkish internet providers blocked Twitter by making their DNS resolvers refuse to answer for twitter.com. People spray-painted 8.8.8.8, the address of Google's public resolver, on walls so others could switch resolvers and get back online. Cloudflare tells the story in its 1.1.1.1 launch post.

🌉 How it connects

Lesson 0.3 puts these round trips next to memory and disk speeds. Load balancers (Lesson 1.2) sit at the end of this journey, CDNs (Lesson 1.4) shrink the distance, and API gateways (Lesson 1.6) terminate TLS for you. gRPC (Lesson 0.4) runs on HTTP/2, and mTLS (Lesson 4.6) is TLS where both sides show a certificate. For AI apps, streaming tokens to the user over one open connection hides most of this setup cost.

Check yourself

1. A user is 100 ms round trip away. With DNS cached, how long until the first byte of a new HTTPS request arrives over TCP + TLS 1.3 + HTTP/2, if the server takes 20 ms?
TCP handshake (1 RTT) + TLS 1.3 (1 RTT) + request/response (1 RTT) = 3 × 100 = 300 ms, plus 20 ms of server time = 320 ms. On a reused connection it would be 120 ms.
2. You're moving your site to a new hosting provider tomorrow. Your DNS record's TTL is 86,400 seconds (1 day). What should you do today?
Resolvers may keep the old answer for a full TTL. Lowering it a TTL ahead of the move means that, on moving day, stale copies expire within minutes. Keep the old servers running for a while anyway, for resolvers that cache too long.
3. Your mobile app's users are on flaky cellular networks, and pages with many images load slowly even over HTTP/2. Which change targets the actual problem?
On lossy networks, HTTP/2 suffers TCP head-of-line blocking: one lost packet holds up every multiplexed stream. QUIC's independent streams fix that (with HTTP/2 kept as a fallback where UDP is blocked). The server's CPU isn't the bottleneck.
📝 TL;DR
  • Every new request: DNS lookup → TCP handshake (1 RTT) → TLS 1.3 (1 RTT; 1.2 needs 2) → HTTP request (1 RTT) → server time.
  • Light in fiber ≈ 200 km/ms: NY ↔ London ≥ 56 ms, NY ↔ Sydney ≥ 160 ms round trip. Distance sets the floor.
  • Fixes: cache DNS, reuse connections, TLS 1.3, HTTP/2 multiplexing, HTTP/3 (QUIC) for lossy networks, CDNs to get close.
  • DNS TTLs trade agility for resilience, and DNS itself can take your whole company offline.
