Phase 0 · Recap

Recap: foundations

The habits and numbers every later lesson builds on: requirements before boxes, round trips and latency, estimation, API contracts, and availability as a budget. Review them here, play the request game, then design a real system on your own.

🧾 Cheat sheet

🧭

0.1 How seniors think

peak QPS ≈ DAU × req/user ÷ 86,400 × peak

Write non-functional requirements with numbers (scale, p99, availability, freshness, cost) before drawing boxes. Start simple; scale the part the numbers say breaks; name each trade-off.

Tools: design doc (goals / non-goals / alternatives), Mermaid or Excalidraw.

🌐

0.2 Hitting Enter

DNS + TCP (1 RTT) + TLS 1.3 (1 RTT) + HTTP (1 RTT)

Light in fiber ≈ 200 km/ms, so far users wait on round trips. Cache DNS, reuse connections, use HTTP/2 or HTTP/3, and get close with a CDN. DNS TTLs trade agility for resilience.

Tools: dig, curl -w, openssl s_client, DevTools.

🧮

0.3 Estimation

RAM 100 ns · DC trip 0.5 ms · ocean 150 ms

1 M requests/day ≈ 12/s. Storage = writes × size × days × 3 copies. Bandwidth = QPS × size × 8. Servers = peak ÷ measured capacity + headroom. Draw a conclusion from every number.

Tools: python3, a spreadsheet, k6 for the per-server number.

🔌

0.4 APIs

polling cost = clients ÷ interval

REST for public APIs, gRPC between services, GraphQL for many client shapes. Cursor pagination, idempotency keys on important POSTs. SSE (one-way) or WebSockets (two-way) instead of polling at scale.

Tools: curl, OpenAPI, protobuf + grpcurl.

🛡️

0.5 Availability

series A·B · parallel 1 − (1−A)(1−B)

99.9% ≈ 43 min/month, 99.99% ≈ 4.3 min. SLI measures, SLO targets, SLA promises. Error budget = 1 − SLO. Remove serial dependencies, spread replicas across zones, shrink MTTR.

Tools: Prometheus + Grafana, burn-rate alerts, uptime checks.

🗣️ Teach it back

Answer out loud, as if an interviewer asked: “Our checkout page is hosted in New York. A customer in Sydney opens it for the first time and pays. Walk me through what happens on the network, roughly how long it takes, and what availability we can honestly promise if checkout calls a third-party payment API that offers 99.9%.”

A strong answer counts round trips (≈ 160 ms each, so over half a second before any server work), suggests a CDN and connection reuse, uses an idempotency key on the payment POST, multiplies the chain, and proposes making the payment step asynchronous so checkout isn't capped at 99.9%.

    🏗️ Design it yourself

    ✏️ The prompt

    Snapshelf, a photo-sharing startup, launches with 2 million daily users and expects 20 million within a year. Users scroll a feed of friends' photos, upload photos, and like them. Most users are in North America and Europe. You're the founding engineer. Using only Phase 0 ideas: write the requirements, estimate the load, sketch the API, describe the network path, and pick an availability target.

    Assume each user views 30 photos and uploads 0.2 a day; originals are 3 MB, feed versions 100 KB; peak = 3× average. Try it on paper before opening the answer.

    🔓 One good answer

    Requirements

    • Functional: upload a photo, view a feed (newest first), like a photo. Out of scope for now: comments, search, video, messaging.
    • Non-functional: 20 M DAU; feed p99 under 300 ms in North America and Europe; 99.9% availability for feed and upload; uploads never lost (durability); like counts may lag a few seconds; cost-conscious.

    Numbers (at 20 M DAU)

    • Feed views: 20 M × 30 ÷ 86,400 ≈ 6,900/s average, ≈ 21,000/s peak. Uploads: 20 M × 0.2 ÷ 86,400 ≈ 46/s (≈ 140/s peak).
    • Storage: 4 M uploads/day × 3 MB = 12 TB/day → about 13 PB/year with 3 copies. Object storage, not a database. (Worth asking: do we need the full original forever?)
    • Bandwidth: 6,900/s × 100 KB × 8 ≈ 5.6 Gbps average, ~17 Gbps at peak: a CDN must serve images.
    • API servers: 21,000/s ÷ ~1,000 per server (to be load-tested) × 1.3 headroom ≈ 27. Photo metadata writes (46/s) fit one primary database with replicas for reads.

    API (Lesson 0.4)

    POST /v1/photos            # returns an upload URL; client uploads the file straight to object storage
  Idempotency-Key: <uuid>   # a retried upload doesn't create two photos
GET  /v1/feed?limit=20&cursor=<last_photo_id>   # cursor pagination: no duplicates while friends post
POST /v1/photos/{id}/likes # counts can lag; aggregate in the background

    Network path and architecture (Lessons 0.1, 0.2)

    • DNS with a CDN in front: images and static files are served from edges near users, so most bytes never reach your servers.
    • Feed API requests: CDN/edge → load balancer → stateless API servers in one region near most users, connections kept alive, HTTP/2 or HTTP/3.
    • Photo bytes go to object storage; metadata (who, when, which file) to a relational database; feed pages cached briefly in Redis.

    Availability (Lesson 0.5)

    • Target 99.9% SLO (≈ 43 min/month), measured as successful feed and upload requests at the load balancer.
    • Critical chain: LB (99.99%) × API servers (≥ 2 across zones) × database (primary + standby). With LB 99.99%, API 99.99%, DB pair ≈ 99.9999% and caching soft, the chain is around 99.98%, comfortably above the SLO.
    • Soft dependencies: if the like counter or cache is down, the feed still loads.

    Trade-offs and classic mistakes

    • Mistake: storing photos in the database. Fix: object storage + CDN, database holds only metadata.
    • Mistake: offset pagination for the feed (duplicates as friends post). Fix: cursors.
    • Mistake: sizing for the 6,900/s average. Fix: plan for peak and launch-day spikes, and load-test.
    • Mistake: microservices and multi-region on day one. Fix: one well-structured app, managed services; revisit when the numbers demand it.
    • Trade-off: keeping full-size originals forever is the biggest cost line (13 PB/year). Storing a compressed version, or moving old originals to cheaper storage, is a product decision worth raising.

    🏆 Boss quiz

    1. An app has 50 million daily users, each making 4 requests a day. Planning for 2× peak, what peak QPS do you design for?
    50 M × 4 = 200 M requests/day ÷ 86,400 ≈ 2,315/s; × 2 ≈ 4,630 QPS. Shortcut: 1 M/day ≈ 12/s, so 200 M/day ≈ 2,400/s.
    2. Users in India complain your US-hosted API is slow, but server logs show 30 ms per request. What's the most likely cause and fix?
    If the server takes 30 ms but users wait much longer, the time is on the network: DNS, TCP, TLS and the request each cost a long round trip. Connection reuse, TLS 1.3/HTTP/3, and moving the endpoint closer attack exactly that (Lesson 0.2).
    3. A sports app must push live scores to 2 million fans watching a match; fans never send anything back. Which mechanism fits best?
    Polling every second is 2 M requests/s, mostly empty. Updates flow one way, so SSE is the simplest push channel; WebSockets also work. Webhooks call servers, not phones.
    4. A request passes a load balancer (99.99%), then one of two app servers (99.9% each, either can serve), then a database (99.95%). Roughly what's the availability?
    App pair: 1 − 0.001² = 99.9999%. Chain: 0.9999 × 0.999999 × 0.9995 ≈ 99.94%, about 5.3 hours a year. The database is now the weakest link; a standby would be the next step.
    5. In a design interview you're asked to “design a link shortener”. What should your first two minutes cover?
    Requirements and numbers first (Lesson 0.1). A shortener is extremely read-heavy (redirects far outnumber new links), which points to caching and a simple write path before any database debate. Phase 7 designs it in full (Lesson 7.2).
