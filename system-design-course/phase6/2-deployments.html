Phase 6 · Lesson 2

Deploying safely: rolling, blue-green, canary, feature flags

Most outages start with a change. Safe deployment means every release reaches a few users first, is watched by a robot, and can be undone in a minute, so a bad change hurts hundreds of people instead of millions.

🧰 You'll need (quick reminders)
  • A pipeline builds one artifact per commit and promotes it (Lesson 6.1).
  • Load balancers decide which server gets each request, and can split traffic by weight (Lesson 1.2).
  • Error rate and SLOs (service level objectives: the reliability target, like 99.9% of requests succeed) (Lesson 0.5).
🎯 Hook

On Friday, July 19, 2024, at 04:09 UTC, CrowdStrike pushed a content configuration update to its Falcon sensor for Windows. A bug in their content validator let a problematic file through, and Windows machines that loaded it crashed with a blue screen. The update was reverted at 05:27 UTC, 78 minutes later. Microsoft estimated 8.5 million Windows devices were affected.

In its own review, the first fix CrowdStrike listed for this kind of content was a staggered deployment: “gradually deployed to larger portions of the sensor base, starting with a canary deployment.” That's this lesson.

Numbers first: big bang vs canary

Your service handles 1,000 requests per second. A new release has a bug that makes 20% of requests fail. (Google's SRE workbook uses this same 20% example.)

Big bang: 100% at onceCanary: 1% first, with automated checks
Traffic on the bad version100%1%
Time until it's undonehumans notice in ~10 min + ~5 min to redeploy = 15 minrobot notices in ~5 min + ~1 min to shift traffic back = 6 min
Failed requests15 × 60 × 1,000 × 20% = 180,0006 × 60 × 1,000 × 1% × 20% = 720

Same bug, 250× less damage. You can't make releases bug-free. You can make each bug small.

damage ≈ traffic × share on new version × extra error rate × time to undo “The harm a bad release does is the traffic it sees, times how bad it is, times how long it stays.” Safe deployment attacks the share and the time; testing attacks the error rate.
💡 Big idea Separate deploy from release, and make every step reversible. Deploying puts new code on servers. Releasing lets users reach it. Rollouts limit how many users a new version reaches; feature flags decide which users see a feature; automated analysis decides whether to continue or roll back.
🧠 Analogy: the canary in the coal mine

The name is literal. Miners carried canaries underground because the small birds react to poisonous gas before people do. A canary release sends a small slice of real traffic to the new version first. If that slice gets sick, you pull back before the rest of your users go in.

What “automated canary analysis” checks

The robot compares the canary against a baseline: servers running the old version that receive the same small slice of traffic and started at the same time. Comparing to a fresh baseline (not the big, long-running production fleet) removes differences like warm caches and uptime.

  • Metrics: error rate, latency percentiles (p99 = the time 99% of requests beat, Lesson 6.3), CPU, memory, crashes.
  • Judgment: “is the canary significantly worse?” Netflix's open-source tool Kayenta uses a statistical test (Mann-Whitney U) for each metric and then combines them into a score.
  • Decision: continue to the next step, or roll back automatically, with no human in the loop.
✏️ Worked example: why the canary needs a few minutes

At 1% of 1,000 requests/s, the canary sees 10 requests/s = 600 per minute. The normal error rate is 0.1%, so in one minute you expect 0.6 errors. Whether you see 0, 1 or 2 is luck.

  • Watch for 5 minutes: 3,000 requests, about 3 errors expected normally. A 20%-broken canary shows about 600. Obvious.
  • A subtle bug adding 0.2% errors shows about 6 extra errors (9 instead of 3). Detectable, but noise can fool you.
  • Set the rollback threshold too low and random noise rolls back good releases. Too high and subtle bugs sail through to 100%.

Bigger slices or longer windows give clearer answers but expose more users. That's the tuning problem in the simulator.

Feature flags: deploy dark, release by percentage

A feature flag is an if statement whose answer comes from a config service, not the code: if flags.on("new-checkout", user). The code ships to everyone, turned off. Then you release it to 1% of users, then 10%, then everyone, with no deploy at all. If it misbehaves, a kill switch turns it off in seconds.

One subtle requirement: a user must get the same answer every time, or the checkout page changes between clicks. So flag systems don't flip a coin per request. They hash the user's ID into a number from 0 to 99 and turn the feature on if it's below the percentage. Unleash, for example, uses a normalized MurmurHash of the user's ID. Raising the percentage from 10 to 20 keeps the first 10% in and adds 10% more.

The hard part: the database doesn't roll back

During a rolling or canary deploy, old and new code run at the same time, against the same database. And if you roll back, old code meets whatever the new code wrote. So every schema change must work with both versions. The pattern is called expand and contract (Martin Fowler calls it “parallel change”): expand, migrate, contract.

✏️ Worked example: renaming a column safely

You want to rename users.name to users.full_name. Doing it in one step breaks every old server still running. Instead, four deploys:

  1. Expand: add the new column full_name (nullable). Old code ignores it. Safe.
  2. Dual-write: new code writes both name and full_name, still reads name. Backfill old rows in small batches.
  3. Switch reads: code reads full_name. Rolling back to step 2 is still safe, because both columns are kept in sync.
  4. Contract: once nothing reads name (days later), stop writing it and drop it.

Each step is boring and reversible. That's the point.

🔥 Real outage · Cloudflare, July 2, 2019

Cloudflare deployed a new rule to its web application firewall (WAF). The rule contained a regular expression that backtracked enormously and exhausted the CPUs serving HTTP and HTTPS traffic on its network worldwide. The service went down for 27 minutes.

Cloudflare's postmortem lists what went wrong, including that its procedure “allowed a non-emergency rule change to go globally into production without a staged rollout,” and that the rollback plan took too long. One fix: staged rollouts of rules, like Cloudflare's other software, while keeping the ability to deploy globally in an emergency.

🧰 Tools you'll actually use

Progressive delivery on Kubernetes: Argo Rollouts, Flagger; multi-cloud: Spinnaker with Kayenta for canary analysis; managed: AWS CodeDeploy, Google Cloud Deploy. Feature flags: LaunchDarkly, Unleash, Flagsmith, Statsig, and the vendor-neutral OpenFeature API. An Argo Rollouts canary that pauses at each step and lets a Prometheus query decide whether to continue:

apiVersion: argoproj.io/v1alpha1
kind: Rollout
metadata: { name: shop }
spec:
  replicas: 20
  strategy:
    canary:
      steps:
        - setWeight: 5                    # 5% of traffic to the new version
        - pause: { duration: 10m }
        - analysis:                       # robot judges the canary
            templates: [ { templateName: success-rate } ]
        - setWeight: 25
        - pause: { duration: 10m }
        - setWeight: 50
        - pause: { duration: 10m }       # then 100%
  # ... selector and pod template as in a normal Deployment
---
apiVersion: argoproj.io/v1alpha1
kind: AnalysisTemplate
metadata: { name: success-rate }
spec:
  metrics:
    - name: success-rate
      interval: 1m
      failureLimit: 2                    # 3 bad measurements = abort and roll back
      successCondition: result[0] >= 0.99
      provider:
        prometheus:
          address: http://prometheus:9090
          query: |
            sum(rate(http_requests_total{app="shop",status!~"5.."}[5m]))
            / sum(rate(http_requests_total{app="shop"}[5m]))

Plain Kubernetes rollback, no extra tools: kubectl rollout status deployment/shop watches a rollout; kubectl rollout undo deployment/shop goes back to the previous version. (PromQL, the query language in that template, is taught in Lesson 6.3.)

⚖️ Trade-offs
Strategy✅ Use when❌ Avoid when
Rolling (default)Small team, low traffic, good tests; free in KubernetesA bad release would be very costly: nothing stops it from reaching 100%
Blue-greenYou need instant rollback, or a clean cutover (e.g. a big runtime upgrade)Doubling the fleet is expensive, or old and new can't share the database
Canary + analysisHigh traffic (enough data for statistics) and a costly blast radiusVery low traffic: 1% of 10 requests a minute tells you nothing; use longer steps or dark launches
Feature flagsReleasing features gradually, A/B tests, kill switches for risky pathsYou never clean them up: hundreds of stale flags make code paths impossible to reason about

Rollback vs roll forward: rolling back is almost always faster and safer during an incident. Roll forward (ship a fix) only when rollback is impossible, such as after a one-way data migration, which is why you avoid one-way migrations.

🚀 Startup vs big tech

Founding engineer (0 → 1)

Rolling deploys from the platform you're on, a one-command rollback you've actually practiced, and a feature-flag library (even a simple config table) for anything risky. Every migration expand-then-contract from day one. Deploy during working hours, not Friday night.

Big tech (1 → 100)

Progressive delivery everywhere: canaries with automated analysis, then region by region (one region or zone first, the rest later), with configuration changes treated exactly like code. Flag platforms with audit logs and owners. Release “bake time” between stages, and automatic rollback tied to SLO burn (Lesson 6.4).

🎤 Interview angle

When an interviewer asks “how do you roll this out?”, a senior answer covers:

  • A staged rollout (canary or region by region) with the metrics that gate each step and an automatic rollback.
  • Feature flags to separate deploy from release, and a kill switch for the risky path.
  • Backward-compatible APIs and schemas (expand and contract), because old and new versions run together.
  • Treating config changes like code changes. Both the CrowdStrike and Cloudflare outages were pushes of content or rules, not app binaries.

Follow-ups: “Your service gets 20 requests a minute. Does a 1% canary work?” (No: too little data. Use longer steps, a bigger slice, or synthetic traffic.) “How do you roll back a database migration?” (You design it so you don't have to.)

🏭 In the real world
Canarying as a discipline 🏢 Google · SRE workbook Canarying Releases

How: Google defines canarying as a partial and time-limited deployment of a change, plus its evaluation. The part that gets the change is “the canary,” the rest is “the control,” and the result decides whether the rollout proceeds.

Why this method: the canary only risks a small fragment of the error budget. The chapter's example: a release that fails 20% of requests is far less harmful on a 5% canary population than deployed globally.

Automated canary analysis 🏢 Netflix + Google · 2018 Automated Canary Analysis at Netflix with Kayenta

How: alongside production, Netflix creates a baseline cluster (old version) and a canary cluster (new version), typically about 3 instances each, each getting a small slice of traffic. Kayenta compares their metrics using confidence intervals from the Mann-Whitney U test and computes a score.

Why this method: comparing against a fresh baseline instead of the long-running production fleet isolates the effect of the change itself. Kayenta is tightly integrated with Spinnaker, Netflix's delivery platform, which then decides to continue or roll back.

A content push that skipped the canary 🏢 CrowdStrike · 2024 Preliminary Post Incident Review

How: a bug in the content validator let a Template Instance with problematic content pass; when sensors loaded Channel File 291 it caused an out-of-bounds memory read and Windows crashes. The fix list includes a staggered rollout starting with a canary, better monitoring during rollout, and more customer control over when updates arrive.

Why this method: even well-tested content can be wrong; a staged rollout turns “every machine at once” into “a few machines, then stop.”

Rolling updates by default 🧰 Open source · Kubernetes Kubernetes Deployments

How: RollingUpdate is the default strategy, with maxSurge and maxUnavailable both defaulting to 25%; Recreate kills all old pods first. kubectl rollout undo returns to the previous revision.

Why this method: zero-downtime replacement with no extra infrastructure; for metric-gated canaries you add a tool like Argo Rollouts on top.

Sticky percentage rollouts 🧰 Open source · Unleash Unleash activation strategies

How: a gradual rollout's percentage uses a normalized MurmurHash of the user's unique ID; “stickiness” keeps each user's answer stable across sessions, and targeting constraints limit who is eligible.

Why this method: hashing gives a random-looking but repeatable split, so users don't flicker between versions and raising the percentage only adds users.

🤯 Fun fact · the 78 minutes

CrowdStrike's bad update was live from 04:09 to 05:27 UTC, and its review says Mac and Linux hosts were not affected. Yet those 78 minutes reached about 8.5 million Windows machines, which Microsoft noted was less than one percent of all Windows machines. Huge reach, tiny window: a perfect picture of why how many receive a change matters as much as how long it stays.

Check yourself

1. 2,000 requests/s. A bad release fails 10% of requests. A 2% canary catches it after 5 minutes and shifts traffic back in 1 minute. About how many requests failed?
6 minutes × 60 s × 2,000 req/s × 2% × 10% = 1,440. The same bug at 100% for the same 6 minutes would fail 72,000. Shrinking the share on the new version is the lever.
2. You need to rename a database column, and you deploy with rolling updates. What's the safe plan?
During the rollout, old and new code share one database, and a rollback brings old code back. Expand and contract keeps every step compatible with both versions. Blue-green doesn't help: both colors still share the database.
3. Your flag system turns a feature on with random() < 0.1 on every request. What goes wrong?
10% of requests isn't 10% of users. A user loading 10 pages sees the feature about once, at random. Hashing the user ID into a bucket from 0 to 99 gives each user one stable answer.
📝 TL;DR
  • Damage ≈ traffic × share on new version × error rate × time to undo. Rollouts shrink the share; robots shrink the time.
  • Strategies: recreate (downtime), rolling (default), blue-green (instant flip), canary (small slice + analysis), dark launch, feature flags.
  • Canary analysis compares against a fresh baseline; thresholds trade false rollbacks against missed bugs.
  • Feature flags separate deploy from release; hash the user ID so each user gets a stable answer.
  • Old and new code share the database: use expand and contract, and treat config pushes like code.
