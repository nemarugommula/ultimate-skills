Phase 6 · Lesson 1b

Versioning & releases: SemVer, lockfiles & changelogs

Most of the code you ship was written by strangers and arrives through version numbers. How you number your own releases, and how you pin everyone else's, decides whether builds are reproducible, upgrades are boring, and one bad package can break you overnight.

🧰 You'll need (quick reminders)
  • CI (continuous integration) builds and tests every change; build once and promote the same artifact (Lesson 6.1).
  • Backward compatible = new code still works for old callers; make changes additive (Lesson 4.5).
  • Supply chain: most of your code is dependencies of dependencies; Log4Shell arrived that way (Lesson 6.6).
🎯 Hook

On Tuesday, March 22, 2016, shortly after 2:30 PM Pacific, npm started seeing hundreds of failed installs per minute. After a dispute over a package name, developer Azer Koçulu had unpublished 273 of his packages. One was left-pad, a tiny string-padding helper that huge projects pulled in indirectly.

Within ten minutes a volunteer published a working replacement as version 1.0.0, and the errors kept coming. Why? Babel and Atom reached left-pad through a package called line-numbers, which asked for exactly 0.0.3. A new number didn't match. npm took the unprecedented step of restoring the original 0.0.3 from a backup; the disruption lasted 2.5 hours. Version numbers, and how you ask for them, are part of your system's design.

Numbers first: your dependency tree is a lottery

A typical web app lists 20 to 50 direct dependencies, but installs hundreds to over a thousand packages once you count their dependencies (check yours: npm ls --all | wc -l). Suppose (illustrative numbers):

  • 1,000 packages in the tree, each releasing about once a month: about 1,000 new versions a month, 33 a day.
  • 1 release in 1,000 breaks something you rely on, by accident.
If every build re-resolves to the newest allowed version…Chance at least one breaking release lands
Over a week (≈ 233 releases)1 − 0.999233 ≈ 21%
Over a month (≈ 1,000 releases)1 − 0.9991000 ≈ 63%
With a committed lockfile0% surprise: nothing changes until you change it on purpose
P(surprise breakage) = 1 − (1 − b)N · r · d “One minus the chance that every one of the N × r × d releases in that window is fine.” Small risks multiply across a big tree, just like flaky tests in Lesson 6.1.
b: chance one release breaks youN: packages · r: releases per package per dayd: days
💡 Big idea A version number is a promise about compatibility. A range says how much of other people's promises you trust. A lockfile is the receipt for exactly what you got. Apps lock exact versions and move the lock forward on purpose, through a robot that opens a pull request and CI that tests it. Libraries declare ranges and keep their promises.
🧠 Analogy: a shopping list and a receipt

Your package.json is a shopping list: “milk, any brand, 1 to 2 litres” (a range). Shop from the list every day and you'll get whatever's on the shelf that day, sometimes a new brand that tastes wrong. The lockfile is the receipt: exactly which carton you bought on Tuesday. To cook Tuesday's recipe again, shop from the receipt. The SemVer label on the carton is the dairy's promise: “same recipe, new packaging” (patch) versus “new recipe” (major).

SemVer: MAJOR.MINOR.PATCH

Semantic Versioning (SemVer, semver.org) gives each part of 2.7.1 a meaning, based on your public API (the functions, options and behavior other people use):

BumpWhenExampleWhat users can do
MAJOR 2.7.1 → 3.0.0Any incompatible change to the public APIRename parse(), remove an option, change a default, drop a supported runtimeUpgrade deliberately, read the migration notes
MINOR 2.7.1 → 2.8.0New functionality, backward compatibleA new optional argument, a new functionTake it automatically
PATCH 2.7.1 → 2.7.2Backward compatible bug fixesFix a crash, fix a wrong roundingTake it automatically
  • Pre-releases add a hyphen: 3.0.0-beta.1. They sort before the release (3.0.0-alpha < 3.0.0), and npm ranges skip them unless you ask for that exact version line, so betas don't leak into anyone's build.
  • Build metadata adds a plus: 3.0.0+20261031.sha.5114f85. It's ignored for ordering.
  • 0.y.z means initial development: the spec says anything may change at any time. If people depend on you in production, you should be at 1.0.0.
  • Released versions are immutable. If you accidentally break compatibility in a minor, the spec's advice is to ship another minor that restores compatibility, never to edit or reuse a released version.

What counts as “breaking” is wider than it looks: a stricter input check, a changed error message that callers parse, a slower algorithm someone depends on. The honest test: could a correct program written against the old version stop working? If yes, it's major.

Ranges: how much of the promise you trust

Your manifest usually asks for a range, not one version. npm's default when you run npm install x is the caret, ^. The rules, from npm's node-semver:

You writeMeansTakes
^1.4.0 (caret)≥ 1.4.0 and < 2.0.0New minors and patches
~1.4.0 (tilde)≥ 1.4.0 and < 1.5.0Patches only
1.4.0exactly 1.4.0Nothing new, including security fixes
^0.4.0≥ 0.4.0 and < 0.5.0In 0.x, the caret treats the minor as major
>=1.4.0 or *anything newerMajors too: breaking changes arrive by themselves

The catch is transitive dependencies. You depend on library A; A's author wrote "B": "^1.4.0". You never chose that range. When B ships a buggy 1.6.0, your next fresh install picks it up, with no change in your repo. That's “it worked yesterday and nobody touched anything”.

Lockfiles: the receipt

npm's docs say package-lock.json describes the exact tree that was generated, so later installs produce identical trees regardless of new releases, and that it's meant to be committed. Then use the right command:

  • npm install may update the lockfile. Use it on your laptop when you mean to change dependencies.
  • npm ci requires a lockfile, exits with an error if it doesn't match package.json, deletes node_modules, and never writes to the lockfile: “essentially frozen” installs. Use it in CI and Docker builds.
EcosystemManifest (ranges)Lockfile (exact)Frozen install
npm / pnpm / Yarnpackage.jsonpackage-lock.json, pnpm-lock.yaml, yarn.locknpm ci, pnpm install --frozen-lockfile
Python (Poetry, uv)pyproject.tomlpoetry.lock, uv.lockpoetry install, uv sync --locked
RustCargo.tomlCargo.lockcargo build --locked
Gogo.mod (minimum versions)go.sum (hashes)the default

Go is the interesting exception. Its minimal version selection (MVS) picks the lowest version that satisfies every requirement, not the newest, so a new release upstream changes nothing until someone raises a minimum. go.sum then stores cryptographic hashes of every module, so a tampered download fails the build. Selection and verification are separate jobs.

Libraries vs apps: npm ignores a package-lock.json anywhere except the root project and won't publish it. So your library's users resolve your ranges themselves, on the day they install. Lock your app; for a library, also run CI against the newest allowed versions, because that's what your users get.

Robots that move the lock forward

A lockfile alone just freezes you, and frozen means slowly accumulating known vulnerabilities. Dependabot (built into GitHub) and Renovate (open source, many platforms) watch registries and open pull requests that update the manifest and lockfile. CI runs your tests on each one. The settings that matter:

  • Wait a few days before proposing a release: Dependabot applies a 3-day cooldown to version updates by default (security updates skip it); Renovate's equivalent is minimumReleaseAge. Most broken or malicious releases are caught and pulled by others in that window.
  • Group non-major updates into one weekly PR per repo, or the PR count drowns your team (worked example below).
  • Automerge green minor and patch updates; Renovate's docs show a rule that excludes 0.x packages, since those may break at any time.
  • Majors get their own PR and a human, with the changelog linked.

Changelogs and commit messages that pick the version

People don't read diffs; they read changelogs. Keep a Changelog suggests a human-written file with an Unreleased section on top and six kinds of change: Added, Changed, Deprecated, Removed, Fixed, Security.

Conventional Commits makes commit messages machine-readable so the version can be computed instead of argued about:

  • fix: … → PATCH. feat: … → MINOR.
  • A footer BREAKING CHANGE: …, or a ! after the type (feat(api)!: …) → MAJOR, whatever the type.
  • Other types (docs, chore, refactor, test, ci…) are allowed and release nothing by themselves.

semantic-release reads those commits in CI, computes the next version, generates release notes and publishes, which, in its own words, removes the link between human emotions and version numbers. Its default rules also release perf and reverts as patches.

Not everything should be SemVer

  

    
What you shipVersion it withWhy

    
A library others install (npm, PyPI = the Python Package Index, Maven)SemVer, strictlyMachines read your number through ranges; it's an API contract

    
An internal service deployed continuouslyThe git commit SHA (a unique hash of the commit) on the image (Lesson 6.1)Nobody installs it; callers depend on its API, not its build number

    
An HTTP or gRPC APIDon't break it: additive changes, rare /v2, or dated versions like Stripe's (Lesson 4.5)You can't make clients upgrade, so “bump the major” isn't a plan

    
Products, OS releases, tools on a scheduleCalVer (calendar versioning): Ubuntu 24.04 is YY.0M; pip uses YY.MINOR.MICROThe number tells users how old it is; good when every release may change things

  

  
Release trains vs continuous delivery. A release train leaves on a fixed schedule with whatever is ready; late features wait for the next one. Chrome ships a new milestone every 4 weeks. Continuous delivery ships each change when it's ready (Lesson 6.1). Trains suit things users must download and install; web services, which you can roll back in a minute (Lesson 6.2), usually skip versions entirely.


  

    ✏️ Worked example: the bot PR budget
    
Your company has 30 repos, each with 40 direct dependencies that release about once a month (typical). You turn on a dependency bot.

    
    
      
  • One PR per update: 30 × 40 = 1,200 PRs a month, about 1,200 ÷ 22 working days ≈ 55 a day. Nobody reviews 55 PRs a day; people start clicking merge without reading, or turn the bot off.
    • 
      
  • Group non-major updates weekly per repo: 30 repos × 52 ÷ 12 weeks a month ≈ 130 PRs a month.
    • 
      
  • Automerge the green ones: if about 1 in 10 groups fails CI, humans look at ≈ 13 a month, plus the majors.
    • 
    

    
Same safety, a hundredth of the noise. The cost of keeping up is a design decision, not a fixed tax.

  


  

    🧰 Tools you'll actually use
    
npm / pnpm / Yarn, Poetry / uv, Cargo, Go modules; Dependabot and Renovate for update PRs; semantic-release, release-please or Changesets for versions and changelogs; commitlint to enforce Conventional Commits; private registries and proxies (Artifactory, Nexus, GitHub Packages) so an upstream deletion can't break your builds.


// package.json: ranges for direct deps, and an override for a transitive one (comments added here; real JSON has none)
{
  "dependencies": {
    "express": "^4.21.2",          // minors + patches
    "pg": "~8.13.1"                // patches only
  },
  "overrides": { "left-pad": "1.3.0" } // force one version deep in the tree
}


# Conventional Commits: the version is computed from these
fix(cart): round totals to whole cents                 # → patch
feat(search): add fuzzy matching                       # → minor
feat(api)!: remove the deprecated v1 client            # → major

refactor(auth): split token parsing

BREAKING CHANGE: verify() now throws instead of returning null   # footer → major


# .github/dependabot.yml
version: 2
updates:
  - package-ecosystem: "npm"
    directory: "/"
    schedule:
      interval: "weekly"
    cooldown:
      default-days: 3                 # let a release age before proposing it
      semver-major-days: 14
    groups:
      non-major:                      # one PR for all minor + patch updates
        patterns: ["*"]
        update-types: ["minor", "patch"]


# CI (GitHub Actions steps): frozen install, test, then release from main
- run: npm ci                      # fails if package.json and the lockfile disagree
- run: npm test
- run: npx semantic-release        # reads commits, bumps, writes notes, publishes
  env:
    GITHUB_TOKEN: ${{ secrets.GITHUB_TOKEN }}
    NPM_TOKEN: ${{ secrets.NPM_TOKEN }}

    
Try it locally: npx semver -r "^1.4.0" 1.4.0 1.6.0 2.0.0-beta.1 2.0.0 prints only the versions the range accepts (1.4.0 and 1.6.0). npm outdated shows what's behind; npm ls left-pad shows who pulls a package in.

    🚀 Startup vs big tech
    

      
Founding engineer (0 → 1)
Commit the lockfile on day one and use npm ci (or your ecosystem's frozen install) in CI and Docker. Turn on Dependabot or Renovate with weekly grouped PRs and automerge for green patch/minor updates. Tag service images with the commit SHA. Only keep a changelog for things other people install.

      
Big tech (1 → 100)
Internal registry proxies so builds never depend on the public registry being up or a package not being deleted; bots across thousands of repos with org-wide presets and cooldowns; Conventional Commits enforced in CI so internal libraries release automatically; SBOMs (software bills of materials: a list of everything inside each build) to answer “where do we run version X?” (Lesson 6.6); release trains for client apps, continuous delivery for services.

It shows up in “how do you run 200 services safely?” and in debugging stories. A senior answer:

    🏭 In the real world
    

      
An exact pin vs a deleted package 📜 npm · 2016 kik, left-pad, and npm

      
How: after left-pad and 272 other packages were unpublished, a replacement 1.0.0 didn't help chains that asked for exactly 0.0.3, so npm restored 0.0.3 from backup. npm's unpublish policy now allows removal freely only within 72 hours of publishing and only if no other public package depends on it.

      
Why this method: a registry is shared infrastructure; once others depend on a version, deleting it breaks strangers' builds.

    

    

      
Minimal version selection 🧰 Go modules · 2018 Russ Cox: Minimal Version Selection

      
How: each module lists minimum versions of its dependencies, and the build uses the lowest version that satisfies them all. go.sum holds hashes of every module that are checked on download.

      
Why this method: it produces what the post calls high-fidelity builds, close to what the author tested, and it's simple: no solver, and no surprise upgrades when someone publishes.

    

    

      
A default cooldown 🏢 GitHub Dependabot dependabot.yml options

      
How: Dependabot doesn't consider a new version for a version update until 3 days after its release, even without configuration; cooldown can set separate days for major, minor and patch. Security updates skip the wait.

      
Why this method: brand-new releases are the riskiest; a short delay lets the wider community find a broken or malicious version first.

    

    

      
A 4-week release train 🏢 Google Chrome · 2021 Speeding up Chrome's release cycle

      
How: starting with Chrome 94, a new milestone every 4 weeks, plus an Extended Stable option with milestones every 8 weeks for enterprises that need more time.

      
Why this method: a browser must be downloaded by billions of devices; a fixed rhythm lets web developers, enterprises and embedders plan, while features ship faster than before.

    

    

      
Calendar versions 🧰 Ubuntu · pip calver.org

      
How: Ubuntu numbers releases YY.0M (24.04 = April 2024); pip uses YY.MINOR.MICRO; Stripe's API versions are dates.

      
Why this method: for scheduled releases, the date is the most useful fact: it tells you how old and how supported a version is.

    

  


  

    🤯 Fun fact · the bot that bumped itself
    
On July 29, 2026, Renovate, the dependency-update bot, released 44.0.0, a major version, right after 43.288.0. Its maintainers explained the changes weren't breaking at all: a squash-merged commit message contained a BREAKING CHANGE reference, and their automated release tooling did exactly what the spec says. Because released versions can't be taken back, they announced they'd simply continue on 44.x. Even the experts get bitten by one line of text.

Check yourself

  

    
1. Your app's tree has 800 packages, each releasing about once a month, and about 1 release in 400 breaks you. With no lockfile, roughly what's the chance at least one breaking release lands in a month?

    

    
800 releases a month, each fine with probability 399/400: 1 − (399/400)800 ≈ 1 − e−2 ≈ 86%. Small per-release risks multiply across a big tree, which is why apps commit a lockfile and take updates through tested PRs.

  

  

    
2. Your library is at 3.4.1. Since then you merged: fix(io): close file handles; feat: add a timeout option; docs: fix typos; refactor!: drop Node 18 support. What does semantic-release publish?

    

    
The ! marks a breaking change, whatever the type, and the biggest bump wins: 4.0.0. Dropping a supported runtime breaks every user still on it, so it really is major. The fix and feat still appear in the changelog.

  

  

    
3. CI started failing overnight with no new commits. The failing package is a dependency of a dependency, which released a new minor version. What's the best lasting fix?

    

    
Pinning direct dependencies doesn't pin their ranges: the transitive package would still float. The lockfile freezes the whole tree, npm ci enforces it, and a bot keeps you current, so changes arrive as tested PRs instead of overnight surprises.

  


  

    📝 TL;DR
    
    
      
  • SemVer: MAJOR = incompatible API change, MINOR = compatible feature, PATCH = compatible fix; 0.x promises nothing; released versions are immutable.
    • 
      
  • ^1.4.0 = < 2.0.0, ~1.4.0 = < 1.5.0, ^0.4.0 = < 0.5.0; pre-releases are skipped. Transitive ranges are chosen by other people.
    • 
      
  • Apps: commit the lockfile, npm ci in CI, and move it forward with Dependabot/Renovate PRs (cooldown, grouping, automerge on green). Libraries: test against the newest allowed versions.
    • 
      
  • Conventional Commits (fix → patch, feat → minor, ! or BREAKING CHANGE: → major) let semantic-release pick versions and write changelogs (Keep a Changelog).
    • 
      
  • SemVer for libraries, commit SHAs for services, no-breaking-changes for APIs, CalVer for scheduled products; trains for installed software, continuous delivery for services.
