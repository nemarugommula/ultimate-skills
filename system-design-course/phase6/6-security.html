Phase 6 · Lesson 6

Security in production: secrets, OWASP, DDoS

At scale, you are attacked all the time, mostly by automated tools looking for the same few mistakes. Security in production means not making those mistakes, and making sure that when one slips through, the damage stays small.

🧰 You'll need (quick reminders)
  • Authentication vs authorization: who you are vs what you're allowed to do; OAuth2, JWT and mTLS (Lesson 4.6).
  • CDNs, rate limiting and API gateways sit in front of your servers (Lessons 1.4, 1.5 and 1.6).
  • The CI pipeline builds and scans every artifact (Lesson 6.1).
🎯 Hook

In December 2021 the world learned about Log4Shell (CVE-2021-44228), a flaw in Log4j, a Java logging library. In versions 2.0-beta9 to 2.14.1, a special string in something that got logged could make the server fetch and run code from an attacker's server. Apache rated it 10.0 out of 10 (critical). The US cybersecurity agency CISA reported “active, widespread exploitation.”

Most affected teams had never chosen Log4j: it came in as a dependency of a dependency. Every company had to answer one question fast: “where do we run it?” Many couldn't. This lesson is about answering questions like that before the attack, not during it.

Numbers first: the scale of attacks

Cloudflare's report on 2025 gives a sense of what's out there:

And for application bugs, the OWASP Top 10:2025 reports that 100% of the applications tested had some form of broken access control, the #1 category for the second edition running.

💡 Big idea Assume breach, limit the blast radius. You will have a bug, a leaked key, or a vulnerable dependency at some point. Defense in depth means several independent layers (edge filtering, authentication, authorization on every request, least-privilege credentials, encryption, audit logs) so one failure doesn't become a catastrophe.
🧠 Analogy: a hotel, not a castle

A castle has one big wall: once you're over it, you're everywhere. A hotel assumes strangers are inside. The front desk checks who you are (authentication), your key card opens only your room and only until checkout (least privilege, short-lived credentials), staff cards open more but are logged (audit), and the safe in your room protects valuables even if someone gets in (encryption at rest).

The OWASP Top 10: the mistakes attackers look for

OWASP (the Open Worldwide Application Security Project) publishes the Top 10 web application security risks, based on data from many tested applications. The 2025 list:

The fix for A01 is boring and essential: check authorization on the server, on every request, against the logged-in user. “The URL is hard to guess” is not a check.

Injection: when data becomes code

If you build a SQL query by gluing strings together, the user's input becomes part of the code:

query = "SELECT * FROM users WHERE name = '" + name + "'"   # ❌ never

The fix is the parameterized query (also called a prepared statement): you send the query shape and the values separately, so the database never treats the value as SQL. OWASP's SQL injection cheat sheet lists it as defense option 1. Try breaking the first version:

Notice O'Brien: string-gluing doesn't just let attackers in, it breaks for real customers too. Parameterized queries fix both. ORMs (object-relational mappers) parameterize for you, until someone writes a raw query “just this once.” Add least privilege as a second layer: the app's database user shouldn't be allowed to DROP tables at all.

Secrets: keys, passwords and tokens

A secret is anything that grants access: database passwords, API keys, cloud credentials, signing keys. Rules that prevent most breaches:

  • Never in git. Not in code, not in a committed .env file. Git history is forever: deleting the line later doesn't remove it from history. GitHub's secret scanning checks a repository's entire Git history on all branches, and its push protection can block a commit that contains a known secret type.
  • If one leaks, rotate it immediately. GitHub's own guidance: rotating the credential matters more than scrubbing history.
  • Use a secrets manager: HashiCorp Vault, AWS Secrets Manager, Google Secret Manager, Azure Key Vault. Apps fetch secrets at startup or runtime; access is logged.
  • Prefer short-lived, per-service credentials. Vault's database secrets engine creates a unique database username and password for each requester, with a lease (for example, 1 hour) after which they're revoked. No shared password to leak, and every query is traceable to one service.
  • Use cloud identities instead of keys where possible: workloads get temporary credentials from their role (Kubernetes service accounts, cloud IAM roles, OIDC from CI), so there's no long-lived key at all.

Least privilege: what can a leaked credential do?

IAM (identity and access management) policies say who can do which actions on which resources. AWS's IAM best practices start with temporary credentials and least-privilege permissions. The difference between a scary incident and a footnote is usually the scope of the credential that leaked.

✏️ Worked example: answering “are we affected by Log4Shell?”

You run 120 services. A critical CVE (a published vulnerability ID) lands on a Friday.

  • Without SBOMs: someone greps 120 repos, misses the ones that pull the library in transitively and the vendor images nobody built, and you're still finding copies weeks later.
  • With SBOMs stored per image: one query over 120 SBOMs lists every image containing log4j-core in the affected range. Patch, rebuild through the pipeline, and redeploy with the canary process from Lesson 6.2.
  • Meanwhile, a WAF rule blocking the attack pattern at the edge buys time, as a mitigation, not a fix.

Same shape as incidents in Lesson 6.4: mitigate at the edge first, then fix properly.

🧰 Tools you'll actually use

Parameterized queries, a least-privilege IAM policy, dynamic secrets from Vault, and scans in CI:

cur.execute("SELECT id, name, email FROM users WHERE name = %s", (name,))   # ✅
# Node + pg
await client.query('SELECT id, name, email FROM users WHERE name = $1', [name]) // ✅

$ vault secrets enable database

# In CI: scan the image for known vulnerabilities, and produce an SBOM
$ trivy image --severity HIGH,CRITICAL ghcr.io/acme/shop:$GIT_SHA
$ syft ghcr.io/acme/shop:$GIT_SHA -o spdx-json > sbom.json

Try it locally: docker run --rm -p 8200:8200 hashicorp/vault server -dev starts a throwaway Vault in dev mode (in-memory, never for production). Secret scanning on your laptop: gitleaks detect scans a repo's history for committed secrets.

🚀 Startup vs big tech

Founding engineer (0 → 1)

The cheap 80%: parameterized queries (use the ORM), an authorization check on every endpoint, secrets in the platform's secret store (never in git), push protection on, MFA everywhere, Dependabot or Renovate, a CDN with DDoS protection in front, encrypted managed databases, and one IAM role per service instead of one shared admin key.

Big tech (1 → 100)

A security team, threat modeling in design reviews, zero-trust networking with mTLS between services, central secrets platforms with dynamic credentials, SBOMs and signed artifacts for everything, bug bounties, red teams, and tamper-proof audit logs feeding a security operations team that has its own on-call and incident process.

🎤 Interview angle

Security often comes up as “what could go wrong?” or “how do you protect this data?” A senior answer covers:

  • AuthN and AuthZ on every request (and the IDOR trap: never trust an ID from the client without checking ownership).
  • Secrets in a manager, short-lived and least-privilege; encryption in transit and at rest.
  • Edge protection: CDN, DDoS mitigation, WAF, rate limits.
  • Supply chain (scans, SBOMs, signing) and audit logs, plus a plan for “a key leaked” (rotate, scope, detect).

Follow-ups: “An engineer committed an AWS key to a public repo an hour ago. What do you do?” (revoke and rotate now, check the audit logs for its use, then fix the process with push protection and short-lived credentials). “How do you store passwords?” (a slow salted hash like bcrypt or Argon2, never encryption you can reverse).

🏭 In the real world
The industry's checklist 🧰 Open source · OWASP · 2025 OWASP Top 10:2025

How: a consensus list of the most critical web application risks. Broken Access Control kept the #1 spot, with 100% of tested applications showing some form of it; Software Supply Chain Failures is A03, and its guidance starts with generating and managing an SBOM for all your software.

Why this method: attackers automate the common mistakes, so fixing the top 10 removes most of the easy wins.

A dependency nobody chose 🏢 CISA · 2021 Apache Log4j Vulnerability Guidance

How: CISA and partners responded to active, widespread exploitation of CVE-2021-44228 in Log4j 2.0-beta9 to 2.14.1, added it to the Known Exploited Vulnerabilities catalog, and told organizations to upgrade to fixed versions such as 2.17.1 for Java 8.

Why this method: a single library embedded in countless products meant the response had to start with an inventory: knowing where you run it.

Attacks too big to absorb yourself 🏢 Cloudflare · 2026 2025 Q4 DDoS threat report

How: Cloudflare reports 47.1 million DDoS attacks in 2025, an average of 5,376 automatically mitigated every hour, and a record 31.4 Tbps attack that lasted 35 seconds.

Why this method: at that size and speed, only a large network that detects and drops attacks automatically, close to their source, can keep a site up.

Credentials that expire on their own 🧰 Open source · HashiCorp Vault Vault database secrets engine

How: instead of a shared password in config, each service asks Vault for credentials; Vault creates a unique database user with a lease and revokes it when the lease ends.

Why this method: no long-lived secret to leak, and since every service has its own login, questionable data access can be traced back to one service.

Catching secrets before they leak 🏭 In production · GitHub About secret scanning

How: secret scanning searches a repository's entire Git history on all branches for API keys, passwords and tokens; push protection can stop a push containing a secret; partner integrations notify service providers about detected keys.

Why this method: leaked keys are found by automated scanners quickly, so detection has to be automatic too, and the fix is always to rotate.

🤯 Fun fact · 35 seconds

The record 31.4 Tbps attack in Cloudflare's report lasted only 35 seconds. That's shorter than it takes a human to read an alert and open a laptop. Big modern attacks are short bursts, which is why DDoS defense has to be fully automatic.

Check yourself

1. An attacker leaks your API key and it stays valid until someone notices, about 3 days later. If you switch to credentials that expire after 15 minutes, by roughly what factor does the window to use a leaked credential shrink?
3 days = 4,320 minutes; 4,320 ÷ 15 = 288, so about 300× less time. Combined with least privilege (less reachable) this shrinks the blast radius enormously, without anyone needing to notice the leak.
2. Your API serves GET /orders/{id}. Logged-in users can fetch other people's orders by changing the number. Which fix is right?
This is broken access control (an insecure direct object reference), OWASP's #1. Random IDs only make it harder to guess; they leak through logs, links and referrers. Authorization must be checked on the server, every time.
3. A startup is hit by a 2 Tbps DDoS attack. Its servers have 10 Gbps network links. What actually keeps the site up?
2 Tbps is 200× a 10 Gbps link: the traffic saturates the pipe before it reaches any code, and botnets use huge numbers of addresses. Only a network much bigger than the attack, spread across many locations, can absorb it.
📝 TL;DR
  • Assume breach; defend in depth; keep each credential's blast radius small (least privilege + short-lived).
  • OWASP Top 10:2025 starts with broken access control: authorize every request on the server. Stop injection with parameterized queries.
  • Secrets: never in git, in a manager, rotated on leak; prefer dynamic credentials and workload identities.
  • Encrypt in transit and at rest; track dependencies with SBOMs and scans; put DDoS protection and a WAF at the edge; keep audit logs.
