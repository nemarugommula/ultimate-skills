Phase 6 · Lesson 1

CI/CD pipelines: from commit to production, automatically

A pipeline is the robot that tests, builds and ships every change. A fast, trustworthy one lets a team ship many small changes a day; a slow, flaky one quietly becomes the bottleneck of the whole company.

🧰 You'll need (quick reminders)
  • Docker images: a packaged, versioned copy of your app and everything it needs (Lesson 5.1).
  • Kubernetes Deployments roll a new image out to running servers (Lessons 5.2 and 5.3).
  • Infrastructure as code / GitOps: the desired state lives in git, and tools apply it (Lesson 5.4).
🎯 Hook

In 2016 Google's testing team wrote that about 1.5% of all test runs across its huge test corpus gave a “flaky” result: the test passed and failed on the same code. That sounds tiny. But they did the math for a project with about 1,000 tests: around 15 of them will likely fail on any given run, for no real reason.

Small per-test problems multiply across a pipeline. By the end of this lesson you'll be able to design a pipeline, measure it, and explain why its speed and trustworthiness decide how fast a company can move.

Numbers first: what a pipeline costs you

Picture a team of 20 engineers. Each pushes about 3 changes a day, so 60 pipeline runs a day. Suppose a run takes 40 minutes.

40-minute pipeline10-minute pipeline
Wait before you know your change works40 min (you switch tasks, lose focus)10 min (grab a coffee)
Engineer-hours spent waiting per day (if each run blocks someone)60 × 40 min = 40 hours60 × 10 min = 10 hours
Fixes you can ship in a 1-hour outage1, maybe5 or 6

Forty engineer-hours a day is five people doing nothing but waiting. That's why big companies have whole teams that only work on build speed.

The words, spelled out

  • CI (continuous integration): everyone merges small changes into the shared main branch often, and every merge is automatically built and tested. The goal: find conflicts and bugs within minutes, not weeks.
  • CD means two related things. Continuous delivery: every change that passes is ready to ship with one click. Continuous deployment: every change that passes is shipped automatically, no click.
  • A pipeline is the ordered list of automated steps (called stages or jobs) a change goes through.
  • An artifact is the thing the pipeline produces and ships: a Docker image, a jar file, a static website bundle. It's tagged with the git commit it came from.
  • An environment is a place the artifact runs: dev, staging (a production look-alike for final checks) and production (real users).
💡 Big idea Build once, promote the same artifact. The pipeline builds one image, tags it with the commit hash, and moves that exact image from staging to production. If you rebuild for each environment, you're shipping something you never tested.

Order matters: cheap, fast checks first. A lint error should fail the run in 1 minute, not after 15 minutes of integration tests.

The test pyramid

Tests come in three sizes, and you want many small ones and few big ones:

LevelHow many (typical)Speed of one testFlakiness
Unit (bottom, wide)thousandsmillisecondslow: no network, no clock
Integration (middle)hundredssecondsmedium: real database, real ports
End-to-end (top, narrow)tenstens of seconds to minuteshigh: browsers, timeouts, many services

An “ice-cream cone” (mostly end-to-end tests) feels thorough but gives a slow, flaky pipeline. Push each check down to the lowest level that can catch it.

🧠 Analogy: the airport security line

The pipeline is airport security for code. Cheap checks first (is that your boarding pass?), expensive ones later (the body scanner). Several lanes run in parallel so the line moves. And if the scanner beeps randomly at 1 in 100 people (a flaky test), soon nobody trusts the beep, and people start waving travellers through. That's the moment security stops working.

Trunk-based development: merge small, merge daily

Two ways to work in git. With long-lived feature branches, a few people work on a branch for days or weeks, then merge a big change. With trunk-based development, everyone merges small changes into the main branch (the “trunk”) at least once a day.

The DORA research program (dora.dev) lists the practices that go with trunk-based development: three or fewer active branches, merging to trunk at least once a day, and no code freezes. Unfinished features hide behind feature flags (Lesson 6.2), so half-built code can be merged safely without users seeing it.

How you measure delivery: the DORA metrics

DORA (DevOps Research and Assessment) studies thousands of teams. It originally used four “key” metrics and now uses five. They split into speed (throughput) and safety (instability):

MetricQuestion it answersType
Change lead timeHow long from commit to running in production?speed
Deployment frequencyHow often do we deploy?speed
Failed deployment recovery timeWhen a deploy breaks things, how fast do we recover?speed
Change fail rateWhat share of deploys need an immediate fix or rollback?safety
Deployment rework rateWhat share of deploys are unplanned, done because of an incident?safety

The surprising finding behind DORA's work: speed and safety are not a trade-off. Teams that ship small changes often tend to break less, because each change is small and easy to undo.

✏️ Worked example: speeding up a 40-minute pipeline

A pipeline runs everything one after another: install 4 min, lint 1, unit tests 8, build 6, scan 2, integration tests 10, deploy to staging 3, smoke tests 2, deploy to production 8. Total: 4 + 1 + 8 + 6 + 2 + 10 + 3 + 2 + 8 = 44 minutes.

  • Cache dependencies: install drops from 4 to 1 min. Saves 3. Install from a committed lockfile with npm ci so every run gets the same versions (Lesson 6.1b).
  • Cache Docker layers: the build only redoes the layers that changed, 6 → 1.5 min. Saves 4.5.
  • Run in parallel: lint, unit tests and the build don't depend on each other. Scan and integration tests both need only the image. Now the slowest branch sets the pace.
  • Shard the unit tests across 4 runners: 8 min becomes about 2 min each (plus a little setup overhead).

Now the critical path is install + build (2.5) → integration tests (10) → staging (3) → smoke (2) → production (8) ≈ 25.5 minutes, down from 44, with no test removed. Build it yourself below.

Flaky tests: small odds, multiplied

A flaky test passes and fails on the same code: a race condition, a timeout that's a bit too tight, a test that depends on another test's leftovers, a call to a real network. Say each test has a tiny chance p of failing for no reason, and you have n tests. A run is clean only if every test behaves:

P(run fails for no reason) = 1 − (1 − p)n “The chance at least one test flakes is one minus the chance that all n of them pass.” With p = 0.1% and n = 1,000 tests, that's 1 − 0.9991000 ≈ 63%.
p: chance one test flakes on one runn: number of tests in the run

Each test is 99.9% reliable, yet nearly two out of three runs go red. People learn to click “re-run” without reading the failure, and then a real failure gets re-run too.

Pick how many tests you have and how flaky each one is. “Retries” re-runs a failed test before declaring failure, which hides flakes (and, sometimes, real intermittent bugs). Press Run 50 pipelines to simulate a day of runs on code that is actually fine: every red dot is a false alarm.

Try it: with 1,000 tests at 0.1%, about 63% of runs fail. One retry brings it down to about 0.1%, because a flake now has to happen twice in a row. That's why most CI systems offer retries, and also why Google's team tracks flaky tests and quarantines the worst ones instead of just retrying forever: a retry hides the symptom, not the cause.

🧰 Tools you'll actually use

Hosted CI: GitHub Actions, GitLab CI, CircleCI, Buildkite. Self-hosted: Jenkins. Kubernetes-native delivery: Argo CD or Flux (GitOps, Lesson 5.4), Spinnaker. Big monorepos use build systems that cache and only rebuild what changed, like Bazel. A GitHub Actions workflow that lints and tests on every pull request, shards tests, and builds one image tagged with the commit on main:

# .github/workflows/ci.yml
name: ci
on:
  pull_request:
  push:
    branches: [main]
concurrency:                         # a newer push cancels the older run
  group: ${{ github.workflow }}-${{ github.ref }}
  cancel-in-progress: true
jobs:
  test:
    runs-on: ubuntu-latest
    strategy:
      matrix:
        shard: [1, 2, 3, 4]             # 4 runners in parallel
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 20
          cache: npm                     # dependency cache keyed on package-lock.json
      - run: npm ci
      - run: npm run lint                 # cheap checks first
      - run: npx jest --shard=${{ matrix.shard }}/4
  build:
    needs: test                         # waits for all 4 shards
    if: github.ref == 'refs/heads/main'
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: docker build -t ghcr.io/acme/shop:${{ github.sha }} .   # build ONCE, tag = commit
      - run: docker push ghcr.io/acme/shop:${{ github.sha }}
  deploy-staging:
    needs: build
    environment: staging                # environments can require approvals and hold secrets
    runs-on: ubuntu-latest
    steps:
      - run: ./deploy.sh staging ${{ github.sha }}   # same image goes to prod later

Try it locally: the open-source tool act runs GitHub Actions workflows on your laptop in Docker (act pull_request). For GitLab, the same ideas live in .gitlab-ci.yml with stages:, needs: and cache:.

🚀 Startup vs big tech

Founding engineer (0 → 1)

Day one: a GitHub Actions workflow that runs lint and tests on every pull request and deploys main automatically to a managed platform. Keep the pipeline under 10 minutes. No staging environment yet is fine if you have preview deploys and quick rollback. Don't build a release process: build a habit of tiny pull requests.

Big tech (1 → 100)

Monorepos or thousands of repos, a build system with remote caching (Bazel-style) that only rebuilds what changed, test sharding across hundreds of machines, flaky-test tracking and quarantine, signed artifacts, and release trains or progressive delivery tied to SLOs. A dedicated developer-productivity team owns pipeline speed as a metric.

🎤 Interview angle

CI/CD rarely gets its own interview question, but “how would you ship this safely?” comes up in almost every senior design and behavioral round. A strong answer covers:

  • The stages in order (fast checks first), and build once, promote the same artifact tagged by commit.
  • Trunk-based development + feature flags, so merging isn't the same as releasing.
  • How you'd measure delivery: the DORA metrics (lead time, deploy frequency, change fail rate, recovery time).
  • How you keep the pipeline fast and trusted: caching, parallelism, the test pyramid, handling flaky tests.

Follow-ups: “Your pipeline takes an hour. Where do you start?” (measure the critical path first). “How do you handle database migrations in CD?” (Lesson 6.2: expand and contract).

🏭 In the real world
Measuring and fighting flaky tests 🏢 Google · 2016 Flaky Tests at Google and How We Mitigate Them

How: Google reported a steady rate of about 1.5% of test runs being flaky, and that almost 16% of its tests showed some flakiness. It re-runs failing tests automatically, tracks flakiness per test, and can quarantine badly flaky tests.

Why this method: at Google's scale even a tiny per-test flake rate turns into many false failures per release, so flakiness has to be measured and managed like any other reliability problem.

The delivery metrics everyone uses 📜 Research · DORA DORA's software delivery performance metrics

How: DORA measures throughput (change lead time, deployment frequency, failed deployment recovery time) and instability (change fail rate, deployment rework rate). It moved from the original four keys to a five-metric model.

Why this method: a few outcome metrics that any team can compute from its deploy history, so teams improve the delivery system instead of arguing about tools.

One repository for a whole company 🏢 Google · 2016 Why Google Stores Billions of Lines of Code in a Single Repository (CACM)

How: Google keeps most of its code in one custom-built monolithic repository that is the common source of truth for tens of thousands of developers, with systems and workflows built to make that practical.

Why this method: one source of truth means one version of each library and changes that can touch many projects at once; the paper also lays out the trade-offs, such as needing heavy tooling investment.

Where CI came from 📜 History · Extreme Programming Martin Fowler: Continuous Integration

How: the article lists the core practices: everything in a version-controlled mainline, an automated self-testing build, everyone pushing to mainline every day, every push triggering a build, fixing broken builds immediately and keeping the build fast.

Why this method: CI was developed as part of Extreme Programming; integrating often keeps each merge small, so problems are cheap to find and fix.

Dependency caching in CI 🏭 In production · GitHub Actions GitHub Actions: dependency caching

How: actions/cache saves folders like ~/.npm under a key (often a hash of the lock file); on the next run it looks for an exact key match, then partial matches, then restore-keys.

Why this method: downloading the same packages on every run is pure waste; a cache keyed on the lock file is only invalidated when dependencies actually change.

🤯 Fun fact · “a couple of hours”

Martin Fowler's CI article quotes Kent Beck, one of the creators of Extreme Programming: “No code sits unintegrated for more than a couple of hours.” In the 1990s that sounded extreme, when many teams merged every few weeks. Today it's simply what trunk-based teams do.

Check yourself

1. Your suite has 800 tests, and each one flakes 0.1% of the time. Roughly how often does a run fail even though the code is fine?
1 − 0.999800 ≈ 0.55. A run is clean only if all 800 tests behave, so tiny per-test odds multiply. That's why flaky tests have to be tracked and fixed, not just retried.
2. A team works on feature branches for 3 weeks at a time, and every merge turns into a day of conflicts and broken tests. What's the best change?
Big merges are painful because they're big. Trunk-based development keeps each integration small, and feature flags separate “merged” from “released”. DORA lists merging to trunk daily and avoiding code freezes as part of the practice.
3. Why should the pipeline build one Docker image, tagged with the commit hash, and deploy that same image to staging and then production?
Rebuilding per environment can pull different dependency versions or base images, so you'd ship something nobody tested. The commit tag also tells you exactly what's running, which makes rollback a one-line change.
📝 TL;DR
  • CI = merge small changes often, each one built and tested automatically. CD = every passing change is ready to ship (delivery) or shipped (deployment).
  • Order stages cheap-to-expensive; build once and promote the same artifact, tagged by commit.
  • Speed comes from caching, parallel jobs and sharding; the critical path sets the wall-clock time.
  • Flakes multiply: P(false failure) = 1 − (1 − p)n. Track and quarantine flaky tests.
  • Measure delivery with DORA: lead time, deploy frequency, recovery time, change fail rate, rework rate.
