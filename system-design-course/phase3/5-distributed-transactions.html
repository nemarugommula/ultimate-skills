Distributed transactions: 2PC, sagas & the outbox

One database gives you transactions for free. Once an operation spans two databases, or a database and a message broker, “all or nothing” becomes a design problem. Here are the three answers the industry actually uses.

🧰 You'll need (quick reminders)
  • ACID transactions: inside one database, a group of writes commits together or not at all (Lesson 2.5).
  • Kafka and CDC: change data capture reads a database's own log and publishes each change (Lesson 3.2).
  • Idempotency: a step that's safe to run twice (Lesson 3.3).
🎯 Hook

Netflix keeps its movie data in a primary database and copies it into others: Elasticsearch for search, caches for speed. In 2019 its engineers described what goes wrong when an application simply writes to two stores in a row, a dual write: if the second write fails, the stores drift apart, and someone has to build a repair job to find and fix the differences.

The obvious fix, a distributed transaction across both, wasn't available either: Elasticsearch doesn't support that kind of transaction. So they built Delta, a platform that reads the database's change log and feeds every other store from it. That's the pattern you'll learn here.

Numbers first: rare failures, every day

An order service saves the order to Postgres, then publishes OrderPlaced to Kafka so the warehouse ships it. Suppose the publish fails (broker blip, process killed by a deploy) only 0.01% of the time.

At scale, “almost never” is “every day”. And you can't fix it by reordering the two writes: publish first and a failed database write creates a ghost event for an order that doesn't exist.

💡 Big idea You can't atomically write to two independent systems without a coordinator. So either coordinate them (two-phase commit, which blocks when the coordinator fails), split the work into local transactions with undo steps (a saga), or write once, to one place, and derive everything else from it (the transactional outbox + CDC).
🧠 Analogy: booking a trip

You need a flight, a hotel and a car. Two-phase commit is a travel agent who phones all three, asks each to hold a booking, and confirms only when all three say yes. If the agent faints mid-call, all three hold your booking, unsure, blocking other customers. A saga is booking each one yourself in turn, and if the car is sold out, cancelling the hotel and then the flight. Each cancellation is a compensating action. The outbox is writing your plan in one notebook, and having an assistant read the notebook and make every call, retrying until each one's done.

Option 1: two-phase commit (2PC)

A coordinator runs two rounds. Phase 1, prepare: “can you commit?” Each participant writes everything to disk, locks the rows and votes yes or no. Phase 2, commit: if all voted yes, “commit”; otherwise “abort”.

The catch: a participant that voted yes has promised to obey, so it cannot decide alone. If the coordinator crashes after the prepare, participants hold their locks until it comes back. That's why 2PC is called a blocking protocol. Postgres supports it (PREPARE TRANSACTION), but its docs say the feature is meant for external transaction managers, not applications, and warn against leaving transactions prepared for long.

Option 2: sagas

A saga (the name comes from a 1987 paper on long-lived transactions) breaks one big transaction into a sequence of local transactions, one per service, each committed on its own. If step k fails, the saga runs compensating transactions for steps k−1 … 1 in reverse: refund the card, release the stock, cancel the order.

HowEach service listens for events and emits the next: OrderCreated → inventory reserves → StockReserved → payments charges…A central orchestrator tells each service what to do and tracks the saga's state

Sagas give up isolation (the I in ACID): other requests can see the order in “pending” while the saga runs, and a refund happens after the charge. Design for it: show “pending” states, and use “semantic locks” like a status = PENDING flag.

✏️ Worked example: a food order saga

Steps: create order (PENDING) → reserve the dish at the restaurant → charge $30 → assign a courier → mark APPROVED. No courier is available.

  • Steps 1–3 committed: an order exists, the dish is reserved, $30 was charged.
  • Step 4 fails, so compensate in reverse: refund $30 → release the dish → set the order to CANCELLED.
  • Net effect: $30 − $30 = $0, nothing held. But for a few seconds the customer's card showed a $30 charge: sagas are “eventually all-or-nothing”, not instantly.
  • If the refund call times out, retry it (with backoff, Lesson 3.3). Compensations must be idempotent and retried until they succeed; there's no undo for an undo.

Option 3: the transactional outbox

The cleanest fix for the dual write: don't write to the broker from your request at all. In the same local transaction as the order, insert a row into an outbox table describing the event. The database guarantees both rows commit together or not at all. Then a separate relay reads the outbox (by polling, or with CDC reading the database log, e.g. Debezium's outbox event router) and publishes to Kafka, retrying until it succeeds.

The relay can crash after publishing but before marking the row as sent, so it may publish twice. That's fine: the event has a unique ID, and consumers dedupe on it (Lesson 3.3). At-least-once + idempotent consumers = effectively once.

🧰 Tools you'll actually use

Sagas / workflows: Temporal (open source + Temporal Cloud), Cadence (open-sourced by Uber), AWS Step Functions, Azure Durable Functions, Camunda. Outbox: a table + Debezium's outbox event router, or a polling relay. 2PC: XA transactions, Postgres PREPARE TRANSACTION. The outbox write, in one transaction:

BEGIN;
INSERT INTO orders (id, customer_id, total_cents, status) VALUES (42, 7, 3000, 'PENDING');
INSERT INTO outbox (id, aggregatetype, aggregateid, type, payload)   -- Debezium's default columns
  VALUES (gen_random_uuid(), 'order', '42', 'OrderPlaced', '{"total_cents":3000}');
COMMIT;   -- both rows or neither; Debezium then publishes to topic outbox.event.order

An orchestrated saga with compensations in Temporal's Python SDK. If the worker crashes, Temporal replays the recorded history and the workflow carries on from the last completed step:

from datetime import timedelta
from temporalio import workflow

T = timedelta(seconds=30)

@workflow.defn
class OrderSaga:
    @workflow.run
    async def run(self, order: dict) -> str:
        undo = []
        try:
            await workflow.execute_activity(reserve_stock, order, start_to_close_timeout=T)
            undo.append(release_stock)
            await workflow.execute_activity(charge_card, order, start_to_close_timeout=T)
            undo.append(refund_card)
            await workflow.execute_activity(assign_courier, order, start_to_close_timeout=T)
            return "APPROVED"
        except Exception:
            for step in reversed(undo):                 # compensate in reverse order
                await workflow.execute_activity(step, order, start_to_close_timeout=T)   # retried by Temporal
            return "CANCELLED"

Try it locally: temporal server start-dev (the Temporal CLI) runs a dev server with a web UI on port 8233, where you can watch each workflow's event history.

Before any of these, ask: can the data live in one database? A single Postgres transaction is simpler than every pattern on this page. Split databases only when you must (Lesson 4.1).

🚀 Startup vs big tech

Founding engineer (0 → 1)

Keep related data in one Postgres and use real transactions. When you must notify other systems, use an outbox table with a simple polling worker. Avoid microservice sagas until the team and the domain demand them; a modular monolith with one database covers a long way.

Big tech (1 → 100)

CDC from every database (Debezium, Netflix's DBLog/Delta), outbox as the standard way to publish events, workflow engines (Temporal, Cadence) for long business processes with compensations, and distributed SQL databases that handle cross-shard transactions internally so applications don't have to.

🎤 Interview angle

“How do you keep the order service and the payment service consistent?” is a classic. A senior answer covers:

  • Spotting the dual write and saying why reordering doesn't fix it.
  • Choosing a saga (orchestrated, for clarity) with explicit compensations, each idempotent and retried.
  • Publishing events via a transactional outbox + CDC, with consumers deduping on event ID.
  • Explaining why 2PC is avoided across services: blocking, coupling, and many systems don't support it.
  • The user-visible in-between states (“payment pending”) and how the UI shows them.

Common follow-ups: “What if the refund fails?” “What if the orchestrator crashes halfway?” “How does the consumer avoid processing an event twice?” “Choreography or orchestration, and why?”

🏭 In the real world
Replacing dual writes with a change log 🏢 Netflix · 2019 Delta: a data synchronization and enrichment platform

How: Delta captures changes from the source database (CDC) and syncs derived stores like Elasticsearch, with optional enrichment by calling other services. The post walks through one real use case: movie search.

Why this method: dual writes drift and need custom repair jobs, and distributed (XA) transactions don't work with stores like Elasticsearch.

The saga and outbox patterns 🧰 Pattern microservices.io: Saga · Transactional outbox

How: a saga is a sequence of local transactions, coordinated by choreography (events) or orchestration (a central coordinator), with compensating transactions to undo. The outbox stores messages in the service's database as part of its local transaction.

Why this method: 2PC across the database and the broker isn't viable, but sending a message after (or during) a transaction isn't reliable without it.

Outbox events straight from the database log 🧰 Open source Debezium outbox event router

How: a Debezium connector captures inserts to the outbox table and routes each to a topic based on its aggregatetype (e.g. outbox.event.order), with the event's id as a header for deduplication.

Why this method: no polling, no extra load on the database, and events go out in commit order.

Durable orchestration 🏢 Uber · 2017 Uber's open source orchestration tool, Cadence

How: Cadence gives engineers persistence, queues and timers so that a long multi-service flow can be written as ordinary code; Uber open-sourced it in 2017. Temporal, a similar open-source engine, replays a workflow's event history to rebuild its state after a crash.

Why this method: hand-written sagas end up as a tangle of callbacks, state tables and retry cron jobs; a workflow engine makes the saga's state durable for you.

Where the word comes from 📜 History · 1987 Garcia-Molina & Salem: Sagas (SIGMOD)

How: long-lived transactions (monthly statements, insurance claims) held database resources for too long, so the paper split them into a sequence of transactions, each with a compensating transaction.

Why this method: holding locks for a long time blocks everyone else; short transactions plus undo steps keep the system moving.

🤯 Fun fact · an idea 30 years ahead

The Sagas paper was written in 1987, at Princeton, for long transactions inside a single database. Decades later it became the standard answer for keeping microservices consistent, without the paper's authors having microservices in mind at all.

🌉 How it connects

ACID inside one database (Lesson 2.5) is what we're trying to stretch here. The outbox relies on CDC and Kafka (Lesson 3.2), and every saga step and consumer must be idempotent (Lesson 3.3). 2PC's coordinator problem is why consensus exists (Lesson 3.4). Service boundaries decide how many sagas you'll need (Lesson 4.2), and the payment system design is a saga with real money (Lesson 7.7).

Check yourself

1. A service saves 2,000,000 orders a day and then publishes an event for each. The publish step fails 0.005% of the time. Roughly how many orders a day are saved but never announced?
2,000,000 × 0.00005 = 100 a day. Tiny failure rates become daily incidents at scale, which is why “just publish after commit” isn't good enough.
2. An order saga charges the card, then fails to reserve stock. What should happen?
Each saga step already committed in its own service, so there's no single ROLLBACK. You undo with compensating transactions in reverse order, and since there's no undo for an undo, compensations must be idempotent and retried until they work.
3. A user-signup service must create the account and reliably publish UserSignedUp to Kafka. Which design is best?
Commit-then-publish loses events when the publish fails. 2PC across Postgres and Kafka isn't practical. The outbox makes the event part of the same local transaction, and the relay delivers it at least once; consumers dedupe on the event ID.
📝 TL;DR
  • Writing to two systems in a row (a dual write) loses or invents events at scale; reordering doesn't help.
  • 2PC is atomic but blocking: prepared participants hold locks until the coordinator decides. Avoid it across services.
  • Sagas = local transactions + compensations in reverse. Orchestrate for clarity; make every step and undo idempotent.
  • Outbox = write the event in the same local transaction, publish it with a relay or CDC, dedupe downstream.
