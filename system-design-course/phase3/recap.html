Phase 3 · Recap

Recap: async & distributed systems

What happens when work leaves the request path: queues and logs to move it, idempotency to survive repeats, consensus to agree, sagas and outboxes to stay consistent, and pipelines to turn events into answers.

🧾 Cheat sheet

📨

3.1 Queues & pub/sub

backlog growth = arrivals − processing. Queues absorb spikes, not missing capacity. Ack + visibility timeout = at-least-once; always a DLQ. Work queue = one consumer; fan-out = every subscriber. SQS/SNS, RabbitMQ, Redis Streams, NATS.

🪵

3.2 Kafka & streaming

Partitions = max parallelism per group. Order only within a partition: key by entity. RF 3, acks=all, min.insync.replicas=2. Alert on lag. CDC turns a DB log into a stream. Kafka, MSK, Confluent, Debezium.

📜

3.2b Event sourcing & CQRS

state = replay(events); snapshots cap replay at N − 1. Commands can fail; events are facts. Append at the expected version. Read models lag (read-your-writes) and can be backfilled: history ÷ (replay − live rate). Version events and upcast. KurrentDB, Postgres events table, Axon, Marten, Kafka.

🔁

3.3 Retries & idempotency

Retries multiply: 3 per layer × 5 layers = 243×. Retry at one layer, full jitter: random(0, min(cap, base·2ⁿ)). Exactly-once effect = at-least-once + idempotency key with a unique constraint. Stripe keys, tenacity, Kafka idempotent producer.

👑

3.4 Consensus

quorum = ⌊n/2⌋ + 1; 3 nodes survive 1, 5 survive 2, even sizes don't help. Raft: terms, randomized timeouts, majority commit. Leases + fencing tokens stop zombie leaders. etcd, ZooKeeper, Consul, KRaft.

⏱️

3.4b Clocks & gossip

If clock offset > gap between writes, LWW drops one. Lamport respects cause; vector clocks flag concurrency, so keep siblings and merge. HLC/TrueTime bound real time. Gossip ≈ log₂ N rounds; phi accrual and SWIM detect failures; Merkle trees repair drift. Cassandra, Riak, memberlist/Consul, CockroachDB.

🧾

3.5 Distributed transactions

Never dual-write. 2PC blocks if the coordinator dies. Saga = local steps + compensations in reverse (idempotent, retried). Outbox = event in the same transaction, relay/CDC publishes. Temporal, Step Functions, Debezium outbox.

🌊

3.6 Batch & stream

Map → shuffle by hash(key) mod R → reduce. Windows: tumbling, sliding, session, on event time. watermark = max seen − delay: bigger delay, more complete, later. ELT into a warehouse first. Spark, Flink, Kafka Streams, dbt.

🏗️ Design it yourself: the food-delivery order pipeline

📋 The brief

A food-delivery app handles 2 million orders a day, with a dinner peak about 10× the daily average. Placing an order must return in under 300 ms. After that: the restaurant must accept it, the card must be charged exactly once, a courier assigned, the customer notified at each step, and a live operations dashboard must show orders per minute per city. Use only ideas from this phase.

Reveal One good design + the classic mistakes

Requirements. Fast synchronous “order placed”; everything else async. Exactly-once charge; no lost or ghost orders; per-order event ordering; restaurant/courier/notification services may be down for minutes; dashboard fresh within ~1 minute; analytics daily.

Numbers. 2,000,000 ÷ 86,400 ≈ 23 orders/s on average, about 230/s at peak. About 6 events per order (placed, accepted, charged, courier assigned, picked up, delivered) → about 1,400 events/s at peak, about 1 KB each ≈ 1.4 MB/s, tiny for Kafka. Per day 12 million events ≈ 12 GB; × 3 replicas × 7 days ≈ 252 GB of Kafka disk.

Architecture.

  • Order service: one Postgres transaction inserts the order (status PENDING) and an outbox row; returns 202 in a few ms. Debezium publishes the outbox to Kafka topic orders, keyed by order ID (per-order ordering), 12 partitions for headroom.
  • Saga orchestrator (e.g. Temporal): restaurant accepts → charge card → assign courier → APPROVED. Compensations: refund, notify restaurant, cancel. Every activity retried with exponential backoff + jitter.
  • Payments: charge with an idempotency key = order ID + attempt purpose, stored with a unique constraint; the payment provider gets the same key.
  • Notifications: fan-out from Kafka to a work queue per channel (push, SMS, email) with DLQs; consumers dedupe on event ID.
  • Dashboard: Flink job, 1-minute tumbling windows by city on event time, watermark delay ~10 s; late events corrected by the nightly batch.
  • Analytics: CDC from Postgres into a warehouse (ELT); nightly Spark/dbt jobs.
  • Consensus: not built by you: managed Kafka (KRaft) and managed Postgres with failover; the orchestrator's own store is replicated.

Trade-offs. Orchestration over choreography (6 steps is too many to follow as scattered events). Outbox adds a relay to run but removes lost/ghost events. The dashboard is approximate for ~10 s and corrected later. Kafka over plain queues because many consumers need the same events and replay is valuable.

Classic mistakes. Publishing to Kafka after commit (dual write). Charging without an idempotency key. No key on the topic (a “delivered” event processed before “picked up”). Retrying in every layer. Visibility timeout shorter than the job. No DLQ, so one bad message blocks a worker forever. Counting the dashboard by processing time. Running your own ZooKeeper/etcd at a startup.

🏆 Boss quiz

1. Jobs normally arrive at 500/s and workers can do 1,500/s. A flash sale sends 2,000/s for 5 minutes. How big does the backlog get?
Growth = 2,000 − 1,500 = 500 jobs/s for 300 s = 150,000. Afterwards it drains at 1,500 − 500 = 1,000/s, so about 150 s. Nobody's request failed; some work was just late.
2. A consumer group of 4 reads a 12-partition topic. One consumer's machine loses power. What happens next?
The group only notices when heartbeats stop for the session timeout (45 s by default). Then it rebalances: 12 partitions over 3 consumers, 4 each. The data is safe in the log; lag just builds up meanwhile.
3. A Kafka consumer charges a card and then commits its offset. It crashes between the two. What prevents a double charge on restart?
Committing first risks losing the charge (at-most-once). Kafka transactions cover Kafka-to-Kafka writes, not an external card charge. The external side effect needs its own idempotency: the repeated event carries the same order ID, so the payment provider returns the original charge.
4. A 3-node etcd cluster has one node down for an upgrade when a second node crashes. What's the cluster's state?
Quorum for 3 is 2. With one node left there's no majority, so no leader can be elected and no write can commit. That's the safe choice. It's also why production control planes often run 5 nodes: one in maintenance plus one failure still leaves 3.
5. A fraud rule: “flag a card with more than 5 failed payments in any 10-minute period”. Which window fits?
Tumbling windows miss bursts that straddle a boundary (3 failures at 12:08 and 3 at 12:11 never share a window). Sliding windows check every recent 10-minute span. Sessions measure activity bursts, not fixed periods.
📝 TL;DR of the phase
  • Move slow or spiky work to queues and logs; size them with arrivals − processing, and watch depth, age and lag.
  • Everything is at-least-once: retry politely (one layer, backoff + jitter) and make every side effect idempotent.
  • Agreement needs majorities: 3 or 5 nodes, leases and fencing; use etcd/ZooKeeper, don't build it.
  • Across services, never dual-write: outbox for events, sagas with compensations for business flows.
  • Batch for complete answers, streams for fresh ones; event time + watermarks make the trade-off explicit.
