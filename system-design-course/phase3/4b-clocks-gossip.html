Phase 3 · Lesson 4b

Time without a leader: clocks, vector clocks & gossip

Machines can't agree on what time it is, so “the latest write wins” quietly loses data. Logical clocks order events by cause instead of by clock, vector clocks spot conflicting writes, and gossip spreads news to thousands of nodes with no leader at all.

🧰 You'll need (quick reminders)
  • Async replicas accept writes and copy them later, so copies can diverge (Lesson 2.3).
  • Last-write-wins (LWW) picks the copy with the latest timestamp; TrueTime is Spanner's clock with an error bar (Lesson 2.6).
  • Consensus uses a leader and majorities; Raft's numbered terms and heartbeats (Lesson 3.4).
🎯 Hook

At midnight UTC (Coordinated Universal Time) on 1 January 2017, a leap second was added to the world's clocks. Deep inside Cloudflare's DNS software, code measured how long an upstream server took to answer by subtracting two readings of the wall clock. It assumed the result could never be negative. During the leap second, time went backwards, the measurement went negative, and a random-number function that was fed that value panicked.

At peak about 0.2% of Cloudflare's DNS queries were affected. The postmortem's diagnosis: the belief that time cannot go backwards. Every distributed system that orders events by wall-clock time makes a version of that bet. This lesson is about not making it.

Numbers first: how wrong is a clock?

Every server's clock is driven by a cheap crystal that ticks slightly too fast or too slow. NTP (Network Time Protocol) nudges it back toward a reference server every so often. Typical figures:

Now the damage. Server A's clock runs 80 ms fast. A user updates their cart on A at real time 12:00:00.000, so the write is stamped .080. Thirty milliseconds later they change it again, and that request lands on server B, whose clock is right: stamped .030. Last-write-wins keeps the higher timestamp: A's older write. The newer change is silently thrown away. No error, no log line.

💡 Big idea Stop asking “what time was it?” and ask “could this event have known about that one?” That's causality, and you can track it with counters instead of clocks. A Lamport clock gives an order that never contradicts cause and effect. A vector clock also tells you when two writes were concurrent (neither knew about the other), so you keep both instead of guessing. And gossip spreads information through a cluster with no leader, reaching everyone in a number of rounds that grows only with log N.
🧠 Analogy: two copies of a shopping list

You and your partner each have a paper copy of the shopping list. Next to it you each keep a tally: “edits by me, edits by you”. When you meet, you compare tallies. If yours says (3, 1) and theirs says (2, 1), yours includes everything theirs has, so you throw theirs away. If yours says (3, 1) and theirs says (2, 2), each of you made an edit the other hasn't seen. Neither list is “newer”; you sit down and merge them. Wristwatches never come into it. That tally is a vector clock.

Lamport clocks: a counter that respects cause

In 1978 Leslie Lamport defined “a happened before b” without any physical clock: a and b are in the same process and a came first, or a is sending a message and b is receiving it (or a chain of those). Otherwise they're concurrent. Then he gave each process a counter:

  1. Before each event, add 1 to your counter.
  2. Every message carries the sender's counter.
  3. On receiving, set your counter to max(yours, the message's) + 1.

Guarantee: if a happened before b, then L(a) < L(b). Sort by (counter, node ID) and you get one total order that every node agrees on and that never puts an effect before its cause. Raft's terms (Lesson 3.4) are this idea: a number that only goes up, and seeing a bigger one means you're behind.

The limit: L(a) < L(b) does not mean a happened before b. Two independent writes get some order, but you can't tell that they were actually concurrent. For conflict detection you need more information.

Vector clocks: one counter per node

A vector clock keeps one counter per replica, like [A:2, B:1, C:0]. A replica that accepts a write adds 1 to its own entry. When versions meet, you compare entry by entry:

Compare V and WMeaningWhat to do
Every entry of V ≤ WV happened before W: W already includes VKeep W, drop V safely
Some entries bigger in V, some in WConcurrent: each saw writes the other didn'tKeep both (called siblings) and merge
✏️ Worked example: the cart from the Dynamo paper, in miniature
  • Replica A takes “add milk”: [A:1]. Then “add bread” on A: [A:2], which supersedes [A:1] (every entry ≥).
  • The network splits. On B, someone adds eggs to the [A:2] version: [A:2, B:1]. On C, someone adds cheese to the same [A:2]: [A:2, C:1].
  • Compare [A:2, B:1, C:0] with [A:2, B:0, C:1]: B is bigger in the first, C in the second. Concurrent. Keep both siblings: {milk, bread, eggs} and {milk, bread, cheese}.
  • The next client to read gets both, merges them (a cart merges by union: {milk, bread, eggs, cheese}) and writes the result through A: [A:3, B:1, C:1], which supersedes both.
  • With last-write-wins, one of eggs or cheese would have vanished, and which one depends on whose clock ran fast.

The cost: the clock grows with the number of replicas that write the key, so Dynamo trimmed the oldest entries once a clock reached about 10. Riak later moved to dotted version vectors, which track the exact write that created each sibling and keep the number of siblings from exploding.

Vector clocks don't care: they never look at the wall clock.

Hybrid logical clocks and TrueTime: keeping real time, safely

Pure counters lose a useful property: “show me the data as of 12:00” means nothing to [A:3, B:1]. Two ways to get time back:

  • Hybrid logical clocks (HLC) (2014): a timestamp is (wall time, small counter). It stays close to the real clock, but it never goes backwards and, like a Lamport clock, a node that receives a later timestamp moves past it. CockroachDB stamps every transaction with an HLC, assumes a maximum clock offset between nodes (500 ms by default), and treats any value stamped within that window as uncertain: the read restarts just above it. A node whose clock drifts past the limit shuts itself down rather than return wrong answers.
  • TrueTime (Spanner, Lesson 2.6): GPS receivers and atomic clocks shrink the uncertainty to a few milliseconds, then each commit waits it out. It's the hardware answer to the same problem. Google's paper adds a telling statistic: in its fleet, bad CPUs were 6 times more likely than bad clocks.

Gossip: how news spreads with no leader

Consensus (Lesson 3.4) needs a leader and majorities. That's right for “who is the primary?”, but far too heavy for “which of these 2,000 nodes are alive, and which key ranges do they own?”. Leaderless systems use gossip (also called epidemic protocols): every second, each node picks a random peer and the two swap what they know. A rumour known by 1 node is known by about 2 after one round, 4 after two, 8 after three…

rounds to reach everyone ≈ log2 N (plus a few) “The number of nodes that know roughly doubles each round, so a cluster 1,000 times bigger needs only about 10 more rounds.” Each node still sends the same few messages per second, however big the cluster gets.
N: number of nodes

Gossip is used for three jobs: membership (who's in the cluster), failure detection (who's stopped answering), and anti-entropy (repairing replicas that drifted apart).

Switch to push with fanout 1 and it's slower (around 18 rounds for 1,024), because late in the epidemic most pushes land on nodes that already know; fanout 2 fixes most of that. Now kill 40% of nodes and add 30% message loss: it still reaches every live node, in about twice the rounds. No leader to lose, no single path to break.

Failure detection: “dead” is a guess

Over a network you can't tell a dead node from a slow one (Lesson 0.2). So every failure detector trades speed against false alarms. Two classic improvements over a fixed timeout:

  • Phi accrual (from a paper by Hayashibara and colleagues; used by Cassandra and Akka): instead of a yes/no timeout, each node learns the normal rhythm of a peer's heartbeats (mean and spread of the gaps) and computes a suspicion level φ (phi) = −log10(probability that a healthy peer would be this late). φ = 8 means a one-in-100-million delay. Cassandra's default threshold is 8. A jittery network automatically gets a more patient detector.
  • SWIM (Scalable Weakly-consistent Infection-style Membership, 2002; the basis of HashiCorp's memberlist, Serf and Consul): each period, a node pings one random peer; if there's no answer it asks k other nodes to try (ping-req), so one bad link doesn't condemn a node. A node that still fails is first marked suspect, and gets time to refute it before being declared dead. Updates ride along on the ping messages, gossip-style, so the load per node stays constant.

Anti-entropy: finding the differences cheaply

Replicas drift: a write missed a replica that was down, a disk lost a file. Comparing two replicas key by key means shipping every key. A Merkle tree (a hash tree) fixes that: each leaf is the hash of a range of keys, each parent the hash of its children, and the root summarizes everything.

✏️ Worked example: one bad key among a million
  • Two replicas hold about 220 ≈ 1,048,576 keys each, in a binary Merkle tree 20 levels deep.
  • Compare the roots: 1 hash each. Different, so compare the two children; only one side differs. Repeat down the tree.
  • That's about 2 hashes per level × 20 levels = 40 hashes exchanged to find the one bad key, instead of a million. If the roots match, the replicas are identical after exchanging a single hash.

Dynamo keeps one Merkle tree per key range; Cassandra builds them during nodetool repair.

🧰 Tools you'll actually use

You rarely implement these yourself; you configure them in Cassandra (gossip, phi accrual, Merkle-tree repair, LWW timestamps), Riak (vector clocks, dotted version vectors, siblings), HashiCorp memberlist, Serf and Consul (SWIM gossip), Akka Cluster (gossip + phi accrual), and CockroachDB (HLC + max offset). On every machine: chrony or ntpd for clock sync, and managed time services such as Amazon Time Sync. And in code: measure durations with a monotonic clock, never with wall time.

# Cassandra: what this node's gossip and failure detector believe
nodetool status          # UN = up/normal, DN = down/normal, per this node's view
nodetool gossipinfo      # each peer's generation, heartbeat version and state
nodetool repair -pr      # anti-entropy: build Merkle trees, stream only mismatched ranges

# cassandra.yaml: suspicion level before marking a peer down (default 8)
phi_convict_threshold: 8

# Consul (Serf/SWIM gossip): cluster membership as this agent sees it
consul members
# a vector clock compare in 6 lines of Python
def compare(v, w):                       # v, w: dicts like {"A": 2, "B": 1}
    nodes = v.keys() | w.keys()
    le = all(v.get(n, 0) <= w.get(n, 0) for n in nodes)
    ge = all(v.get(n, 0) >= w.get(n, 0) for n in nodes)
    return "equal" if le and ge else "before" if le else "after" if ge else "concurrent"

Try it locally: consul agent -dev in one terminal, then consul members in another. In Python, time a request with time.monotonic(), not time.time(); in Go, time.Since(start) uses the monotonic reading.

🚀 Startup vs big tech

Founding engineer (0 → 1)

One primary database gives you one order for free; you don't need any of this yet. Do two things now: run chrony or your cloud's time service everywhere, and measure durations with monotonic clocks. Never use timestamps to decide which of two writes wins, and use database sequences, not wall time, for “latest” logic.

Big tech (1 → 100)

Multi-region, always-writable stores (Cassandra, DynamoDB global tables, Riak-style systems) where the conflict policy is a design decision per table; gossip-based membership in service meshes and databases; tuned failure detectors (Akka's docs suggest raising phi from 8 to 12 on noisy cloud networks); clock-offset monitoring as an alert; and HLC or TrueTime in globally distributed SQL.

🎤 Interview angle

When a design has multiple writable replicas, the interviewer wants to hear:

  • That wall-clock LWW can drop writes, with the reason (clock offset larger than the gap between writes) and when that's acceptable.
  • How you detect conflicts (vector clocks / version vectors) and how you resolve them (merge function, CRDT, or ask the user).
  • How nodes learn about membership and failures without a central registry: gossip, with spread time ≈ log N rounds, and a failure detector tuned for false alarms vs detection speed.
  • How replicas repair drift: anti-entropy with Merkle trees, read repair, hinted handoff.

Common follow-ups: “Two users edit the same document offline. What happens when they reconnect?” “How long until the whole cluster knows a node died?” (detection time + about log₂ N gossip rounds). “Why not just use NTP timestamps?”

🏭 In the real world
Ordering without clocks 📜 History · 1978 Lamport: Time, Clocks, and the Ordering of Events in a Distributed System (PDF)

How: defines “happened before” as a partial order from process order and messages, and logical clocks that satisfy the clock condition: if a happened before b, then C(a) < C(b). Breaking ties by process gives a total order all processes agree on.

Why this method: physical clocks are never perfectly in sync, but cause and effect can be tracked exactly with counters carried on messages.

Vector clocks, gossip and Merkle trees in one system 🏢 Amazon · 2007 Dynamo: Amazon's Highly Available Key-value Store (PDF)

How: vector clocks detect concurrent versions and the application reconciles them (the shopping cart merges); each node gossips membership with a random peer every second; Merkle trees drive anti-entropy. Over 24 hours of shopping-cart traffic, 99.94% of requests saw exactly one version.

Why this method: an “always writable” cart: adding an item must never fail, so conflicts are allowed and resolved later rather than prevented.

Gossip and phi accrual, but last-write-wins 🧰 Open source Apache Cassandra: Dynamo-style architecture

How: every second each node updates its heartbeat and gossips with a random peer; a phi accrual failure detector decides UP or DOWN locally; Merkle-tree repair fixes drift. Unlike Dynamo, conflicts are resolved by last-write-wins on per-column timestamps, and the docs say plainly that correctness depends on clocks, so run NTP.

Why this method: LWW keeps the data model simple (no siblings for apps to merge), at the cost of trusting synchronized clocks.

SWIM membership as a library 🧰 HashiCorp memberlist (Go)

How: based on the 2002 SWIM paper (random probes, indirect ping-req, suspicion, infection-style dissemination), extended with “Lifeguard” to avoid falsely accusing peers when the local node is slow from CPU starvation or network delay. Serf and Consul build on it.

Why this method: constant message load per node and failure detection that doesn't slow down as the cluster grows.

Spanner's guarantees without atomic clocks 🏢 Cockroach Labs · 2022 Living without atomic clocks

How: hybrid logical clocks plus a configured maximum clock offset. A read that meets a value inside its uncertainty window restarts with a higher timestamp; nodes compare offsets and a node beyond the limit terminates itself.

Why this method: runs on ordinary cloud machines with NTP, paying with occasional read restarts instead of special hardware.

🤯 Fun fact · relativity in your database

Lamport says the idea came from physics. Special relativity teaches that observers in different places can disagree about which of two events came first; only events that could causally affect each other have a fixed order. Reading a note on keeping duplicate databases in sync, he recognized the same structure in messages between computers. He also recalls Jim Gray telling him that people called the paper either trivial or brilliant, and he wouldn't argue with either.

🌉 How it connects

This lesson is the leaderless half of Phase 3. Raft (Lesson 3.4) avoids conflicts by electing one leader; Dynamo-style stores accept conflicts and detect them with vector clocks, the AP choice from CAP (Lesson 2.6). Gossip carries the ring membership that consistent hashing needs (Lesson 2.4). Kafka gives you one order per partition because each partition has one leader (Lesson 3.2). Event sourcing (Lesson 3.2b) needs an order per stream, which a version number gives. Chat (Lesson 7.4) needs messages in causal order. In collaborative and offline-first apps, CRDTs push the merge-instead-of-overwrite idea all the way to the data type.

Check yourself

1. A 1,000-node cluster gossips membership: every second, each node exchanges state with one random peer (push-pull). Roughly how long until all nodes know about a new member?
The number of nodes that know roughly doubles each round, so it takes about log₂ 1,000 ≈ 10 rounds, at one round per second. That's why gossip scales: 1,000× more nodes costs only about 10 more rounds, and each node still sends one message per second.
2. Replica X holds a version with vector clock [A:3, B:1, C:0]; replica Y holds [A:2, B:2, C:0]. What should happen when they sync?
X is bigger in A, Y is bigger in B, so neither includes the other: each saw a write the other didn't. Dropping either loses a write. Keep both and merge (union for a cart), then write the merged version with a clock that dominates both.
3. A shopping cart is replicated in three regions and must stay writable during a network partition. Adding an item must never be lost. Which design fits?
LWW can silently drop an add when clocks disagree or writes race. Raft prevents conflicts but the minority side can't write during a partition, which breaks “always writable”. Detecting concurrency and merging is exactly what Dynamo did for carts. The known catch: a removed item can come back after a merge.
📝 TL;DR
  • Clocks drift and jump; NTP offsets of 100+ ms are normal. If writes are closer together than the offset, timestamps order them wrongly, and LWW silently drops one.
  • Lamport clocks: counter, max on receive. Order respects cause, but can't detect concurrency. Vector clocks can: compare entry by entry; neither ≤ the other means conflict: keep siblings, merge.
  • HLC = wall time + counter (CockroachDB); TrueTime = tiny, known uncertainty, then wait (Spanner).
  • Gossip reaches everyone in ≈ log₂ N rounds with constant load per node. Failure detection is a guess: phi accrual adapts to jitter, SWIM adds indirect probes and suspicion.
  • Merkle trees find differences between replicas by exchanging a few dozen hashes instead of every key.
