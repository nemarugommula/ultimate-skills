Phase 3 · Lesson 6

Batch & stream processing (Spark, Flink)

Turning raw events into answers: crunch yesterday's terabytes in one big job (batch), or keep a running answer that updates every second (streaming). Dashboards, recommendations, fraud checks and billing all run on one or both.

🧰 You'll need (quick reminders)
  • Kafka: an ordered, replayable log of events, split into partitions (Lesson 3.2).
  • Sharding by key: spread data over machines with hash(key) mod N (Lesson 2.4).
  • Object storage (S3, GCS): cheap, huge storage for files (Lesson 2.7).
🎯 Hook

In 2004 two Google engineers, Jeffrey Dean and Sanjay Ghemawat, described MapReduce: a way to write a function that runs over thousands of machines without thinking about failures. Within Google, they wrote, hundreds of MapReduce programs had been written and upwards of one thousand MapReduce jobs ran on Google's clusters every day.

They'd also rewritten Google's production indexing system on it, a job taking in more than 20 TB of crawled documents. One phase of it shrank from about 3,800 lines of C++ to about 700. Open-source Hadoop MapReduce, and later Spark, took the same model to everyone else.

Numbers first: why one machine isn't enough

Your app writes 1 TB of logs a day. You want daily stats. One machine reads from disk at about 200 MB/s (typical for a fast disk).

And the same 1 TB/day as a stream is only 1,000,000 MB ÷ 86,400 s ≈ 11.6 MB/s, easy for a few machines, if you process it as it arrives. That's the two styles of data processing:

💡 Big idea Big data processing is split, process in parallel, regroup by key, combine. Batch does it over a finished pile of data; streaming does it continuously over windows of time. The new problem streaming brings is time itself: events arrive late and out of order, so you must decide how long to wait before answering.
🧠 Analogy: counting votes

Batch is election night: lock the doors, split the ballots among many counting tables (map), gather each candidate's piles together (shuffle), add them up (reduce). Streaming is a live tally that updates as ballots arrive. Postal ballots arrive days late, so at some point the officials must say “we're calling this district now”. That cut-off is a watermark: call too early and the tally is wrong; wait too long and nobody gets a result tonight.

MapReduce: the pattern under everything

  1. Map: each worker reads one chunk (a split) and emits key-value pairs: for word count, ("the", 1) for every word.
  2. Shuffle: pairs are sent to reducers by key, using hash(key) mod R, so all "the" pairs meet at one reducer.
  3. Reduce: each reducer combines the values for its keys: ("the", 6).

The framework handles the hard parts. If a worker stops answering the master's pings, its tasks are rerun elsewhere. Near the end, slow machines (“stragglers”) get backup copies of their tasks, and whichever finishes first wins: the paper reports a sort taking 44% longer with backups turned off. A combiner pre-adds counts on each mapper, so less data crosses the network.

Streaming: windows and time

A stream never ends, so “count the clicks” has to become “count the clicks per window”. The three common windows (all built into Flink):

WindowWhat it isExample
TumblingFixed size, no overlap: 12:00–12:10, 12:10–12:20…Orders per minute on a dashboard
Sliding (hopping)Fixed size, overlapping: a 10-minute window every 5 minutes“Logins in the last 10 minutes” for fraud rules
SessionCloses after a gap of inactivity; different length per userOne user's browsing session

Which time? Event time is when it happened (the timestamp on the phone). Processing time is when your server sees it. They differ: a phone in a tunnel uploads its clicks 20 seconds late. Counting by processing time is simple but wrong; counting by event time is right but needs to know when a window is “complete”.

A watermark is the stream processor's estimate of event-time progress: “I don't expect any more events older than t.” A common rule is watermark = largest event time seen − a delay. When the watermark passes a window's end, the window fires. Events that show up after that are late: dropped, sent to a side output, or used to update the result if you allow some lateness.

watermark = max event time seen − delay “The watermark trails the newest event by a fixed delay.” A bigger delay catches more stragglers but makes every result later.
✏️ Worked example: picking a watermark delay

Clicks are counted in 10-second tumbling windows. About 88% of events arrive within 2 s; 12% come from phones that were offline and arrive 5–25 s late.

  • Delay 2 s: the 12:00:00–12:00:10 window fires once an event stamped 12:00:12 or later arrives, roughly 2–4 s after the window ends. Fast, but most offline clicks miss their window.
  • Delay 20 s: nearly every click makes it in, but each count appears about 20 s after its window ends, too slow for a live dashboard, fine for billing.
  • Typical fix: a short delay for the dashboard plus allowed lateness or a nightly batch job that corrects the totals.

Putting it together: lambda, kappa and where the data lands

  • Lambda architecture: run a batch pipeline (correct, slow) and a streaming pipeline (fast, approximate) side by side and merge their results. Downside: the same logic written twice, in two systems.
  • Kappa architecture: streaming only. Keep the raw events in Kafka long enough, and when the logic changes, start a second copy of the job reading from the beginning, then switch over. Jay Kreps proposed it in 2014 as a simpler alternative.
  • Warehouse vs lake: a data warehouse (Snowflake, BigQuery, Redshift) stores cleaned tables for SQL; a data lake stores raw files cheaply in object storage (S3 + Parquet). Table formats like Apache Iceberg and Delta Lake add tables on top of the lake (a “lakehouse”).
  • ETL vs ELT: Extract-Transform-Load cleans data before loading it; Extract-Load-Transform loads raw data first and transforms it inside the warehouse with SQL (often with dbt). ELT is the common modern default because warehouse compute is cheap and raw data stays available.
🧰 Tools you'll actually use

Batch: Apache Spark (Databricks, AWS EMR, Google Dataproc), warehouse SQL with dbt, orchestrated by Airflow or Dagster. Streaming: Apache Flink (Amazon Managed Service for Apache Flink, Confluent), Kafka Streams, Spark Structured Streaming, Google Dataflow (Apache Beam). Word count in PySpark:

from pyspark.sql import SparkSession, functions as F

spark = SparkSession.builder.appName("wordcount").getOrCreate()
lines = spark.read.text("s3://my-logs/2026-10-30/*.txt")            # each file is split across workers
counts = (lines
    .select(F.explode(F.split(F.lower("value"), r"\s+")).alias("word"))   # map
    .groupBy("word").count())                                        # shuffle + reduce
counts.write.mode("overwrite").parquet("s3://my-reports/wordcount/2026-10-30/")

A 10-second tumbling window with a 5-second watermark in Flink SQL:

CREATE TABLE clicks (
  user_id    BIGINT,
  url        STRING,
  event_time TIMESTAMP(3),
  WATERMARK FOR event_time AS event_time - INTERVAL '5' SECOND   -- wait 5 s for stragglers
) WITH ('connector' = 'kafka', 'topic' = 'clicks', ...);

SELECT window_start, window_end, COUNT(*) AS clicks
FROM TUMBLE(TABLE clicks, DESCRIPTOR(event_time), INTERVAL '10' SECONDS)
GROUP BY window_start, window_end;

Try it locally: pip install pyspark and run the word count on a folder of text files (use a local path instead of s3://). For Flink, the official “Flink Operations Playground” runs a small Flink cluster with Kafka using Docker Compose.

⚖️ Trade-offs
✅ Batch is better when…✅ Streaming is better when…
Hourly or daily freshness is fine (reports, billing, ML training sets)The value is in reacting now (fraud, alerts, live pricing)
You need exact, reproducible answers over all the dataApproximate-then-corrected is OK
The team is small: batch jobs are easier to test, rerun and debugYou already have events in Kafka and a team to run long-lived jobs

Streaming costs: always-on jobs, state that must be checkpointed and restored, watermark tuning, and on-call for a pipeline instead of a cron job. Many “real-time” needs are really “every 5 minutes”, which a small batch job does fine.

🚀 Startup vs big tech

Founding engineer (0 → 1)

Copy the production database into a managed warehouse (BigQuery, Snowflake) with an off-the-shelf connector, transform with SQL/dbt, run it hourly or nightly. That's ELT, and it covers analytics for a long time. Add streaming only for one clear real-time need.

Big tech (1 → 100)

A data platform: Kafka as the event backbone, CDC from every database, Flink jobs for real-time features and fraud, Spark on a lakehouse (Iceberg/Delta) for petabyte batch, a scheduler for thousands of jobs, data quality checks, and lineage so you know which dashboard breaks when a column changes.

🎤 Interview angle

Data pipelines show up in “design a metrics dashboard”, “top-K trending” or “ad click counting”. A senior answer covers:

  • Freshness requirement first: seconds (stream), minutes (micro-batch), or daily (batch).
  • Event time vs processing time, the window type, and a watermark delay with a reason.
  • Late and duplicate events: allowed lateness, dedupe by event ID, exactly-once sinks (Lesson 3.3).
  • Reprocessing: how you fix a bug and recompute (replay Kafka, or a batch backfill).
  • Hot keys in the shuffle (one huge key overloads one reducer) and how to split them.

Common follow-ups: “A user's phone was offline for an hour; what happens to their clicks?” “How do you count unique users per day without storing every ID?” (Approximate counting, e.g. HyperLogLog.) “Lambda or kappa?”

🏭 In the real world
The paper that started big data 📜 Google · 2004 MapReduce: Simplified Data Processing on Large Clusters (OSDI)

How: users write map and reduce functions; the library splits input, partitions intermediate keys with hash(key) mod R, reruns tasks from failed workers, and runs backup tasks for stragglers. The paper's experiments ran on a cluster of about 1,800 machines.

Why this method: hiding distribution and failure behind two functions let many engineers write large-scale jobs, including Google's rewritten indexing system.

A faster engine on the same idea 🏢 Databricks · 2014 Spark officially sets a new record in large-scale sorting

How: Spark sorted 100 TB on 206 EC2 machines in 23 minutes. The previous record, set with Hadoop MapReduce, sorted 102.5 TB in 72 minutes on 2,100 machines.

Why this method: the same map-shuffle-reduce model, with a better engine: the post credits a sort-based shuffle, a new Netty-based network module and an external shuffle service. The sort ran on disk, without Spark's in-memory cache.

Event time, windows and watermarks 🧰 Open source Apache Flink: timely stream processing

How: Flink defines a watermark(t) as a declaration that event time has reached t, so no more elements with timestamps ≤ t are expected. Windows (tumbling, sliding, session, global) fire when the watermark passes their end, plus any allowed lateness.

Why this method: counting by event time gives correct answers even when events arrive out of order, and the watermark makes the speed-versus-completeness trade-off an explicit setting.

One pipeline instead of two 🏢 LinkedIn / O'Reilly · 2014 Jay Kreps: Questioning the Lambda Architecture

How: keep the full event log in Kafka; to reprocess, start a new instance of the stream job from the beginning of the log with more parallelism, write to a new output table, then switch readers over.

Why this method: in his words, maintaining code that must produce the same result in two complex distributed systems is as painful as it sounds.

🤯 Fun fact · the accidental Greek letter

“Kappa architecture” was named almost as a joke. In the same 2014 post, Kreps suggested the name while adding that it “may be too simple of an idea to merit a Greek letter”. The name stuck anyway.

Check yourself

1. A nightly job must read 6 TB. Each worker reads about 200 MB/s. Roughly how many workers do you need to finish the reading in about 5 minutes?
One worker: 6,000,000 MB ÷ 200 MB/s = 30,000 s. To get to 300 s you need 30,000 ÷ 300 = 100 workers. Real jobs need a bit more for the shuffle and stragglers.
2. A live dashboard counts purchases per minute by event time. Mobile clients often send events up to 30 s late. Results must appear within 10 s of each minute ending. What's the best design?
Processing time puts late purchases in the wrong minute. A 30 s delay breaks the 10 s requirement. The usual answer is fast-and-approximate first, then corrected: Flink's allowed lateness updates the result, or a batch job reconciles it.
3. In a word-count MapReduce job, one reducer takes 10× longer than the others. What's the most likely cause?
hash(key) mod R sends every pair for a key to the same reducer, so skewed keys create skewed reducers. Combiners help (they pre-add counts on each mapper); for extreme skew, split the hot key into sub-keys and combine afterwards.
📝 TL;DR
  • Batch = bounded data, big parallel jobs, hours-fresh. Stream = unbounded data, windows, seconds-fresh.
  • MapReduce: map → shuffle by hash(key) mod R → reduce, with reruns for failures and backup tasks for stragglers.
  • Windows: tumbling, sliding, session. Use event time; a watermark (max seen − delay) decides when a window fires.
  • Bigger watermark delay = more complete, later results. Combine fast streaming with correction (lateness or batch).
  • Startups: ELT into a warehouse first. Kappa (replayable stream) beats running two codebases (lambda).
