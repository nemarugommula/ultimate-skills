Phase 3 · Lesson 2b

Event sourcing & CQRS

Store every fact that happened (“Deposited $50”, “Withdrew $20”) instead of only the latest state, and build as many read-optimized views from those facts as you need. You get a perfect audit trail and the power to replay history, in exchange for eventual consistency and real extra complexity.

🧰 You'll need (quick reminders)
  • A log is an append-only, ordered list of records; Kafka keeps one that consumers can rewind and replay by offset (Lesson 3.2).
  • CDC (change data capture) turns a database's own change log into a stream of events (Lessons 3.2 and 3.5).
  • Replication lag: a copy that's updated asynchronously can be a little behind, so a read can be stale (Lesson 2.3).
🎯 Hook

In 2011 Martin Fowler described the architecture of LMAX, a retail financial trading platform. All of its business logic, every trade from every customer in every market, ran on one thread that handled 6 million orders per second on commodity hardware, entirely in memory.

How do you trust an in-memory system with people's money? Its current state was entirely derivable from the input events. If the machine died, a replacement replayed the events and arrived at exactly the same state. LMAX ran three such processors, two in the main data center and one at a disaster-recovery site, all fed the same events. That idea, “the events are the truth; state is just a calculation”, is event sourcing.

Numbers first: what does a balance of $130 tell you?

A normal (CRUD: create, read, update, delete) system stores the latest state and overwrites it on every change. An event-sourced system stores the changes themselves:

The storage cost is real but modest: disks are cheap, and facts compress well. The bigger costs are elsewhere: rebuilding state takes work, and the views you read from lag behind the facts. This lesson is about paying those costs wisely.

💡 Big idea Event sourcing: the source of truth is an append-only list of events; current state is derived by replaying them. CQRS (command query responsibility segregation): use one model to change data (commands, which check the rules) and separate models to read it (views shaped for each screen). They're independent ideas that fit together: the events from the write side feed every read side.
🧠 Analogy: a chess score sheet

Serious chess players write down every move. They don't photograph the board after each move; the board is just what you get by replaying the moves. With the score sheet you can set up the position at move 20, find the exact move where the game went wrong, and a commentator can produce a totally different view (an annotated game, a list of captures) from the same sheet. Moves are never erased: a mistake is part of the history. And if the game is 200 moves long, a player might jot down the full position at move 150 so nobody has to replay from move 1. That's a snapshot.

The words you need

TermPlain meaning
CommandA request to change something: Withdraw 80. It can be rejected (“insufficient funds”). Named in the imperative.
EventA fact that already happened: Withdrew 80. It can't be rejected or edited, only followed by more events. Named in the past tense.
Stream / aggregateThe events of one entity (one account, one order), in order. The aggregate is the code that loads them, enforces the rules, and emits new events.
Event storeThe database holding streams: append-only, read by stream, with a version check on append.
Projection / read modelCode that reads events and builds a view for queries (a balance cache, a statement table, a search index), and the view itself.
SnapshotA saved copy of an aggregate's state at version N, so loading means “snapshot + events after N”.
UpcastingConverting an old event format to the current one while reading it, so stored events never change.

The write side: commands in, events out

Every change follows the same four steps. Suppose account-42 has 7 events and a balance of $100:

  1. Load: read the stream and replay it: balance $100, version 7.
  2. Decide: the command Withdraw 80 checks the rule “balance can't go below zero”. $100 ≥ $80, so it's allowed.
  3. Append Withdrew 80 as event 8, only if the stream is still at version 7. This check is called optimistic concurrency (assume no conflict; detect it at write time).
  4. Publish: projections pick up event 8 and update their views.

Step 3 is what protects the rule. Two tellers who both loaded version 7 can't both append event 8: the second append fails, reloads (balance now $20) and its Withdraw 80 is rejected. Without the check, both succeed and the balance becomes −$60. You'll break it yourself below.

✏️ Worked example: what replay costs, and what snapshots save

An account gets about 30 events a month. After 5 years: 30 × 12 × 5 = 1,800 events. Say loading and applying one event costs about 0.02 ms (an illustrative number; measure your own).

  • No snapshots: every command replays 1,800 events = 1,800 × 0.02 = 36 ms before it can even check the balance. At 1,000 commands/s that's 36 CPU-seconds of replay every second.
  • Snapshot every 100 events: load the latest snapshot, then replay at most 99 events (about 50 on average): 50 × 0.02 = 1 ms plus one snapshot read. Roughly 36× less work.
  • The snapshot is disposable: if its format changes or it has a bug, delete it and rebuild from events. The events stay the truth.

Most streams are short (an order has maybe 10 events), and they never need snapshots. Snapshot only the long-lived ones.

The read side: CQRS and projections

Replaying events is fine for one account during a command. It's hopeless for “show me all accounts in London with a balance over $10,000”. So you don't query the events. You build read models: separate stores, each shaped for one kind of query, kept up to date by projections that consume the event stream (often through Kafka, Lesson 3.2):

Read modelShapeTypical storeServes
Balance viewaccount → balanceRedis, a key-value tableThe app's home screen, thousands of reads/s
Statementone row per transaction, by account and datePostgresMonthly statements, exports
Searchdenormalized documentsElasticsearch / OpenSearchSupport staff searching by name or amount
Fraud featuresrolling counts per card per hourA stream processor's state (Lesson 3.6)Real-time scoring

Commands go to the write model, which only has to enforce rules and append events. Queries go to read models, which never enforce anything: they're denormalized copies, rebuilt from events whenever needed. Each side can use a different database, scale separately, and change without touching the other.

You can do CQRS without event sourcing too: a normal database on the write side, with CDC (Lesson 3.2) streaming its changes into read models. Many teams start there.

The price: read models are eventually consistent. Between the append and the projection catching up (milliseconds usually, minutes during an incident), a read can return the old answer. It's exactly replication lag (Lesson 2.3), and the fixes are the same: return the new event's version with the command's response, and have the reader wait until the read model has reached it (read-your-writes), or show the user the result the command already returned.

✏️ Worked example: adding a view nobody planned for

A year after launch, product wants “spending by category per month, for every customer, since day one”.

  • CRUD world: you only have current balances. The history is gone; the report can start from today.
  • Event-sourced world: write a new projection, point it at offset 0 of the log, and let it replay. With 10 M past events at 20,000/s while 500/s keep arriving, it catches up in 10,000,000 ÷ 19,500 ≈ 513 s. Then it simply keeps consuming live events.
  • Same trick for bug fixes: if a projection was wrong, deploy the fixed code to a new read model, backfill it next to the old one, and switch queries over when it's caught up. No migration scripts on the truth.

The hard parts nobody mentions in the talk

  • Events are forever, so their schema is forever. A Deposited event written in 2021 must still be readable in 2031. Make changes additive (new optional fields), put a version on each event type, and use upcasters: small functions that turn Deposited v1 into Deposited v2 while reading, so the stored events never change. Microsoft's pattern guide recommends exactly these three, and warns that a bug fix in code doesn't fix events already written: you may need compensating events.
  • Deleting personal data. “Immutable forever” collides with privacy laws that require erasure. Common answers: keep personal data out of events (store a reference), or encrypt it with a per-person key and delete the key.
  • Rules across entities. Optimistic concurrency protects one stream. “Usernames must be unique across all accounts” spans streams, so you need a separate check (a unique index, a reservation), or accept and fix it after the fact.
  • Projections must be idempotent. They consume at-least-once (Lesson 3.3): store the last event version they applied and skip anything at or below it.
🧰 Tools you'll actually use

Purpose-built event stores: KurrentDB (formerly EventStoreDB; managed as Kurrent Cloud). Frameworks: Axon (Java), Marten (.NET, on Postgres). Or plain Postgres with an append-only table, which many teams use. To feed read models: Kafka, Debezium CDC, or the event store's own subscriptions. The whole idea in Postgres:

CREATE TABLE events (
  stream_id  text  NOT NULL,             -- 'account-42'
  version    int   NOT NULL,             -- 1, 2, 3 … within the stream
  type       text  NOT NULL,             -- 'Deposited', 'Withdrew'
  data       jsonb NOT NULL,             -- {"amount": 50, "v": 2}
  at         timestamptz DEFAULT now(),
  PRIMARY KEY (stream_id, version)    -- two writers at the same version: one fails
);
-- append event 8, which only works if nobody else wrote version 8 first
INSERT INTO events (stream_id, version, type, data)
  VALUES ('account-42', 8, 'Withdrew', '{"amount": 80}');
-- load = latest snapshot (say at version 700) + the events after it
SELECT type, data FROM events
 WHERE stream_id = 'account-42' AND version > 700 ORDER BY version;

The same append with the KurrentDB Node.js client, where streamState is the optimistic-concurrency check:

await client.appendToStream("account-42", jsonEvent({ type: "Withdrew", data: { amount: 80 } }),
  { streamState: 7n });   // fails if the stream isn't at revision 7 any more

Try it locally: docker run --name kurrentdb-node -it -p 2113:2113 docker.kurrent.io/kurrent-latest/kurrentdb:latest --insecure --run-projections=All, then open http://localhost:2113 to browse streams.

⚖️ Trade-offs: when it pays and when it's overkill
✅ Worth it when…❌ Overkill when…
The history is the business: ledgers, payments, order lifecycles, insurance claims, inventoryYou only ever need the current value (a user's settings, a product catalog)
Audit and “why is it in this state?” questions come up weeklyAn audit table or CDC into a warehouse would answer them
Many different read shapes over the same data, and new ones keep arrivingOne database with a few indexes serves every query fine
Reads vastly outnumber writes and need different scalingEvery screen needs the latest data instantly (no lag tolerated)
The team understands the domain and its events wellIt's a prototype or an MVP (minimum viable product) whose model will change monthly

Fowler's own warning on CQRS: “for most systems CQRS adds risky complexity”. Use it in the one part of the system that needs it, not everywhere.

🚀 Startup vs big tech

Founding engineer (0 → 1)

Default to a normal Postgres schema. If money or a legal audit trail is involved, add an append-only ledger_entries or events table next to the current-state table, written in the same transaction. That's 80% of the benefit. Need a new view? A CDC stream or a nightly job. Go full event sourcing only for the one aggregate where history really matters.

Big tech (1 → 100)

Event-sourced cores for ledgers and order lifecycles, events published through Kafka with a schema registry (Lesson 3.2), dozens of read models owned by different teams, backfills as a routine operation, upcasters and versioning rules in the design review checklist, and lag on every projection as a monitored metric (Lesson 6.3).

🎤 Interview angle

Saying “we'll use event sourcing” is a red flag unless you justify it. A senior answer:

  • Names why: audit, temporal queries, or many read shapes. Otherwise proposes a simpler design.
  • Separates commands (validated, can fail) from events (facts), and protects invariants with optimistic concurrency per stream.
  • Explains read-model lag and how the UI copes (read-your-writes via a version token, or showing the command's result).
  • Covers snapshots for long streams, idempotent projections, schema evolution (upcasting) and rebuilds (backfill a new read model, then switch).

Common follow-ups: “How do you delete a user's data?” “A projection had a bug for a week: what do you do?” “How do you enforce a rule that spans two aggregates?”

🏭 In the real world
Event sourcing, named and explained 📜 History · 2005 Martin Fowler: Event Sourcing

How: record every change to an application's state as an event, in order, then rebuild state, query it at any past time, or replay with corrected events. Fowler notes that accounting systems are some of the strongest examples, and that a version control system is a familiar one.

Why this method: audit and “what did it look like then?” questions become a replay instead of an archaeology project.

One thread, all trades, rebuilt from events 🏢 LMAX · 2011 The LMAX Architecture

How: an in-memory business logic processor whose state is entirely derivable from its input events. Three processors (two in the main data center, one for disaster recovery) process the same event stream, so a failover just switches to another one.

Why this method: keeping everything in memory on one thread removed database and locking overhead, and event sourcing made that safe to do with money.

Download limits with a full history 🏢 Netflix · 2017 Scaling Event Sourcing for Netflix Downloads

How: for the downloads feature launched in late 2016, license, device and downloaded-title aggregates are rebuilt from events in an event store; commands go through handlers that check business rules (like download limits) and append new events.

Why this method: the team wanted to look back in time to debug how a member's account reached a state, and to change business rules flexibly; plain current-state storage gave neither.

CQRS from a 1980s principle 📜 History · 2010 Greg Young: CQRS Documents (PDF)

How: Young traces CQRS to Bertrand Meyer's command-query separation (a method either changes state or returns data, never both) and lifts it to architecture: split the object model in two, one for commands and one for queries. The same documents describe event storage and “rolling snapshots” for streams with a million events.

Why this method: the write side can focus on behaviour and rules, while each read side is a cheap, rebuildable, denormalized view.

A database built for events 🧰 Open source KurrentDB docs

How: an append-only log of events grouped into streams, with subscriptions and connectors that push events to other systems, and built-in projections. Appends take an expected stream state for optimistic concurrency.

Why this method: you get stream reads, version checks and subscriptions out of the box instead of building them on a general database.

🤯 Fun fact · accountants got there first

Greg Young's CQRS documents point out that a bank ledger already works this way: the current balance can be read directly or recomputed by adding up every change since the beginning, which is how tired accountants caught their own 3 am arithmetic mistakes. Accountants never erase an entry; they add a correcting one. Event sourcing is double-entry bookkeeping's habit, applied to software.

🌉 How it connects

The event log is the Kafka idea (Lesson 3.2) applied to your own domain: a replayable log that many consumers read. Read models are caches (Lesson 1.3) and replicas (Lesson 2.3) with the same staleness problems. Projections must be idempotent (Lesson 3.3). Publishing events reliably from the write side uses the outbox (Lesson 3.5), and long business processes on top of events are sagas (Lesson 3.5). Stream processors like Flink are projections at scale (Lesson 3.6). The payment system design leans on an append-only ledger (Lesson 7.7). In AI systems, the same habit shows up as logging every prompt, tool call and result, so an agent's run can be replayed and debugged later.

Check yourself

1. An account stream has 2,400 events. A snapshot is saved after every 200th event. What's the most events you'd ever replay to load it?
You load the latest snapshot and replay only what came after it. Just before the next snapshot that's 199 events (about 100 on average), instead of all 2,400. Twelve is the number of snapshots, not the events replayed.
2. Product wants a new “spending by category” dashboard covering the last three years. The system is event-sourced. What's the best plan?
This is the superpower of keeping facts: a view nobody planned for can be built from full history. Backfill time ≈ history ÷ (replay speed − live rate). Replaying on every page view would be far too slow; that's what read models are for.
3. A user deposits $50, the page reloads, and the balance still shows the old amount. A second later it's right. What's happening, and what's the fix?
Read models are eventually consistent, just like async replicas (Lesson 2.3). Read-your-writes with a version token fixes it for the user who wrote, without making every read slow.
📝 TL;DR
  • Event sourcing stores facts in an append-only stream; state = replay (apply each event in order). You get audit, time travel and replay-after-bug-fix.
  • Commands can be rejected; events can't. Protect rules with optimistic concurrency (append only at the expected version).
  • Snapshots cap replay cost at N − 1 events; they're disposable, the events are the truth.
  • CQRS: one write model, many read models built by projections. Read models lag, so plan read-your-writes; new ones can be backfilled from history.
  • Events are forever: version them and upcast. Use all this only where history is the business.
