Phase 3 · Lesson 2

Kafka & event streaming

A queue that never forgets: Kafka stores events in an ordered, replicated log that many readers can replay at their own pace. It's how big companies move data between hundreds of systems in real time.

🧰 You'll need (quick reminders)
  • Queues decouple producers and consumers; acks + redelivery give at-least-once delivery (Lesson 3.1).
  • Replication: keeping copies of data on several machines, with a leader taking writes (Lesson 2.3).
  • Sharding: splitting data by a key so many machines share the load (Lesson 2.4).
🎯 Hook

In 2019 LinkedIn reported running over 100 Kafka clusters with more than 4,000 brokers (Kafka servers), serving 100,000 topics and 7 million partitions. Together they handled more than 7 trillion messages per day. That's about 81 million messages every second, on average.

Kafka was born at LinkedIn to answer one question: how do you get every change, click and event to every system that needs it, without wiring hundreds of systems to each other?

Numbers first: a log you can replay

A classic queue deletes a message once it's acked. Kafka doesn't. It appends every event to a log and keeps it for a set time (the broker default is 168 hours, 7 days). Each reader remembers how far it has read. That small change unlocks a lot:

Queue (SQS, RabbitMQ)Log (Kafka)
After a consumer acksMessage deletedEvent stays until retention expires
Ten teams want the dataTen copies, one queue eachOne copy; ten consumer groups read it independently
Bug found in yesterday's processingData is goneRewind and reprocess from yesterday
OrderingUsually best-effortGuaranteed within a partition
Per-message tricksPer-message ack, delay, DLQ, priorityReads in order; one stuck message blocks its partition
💡 Big idea A log is an append-only, ordered list of records. Writers only add to the end; readers keep a bookmark called an offset (“I've read up to record 1,204”). Because the log is the record of what happened, any number of systems can build their own view of the data by reading it, now or replaying it later.
🧠 Analogy: a ship's logbook, photocopied

The captain writes every event in the logbook, in order, and never tears out pages. The navigator, the cook and the insurance company each keep their own bookmark and read at their own speed. The cook reads only yesterday's pages; the insurer reads the whole thing once a month. If the cook loses track, she flips back. And because the book is split into several volumes (one per deck), several clerks can write at once: that's partitions.

The pieces of Kafka

TermPlain meaning
BrokerOne Kafka server. A cluster has several (3 is a typical minimum).
TopicA named stream of events, like orders or page-views.
PartitionA topic is split into partitions, each its own ordered log on some broker. Partitions are the unit of parallelism.
KeyOptional field on each event (e.g. user ID). Events with the same key go to the same partition, so they stay in order.
OffsetAn event's position in its partition: 0, 1, 2, … Consumers commit offsets to remember progress.
Consumer groupA set of consumers sharing the work. Each partition is read by exactly one member of the group.
LagHow far behind a group is: latest offset minus committed offset. The number to alert on.
RetentionHow long events are kept (time or size), or compaction: keep only the latest event per key.

Partitions: how Kafka scales

One partition is read by one consumer in a group. So the number of partitions is the ceiling on parallelism: a topic with 6 partitions can use at most 6 consumers in one group. A 7th sits idle.

partition = hash(key) mod number of partitions “Hash the key and take the remainder.” Same key, same partition, same order, as long as the number of partitions doesn't change.
key: e.g. user ID or order IDpartitions: fixed when you create the topic (can grow, but keys then move)
✏️ Worked example: sizing a clickstream topic

Your app emits 50,000 events per second at peak, about 1 KB each. One consumer instance can process about 5,000 events per second (it writes to a database).

  • Throughput: 50,000 × 1 KB = 50 MB/s. Per day: 50 MB/s × 86,400 s = 4.32 TB.
  • Replication factor 3 (three copies): 4.32 × 3 = 12.96 TB of disk per day. With 7-day retention: about 91 TB across the cluster.
  • Consumers: 50,000 ÷ 5,000 = 10 at peak, so you need at least 10 partitions. Pick more (say 24) so you can grow without changing the count, because adding partitions later moves keys.

If consumers fall behind by 900,000 events and have 2,000 events/s of spare capacity, catching up takes 900,000 ÷ 2,000 = 450 s. Lag is the early-warning signal.

Things to try: with 2 consumers the group can do 4,000/s against 5,000/s produced, so lag climbs. Add a third and watch it fall. Add consumers until you have more than 6: the extras are idle. Turn on the hot key: one partition gets half of all events and its single consumer can't keep up, no matter how many consumers you add. That's why you pick keys that spread evenly.

Ordering: per partition, by key

Kafka guarantees that a consumer reads one partition's events in exactly the order they were written. It makes no promise across partitions. So if “deposit $100” and “withdraw $80” for the same account land in different partitions, a faster consumer may apply the withdrawal first.

The fix is to give both events the same key (the account ID). Same key → same partition → same order.

Durability: replicas and the in-sync set

Each partition has a leader replica (takes reads and writes) and followers that copy it on other brokers. A common production setting is replication factor 3: three copies. Followers that are caught up form the ISR (in-sync replicas). An event counts as committed once every replica in the ISR has it, and consumers only ever see committed events.

Producer settingWaits forIf the leader dies right after
acks=0NothingEvent may be lost; producer never knows
acks=1The leader's own writeLost if followers hadn't copied it yet
acks=all + min.insync.replicas=2Every in-sync replica, and at least 2 of themSafe: another replica has it and becomes leader

With 3 replicas and min.insync.replicas=2, you can lose one broker and keep accepting writes without losing acknowledged data. Lose two and writes are refused (an error, not silent loss). Current Kafka producers default to acks=all with idempotence turned on, so retries don't write duplicates (more in Lesson 3.3).

Change data capture: the database as a stream

Every database already keeps a log of its changes (Postgres's write-ahead log, MySQL's binlog). Change data capture (CDC) tools like Debezium read that log and publish every committed row change to Kafka, in commit order. Now the search index, the cache, the warehouse and the recommendation service can all stay in sync with the database, without the app writing to each of them (the dangerous “dual write”, Lesson 3.5). Make the log itself your source of truth and you get event sourcing and CQRS (Lesson 3.2b).

A Python consumer with confluent-kafka, committing only after the work is done (at-least-once):

from confluent_kafka import Consumer
c = Consumer({"bootstrap.servers": "localhost:9092", "group.id": "billing",
              "auto.offset.reset": "earliest", "enable.auto.commit": False})
c.subscribe(["orders"])
while True:
    msg = c.poll(1.0)
    if msg is None or msg.error():
        continue
    charge(msg.key(), msg.value())     # must be idempotent: a crash here means a redelivery
    c.commit(message=msg)              # move the bookmark forward

Try it locally: docker run -p 9092:9092 apache/kafka:4.0.2 starts a single broker (the image from the Kafka quickstart). Then run the CLI commands above from the Kafka download.

⚖️ Trade-offs: Kafka or a plain queue?
✅ Reach for Kafka when…❌ A queue is better when…
Many independent consumers need the same eventsYou just need background jobs done once
You need replay: rebuild a search index, fix a bug, backfill a new serviceYou need per-message retries, delays or priorities
Throughput is high (tens of thousands of events per second and up)Volume is low and you don't want to run a cluster
Per-key ordering matters (all events for one account in order)One slow or poison message mustn't block others behind it

Costs: partitions to plan, consumer lag to watch, rebalances that pause consumption, and operational weight (brokers, disks, upgrades). Managed Kafka removes most of the last one, for a price.

🚀 Startup vs big tech

Founding engineer (0 → 1)

You probably don't need Kafka yet. A queue plus Postgres goes a long way. When you do (analytics events, CDC into a warehouse, several consumers), use a managed service, a handful of topics, 6–12 partitions each, keys by entity ID, and alerts on consumer lag.

Big tech (1 → 100)

Kafka becomes the company's central nervous system: hundreds of clusters, schema registries so producers can't break consumers, CDC from every database, tiered storage for long retention, mirroring between regions, and platform teams who own it. LinkedIn runs custom patches for its scale.

🎤 Interview angle

When you put Kafka in a design, a senior answer covers:

  • Topic and key choice: what's the key, does it spread evenly, and what ordering does it guarantee?
  • Partition count from throughput math, with headroom (adding partitions later moves keys).
  • Delivery: commit offsets after processing (at-least-once) + idempotent consumers.
  • Durability: replication factor 3, acks=all, min.insync.replicas=2.
  • Operations: lag alerts, retention vs disk cost, what a rebalance does to latency.

Common follow-ups: “How do you keep a user's events in order?” “What happens when a consumer dies?” “Kafka or SQS here, and why?” “How would you replay last Tuesday?”

🏭 In the real world
The log as the company's data backbone 🏢 LinkedIn · 2019 How LinkedIn customizes Apache Kafka for 7 trillion messages per day

How: 100+ clusters and 4,000+ brokers carry activity tracking, messaging and metrics. Some clusters have over 140 brokers and a million replicas, which pushed LinkedIn to patch controller and broker startup performance.

Why this method: one shared log lets every team publish once and lets any number of systems consume, instead of point-to-point pipelines between every pair.

Every article ever, in one log 🏢 The New York Times · 2017 Publishing with Apache Kafka at The New York Times

How: the “Monolog” topic holds every published asset, totally ordered by publication time. Search indexes and other services are built by reading it from the beginning.

Why this method: to change a search schema you build a new index from the log and throw the old one away, instead of a risky migration.

The essay that explained it 📜 History · 2013 Jay Kreps: The Log (LinkedIn Engineering, archived)

How: Kreps defines a log as “an append-only, totally-ordered sequence of records ordered by time” and shows how databases, replication and data integration are all built on one.

Why this method: if every system consumes the same ordered log, they all end up consistent with each other, which is far simpler than syncing pairs of systems.

Change data capture from the database log 🧰 Open source Debezium architecture

How: connectors run in Kafka Connect; the MySQL connector reads the binlog and the PostgreSQL connector reads a logical replication stream, then send row changes to Kafka topics.

Why this method: the database's own log already has every committed change, in order, so nothing in the application has to remember to publish.

Ordering, retention and replicas 🧰 Open source Apache Kafka: introduction

How: events with the same key go to the same partition, and any consumer reads a partition in the order written; events aren't deleted after consumption; a replication factor of 3 is a common production setting.

Why this method: per-partition ordering is cheap to guarantee and enough for most needs (order per user or per account), while partitions still scale out.

🤯 Fun fact · 170 years in one partition

The New York Times' Monolog contains every asset published since 1851, and it's a single-partition topic, on purpose: one partition means one total order, so a consumer always sees an asset before anything that references it. It fits on one disk because, as the team put it, it's all text written by humans.

Check yourself

1. A topic gets 30,000 events per second. Each consumer handles 4,000 per second. What's the minimum number of partitions so one consumer group can keep up?
30,000 ÷ 4,000 = 7.5, so you need 8 consumers, and since each partition is read by only one consumer in a group, at least 8 partitions. You'd choose more (12 or 16) for growth, since adding partitions later moves keys between partitions.
2. A bank streams account events through Kafka with no key. Sometimes a withdrawal is applied before the deposit that funded it. What's the fix?
Kafka only orders events within a partition. With no key, an account's events spread over partitions read by consumers at different speeds. Keying by account ID sends them all to one partition, read in order by one consumer.
3. Your topic has 6 partitions. Lag is growing, so you scale the consumer group from 6 to 12 instances. What happens?
Partitions are the ceiling on parallelism within a group. To go past 6 consumers, add partitions (and accept that keys move) or make each consumer faster, for example by batching database writes.
📝 TL;DR
  • Kafka is a replicated, partitioned, append-only log. Events stay for the retention period; consumers track offsets and can replay.
  • Partitions = parallelism. One consumer per partition per group; extra consumers idle.
  • Ordering is per partition: key by the entity whose events must stay in order, and pick keys that spread evenly.
  • Durability: replication factor 3, acks=all, min.insync.replicas=2. Watch consumer lag.
  • CDC (Debezium) turns a database's own log into a stream, so other systems stay in sync without dual writes.
