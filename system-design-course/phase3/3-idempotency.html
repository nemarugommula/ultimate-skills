Phase 3 · Lesson 3

Retries, idempotency & exactly-once

Networks fail, so clients retry, and retries cause two classic disasters: storms that keep a sick server down, and duplicates that charge a customer twice. Backoff with jitter fixes the first; idempotency keys fix the second.

🧰 You'll need (quick reminders)
  • Timeouts: if no answer comes in time, the caller gives up; it can't tell “slow” from “lost” (Lesson 0.2).
  • At-least-once delivery: queues and Kafka redeliver after a crash, so duplicates happen (Lessons 3.1 and 3.2).
  • Transactions: several database writes that succeed or fail together (Lesson 2.5).
🎯 Hook

At 2:19 am PDT on Sunday, September 20, 2015, a brief network disruption hit some of DynamoDB's storage servers in AWS's US-East region. They asked an internal metadata service for their membership data, didn't get answers in time, and kept retrying. The retries kept the metadata service overloaded, and DynamoDB's error rate climbed to about 55%.

The overload even blocked the requests needed to add capacity. At 5:06 am the team paused requests to the metadata service, which “decreased retry activity”. Only then could they add capacity. DynamoDB was back to normal error rates at 7:10 am. A brief network glitch became nearly five hours of trouble, and retries were the amplifier.

Numbers first: retries multiply

Retrying is selfish: the client spends more of the server's time to raise its own chance of success. That's fine when failures are rare. It's a disaster when the server is failing because it's overloaded, and it compounds through layers:

1 (just the client)3
3 (client → API → service → database)3 × 3 × 3 = 27

That 243× figure comes from the AWS Builders' Library: if every layer retries independently, a struggling database sees 243 times the load and is unlikely to ever recover. Their fix: retry at one layer only, back off, and add jitter.

💡 Big idea Two rules make retries safe. 1. Retry politely: wait longer after each failure (exponential backoff), add randomness (jitter) so clients don't retry in sync, and cap the number of attempts. 2. Make the operation idempotent: doing it twice has the same effect as doing it once, so a retry can never double-charge, double-send or double-book.
🧠 Analogy: the crowded shop door, and the lift button

Jitter: a shop opens late and 500 people are waiting. If they all push the door at the same second, nobody gets in. If each waits a random few seconds, they flow in. Idempotency: pressing the lift's call button five times doesn't call five lifts. The button is idempotent: once is the same as many. A good payment API should behave like the lift button, not like a vending machine that takes your coin every time.

Backoff and jitter

Exponential backoff doubles the wait after each failure: 100 ms, 200 ms, 400 ms, 800 ms, … up to a cap. But if 2,000 clients all failed at the same moment, they all wait exactly 100 ms and all retry at the same moment again: a synchronized wave. Full jitter picks a random wait between zero and the backoff value, which spreads the wave out.

sleep = random(0, min(cap, base × 2attempt)) “Sleep a random time between zero and the backoff, where the backoff doubles each attempt but never exceeds the cap.” This is “Full Jitter” from the AWS Architecture Blog.
base: first wait (e.g. 100 ms)cap: longest wait (e.g. 20 s)
✏️ Worked example: how long do 8 retries take?

Base 100 ms, cap 20 s, up to 8 retries.

  • Plain backoff waits 0.1 + 0.2 + 0.4 + 0.8 + 1.6 + 3.2 + 6.4 + 12.8 = 25.5 s in total before giving up.
  • With full jitter, each wait is on average half its backoff, so about 12.75 s on average, and different for every client.
  • A user-facing request usually can't wait 25 s. That's why user-facing calls retry only 2–3 times with a short cap, while background jobs can retry for minutes.

The other problem: duplicates

A client sends “charge $50”. The server charges the card and replies, but the reply is lost (a phone switching from Wi-Fi to 4G, a timeout at a load balancer). The client can't tell whether the charge happened. If it retries a plain request, the customer pays $100.

Delivery guaranteeWhat it meansTypical source
At-most-onceNever retried. Maybe lost, never duplicated.Fire-and-forget pub/sub, “no retries”
At-least-onceRetried until acknowledged. Never lost, maybe duplicated.Queues, Kafka consumers, any client that retries
Exactly-once (effectively once)The effect happens once, even though delivery may repeat.At-least-once delivery + idempotent processing

True exactly-once delivery over an unreliable network isn't possible in general: you can't tell a lost reply from a lost request. What systems actually build is at-least-once delivery plus deduplication, which gives an exactly-once effect.

Idempotency keys

The client generates a unique key (a random UUID) for each intended operation and sends it with every attempt. The server stores the key with the result. A retry with the same key gets the stored result back instead of running again.

✏️ Worked example: how many double charges?

A shop takes 1,000,000 payments a day. Suppose (typical numbers) 0.1% of requests time out on the client side and get retried, and in half of those the server had actually charged the card.

  • Retries per day: 1,000,000 × 0.001 = 1,000.
  • Double charges without idempotency: 1,000 × 0.5 = 500 angry customers a day, plus support tickets and refunds.
  • With idempotency keys: 0. Storage cost: 1,000,000 keys a day × ~200 bytes ≈ 200 MB/day, deleted after a day or so.

Notice the race: “check, then insert” works for a slow retry but fails a double-tap, because both requests check before either inserts. The fix is to let the database decide: insert the key with a unique constraint in the same transaction as the charge, and whoever loses the insert returns the stored result.

Idempotency without keys

  • Natural idempotency: “set the status to SHIPPED” is safe to repeat; “add 1 to the counter” isn't. Prefer setting values to incrementing them.
  • Dedupe on message ID for queue and Kafka consumers: store processed message IDs (with a TTL) and skip repeats.
  • Conditional writes: “update the order only if its version is still 7” (optimistic concurrency, Lesson 2.5).
  • Broker features: Kafka's idempotent producer stops duplicate writes from producer retries, and its transactions tie consuming, processing and producing together. SQS FIFO queues drop a re-sent message with the same deduplication ID within a 5-minute window.
🧰 Tools you'll actually use

Retry libraries: tenacity (Python), Resilience4j (Java), Polly (.NET), cockatiel/p-retry (Node); the AWS SDKs have retries built in (with token-bucket retry throttling since 2016). Idempotency: a table in your database, or Redis SET key value NX EX 86400 (set only if it doesn't exist). Stripe's API takes an Idempotency-Key header; Kafka has enable.idempotence. Full-jitter backoff in plain Python:

import random, time

def call_with_retries(fn, attempts=4, base=0.1, cap=5.0):
    for n in range(attempts):
        try:
            return fn()
        except (TimeoutError, ConnectionError):          # retry only errors that might succeed next time
            if n == attempts - 1:
                raise
            time.sleep(random.uniform(0, min(cap, base * 2 ** n)))   # full jitter

The server side: an idempotency table, written in the same transaction as the charge (Postgres):

CREATE TABLE idempotency_keys (
  key          text PRIMARY KEY,            -- the unique constraint does the hard part
  request_hash text NOT NULL,               -- reject the same key with different parameters
  response     jsonb,
  created_at   timestamptz NOT NULL DEFAULT now()
);
BEGIN;
INSERT INTO idempotency_keys (key, request_hash) VALUES ($1, $2)
  ON CONFLICT (key) DO NOTHING;           -- 0 rows inserted? It's a repeat: return the stored response
INSERT INTO charges (customer_id, amount_cents) VALUES ($3, 5000);
UPDATE idempotency_keys SET response = $4 WHERE key = $1;
COMMIT;

Try it: Stripe's test mode accepts curl https://api.stripe.com/v1/charges -u sk_test_… -H "Idempotency-Key: <uuid>" -d amount=2000 -d currency=usd …; send it twice and you get the same charge back. Locally, docker run -p 5432:5432 -e POSTGRES_PASSWORD=dev postgres and run the SQL above twice with the same key.

⚖️ Trade-offs
ChoiceGoodCost / risk
More retry attemptsRides out longer blipsMultiplies load during overload; slower failure for users
Retry at every layerEach layer looks “robust”Multiplicative storms (35 = 243×). Retry at one layer.
Retry budget / token bucketCaps retries to a share of trafficSome requests fail fast instead of retrying

Never retry errors that won't change (400 Bad Request, 403 Forbidden). Retry timeouts, 503s and 429s (respect any Retry-After header), and stop retrying when a circuit breaker opens (Lesson 4.4).

🚀 Startup vs big tech

Founding engineer (0 → 1)

Use your SDK's built-in retries (check that they back off with jitter), retry in one layer, keep user-facing retries to 2–3. Put an idempotency key on every payment, order and signup endpoint from day one: one Postgres table with a unique key. Make every queue consumer safe to run twice.

Big tech (1 → 100)

Shared retry policies in client libraries and the service mesh, retry budgets and token buckets per client, circuit breakers, load shedding on servers, idempotency frameworks used across services (Airbnb's Orpheus), dedupe stores with TTLs, and exactly-once stream processing inside Kafka/Flink pipelines.

🎤 Interview angle

Whenever your design has a retry or a queue, expect “what if this happens twice?”. A senior answer covers:

  • Which operations have side effects, and how each is made idempotent (key, dedupe table, conditional write).
  • Where retries happen (one layer), with exponential backoff + jitter, a cap and a retry budget.
  • The difference between exactly-once delivery (not achievable in general) and exactly-once effect (at-least-once + dedupe).
  • How long you keep keys (e.g. 24 hours) and what happens to a retry after that.

Common follow-ups: “Two retries arrive at the same millisecond: now what?” “Who generates the key, client or server?” “Your consumer crashed after charging but before committing its offset. What happens on restart?”

🏭 In the real world
Idempotency keys on every write 🏢 Stripe · 2017 Designing robust and predictable APIs with idempotency

How: clients send an Idempotency-Key header on POST requests; a retry with the same key is safe. Stripe's docs suggest V4 UUIDs, allow keys up to 255 characters, and (for API v1) prune keys after they're at least 24 hours old.

Why this method: payment requests cross unreliable networks; the key lets clients retry aggressively without ever charging twice.

Full jitter 🏢 AWS · 2015 Exponential Backoff And Jitter (AWS Architecture Blog)

How: Marc Brooker simulated clients competing for a resource and compared no jitter, “Full Jitter”, “Equal Jitter” and “Decorrelated Jitter”. Backoff alone still left clients clustered; jitter spread them and cut the total work.

Why this method: randomness is the cheapest way to break synchronization between thousands of clients that failed at the same moment.

Retry at one layer, with a token bucket 🏢 Amazon Timeouts, retries and backoff with jitter (Builders' Library)

How: retrying at a single point in the stack avoids the 243× multiplication; a local token bucket lets calls retry while tokens last, then at a fixed rate. AWS added that behavior to its SDK in 2016.

Why this method: retries help when failures are rare and hurt when they're caused by overload; a budget keeps them in the first case.

An idempotency framework for payments 🏢 Airbnb · 2019 Avoiding double payments in a distributed payments system

How: a shared library, Orpheus, splits each request into pre-RPC, RPC and post-RPC phases, with database commits around them, and reads and writes idempotency data on the primary database, not a replica.

Why this method: a replica that lags behind could miss a recorded key and allow a duplicate payment; the primary is always current.

Exactly-once inside Kafka 🧰 Open source · 2017 Exactly-once Semantics are Possible: Here's How Kafka Does It

How: Kafka 0.11 added an idempotent producer (the broker drops duplicate writes from retries) and transactions that commit output records and consumer offsets atomically.

Why this method: stream pipelines that read, transform and write Kafka topics can avoid duplicates without every consumer building its own dedupe.

🤯 Fun fact · Orpheus

Airbnb named its idempotency library Orpheus, after the hero of Greek myth who could charm all living things. In their words, they wanted a library that could orchestrate requests across many payment services the same way.

🌉 How it connects

Queues (3.1) and Kafka (3.2) deliver at least once; this lesson makes that safe. Sagas need idempotent steps and compensations (Lesson 3.5). Circuit breakers and load shedding are the server-side partners of client backoff (Lesson 4.4), and rate limits return the 429s that clients should back off from (Lesson 1.5). The payment system design leans on idempotency keys everywhere (Lesson 7.7). In AI systems, LLM APIs return 429 rate-limit errors under load; agents and batch jobs that retry them need the same backoff, jitter and dedupe of tool calls with side effects.

Check yourself

1. A request passes through 4 layers (app → gateway → service → database client), and each layer retries up to 3 attempts. In the worst case, how many calls reach the database for one user action?
Each layer multiplies: 3 × 3 × 3 × 3 = 34 = 81. Retries at each layer multiply, they don't add. That's why the advice is to retry at one layer only.
2. An order API sometimes creates duplicate orders when the mobile app retries after a timeout. What's the best fix?
Removing retries loses orders when the network blips. Backoff and jitter reduce load but don't stop duplicates. An idempotency key makes the retry safe: same key → same order, enforced atomically by the database.
3. 3,000 clients lost their connections at the same moment. They all retry with exponential backoff (100 ms, 200 ms, 400 ms…) but no jitter. What happens?
Same failure time + same schedule = everyone retries at the same instant. Backoff makes the waves rarer but not smaller. Jitter (a random wait up to the backoff) spreads each wave out.
📝 TL;DR
  • Retries are selfish and multiply across layers (3 per layer × 5 layers = 243×). Retry at one layer.
  • Use exponential backoff + full jitter: sleep = random(0, min(cap, base × 2n)), with a cap on attempts or a retry budget.
  • Exactly-once delivery isn't achievable over an unreliable network; exactly-once effect = at-least-once + idempotency.
  • Idempotency keys: client-generated per intended operation, stored atomically (unique constraint) with the result, expired after ~24 h.
